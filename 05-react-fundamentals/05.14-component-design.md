### Single Responsibility
Each component should do one thing well.

```jsx
// ❌ God component - does everything
function UserDashboard() {
  // fetch user, fetch posts, fetch comments
  // render table, handle sorting, handle filtering
  // handle modal state, form state, notification state
  // 500+ lines
}

// ✅ Split into focused components
function UserDashboard() {
  return (
    <DashboardLayout>
      <UserProfile />
      <UserPosts />
      <UserActivity />
    </DashboardLayout>
  );
}
```

### Presentational vs Container (Legacy - still useful concept)

| Presentational | Container |
|----------------|-----------|
| How things look | How things work |
| No data fetching | Fetches data |
| Receives props | Passes props |
| Pure, reusable | Stateful, app-specific |
| `UserCard` | `UserCardContainer` |

**Modern approach:** Use **hooks** to separate data logic from presentation.

```jsx
// ✅ Modern: hook + presentational component
function useUser(id) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${id}`).then(r => r.json()).then(setUser);
  }, [id]);
  return user;
}

function UserCard({ user }) { // pure, easy to test
  return <div>{user.name}</div>;
}

function UserCardContainer({ id }) {
  const user = useUser(id);
  if (!user) return <Spinner />;
  return <UserCard user={user} />;
}
```

### Component Size
- **< 100 lines** - ideal
- **100-200 lines** - acceptable
- **> 300 lines** - split into subcomponents
- **> 500 lines** - definitely refactor

### Props Design
```jsx
// ❌ Boolean prop explosion
<Button
  primary secondary danger loading disabled rounded outlined />
// 7 booleans → 128 combinations!

// ✅ Variant / size / etc.
<Button variant="primary" size="lg" loading />
// 5 variants × 3 sizes × 2 states = 30 well-defined combos
```

### Naming Conventions
```jsx
// ✅ PascalCase for components
function UserProfile() {}

// ✅ handleX for event handlers in the component
function handleClick() {}

// ✅ onX for event handler props
<Button onClick={handleClick} onSelect={handleSelect} />

// ✅ isX / hasX for booleans
<Modal isOpen hasFooter />

// ✅ getX / setX for accessor-style functions
getUserName(), setUser()

// ❌ Avoid
function userProfile() {} // lowercase
<Button click={handleClick} /> // not onX
<Modal open footer /> // ambiguous
```

### File Structure Options

**Feature-based (recommended for large apps):**
```
src/
├── features/
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   └── index.ts
│   └── dashboard/
└── shared/
    ├── components/
    ├── hooks/
    └── utils/
```

**Type-based (simpler apps):**
```
src/
├── components/
├── hooks/
├── pages/
├── utils/
└── api/
```

### Component API Design Principles
1. **Simple API for common cases; escape hatches for complex.**
2. **Sensible defaults.**
3. **Composition over configuration.**
4. **Consistency with HTML/native semantics.**
5. **Accessible by default.**

```jsx
// ✅ Clean API
<Modal isOpen onClose={close} title="Confirm">
  <p>Are you sure?</p>
</Modal>

// ❌ Too many config props
<Modal
  showModal
  handleClose={close}
  headerText="Confirm"
  content="Are you sure?"
  showFooter
  footerConfirmText="OK"
  footerCancelText="Cancel"
  onFooterConfirm={confirm}
/>
```

### Real-World Deal-Breakers
- **God components** → unmaintainable, hard to test.
- **Prop drilling** → 5+ levels of props passed through → use Context or composition.
- **Boolean prop explosion** → use variant enums.
- **Inconsistent naming** → `onClick` vs `onPress` vs `handleClick` - team confusion.
- **Breaking changes without version bump** → changing a public component API breaks consumers.
- **No tests** → refactoring is risky.
- **Over-abstraction** → extracting a component for one-off use adds complexity without value.
