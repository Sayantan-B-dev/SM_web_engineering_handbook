## 13.4 Server State

### Subtopic Tree
- Definition: data owned by the server
- Caching, background refetching, invalidation
- Why it's different from client state
- Tools: TanStack Query, SWR, RTK Query
- Optimistic updates
- Loading/error/data states

### Why Server State Is Different
Server state is:
- **Asynchronous** - fetched over network
- **Shared** - multiple users see the same data
- **Potentially stale** - server may have newer data
- **Remote** - not yours to mutate directly

Treating it like client state (e.g., `useState` + `useEffect`) leads to:
- No caching (refetch on every mount)
- No deduplication (multiple components fetch the same data)
- No background refetching
- No cache invalidation
- Manual loading/error states

### Solution: Specialized Tools
```jsx
// ❌ Manual - misses caching, dedup, invalidation
function User({ id }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${id}`).then(r => r.json()).then(setUser);
  }, [id]);
  return <p>{user?.name}</p>;
}

// ✅ TanStack Query - cache, dedup, background refetch
function User({ id }) {
  const { data, isLoading } = useQuery({
    queryKey: ['user', id],
    queryFn: () => fetch(`/api/users/${id}`).then(r => r.json()),
  });
  if (isLoading) return <Spinner />;
  return <p>{data.name}</p>;
}
```

### Real-World Deal-Breakers
- **Fetching server data with `useEffect` + `useState`** → no caching, duplicated requests, manual state management.
- **Storing server data in Redux** → you rebuild React Query poorly. Use React Query for server, Redux for client.
- **No cache invalidation strategy** → stale data persists after mutation.
- **Not handling loading/error states** → blank screens, unhandled crashes.
