## 13.1 Local State

### Subtopic Tree
- Definition: state owned by a single component
- `useState` / `useReducer`

### What Local State Is
State that is **only used by one component and its direct children** via props. It doesn't need to be shared, persisted, or synchronized with other parts of the app.

```jsx
function SearchBox() {
  const [query, setQuery] = useState(''); // local state
  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}
```

### When Local State Is Enough
- Toggle (open/closed, dark/light)
- Form draft (before submit)
- Input value
- Hover/focus states
- Animation state
- UI-only state (accordion, tabs)

### Co-Location Principle
**Keep state as close as possible to where it's used.** If only one component needs the state, don't lift it. If only one branch needs it, don't put it at the root.

```jsx
// ❌ State too high - App re-renders on every keystroke
function App() {
  const [search, setSearch] = useState('');
  return (
    <>
      <SearchInput value={search} onChange={setSearch} />
      <ExpensiveTree />  {/* re-renders unnecessarily */}
    </>
  );
}

// ✅ State co-located
function App() {
  return (
    <>
      <SearchBox />
      <ExpensiveTree />  {/* never re-renders on search */}
    </>
  );
}
```

### Re-Mount Resets State
```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}

// Changing key unmounts and remounts → state resets
<Counter key={userId} />
```

### Real-World Deal-Breakers
- **State lifted too high** → entire subtree re-renders on unrelated changes.
- **Storing props in local state** → props change but state doesn't update. Use props directly.
- **Not resetting state when identity changes** → stale data (use `key` prop).
- **Using context for local UI state** → unnecessary overhead; keep it local.
