## 15.7 Route Boundaries

### Subtopic Tree
- Error boundaries (`ErrorBoundary` export)
- Nested error boundaries (closest boundary wins)
- `useRouteError` hook
- `isRouteErrorResponse` type guard
- Throwing `data()` with status codes
- Root error boundary (required)
- `HydrateFallback` (loading boundary)
- Pending states (`useNavigation`)

### Root Error Boundary (Required)
All applications should at minimum export a root error boundary. This one handles three main cases: thrown `data()` with a status code, instances of `Error`, and randomly thrown values.

```tsx
import { useRouteError, isRouteErrorResponse } from 'react-router';

export function ErrorBoundary() {
  const error = useRouteError();

  if (isRouteErrorResponse(error)) {
    return (
      <>
        <h1>{error.status} {error.statusText}</h1>
        <p>{error.data}</p>
      </>
    );
  } else if (error instanceof Error) {
    return (
      <div>
        <h1>Error</h1>
        <p>{error.message}</p>
        <pre>{error.stack}</pre>
      </div>
    );
  } else {
    return <h1>Unknown Error</h1>;
  }
}
```

### Nested Error Boundaries
When an error is thrown, the **"closest error boundary"** is rendered. Consider nested routes:

```jsx
route("/app", "app.tsx", [           // ✅ has error boundary
  route("invoices", "invoices.tsx", [ // ❌ no error boundary
    route("invoices/:id", "invoice-page.tsx", [ // ✅ has error boundary
      route("payments", "payments.tsx"),        // ❌ no error boundary
    ]),
  ]),
]);
```

| Error origin | Rendered boundary |
|-------------|-------------------|
| `app.tsx` | `app.tsx` |
| `invoices.tsx` | `app.tsx` |
| `invoice-page.tsx` | `invoice-page.tsx` |
| `payments.tsx` | `invoice-page.tsx` |

### Throwing `data()` in Loaders
```tsx
export async function loader({ params }) {
  let record = await fakeDb.getRecord(params.id);
  if (!record) {
    throw data('Record Not Found', { status: 404 });
  }
  return record;
}
```

### Production Error Sanitization
In production mode, any errors that happen on the server are **automatically sanitized** before being sent to the browser to prevent leaking sensitive server information (like stack traces). The original error is untouched on the server.

### Real-World Deal-Breakers
- **No root error boundary** → unhandled errors render a blank page.
- **Throwing errors for control flow** → error boundaries are for unintentional errors, not form validation.
- **Missing nested boundaries** → one route's error crashes the entire app.
- **`error.data` in production** → sanitized; use `throw data()` for user-facing messages.
