## 14.3 Mutations

### Subtopic Tree
- `useMutation` hook
- `mutationFn`
- `mutate` vs `mutateAsync`
- Lifecycle callbacks (`onMutate`, `onSuccess`, `onError`, `onSettled`)
- Mutation states (`isPending`, `isError`, `isSuccess`)
- `reset()`
- Side effects (invalidate queries, update cache)

### Basic Mutation
```tsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

function AddTodo() {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: (newTodo: string) =>
      fetch('/api/todos', { method: 'POST', body: JSON.stringify({ text: newTodo }) }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['todos'] });
    },
  });

  return (
    <button onClick={() => mutation.mutate('New todo')} disabled={mutation.isPending}>
      {mutation.isPending ? 'Adding...' : 'Add'}
    </button>
  );
}
```

### `mutate` vs `mutateAsync`
- `mutate` - fire-and-forget, doesn't return a promise.
- `mutateAsync` - returns a promise; use when you need to `await` or chain.

```tsx
// mutate - no await
mutation.mutate(data);

// mutateAsync - await
const result = await mutation.mutateAsync(data);
```

### Mutation Key (v5)
```tsx
useMutation({
  mutationKey: ['addTodo'],
  mutationFn: addTodo,
});
```
Mutation keys are optional but useful for filtering mutations with `useIsMutating`.

### Real-World Deal-Breakers
- **Using `mutateAsync` without try/catch** → unhandled promise rejection. `mutate` handles errors via callbacks; `mutateAsync` throws.
- **Invalidating queries in `onSuccess` only** → on error, cache may be stale. Prefer `onSettled` for invalidation.
- **Not resetting mutation state** → error state persists after a successful retry. Call `mutation.reset()`.
- **Assuming mutation state is shared** → each `useMutation` call has its own state.
