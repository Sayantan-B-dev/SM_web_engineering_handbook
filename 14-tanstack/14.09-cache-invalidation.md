## 14.9 Cache Invalidation

### Subtopic Tree
- `queryClient.invalidateQueries`
- Prefix matching (default)
- `exact: true` for exact match
- `refetchType` (`active`, `inactive`, `all`, `none`)
- `refetchQueries` (force immediate refetch)
- `resetQueries` (reset to initial state)
- Invalidation after mutations
- Real-time invalidation (WebSocket)

### How Invalidation Works
When a query is invalidated with `invalidateQueries`, two things happen: it is **marked as stale**, and **active queries refetch in the background** by default.

```tsx
// Invalidate all queries starting with ['todos']
queryClient.invalidateQueries({ queryKey: ['todos'] });

// Invalidate only the exact key
queryClient.invalidateQueries({ queryKey: ['todos', 1], exact: true });

// Invalidate but don't refetch immediately
queryClient.invalidateQueries({ queryKey: ['todos'], refetchType: 'none' });
```

### `refetchType` Options

| Value | Behavior |
|-------|----------|
| `'active'` (default) | Refetch only active queries |
| `'inactive'` | Refetch only inactive queries |
| `'all'` | Refetch all matching |
| `'none'` | Just mark stale, don't refetch |

### Real-World Deal-Breakers
- **`invalidateQueries` with no key** → invalidates **all** queries. Always scope with a key.
- **Assuming inactive queries refetch by default** → they don't; use `refetchType: 'all'` if needed.
- **`refetchQueries` instead of `invalidateQueries`** → forces immediate refetch even if data is fresh; wasteful. Use invalidation for normal flows.
- **No invalidation after mutation** → users see stale data.
