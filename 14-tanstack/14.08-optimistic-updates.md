## 14.8 Optimistic Updates

### Subtopic Tree
- `onMutate` callback
- Cancel outgoing queries
- Snapshot previous data
- Write optimistic data
- Rollback on error (`onError` with context)
- Settle with invalidation (`onSettled`)
- The canonical four-step pattern
- `useMutation` returned variables approach

### The Canonical Pattern (v5)
```tsx
const mutation = useMutation({
  mutationFn: updateTodo,

  onMutate: async (newTodo) => {
    // 1. Cancel outgoing refetches
    await queryClient.cancelQueries({ queryKey: ['todos'] });

    // 2. Snapshot previous value
    const previousTodos = queryClient.getQueryData(['todos']);

    // 3. Optimistically update
    queryClient.setQueryData(['todos'], (old) =>
      old.map(t => t.id === newTodo.id ? newTodo : t)
    );

    // 4. Return context for rollback
    return { previousTodos };
  },

  onError: (err, newTodo, context) => {
    // Rollback on error
    queryClient.setQueryData(['todos'], context.previousTodos);
  },

  onSettled: () => {
    // Invalidate to sync with server (even on success)
    queryClient.invalidateQueries({ queryKey: ['todos'] });
  },
});
```

The four steps: **cancel → snapshot → write → settle with invalidate**. Invalidation in `onSettled` (not `onSuccess`) ensures eventual consistency even after a 500.

### Real-World Deal-Breakers
- **Not cancelling outgoing queries in `onMutate`** → race condition: refetch overwrites optimistic update.
- **Not returning context from `onMutate`** → no rollback capability on error.
- **Invalidating in `onSuccess` only** → on error, cache stays optimistic (wrong). Use `onSettled`.
- **Mutating cache directly without snapshot** → can't rollback; UI stuck in wrong state.
- **Optimistic update for operations that can't fail gracefully** → server assigns IDs, timestamps, etc.; optimistic data may be wrong.
