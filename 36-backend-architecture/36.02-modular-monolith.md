## 36.2 Modular Monolith

### Subtopic Tree
- Definition: single deployable, multiple bounded internal modules
- Module boundaries (public API + private internals)
- Dependency direction (acyclic)
- Communication via explicit interfaces
- Build-tool enforcement (Go workspaces, Rust workspaces, Java modules, Python namespace packages)
- The 2026 default architecture
- Migration path: modular monolith → microservices

### What a Modular Monolith Is
A modular monolith runs as a **single deployment unit** but is organized internally into **clear modules with strong boundaries**. It gives teams most of the structural benefits of microservices at a fraction of the operational cost. The system often deploys as a single unit and is usually debugged from one place, while keeping the code comprehensible without a service map.

### The Module Structure
```text
Single Deployment Unit
├── module: auth      (own tables: users, sessions)
├── module: posts     (own tables: posts, comments)
├── module: billing   (own tables: invoices, payments)
└── module: shared    (utils, types, UI kit)
```

Each module has:
- A **public API** (`index.ts` with explicit exports)
- **Private internals** (components, hooks, helpers)
- **Own data** (tables, schema)
- No direct imports from other modules' internals

### Why It's the 2026 Default
The most popular alternative in 2026 is the modular monolith. It runs as a single deployment unit but is organized internally into clear modules with strong boundaries. Teams get the operational simplicity of a single deployment without giving up code organization, modularity, or testability.

Languages and frameworks have made the pattern easier. Go workspaces, Rust workspaces, modern Java modules, and Python namespace packages all support clean internal boundaries. Build tools enforce module boundaries at compile time. The result is monoliths that feel like microservices to write but deploy like monoliths.

### Real-World Example: Shopify
Shopify has run one of the largest Rails codebases in production this way for years. When starting out, they ruled out microservices and chose modular architecture instead to keep the code in one place while enforcing strict boundaries between components.

### Migration to Microservices (When the Time Comes)
When a specific module's traffic grows to the point where it needs independent scaling, extract it as a service. Refactoring a good monolith into microservices is easier than fixing bad microservices, which is expensive and painful.

### Deeper Explanation: The Default That Earns Extraction

A modular monolith keeps one deployable but enforces internal boundaries: each module owns its schema, exposes its interface, and communicates with others through explicit calls or in-process events. This is the most cost-effective architecture for most products because it delivers the consistency and operational simplicity of a monolith while making future extraction a deployment decision rather than a rewrite.

Making it real requires enforcement, not intention:

- **Schema ownership** â€” one schema (or table prefix) per module, with no cross-module foreign keys; reference by id and query through the owning module.
- **Interface layer** â€” a typed public API per module; internal files are not importable (lint rules, path restrictions, or separate packages).
- **Events for side effects** â€” in-process events for cross-module reactions, so the producer does not know its consumers.
- **Tests per module** plus a few integration tests across modules.

### Additional Pitfalls
- **Boundaries that exist only in the README.** Without lint or package boundaries, the first deadline erases them.
- **Cross-module joins for convenience.** They recreate coupling; define a read model instead.
- **Module-to-module cycles.** They indicate a missing domain owner; untangle the direction of dependency.
- **Synchronous chains across modules.** A call chain of five modules makes latency and failure hard to reason about.

### Real-World Deal-Breakers
- **No enforcement** → module boundaries decay within weeks. Enforce with lint rules and CI checks.
- **Modules reaching into each other's tables** → you have a distributed monolith (worst of both). Each module owns its data.
- **Premature extraction** → extracting modules before the domain stabilizes freezes wrong boundaries.
- **Over-reuse** → extracting all shared logic into a common base service creates a single point of failure. Over-reuse leads to all services depending on the base service, so a change requires regression testing across the entire chain.
