## 36.8 API Gateway

### Subtopic Tree
- North-south traffic (client to backend)
- Request routing
- Authentication (JWT, OAuth 2.0, API keys)
- Rate limiting and quotas
- Request/response transformation
- SSL termination
- Gateway aggregation
- Gateway offloading
- When API gateway ≠ service mesh

### What an API Gateway Does
An API gateway sits on the request path between API clients and backend services. It matches requests to routes, applies configured policies, selects an upstream, and returns the response to the client. Common gateway responsibilities include authenticating API consumers (API keys, JWT, OAuth 2.0), applying rate limits and quotas, transforming requests and responses, providing a stable API endpoint while backend locations change, and emitting metrics, logs, or traces.

### Gateway Patterns

| Pattern | Purpose |
|---------|---------|
| **Gateway Routing** | Route requests to different services based on path |
| **Gateway Aggregation** | Combine multiple requests into one |
| **Gateway Offloading** | Centralize SSL, auth, rate limiting |
| **BFF (Backends for Frontends)** | Separate backend per client type |

---

### Deeper Explanation: The Edge Where Cross-Cutting Concerns Live

An API gateway centralises what every service would otherwise reimplement: authentication, rate limiting, request routing, header policy, request/response transformation, caching, and observability. Its value is consistency at the edge; its risk is becoming a distributed monolith with business logic inside.

Good gateway responsibilities: TLS termination, auth token verification (or delegating to an authorisation service), CORS and security headers, rate limits per key, routing to services, request logging and tracing, and response caching for public reads. Bad ones: domain logic, per-endpoint special cases, and complex orchestration that belongs in a service or a workflow engine. Keep the domain in services; keep the gateway to policy.

### Additional Pitfalls
- **Business logic in the gateway.** It becomes the deployment bottleneck for every change.
- **A single point of failure without redundancy.** The gateway must be as available as the product.
- **Auth only at the gateway.** Services still need per-resource authorisation.
- **Header and body transformation sprawl.** Rules accumulate until no one can predict a request's shape.
- **No per-route SLOs.** Without them, gateway latency hides which route is degrading.

### Real-World Deal-Breakers
- **No API gateway** → every client hits backend services directly. No central auth, rate limiting, or routing.
- **Gateway as a service mesh** → API gateway handles north-south (client to backend); service mesh handles east-west (service to service). They are complementary, not substitutes.
- **No rate limiting at gateway** → backend services are exposed to abuse.
