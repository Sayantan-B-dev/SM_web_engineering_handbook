### What Event-Driven Architecture Is
Event-driven architecture replaces synchronous request chains with **asynchronous event publishing**. Systems communicate through events - immutable records of state changes or significant occurrences - rather than through direct, synchronous requests.

### The Three Patterns People Conflate
"Event-driven" hides three distinct patterns that people routinely conflate:

| Pattern | What it means | Consumer behavior |
|---------|--------------|-------------------|
| **Event Notification** | Thin signal, consumer calls back | Consumer receives signal, fetches data |
| **Event-Carried State Transfer** | Fat event, consumer is self-sufficient | Consumer receives all data in the event |
| **Event Sourcing** | Events are the database | State is derived from event log |

### The Transactional Outbox Pattern
Dual-writes fail silently **1-5% of the time** in production. A service writes to its database and then publishes to SNS or EventBridge in the same request; the publish step fails; the event is gone. A month in, the team is debugging missing inventory updates with no audit trail.

**The fix:** Use the transactional outbox pattern. Write to your service's database in a single transaction, then let EventBridge Pipes pull from DynamoDB Streams or DMS-CDC and fan out to a dedicated EventBridge custom bus.

### The Four Patterns That Decide Success or Failure
The four patterns that decide whether EDA succeeds or collapses are **sagas, transactional outbox, schema evolution, and idempotency**.

### When EDA Is Right
Asynchronous workloads - background jobs, notifications, data pipelines, high-throughput processing - are where event-driven architecture earns its place. It allows both sides to move without waiting on each other.

### When EDA Is Wrong
The failure modes tend to be quiet. Backlogs can accumulate without obvious symptoms. Retry logic introduces ordering edge cases. A consumer falling behind is invisible until it's catastrophic.

---

### Deeper Explanation: Events Are For Reaction, Not For Queries

An event is a fact that already happened; an event-driven architecture lets many consumers react without the producer knowing them. The benefits are decoupling and extensibility ("add a consumer, change nothing else"); the costs are ordering, duplication, schema evolution, and debugging a flow that no longer exists in one place.

The practices that make it work: **idempotent consumers** (every event has an id, every handler can safely re-run), **at-least-once delivery assumed** (dedupe by id), **schema versioning with backward-compatible changes**, **event envelopes carrying metadata** (id, type, version, occurredAt, correlationId, tenant), **dead-letter queues** with visibility, and **outbox publishing** so a state change and its event are atomic.

Two families to distinguish: **events as notifications** ("order_created: here is the id", consumer fetches details) versus **events as state transfer** ("order_created: here is the whole order"). Notifications are smaller and safer for schema evolution; state transfer avoids read-back but couples payload shape to consumers.

### Additional Pitfalls
- **Events without ids.** Deduplication becomes impossible; retries double-apply effects.
- **Publishing inside a transaction without an outbox.** The event is lost when the transaction commits after a crash, or published before it.
- **Consumers that require strict ordering globally.** Partition keys give per-entity ordering only; design accordingly.
- **No dead-letter queue.** Poison messages block a partition forever.
- **Events treated as a query API.** Replaying to answer a question is a database problem.

### Real-World Deal-Breakers
- **No transactional outbox** → dual-writes fail silently 1-5% of the time. Use the outbox pattern.
- **No schema evolution** → undocumented event shapes accumulate. "Six months in, the bus carries a hundred undocumented event shapes".
- **No idempotency** → retried events create duplicates.
- **No Saga for workflows** → multi-step workflows require choreography across services. Use Step Functions or Saga.
- **No observability** → "required for debugging the failure modes that event-driven systems make subtle".
- **Event sourcing for CRUD** → events are the database, but if you just need CRUD, you're over-engineering.
