### What a Service Mesh Does
A service mesh is an **infrastructure layer for workload-to-workload communication**. A mesh control plane distributes configuration and identity information to a data plane that processes service traffic. Common service mesh responsibilities include assigning and verifying workload identities, encrypting service-to-service traffic with mTLS, applying traffic policies between workloads, collecting telemetry for calls inside the mesh, and controlling service discovery, routing, retries, and failover within the mesh.

### API Gateway vs Service Mesh

| Dimension | API Gateway | Service Mesh |
|-----------|------------|-------------|
| **Traffic scope** | North-south (client to backend) | East-west (service to service) |
| **Identity model** | Client credentials, tokens, API keys | Workload identity, mTLS |
| **Policy subject** | API client, consumer, route | Workload, service, namespace |
| **Deployment** | Shared/dedicated gateway instances | Control plane + sidecar proxies |
| **Main users** | API, platform, security teams | Platform, infrastructure teams |

---

### Deeper Explanation: When A Mesh Earns Its Complexity

A service mesh moves cross-cutting network concerns (mTLS, retries, timeouts, circuit breaking, traffic shifting, telemetry) into sidecars or per-node proxies, so individual services stop implementing them. The upside is uniform, language-agnostic policy and excellent telemetry. The cost is an entire extra infrastructure layer with its own failure modes and expertise requirement.

It is worth deploying when you have many services and polyglot teams, and when uniform mTLS plus fine-grained traffic control (canaries, mirroring, fault injection) are actually needed. For a single-team product with a handful of services, a gateway plus library-level resilience usually delivers the same value at a fraction of the operational cost.

### Additional Pitfalls
- **Adopting a mesh for its dashboard.** The telemetry is impressive; the operational load is real.
- **Timeouts configured in both service and mesh.** Conflicting values create confusing behaviour.
- **Mesh-level retries without idempotency.** Retrying a non-idempotent call duplicates effects.
- **No capacity planning for sidecars.** Memory and CPU overhead per pod adds up.
- **Assuming the mesh covers everything.** External dependencies still need explicit policy.

### Real-World Deal-Breakers
- **Service mesh for north-south** → service mesh handles east-west. Use an API gateway for client traffic.
- **No mTLS** → service-to-service traffic is unencrypted. A service mesh provides mTLS by default.
- **No workload identity** → you can't verify which service is calling.
- **Service mesh without platform team** → service mesh adds operational complexity. Requires dedicated platform/SRE team.
