### The Saga Pattern
A saga is a sequence of local transactions where each service performs its operation and triggers the next step. If a step fails, the saga runs **compensating transactions** to undo the preceding changes. This replaces distributed transactions, which are often impractical in a microservices architecture.

**Orchestration vs Choreography:**
- **Orchestration** - a central orchestrator (e.g., Step Functions) coordinates the saga.
- **Choreography** - each service decides when and how to process, based on events. Reduces coupling but makes the workflow harder to trace.

### The Circuit Breaker Pattern
```text
Closed → Service calls succeed normally
   ↓ (failures exceed threshold)
Open → Service calls fail immediately (fail fast)
   ↓ (after timeout)
Half-Open → Allow limited calls to test recovery
   ↓ (success)
Closed (recovered)
```

### Deeper Explanation: The Fallacies In Practice

The classic fallacies (the network is reliable, latency is zero, bandwidth is infinite, topology is stable, there is one admin) are not academic â€” each has a concrete symptom and mitigation:

| Fallacy | Symptom | Mitigation |
|---|---|---|
| Network is reliable | Silent message loss | Retries + idempotency + acknowledgement |
| Latency is zero | Timeouts under load cascade | Budgets per hop, async where possible |
| Bandwidth is infinite | Oversized payloads slow everything | Paginate, project columns, compress |
| Topology is stable | Stale DNS/connections | Connection pools with health checks, retry with backoff |
| One admin | Conflicting configuration changes | Infrastructure as code, review, drift detection |

Then the harder layer: **partial failure**. A dependency being slow is worse than being down, because slow dependencies consume your concurrency. That is why timeouts, circuit breakers, bulkheads (separate pools per dependency), and load shedding are the core reliability toolkit â€” with observability to know which dependency is degrading.

### Additional Pitfalls
- **No timeouts.** Requests wait forever and occupy connections until the service collapses.
- **Retries without jitter.** Synchronised retries create a thundering herd.
- **No circuit breaker.** A failing dependency keeps taking traffic and every request pays the timeout.
- **Shared thread/connection pools across dependencies.** One slow dependency starves the rest.
- **Assuming clocks agree.** Ordering and expiry need logical time or server-issued timestamps.

### Real-World Deal-Breakers
- **No circuit breaker** → one failing service cascades to the entire system.
- **No bulkhead** → one workload consumes all connection pool resources.
- **No idempotency** → retries create duplicate side effects.
- **No distributed tracing** → you can't debug across service boundaries.
- **Distributed transactions** → impractical. Use Saga.
- **No retry with backoff** → transient failures become permanent failures.
- **No leader election** → multiple writers corrupt data.
