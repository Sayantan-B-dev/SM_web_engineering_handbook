## 36.6 Background Jobs

### Subtopic Tree
- Job queues vs workflow engines
- BullMQ (Node.js, Redis-backed)

- Idempotency

### The Distinction

| Job Queue (BullMQ, Celery, Sidekiq) | Workflow Engine (Temporal, Inngest) |
|--------------------------------------|-------------------------------------|
| Execute discrete tasks asynchronously | Orchestrate multi-step processes |
| Stateless, fire-and-forget | Durable state across steps |
| Limited retry semantics | Automatic retries, compensation |
| No long-running state | Run for days, weeks, or years |

### BullMQ
BullMQ is a **Redis-backed job queue for Node.js**. It provides high-performance, fine-grained control over job processing. It handles **95% of background job use cases** with automatic retries, delayed execution, and concurrency control.

```typescript
import { Queue, Worker } from 'bullmq';

const queue = new Queue('email', { connection: redis });

// Add a job
await queue.add('send-welcome', { userId: '123' }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 1000 },
});

// Process jobs
const worker = new Worker('email', async (job) => {
  await sendWelcomeEmail(job.data.userId);
}, { connection: redis });
```

### Temporal
Temporal is a **workflow orchestration platform** for complex, polyglot, long-running workflows with strong guarantees. It's the right choice when your workflow needs to **wait for a human action (days or weeks)**, requires durable state across restarts, or has complex recovery guarantees.

### When to Use Which
- **BullMQ** → simple, stateless background jobs. Automatic retries, delayed execution, concurrency control.
- **Inngest** → event-driven SaaS for serverless environments. Developer-friendly, native integrations.
- **Temporal** → complex, polyglot, long-running workflows with strong guarantees. Use when BullMQ or Inngest cannot express what you need.

### Deeper Explanation: The Shape Of A Reliable Job

Background jobs turn latency out of the request path, but reliability is a design property: a job must be **idempotent**, **observable**, **retryable with backoff**, **bounded in runtime**, and **safe under concurrency**. The minimal reliable pattern:

1. Enqueue with a unique job id and a payload reference (not a giant blob).
2. Claim with a lock/lease so two workers do not process the same job.
3. Execute with a timeout and checkpoint progress for long work.
4. Record the outcome (success/failure plus attempt count and duration).
5. Retry with exponential backoff and jitter up to a cap; then dead-letter and alert.
6. Expose status to the user when the job is user-visible ("export ready" / "export failed, retry").

Frontend-relevant jobs: exports, image/video processing, email/push fan-out, webhook delivery, search indexing, report generation, and AI batch tasks.

### Additional Pitfalls
- **Jobs that assume single execution.** Duplicates are the norm under retries and leases.
- **No progress reporting for long jobs.** Users retry and create duplicates.
- **Long transactions or locks inside jobs.** They block interactive traffic.
- **No concurrency limits per type.** A burst of imports can starve everything else.
- **Silent failures.** Without alerting on dead letters, jobs disappear quietly.

### Real-World Deal-Breakers
- **Cron jobs for complex workflows** → stateless, manual intervention on failure. Use a workflow engine.
- **No retry strategy** → transient failures cause permanent job loss.
- **No idempotency** → retried jobs create duplicate side effects.
- **No DLQ for failed jobs** → failed jobs disappear silently.
- **BullMQ for multi-day workflows** → BullMQ is for discrete tasks. Use Temporal for long-running stateful workflows.
