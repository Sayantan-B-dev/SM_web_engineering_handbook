## Form Validation

### Subtopic Tree
- Validation timing: `onSubmit`, `onBlur`, `onChange`, `onTouched`, `all`
- Field-level vs form-level validation
- Synchronous vs asynchronous validation
- Cross-field validation (password confirmation, date ranges)
- Debouncing expensive checks (username availability)
- Race conditions in async validation
- Native constraint validation (`required`, `pattern`, `minLength`, `setCustomValidity`)
- Client errors vs server errors
- Client validation is UX; server validation is security

### Validation Timing
| Mode | Fires when | Best for |
|------|-----------|----------|
| `onSubmit` | On submit only | Cheap first pass |
| `onBlur` | Field loses focus | Most forms |
| `onChange` | Every keystroke | Instant feedback, simple rules |
| `onTouched` | First blur, then every change | Progressive feedback |
| `all` | Blur + change | Strict forms |

In React Hook Form the mode is set once:

```tsx
const form = useForm({ mode: 'onTouched', resolver: zodResolver(schema) });
```

Firing on every keystroke from the very first character means the user sees an error before they have finished typing - `onTouched` exists precisely to avoid that.

### Field-Level vs Form-Level
```tsx
// Field-level - the rule only needs this value
<input
  {...register('email', {
    validate: (value) => value.endsWith('@acme.com') || 'Use your work email',
  })}
/>
```
A rule that spans multiple fields belongs in the form-level schema (`.refine()`), not in an individual field, so it stays in one place.

### Async Validation
```tsx
<input
  {...register('username', {
    validate: async (value) => {
      const res = await fetch(`/api/username?value=${encodeURIComponent(value)}`);
      return (await res.json()).available || 'Username taken';
    },
  })}
/>
```
Two rules for network-backed validation: debounce before every request, and ignore stale responses - a slow earlier request must not overwrite the result of a faster later one.

### Native Validation
```html
<input type="email" required minLength={3} pattern="[^@]+@[^@]+" />
```
Native constraint validation is free, drives mobile keyboards, and is announced by assistive tech, but the messages are browser-specific and hard to style. Treat it as a floor, not as your only layer.

### Client vs Server
- **Client validation** - fast feedback and obvious mistakes blocked early; trivially bypassable.
- **Server validation** - the only validation that counts, and the only place uniqueness, permissions, and business rules can be enforced.

Server errors must be mapped back onto the matching fields (with `setError`), not dumped into one form-level banner the user has to decode.

### Real-World Deal-Breakers
- **Validating on `onChange` from the first keystroke** → errors flash while the user is still typing.
- **No server validation** → a `curl` request bypasses everything the UI enforces.
- **Async validation with no debounce** → one network request per keystroke.
- **Ignoring stale async results** → the error state flickers to an outdated answer.
- **Disabling submit until the form is valid** → the user can't submit to learn what is wrong; validate on submit and focus the first invalid field.
