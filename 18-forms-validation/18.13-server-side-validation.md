## 18.9 Server-Side Validation

### Subtopic Tree
- Always validate server-side
- Same schema on client and server
- Zod `safeParse` in Server Actions
- Mapping server errors back to fields
- `useActionState` (React 19)
- Progressive enhancement
- Security: never trust the client

### Pattern (Next.js Server Action + RHF)
```tsx
// app/actions.ts
'use server';
import { z } from 'zod';

const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});

export async function loginAction(prevState, formData) {
  const result = schema.safeParse({
    email: formData.get('email'),
    password: formData.get('password'),
  });

  if (!result.success) {
    return { errors: result.error.flatten().fieldErrors };
  }

  // ... authenticate
}
```

```tsx
// Client - map server errors back to fields
const onSubmit = async (data) => {
  const result = await loginAction(data);
  if (result.errors) {
    Object.entries(result.errors).forEach(([field, messages]) => {
      form.setError(field, { message: messages[0] });
    });
  }
};
```

### Real-World Deal-Breakers
- **Client-only validation** → trivially bypassed via DevTools, raw HTTP. Always validate server-side.
- **Different schemas on client vs server** → schema drift; server rejects what client accepts. Use one schema.
- **Not mapping server errors to fields** → user sees generic error instead of "Email already taken".
