## Schema Validation

### Subtopic Tree
- One schema as the single source of truth
- Libraries: Zod, Valibot, ArkType, Yup
- `parse` (throws) vs `safeParse` (returns a result)
- Sync vs async validation (`parseAsync`, promise-returning refinements)
- Composition: `.extend()`, `.merge()`, `.pick()`, `.omit()`, `.partial()`
- Discriminated unions for variant payloads
- Refinements for cross-field rules
- Transforms for normalising input
- Validating at the boundary: forms, Server Actions, route handlers, `process.env`
- Mapping issues back to fields
- One schema shared by client and server

### The Schema Is the Contract
A schema describes both the shape **and** the rules of data. Define it once, derive the TypeScript type from it, and reuse the exact same schema on the client and the server.

```typescript
const signupSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  age: z.coerce.number().int().positive(),
});

type Signup = z.infer<typeof signupSchema>;
```

### Validate at the Boundary
```tsx
// Client - as the form resolver
useForm({ resolver: zodResolver(signupSchema) });
```

```typescript
// Server - the same schema, on the same data
'use server';
export async function signup(formData: FormData) {
  const parsed = signupSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) {
    return { errors: z.flattenError(parsed.error).fieldErrors };
  }
  // parsed.data is typed and trusted from here on
}
```
Data crossing a boundary is untrusted by definition - validate it where it enters.

### Composition Beats Duplication
```typescript
const base = z.object({ id: z.string(), name: z.string() });

const withEmail = base.extend({ email: z.string().email() });
const withoutId = base.omit({ id: true });
const draft     = base.partial(); // every field optional
```
Compose one schema into the variants you need instead of copy-pasting rules that then drift apart.

### Discriminated Unions
```typescript
const eventSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('click'), x: z.number(), y: z.number() }),
  z.object({ type: z.literal('keypress'), key: z.string() }),
]);
```
The discriminant tag narrows the type and produces useful error messages ("no variant matched `type`").

### From Issues Back to Fields
```typescript
const result = schema.safeParse(input);
if (!result.success) {
  for (const issue of result.error.issues) {
    // issue.path → ['email']; use it to attach the message to the field
  }
}
```
A refinement that sets no `path` produces an issue with an empty path, so it cannot be mapped to a field. Always pass `path` on cross-field refinements.

### Real-World Deal-Breakers
- **Validating with ad-hoc `if` statements** → the rules drift between client and server.
- **Hand-writing a type next to the schema** → the two disagree the moment the schema changes; derive with `z.infer`.
- **Calling `.parse()` in a UI path** → it throws; use `.safeParse()` and render the issues.
- **Trusting environment variables** → a missing `process.env` value becomes the string `"undefined"`; parse the env at startup and fail fast.
- **Forgetting to coerce** → form values and env vars are strings; numbers and booleans need `.coerce` or an explicit conversion.
