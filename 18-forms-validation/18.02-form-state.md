## 18.5 Form State (Controlled vs Uncontrolled)

### Subtopic Tree
- Controlled components (React owns state)
- Uncontrolled components (DOM owns state)
- Performance implications
- File inputs (always uncontrolled)
- When to choose which
- Hybrid approaches
- The `defaultValue` vs `value` trap

### Controlled vs Uncontrolled

| | Controlled | Uncontrolled |
|--|-----------|-------------|
| State lives in | React (`useState`) | DOM (`ref`, `defaultValue`) |
| Re-render on input | Every keystroke | Never |
| Real-time validation | Easy | Harder |
| File inputs | ❌ Impossible | ✅ Required |
| Performance | Slower for large forms | Faster |

**File inputs are ALWAYS uncontrolled because their value is read-only for security reasons.**

### When to Use Which
- **Controlled** → real-time validation, conditional fields, formatted input.
- **Uncontrolled** → file inputs, third-party integrations, submit-only forms, performance-critical forms.
- **For submit-only forms, uncontrolled inputs plus a form action are simpler and faster.**

### The Trap: Switching Modes
```jsx
// ❌ Switching from uncontrolled to controlled
<input defaultValue="initial" value={undefined} /> // React warns

// ✅ Pick one mode and stay consistent
<input value={text} onChange={e => setText(e.target.value)} /> // controlled
// OR
<input defaultValue="initial" ref={inputRef} /> // uncontrolled
```
Mixing controlled and uncontrolled is one of the most common React form mistakes.

### Real-World Deal-Breakers
- **Controlled inputs for large forms** → every keystroke re-renders the entire form. Use RHF (uncontrolled).
- **Trying to control file inputs** → throws "Cannot set property value of #<HTMLInputElement>".
- **Switching controlled ↔ uncontrolled** → React warning, unpredictable behavior.
- **Using `useState` for every field** → 20 fields = 20 `useState` calls, full re-render on every keystroke.
