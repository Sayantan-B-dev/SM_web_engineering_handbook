### Event Loop Model (Browser)
The event loop continuously checks: **Is the call stack empty?** If yes, it processes all microtasks, then renders (if needed), then takes one macrotask and repeats.

```
┌─────────────────────────┐
│       Call Stack        │
└───────────┬─────────────┘
            │ empty?
            ▼
┌─────────────────────────┐
│   Microtask Queue       │ ← Promises, queueMicrotask, MutationObserver
│   (drain ALL)           │
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│   Render (if needed)    │ ← requestAnimationFrame, style, layout, paint
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│   Macrotask Queue       │ ← setTimeout, setInterval, I/O, UI events
│   (take ONE)            │
└─────────────────────────┘
```

### Execution Order Example
```javascript
console.log('1'); // sync

setTimeout(() => console.log('2'), 0); // macrotask

Promise.resolve().then(() => console.log('3')); // microtask

queueMicrotask(() => console.log('4')); // microtask

console.log('5'); // sync

// Output: 1, 5, 3, 4, 2
```

**Explanation**:
1. Sync code runs first: `1`, `5`.
2. Microtasks drain: `3`, `4`.
3. One macrotask: `2`.

### `requestAnimationFrame` vs `setTimeout`
```javascript
// ❌ setTimeout — not synced to frame rate
setTimeout(animate, 16); // ~60fps but may drift

// ✅ requestAnimationFrame — synced to browser repaint
function animate() {
  // update styles
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);
```

### Microtask Starvation
```javascript
// ❌ Infinite microtask loop — browser freezes
function loop() {
  Promise.resolve().then(loop);
}
loop();

// ✅ Use setTimeout for yielding
function loop() {
  setTimeout(loop, 0);
}
```

**Real-world deal-breaker**: Microtasks have priority over rendering. An infinite microtask chain blocks the browser completely — no rendering, no user input, no timers.

### Real-World Deal-Breakers
- **Blocking the main thread** → long synchronous operations (heavy computation, large JSON parsing) freeze the UI. Use Web Workers.
- **`setTimeout(fn, 0)` is not immediate** → it's deferred to the next macrotask cycle; minimum delay is ~4ms after nested calls.
- **Assuming microtasks run before rendering** → microtasks drain before rendering, but a long microtask chain delays paint.
- **`await` ordering** → each `await` yields to the microtask queue, allowing other microtasks to run before resuming.
