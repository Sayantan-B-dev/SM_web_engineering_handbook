### Tool Call Cards
The tool calling pattern shows how to render structured, type-safe UI cards for every tool call your agent makes, complete with loading states and error handling. When a LangGraph agent decides it needs external data, it emits one or more tool calls as part of an AI message. Each tool call includes a `name` (e.g., `"get_weather"`), `args` (structured arguments), and `id` (unique identifier linking the call to its result `ToolMessage`). The `useStream` hook unifies all of this into a single `toolCalls` array you can render directly.

```tsx
function ToolCard({ toolCall }: { toolCall: AssembledToolCall }) {
  switch (toolCall.state) {
    case 'input-available':
      return <LoadingCard tool={toolCall.name} args={toolCall.args} />;
    case 'output-available':
      return <ResultCard tool={toolCall.name} output={toolCall.output} />;
    case 'error':
      return <ErrorCard tool={toolCall.name} error={toolCall.error} />;
  }
}
```

### Deeper Explanation: Making Autonomy Legible

An agent interface has one job: let a human stay in control while doing most of the work. The patterns that achieve it:

- **Timeline of steps** with status (pending/running/done/failed), arguments, results, and duration. Expandable, not exhaustive by default.
- **Interrupt controls** at every level â€” stop the run, skip a step, edit the arguments and retry.
- **Explicit handoff moments** for approvals, with the exact payload to be sent shown before sending.
- **Failure surfacing** â€” which step failed, why, and what the recovery options are (retry, edit, abandon).
- **Provenance** â€” every artifact the agent produced links back to the step that produced it.

The strongest default is **"supervised autonomy"**: the agent plans and executes read-only steps freely, and pauses for anything that writes, spends, or is publicly visible.

### Additional Pitfalls
- **Black-box spinners for long runs.** No visibility means no trust and no debugging.
- **Approval fatigue.** Approving every trivial step trains users to click yes; reserve approvals for consequential actions.
- **No editing of a step's arguments.** The most useful intervention is fixing one parameter, not restarting.
- **Chat-only interface for structured work.** Where a form, diff, or preview is clearer than prose, render it instead of a message.
- **No cost or step counter.** Users need to understand what they are spending.

### Real-World Deal-Breakers
- **Raw JSON output** → users can't read tool results. Render typed cards.
- **No loading state per tool** → users don't know which tool is running.
- **No error handling per tool** → a failed tool shows a broken card.
- **No approval flow** → destructive tools execute without confirmation.
- **No context usage display** → users don't know how much context is left.
