### The Standard RAG Stack
A common RAG application architecture uses a shared backend with three frontends (dashboard, chat tool, embed tool) in a monorepo architecture, with authentication using Clerk, Next.js, and React.

A full-stack RAG application typically has a Python (FastAPI) backend and a React (TypeScript) frontend with a decoupled, service-oriented architecture. The RAG chat flow: a user submits a question through the React UI, the backend retrieves relevant chunks, the LLM generates a response, and the response streams back to the UI.

### Chat UI with Source Citations
```tsx
function RAGChat() {
  const { messages, input, handleInputChange, handleSubmit } = useChat({
    api: '/api/rag/chat',
  });

  return (
    <div>
      {messages.map((m) => (
        <div key={m.id}>
          <Markdown>{m.content}</Markdown>
          {m.citations?.map((c) => (
            <CitationCard key={c.id} source={c.source} page={c.page} />
          ))}
        </div>
      ))}
      <form onSubmit={handleSubmit}>
        <input value={input} onChange={handleInputChange} />
      </form>
    </div>
  );
}
```

### File Upload and Ingestion
```tsx
function FileUpload() {
  const [uploading, setUploading] = useState(false);

  async function handleUpload(file: File) {
    setUploading(true);
    const formData = new FormData();
    formData.append('file', file);
    await fetch('/api/rag/ingest', { method: 'POST', body: formData });
    setUploading(false);
  }

  return (
    <input
      type="file"
      onChange={(e) => e.target.files?.[0] && handleUpload(e.target.files[0])}
    />
  );
}
```

### Deeper Explanation: The Frontend Half Of RAG

The backend owns retrieval quality; the frontend owns **trust and iteration**. That means four UI obligations:

- **Progress with stages** â€” "searching â†’ reading 6 sources â†’ writing" beats an unlabelled spinner and hides latency variance.
- **Citations inline and inspectable** â€” each claim shows the source; clicking opens the passage, not the document root.
- **Confidence and refusal** â€” when retrieval is weak, the UI should say so rather than present an answer with the same styling as a confident one.
- **Iteration affordances** â€” "search only in X", "include archived", "answer with more detail" mapped to explicit retrieval parameters rather than prompt pleading.

Also cache aggressively: embeddings and retrieval results for identical queries are cheap wins, and a conversation's retrieved context can be reused across follow-ups.

### Additional Pitfalls
- **Styling uncertain answers like certain ones.** Present retrieval strength honestly (sources found, coverage).
- **Hiding the sources behind a click-through to a PDF.** Give the exact passage with highlighting.
- **No query refinement controls.** Users cannot express the filter they mean if the UI has no control for it.
- **Refetching retrieval on every token.** Retrieval happens once per turn; generation streams separately.
- **No client-side caching of retrieved context.** Follow-up questions pay the retrieval cost twice.

### Real-World Deal-Breakers
- **No source citations** → users can't verify the answer. Always show sources.
- **No streaming** → RAG responses are long; streaming is essential.
- **No chunking strategy** → chunks too large (noise) or too small (missing context).
- **No reranking** → top-K vector results are often not the most relevant.
- **No feedback loop** → you can't improve retrieval without user feedback (thumbs up/down).
