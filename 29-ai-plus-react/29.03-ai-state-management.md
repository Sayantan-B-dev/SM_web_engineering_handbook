### Why AI State Is Different

| App State | AI Chat State |
|-----------|--------------|
| Discrete, deterministic | Streaming, probabilistic |
| One value per key | Arrays of messages + tool calls + reasoning |
| Settled after mutation | In-flight for seconds |
| Local component scope | Shared across multiple components |

### ai-sdk-zustand - Global Chat State
A drop-in replacement for `@ai-sdk/react` that gives you global state access to your AI chats. No prop drilling, better performance, simplified architecture. Use it when multiple components need chat data, building complex chat UIs, or need performance optimization.

```typescript
import { create } from 'zustand';
import { createAIChatStore } from 'ai-sdk-zustand';

const useChatStore = createAIChatStore({
  api: '/api/chat',
  model: 'gpt-4.1',
});

function ChatMessages() {
  const messages = useChatStore((s) => s.messages);
  return messages.map((m) => <Message key={m.id} message={m} />);
}

function ChatInput() {
  const { input, setInput, submit } = useChatStore();
  return <input value={input} onChange={(e) => setInput(e.target.value)} />;
}
```

### @mzhub/react - "Redux for AI"
@mzhub/react provides AI-Native State Management for React - the "Redux for AI". Synapse wraps AI providers (cloud and local) with safety, validation, and React integration. It supports Groq (fast inference) and Cerebras (wafer-scale) as providers.

### AI-Powered State Stores
`ai-state-store` is an AI-powered state management library for React. You dispatch natural language, and AI handles the rest.

```typescript
import { createAIStore } from 'ai-state-store';

const store = createAIStore({
  provider: 'openai',
  apiKey: process.env.OPENAI_API_KEY,
  state: {
    todos: [],
    filter: 'all',
  },
});

// Dispatch natural language
store.dispatch('add a todo called "Buy milk"');
store.dispatch('show only completed todos');
```

### Deeper Explanation: Model State Has A Lifecycle, Not A Fetch

AI state is not query state: a generation has an id, a status (`idle â†’ streaming â†’ complete | error | cancelled`), a partial message, tool calls in flight, a token count, and a cost. Modelling that explicitly is what makes the UI predictable and resumable.

Three architectural choices:

- **Server-owned sessions** (a conversation id, messages in a database, streaming over SSE) â€” resumable across devices and refreshes, easiest to make safe, best for products with history.
- **Client store with server persistence** â€” the store is the render source, writes are batched to the server; good for offline-tolerant drafts.
- **Local-only** â€” fine for ephemeral tools; the user must understand that a refresh loses the thread.

Whatever the choice, keep **streaming state out of React component state**: a token arriving 30 times a second must update a store slice (or a message-specific subscription) and re-render only the affected message.

### Additional Pitfalls
- **One big state object for the whole conversation.** Every token re-renders every message.
- **No persistence.** Users expect history; losing a long answer to a refresh is unacceptable in-product.
- **Regeneration appends instead of replacing.** Branching needs explicit modelling (a message tree), not a flat array.
- **Token and cost invisible.** Without per-session accounting you cannot rate-limit or price the feature.
- **Cancellation not represented in state.** A cancelled generation must be a distinct, renderable status.

### Real-World Deal-Breakers
- **Putting chat state in Redux** → you'll rebuild `useChat` poorly. Use a dedicated AI state layer.
- **Prop drilling chat state** → `messages`, `input`, `status`, `toolCalls` through 5 levels. Use global chat state.
- **Mixing AI chat state with app state** → clearing the chat clears the app. Separate them.
- **No performance optimization** → every keystroke re-renders the entire chat tree. Select only what you need.
- **Stale closures in streaming callbacks** → the callback captures the initial state. Use refs or functional updates.
