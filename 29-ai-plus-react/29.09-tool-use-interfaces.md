### Type-Safe Tool Arguments (Zod)
The Vercel AI SDK uses Zod schemas for type-safe tool validation.

```typescript
import { z } from 'zod';
import { tool } from 'ai';

const getWeather = tool({
  description: 'Get current weather for a location',
  parameters: z.object({
    location: z.string().describe('City name'),
    unit: z.enum(['celsius', 'fahrenheit']).default('celsius'),
  }),
  execute: async ({ location, unit }) => {
    return await fetchWeather(location, unit);
  },
});
```

### Tool State Machine
```typescript
type ToolState =
  | 'input-streaming'    // arguments are streaming in
  | 'input-available'    // arguments complete, tool executing
  | 'output-available'   // tool result available
  | 'error';             // tool execution failed
```

### Tool Registry Pattern
```tsx
const toolRegistry = {
  get_weather: {
    component: WeatherCard,
    requiresApproval: false,
  },
  delete_project: {
    component: DeleteConfirmation,
    requiresApproval: true,
  },
  search_docs: {
    component: SearchResults,
    requiresApproval: false,
  },
};

function ToolRenderer({ toolCall }: { toolCall: AssembledToolCall }) {
  const entry = toolRegistry[toolCall.name];
  if (!entry) return <FallbackToolCard toolCall={toolCall} />;
  const Component = entry.component;
  return <Component toolCall={toolCall} />;
}
```

### Deeper Explanation: Tool Calls Deserve Their Own UI

A tool call is a first-class event, not a line of text. Rendering it as a message ("I searched for X and found 3 results") wastes the opportunity; rendering it as a structured card gives the user control:

- **Input display**: what parameters were chosen, editable before running (with sensible defaults).
- **Output display**: typed by tool â€” a table for search, an image for generation, a diff for edits, a map for location.
- **Status**: queued/running/succeeded/failed, with duration and retry.
- **Approval**: for mutating tools, show the exact effect and require a click.

This also makes evaluation possible: tool calls with structured inputs and outputs can be logged, replayed, and asserted against in tests, which is impossible with prose.

### Additional Pitfalls
- **Tool output stuffed into the transcript.** Long outputs destroy the chat UX; collapse with a "show full result" affordance.
- **No editable parameters.** Users cannot fix a wrong filter without re-typing the prompt.
- **Rendering untrusted tool output as HTML.** Sanitise; it may contain user-generated content.
- **Hiding failures.** A red step with the error message is far more useful than a silent fallback.
- **No retry affordance per tool call.** The most common recovery action is re-running one step.

### Real-World Deal-Breakers
- **No Zod validation** → tool arguments are `any`; runtime errors from bad shapes.
- **No tool state machine** → the UI doesn't show loading, success, or error states.
- **No tool registry** → every tool requires custom rendering logic scattered across files.
- **Client-side execution of server tools** → security vulnerability. Server tools must execute on the server.
