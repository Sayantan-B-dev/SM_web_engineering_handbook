### Agent State in React
```tsx
import { useStream } from '@langchain/react';

function AgentChat() {
  const stream = useStream<typeof myAgent>({
    apiUrl: 'http://localhost:2024',
    assistantId: 'agent',
  });

  return (
    <div>
      {stream.messages.map((msg) => (
        <Message key={msg.id} message={msg} toolCalls={stream.toolCalls} />
      ))}
    </div>
  );
}
```

### Reasoning Display
```tsx
function ReasoningBlock({ reasoning }: { reasoning: string }) {
  const [open, setOpen] = useState(false);
  return (
    <div className="rounded border bg-gray-50 p-3 text-sm text-gray-600">
      <button onClick={() => setOpen(!open)} className="font-medium">
        {open ? 'Hide' : 'Show'} reasoning
      </button>
      {open && <p className="mt-2">{reasoning}</p>}
    </div>
  );
}
```

### Agent Plans and Multi-Step Work
CrewAI's generative UI shows that instead of reacting to a single tool call, you should **render the agent's state as it changes**. This is the right pattern for multi-step work. MCP tool calls surface as standard tool-call UI - render them with `useRenderTool` like any other tool.

### Agent Composition with Hooks
The `agentry` package provides React patterns for agent composition, including JSX `<Tool>` with inline props for declarative tool registration, subagents as specialist tools, `useExecutionState()` for tracking agent state, and `useMessages()` for accessing conversation history.

### Deeper Explanation: Agents In A Product, Not In A Chat

Putting an agent in a React product means making its work **visible, interruptible, and reversible**:

- **Stream the plan and steps** â€” users need to see what it is doing and why, not a black-box spinner for 40 seconds.
- **Per-step approvals** â€” any step with side effects gets a confirmation, or runs in a dry-run mode by default.
- **Partial results are useful** â€” write results into the UI as they are produced so the user can stop early and keep what exists.
- **A hard budget** â€” max steps, max cost, wall-clock timeout, with a clear "stopped becauseâ€¦" message.
- **Full trace for support** â€” every prompt, tool call, response, and token count, viewable by engineers (never by unauthorised users).

The React-specific trap: agents run longer than a component's lifetime. State must live in a server session or a store keyed by run id, so a navigation or refresh does not orphan the work.

### Additional Pitfalls
- **Agent runs bound to a component.** Unmount aborts or orphans the run; key it by run id in a store.
- **No dry run.** Side effects without preview are unacceptable for anything expensive or public.
- **Opaque progress.** Users abandon agents that give no signal; stream steps and status.
- **No cost ceiling per user.** A loop can burn the quota; enforce limits server-side.
- **No audit trail.** Support cannot debug without a stored trace of steps and tool calls.

### Real-World Deal-Breakers
- **No reasoning display** → users can't see why the agent made a decision. Show reasoning collapsible.
- **No approval for destructive tools** → the agent deletes data without confirmation.
- **No max steps** → the agent loops forever. Cap iterations.
- **No observability** → you can't debug agent decisions. Log every step, tool call, and result.
- **Too many tools** → the agent gets confused. Keep tool count under 10-15.
