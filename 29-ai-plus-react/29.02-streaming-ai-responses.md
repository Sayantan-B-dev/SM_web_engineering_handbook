### The Streaming Pipeline
```text
Server:
  streamText() → SSE stream → chunked HTTP response

Client:
  useChat() → reads SSE → updates messages[] → React re-renders
```

### Server-Side Streaming (Next.js Route Handler)
```typescript
// app/api/chat/route.ts
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';

export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = streamText({
    model: openai('gpt-4.1'),
    messages,
    tools: {
      getWeather: {
        description: 'Get weather for a location',
        parameters: z.object({ location: z.string() }),
        execute: async ({ location }) => fetchWeather(location),
      },
    },
  });

  return result.toDataStreamResponse();
}
```

### Client-Side Streaming (React)
```tsx
'use client';
import { useChat } from '@ai-sdk/react';

function Chat() {
  const { messages, input, handleInputChange, handleSubmit, status } = useChat();

  return (
    <div>
      {messages.map((m) => (
        <div key={m.id}>
          <strong>{m.role}:</strong>
          <Markdown>{m.content}</Markdown>
          {m.toolInvocations?.map((tool) => (
            <ToolCard key={tool.toolCallId} invocation={tool} />
          ))}
        </div>
      ))}
      <form onSubmit={handleSubmit}>
        <input value={input} onChange={handleInputChange} />
        <button disabled={status === 'streaming'}>Send</button>
      </form>
    </div>
  );
}
```

### Browser-Native Streaming (Prompt API)
The Chrome for Developers blog shows a complete streaming chat interface running entirely in the browser, using the built-in Prompt API (`@browser-ai/core`) with automatic fallback to Gemini 2.5 Flash when the Prompt API is unavailable. It uses the Vercel AI SDK's `useChat` hook for streaming multi-turn conversations, runs the model loop in the browser without a backend server, and renders GitHub-style Markdown with handling for incomplete tokens during streaming.

### Incremental JSON Stream Parsing
For generative UI, the streaming architecture uses an incremental JSON stream parser with brace-depth counting, a recursive discriminated `UINode` Zod schema as the contract between LLM output and React rendering, and validation of each parsed JSON object at the stream boundary using Zod's `safeParse`, emitting typed error nodes on failure.

```typescript
// lib/json-stream-parser.ts
class IncrementalJSONParser {
  private buffer = '';
  private depth = 0;

  push(chunk: string): object[] {
    this.buffer += chunk;
    const objects: object[] = [];

    let start = 0;
    for (let i = 0; i < this.buffer.length; i++) {
      if (this.buffer[i] === '{') this.depth++;
      if (this.buffer[i] === '}') {
        this.depth--;
        if (this.depth === 0) {
          const json = this.buffer.slice(start, i + 1);
          try {
            objects.push(JSON.parse(json));
          } catch {
            // incomplete - wait for more
          }
          start = i + 1;
        }
      }
    }
    this.buffer = this.buffer.slice(start);
    return objects;
  }
}
```

### Deeper Explanation: Stream Parsing Is A Protocol Problem

Streaming AI responses are SSE-like streams with a provider-specific framing: text deltas, tool-call deltas (JSON fragments arriving in pieces), usage, and stop reasons. The engineering requirements:

- **Accumulate fragments by index/id.** Tool-call arguments arrive in pieces; you must concatenate before `JSON.parse` succeeds.
- **Handle partial markdown.** A code fence may open in one chunk and close three chunks later; render with a tolerant parser (or buffer per block).
- **Never mutate a stream in two components.** One consumer per stream; fan out through a store.
- **Flush and clean up on abort.** Cancelled streams must not leave dangling readers or partial state.
- **Persist the final message server-side.** A refresh mid-generation should resume or re-fetch, not duplicate.

With the Vercel AI SDK, `useChat` handles a lot of this; the part it cannot decide for you is *where the state lives* and how the UI degrades when streaming is unsupported.

### Extended Example: Decoding A Provider Stream Manually

```ts
export async function* readSse(res: Response): AsyncGenerator<{ event?: string; data: string }> {
  const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = '';
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    const parts = buffer.split('\n\n');
    buffer = parts.pop() ?? '';
    for (const part of parts) {
      const lines = part.split('\n');
      const event = lines.find((l) => l.startsWith('event:'))?.slice(6).trim();
      const data = lines.filter((l) => l.startsWith('data:')).map((l) => l.slice(5).trim()).join('\n');
      if (data) yield { event, data };
    }
  }
}

// Tool-call arguments arrive as fragments â€” accumulate, parse once, validate
const partials = new Map<number, string>();
for await (const { data } of readSse(res)) {
  const chunk = JSON.parse(data);
  for (const call of chunk.choices?.[0]?.delta?.tool_calls ?? []) {
    partials.set(call.index, (partials.get(call.index) ?? '') + (call.function?.arguments ?? ''));
  }
}
```

### Additional Pitfalls
- **Parsing each chunk independently.** Split JSON across chunks is the norm, not the exception.
- **Rendering raw markdown per token.** Flicker and broken code fences; buffer per block or use a tolerant renderer.
- **One stream, many subscribers.** Two components reading the same body consume each other's chunks.
- **Not aborting on unmount.** The request continues, the state leaks, and half-answers get written to the store.
- **No fallback for non-streaming environments.** Some proxies buffer everything; detect and degrade to a full response.

### Real-World Deal-Breakers
- **No streaming** → users wait 5-30 seconds for a response. Always stream.
- **SSE framing not stripped** → the client sees `data: {...}\n\n` instead of clean JSON. Strip SSE framing server-side.
- **No incomplete token handling** → Markdown renders broken during streaming. Buffer and harden.
- **No error handling in the stream** → a mid-stream error leaves the UI in a broken state. Handle `onError` and provide a retry.
- **No `status` checks** → users can send messages while the assistant is still responding. Disable input during `status === 'streaming'`.
