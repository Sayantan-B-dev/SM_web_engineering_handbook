## 30.7 Open-Ended Generative UI (MCP Apps)

### Subtopic Tree
- Low control, high freedom
- Agent returns a full UI surface (iframe or arbitrary HTML)

### What Open-Ended Generative UI Is
Open-ended Generative UI gives the agent **full autonomy** to generate the entire UI surface - often an iframe or arbitrary HTML. This is the most flexible and the most dangerous approach.

### MCP Apps
MCP Apps is a jointly authored extension to the Model Context Protocol from Anthropic and OpenAI that formalizes open-ended generative UI. The agent returns a full UI surface, and the frontend renders it in a sandboxed environment.

### Real-World Example: Excalidraw
The CopilotKit repository includes a real-world example of Excalidraw MCP Apps, where the agent generates an Excalidraw diagram from a prompt.

### The Security Problem
Allowing agents to generate HTML and JavaScript that the client renders and executes directly creates a **fundamental security risk**. If someone deliberately hides an instruction in the input, the Agent could be manipulated by prompt injection, unknowingly generating a script that stealthily steals user data.

CVE-2026-17496 is a real example: NoteGen's AI chat preview component passes model-generated HTML directly into the DOM via `dangerouslySetInnerHTML` with no sanitization and no CSP, allowing an attacker who can influence the model's prompt to execute arbitrary JavaScript in the privileged Tauri desktop webview context.

### When Open-Ended Is Appropriate
- **Sandboxed environments** - iframes with `sandbox` attributes, no access to parent DOM.
- **Non-critical surfaces** - internal tools, experimental features.
- **Trusted agents** - you control the agent, the prompts, and the tools.
- **Never** for brand-critical, high-traffic, or auth-bearing surfaces.

---

### Deeper Explanation: Open-Ended UI Needs A Sandbox, Not Permission

When the model may produce arbitrary components or markup, the only defensible approach is **isolation**: render generated code in a sandboxed iframe or worker with no access to cookies, storage, the parent DOM, or your network credentials, and communicate only through a typed message bridge. That is how "build me any widget" products stay safe.

The essential controls:

- `<iframe sandbox="allow-scripts">` **without** `allow-same-origin`, served from a separate origin so it cannot touch your app's storage.
- A strict CSP inside the sandbox: no network egress except an allow-listed API, no top navigation.
- A message-only bridge with a validated schema, rate limits, and a size cap.
- Resource limits: CPU time, message volume, and rendering size, with a hard kill.
- Explicit product framing: prototypes and explorations, not primary flows.

### Additional Pitfalls
- **`allow-same-origin` with `allow-scripts`.** That combination lets the sandbox remove its own restrictions.
- **Passing credentials into the sandbox.** It should call your API through a scoped, short-lived token or not at all.
- **No kill switch.** A runaway render must be terminable from the host.
- **Assuming generated markup is accessible.** It is not; provide an alternative representation for every generated view.

### Real-World Deal-Breakers
- **`dangerouslySetInnerHTML` without sanitization** → XSS. Use sandboxed iframes or typed component trees.
- **No CSP** → script injection is possible.
- **No prompt injection defense** → the agent executes malicious instructions.
- **Using open-ended for critical surfaces** → security vulnerability. Use controlled or declarative.
