## 30.11 Performance & Layout Shift

### Subtopic Tree
- Layout shifts during streaming (CLS)
- Reserving space with `min-height` / `aspect-ratio`
- `contain: layout` for streaming containers
- Dimension-matched skeletons
- Zero-frame synchronous hydration

- Avoiding thousands of text nodes

### The Layout Shift Problem
An AI application can generate a response quickly and still feel slow. Users may wait without feedback, watch the layout shift as text arrives, or struggle to recover when a connection interrupts an otherwise useful answer. Late-injected chat windows or assistants shift existing content. Dynamic AI content loading into containers that don't reserve space upfront causes Cumulative Layout Shift (CLS).

### The Fix: Reserve Space
Reserve space for streaming containers using CSS `min-height` and `aspect-ratio` to prevent content below from jumping. Use `contain: layout` on the streaming container so that layout changes inside don't affect the rest of the page.

```css
.streaming-container {
  contain: layout;
  min-height: 200px;
  aspect-ratio: 16 / 9; /* if rendering media */
}

.skeleton {
  /* dimension-matched to final content */
  width: 100%;
  height: 100%;
}
```

### Zero-Frame Synchronous Hydration
Flutter's `streaming_gen_ui` package replaces standard `StreamBuilder` with an `AdaptiveStreamBuilder` that synchronously listens to cached stream emissions on frame 1, eliminating mounting flickers and layout shifts when viewing completed/historical messages.

### Pretext (Text Layout Engine)
Pretext is a sub-millisecond text layout engine that bypasses the DOM for pure arithmetic performance. It predicts message height, reduces layout shift, and measures multilingual text without DOM reflow.

---

### Deeper Explanation: Generated Trees Must Not Move

Progressive rendering is inevitable, so layout stability has to be designed in. Four techniques carry most of the weight:

- **Reserve space per node type.** A chart placeholder is chart-sized; a table skeleton has the right row height. Use container queries or fixed aspect ratios rather than guessing.
- **Cap and paginate.** Maximum nodes, rows, and nesting depth keep render time bounded and keep the layout from growing mid-interaction.
- **Stable identity.** Node keys derived from content/type, not array index, so late-arriving fields update in place.
- **Isolate re-renders.** A stream updating node 7 must not re-render nodes 1-6; memoise per node and subscribe narrowly.

Also budget the work: JSON parse + validate + render should stay inside a frame for typical payloads; if validation of a large spec is expensive, do it in a worker.

### Additional Pitfalls
- **Skeletons of the wrong size.** The most common CLS source in generated UI.
- **Re-parsing the whole spec per chunk.** Cost grows with output length; parse incrementally.
- **Unbounded charts and lists.** A 5 000-row table freezes the tab; enforce caps in the schema.
- **Animating entry of every node.** Subtle is better; large simultaneous animations read as jank.
- **No measurement.** Instrument time-to-first-render and CLS for generated views specifically.

### Real-World Deal-Breakers
- **No `contain: layout`** → streaming content reflows the entire page.
- **No reserved space** → CLS as content streams in.
- **Naive implementation** → thousands of text nodes, each triggering a layout recalculation.
- **No skeleton** → users see a blank container that suddenly fills with content.
