## 30.6 Controlled Generative UI (AG-UI)

### Subtopic Tree
- High control, low freedom
- Frontend owns the components
- Agent selects from a fixed set
- Tool-based rendering (one tool → one component)
- Progressive rendering as arguments stream
- Backend tool rendering
- Best for: high-traffic, brand-critical surfaces

### What Controlled Generative UI Is
Controlled Generative UI (AG-UI) gives the frontend **full control over every pixel**. The agent doesn't generate a layout - it **selects from a fixed set of pre-built components** and provides the data. This is the most constrained and safest approach.

### Tool-Based Rendering
The agent calls a tool on the backend. You register a component for that tool. The agent picks the component, and the frontend renders it with the agent's arguments. This maps one tool to one component - the agent doesn't compose layouts.

```typescript
// Register a tool for weather
const getWeather = tool({
  description: 'Get current weather for a location',
  parameters: z.object({ location: z.string() }),
  execute: async ({ location }) => fetchWeather(location),
});

// Register a component for the tool
const toolComponents = {
  get_weather: WeatherCard, // one tool → one component
};
```

### Progressive Rendering
As the agent streams tool arguments, the frontend can render progressive states: `input-streaming` → `input-available` → `output-available` → `error`. This gives users immediate feedback even before the tool completes.

---

### Deeper Explanation: Control Is A Product Feature, Not A Limitation

Controlled generative UI keeps the model inside a governed surface â€” a component set, a permission model, an interaction budget. Teams that treat this as a limitation build worse products; teams that treat it as the feature get consistency, accessibility, and reviewability for free.

The control levers, in order of impact:

- **Component allow-list** â€” what can appear at all.
- **Prop schemas** â€” what values are expressible (enums over free strings).
- **Interaction policy** â€” which components may mutate data, and whether approval is required.
- **Budget** â€” maximum nodes, maximum nesting depth, maximum payload bytes.
- **Rendering policy** â€” all output renders through the design system, in the app's own layout slots.

### Additional Pitfalls
- **Allow-list without prop constraints.** The model still picks colours, sizes, and copy that violate the design system.
- **Approval fatigue from over-policing.** Reserve approvals for destructive or costly actions.
- **No budget caps.** A recursive spec is a denial of service against your own renderer.
- **Control implemented only in the prompt.** Prompts are advisory; enforce in the validator and the renderer.

### Real-World Deal-Breakers
- **Using controlled for the long tail** → you'll build 50 one-off components. Use declarative for secondary interactions.
- **No progressive rendering** → users wait for the full tool result before seeing anything.
- **Too many tools** → the agent gets confused. Keep tool count under 10-15.
