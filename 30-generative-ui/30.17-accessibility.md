### The Accessibility Gap
AI-powered UI generation tools promise to democratize interface design through natural language prompts, yet their impact on accessibility compliance remains underexplored. Research found that **AI-generated interfaces achieved only 29.0% compliance**, with deterministic criteria such as color contrast (26.8%) and the use of color (19.2%) showing the lowest adherence.

The results reveal gaps such as **missing labels, improper ARIA usage, focus issues and keyboard navigation failures**.

### The Homogenization Problem
While these tools consistently achieve basic accessibility compliance, they rely on **homogenized design patterns**. AI-generated UIs look the same and don't adapt to different accessibility needs.

### The Fix: Generation-Time Constraints
A standards-aware adaptive interface generation system operationalizes accessibility requirements as **generation-time constraints** and combines them with explicit accessibility profiles to shape content structure.

In other words: encode WCAG requirements into the component catalog. Every component in the registry has accessibility baked in (proper ARIA, focus management, color contrast). The AI can't generate an inaccessible component because the catalog only contains accessible components.

### Generative UI as an Accessibility Bridge
Generative UI can transform inaccessible user-generated content: (1) HTML regeneration for screen readers, (2) conversational guidance for step-by-step listing, and (3) audio-guided photo framing for blind sellers.

### Deeper Explanation: Generated UI Inherits Your Accessibility â€” Or Loses It

The design system is the accessibility guarantee: if generated trees can only compose accessible primitives, the output is accessible by construction. Three rules make that true in practice:

- **Semantic components only.** A `Metric` renders a labelled figure, a `Table` renders `<table>` with headers, a `Section` renders a landmark or a heading â€” never a `div` soup with inline styles.
- **Live regions for streaming.** Wrap the streamed answer in an `aria-live="polite"` region (with sensible chunking, or screen readers will read every token), and announce status changes via `role="status"`.
- **Focus and keyboard.** Generated interactive elements must be reachable in order, with visible focus, and the generated region must not steal focus while streaming.

Then verify: run axe on rendered platforms, and test with a screen reader on a streamed answer â€” the failure modes (read-every-token, focus jumping, unlabelled charts) are immediately obvious.

### Additional Pitfalls
- **`aria-live="assertive"` on a stream.** It interrupts constantly; use polite plus throttled updates.
- **Icons without labels.** Models produce decorative icons; every meaning-bearing icon needs an accessible name.
- **Charts with no text alternative.** Provide a summary table or an accessible description, not just an image.
- **Colour as the only signal.** Generated "trend" indicators must not rely on green/red alone.
- **No keyboard path for generated forms.** Validation and submission must work without a mouse.

### Real-World Deal-Breakers
- **No accessibility in the catalog** → AI generates inaccessible components. Bake accessibility into the registry.
- **No color contrast validation** → 26.8% adherence. Enforce contrast in the design system.
- **No keyboard navigation** → focus issues and keyboard failures. Test every generated component.
- **No post-render verification** → accessibility violations ship silently. Audit after render.
