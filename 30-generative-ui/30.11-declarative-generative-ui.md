### What Declarative Generative UI Is
Declarative generative UI is in the **middle of the generative UI spectrum**. The agent emits a structured specification, and the frontend composes the interface from a catalog of components you register ahead of time. Instead of rendering text responses in chat bubbles, the agent output is the UI: forms, cards, dashboards, and more.

### When to Use It
Use declarative generative UI for the **long tail** of your product, where the agent can compose layouts you did not fully anticipate while staying inside a set of components you approve: secondary interactions, internal tools, and dashboards.

**When NOT to use it:** When a surface is high-traffic or brand-critical and must be exact, move toward **controlled generative UI**. When you want interfaces created outside your application, move toward **open-ended generative UI**.

### The Catalog as Guardrail
The catalog is the guardrail that makes this approach safe: the agent can arrange and combine your components freely, but cannot step outside the set you approve. This balances creativity against predictability.

### How It Works
1. **Define a catalog** - declare what components the AI can use, with typed props
2. **Prompt the AI** - describe the UI you want in natural language
3. **AI generates a spec** - a JSON document describing the component tree
4. **Render safely** - json-render's `Renderer` renders the spec using your components

---

### Deeper Explanation: Declarative Wins Because It Is Reviewable

Declarative approaches (json-render, LangChain-style specs) share one property: the model's output is **data that a human can diff, store, and replay**. That makes them compatible with normal engineering practice â€” code review of the catalogue, snapshot tests of renderers, fixtures for evaluation â€” which is exactly what open-ended generation cannot offer.

A practical pipeline:

1. **Catalogue**: components with prop schemas and a description the model can reason about.
2. **Spec**: model emits `{ component, props, children }` validated against the catalogue.
3. **Renderer**: registry lookup with error boundaries, skeletons, and design-system primitives.
4. **Persistence**: store the validated spec (not the rendered HTML) so the view can be re-rendered, edited, and diffed later.
5. **Evaluation**: a fixture set of prompts with expected node types, run in CI when prompts or catalogues change.

### Additional Pitfalls
- **Storing rendered output instead of the spec.** You lose the ability to re-render, theme, or migrate.
- **Catalogue and renderer drifting.** Generate prop schemas from one source so they cannot diverge.
- **No evaluation fixtures.** Prompt changes become unmeasurable.
- **Letting the model choose props outside the design system.** Enums and tokens only; no raw colour/size values.

### Real-World Deal-Breakers
- **No catalog** → the AI generates components you don't have. Always define a catalog.
- **Using declarative for brand-critical surfaces** → the agent's layout may not match your design. Use controlled.
- **Not validating the spec** → malformed specs crash the renderer. Validate with Zod.
