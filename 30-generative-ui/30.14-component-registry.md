## 30.8 Component Registry (The Zod Contract)

### Subtopic Tree
- The registry maps catalog components to real implementations
- Zod schema per component
- Description for the AI (when to use it)
- Props validation before render
- Recursive tree rendering
- Fallback for unknown components
- Per-platform registries (web, mobile, CLI, MCP)

### The Catalog Definition
The catalog describes every component the AI is allowed to use. Each component has a **Zod schema for its props** and a **description that the AI reads** to understand when to use it.

```typescript
const catalog = defineCatalog(schema, {
  components: {
    Card: {
      description: "A card container with optional title and padding",
      props: z.object({
        title: z.string().optional(),
        padding: z.enum(["sm", "md", "lg"]).optional(),
      }),
    },
    Stack: {
      description: "Layout children vertically or horizontally with consistent spacing",
      props: z.object({
        direction: z.enum(["vertical", "horizontal"]).optional(),
        gap: z.enum(["sm", "md", "lg"]).optional(),
      }),
    },
    TextInput: {
      description: "A text input field with optional label and placeholder",
      props: z.object({
        label: z.string().optional(),
        placeholder: z.string().optional(),
        type: z.enum(["text", "email", "password", "number", "textarea"]).optional(),
      }),
    },
    Button: {
      description: "A clickable button with label and style variants",
      props: z.object({ label: z.string(), variant: z.enum(["primary", "secondary"]) }),
    },
  },
});
```

### The Registry
The registry maps each catalog component to its actual rendering implementation:

```typescript
const registry = {
  Card: ({ title, padding, children }) => (
    <div className={`card p-${padding}`}>{title && <h3>{title}</h3>}{children}</div>
  ),
  Stack: ({ direction, gap, children }) => (
    <div className={`flex flex-${direction} gap-${gap}`}>{children}</div>
  ),
  TextInput: ({ label, placeholder, type }) => (
    <label>{label}<input type={type} placeholder={placeholder} /></label>
  ),
  Button: ({ label, variant }) => (
    <button className={`btn-${variant}`}>{label}</button>
  ),
};
```

### Recursive Tree Rendering
```tsx
function renderNode(node: UINode, registry: Registry): React.ReactNode {
  const Component = registry[node.type];
  if (!Component) return <FallbackNode type={node.type} />;
  return <Component {...node.props}>{node.children?.map((c) => renderNode(c, registry))}</Component>;
}
```

### Per-Platform Registries
Create separate component registries for multi-surface rendering (web, mobile, CLI, MCP). The same catalog can render to different platforms with different component implementations.

---

### Deeper Explanation: The Registry Is The Contract

The component registry is the single artifact that defines capability, safety, and testability for generative UI. One entry per component, with the schema used for three purposes at once: advertising to the model, validating its output, and typing the renderer.

```ts
import { z } from 'zod';

export type WidgetDef<P> = {
  description: string;      // what the model reads â€” treat it as prompt engineering
  schema: z.ZodType<P>;
  Component: React.ComponentType<P>;
  heavy?: boolean;          // lazy-load instead of bundling
};

export const widgets = {
  metric: {
    description: 'A single labelled number with optional trend. Use for KPIs.',
    schema: z.object({ label: z.string().max(40), value: z.number(), delta: z.number().optional(), unit: z.enum(['usd', 'pct', 'count']) }),
    Component: MetricTile,
  },
  table: {
    description: 'A small table, max 6 columns and 50 rows. Use for structured comparisons.',
    schema: z.object({ columns: z.array(z.string().max(24)).min(1).max(6), rows: z.array(z.array(z.union([z.string(), z.number(), z.null()]))).max(50) }),
    Component: DataTable,
  },
} satisfies Record<string, WidgetDef<unknown>>;

export const catalogueForModel = Object.entries(widgets).map(([name, w]) => ({
  name,
  description: w.description,
  parameters: z.toJSONSchema(w.schema),
}));
```

### Additional Pitfalls
- **Descriptions treated as documentation rather than prompts.** The model only knows what the description says; ambiguity produces wrong choices.
- **Manually duplicated schemas.** Generate the model-facing JSON Schema from the same Zod schema the renderer validates with.
- **No `heavy` flag.** Bundling twelve chart libraries kills the initial load; lazy-load the heavy ones.
- **Registry entries without size or count caps.** Every prop schema needs bounds, or the model can exhaust the renderer.
- **No tests per entry.** Snapshot each component with a representative validated payload.

### Real-World Deal-Breakers
- **No Zod schema per component** → props are `any`; runtime errors from bad shapes.
- **No description** → the AI doesn't know when to use the component.
- **No fallback** → unknown component types crash the renderer.
- **Single registry for all platforms** → web components rendered on mobile. Use per-platform registries.
