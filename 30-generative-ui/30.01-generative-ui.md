### The Core Mental Model
Generative UI allows AI agents to generate tailored UI widgets in real-time, matching the interface to the user's specific interaction. Instead of returning a text response that a developer has to interpret, the model returns a **structured specification** describing what components to render, which the frontend maps to real React (or Vue, Svelte, Flutter) components.

The dominant pattern today - where an LLM generates Markdown that gets converted post-hoc to HTML - carries serious architectural costs: layout shifts as content reflows during conversion, zero type safety at the rendering boundary, and no path to component-level interactivity like Server Actions or client-side event handlers. Generative UI replaces plain-text LLM responses with interface components that stream and render as they are generated.

```text
LLM token stream → Structured JSON spec → Zod validation → Component registry → React tree
```

### The Three Paradigms

CopilotKit breaks Generative UI into three practical patterns, implemented using different agentic UI protocols:

| Paradigm | Control | Protocol | Description |
|----------|---------|----------|-------------|
| **Controlled** | High control, low freedom | AG-UI | Frontend owns the components; agent selects from a fixed set |
| **Declarative** | Shared control | A2UI, Open-JSON-UI | Agent returns a UI spec (cards, forms, lists in JSON); frontend renders from spec |
| **Open-ended** | Low control, high freedom | MCP Apps / Custom UIs | Agent returns a full UI surface, often an iframe or arbitrary HTML |

### Deeper Explanation: A Spectrum From Text To Arbitrary UI

Generative UI is not one thing; it is a spectrum, and where you sit determines your safety and complexity budget:

| Level | Model output | Control | Fits |
|---|---|---|---|
| Text only | Prose | Total | Answers, explanations |
| Structured text | Markdown/JSON data | Total | Summaries, tables of data |
| Declarative UI | Component tree from a fixed catalogue | High | Dashboards, forms, report builders |
| Tool-driven UI | Component chosen per tool call | High | Assistants with a widget vocabulary |
| Open-ended UI | Arbitrary components/markup | Low | Prototypes, canvas apps |

Most production value is delivered at the declarative and tool-driven levels, where the renderer is still entirely yours.

### Additional Pitfalls
- **Starting at the most open level.** It demos beautifully and fails audits, accessibility checks, and layout review.
- **No catalogue boundary.** Once the model can invent structure, your design system no longer constrains the product.
- **Confusing data with presentation.** Let the model decide *what* to show; the design system decides how.
- **No fallback renderer.** A rejected or invalid tree must degrade to text, not a blank screen.

### Real-World Deal-Breakers
- **`dangerouslySetInnerHTML` for LLM output** → XSS vulnerability. Use typed component trees instead.
- **No Zod validation at the stream boundary** → malformed JSON crashes the renderer.
- **No component registry** → you can't map JSON types to React components.
- **Choosing open-ended when declarative suffices** → unnecessary security surface. Start constrained.
