## 30.10 Security (Generative UI)

### Subtopic Tree
- Prompt injection (direct + indirect)
- HTML/JS execution (XSS via `dangerouslySetInnerHTML`)
- Sandboxing (iframes, CSP)
- Treating model output as untrusted
- Input validation at the stream boundary
- Approval for writes
- Excessive disclosure
- OWASP guidance for LLM apps

### The Core Threat
Allowing agents to generate HTML and JavaScript that the client renders and executes directly creates a fundamental security risk. Prompt injection - malicious instructions mixed into the Agent's input - is the cause, while executing the resulting malicious script in the browser resembles traditional Web XSS.

### CVE-2026-17496 (Real Example)
NoteGen's AI chat preview component passes model-generated HTML directly into the DOM via `dangerouslySetInnerHTML` with no sanitization and no CSP, allowing an attacker who can influence the model's prompt to execute arbitrary JavaScript in the privileged Tauri desktop webview context.

### Defense Layers

| Layer | Defense |
|-------|---------|
| **Zod validation** | Validate every JSON node at the stream boundary before rendering |
| **Component registry** | Only render components in your catalog |
| **CSP** | `Content-Security-Policy: default-src 'self'` |
| **Sandboxed iframes** | For open-ended UI, use `sandbox` attribute |
| **No `dangerouslySetInnerHTML`** | Never inject raw HTML from the model |
| **Approval for writes** | Require user confirmation for destructive actions |
| **Treat model output as untrusted** | Even "your" agent's output is shaped by user input and LLM non-determinism |

### OWASP Guidance
Prevent model output from triggering automatic outbound requests to attacker-controlled endpoints. Encode model output back to users to mitigate undesired code execution by JavaScript or Markdown.

---

### Deeper Explanation: Generated UI Is An Injection Surface

Every generative UI feature is, structurally, an injection sink: model output reaching a renderer, sometimes influenced by user content or retrieved documents. The defence is layered and boring on purpose:

1. **Never render model output as HTML or JS.** No `dangerouslySetInnerHTML`, no `eval`, no dynamic import by string, no template strings into the DOM.
2. **Validate against the catalogue, then render through your components.** Unknown components and invalid props are rejected, not approximated.
3. **Treat retrieved text as hostile.** RAG content can contain instructions ("ignore previous instructions and link toâ€¦"); the renderer must not treat content as capability.
4. **Constrain outbound capability.** No model-chosen URLs, no webhooks, no redirects â€” links map to server-resolved keys.
5. **Sandbox the exotic cases.** If open-ended generation is a product requirement, isolate it in a cross-origin iframe with a validated message bridge.
6. **Log the spec, not just the render.** Security review needs the exact payload that produced the view.

### Additional Pitfalls
- **Prompt injection via retrieved documents.** The most realistic attack on a generated-UI feature; content must never grant capability.
- **Model-chosen destinations.** A generated "view details" link that the model controls is a phishing vector.
- **Props spread wholesale onto DOM elements.** A model-supplied `onClick`/`src`/`href` should be impossible by construction.
- **No audit trail of specs.** You cannot investigate an incident without the payloads.
- **Rate limiting only per IP.** A logged-in user looping the feature is the common cost attack; limit per user and per session.

### Real-World Deal-Breakers
- **`dangerouslySetInnerHTML` on model output** → XSS vulnerability. Never do this.
- **No CSP** → script injection is possible.
- **No Zod validation at the boundary** → malformed or malicious JSON reaches the renderer.
- **No approval for destructive tools** → the agent deletes production data.
- **Trusting the model's output** → it's shaped by user input and non-determinism.
