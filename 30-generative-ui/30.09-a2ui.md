### What A2UI Is
A2UI v0.9 is a framework-agnostic standard for declaring UI intent. It allows local or remote agents to communicate with any client application using a common language, ensuring your agent can generate your UI using your existing component catalog on any device.

The protocol uses a **unidirectional stream of JSON messages** from the agent to the renderer to describe and update the UI. The renderer consumes this stream and renders native components - without executing arbitrary code.

### The 5-Step Integration
```python
# Step 1: Define your catalog (basic or bring your own)
my_catalog = CatalogConfig.from_path(
    name="<MY_CATALOG_NAME>",
    catalog_path="file:///path/to/catalog.json",
    examples_path="path/to/examples/folder/*.json",
)

# Step 2: Initialize the Schema Manager
schema_manager = A2uiSchemaManager(version="0.9", catalogs=[my_catalog])

# Step 3: Generate the System Prompt
system_instruction = schema_manager.generate_system_prompt(...)
```
Adding A2UI to any Python agent is now a simple `pip install` or `uv add` away.

### Renderers
A2UI supports Flutter, Lit, Angular, React, and Jetpack Compose (Android). The Jetpack Compose renderer maps the A2UI JSON protocol to native Compose components without executing arbitrary code.

### Deeper Explanation: Agent-to-UI As A Negotiated Contract

Agent-to-UI protocols (A2UI and similar) standardise the envelope between an agent runtime and a client renderer: capability advertisement, event framing, and component declarations. The reason to adopt one rather than inventing your own is **interoperability** â€” the same renderer can serve several agents or models, and the same agent can target several clients (web, desktop, mobile).

The design questions a protocol must answer: what capabilities does this client support (component list, versions)? How are streaming frames framed and resumed? What happens when the agent emits a component the client does not know? Who owns state â€” agent, client, or shared session?

The last one is where most implementations stumble: without an explicit session id and resumable sequence, reconnects produce duplicated or missing UI.

### Additional Pitfalls
- **Assuming a shared state model.** Define ownership explicitly; "both sides mutate" produces divergence.
- **No capability negotiation.** A new agent feature breaks older clients unless components are declared and degraded.
- **Ignoring resumption.** Long agent runs will be interrupted; sequence numbers and replay are mandatory.
- **Adopting a protocol for a single client.** If you will never have a second renderer, a small in-house frame format is cheaper.

### Real-World Deal-Breakers
- **Assuming A2UI requires Google Cloud** → it's framework-agnostic and open. Works with any agent, any client.
- **Not using the catalog** → the agent generates components you don't have. Always define your catalog.
- **No transport strategy** → A2UI over WebSockets is different from A2UI over REST. Pick based on your architecture.
- **Ignoring client-defined functions** → validation logic can run on the client, reducing server round-trips.
