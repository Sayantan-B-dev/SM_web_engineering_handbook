## Tool-Driven UI

### Subtopic Tree
- Tools as the model's only action surface
- A tool per UI capability (`render_chart`, `show_form`, `highlight_row`)
- Tool arguments as props for pre-built UI components
- Streaming a tool call before its arguments finish
- Server tools vs client tools vs UI-only tools
- Mapping tool results back to model turns
- Approval flows for mutating UI actions
- Failure and empty states

### The Mental Model
Instead of asking the model to describe a UI, expose **UI capabilities as tools** whose arguments are the props of a real, reviewed component. The model's job becomes selection plus parameters: "call `show_timeseries` with these points and this title". The app owns the rendering, the styling, and the constraints â€” so a hallucinating model can produce a wrong chart, never a broken page or an injected script.

```ts
import { z } from 'zod';

// UI tools: each maps to one component in the app, with a strict prop schema.
export const showTimeseries = {
  name: 'show_timeseries',
  description: 'Render a time series chart. Use for data that changes over time.',
  schema: z.object({
    title: z.string().max(60),
    series: z.array(z.object({ label: z.string().max(24), points: z.array(z.number()).min(2).max(365) })).min(1).max(4),
    interval: z.enum(['day', 'week', 'month']),
  }),
  render: (props) => <TimeSeries {...props} />,
};
```

```tsx
// Rendering happens per tool call, so partial streams can show a skeleton with the title
function ToolCallCard({ call }: { call: ToolCall }) {
  const tool = registry[call.name];
  if (!tool) return <FallbackCard message={`Unsupported: ${call.name}`} />;

  const parsed = tool.schema.safeParse(call.arguments);
  if (!parsed.success) return <FallbackCard message="The assistant asked to render something invalid." />;

  return call.status === 'streaming' ? <Skeleton title={call.arguments.title} /> : tool.render(parsed.data);
}
```

### Real-World Deal-Breakers
- **A generic `render_html` tool.** It hands arbitrary markup and scripts to the model; UI tools must be typed and narrow.
- **Tool arguments trusted without validation.** Validate against the same schema you advertised, on the server if the tool mutates anything.
- **One giant `render_dashboard` tool with ten optional fields.** Small models fill optional fields wrongly; prefer several focused tools with enums.
- **No fallback for unknown tools.** A stale client or a new model version will call tools you no longer support; render a graceful placeholder.
- **Mutating UI actions with no approval.** A tool that submits a form or changes data needs a confirmation step and a dry run.
- **Streaming skeletons that shift layout.** Reserve the final size so the skeleton does not jump when the component mounts.
