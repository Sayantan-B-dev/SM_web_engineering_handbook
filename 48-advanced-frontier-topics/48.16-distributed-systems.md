## 48.16 Distributed Systems

### Subtopic Tree
- Edge compute for proximity-sensitive work: routing, auth, personalization
- Data-heavy queries belong in a region co-located with your database
- Edge rendering: execution closer to the user
- Routing Middleware runs before the cache
- Streaming SSR + edge distributed execution + microfrontend modularity
- Orchestration for low-latency systems: resolving dependencies, tracking cache identity, running local inference, timing execution

### The Key Insight
The distributed system underneath is where teams get wrecked, not because composable architecture is wrong. **Edge compute belongs on proximity-sensitive work like routing, auth, and personalization; data-heavy queries belong in a region co-located with your database**.

### Edge Rendering
Edge rendering shifts execution closer to the user. As latency expectations shrink and personalization demands grow, traditional origin-based rendering fails to keep up. Edge rendering is **rapidly redefining how modern frontend systems are designed, deployed, and experienced by users**.

### The 2026 Frontend Architecture
Frontend architecture has moved in a different direction: **rendering on the server, execution at the edge, and less JavaScript in the browser**. From streaming SSR to edge distributed execution and microfrontend-driven modularity, performance, modularity, and distributed execution define success.

### Deeper Explanation: The Frontier Runs On The Same Fundamentals

Everything at the frontier â€” collaborative editors, offline-first apps, edge compute, agent fleets â€” is a distributed system, and the fundamentals are unchanged: partial failure, ordering, idempotency, consistency, and observability. What is new is that these problems now appear in the browser: a tab is a replica, the network is unreliable, and the user's device can suspend at any moment.

The practical checklist: every write carries an idempotency key, every read states its consistency expectation, every timeout has a retry policy with jitter and a cap, every workflow has a compensation path, and every hop contributes to a trace. Applications that respect these rules stay debuggable as they grow; those that do not accumulate failures that appear random.

### Additional Pitfalls
- **Assuming reliable delivery from a browser.** Reconnects, suspensions, and background throttling are normal.
- **No idempotency.** Duplicate submissions and double effects.
- **Retries without backoff or caps.** Self-inflicted outages.
- **Mixed consistency expectations.** Reads must declare whether staleness is acceptable.
- **Observability added later.** Distributed debugging without traces is guesswork from day one.

### Real-World Deal-Breakers
- **Edge compute for database queries** → cold start + database latency > origin latency. Keep data-heavy queries in the database region.
- **No cache identity tracking** → edge functions can't coordinate cache invalidation.
- **No orchestration** → micro-frontends send multiple requests before rendering. Use framework-aware orchestration.
