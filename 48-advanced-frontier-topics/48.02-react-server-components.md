## 48.2 React Server Components

### Subtopic Tree

### What They Are
React Server Components (RSC) are a new React paradigm where components render exclusively on the server, sending only HTML to the client. **Next.js App Router makes Server Components the default rendering strategy**. As of 2026, RSC is the **recommended approach for new React applications**, with mature framework support in Next.js.

### Framework Support
Next.js App Router is the **most production-ready and mature RSC implementation available today**. React Router v7 has RSC support in active development - an early, unstable version is available to try in v7.9.2, but it's **not yet recommended for production**.

### Next.js 16.2 LTS (April 2026)
Covers App Router, **Cache Components (replacing experimental_ppr)**, streaming SSR, Server Actions, and React 19 patterns for server-first architecture. Turbopack is the default bundler.

### Deeper Explanation: The Server/Client Split Is An Architectural Boundary

RSC splits components by *where they run*, not by what they render: Server Components run only on the server, can be async, and ship no JavaScript; Client Components are interactive and hydrate. The boundary is declared with `'use client'` and it propagates downward, which means it is an architectural decision â€” everything below a client component becomes client code.

The practical consequences: push data fetching up into server components (no waterfalls, fewer bundles), keep interactive leaves small and deep (so the client bundle stays thin), pass serialisable props across the boundary, and use Suspense boundaries to stream. The mental model to keep: the server component tree is the *shell*, and client components are the *islands* embedded in it.

### Additional Pitfalls
- **`'use client'` near the root.** The whole tree becomes client code and you lose the benefit.
- **Passing functions or class instances across the boundary.** They are not serialisable.
- **Fetching data inside client components when it could be on the server.** Waterfalls and larger bundles.
- **No Suspense boundaries.** Streaming degrades into one slow render.
- **Treating RSC as a rendering optimisation only.** Its main wins are bundle size and data access.

### Real-World Deal-Breakers
- **Using hooks in Server Components** → build error. Server Components have a limited API.
- **Passing event handlers from Server → Client Components** → functions aren't serializable. Define handlers inside Client Components.
- **No Suspense boundaries** → the entire page blocks until every async component resolves.
