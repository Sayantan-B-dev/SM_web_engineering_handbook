### What's New in 2026
**SharedWorkers now ship in ALL browsers** (Safari joined in 2022). Performance benchmarks show SharedWorker = **shared application heap across browser windows**.

### Extended Lifetime (Edge 148)
Shared Worker's lifetime has been extended. When creating a shared worker, you can set the **`extendedLifetime` option** to keep the worker alive for a limited time after all client pages have closed.

### When to Use Which Worker

| Worker Type | Use when |
|-------------|----------|
| **Dedicated Web Worker** | Expensive work needed by one page |
| **Shared Worker** | Live coordination among same-origin tabs |
| **Service Worker** | Request interception and offline behavior |

### Neo.mjs Multi-Window Pattern
Neo.mjs has supported native multi-window applications via SharedWorkers since its GA release in November 2019. The App Worker (SharedWorker) owns all application state - windows are purely rendering surfaces. The SharedWorker pattern **eliminates the coordination complexity entirely**.

### Deeper Explanation: The Default Home For Heavy Work

As apps get heavier, "which thread?" becomes as natural a question as "which layer?". Workers are the only escape from the main thread, and the frontier pattern is a small fleet: one worker per concern (parsing, search indexing, diffing, crypto), each with a typed protocol, cancellation, and warm-up. WASM modules live inside those workers.

The decision rule from chapter 23 still applies: offload when the work exceeds a frame and the payload can be transferred or kept small; otherwise keep it local and chunk it. What is new at the frontier is more reliance on workers because apps increasingly run models, parsers, and codecs client-side.

### Additional Pitfalls
- **A single worker for everything.** One long job blocks the rest; pool or shard by concern.
- **Chatty protocols.** Clone cost on the main thread can exceed the work moved.
- **No cancellation.** Background jobs keep running after the user moves on.
- **Ignoring mobile capacity.** More workers than cores increases contention and throttling.
- **No error surface.** A crashed worker must restart and report, not fail silently.

### Real-World Deal-Breakers
- **Using PostMessage chains for multi-window apps** → coordination complexity explodes. Use SharedWorkers instead.
- **Service Worker for application state** → wrong abstraction (designed for caching, not application state).
- **No SharedArrayBuffer for shared state** → each worker has its own memory. Use SharedArrayBuffer with COOP/COEP.
