## 48.15 Observability

### Subtopic Tree

- Frontend Observability is the managed (Grafana Cloud) surface

### The Stack
Grafana Faro is the OSS + Grafana Cloud RUM (Real User Monitoring) - a web SDK that captures **page load metrics, route changes, errors, user interactions**, and ships as **OTel-compatible telemetry**. Faro runs in the browser and instruments your app, shipping telemetry through the platform collector (Alloy) into the shared observability stores: errors and events land in **Loki**, browser spans in **Tempo**, and Core Web Vitals in **Mimir**.

### Critical Configuration
- `beforeSend` PII filtering
- `propagateTraceHeaderCorsUrls` (without this, browser traces never connect to backend spans)
- `app.version` for release tracking
- `paused` on localhost
- Error boundary to catch React errors

---

### Deeper Explanation: One Journey, Correlated Signals

The frontier of frontend observability is correlation: a user interaction produces metrics, logs, an error event, and a trace that all share an identifier, so an incident can be followed from the browser to the database without guesswork. That requires propagating trace context from the client, sampling deliberately (head sample plus keep-all-errors), and enforcing privacy centrally in a collector rather than in each service.

The budget discipline is part of the design: cap frontend sampling, never label metrics with high-entropy values, define retention per signal, and alert on user-visible symptoms with a runbook link. Observability that costs more than it saves in incident time gets cut in the next budget cycle.

### Additional Pitfalls
- **Signals that do not correlate.** Without a shared trace id, debugging is timestamp archaeology.
- **Redaction implemented per service.** One omission leaks data; centralise in the collector.
- **Cardinality explosions.** User ids and full URLs as metric labels create five-figure bills.
- **Alerts without owners or runbooks.** They get muted within a month.
- **Instrumentation on the critical path.** Telemetry must never slow the interaction it measures.

### Real-World Deal-Breakers
- **No `beforeSend` PII filter** → user emails, tokens logged to observability stores.
- **No `propagateTraceHeaderCorsUrls`** → browser traces never connect to backend spans. You have two disconnected halves.
- **No `app.version`** → errors can't be filtered by deploy.
- **No sourcemap upload** → stack traces minified and useless.
