## 48.4 Distributed Browser Computing

### Subtopic Tree
- Edge-Net: distributed P2P browser compute network
- Browser visitors contribute idle CPU cycles via Web Workers running Rust/WASM
- SwarmLLM: splits 27B model across browser tabs, 10KB hidden state per token over WebRTC
- Cloudflare Kitesurf: agent-native browser runtime on V8 isolates
- Wasimoff: computation offloading using WebAssembly bytecode

### What It Is
Distributed browser computing is the idea that **browser visitors can contribute idle CPU cycles** to a distributed compute network. Edge-Net is a distributed P2P browser compute network where browser visitors contribute idle CPU cycles via Web Workers running Rust/WASM.

### SwarmLLM (September 2026)
SwarmLLM published a public MIT licensed browser runtime and a **September 7, 2026 demo that splits Qwen 3.8 27B across browser tabs** and sends an approximately **10 KB hidden state per generated token over direct WebRTC links**.

### Cloudflare Kitesurf (August 2026)
Cloudflare's Kitesurf is the **first agent-native browser runtime**. The browser runs on the same V8 isolate infrastructure that powers Cloudflare Workers - meaning agent workloads execute in the same edge-compute environment that already handles a significant share of global web traffic.

---

### Deeper Explanation: Users As A Compute Fleet

The idea is to use many browser sessions as a distributed compute pool (a "browser-based supercomputer") for embarrassingly parallel work. Technically it is feasible: WASM for compute, workers for parallelism, WebRTC/websockets for dispatch, and a scheduler that respects device capacity. Practically it is a trust and economics problem before it is an engineering one: you are spending someone else's CPU, bandwidth, and battery, and any real deployment needs explicit consent, fair scheduling, throttling on constrained devices, and a credible incentive.

Legitimate near-term versions are narrower: volunteer computing for a cause, cooperative rendering farms for a shared render job, or internal batch work on managed machines. For most products the honest answer is a server or a cloud function.

### Additional Pitfalls
- **Borrowing CPU without consent.** Battery, thermals, and metered data are the user's cost.
- **Assuming reliable participation.** Tabs close, laptops sleep; tasks must be checkpointed and re-queued.
- **No verification of results.** Untrusted clients can return wrong answers; require redundant verification or spot checks.
- **Ignoring device classes.** A phone throttles and dies; capacity must be declared and respected.
- **Underestimating coordination.** Scheduling, retries, and result validation dominate the work.

### Real-World Deal-Breakers
- **No privacy controls** → contributing CPU cycles to a distributed network means running untrusted code. Sandboxing is mandatory.
- **Network reliability** → P2P browser compute depends on users keeping tabs open. Not suitable for critical workloads.
- **WebRTC signaling** → requires a signaling server (or QR-code-based signaling like QWBP).
