## 48.3 Concurrent React

### Subtopic Tree
- `useTransition` - mark state updates as non-blocking
- `useDeferredValue` - defer a value so expensive renders don't block urgent updates
- React 19 flips the model - concurrent features are now default
- Suspense integration
- Prioritizing urgent updates over less important ones

### What It Is
React's concurrent features allow you to keep your app responsive during expensive updates. These features include **transitions, deferred values, and concurrent rendering**, which help prioritize urgent updates over less important ones.

### `useTransition` vs `useDeferredValue`

| Hook | Use when |
|------|----------|
| `useDeferredValue` | A single value is expensive to render |
| `useTransition` | Multiple state updates, some non-critical |
| `useTransition` (has `isPending`) | Need loading indicator for transition |

### React 19 Change
React 19 **flips the model** - you no longer have to wrap updates in `startTransition` or use `useDeferredValue` explicitly to get any benefit.

---

### Deeper Explanation: Interruption Is The Feature

Concurrent rendering lets React prepare, pause, and abandon renders so urgent updates (typing, clicking) are not blocked by expensive ones (filtering a huge list, transitioning a view). That is why the APIs look unusual: `useTransition` marks work as interruptible, `useDeferredValue` keeps a stale value while a new one is computed, and Suspense boundaries let React keep showing the previous UI while new content loads.

The discipline is prioritisation, not parallelism: your code still runs on one thread, so the win comes from not blocking the *urgent* work. Used well, it removes jank and loading flashes; used carelessly (deferring everything, or using fake timers to simulate it), it just delays work and confuses the UI about what is happening.

### Additional Pitfalls
- **Transitioning everything.** Users lose feedback that anything is happening.
- **Deferred values without a pending indicator.** The UI silently shows stale data.
- **Blocking work in effects during a transition.** It defeats the prioritisation.
- **Treating concurrency as threading.** It does not add CPU; move real work to a worker.
- **No measurement.** Compare INP and dropped frames before and after.

### Real-World Deal-Breakers
- **Putting the input value in `startTransition`** → laggy typing. The input's own value must be urgent.
- **Using `useDeferredValue` for cheap renders** → no benefit, adds complexity.
- **`isPending` is a heuristic** → may flicker on fast transitions.
