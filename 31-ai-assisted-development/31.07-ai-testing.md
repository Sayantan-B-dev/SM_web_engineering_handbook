### Löb - End-to-End Tester
Löb is an LLM in a tool-use loop. It reads your git diff, decides what to test, drives the running app in a **real Chromium browser**, checks the side effects directly in **Postgres, Redis, the logs and the API**, and files a GitHub issue with evidence when something breaks. For voice apps, it also speaks to the app, with synthesized speech injected into the browser's microphone. **There is no test script.** Each step, the model picks the next tool from what it has observed so far.

```bash
loeb run "Test sign-up with a new email"  # terminal dashboard
loeb run                                   # agent decides what to test from the diff
loeb run --dry-run                         # reads diffs, proposes plan, runs nothing
loeb run --ci "Test sign-up"               # no UI; exit 0 pass, 1 bugs found, 2 error
```
Named after Löb's theorem, which implies a formal system can't vouch for its own soundness. **Löb is the outside check: an agent's claim that its code works counts only when the running app confirms it.**

### Deeper Explanation: Generated Tests Need Adversarial Review

AI is genuinely good at producing test scaffolding: edge cases for a validator, table-driven cases for a parser, Playwright flows for a journey. The risk is subtler than wrong tests: models write tests that **encode the implementation's behaviour, including its bugs**, and they occasionally weaken assertions to make failures disappear.

Reviewing generated tests therefore focuses on the assertions, not the arrangement:

- **Does each test fail if the behaviour breaks?** Mutation-test the critical ones.
- **Are the expectations independent of the implementation?** Compare against a spec, not the code.
- **Do the edge cases exist?** Empty, null, boundary, concurrency, error paths.
- **Did any existing test change?** Weakened assertions in a diff are a red flag.

### Additional Pitfalls
- **Accepting assertion changes in diffs.** The single most dangerous AI-assisted change to a test suite.
- **Hundreds of near-duplicate cases.** They slow CI and add no coverage; keep representative cases.
- **Testing implementation details.** Generated tests often assert internals, which then break on every refactor.
- **No mutation or coverage guardrail.** A test suite that cannot fail review is an illusion of safety.

### Real-World Deal-Breakers
- **Using AI testing without real browser verification** → Löb's insight: "an agent's claim that its code works counts only when the running app confirms it."
- **No side-effect verification** → Löb checks Postgres, Redis, logs, and the API directly. Test results alone are insufficient.
- **Assuming AI test generation is enough** → generated tests can be fragile. Use agents for maintenance and triage, not just generation.
