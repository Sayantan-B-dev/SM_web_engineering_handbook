### Deeper Explanation: Inline Completion Is A Latency Product

Copilot's core value is sub-300 ms suggestions in the editor, which means its context is deliberately narrow (open file, recent edits, some repo signals). Understanding that explains both its strengths and its failure modes: it is excellent at patterns already visible in the file and poor at global consistency it cannot see.

Getting value out of it is mostly about *feedback density in the file*: imports, types, and a couple of representative examples nearby make suggestions dramatically better. It also shines at mechanical breadth â€” tests for a module, repetitive branches, translating one pattern into another.

Where it needs supervision: anything security-sensitive (a suggested `eval`, a regex, a SQL string), anything with API drift (it may suggest a deprecated call), and anything where you have not decided the design yet (it will answer the wrong question fluently).

### Additional Pitfalls
- **Accepting multi-line suggestions without reading.** The classic incident shape is a subtly wrong conditional.
- **Leaving licensed code in place.** Public-code filters reduce but do not eliminate the risk; review unusual blocks.
- **Letting it define your conventions.** It mirrors what is nearby, including existing inconsistencies.
- **Trusting completion for tests.** Generated tests can assert the implementation's bugs; check the assertions by hand.

### Real-World Deal-Breakers
- **Using Copilot for complex, long-horizon tasks** → Copilot is strongest for inline completions and GitHub-native workflows. For deep reasoning, use Claude Code.
- **No enterprise governance** → Copilot enterprise requires SSO, audit logs, and zero-data-retention mode for sensitive repos.
- **Assuming Copilot Free is enough** → 50 agent requests/month runs out fast for production work.
