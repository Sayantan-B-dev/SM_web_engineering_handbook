### What Vibe Coding Is in 2026
When Karpathy introduced the term in early 2025, he described a workflow where a developer "fully gives in to the vibes, embrace exponentials, and forget that the code even exists." The 2026 reality is **significantly more disciplined**. Vibe coding now means a developer writes natural-language specs, and AI generates code under structured human oversight, with multi-model orchestration, persistent project context, and layered validation. It is **not no-code**, and it is **not low-code**.

### The Four-Stage Loop
```
Prompt → Generate → Review → Refine
  ↑                              │
  └──────────────────────────────┘
```

Each stage demands a distinct skill set:
- **Prompting** compresses architectural decisions into natural language.
- **Generation** is the AI producing a first draft.
- **Review** is where engineering discipline lives, applying human judgment to AI output against production standards.
- **Refinement** closes the loop, feeding targeted corrections back to the AI to produce improved output without regenerating from scratch.

**The most common failure pattern**: treating the Generate stage as the finish line. Review and Refine consume a significant share of total effort and represent the **highest-value human contribution** (emphasis is my interpretation of the source).

### When to Use Vibe Coding
✅ MVPs, prototypes, internal tools, solo projects, CRUD-heavy applications
✅ When the developer understands the domain well enough to evaluate output quality
✅ When speed of iteration matters more than micro-level optimization

### When NOT to Use
❌ Safety-critical systems (medical devices, avionics)
❌ Highly regulated codebases requiring formal verification
❌ Performance-sensitive low-level code where memory layout and instruction-level optimization matter

### Deeper Explanation: Vibe Coding Is A Prototyping Method

Vibe coding â€” iterate with the model until it works, reading little of the code â€” is excellent for exploration and dangerous as a production method, and both halves are true for structural reasons:

- **Exploration**: the goal is learning, the cost of being wrong is zero, and speed dominates. Fast feedback plus a prototype scope is exactly where loose iteration shines.
- **Production**: the goal is durability, the cost of being wrong is high, and the repository outlives the session. Debt compounds invisibly when nobody read the diff.

The mature version is a **graduation path**: prototype fast with loose iteration, then before it reaches users, rewrite or harden the parts that matter â€” tests, error handling, accessibility, security, and a design that a colleague can change next month. Document the boundary so everyone knows which code is a sketch.

### Additional Pitfalls
- **Vibe-coded code reaching production without hardening.** The bug appears in the one state nobody tested.
- **No tests at all.** Without a safety net, the second iteration breaks the first feature.
- **Missing security review.** Generated code frequently misses authorisation and input validation.
- **Abandoned prototypes in the main branch.** They become maintenance burden nobody owns.
- **No licence or dependency review.** Prototype dependencies sneak into production.

### Real-World Deal-Breakers
- **Treating Generate as the finish line** → Review and Refine are the highest-value stages. The most common failure pattern.
- **Vibe coding safety-critical systems** → AI generates plausible code, not provably correct code.
- **No spec** → prompt engineering functions as software architecture. A vague spec produces vague code.
- **No review discipline** → you must be able to explain every line. "If you cannot trace the data flow from input to output, do not ship it."
