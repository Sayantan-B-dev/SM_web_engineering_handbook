### The Data
An IEEE study analyzing five LLMs found that **49 out of 120 samples (40.8%)** were identified as vulnerable, 65 (54.2%) as secure, and 6 (5.0%) partially vulnerable.

Framework-constrained program generation showed **alarmingly high rates (18%-50%)**, particularly in **Authentication & Identity** and **Cookie Management** scenarios (up to **83%** and **78%** respectively).

Veracode's 2026 benchmark found known vulnerabilities in roughly **44%** of AI code-generation tasks, including cryptographic misconfiguration and insecure resource handling.

Georgia Tech's Vibe Security Radar found about 18 cases across seven months in 2025, then **56 cases in the first three months of 2026** - with March 2026 alone having 35. Of 74 confirmed cases, **14 are critical risks and 25 are high**. These include command injection, authentication bypass, and server-side request forgery.

### Common Vulnerabilities in AI-Generated Code
- Client-side-only authentication
- Browser-exposed API keys
- Permissive or missing Supabase Row-Level Security policies
- Command injection
- Authentication bypass
- Server-side request forgery (SSRF)
- Insecure code patterns inherited from training data
- Supply-chain risks

### AIALIB (2026)
A threat library for AI-generated code that systematically generates, analyzes, and structures potential vulnerabilities from LLM-produced code.

### Deeper Explanation: Generated Code Inherits Statistical Habits

Models learn from the world's code, including its insecure patterns: string-concatenated SQL, `eval` in templates, permissive CORS, secrets in `.env.example` that get committed, and authorisation checked in the UI only. None of this is malice; it is prevalence. So generated code needs the same review lens as a junior engineer's first pull request â€” plus extra attention to four categories:

- **Authorisation** â€” checks must be server-side, per resource, not just "is logged in".
- **Secrets and configuration** â€” no keys in code, examples, or client bundles.
- **Dependencies** â€” new packages arrive with licences, maintenance status, and supply-chain risk.

Automate the mechanical parts: SAST in CI, dependency scanning, secret scanning, and an allow-list for new dependencies.

### Additional Pitfalls
- **Trusting that generated code was reviewed because it compiled.** Security is not a compiler property.
- **Ignoring new dependencies.** Typosquats and abandoned packages are common in suggestions.
- **Client-side-only authorization.** Generated guards often live in components; they must be mirrored server-side.
- **Prompt-injected instructions in context.** Files or issues read by an agent can attempt to change its behaviour; treat them as data.

### Real-World Deal-Breakers
- **Assuming AI code is secure** → 40.8% vulnerable. Always do a security pass.
- **No security review** → AI code is not secure by default. It inherits vulnerabilities from training data.
- **Client-side-only auth** → a common AI-generated vulnerability. Always validate server-side.
- **Browser-exposed API keys** → AI may embed secrets in frontend code. Use a BFF.
- **Missing RLS policies** → AI-generated Supabase schemas often lack Row-Level Security.
