### What to Actually Measure
- **actualDuration per component** - how long its render took.
- **Total commit time** - how long the browser was blocked.
- **Re-render frequency** - how many times a component re-renders per interaction.
- **Long tasks** - any synchronous block > 50ms.

### Frame Budget
For 60fps, each frame has **16.67ms**. If your render + commit exceeds that, frames drop. React's Profiler flamegraph makes it obvious which component is eating the budget.

### Reading the Flamegraph
- **Width** = time spent rendering that component (self + children).
- **Color** = whether it rendered (gray = skipped).
- **Height** = tree depth.
- **Click a bar** → see exact reason for render.

### `performance.mark` / `performance.measure` for Micro-Benchmarks
```javascript
performance.mark('calc-start');
const result = expensiveCalculation(data);
performance.mark('calc-end');
performance.measure('calc', 'calc-start', 'calc-end');
const [measure] = performance.getEntriesByName('calc');
console.log(measure.duration); // ms
```
This is more precise than wrapping in `useMemo` and guessing whether it helped.

### StrictMode Double-Render Confusion
In dev StrictMode, components render twice. The Profiler shows **both** renders. A component that looks "slow" may only be slow because you're seeing two renders. Compare dev vs production profiling to see the real cost.

### Real-World Deal-Breakers
- **Optimizing without profiling** → "feelings don't ship reliable software"; you may make things slower.
- **Optimizing the wrong component** → the flamegraph's widest bar is often a parent whose *children* are slow, not the parent itself.
- **Ignoring commit time** → DOM mutations and layout effects can be the bottleneck, not render.
- **Assuming a slow dev render = slow production** → StrictMode doubles renders; production doesn't.
