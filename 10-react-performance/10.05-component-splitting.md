## 10.5 Component Splitting

### Subtopic Tree
- Splitting large components into smaller ones
- Co-locating state to limit re-render scope
- Moving state down
- Separating "hot" state from "cold" subtrees
- Extracting expensive subtrees into memoized children
- Container / presentational split
- Suspense boundaries as split points

### Why Splitting Helps Performance
In React, when a component's state changes, the component and **all its descendants** re-render. If a `Parent` holds `count` state and renders an `ExpensiveList` that doesn't depend on `count`, the list re-renders anyway.

**Fix 1 - Move state down:**
```jsx
// ❌ App-level state re-renders everything
function App() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveList items={items} />
    </>
  );
}

// ✅ Extract counter into its own component
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
function App() {
  return (
    <>
      <Counter />
      <ExpensiveList items={items} />
    </>
  );
}
```
Now only `Counter` re-renders on click.

**Fix 2 - Extract expensive subtree as a memoized child:**
```jsx
const ExpensiveList = React.memo(function ExpensiveList({ items }) { ... });
// Parent passes stable `items` reference → list skips re-render
```

**Fix 3 - Suspense boundary as split point:**
Each `<Suspense>` boundary hydrates and renders independently. A slow sibling doesn't block a fast one.

### Real-World Deal-Breakers
- **One giant component with mixed concerns** → every state change re-renders the whole tree.
- **Lifting state too high** → global-ish state forces wide re-renders; co-locate.
- **Extracting but not memoizing the child** → child still re-renders (parent did), just less code in the parent.
- **Splitting into too many tiny components** → more function calls, more fiber nodes, more overhead; split at **state boundaries**, not arbitrarily.
