### What Smart Contracts Are
Smart contracts concentrate high-value assets and complex logic in small, immutable programs, where even minor bugs can cause major losses. They are self-executing programs deployed to the blockchain, with code and state stored on-chain.

### Solidity in 2026
Solidity is the most widely used smart contract language, with **116 versions published as of February 2026**. Solidity 0.8+ introduced built-in overflow checks, eliminating an entire class of vulnerabilities.

### The Eight Root-Cause Families of Vulnerabilities
A 2026 attack-centric taxonomy unifies Solidity vulnerabilities into **eight root-cause families** covering control flow, external calls, and more. The most critical:

| Vulnerability | Description | Historical example |
|--------------|-------------|-------------------|
| **Reentrancy** | External call re-enters the contract before state update | The DAO hack (2016) |
| **Access Control** | Missing or incorrect permission checks | Parity Wallet freeze (2017) |
| **Integer Overflow** | Arithmetic exceeds type bounds | BatchOverflow (2018) |
| **Front-running** | Transaction ordering manipulation | MEV extraction |
| **Oracle Manipulation** | Price feed manipulation | DeFi exploits |

Reentrancy remains one of the most critical classes of vulnerabilities in Ethereum smart contracts, yet widely used detection tools and datasets continue to reflect outdated patterns and obsolete Solidity versions.

### Deeper Explanation: Contracts Are APIs With Permanent Semantics

For a frontend engineer, a deployed contract is an API where the interface is public, the implementation is immutable (or upgradeable behind a proxy), and calls split into two kinds:

- **`view`/`pure` reads** â€” free, instant, callable via RPC without a transaction (still rate-limited by your provider).
- **State-changing writes** â€” a transaction must be signed, mined, and confirmed; it costs gas and can revert.

Integration specifics that matter: the **ABI** is the typed interface (generate TypeScript types with wagmi/viem from the ABI), events are the reliable history source, and **reverts** return machine-readable reasons only if the contract uses custom errors. Upgradeable contracts (proxy patterns) mean the address is stable but behaviour can change â€” a security consideration to disclose, not just an implementation detail.

### Additional Pitfalls
- **Calling a write as if it were a read.** Users then wonder why nothing happened; writes need wallet interaction.
- **Not handling reverts.** Give the user the reason (map custom errors to human messages).
- **Trusting an ABI you did not pin.** Verify the deployed bytecode/ABI for the address you are calling.
- **Ignoring upgradeability.** "Immutable protocol" claims may be false; check the proxy admin.
- **No slippage/deadline parameters in DeFi interactions.** Users lose funds to price movement.

### Real-World Deal-Breakers
- **No audit** → even minor bugs can cause major losses. Every production contract needs an audit.
- **Using outdated Solidity** → the compiler version itself is a risk. CompileGuard detects this.
- **Ignoring reentrancy** → it's still the most critical class of vulnerability in 2026.
- **Upgradeable contracts without governance** → proxy patterns allow admin to change logic. Users must trust the admin.
- **No formal verification** → for high-value contracts, formal verification is the only way to prove correctness.
