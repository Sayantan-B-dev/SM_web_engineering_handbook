### The Core Mental Model
Web3 is based on blockchain technology and represents an internet form of "read-write + own," with the core goal of achieving user sovereignty over data, assets, and identity, ending the platform monopoly of the Web2 era. In the context of Ethereum, Web3 refers to decentralized apps that run on the blockchain - apps that allow anyone to participate without monetizing their personal data.

The fundamental shift: in Web2, a centralized server authenticates you and holds your data. In Web3, you authenticate yourself by proving you control a specific address - and anyone can verify it independently.

### Web2 vs Web3 - Practical Comparisons

| Web2 | Web3 |
|------|------|
| Twitter can censor any account or tweet | Web3 tweets would be uncensorable because control is decentralized |
| Payment service may decide to not allow payments for certain types of work | Web3 payment apps require no personal data and can't prevent payments |
| Servers for gig-economy apps could go down and affect worker income | Web3 servers can't go down - they use Ethereum, a decentralized network of 1000s of computers as their backend |

| Limitation | Detail |

### Deeper Explanation: What Changes When The Backend Is A Blockchain

A blockchain is a replicated state machine with a public log: state is public, transactions are irreversible once final, writes cost money, and every write is signed by a key the user holds. Each property inverts an assumption a normal web developer carries:

| Normal web assumption | Blockchain reality |
|---|---|
| Server decides authorisation | The contract's logic and the user's signature decide |
| Writes are cheap and reversible | Every write costs gas and is effectively permanent |
| Latency is tens of ms | Finality is seconds to minutes |
| You can hide state | State and history are public |
| Users have accounts you manage | Users hold keys; you never see them |
| You can fix a bug with a deploy | Contracts are immutable unless upgradeable by design |

The practical scope for a React developer: wallet connection, network handling, reading on-chain data, submitting transactions the user signs, and presenting irreversible actions with the right confirmation and error handling. Everything else (gas estimation, nonces, RPC reliability, indexers) is infrastructure you either adopt from a library or operate.

### Additional Pitfalls
- **Treating a transaction as a request/response call.** It needs pending/submitted/confirmed/failed states, reorg tolerance, and UI that survives a refresh.
- **Assuming a single chain.** Multi-chain support means chain ids, per-chain contracts, and per-chain RPC health.
- **Ignoring gas and failure modes.** Reverts, out-of-gas, and underpriced transactions are normal user experiences.
- **Storing private keys.** Not your job; the wallet signs, and you never hold a key.

### Real-World Deal-Breakers
- **Treating Web3 as a monolith** → Web3 is not one thing. It's a stack: L1, L2, wallets, RPCs, indexers, oracles. Each layer has different trade-offs.
- **Ignoring the UX gap** → the extra steps, software, and education required are a hurdle to adoption.
- **Assuming decentralization = no cost** → putting code on the blockchain is expensive; most dapps put only small portions of their code on-chain.
- **90% of Web3 games failed by 2026** → building on-chain games with current UX and economics is extremely difficult.
