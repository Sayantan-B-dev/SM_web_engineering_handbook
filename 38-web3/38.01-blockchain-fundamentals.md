### What a Blockchain Is
Blockchain functions as a shared network where transactions are grouped into blocks, validated by the network, and added to a continuously growing chain. Each block links to the prior one, creating a permanent historical record.

### Key Characteristics

| Characteristic | Definition |
|---------------|------------|
| **Transparency** | Transactions are publicly verifiable |
| **Security** | Cryptography protects data integrity |
| **Immutability** | Once recorded, transactions generally cannot be changed |
| **Decentralization** | No single entity controls the network |

### Consensus: PoW vs PoS

| | Proof of Work (PoW) | Proof of Stake (PoS) |
|--|---------------------|---------------------|
| **How it works** | Miners solve computational puzzles | Validators stake tokens |
| **Energy** | Energy-intensive | Energy-efficient |
| **Example** | Bitcoin | Ethereum |
| **Security model** | 51% of hash power | 51% of staked value |
| **Hardware** | ASICs, GPUs | Standard hardware |

Ethereum operates using a proof-of-stake consensus mechanism, where network participants validate transactions by staking tokens rather than using energy-intensive mining.

### Deeper Explanation: Consensus Is What Makes The Web3 Trade-Off Worth It

The core engineering question is *how the network agrees on state without a trusted operator*: proofs of work/stake for ordering, block finality for irreversibility, hashes for integrity, and Merkle trees for efficient verification of inclusion. Public verifiability is the unique product property â€” anyone can verify the chain, so no single party can rewrite it.

The costs are the direct consequence of that design: throughput is bounded by block size and time, latency by finality, and cost by block-space demand. Layer-2 rollups, sidechains, and sharded/parallel execution exist precisely to move throughput up while keeping verification on the base layer. For application developers the practical framing is: the chain is a slow, expensive, global, public database with strong guarantees â€” use it where those guarantees matter and keep everything else off-chain.

### Additional Pitfalls
- **Designing products that need high throughput on the base layer.** Read the gas and finality budget before choosing the chain.
- **Confusing finality with confirmation count.** Some chains reorg; UI must handle "confirmed then reverted".
- **Assuming privacy.** Public chains reveal amounts, addresses, and timing; privacy needs extra design.
- **Ignoring L2 cost differences.** Fees can differ by orders of magnitude across chains for the same action.

### Real-World Deal-Breakers
- **Confusing immutability with "no changes ever"** → upgrades happen via forks or migration contracts; data may be migrated.
- **Assuming all blockchains are the same** → Bitcoin is a store of value; Ethereum is a programmable platform; Solana is a high-performance network.
- **Ignoring gas costs** → every state change costs gas. Dapps that put everything on-chain are economically unviable.
