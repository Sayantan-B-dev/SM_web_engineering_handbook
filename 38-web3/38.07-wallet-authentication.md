### How Wallet-Based Authentication Works
The core flow is simple:
1. Your dapp asks the user to connect their wallet
2. The wallet shares the user's Ethereum address - this is their public identifier
3. Your dapp generates a unique message (a nonce or challenge)
4. The user signs the message with their private key
5. Your backend verifies the signature against the claimed address
6. If valid, the user is authenticated

**No password was ever typed, stored, or transmitted.**

### SIWE Message Structure
A SIWE message looks like:

```
example.com wants you to sign in with your Ethereum account:
0xAb5801a7D398351b8bE11C439e05C5B3259aeC9B

I accept the Terms of Service: https://example.com/tos

URI: https://example.com/login
Version: 1
Chain ID: 1
Nonce: 32891757
Issued At: 2024-06-12T14:30:00Z
```

### Key SIWE Features
- **Domain binding**: The message includes the domain, preventing phishing
- **Chain ID**: Specifies which network the signature is valid for
- **Nonce**: Prevents replay attacks
- **Expiration**: Optional timestamp limiting validity window
- **Resources**: Optional URIs for scoped access

### Client-Side Implementation
```typescript
import { SiweMessage } from 'siwe'
import { BrowserProvider } from 'ethers'

async function signIn() {
  const provider = new BrowserProvider(window.ethereum)
  const signer = await provider.getSigner()
  const address = await signer.getAddress()

  // 1. Get a nonce from your backend
  const { nonce } = await fetch('/api/auth/nonce').then(r => r.json())

  // 2. Create and sign the SIWE message
  const message = new SiweMessage({
    domain: window.location.host,
    address,
    statement: 'Sign in to My Dapp',
    uri: window.location.origin,
    version: '1',
    chainId: 1,
    nonce,
  })

  const signature = await signer.signMessage(message.prepareMessage())

  // 3. Send to backend for verification
  await fetch('/api/auth/verify', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ message: message.prepareMessage(), signature }),
  })
}
```

### SIWE vs OAuth

| Feature | SIWE | OAuth |
|---------|------|-------|
| Credentials | Wallet signature | Password / social login |
| Server stores | Nothing (or nonce) | Session data |
| Phishing resistance | Domain binding | Depends on provider |
| Chain-specific | Yes (chain ID) | No |
| Replay protection | Nonce | State parameter |

### Deeper Explanation: Sign-In Is Not a Login In The Traditional Sense

Wallet authentication (SIWE and similar) proves control of an address by having the user sign a structured message containing domain, address, URI, nonce, issued-at, and chain id. The signature itself is not a session: your backend must verify it (domain binding, nonce freshness, expiry, chain), then issue a normal server-side session. That split is what makes it secure â€” the wallet proves identity, your server manages sessions.

The important failure modes: signature replay (missing domain/nonce binding), phishing UIs (the message must clearly state the domain and purpose), address-only "authentication" (no signature = no proof), and multi-address users (which address is the account, and how are they linked?). Also plan for key rotation, recovery, and the difference between a smart account and an EOA.

### Additional Pitfalls
- **Treating an address as authentication.** Anyone can claim any address; only a signature proves control.
- **No domain binding in the message.** A signature harvested on another site can be replayed against yours.
- **Nonce reuse or no expiry.** Replay attacks with no window limit.
- **No session after verification.** The signed message is a one-time proof, not a session token.
- **Ignoring multi-chain identity.** The same address on different chains is the same key â€” decide whether that is one account or several.

### Real-World Deal-Breakers
- **No nonce validation** → replay attacks. Always use a server-generated nonce.
- **No domain binding** → a signature valid on one dApp can be replayed on another.
- **No expiration** → a signature is valid forever. Add an expiration timestamp.
- **Storing the signature** → the signature is not a credential. After verification, set an HttpOnly session cookie.
- **Not using SIWE when it's available** → "Use SIWE (EIP-4361) when possible - it handles all of the above for you".
