## 7.10 Effects vs Events

### Subtopic Tree
- Event handlers - respond to user actions
- Effects - synchronize with the outside world
- When to use each
- Why useEffect is not a lifecycle method
- Common mistakes (using effects for events)

### The Rule
- **Event handler** → run *because the user did something*.
- **Effect** → run *because the component rendered and something outside React needs sync*.

### Event Handler (Preferred)
```jsx
function Form() {
  function handleSubmit(e) {
    e.preventDefault();
    api.submit(formData); // user-triggered → event handler
  }
  return <form onSubmit={handleSubmit}>...</form>;
}
```

### Effect (Sync with Outside World)
```jsx
function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    return () => connection.disconnect(); // sync on roomId change
  }, [roomId]);
}
```

### Anti-Pattern: Effect as Event Handler
```jsx
// ❌ "Event" faked as state → effect
const [submitted, setSubmitted] = useState(false);
useEffect(() => {
  if (submitted) api.submit(data);
}, [submitted]);

// ✅ Do it in the handler
function handleSubmit() {
  api.submit(data);
}
```

### Why `useEffect` Is Not a Lifecycle
`componentDidMount` runs once on mount. `useEffect` runs based on deps. It's about **synchronization**, not lifecycle moments.

```jsx
// "On mount" - but really: sync with `roomId`
useEffect(() => {
  connect(roomId);
  return () => disconnect();
}, [roomId]);
```

### Real-World Deal-Breakers
- **Using `useEffect` to react to user clicks** → indirect, fragile; use handler directly.
- **Deriving state with effects** → compute during render instead.
- **Effect for one-time "setup"** → mount-based thinking; think in terms of deps/sync.
- **Effect that updates state based on props** → often a derived-state bug; compute during render or use state-from-props pattern.
