## 7.1 Rendering

### Core Mental Model
**Rendering = React calls your component function to figure out what the UI should look like.**

It does **not** mean:
- The DOM is updated
- The browser painted something
- The user sees anything new

It means React executed your function and got back a tree of React elements (plain JS objects).

```jsx
function Counter() {
  console.log('Rendering Counter'); // fires on every render
  return <p>Hello</p>;
}
```

Every time this log runs, React is "rendering" `Counter`. The DOM may or may not change - that depends on reconciliation.

### What Triggers a Render
1. **Initial render** - `root.render(<App />)`.
2. **State change** - `setState` with a different value.
3. **Parent re-renders** - children re-render unless memoized.
4. **Context change** - consumers re-render.
5. **Force update** - `useReducer` dispatch, `forceUpdate` (legacy), external store updates (`useSyncExternalStore`).

### Rendering Is Pure
During render, a component must:
- Return the same output for the same inputs.
- Not mutate anything outside itself.
- Not have side effects (no fetch, no DOM writes, no timers).

```jsx
// ❌ Impure - mutates external variable during render
let counter = 0;
function Bad() {
  counter++; // side effect!
  return <p>{counter}</p>;
}

// ✅ Pure
function Good({ value }) {
  return <p>{value}</p>;
}
```

**Why purity matters:** React may call your component multiple times (StrictMode, concurrent rendering, suspense) - impure renders produce inconsistent UI.

### Real-World Deal-Breakers
- **Confusing "render" with "DOM update"** → thinking the DOM is touched on every render. It's not - React diffs first.
- **Side effects during render** → duplicate API calls, unpredictable state.
- **Expensive work in render body** → runs on every re-render, kills performance.
- **Logging/DOM reads during render** → misleading in StrictMode (double-invoked).
