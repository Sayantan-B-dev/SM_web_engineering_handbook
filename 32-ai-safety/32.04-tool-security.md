## 32.4 Tool Security

### Subtopic Tree
- Tool input validation (the boundary between probabilistic and deterministic)
- Tool output validation (tool outputs flow back into the model)
- Tool allowlisting (allowed-tool set)
- Parameter sanitization
- Output verification
- Permission enforcement
- The OWASP API Security Top 10 applied to tool calls

### The Core Principle
Tool input validation is **the boundary between the model's probabilistic output and your deterministic systems**. It deserves the same rigor as a public API.

```typescript
// ❌ BAD - trusting the model's output
const result = await db.query(`SELECT * FROM users WHERE id = ${args.userId}`);

// ✅ GOOD - validate and sanitize
const schema = z.object({ userId: z.string().uuid() });
const { userId } = schema.parse(args);
const result = await db.query('SELECT * FROM users WHERE id = $1', [userId]);
```

### Tool Output Validation (The Critical Gap)
Tool outputs flow back into the model context and can themselves carry prompt injection payloads. **Stripping or escaping known-bad content from tool outputs before they enter the context window blocks the most common indirect injection vector**. Schema validation alone catches the obvious cases; semantic validation catches the rest.

```typescript
// Validate tool output before it enters the model context
function sanitizeToolOutput(raw: string): string {
  // Strip instruction-like patterns
  return raw
    .replace(/ignore previous instructions/gi, '[REDACTED]')
    .replace(/system prompt/gi, '[REDACTED]')
    .replace(/you are now/gi, '[REDACTED]');
}
```

### Tool Allowlisting
Every tool call should be gated through a **deterministic policy** that checks the tool is in the allowed set. The security baseline enforces: `user input → [scan] → LLM → [gate] → tool → [scan result] → LLM → [scan] → response`.

### Authentication and Audit (2026 Baseline)
Authentication for tool calls has moved decisively toward **short-lived credentials and explicit user delegation**. The standard pattern is OAuth-style token exchange where the agent presents user context and receives a **per-request, narrowly scoped, short-TTL credential** for each tool call. Long-lived service tokens stored in agent configs are increasingly considered a **finding** rather than a normal pattern.

Audit logging: every tool call should produce a structured log entry capturing the **requesting user, the model version, the prompt that triggered the call, the tool name and arguments, the response, and a request ID** that ties the entry to the upstream conversation.

---

### Deeper Explanation: Tools Are Privileged Code With A Probabilistic Caller

Every tool you expose is production code invoked by a nondeterministic, adversarial-influenceable caller. That makes tool security a distinct discipline:

- **Scope narrowly.** `get_order(id)` beats `run_sql(query)`. The narrower the tool, the smaller the space an injection can occupy.
- **Authorise per call, server-side.** Identity, tenant, and permission checks belong in the tool implementation, using the authenticated session â€” never parameters the model supplies.
- **Validate arguments against schemas and business rules.** A uuid format check plus an ownership check beats trusting a parsed string.
- **Make side effects idempotent and auditable.** Idempotency keys, dry-run modes for writes, and a record of who (or what) triggered the call.
- **Rate limit and budget.** Per user, per session, per tool; a tool loop is a cost and abuse vector.

### Additional Pitfalls
- **Authorisation trusted from the model's arguments.** "userId" in a tool call must be ignored in favour of the session.
- **One broad tool exposing the whole database.** The classic privilege escalation in AI features.
- **Writes without confirmation.** Sending, deleting, and paying need human-in-the-loop or a dry run.
- **No per-tool rate limits.** A stuck loop becomes an outage or a bill.
- **Tool outputs echoed verbatim.** They may contain PII or instructions; sanitise and truncate.

### Real-World Deal-Breakers
- **No tool input validation** → the model's probabilistic output directly hits your database. Always validate with strict schemas.
- **No tool output validation** → tool outputs carry IPI payloads back into the model context.
- **No tool allowlisting** → the model can call any tool. Gate every call through a deterministic policy.
- **Long-lived service tokens** → a compromised agent has permanent access. Use short-lived, per-request credentials.
- **No audit trail** → you cannot investigate an incident after the fact. Log every tool call with full context.
