## 32.10 Agent Sandboxing

### Subtopic Tree
- OS-level isolation (macOS Seatbelt, Windows containers)
- Policy-driven containment (MXC, Strands Box, OpenShell)
- Four checkpoints: shell commands, Python code, tool calls, network traffic
- Behavioral policies (weigh past actions)
- The agent cannot grant itself additional access
- Cross-platform containment (Windows, macOS, Linux)

### What Sandboxing Is
An agent **cannot be its own security authority**. It must run within a boundary defined by the developer or organization and **enforced independently of the agent itself**.

### Microsoft Execution Containers (MXC)
MXC is a policy-driven execution layer for untrusted code or dynamically generated workloads. Developers declare the resources a workload requires (files, network destinations), and MXC enforces the resulting boundary with the appropriate container. **The policy remains outside the agent workload's control**, so the agent or generated code cannot grant itself additional access.

### AWS Strands Box
Strands Box pairs **operating-system isolation** with rules that can weigh what an agent has already done before letting it act again. It routes shell commands, Python code, tool calls, and network traffic through **four checkpoints**. A rule example: an agent is allowed a **maximum of three successful posts within ten minutes**.

### Nvidia OpenShell
OpenShell provides sandboxed execution and enforces policy controls **outside the agent's reach** while governing access to data, networks, and system resources. Nvidia's view: AI security remains an engineering problem, and every agent deployment needs **enforceable boundaries, an accountable owner**.

### Deeper Explanation: Isolation Is The Only Guarantee

Since prompts cannot be trusted, the model's environment must assume compromised behaviour. Sandboxing gives you that assumption in concrete form: the process can only reach what you have explicitly granted.

Layers, from strongest to weakest:

1. **Disposable container or micro-VM per session** â€” filesystem scoped to a workspace, no host mounts, network egress allow-list, CPU/memory/time limits.
2. **Separate credentials per session** â€” short-lived, scoped tokens; no long-lived secrets in the sandbox.
3. **No production network access** â€” agents run against staging or local dependencies; real data never enters.
4. **Kill switch and budget** â€” wall-clock, token, and cost ceilings with an external watchdog.
5. **Recreate, never reuse** â€” snapshots are per-run; persistent sandboxes accumulate credentials and state.

### Additional Pitfalls
- **Running agents on developer machines with production credentials.** One prompt injection reaches production.
- **Allow-all network egress.** Exfiltration and dependency downloads are the same channel.
- **Long-lived sandboxes.** They accumulate secrets, caches, and privilege.
- **No resource ceiling.** A runaway loop can consume the host and the budget.
- **Assuming container isolation is absolute.** Kernel-level escapes exist; keep the credential surface minimal.

### Real-World Deal-Breakers
- **No sandbox** → the agent has unrestricted access to files, network, and processes. Use OS-level isolation.
- **Policy inside the agent's control** → the agent can modify its own policy. Enforce policy outside the agent.
- **No behavioral policies** → the agent can execute unlimited actions. Limit actions per time window.
- **No cross-platform containment** → the agent escapes when deployed on a different OS. Use a unified containment model.
