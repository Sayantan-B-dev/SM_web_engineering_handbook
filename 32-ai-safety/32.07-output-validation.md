## 32.7 Output Validation

### Subtopic Tree
- The boundary between model output and tool execution
- Schema validation (Zod, JSON Schema)
- Semantic validation (beyond schema)
- Checking tool call arguments against policy
- Scanning generated content for instruction-following indicators
- Stripping known-bad content from tool outputs

### Why Output Validation Matters
Rather than trying to prevent models from being influenced, defenders increasingly validate what the model produces **before it reaches a tool or the user**. For agents, this means checking tool call arguments against policy before execution. For assistants, it means scanning generated content for indicators of instruction-following from untrusted sources.

### Two Layers of Validation
**Schema validation** catches the obvious cases - wrong types, missing fields, invalid formats. **Semantic validation** catches the rest - values that are syntactically valid but semantically dangerous.

```typescript
// Schema validation
const parsed = ToolCallSchema.safeParse(toolCall);
if (!parsed.success) return reject(parsed.error);

// Semantic validation
if (isDestructive(parsed.data) && !hasApproval(parsed.data)) {
  return requireApproval(parsed.data);
}
```

### Tool Output Sanitization
Tool outputs flow back into the model context and can themselves carry prompt injection payloads. **Stripping or escaping known-bad content from tool outputs before they enter the context window blocks the most common indirect injection vector**.

---

### Deeper Explanation: The Boundary Between Model And World

Everything the model produces should pass through a validating boundary before it affects anything: parsing JSON, checking schema, checking business invariants, sanitising text for rendering, and policy-checking any action. Think of it as the equivalent of an API gateway for probabilistic output.

Four checks, in order:

1. **Structural** â€” matches the schema (types, bounds, enums).
2. **Semantic** â€” makes sense for this user and resource (the order id belongs to them; the date is plausible).
3. **Safety** â€” no instructions, no secrets, no unsafe URLs, no executable payloads.
4. **Presentation** â€” rendered through allow-listed components/markdown with sanitisation.

Fail closed: if validation fails twice, degrade to a safe default (a generic message, a plain-text answer) instead of showing or executing something unverified.

### Additional Pitfalls
- **Markdown rendered without sanitisation.** Model output is untrusted HTML input.
- **Trusting a URL in the output.** Resolve links server-side from keys; never render model-chosen destinations.
- **Executing generated code or SQL.** Allow-listed operations only, with parameters.
- **No repair-then-fallback path.** A single retry with the validation error, then a safe default.
- **Validating only the final answer.** Tool arguments need the same rigour.

### Real-World Deal-Breakers
- **No schema validation** → the model's output directly drives tool execution with no type safety.
- **No semantic validation** → a syntactically valid tool call can still be destructive.
- **No output sanitization** → tool outputs carry IPI payloads back into the model context.
- **No approval gate for destructive tools** → the model deletes production data without confirmation.
