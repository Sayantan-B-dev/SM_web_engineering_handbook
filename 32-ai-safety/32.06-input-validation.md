## 32.6 Input Validation

### Subtopic Tree
- Strict schemas with value-level validators
- URL allowlists
- File path containment
- Parameter range checks
- SQL bind variables (not string concatenation)
- Prompt scanning (classifier or rules DSL)
- User input → scan → LLM gate

### The Input Validation Pipeline
```
User input → [scan] → LLM → [gate] → tool → [scan result] → LLM → [scan] → response
```
Every stage has a validation gate. The scan validates LLM inputs before they reach the model. The gate validates tool calls before execution. The result scan validates tool outputs before they re-enter the model.

### What to Validate
Every tool entry point should have a **strict schema with value-level validators**, not just type-level ones. URL allowlists, file path containment, parameter range checks, SQL bind variables rather than string concatenation.

```typescript
const ToolInputSchema = z.object({
  url: z.string().url().refine((u) => ALLOWED_DOMAINS.some((d) => new URL(u).hostname.endsWith(d)), 'Domain not allowed'),
  filePath: z.string().refine((p) => !p.includes('..'), 'Path traversal detected'),
  limit: z.number().int().min(1).max(100),
});
```

### Prompt Scanning
Use a fine-tuned classifier or a rules DSL to scan user input for injection patterns before it reaches the model. This is the first gate in the pipeline.

---

### Deeper Explanation: Validate The Message, Not Just The Request

Input validation for AI features covers four things: the user's text (length, encoding, profanity/spam policy), the retrieved content (source allow-list, sanitisation, size), the attachments (type, size, parsing safety), and the tool arguments the model produces (schema, business rules). The third one is what people forget: parsing a PDF or DOCX is code execution against untrusted bytes, and PDF parsers have a long CVE history.

Practical measures: cap sizes and token counts before calling the model, strip scripts and macros from extracted text, run parsing in a worker or sandbox, allow-list remote URLs (and never fetch them from the prompt directly â€” use a server-side fetch with SSRF protections), and normalise unicode to defeat homoglyph-based filter bypass.

### Additional Pitfalls
- **Unbounded input.** A 5 MB paste is a cost and latency incident; cap and truncate with a clear message.
- **Fetching URLs from user input server-side.** That is SSRF unless you validate scheme, host, and redirects.
- **Trusting extracted document text.** It can carry injection payloads and invisible unicode instructions.
- **No spam or abuse limits.** Prompt spam consumes tokens; rate limit per user with progressive friction.
- **Validating only on the client.** All of it must be repeated server-side.

### Real-World Deal-Breakers
- **Type-level validation only** → the schema says `string` but the value is `../../../etc/passwd`. Add value-level validators.
- **No URL allowlist** → the model can call any URL, including attacker-controlled endpoints.
- **String concatenation in SQL** → SQL injection through tool arguments. Use bind variables.
- **No prompt scanning** → injection payloads reach the model unfiltered.
