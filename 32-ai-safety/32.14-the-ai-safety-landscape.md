### The Core Mental Model
AI safety in 2026 is not about making models "behave." It is about **architecting systems that assume the model will be fooled**. The OWASP LLM Top 10 2026 identifies the ten most critical risks facing LLM-powered applications, ranked by real-world incident data:

| Rank | Risk | Movement |
|------|------|----------|
| LLM01 | Prompt Injection | No change (still #1) |
| LLM02 | Sensitive Information Disclosure | No change |
| LLM03 | Excessive Agency | Up 3 (from #6) |
| LLM04 | Supply Chain | Down 1 |
| LLM05 | Data and Model Poisoning | Down 1 |
| LLM06 | Unbounded Consumption | Up 4 (from #10) |
| LLM07 | Misinformation | Up 2 |
| LLM08 | Hidden Context Exposure | Renamed from System Prompt Leakage |
| LLM09 | Vector and Embedding Weaknesses | Down 1 |
| LLM10 | Improper Output Handling | Down 5 (from #5) |

The biggest moves: **Excessive Agency climbed from #6 to #3** (agents are getting more permissions) and **Unbounded Consumption jumped from #10 to #6** (cost is now a top-tier risk).

### Deeper Explanation: Model Output Is Untrusted Input

Every AI safety control follows from one reframing: **the model is an untrusted component inside your trust boundary**, like a user-supplied string or a third-party API. Its output can contain instructions, code, links, and claims, and it can be influenced by data you did not author (documents, web pages, tickets, emails). So the defences are ordinary application-security defences applied to a probabilistic component:

- **Input controls** â€” treat retrieved/user content as data, never as capability; separate it structurally from instructions.
- **Output controls** â€” validate, constrain, and render through allow-lists; never execute or interpret raw output.
- **Capability controls** â€” least privilege on tools, per-call authorisation, and human approval for consequential actions.
- **Observability** â€” log prompts, tool calls, and decisions so incidents are investigable.

Threat modelling for an AI feature is therefore less about "model alignment" and more about injection, privilege, data flow, and auditing â€” with an extra category for confident wrongness.

### Additional Pitfalls
- **Security review skipped because "it is just a feature".** Injection, data exfiltration, and privilege escalation are fully applicable.
- **Safety implemented only in the system prompt.** Prompts are requests; enforcement belongs in code.
- **No data-flow inventory.** You cannot protect what you have not mapped: what enters the prompt, where it goes, what it may leave.
- **No incident playbook.** AI failures need logging, rollback, and user communication like any other incident class.

### Real-World Deal-Breakers
- **Treating AI safety as "model alignment"** → the model is not the attack surface. The **system** is. Your tools, your retrieval pipeline, your permission boundaries.
- **Assuming prompt injection is a "chatbot problem"** → indirect injection is now the default case. The user did not type the payload; the document did.
- **No governance despite adoption** → 94% of engineering leaders say their teams use AI; only 6% have systems to scale and govern it.
- **Assuming the model is trustworthy** → the security baseline for agents assumes the model is **not** trusted, the network is **not** trusted, and the user is **not** trusted.
