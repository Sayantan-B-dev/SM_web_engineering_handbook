### The Attack Surface
Sensitive information disclosure is the **#2 risk** in the OWASP LLM Top 10 2026. It covers any case where the model reveals information it should not - PII, API keys, internal documents, other tenants' data.

**Three primary vectors:**

1. **Prompt leakage** - the model reveals its system prompt, which may contain secrets, internal instructions, or configuration.
2. **Training data leakage** - the model regurgitates memorized training data (PII, copyrighted text, secrets).
3. **Retrieval pipeline leakage** - RAG systems retrieve documents from other tenants, or embeddings are inverted to recover original text.

### Embedding Inversion
If the vector store is weakly controlled, attackers can **recover the original text from embeddings**, read another tenant's data, or poison what the model retrieves. This is a critical risk for multi-tenant RAG systems.

### Cross-Tenant Leakage in RAG
RAG systems introduce **privacy risks and potential data leakage issues from the retrieval pipeline**. Indirect prompt injections occur when hidden instructions inside retrieved documents slip into the model's context as trusted evidence, exploiting weak guardrails in RAG systems and leading to **unauthorized data leaks, ambiguous outcomes, and policy overrides**.

### Deeper Explanation: Four Leak Paths To Close

- **Prompt â†’ provider.** Whatever you send is data you have disclosed. Know your provider's retention, training, and residency terms per model and tier.
- **Retrieval â†’ other users.** Multi-tenant RAG must filter by tenant and permission at query time; a shared index without filters is a breach waiting to happen.
- **Context â†’ logs/traces.** Prompts and outputs stored for debugging are production data; apply the same access controls as your database.
- **Response â†’ user.** A model can surface a system prompt, another user's data (through retrieval bugs), or internal identifiers.

Mitigations are unglamorous: classify data before it enters prompts, filter retrieval per user, redact in logs, keep secrets out of context entirely (fetch them server-side at execution time), and prefer least-capability tools over "database access".

### Additional Pitfalls
- **Pasting production data into a chat UI for debugging.** It leaves your boundary permanently.
- **System prompts containing secrets or internal URLs.** Injected content can extract them.
- **Shared vector index across tenants.** Filter at query time, and test it adversarially.
- **Unredacted telemetry.** Prompt logs are a favourite target in audits.
- **Assuming "enterprise tier" removes the need for classification.** It changes retention, not necessity.

### Real-World Deal-Breakers
- **No tenant isolation in vector stores** → one tenant can retrieve another tenant's documents. Enforce row-level security or namespace isolation.
- **No embedding access controls** → embedding inversion can recover original text. Encrypt embeddings at rest.
- **System prompts contain secrets** → never put API keys or PII in system prompts. They can be extracted.
- **No output scanning** → the model may regurgitate sensitive data from context or training. Scan outputs for PII patterns.
