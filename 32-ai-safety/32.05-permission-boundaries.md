### Least Privilege for Agents
Least privilege for agents starts with **refusing to grant tool access in bulk**. The common failure pattern is wiring an agent to a broad credential - an AWS admin role, a database connection with full read-write, a Slack bot token with all scopes - and then relying on the model to behave well.

**The baseline is the opposite:** every tool gets the minimum credential it needs, and every credential is scoped to the minimum resource set.

| Platform | Baseline |
|----------|----------|
| **AWS** | Per-tool IAM roles with explicit resource ARNs (no wildcards) |
| **Databases** | Per-tool read-only connections with row-level security |
| **SaaS APIs** | Dedicated service accounts with only the scopes each tool requires |

We have seen this single control **prevent multiple incidents from escalating into reportable breaches**.

### Privilege Decomposition
The idea that a single agent session should have every permission needed for a full workflow is fading. Instead, teams **break workflows into stages**, hand tokens with narrow scopes to each stage, and **require cross-stage approvals for sensitive actions**. This is essentially the principle of least privilege applied to an AI execution context.

### The Runaway Agent Problem
AWS introduced **Strands Box**, an open-source sandbox that restricts AI agents in file, shell, and network access. A rule allows an agent a maximum of three successful posts within ten minutes. The tool combines OS-level isolation with policies that **weigh what an agent has already done before letting it act again**.

Microsoft's Execution Containers (MXC) enforce policy at runtime, outside the agent's control. The policy remains outside the agent workload's control, so the agent or generated code **cannot grant itself additional access**. Consider a coding agent asked to update a website: it needs read/write to the repo and read access to production config, but **should not be able to modify that config**. Without a managed execution boundary, the agent may decide changing the server config is the fastest way to complete the task.

### Deeper Explanation: Model Roles, Not User Roles

Permission boundaries for AI features need their own principal: the *agent identity*, with its own scopes, quotas, and audit trail â€” narrower than any human's, and never a shared service account with broad rights.

Design rules that hold up in audits:

- **The model acts as a limited service identity**, with explicit scopes per feature (read orders, create drafts), never "admin".
- **The user's permission is the ceiling.** An agent on behalf of a user can do at most what that user could do, and only for their tenant.
- **Escalate with consent.** Anything beyond the ceiling requires explicit approval, recorded with the payload.
- **Separate read and write identities.** Read-only tools with broad-ish access plus narrow write tools, gated by approval.
- **Bounds on volume.** Quotas per user and per run cap blast radius even when permissions allow.

### Additional Pitfalls
- **A single broad service account for all AI features.** One compromised prompt reaches everything.
- **Permissions checked in the UI only.** The tool implementation is the boundary.
- **No audit trail per call.** Without actor, arguments, and result, you cannot answer "what did it do".
- **Sharing credentials with the model provider.** Keys stay server-side; the model never sees them.
- **Ignoring tenant isolation in retrieval.** Permission boundaries apply to *context* as much as to tools.

### Real-World Deal-Breakers
- **Bulk tool access** → one compromised agent has full cloud access. Scope every credential.
- **Wildcard IAM policies** → `"Resource": "*"` gives the agent access to everything. Use explicit ARNs.
- **Long-lived tokens** → a compromised agent has permanent access. Use short-TTL, per-request credentials.
- **No cross-stage approvals** → the agent can execute a full workflow without human checkpoints. Break into stages.
- **Agent as its own security authority** → the agent cannot be trusted to enforce its own boundaries. The policy must be enforced independently.
