
Clicking in a console is an unreviewable, undocumented, unrepeatable change. Even a solo engineer benefits from IaC: it is the only way to answer "what does production look like?" without logging in.

### SLOs Drive Decisions

```text
SLO: 99.9% of document saves succeed within 1s, measured over 28 days
     Budget: 0.1% of 8.6M saves = 8,600 failed saves per 28 days
```

```text
Budget remaining > 50%   -> ship freely
Budget remaining 10-50%  -> review releases more carefully; prioritise reliability
Budget exhausted         -> feature freeze; reliability work only
```

An error budget converts "should we ship?" from an argument into arithmetic. It also gives product and engineering a shared language for the reliability-versus-speed trade-off.

### Alerting On Symptoms

| Alert on | Not on |
|---|---|
| Save failure rate > 0.5% for 5 min | CPU > 80% |
| p95 sync latency > 500ms for 10 min | Memory growing (may be normal) |
| Login failure rate spike | A single 5xx |
| Queue depth growing for 15 min | Disk I/O (may be fine) |

Every alert must be actionable and tied to a runbook step. An alert whose response is "look at the dashboard" will be ignored within a month.

### Runbooks

```markdown
## Runbook: sync servers at capacity

Symptom: connection count > 80% of the limit for 10 minutes.

1. Confirm: Grafana -> Realtime -> Active connections by instance.
2. Immediate: scale the fleet: `flyctl scale count 6 --app atlas-sync-prod`
3. If scaling does not reduce per-instance load: check for a hot document
   (one document with thousands of connections) -> Grafana panel "top documents".
4. If a hot document is found: enable per-document connection throttling.
5. After the incident: add jitter to reconnect, revisit the sharding threshold.
```

A runbook turns an unfamiliar 2am problem into a procedure. Writing one is a fifteen-minute investment that saves an hour of panic.

### Incident Practice

```text
1. Detect       - alert or customer report
2. Declare      - a named incident commander, a channel, a start time
3. Mitigate     - stop the bleeding (rollback, scale, disable a flag)
4. Communicate  - status page + customers, on a fixed cadence
5. Resolve      - verify recovery with data, not vibes
6. Postmortem   - timeline, contributing factors, action items with owners and dates
```

Mitigate before you diagnose. The instinct to find the root cause first is what turns a 10-minute outage into a two-hour one.

### Deeper Explanation: Reliability Is A Budget, Not A Virtue

"Make it more reliable" is not an engineering instruction until it has a number, a cost and a trade-off. 99.9% and 99.99% are the same sentence with a ten-times price difference, and the honest answer for most products is that 99.9% plus fast recovery beats 99.99% with slow releases.

SRE's contribution is making that trade-off explicit and measurable, so the decision is made once, deliberately, rather than every time someone is paged.

### Additional Pitfalls

- **Alerts with no runbook.** The responder improvises under pressure at the worst time.
- **No error budget.** Reliability work competes with features on vibes, and always loses.
- **Load testing at constant load only.** It finds throughput, not the saturation knee.
- **Postmortems that assign blame.** The next incident's information is withheld out of fear.
- **Configuration drift.** IaC exists but a console change was never codified, so the next apply reverts it invisibly.

### Real-World Deal-Breakers
- **No rollback capability** - a bad deploy becomes a long outage fixed under pressure.
- **Alerting on causes rather than symptoms** - the product is broken while dashboards are green, and noisy when it is healthy.
- **Single-AZ database with no tested restore** - one AZ event is total data loss.
- **On-call without limits** - burnout, departures and degraded judgement during real incidents.
