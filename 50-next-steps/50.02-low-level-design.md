### What LLD Produces

An LLD answers: *what are the units of code, what are their contracts, what invariants do they protect, and how do they fail.* In an interview it is a class diagram plus signatures. In real work it is the shape of a module before you write it - which is why writing the interface first saves days.

### Interface First

```typescript
/** The contract: what a document store promises, independent of Postgres/Yjs. */
export interface DocumentStore {
  /** Throws NOT_FOUND. Returns metadata only, never the CRDT body. */
  getMeta(id: DocumentId): Promise<DocMeta>;

  /** Appends an operation. Idempotent by (docId, actorSeq). */
  appendOp(id: DocumentId, op: EncodedOp): Promise<{ seq: number }>;

  /** Returns ops with seq > sinceSeq, ordered by seq, capped at limit. */
  opsSince(id: DocumentId, sinceSeq: number, limit: number): Promise<EncodedOp[]>;

  /** Compacts: replaces history up to seq with a snapshot. Safe to retry. */
  compact(id: DocumentId, snapshot: Uint8Array, upToSeq: number): Promise<void>;
}
```

Two interfaces - the domain contract and the Postgres implementation - means the sync engine can be tested against an in-memory store, and Postgres can be replaced without touching business logic.

### Invariants Are The Design

```typescript
/**
 * Invariants of the OpLog (write them down; encode them in types and tests):
 *  I1: seq is strictly increasing per document.
 *  I2: Applying the same op twice is a no-op (idempotent).
 *  I3: An op is never visible to a reader before it is durable (no read-your-write races).
 *  I4: compact() never removes ops newer than snapshot's state vector.
 *  I5: An actor's ops are never reordered relative to each other.
 */
```

Invariants are what makes an LLD reviewable. "Is I4 enforceable here?" is a question with an answer; "does this class look clean?" is not.

### State Machines Instead Of Boolean Soup

```typescript
type SyncState =
  | { s: 'idle'; lastSyncedAt: number }
  | { s: 'syncing'; since: number }
  | { s: 'offline'; queued: number }
  | { s: 'error'; reason: SyncError; retries: number };

/** Illegal states are unrepresentable: there is no `isSyncing && isOffline`. */
function reduce(state: SyncState, event: SyncEvent): SyncState {
  switch (state.s) {
    case 'idle':
      return event.type === 'push' ? { s: 'syncing', since: event.since } : state;
    case 'syncing':
      if (event.type === 'ok') return { s: 'idle', lastSyncedAt: Date.now() };
      if (event.type === 'network') return { s: 'offline', queued: event.queued };
      return { s: 'error', reason: event.reason, retries: 0 };
    case 'offline':
      return event.type === 'online' ? { s: 'syncing', since: state.queued } : state;
    case 'error':
      return event.type === 'retry' ? { s: 'syncing', since: 0 } : state;
  }
}
```

A state machine replaces four booleans (16 nominal states, most impossible) with four real states and a total function over transitions.

### Patterns Worth Knowing

| Pattern | Use it for | The trap |
|---|---|---|
| Strategy | interchangeable algorithms | over-abstraction for one implementation |
| Factory | complex construction, DI | hiding a dependency graph that should be explicit |
| Adapter | wrapping third-party APIs | leaking the third-party shape everywhere |
| Observer | events, subscriptions | unbounded listeners, leak on unmount |
| Repository | persistence behind a domain interface | generic repositories that mirror the ORM |
| Command | undo/redo, queued mutations | state explosions if commands are too granular |
| Circuit breaker | external calls | masking a systematic bug as "transient" |

The trap column is the important one. Patterns are a vocabulary for describing solutions; applying them pre-emptively is how codebases become unreadable.

### Concurrency At The Unit Level

```typescript
// Prefer immutability + a single owner over shared mutable state
class DocumentSession {
  private readonly ydoc: Y.Doc;          // single-writer within this class
  private readonly queue: EncodedOp[] = [];

  // All mutation funnels through one async method: no interleaving surprises
  async apply(op: EncodedOp) {
    await this.persist(op);              // durable first
    this.enqueueBroadcast(op);           // then broadcast
  }
}
```

The rule: **define who may write to each piece of mutable state, and make it one place.** Most concurrency bugs are an ownership failure, not a locking failure.

### Deeper Explanation: LLD Is The Discipline Of Making Systems Explainable

The value of an LLD is not the diagram. It is that you were forced to name every unit, state its contract, list its invariants, and describe its failure behaviour before writing a line.

When an LLD is done well, implementation is mechanical and code review is about *correctness of the model* rather than style. When it is skipped, correctness is discovered through bugs - which is the most expensive way to learn it.

### Additional Pitfalls

- **Interfaces that mirror the implementation.** An interface with `getConnection()` has not abstracted anything.
- **Leaky invariants.** Documented but unenforced invariants are worse than none; enforce in types or assert in code.
- **Inheritance for reuse.** Composition needs a plan; inheritance needs an excuse.
- **Error handling bolted on at the end.** Idempotency and retry semantics must be designed into the contract.
- **Testability as an afterthought.** If a unit cannot be tested without a database, its boundary is wrong.

### Real-World Deal-Breakers
- **No defined invariants** - concurrency and ordering bugs appear under load and cannot be reasoned about.
- **Boolean state soup** - impossible states occur in production and the UI renders nonsense.
- **Interfaces designed after the implementation** - the abstraction leaks and never gets used.
- **Shared mutable state with no owner** - races that reproduce once a week and never locally.
- **Idempotency absent from the contract** - a retry after a timeout double-applies an operation.
