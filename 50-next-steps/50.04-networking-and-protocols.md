### The Order Of Operations

```text
1. DNS resolve        a9f3.cdn.net -> 151.101.x.x      (cacheable, TTL-bound)
2. TCP connect        1 RTT (3-way handshake)
3. TLS 1.3 handshake  1 RTT (0-RTT on resumption)
4. HTTP request       H2 multiplexed; H3 over QUIC     (no TCP head-of-line blocking)
5. Response + render
```

Ten years of frontend performance work has been about deleting steps from this list: preconnect removes 1-3, HTTP/2 removes new connections, caching removes step 4 entirely.

### Caching Headers That Actually Work

```http
# Immutable asset, content-hashed filename: never revalidate
Cache-Control: public, max-age=31536000, immutable

# HTML: revalidate every time, serve stale while checking (fast + correct)
Cache-Control: no-cache
ETag: "a3f2-9c"

# Personalised API response: never store anywhere
Cache-Control: private, no-store

# CDN-cached public data with CDN freshness separate from browser
Cache-Control: public, max-age=60, s-maxage=600, stale-while-revalidate=30
```

```http
# If the response varies by a header, you MUST say so or the CDN serves the wrong variant
Vary: Accept-Encoding, Accept-Language
```

Forgetting `Vary` is how a CDN ends up serving a gzip response to a client that asked for brotli, or one locale's HTML to another.

### HTTP/3 And Why It Matters For Mobile

```text
HTTP/1.1  connections per origin: 6, no multiplexing, head-of-line blocking
HTTP/2    one connection, multiplexed streams, still TCP HoL blocking on packet loss
HTTP/3    QUIC over UDP, per-stream loss recovery, faster on lossy mobile networks
```

On a clean datacentre link the difference is marginal. On a phone in a lift, HTTP/3 is a visible improvement because one lost packet no longer stalls every stream.

### CORS In One Table

| Header | Purpose |
|---|---|
| `Access-Control-Allow-Origin` | which origins may read the response |
| `Access-Control-Allow-Credentials` | whether cookies may be sent (never with `*`) |
| `Access-Control-Allow-Methods` | which verbs are permitted |
| `Access-Control-Allow-Headers` | which request headers are permitted |
| `Access-Control-Max-Age` | how long to cache the preflight |

CORS is a *browser* protection for the user, not a server security control. A request blocked by CORS still reached your server and executed.

### Debugging Toolkit

```bash
dig +short example.com A                 # DNS answer and TTL
curl -v --http2 https://api.example.com  # handshake, TLS, headers, timing
curl -w '%{time_namelookup} %{time_connect} %{time_starttransfer} %{time_total}\n' -o /dev/null -s URL
openssl s_client -connect api.example.com:443 -servername api.example.com   # cert chain
```

The `curl -w` timing breakdown tells you instantly whether you have a DNS, TCP, TLS or server problem - far faster than guessing.

### Deeper Explanation: The Network Is Where Assumptions Die

Every millisecond your product loses is a step in the list above that someone chose not to eliminate. The professional habit is to measure the breakdown before optimising anything: a 900ms load might be 400ms DNS from a missing `preconnect`, 300ms TTFB from an uncached query, and 200ms of layout shift - three unrelated problems, three unrelated fixes.

### Additional Pitfalls

- **`Cache-Control: no-store` on immutable assets.** Throws away the entire caching layer for no reason.
- **`Access-Control-Allow-Origin: *` with credentials.** The browser rejects it, and it signals a misunderstanding of CORS.
- **A single timeout value everywhere.** Connection, request and idle timeouts have different correct values.
- **Preflight on every request.** A non-cached `Access-Control-Max-Age` adds an RTT to every call.
- **No HTTP/2 or HTTP/3 at the edge.** Multiplexing is free performance left on the table.

### Real-World Deal-Breakers
- **Missing `Vary` on a CDN** - wrong-encoding or wrong-locale responses served to users.
- **Public caching of authenticated responses** - one user's data served to another; a breach.
- **No request timeouts** - a hung dependency exhausts the connection pool and takes the app down.
- **CORS treated as authorisation** - the request still executes server-side; the API remains unprotected.
