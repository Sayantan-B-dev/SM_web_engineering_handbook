## 50.1 High-Level Design (HLD)

### What You Are Actually Producing

An HLD answers: *what are the moving parts, what talks to what, where does data live, and what happens when a part fails.* It is a page of diagram plus a page of reasoning. Code comes later and is a consequence of it.

The beginner mistake is starting from a framework. The professional mistake is starting from a diagram shape they have seen before (always a load balancer, always Kafka). Start from requirements.

### Estimate Before You Design

```text
Users:            50,000 registered, 5,000 daily active
Sessions/day:     5,000 daily x ~120 events   = 600k events/day ~ 7 events/sec avg
Peak factor:      x10                          = 70 events/sec peak
Payload:          ~2 KB/event                 = 140 KB/s   ~ 12 GB/day
Storage/year:     12 GB/day x 365             = ~4.4 TB/year
Hot working set:  last 30 days ~ 360 GB       -> fits comfortably in one Postgres + object storage
AI:               0.3 calls/user/day x 8k tokens x 5,000 = ~12M tokens/day
```

Those numbers decide everything: 70 events/sec needs **no** Kafka, no sharding, and no NoSQL. A single well-indexed Postgres plus Redis handles it with room to spare. The most valuable senior skill on display here is *not* choosing the distributed system.

### The Diagram Set

```text
Level 1  Context:    the system, its users, and external systems
Level 2  Container:  deployable units (web app, API, worker, DB, cache, queue)
Level 3  Component:  modules inside one container, with responsibilities
Level 4  Code:       class/function level - usually skip in an HLD
```

```text
[Browser] --HTTPS--> [CDN] --> [Web app: RSC + actions]
                                     |
                    +----------------+----------------+
                    |                |                |
              [Postgres]        [Redis]        [Object storage]
                    ^
                    |
             [Worker: jobs, email, exports]  <-- [Queue]
```

```text
[Sync servers] --Pub/Sub--> [Redis] --Pub/Sub--> [Sync servers]   (realtime fan-out)
       |
  [Postgres: op log + snapshots]
```

### Storage Selection Is A Requirements Exercise

| Access pattern | Choice | Why |
|---|---|---|
| Transactions, joins, constraints | PostgreSQL | correctness features are free, you pay later without them |
| Key-value with TTLs | Redis | sub-ms, memory-bound, disposable |
| Large immutable files | Object storage | cheap, durable, served via CDN + signed URLs |
| Full-text search at scale | Dedicated search engine | ranking, faceting, typo tolerance |
| Hierarchical event history | Append-only log | immutable replay, auditability |
| Analytics over billions of rows | Columnar warehouse | scans over columns, not rows |

### Non-Functional Requirements Are The Real Design

```text
Availability:    99.9% (43m/month) - 99.99% costs 10x and needs multi-region
Latency:         p95 < 200ms for reads, p95 < 500ms for writes
Consistency:     strong for billing and permissions; eventual for feeds and presence
Durability:      no loss of user content (RPO 0 for documents)
Recovery:        RTO 30 minutes, tested
Data residency:  EU customer data stays in the EU
```

These are the numbers that actually shape architecture. Without them, every design discussion is taste.

### Cache Placement

```text
CDN            static assets, public pages                (minutes to days)
Edge           personalised read models, feature flags    (seconds)
Application    query results, computed views              (seconds to minutes)
Database       materialised views, prepared plans         (seconds)
Client         the router cache, offline documents        (session)
```

Every layer added is a staleness risk. Add cache only where a measurement shows a need, and always with a defined invalidation story.

### Failure Domains

```text
One request fails        -> errors within one action
One instance dies        -> capacity loss, drained gracefully (49.31)
One AZ fails             -> degraded, survives with replicas
One region fails         -> outage unless multi-region
One dependency fails     -> partial outage; decide what degrades and what blocks
The database is gone     -> the product is gone; plan RTO/RPO explicitly
```

### Deeper Explanation: HLD Is Where Senior Begins

A mid-level engineer can implement a component well. A senior engineer can decide **which components should exist at all**, and that decision is the difference between a system that grows and one that collapses under its own coordination cost.

The three questions that reveal whether someone can do HLD:

1. What are the requirements, expressed as numbers?
2. What is the simplest design that meets them?
3. What breaks first, and what does the user see when it does?

Anyone can draw boxes. Answering those three with specifics is the skill.

### Additional Pitfalls

- **Designing for scale you do not have.** Premature distribution buys permanent operational cost for imagined load.
- **No stated consistency requirement.** "We'll use eventual consistency" without saying where it is unacceptable is a bug generator.
- **Ignoring the failure story.** A design without a degradation plan fails unpredictably.
- **Diagrams with no data-flow direction.** Boxes and arrows that do not say who calls whom and when.
- **No ADR trail.** Six months later nobody remembers why, and the decision gets re-litigated.

### Real-World Deal-Breakers
- **Architecture chosen before requirements** - a distributed system for 7 events/sec, with matching complexity and bills.
- **No non-functional requirements** - performance and availability become arguments rather than targets.
- **Single region with a global user base** - hundreds of milliseconds added to every interaction.
- **No documented decision history** - the team re-decides the same trade-off every quarter.
- **A cache everywhere with no invalidation policy** - users see stale data and nobody can explain why.
