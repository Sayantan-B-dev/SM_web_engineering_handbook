### The Fallacies, Applied

```text
1. The network is reliable        -> assume drops; make every call timeout + retry-safe
2. Latency is zero                -> every remote call is a failure mode, not a function call
3. Bandwidth is infinite          -> pagination and streaming, never "send everything"
4. The network is secure          -> encrypt, authenticate, assume hostile transit
5. Topology doesn't change        -> DNS changes, AZs fail, IPs move
6. There is one administrator     -> version skew between services is normal
7. Transport cost is zero         -> cross-region chatter dominates latency
8. The network is homogeneous     -> a phone on 2G and a datacentre box are both clients
```

Every distributed bug you will ever debug is one of these eight, wearing a disguise.

### CAP And PACELC

CAP says: under a network partition, choose consistency or availability. PACELC extends it: even with no partition, choose latency or consistency.

```text
Postgres primary (read from primary)   -> PC/EC  (consistent, slower)
Postgres read replica                  -> PA/EL  (stale reads possible, fast)
Redis cache                            -> PA/EL  (fast, can be stale)
Billing ledger                         -> PC/EC  (never trade correctness for speed)
Document CRDT                          -> PA/EL  (converges later; availability first)
```

Most real systems are a *mix*, chosen per data type. The skill is deciding per operation, not per company.

### Exactly-Once Is A Lie; Idempotency Is The Answer

```typescript
/** At-least-once delivery + idempotent handling = effectively-once. */
async function handleEvent(evt: Event) {
  // Uniqueness enforced by the database, not by hope
  const inserted = await db.query(
    `insert into processed_events (event_id, handler, processed_at)
     values ($1, $2, now())
     on conflict (event_id, handler) do nothing
     returning event_id`,
    [evt.id, 'billing'],
  );
  if (inserted.rowCount === 0) return;    // already handled: safe retry

  await applyBilling(evt);                // inside the same transaction where possible
}
```

A unique constraint is the only reliable de-duplicator. In-memory sets, "we check before we act", and message-broker dedup windows all eventually fail under concurrency or after a restart.

### Clocks

```text
Wall clock (Date.now)   -> can jump backwards; NTP corrections; never order events with it
Monotonic clock         -> measures durations only; no absolute meaning
Logical clock (Lamport) -> total order for causality; no real time
Vector clock            -> detects concurrency, not just order
Hybrid (HLC)            -> wall-clock-ish + causality; used by modern databases
```

Rule: **use wall clocks for display, logical clocks for ordering.** The Atlas CRDT (49.22) does exactly this.

### Retries With Jitter

```typescript
async function withRetry<T>(fn: () => Promise<T>, opts = { attempts: 4, baseMs: 200, capMs: 5_000 }) {
  for (let i = 0; i < opts.attempts; i++) {
    try {
      return await withTimeout(fn(), 3_000);
    } catch (err) {
      if (!isRetryable(err) || i === opts.attempts - 1) throw err;
      const backoff = Math.min(opts.capMs, opts.baseMs * 2 ** i);
      await sleep(Math.random() * backoff);      // full jitter: no synchronised retry storm
    }
  }
  throw new Error('unreachable');
}
```

Without jitter, every client whose request failed at the same moment retries at the same moment, and the recovering service is knocked over again.

### Sagas Instead Of Distributed Transactions

```text
Order:  reserve inventory -> charge payment -> create shipment -> notify
Saga:   each step has a compensating action
        create shipment fails  -> refund payment -> release inventory -> notify failure
```

Two-phase commit across services requires coordination infrastructure and holds locks across the network. A saga accepts temporary inconsistency and defines explicit compensation - which is also what a business actually wants (a refund is a real, auditable thing).

### Deeper Explanation: Distribution Is A Last Resort

Every property you take for granted in a single process - ordering, atomicity, shared memory, a single clock - is gone the moment you cross a network boundary.

The professional posture is therefore conservative: keep a system on one machine for as long as it can possibly handle the load, and distribute only where a measurement forces it. Each additional service doubles the number of failure modes you own.

### Additional Pitfalls

- **Retrying non-idempotent operations.** A timeout is not a failure; the write may have succeeded.
- **No timeout on a remote call.** One slow dependency becomes a full outage as connection pools fill.
- **Using `Date.now()` to order events.** Clock skew produces permanently wrong ordering.
- **Synchronous chains across services.** p99 latencies multiply; a four-hop chain at p99 each is a coin flip.
- **No bulkhead.** One saturated dependency consumes all workers and takes down unrelated features.

### Real-World Deal-Breakers
- **Retries without jitter** - a retry storm turns a blip into a lasting outage.
- **No idempotency on payment or write paths** - double charges and duplicated records.
- **Cross-region synchronous calls in a request path** - every request pays the distance twice.
- **Assuming a message arrives exactly once** - silent duplicates in billing and notifications.
- **No defined consistency requirement** - two services disagree permanently with no source of truth.
