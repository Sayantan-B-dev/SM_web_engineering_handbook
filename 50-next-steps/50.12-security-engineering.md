### Threat Modelling In Fifteen Minutes

```text
1. Assets        what would hurt if lost or leaked? (customer documents, tokens, keys)
2. Actors        who wants them? (opportunist, competitor, insider, automated scanner)
3. Boundaries    where does trust change? (browser->server, server->DB, server->LLM API)
4. STRIDE        per boundary: Spoofing, Tampering, Repudiation,
                 Information disclosure, Denial of service, Elevation of privilege
5. Controls      one concrete control per credible threat
```

```text
Boundary: browser -> server action
  Spoofing            -> session cookie, HttpOnly, SameSite, rotation
  Tampering           -> Zod validation server-side; never trust the body
  Information discl.  -> authorise per resource; NOT_FOUND not FORBIDDEN
  DoS                 -> rate limits per user and per route
  Elevation           -> re-check role server-side; no role from the client
```

This is the exercise that finds real weaknesses. A generic checklist does not know that your app pastes user content into an LLM prompt.

### Cryptography Rules

```text
Use                  Never
AES-256-GCM          custom ciphers, ECB mode
Argon2id (passwords)  SHA-256 for passwords
TLS 1.3              TLS 1.0/1.1, self-signed in prod
libsodium / WebCrypto hand-rolled crypto, custom JWT signing
randomUUID / secrets   Math.random() for tokens
```

```typescript
import { randomBytes, timingSafeEqual } from 'node:crypto';

const token = randomBytes(32).toString('base64url');          // CSPRNG

// Constant-time comparison for any secret
export function safeEqual(a: string, b: string) {
  const ab = Buffer.from(a); const bb = Buffer.from(b);
  return ab.length === bb.length && timingSafeEqual(ab, bb);
}
```

`===` on a token leaks information through timing. It is a one-line fix that closes a real class of attack.

### Secrets Lifecycle

```text
Store      parameter store / vault, never in Git or an image layer
Access     short-lived credentials via workload identity (OIDC)
Rotate     scheduled, automated, and tested in staging first
Detect     scanning in CI and in git history (gitleaks)
Respond    rotation runbook ready before it is needed
```

A secret that has ever been committed must be rotated, not deleted. Git history is permanent and forks keep copies.

### Detection And Response

| Layer | Signal |
|---|---|
| Auth | failed-login spikes, impossible travel, new device + immediate sensitive action |
| Data | unusual export volume, bulk reads outside business hours |
| Network | egress to unexpected destinations |
| Dependencies | new postinstall scripts, unexpected maintainer changes |
| Application | authorisation denials clustered by user |

```text
Response: contain, eradicate, recover, notify, learn.
Have the runbook written, the contacts current, and the legal path known before an incident.
```

### Deeper Explanation: Security Is A Property Of The Design

You cannot test quality into a system, and you cannot patch security into one. Every serious vulnerability class - IDOR, XSS, SSRF, secret leakage - is prevented structurally: authorise in one place, sanitise at one boundary, scope secrets to the server, validate all input.

The professional practice is therefore boring and consistent: a threat model per feature, a control at each trust boundary, secure defaults in the framework and the design system, and an incident plan that is rehearsed rather than imagined.

### Additional Pitfalls

- **Authenticating but not authorising.** Knowing who the caller is does not mean they may do this.
- **Trusting a client-provided role, tenant or price.** Anything from the client is input, not fact.
- **Secrets in logs.** Debug logging a config object leaks credentials into a centralised log store.
- **No dependency review on PRs.** A malicious transitive package arrives inside a routine feature PR.
- **Security as a pre-launch checklist.** The design decisions that matter are already made by then.

### Real-World Deal-Breakers
- **No authorisation on a data endpoint** - one missing check is a customer-visible breach.
- **Stored XSS in user content** - session theft and self-propagating worms.
- **Credentials in Git history** - rotate immediately; deletion does not undo exposure.
- **No detection or response plan** - the breach is discovered by a third party, months later.
