### What Platform Teams Actually Build

```text
Golden path for a new service:
  1. scaffolder generates the repo (lint, tests, CI, Dockerfile, healthcheck, observability)
  2. CI runs with sensible defaults on the first push
  3. deploy pipeline exists and targets staging
  4. dashboards and alerts are provisioned, not requested
  5. ownership metadata registered automatically

Result: a new service is production-shaped on day one, with security and
observability defaults the author did not have to remember.
```

### DORA Metrics As A Health Signal

| Metric | Elite | What it reveals |
|---|---|---|
| Deploy frequency | on demand (daily+) | batch size and risk |
| Lead time for change | < 1 day | friction from commit to production |
| Change failure rate | 0-15% | verification quality |
| Mean time to restore | < 1 hour | observability and rollback readiness |

Do not use these to rank people. Use them to find the constraint: high lead time points at CI or review; high MTTR points at observability and rollback.

### Local Development Parity

```yaml
# docker compose: the same versions as production, seeded and ready
services:
  db:    { image: postgres:17-alpine, environment: { POSTGRES_DB: atlas } }
  redis: { image: redis:7-alpine }
  sync:  { build: ./services/sync, depends_on: [db, redis] }
```

```bash
npm run dev          # one command: db + migrations + seed + app + workers
```

Every manual setup step is a step that will be skipped, broken, or differently performed. "Clone, one command, working app" is the highest-leverage DX investment a team can make.

### Documentation As Code

```text
docs/adr/            architecture decision records (why, not what)
docs/runbooks/       operational procedures, linked from alerts
services/*/README    ownership, endpoints, dependencies, on-call rotation
```

Documentation that lives outside the repo goes stale in weeks. Documentation generated, linked and reviewed alongside the code survives.

### Deeper Explanation: DX Compounding

Developer experience compounds. A five-minute saving in the inner loop, repeated fifty times a day across ten engineers, is hours per day. A one-time improvement to onboarding turns a two-week ramp into two days, for every hire forever.

The reason to invest in platform work is not aesthetic. It is that every unit of friction in the delivery loop is paid over and over, and the cheapest time to remove it is before the team grows.

### Additional Pitfalls

- **Platform built without users.** An internal tool nobody asked for, adopted by nobody.
- **Golden path that is not the easiest path.** Engineers route around it and you maintain two worlds.
- **Ticket-driven infrastructure.** Slow, interrupt-driven and impossible to scale past one team.
- **CI that takes forty minutes.** People batch changes, and batch size is the risk driver.
- **Onboarding by tribal knowledge.** Every new hire costs a senior engineer a week.

### Real-World Deal-Breakers
- **No golden path** - every service is bespoke; security and observability are inconsistent.
- **Infrastructure by ticket** - a one-day provisioning queue becomes a two-week project.
- **No local parity** - "works in staging, not locally" becomes the default debugging experience.
- **Metrics used to rank engineers** - the numbers get gamed and stop measuring anything real.
