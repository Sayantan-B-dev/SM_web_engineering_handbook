### Percentiles, Not Averages

```text
100 requests: 99 at 20ms, 1 at 5,000ms
average = 69ms     <- looks fine
p95     = 20ms
p99     = 5,000ms  <- what one user in a hundred experiences
```

In a request path that fans out to 10 services, a 1% slow path means a 10% chance the *user's* request hits a slow dependency. Tail latency compounds; averages hide it.

```text
p50  the typical experience
p95  the experience of your most active users (they make most requests)
p99  the experience that generates support tickets
max  the experience that generates incidents
```

### Little's Law And Queueing

```text
L = λ x W
concurrency = arrival rate x time in system

10,000 rps x 0.02s = 200 in-flight requests
```

And the queueing knee:

```text
utilisation  0.5  -> queue wait  ~ 1x service time
utilisation  0.8  -> queue wait  ~ 4x service time
utilisation  0.9  -> queue wait  ~ 9x service time
utilisation  0.95 -> queue wait ~ 19x service time
```

A system running at 80% utilisation under an average load is already near a cliff for any spike. Capacity planning is about headroom, not averages.

### Budgets In CI

```typescript
// performance/budget.ts - a regression fails the build
export const BUDGETS = {
  initialJsGzipKb: 180,
  lcpMs: 2500,
  inpMs: 200,
  apiP95Ms: 300,
  editorKeystrokeMs: 50,
} as const;

if (measured.initialJsGzipKb > BUDGETS.initialJsGzipKb) {
  throw new Error(`Bundle budget exceeded: ${measured.initialJsGzipKb} KB > ${BUDGETS.initialJsGzipKb} KB`);
}
```

An unenforced budget is a wish. Performance regressions accumulate one dependency, one component and one query at a time until nobody can find the cause.

### Deeper Explanation: Performance Is Usually A Design Choice

By the time you are optimising, the expensive decisions are already made: an N+1 query pattern, a page-level `'use client'`, a chatty service boundary, a synchronous call to a slow dependency in a request path.

Professionals therefore spend their effort on *design* performance: set budgets, choose data access patterns that scale, keep the critical path short, and measure continuously. Optimisation then becomes confirming the design, not rescuing it.

### Additional Pitfalls

- **Optimising without a baseline.** No measurement means no way to know whether the change helped.
- **Averages in dashboards.** They hide the tail that generates complaints.
- **Caching to hide a slow query.** The query is still slow; the problem returns at the next cache miss.
- **Load tests against a warm cache and a seeded database.** The numbers are fiction.
- **Micro-optimising a path that is not hot.** Time spent for no user-visible change.

### Real-World Deal-Breakers
- **No performance budget in CI** - regressions ship continuously and are found by users.
- **Systems run at 85%+ utilisation** - a small spike becomes a queueing collapse.
- **Tail latency ignored in a fan-out path** - a small per-service tail becomes a large user-facing failure rate.
- **Load testing only at steady state** - the ramp and the recovery are where systems actually fall over.
