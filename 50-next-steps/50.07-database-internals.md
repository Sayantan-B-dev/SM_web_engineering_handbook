### B-Tree vs LSM

| | B-tree (Postgres, MySQL) | LSM-tree (Cassandra, RocksDB) |
|---|---|---|
| Reads | fast, predictable | slower (checks multiple levels) |
| Writes | in-place, may random-write | append-only, fast |
| Space | may fragment | compaction overhead |
| Best for | transactional, mixed | write-heavy, time-series |

For a product database with transactional requirements, B-tree (Postgres) remains the right default. LSM shines when writes dominate and access patterns are key-based.

### Index Selection

| Index | Use for | Example |
|---|---|---|
| B-tree | equality, range, ordering | `(workspace_id, updated_at desc)` |
| Partial | a filtered hot subset | `where deleted_at is null` |
| Covering | index-only scans | include the selected columns |
| GIN | full-text, JSONB, arrays | `tsv @@ query`, `tags @> '{x}'` |
| BRIN | large, naturally ordered | time-series append-only tables |
| Hash | equality only, rarely worth it | - |

```sql
-- Covering index: the sidebar query never touches the heap
create index docs_sidebar_idx on documents (workspace_id, updated_at desc)
  include (id, title)
  where deleted_at is null;
```

### Reading A Plan

```
Limit  (cost=0.43..118.70 rows=50 width=48) (actual time=0.031..0.118 rows=50 loops=1)
  Buffers: shared hit=8
  ->  Index Only Scan using docs_sidebar_idx on documents
        Index Cond: (workspace_id = '...'::uuid)
        Heap Fetches: 0
Planning Time: 0.190 ms
Execution Time: 0.140 ms
```

```text
"actual time" far above "cost"      -> stale statistics; run ANALYZE
"rows=1 ... actual rows=50000"      -> bad estimate; extended statistics needed
"Seq Scan" on a hot table           -> missing or unusable index
"Heap Fetches: 12000"               -> not actually index-only; check the visibility map
"Buffers: shared read=40000"        -> cold cache or a scan that should not be happening
```

`EXPLAIN (ANALYZE, BUFFERS)` is the single most valuable database skill. Everything else about tuning is guesswork without it.

### MVCC And Vacuum

```sql
-- Deleted/updated rows remain until vacuum reclaims them
select relname, n_dead_tup, last_autovacuum
  from pg_stat_user_tables
 order by n_dead_tup desc
 limit 10;
```

High `n_dead_tup` with infrequent autovacuum means bloat: indexes grow, scans slow down, and the disk fills. `VACUUM` is not maintenance you can ignore in a write-heavy system.

### Isolation Levels And Anomalies

| Level | Allows | Breaks |
|---|---|---|
| Read committed (Postgres default) | non-repeatable reads, phantom reads | no lost updates within a statement |
| Repeatable read | - | serialization failures possible |
| Serializable | nothing (SSI) | requires retry logic on conflicts |

```sql
-- Correct pattern for a read-modify-write under concurrency
begin;
select version from documents where id = $1 for update;   -- or rely on a version column
update documents set title = $2, version = version + 1 where id = $1 and version = $3;
commit;
```

### Deeper Explanation: The Database Decides Your Ceiling

Application code scales horizontally and cheaply. The database does not: it holds state, and state is expensive to move. Almost every performance ceiling a growing product hits is a database decision made months earlier - an index that was never added, a query that was never explained, a schema that forced a scan.

Professionals treat the schema and its indexes as first-class design artefacts, reviewed like an API. Amateurs treat the database as a place to dump objects.

### Additional Pitfalls

- **`seq scan` on tables with millions of rows.** Usually a missing partial index, not a need for a bigger machine.
- **No `ANALYZE` after a bulk load.** The planner works from stale statistics and chooses bad plans.
- **Long-running transactions.** They block vacuum and cause bloat across the whole database.
- **Sharding before partitioning.** Partitioning inside one database is far cheaper and often sufficient.
- **N+1 queries hidden behind an ORM.** Profile with real data volumes, not 20 seed rows.

### Real-World Deal-Breakers
- **No index on the primary access path** - performance decays as the customer succeeds.
- **Autovacuum disabled "for performance"** - bloat and eventually transaction-ID wraparound.
- **Migrations that lock a large table** - a deploy causes minutes of downtime under load.
- **Read replicas without handling replication lag** - read-your-own-write breaks and users think data was lost.
