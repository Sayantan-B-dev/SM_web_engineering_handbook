### Failure Domains And What Survives

```text
Process crash      -> orchestrator restarts it          (seconds)
Instance loss      -> load balancer routes away         (seconds)
AZ loss            -> replicas in another AZ            (minutes, automatic)
Region loss        -> needs multi-region               (hours, manual)
Data corruption    -> needs backups + PITR             (minutes, manual)
```

Match the architecture to the requirement. "We must survive a region loss" is a 3-10x cost multiplier and should be a conscious business decision, not an assumption.

### Choosing Compute

| Workload | Choose | Why |
|---|---|---|
| Request/response web app | serverless or containers | scales to zero, pay per use |
| Long-lived WebSockets | containers/VMs | serverless cannot hold sockets |
| Background jobs | queue + workers | retries, backpressure, isolation |
| Scheduled maintenance | cron/serverless timer | rare, cheap |
| Data-heavy batch | spot VMs | 70% cheaper, interruption-tolerant |
| Latency-critical reads | edge/CDN | close to the user |

### Networking Boundaries

```text
Internet -> CDN/WAF -> public load balancer -> app subnet
                                                  |
                                        private subnet: DB, cache
                                        (no route to the internet)
```

The database must never have a public endpoint. Private subnets plus security groups plus an egress path only where required is the baseline; it removes an entire class of incident.

### Autoscaling On The Right Signal

```text
Web/API            -> requests per target, or CPU
WebSocket servers  -> active connections (memory-bound, not CPU-bound)
Queue workers      -> queue depth and age (oldest message), not CPU
Batch              -> schedule, not autoscaling
Database           -> vertical first; read replicas for read scale
```

Autoscaling the realtime tier on CPU is the classic mistake: idle sockets consume no CPU, so the fleet never scales while memory runs out and connections are refused.

### Cost Architecture

| Item | Often overlooked | Lever |
|---|---|---|
| Egress | 60-80% of a CDN bill | cache aggressively, signed URLs, compress |
| Idle capacity | over-provisioned "just in case" | right-size, schedule down non-prod |
| Storage tiers | hot storage for cold data | lifecycle policies |
| Cross-AZ traffic | chatty service-to-service calls | co-locate, batch |
| Observability | log volume in the bill | sampling, retention, cardinality |

### Deeper Explanation: You Are Buying Failure Domains

The real question in cloud architecture is not "which service?" but "which failure domains am I insulated from, and at what price?" A single-AZ deployment is cheap and fails for two hours a year. A multi-region active-active deployment is resilient and triples cost and complexity.

Professionals make that trade explicitly, per system, and write it down - including the systems where the answer is deliberately "we will accept an outage and restore from backup."

### Additional Pitfalls

- **Multi-region active-active without a data strategy.** Latency and conflict resolution become unsolvable later.
- **Serverless for a socket workload.** Fails in production after working locally.
- **No egress awareness.** A video-heavy feature generates a bill that outgrows the revenue.
- **IAM with wildcard permissions.** One compromised component reaches everything.
- **Backups in the same account and region.** A compromised account loses the data and the backups.

### Real-World Deal-Breakers
- **Publicly reachable database** - exposed to the internet and to credential stuffing; a breach.
- **No DR plan with a tested restore** - RTO and RPO are assumptions until exercised.
- **Over-broad IAM roles** - any RCE escalates immediately to full account access.
- **Autoscaling WebSocket servers on CPU** - capacity never scales while memory runs out.
