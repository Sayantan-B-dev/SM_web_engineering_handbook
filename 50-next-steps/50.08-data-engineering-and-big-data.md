### OLTP And OLAP Are Different Problems

| | OLTP (Postgres) | OLAP (warehouse) |
|---|---|---|
| Query shape | one row, indexed | scan millions, aggregate |
| Optimised for | write throughput, correctness | scan throughput, compression |
| Schema | normalised | denormalised (star) |
| Updates | frequent, in-place | append/merge in batches |
| Example | "get document 42" | "weekly active editors by plan" |

Running analytics on the production database is the most common data mistake in a growing product: one dashboard query can hold locks and slow every user.

### Dimensional Modelling

```text
fact_document_edits
  edit_id, occurred_at, document_id, user_id, workspace_id,
  edits_count, bytes_delta, ai_assisted

dim_users      (user_id, signup_date, plan, country, ...)
dim_documents  (document_id, workspace_id, created_at, type, ...)
dim_dates      (date, week, month, quarter, year, is_weekend)
```

Facts are events with measures; dimensions are context. Almost every analytics question becomes a group-by over a fact joined to dimensions - and pre-joining them into a wide fact table is what makes warehouse queries fast.

### Columnar Storage

```text
Row store  : [id1,..,id2,..] -> read one full row cheaply, whole rows for a scan
Column store: [all ids][all dates][all counts] -> read one column across billions of rows
```

```sql
create table fact_edits (
  occurred_at  timestamp,
  workspace_id uuid,
  user_id      uuid,
  edits        int
)
partition by range (occurred_at);                 -- prune by time automatically
```

Parquet + partition pruning + column pruning turns a 10 TB scan into a 10 GB one. Most "big data" performance work is exactly this.

### ELT And Idempotent Transformation

```sql
-- dbt model: idempotent, tested, documented version control for transformations
with daily as (
  select
    date_trunc('day', occurred_at) as day,
    workspace_id,
    count(distinct user_id)        as active_editors,
    sum(edits)                     as total_edits
  from {{ ref('fact_edits') }}
  where occurred_at >= current_date - interval '30 days'
  group by 1, 2
)
select * from daily
```

### Orchestration

```text
extract -> load raw -> transform -> test -> publish
   |          |           |          |         |
 idempotent  append-only  rebuilds   fails     only on green
```

Every run must be re-runnable without duplicating data. A pipeline that cannot be safely re-run is a pipeline that will eventually be run twice, in an incident, under pressure.

### Deeper Explanation: Data Platforms Earn Their Complexity

A warehouse, an orchestrator and a transformation layer are a serious investment. They pay off when there are questions you need to answer repeatedly, with trustworthy numbers, that production queries cannot answer without hurting users.

Below that threshold, the honest answer is often: replicate Postgres to a read replica, run SQL there, and revisit in six months. Big data tooling applied to small data produces large costs and small insights.

### Additional Pitfalls

- **No data contracts.** A producer changes a field name and every downstream dashboard silently breaks.
- **Non-idempotent loads.** A retry duplicates rows and inflates metrics; nobody notices for a quarter.
- **Analytics on the production primary.** Dashboards degrade the product for real users.
- **No retention policy.** Storage cost grows forever for data nobody queries.
- **PII copied into the warehouse by default.** Compliance exposure in a system with weaker access controls.

### Real-World Deal-Breakers
- **Untested transformations** - decisions made on wrong numbers, with false confidence.
- **No lineage** - a broken metric takes days to trace back to a changed source column.
- **Duplicated loads** - double-counted revenue reported to the business.
- **Personal data in an ungoverned warehouse** - a breach surface and a GDPR problem.
