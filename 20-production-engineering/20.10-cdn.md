### The Caching Header That Matters Most
> "`Cache-Control: public, max-age=31536000, immutable` - the `immutable` directive tells browsers and CDN edges never to revalidate. Since the URL changes when the content changes, the old URL is correct forever. This is the single most impactful caching header for frontend assets."

### HTML Caching - The Hard Part
```text
/assets/app.abc123.js   → Cache-Control: public, max-age=31536000, immutable
/assets/styles.def456.css → Cache-Control: public, max-age=31536000, immutable
/index.html              → Cache-Control: public, max-age=0, must-revalidate
```

**Stale HTML problem:** If `index.html` is cached at the CDN edge with a long TTL, it can keep pointing to old JS bundles after a deploy. Worse, if you clean up old assets, the stale HTML 404s. Solution: short TTL for HTML + keep old assets for at least 30 days.

---

### Deeper Explanation: The Cache Hierarchy Is The Product

A CDN is not "a server closer to the user" â€” it is a **hierarchical cache with a configuration language**. Everything that matters is the answer to two questions: how long may this response be reused, and under what key. Get those right and the CDN absorbs traffic spikes for free; get them wrong and users see stale bundles or you pay origin egress for content that never changes.

Rules that hold across Vercel, Cloudflare, AWS, and Fastly:

- **Content-hashed assets: `max-age=31536000, immutable`.** The URL changes when the content changes, so caching forever is safe.
- **HTML entry points: `no-cache` (revalidate) or a very short TTL.** This is the pointer that must not be stale.
- **Vary deliberately.** `Vary: Accept-Encoding` is default; `Vary: Cookie` or `Accept-Language` fragments the cache and is a common performance cliff. Prefer per-locale URLs over `Vary` on locale.
- **Stale-while-revalidate** gives instant responses during revalidation: fast for users, fresh within seconds.
- **Compression at the edge**, Brotli preferred, plus early hints for the fonts and the entry bundle.

### Extended Example: Headers That Produce The Right Cache Behaviour

```nginx
# entry point â€” always revalidated
location = /index.html {
  add_header Cache-Control "public, max-age=0, must-revalidate";
  add_header Link "</fonts/inter.woff2>; rel=preload; as=font; crossorigin";
}

# immutable hashed assets â€” cached for a year at every layer
location ^~ /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
  access_log off;
}

# API reads â€” allow the edge to serve a 60s stale copy while revalidating
location /api/feed {
  add_header Cache-Control "public, max-age=0, s-maxage=60, stale-while-revalidate=300";
}
```

### Additional Pitfalls
- **Caching HTML with a long TTL.** Users keep an old app shell that references purged assets; every deploy becomes a support ticket.
- **`Vary: Cookie` on a public page.** Cache hit rate collapses to zero for logged-in traffic.
- **Assuming a purge is instant.** Global invalidation is eventually consistent; make the URL the cache key instead of purging.
- **Serving uncompressed or double-compressed responses.** Verify with `curl -H 'Accept-Encoding: br' -I`.
- **Forgetting `stale-while-revalidate`.** The opportunity cost is a second request on the critical path for every cache expiry.

### Real-World Deal-Breakers
- **Caching HTML too long** → users get stale pages pointing to deleted assets.
- **No `immutable` on hashed assets** → browsers revalidate unnecessarily.
- **Deleting old assets immediately** → users with stale HTML get 404s. Keep old assets for 30+ days.
- **No CDN** → global users experience 500ms+ TTFB.
