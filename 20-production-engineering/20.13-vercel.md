### Deeper Explanation: Vercel Is A Build Contract

Vercel's mental model: your repository is a *build contract* â€” framework detection, a build command, an output convention â€” and every push produces an immutable deployment bound to a URL. The implications are what matter:

- **Deployments are immutable and addressable.** Every push gets its own URL, which makes preview review and instant rollback trivial (`vercel rollback` or promote a previous deployment).
- **The edge is part of the runtime.** Middleware, ISR, and edge functions execute close to users, so which layer a piece of logic runs in is a real architecture decision, not a deployment detail.
- **Caching is declarative.** `revalidate`, route segment config, and `Cache-Control` headers drive a shared CDN cache; being explicit about them is the difference between a fast site and one that re-renders per request.
- **Environment variables are per environment** (Production, Preview, Development), and client-exposed ones must be prefixed `NEXT_PUBLIC_` â€” i.e. public forever.

### Additional Pitfalls
- **A build-time secret exposed as `NEXT_PUBLIC_`.** It ships to every visitor; use a server route to mint scoped tokens instead.
- **Assuming preview deployments are private.** They are publicly reachable by URL unless protected; add Deployment Protection for anything sensitive.
- **Unbounded serverless execution.** Long jobs on a request path hit function limits; move them to a queue or cron.
- **Ignoring the build output size.** Large functions cold-start slowly and can exceed bundle limits; inspect the build summary.
- **No staging environment.** If preview is your staging, preview-only data and secrets must be genuinely isolated.

### Real-World Deal-Breakers
- **Using ISR heavily** → locked into Vercel; migration is painful.
- **No bandwidth monitoring** → a viral post can cost thousands in overages.
- **Assuming Vercel is cheap at scale** → $20/seat + $40/100GB adds up fast.
