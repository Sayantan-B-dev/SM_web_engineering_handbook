### Atomic Rollouts with Content-Hashed Assets
> "A deployment reduces to two steps: upload the new hashed assets to the CDN, then update the `index.html` to reference the new entry points. Rolling back means pointing the HTML at the previous set of hashes."

```text
Deploy v1: /assets/app.abc123.js  ← immutable, cached forever
           /index.html            ← references abc123

Deploy v2: /assets/app.789xyz.js  ← new file, new hash
           /index.html            ← updated to 789xyz

Rollback:  /index.html            ← point back to abc123
           (app.abc123.js still on CDN)
```

### Database Migration Rollback
The hardest part of rollback: **database migrations**. A forward-only migration that drops a column can't be rolled back safely. Strategies:
- **Expand-contract pattern** - add new column, migrate data, drop old column in a later deploy.
- **Backward-compatible migrations** - new code works with both old and new schema.
- **Blue-green databases** - separate databases per environment.

### Deeper Explanation: Rollback Is A Design Constraint, Not A Button

A safe rollback demands three things decided *before* the incident: the previous artifact still exists and is deployable, the change is backward compatible with the state left behind, and one person can execute it without a meeting. That third point matters most under pressure.

The hard part is usually state. Frontend rollbacks interact with four kinds of state:

- **Cache**: old HTML referencing purged new assets (or vice versa) â€” solved by immutable hashed assets plus short-cached entry points, and by invalidating the entry point on rollback.
- **Browser storage**: a new schema written by the new version must be readable by the old one. Version your persisted state and write migrations that tolerate *down*-leveling, or accept that rolling back is not possible and use forward-only fixes.
- **Server API**: rolling back the client while the server has already evolved is fine only if the API is additive; otherwise roll back both.
- **Flags**: the cheapest rollback of all â€” a kill switch turns a 4-hour incident into a 30-second config change.

### Extended Example: Storage Schema Versioning That Survives A Rollback

```ts
import { z } from 'zod';

const V2 = z.object({
  version: z.literal(2),
  cart: z.array(z.object({ sku: z.string(), qty: z.int().positive() })),
});

const KEYS = { state: 'app.state' } as const;

export function loadState() {
  const raw = localStorage.getItem(KEYS.state);
  if (!raw) return { version: 2 as const, cart: [] };
  try {
    const parsed = V2.parse(JSON.parse(raw));
    return parsed;
  } catch {
    // Unknown shape (older or newer build): start clean rather than crash.
    // Forward-only features must therefore be additive, not destructive.
    localStorage.removeItem(KEYS.state);
    return { version: 2 as const, cart: [] };
  }
}
```

### Additional Pitfalls
- **A rollback path that was never rehearsed.** You discover the missing permission, the wrong image tag, or the expired token during the incident.
- **Destructive migrations shipped alongside UI changes.** A dropped column cannot be un-dropped; split the deploy into expand, migrate, contract.
- **Relying on CDN purge that takes minutes.** Design the cache keys so a rollback does not need a global purge.
- **No "what changed" view.** Rollback decisions stall while people reconstruct the release scope; keep an automated change list per artifact.
- **Rolling back during an active data write.** Your users may lose work; freeze writes or make the write path tolerant of both versions first.

### Real-World Deal-Breakers
- **No rollback plan** → rollback takes 30-60 minutes of manual recovery.
- **Destructive migrations** → rollback impossible. Use expand-contract.
- **No skew protection** → users with a tab open from before deploy hit old JS against new API.
- **Rollback not tested in staging** → the rollback plan fails when you need it most.
