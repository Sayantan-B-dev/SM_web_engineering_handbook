## 20.4 CI/CD

### Subtopic Tree
- Continuous Integration (CI) - automated testing, linting, type checking
- Continuous Deployment (CD) - automated deployment on merge
- Pipeline stages: lint → typecheck → test → build → deploy
- Path filtering (only run jobs for changed packages)
- Matrix builds (multiple Node versions)
- Caching (dependencies, build artifacts)
- Parallelism and sharding
- Deployment gates (manual approvals)
- Pipeline security (OIDC, least privilege)

### Standard CI Pipeline Stages
```
PR opened → Lint → Typecheck → Unit tests → Build → Preview deploy → E2E tests
Merge to main → Lint → Typecheck → Tests → Build → Deploy to staging → Smoke tests → Deploy to production
```

---

### Deeper Explanation: CI Is A Gate, CD Is A Contract

Continuous integration answers one question: *is this commit safe to merge?* Continuous delivery answers a different one: *can we put this commit in front of users within minutes, safely?* Optimising for the first without the second produces fast merges and terrifying deploys; optimising for the second without the first produces confident deploys of code nobody verified.

A pipeline worth trusting has four properties: **deterministic** (same commit â†’ same artifact, pinned toolchain, lockfile honoured), **fast on the critical path** (lint and unit tests in the first minute; E2E sharded and parallel), **exclusive** (a branch cannot merge with a red required check), and **reversible** (an artifact is immutable and redeployable, so rollback is a pointer change, not a rebuild). Cache only what is safe to cache â€” dependency stores and build outputs keyed by lockfile hash, never anything derived from secrets.

### Extended Example: Pipeline Shape That Keeps The Critical Path Short

```yaml
name: ci
on: [pull_request]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true      # supersede stale runs on the same branch

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint && pnpm typecheck
      - run: pnpm test -- --coverage
      - run: pnpm build
  e2e:
    needs: verify              # do not spend 10 minutes on E2E before lint passes
    runs-on: ubuntu-latest
    strategy: { fail-fast: false, matrix: { shard: [1, 2, 3, 4] } }
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm exec playwright test --shard=${{ matrix.shard }}/4
      - uses: actions/upload-artifact@v4
        if: failure()
        with: { name: traces-${{ matrix.shard }}, path: test-results }
```

### Additional Pitfalls
- **No `--frozen-lockfile`.** CI silently resolves newer versions and reports a failure that cannot be reproduced locally.
- **`cancel-in-progress` missing.** Two pushes to one branch burn double the runners and race on deploy environments.
- **Caching `node_modules` instead of the package-manager store.** Path-based caches break across OS and lockfile changes; cache the store keyed by lockfile hash.
- **Required checks that are flaky.** One flaky E2E turns every review into a re-run ritual; quarantine and fix instead of retrying.
- **Deploying the result of a rebuild instead of the verified artifact.** The thing you tested must be the thing you ship â€” build once, promote the artifact.

### Real-World Deal-Breakers
- **No path filtering** → a README change triggers a 30-minute full build.
- **No dependency caching** → `npm install` runs from scratch every time.
- **No type checking in CI** → TypeScript errors ship to production.
- **Deploy from a developer's machine** → non-reproducible, unauditable.
- **No deployment gates** → broken code deploys to production automatically.
