### Deeper Explanation: The Edge Is A Programmable Layer

Cloudflare's distinguishing idea is that the edge is not just a cache â€” it is a programmable request pipeline (Workers, Pages Functions) with a globally distributed key-value store (KV), SQL (D1), strong-consistency storage (Durable Objects), object storage (R2), and queues. That lets an application make decisions before any origin is involved: A/B assignment, geo routing, auth checks, bot mitigation, and response transformation.

The trade-off is architectural. Edge compute has a stricter runtime (limited Node APIs, size and CPU limits per request) and unbounded-state problems, so the question is not "can I move it to the edge" but "which decisions benefit from being close to the user": routing, caching, header policy, redirects, and feature-flag evaluation for cheap flags. Anything transactional, long-running, or CPU-heavy stays at the origin or in a queue.

### Extended Example: A Worker For Caching, Flagging, And Bot Mitigation

```ts
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);

    // 1. Bot mitigation and cheap abuse limits before reaching the origin
    if (isLikelyBot(request) && url.pathname.startsWith('/api/')) {
      return new Response('Forbidden', { status: 403 });
    }

    // 2. Flag evaluation at the edge keeps the client bundle flag-free
    if (url.pathname === '/' ) {
      const cohort = await env.FLAGS.get(`flag:new-home:${cookieValue(request, 'uid')}`);
      const res = await fetch(request);
      if (cohort === 'on') return rewriteTo(request, '/home-v2');
      return res;
    }

    // 3. HTML from cache, revalidate in the background
    const cache = caches.default;
    const hit = await cache.match(request);
    if (hit) {
      ctx.waitUntil(revalidate(request, env, cache));
      return hit;
    }
    return fetchAndCache(request, env, cache);
  },
};
```

### Additional Pitfalls
- **Treating Workers like Node.** Missing APIs and per-request CPU limits surface as confusing runtime errors; check the compatibility flags you actually need.
- **Using KV for read-after-write data.** KV is eventually consistent; sessions and counters belong in Durable Objects or the origin.
- **A cache rule that caches personalised HTML.** The most embarrassing CDN bug there is; scope cache keys or bypass on cookies.
- **Edge logic the team cannot test locally.** Keep worker code in the repo with a dev/test harness, not configured only in the dashboard.
- **Dashboard-only configuration.** It cannot be reviewed, diffed, or recreated; use Terraform/Wrangler config where possible.

### Real-World Deal-Breakers
- **Next.js on Cloudflare** → slightly rougher DX than Vercel. Test thoroughly.
- **Workers runtime limitations** → no Node.js APIs (only a subset). Check compatibility.
- **D1 (SQLite at edge)** → not a full Postgres replacement. For simple data only.
- **No build-time static prerendering** → vinext (Cloudflare's experimental Next.js) doesn't support `generateStaticParams()` yet.
