### S3 + CloudFront Architecture
```text
User → Route 53 → CloudFront (CDN + HTTPS) → S3 (static assets)
                                           → API Gateway → Lambda → DynamoDB
```

```bash
# Create S3 bucket
aws s3 mb s3://my-frontend-app-assets

# Upload build
aws s3 sync dist/ s3://my-frontend-app-assets --delete

# Create CloudFront distribution
aws cloudfront create-distribution \
  --origin-domain-name my-frontend-app-assets.s3.amazonaws.com
```

### Origin Access Control (OAC)
OAC restricts the S3 bucket so **only CloudFront can access it**. The bucket is private; users go through CloudFront.

---

### Deeper Explanation: Static Frontends Need Four Services, Not Forty

The AWS surface area is enormous, but a React app almost always needs the same four building blocks:

- **S3** â€” object storage for the built assets, versioned and server-side encrypted, with public access blocked in favour of an origin access control.
- **CloudFront** â€” the CDN that reads from S3 and the API, applies cache policy, terminates TLS, and gives you a custom domain with a certificate.
- **IAM** â€” the permission model: deploy roles (scoped to the bucket and distribution), immutable infrastructure roles, and OIDC federation for CI instead of long-lived keys.
- **CloudWatch** â€” metrics, logs, and alarms, including synthetic canaries that catch "the page loads but is blank".

Layered on top: Route 53 (DNS), ACM (certificates), Secrets Manager, and DynamoDB/RDS for state. The skill is knowing which of these you must own versus which a platform will own for you â€” knowing the difference is what separates "using AWS" from "rebuilding Vercel badly".

### Extended Example: Deploy With OIDC, Then Invalidate Deliberately

```yaml
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789012:role/deploy-web
    aws-region: eu-west-1

- name: Assets (immutable, long TTL)
  run: aws s3 sync dist/assets s3://web-assets/assets --cache-control 'max-age=31536000,immutable'
- name: Entry points (short TTL)
  run: aws s3 sync dist/ s3://web-assets/ --exclude 'assets/*' --cache-control 'max-age=0,must-revalidate'
- name: Invalidate only the entry points
  run: aws cloudfront create-invalidation --distribution-id "$DIST" --paths '/index.html' '/*.json'
```

### Additional Pitfalls
- **Public S3 buckets.** Use origin access control so only CloudFront can read the objects.
- **Long-lived IAM access keys in CI.** Prefer OIDC federation with short-lived credentials.
- **Invalidating `/*` on every deploy.** It is slow and billed per path; hash the assets instead.
- **One CloudFront distribution for everything.** Separate cache policies per app or one team's rules silently break another's.
- **No budget alarms.** A crawler hitting an uncached endpoint can produce a five-figure bill; alarm on spend and on 4xx/5xx spikes.

### Real-World Deal-Breakers
- **S3 bucket public** → anyone can list and download your files. Use OAC + private bucket.
- **No CloudFront** → S3 alone has no edge caching; global users experience high latency.
- **No ACM certificate** → CloudFront default domain is `*.cloudfront.net`; custom domain needs a cert.
- **No IAM least privilege** → CI/CD credentials have full AWS access. Use scoped IAM roles.
