### Release Strategy Comparison

| Strategy | How it works | Best for | Rollback speed |
|----------|-------------|----------|----------------|
| **Blue/Green** | Two identical environments; switch traffic | Critical systems | Instant (DNS/LB switch) |
| **Canary** | Route 1% → 5% → 10% → 100% to new version | High-risk changes, large user base | Fast (redirect traffic) |
| **Rolling** | Replace instances gradually | Container orchestration | Moderate |
| **Feature Flag** | Deploy code, toggle feature on/off | Decoupling deploy from release | Instant (flag toggle) |

### Deeper Explanation: Decouple Deploy From Release

A deploy moves code to production. A release makes it visible to users. Separating the two is what lets a team ship on Friday at 17:00 and go home: the risky path is behind a flag, the rollout is progressive, and the switch is a configuration change that does not require a build.

The vocabulary to be precise about:

| Strategy | Shape | Best for |
|---|---|---|
| **Blue/green** | Two full environments, switch traffic | Instant rollback, whole-service swap |
| **Canary** | Small percentage of traffic to the new version | Detecting regressions on real traffic |
| **Progressive / percentage rollout** | 1% â†’ 10% â†’ 50% â†’ 100% | Frontend bundles behind flags and edge routing |
| **Ring/Beta** | Internal â†’ trusted users â†’ everyone | Products with engaged early users |
| **Feature flag** | Code shipped dark, enabled per cohort | Everything risky, plus experiments |

Static frontends rarely blue/green; they do **atomic asset promotion** (upload all hashed assets, then flip the HTML/edge routing) plus **progressive client rollout** controlled by a flag or edge logic.

### Extended Example: Atomic Promotion Plus A Kill Switch

```bash
# 1. Upload immutable, content-hashed assets first (safe: nothing references them yet)
aws s3 sync dist/assets s3://app-assets/assets --cache-control 'public,max-age=31536000,immutable'

# 2. Publish the HTML entry points with short caching
aws s3 sync dist/ s3://app-assets/ --exclude 'assets/*' --cache-control 'no-cache'
aws cloudfront create-invalidation --distribution-id "$DIST" --paths '/index.html' '/'

# 3. Release the risky feature to a cohort, with an instant off switch
```

### Additional Pitfalls
- **Deploying assets and HTML together with `no-store` everywhere.** Correct but slow; use immutable hashed assets plus a short-cached entry point instead.
- **A canary with no automated comparison.** Watching a dashboard manually at 2am is not a canary; define the metric and the abort threshold first.
- **Feature flags with no owner or expiry.** Dead flags become permanent branches in production logic; give each one an expiry date.
- **Release notes written after the incident.** Capture the change list at deploy time from the artifact, not from memory.
- **Rollback that requires a rebuild.** If rollback means re-running CI, it is a second risky deploy; promote the previous artifact instead.

### Real-World Deal-Breakers
- **All-or-nothing deploys** → one broken deploy takes down 100% of users.
- **No rollback plan** → a bad deploy becomes an emergency.
- **Feature flags never cleaned up** → 50 stale flags; code becomes unreadable.
- **No canary monitoring** → canary deploys without automated health gates are just slower full deploys.
