## 20.16 Observability (Production Engineering Focus)

### Subtopic Tree
- Logging (console → Loki, CloudWatch)
- Metrics (Core Web Vitals → Mimir, Datadog)
- Tracing (browser spans → Tempo, Jaeger)
- Error monitoring (Sentry, Grafana Faro, Datadog RUM)
- User action tracking
- Geolocation insights
- Session replay
- Synthetic monitoring
- Grafana Faro Web SDK
- OpenTelemetry for browsers

### The Key Shift
> "Traditional frontend performance monitoring tells you whether your application is fast. It doesn't tell you whether people are actually succeeding when using it. It can't reveal which workflows are failing, which user segments are affected, or whether a JavaScript error is quietly preventing customers from completing the actions that matter most."

### Grafana Faro Web SDK
Faro runs in the browser and instruments your app, shipping telemetry through the platform collector (Alloy) into shared observability stores: errors and events land in Loki, browser spans in Tempo, and Core Web Vitals in Mimir.

**What Faro provides:**
- Core Web Vitals (TTFB, FCP, CLS, LCP, INP) collected automatically.
- Logging (`console.info`, `console.warn`, `console.error`).
- Exceptions with stack traces and automatic sourcemap deobfuscation.
- Custom events and metrics.
- OpenTelemetry-based browser traces, connected to backend spans.

### Real-World Deal-Breakers
- **Performance monitoring only** → you know the app is fast but not whether users are succeeding.
- **No error tracking** → JS errors silently prevent conversions.
- **No sourcemaps in production** → stack traces are minified and useless.
- **No user action tracking** → you can't see where users get stuck.
- **No session replay** → debugging a user-reported issue is guesswork.
