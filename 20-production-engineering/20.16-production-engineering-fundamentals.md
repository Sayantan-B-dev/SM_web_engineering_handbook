### The Core Mental Model
> "Deploying means pushing code to production infrastructure. Releasing means letting users see it. When those two actions are fused into one, every deploy is a public event, every rollback is an emergency, and nobody ships on Fridays." - Steve Kinney

Production engineering is about **decoupling deployment from release**. You should be able to deploy code invisible to users, release to 1% of traffic, roll back a bad release without touching the pipeline, and give every PR its own live environment.

### DORA Metrics (The Four Keys)

| Metric | What it measures | Elite benchmark |
|--------|-----------------|----------------|
| **Deployment Frequency** | How often you deploy | On-demand (multiple per day) |
| **Lead Time for Changes** | Commit → production | Less than 1 hour |
| **Change Failure Rate** | % of deploys causing incidents | 0-15% |
| **MTTR** | Mean time to restore | Less than 1 hour |

### Deeper Explanation: The Three Planes Of Production

Production engineering for a frontend team is easiest to reason about as three planes, each with its own failure mode:

- **Build plane** â€” bundling, transpiling, asset hashing. Fails loudly in CI, costs minutes, and is fully reproducible from a lockfile.
- **Delivery plane** â€” environments, secrets, pipelines, previews, releases. Fails *silently*: a missing env var ships a broken analytics client, a partial rollout corrupts cache entries.
- **Runtime plane** â€” CDN, TLS, reverse proxy, observability. Fails *partially*: 3% of users on an old edge node get a stale bundle and nobody sees it in the monitoring dashboard unless the dashboard exists.

The senior distinction is that the build plane is a compiler problem (deterministic, testable) while the other two are distributed-systems problems (eventually consistent, observable only after the fact). Every practice in this chapter exists to convert a silent delivery/runtime failure into a loud build-plane failure â€” lockfiles, schema-validated env vars, health checks, canaries, and rollback drills.

### Additional Pitfalls
- **Treating production as a different codebase.** The only differences between environments should be values (env vars, endpoints), never code paths chosen by `if (process.env.NODE_ENV)` scattered everywhere.
- **No named owner for the delivery plane.** When nobody owns the pipeline, a failing deploy becomes an argument instead of a fix.
- **Launching without a rollback path.** The first time you need rollback is the worst time to discover you cannot do it.

### Real-World Deal-Breakers
- **Deploy = release** → every deploy is a public event; nobody ships on Fridays.
- **No DORA metrics** → you don't know if your delivery process is improving or degrading.
- **Resilience as an afterthought** → failures in production catch you unprepared. Design for failure from day one.
- **No immutable infrastructure** → you can't reliably roll back because you don't know what's deployed.
