### Vercel Preview Deployments
Vercel automatically creates a preview deployment for every Git branch and PR. The URL is posted as a PR comment. Each preview is a full production-like environment with its own URL.

---

### Deeper Explanation: A Preview Must Be Temporary, Isolated, And Disposable

A preview deployment turns every pull request into something a designer, a PM, or a QA engineer can click. To be useful it needs three properties:

- **Isolation** â€” its own URL, its own environment variables, and ideally its own database schema or branch. Sharing production data with a preview is how test writes reach real users.
- **Ephemerality** â€” created on PR open/push, destroyed on merge/close. Orphaned previews leak storage, secrets, and DNS records and eventually cost real money.
- **Parity** â€” the preview should run the *same build* as production (same Node version, same env validation), otherwise "works in preview" stops meaning anything.

The strong version of previews is *preview data*: a branched database or a seeded snapshot, so migrations and destructive paths can be tested before they exist in production.

### Extended Example: Per-PR Database Branch Plus Sticky Comment

```yaml
- name: Branch the database for this PR
  run: |
    npx neonctl branches create --name "pr-${{ github.event.number }}" \
      --parent main --expires-at "$(date -u -d '+3 days' +%FT%TZ)"
  env:
    NEON_API_KEY: ${{ secrets.NEON_API_KEY }}

- name: Comment the preview URL
  uses: marocchino/sticky-pull-request-comment@v2
  with:
    message: |
      Preview: ${{ steps.deploy.outputs.url }}
      API:     ${{ steps.deploy.outputs.api_url }}

- name: Tear down on close
  if: github.event.action == 'closed'
  run: npx neonctl branches delete "pr-${{ github.event.number }}"
```

### Additional Pitfalls
- **Preview deployments with production secrets.** Anyone able to open a PR then has a path to prod; scope preview secrets to staging only.
- **No expiry on branched infrastructure.** Leaked branches and URLs accumulate silently until the bill arrives.
- **Previews only for the frontend.** A frontend preview pointed at production APIs cannot test a backend change at all.
- **Forgetting previews in the CSP and cookie domains.** Cookies set for `example.com` are not sent to `pr-42.preview.example.com`; set the `Domain` attribute deliberately.
- **Assuming previews are private.** Many hosts publish them publicly by default; add auth for anything not meant to be public.

### Real-World Deal-Breakers
- **No preview deployments** → reviewers can't see changes without pulling the branch locally.
- **Preview uses production database** → a PR migration wipes production data. Use a staging DB.
- **No preview protection** → preview URLs are public; unmerged features are visible to anyone.
- **No cleanup** → hundreds of stale preview deployments accumulate.
