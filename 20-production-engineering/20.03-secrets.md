### The AI-Era Problem
AI coding assistants can accidentally expose secrets. Even with instructions to "not read `.env` files," LLMs find creative ways to access them using `cat`, `grep`, or shell tricks.

**Solution:** Secrets encrypted at rest, decrypted only to memory when running:
```bash
npx hush run -- npm start
# Secrets never touch disk, never appear in shell history
```

### GitHub Actions: Secrets vs OIDC
```yaml
# ❌ Long-lived secrets in GitHub
env:
  AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET }}

# ✅ OIDC - no long-lived credentials
permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789:role/GitHubActions
      aws-region: us-east-1
```
OIDC eliminates long-lived credentials by letting GitHub Actions assume an IAM role directly.

---

### Deeper Explanation: Secrets Have A Blast Radius, Manage That Instead Of The List

You can never be sure a secret stays secret forever; you can be sure that rotating it, scoping it, and detecting its use is cheap if you designed for it. Three properties turn secrets from a liability into a controlled risk:

- **Least privilege.** A client-side map key, a read-only database role, a token scoped to one repository. A leaked narrow key is an incident; a leaked root key is a breach.
- **Short lifetime.** Prefer federated identity (OIDC from CI to cloud, short-lived tokens from a broker) over long-lived static strings. If a key must be static, rotate it on a schedule, not after the incident.
- **Detectability.** Secret scanning in git and in CI, plus per-key usage metrics, so you learn about a leak from an alert rather than a customer.

Hard rule: **secrets never enter the client bundle, never enter a log, and never enter a screenshot in a pull request.** A server route mints short-lived credentials for the browser when the browser genuinely needs access.

### Additional Pitfalls
- **A secret in a Docker image layer or a build log.** Both are readable long after the job ends; pass secrets at runtime, never at build time.
- **Logging a config object to debug.** Redact with an allow-list, not a deny-list â€” new keys default to hidden.
- **The same key across all environments.** A staging compromise then reaches production data; issue per-environment keys.
- **Rotating by editing the value everywhere.** Keep secrets in one manager and reference them; rotation should not require touching ten repos.
- **Assuming deleting the commit removes the secret.** It stays in the object database and in every clone; rotate first, rewrite history second.

### Real-World Deal-Breakers
- **Secrets in CI environment variables** → visible in logs if not masked. Use OIDC or a secrets manager.
- **No rotation** → leaked secrets stay valid forever.
- **No audit trail** → you don't know who accessed what secret and when.
- **Secrets in Docker images** → anyone with the image can extract them. Use runtime injection.
