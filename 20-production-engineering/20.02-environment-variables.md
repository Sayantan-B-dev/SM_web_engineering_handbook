### The Hard Truth About Frontend Secrets
> "Frontend applications cannot securely store secrets: any embedded API key is extractable by users and attackers. Environment variables in frontend frameworks like `REACT_APP_API_KEY` are embedded directly into JavaScript strings during build. Anyone can grep your bundled code or inspect the Network tab."

**Frontend env vars are PUBLIC. Never put secrets in them.**

### Framework Prefixes

| Framework | Client prefix | Server-only |
|-----------|--------------|-------------|
| Next.js | `NEXT_PUBLIC_*` | No prefix |
| Vite | `VITE_*` | N/A (all client) |
| Create React App | `REACT_APP_*` | N/A |
| Astro | `PUBLIC_*` | No prefix |
| SvelteKit | `PUBLIC_*` | No prefix |
| Expo | `EXPO_PUBLIC_*` | N/A |

### The BFF Pattern
Place a server-side layer between frontend and third-party APIs. The BFF holds the secrets; the frontend never sees them.

```typescript
// ❌ Frontend calls Stripe directly with secret key
const stripe = new Stripe(import.meta.env.VITE_STRIPE_SECRET); // LEAKED

// ✅ BFF holds the secret
// server/api/payments.ts
export async function POST(req: Request) {
  const stripe = new Stripe(process.env.STRIPE_SECRET); // server-only
  const { amount } = await req.json();
  const payment = await stripe.paymentIntents.create({ amount });
  return Response.json({ clientSecret: payment.client_secret });
}
```

### Type-Safe Env Validation
```typescript
// env.ts
import { z } from 'zod';

const EnvSchema = z.object({
  NEXT_PUBLIC_API_URL: z.string().url(),
  DATABASE_URL: z.string(),
  STRIPE_SECRET: z.string().startsWith('sk_'),
});

export const env = EnvSchema.parse(process.env);
// Throws at startup if any env var is missing or malformed
```

### Secret Management Tools (2026)
- **Hush** - AI-native secrets manager; secrets encrypted at rest, decrypted to memory only. Works with Next.js, Vite, Remix, Expo.
- **Infisical** - centralized secrets management with framework integrations.
- **1Password + dotenvx** - encrypted `.env` files, keys from 1Password.

### Deeper Explanation: `NEXT_PUBLIC_`/`VITE_` Is A Build-Time Contract

For browser bundles there is no such thing as a runtime environment variable: values are **inlined at build time**. Two consequences dominate everything else:

1. **Anything inlined into a client bundle is public.** Prefix conventions (`VITE_`, `NEXT_PUBLIC_`, `PUBLIC_`) are not protection â€” they are documentation of what is already exposed.
2. **One build artifact per environment combination.** If the API URL is inlined, staging and production are different artifacts; if you need the same artifact everywhere, read config at runtime from `/config.json` or from the server on each request.

Client-visible variables should be treated as *capabilities*, not credentials: an analytics write key, a public Stripe key, a Sentry DSN. Secrets stay on the server and reach the browser only as a token minted per request.

### Extended Example: Boot-Time Validation With The Same Schema On Both Sides

```ts
// src/env.ts â€” imported by the client entry and by the server
import { z } from 'zod';

const ClientEnv = z.object({
  VITE_API_URL: z.url(),
  VITE_SENTRY_DSN: z.url().optional(),
  VITE_FLAGS: z.enum(['on', 'off']).default('off'),
});

export const env = ClientEnv.parse({
  VITE_API_URL: import.meta.env.VITE_API_URL,
  VITE_SENTRY_DSN: import.meta.env.VITE_SENTRY_DSN,
  VITE_FLAGS: import.meta.env.VITE_FLAGS,
});
```

```ts
// server env â€” fails at boot, not at 2am in a request handler
const ServerEnv = z.object({
  DATABASE_URL: z.string(),
  JWT_SECRET: z.string().min(32),
  STRIPE_SECRET_KEY: z.string().startsWith('sk_'),
});
export const serverEnv = ServerEnv.parse(process.env); // throws on a missing key
```

### Additional Pitfalls
- **`process.env.X` inside client code that is not prefixed.** The bundler replaces it with `undefined` and you debug an empty string at runtime.
- **Validating env vars lazily.** A missing key should crash at boot with a readable message, not inside a random user request.
- **One `.env` file for every environment.** Copy-pasting `.env` is how staging keys end up in production (and production data ends up in staging).
- **Reading env vars in a module that is imported by tests.** Validation throws during import; inject config or parse lazily behind a function.
- **Assuming a redeploy picks up a changed variable.** For inlined builds, a config change requires a rebuild and redeploy â€” document that in the runbook.

### Real-World Deal-Breakers
- **`NEXT_PUBLIC_` on a secret** → embedded in JS bundle; anyone can extract it.
- **No env validation** → missing `DATABASE_URL` crashes at runtime, not build time.
- **`.env` committed to git** → secrets leaked permanently in git history.
- **Plaintext `.env` files on disk** → AI coding assistants can read them via `cat` or `grep`.
- **No rotation strategy** → a leaked key stays valid forever. Use a secrets manager with rotation.
