### Basic CI Workflow
```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [20.x, 22.x]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test -- --coverage

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20.x
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: build
          path: dist/
          retention-days: 7
```

### Deeper Explanation: Workflows Are Programs With A Security Model

GitHub Actions is an event-driven runner with an important twist: **`pull_request` from a fork runs with a read-only token and no secrets**, while `pull_request_target` runs with secrets and write permissions. That difference is the root of the most common CI security incident â€” a fork's code reaching `pull_request_target` and exfiltrating secrets. Treat every workflow input (branch name, PR title, commit message) as untrusted and never interpolate it directly into a `run:` block.

The other mental model is the cost/latency trade-off: a job per concern gives parallel feedback, but each job pays checkout and install. Use a matrix for sharding, `needs` to gate expensive work on cheap checks, and caching for the dependency store. Keep workflow logic in the repo (composite actions or a `Makefile`/`justfile`) so it can be run locally.

### Extended Example: Safe Script Injection And A Gated Deploy

```yaml
name: preview
on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  comment:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      # WRONG: run: echo "${{ github.event.pull_request.title }}"  (command injection)
      - name: Echo the title safely
        env:
          TITLE: ${{ github.event.pull_request.title }}   # passed as data, not code
        run: printf 'PR: %s\n' "$TITLE"

  deploy:
    if: github.event.pull_request.draft == false
    needs: comment
    environment: preview        # environment protection rules + scoped secrets
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install --frozen-lockfile && pnpm build
      - run: npx vercel deploy --prebuilt --token "$VERCEL_TOKEN"
        env:
          VERCEL_TOKEN: ${{ secrets.VERCEL_TOKEN }}
```

### Additional Pitfalls
- **`${{ ... }}` interpolation inside `run:`.** Branch names and PR titles are attacker-controlled; use `env:` and shell quoting.
- **`pull_request_target` with a checkout of the fork's HEAD.** That combination gives untrusted code your secrets.
- **`permissions: write-all` at the workflow level.** Grant the two scopes the job needs; the default token should be read-only.
- **A single mega-workflow nobody dares to edit.** Split by concern and reuse with composite actions; a pipeline is code and needs review too.
- **Pinning actions by tag (`@v4`).** Tags are mutable â€” pin by commit SHA in security-sensitive repos, or at minimum pin the major version consciously.

### Real-World Deal-Breakers
- **No `concurrency` group** → multiple pushes to the same branch run redundant pipelines.
- **No `cache: 'npm'`** → `npm ci` downloads everything every run.
- **No `needs` dependency** → build runs even when tests fail, wasting CI minutes.
- **No artifact retention limit** → artifacts accumulate forever; storage costs grow.
- **Long-lived AWS credentials** → use OIDC instead.
