### Automatic HTTPS
All modern hosting platforms (Vercel, Netlify, Cloudflare Pages, AWS CloudFront) provide automatic HTTPS with free certificates. No manual certificate management needed.

### HSTS Header
```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
```
Forces browsers to use HTTPS for all future requests. **Preload** submits your domain to Chrome's HSTS preload list.

---

### Deeper Explanation: TLS, HSTS, And The Cookie Contract

HTTPS is three things at once: transport encryption (nobody can read or modify the response), identity (the certificate binds the hostname to a key), and a **platform contract** â€” browsers gate powerful APIs (service workers, geolocation, clipboard, camera, WebAuthn) on a secure context, and `Secure` cookies only work over TLS. Losing HTTPS silently disables the offline layer of your app, which is why mixed content is a functional bug, not just a security warning.

Practical configuration points:

- **Terminate TLS at the edge/CDN**, keep origin traffic encrypted too (VPC-private or also TLS) â€” "the private network is safe" is a dated assumption for a zero-trust posture.
- **Redirect HTTP â†’ HTTPS with HSTS**, and preload only once you are certain every subdomain supports TLS. HSTS is hard to undo.
- **Set `Secure`, `HttpOnly`, and `SameSite` on every cookie**, and scope `Domain` narrowly so preview hosts do not receive production cookies.
- **Certificate automation** (Let's Encrypt/ACME, or the platform's own rotation) with renewal alerting â€” expiry is still a top cause of avoidable outages.

### Extended Example: Headers That Make HTTPS Actually Enforced

```nginx
server {
  listen 80;
  server_name app.example.com;
  return 301 https://$host$request_uri;
}

server {
  listen 443 ssl http2;
  server_name app.example.com;

  add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
  add_header Content-Security-Policy "upgrade-insecure-requests" always;

  ssl_protocols TLSv1.2 TLSv1.3;
  ssl_prefer_server_ciphers off;
  ssl_stapling on;
}
```

### Additional Pitfalls
- **`upgrade-insecure-requests` as the only fix for mixed content.** It upgrades requests but silently breaks ones that cannot be upgraded; fix the URLs instead.
- **HSTS preload before every subdomain is TLS-ready.** You lose access to plain HTTP on those hosts for months.
- **Hard-coded `https://` in the code but `http://` in an OG image URL.** Social crawlers and email clients see the broken variant first.
- **Cookies without `Secure` on a site that also serves HTTP.** They travel in cleartext and are trivially stolen on hostile networks.
- **Expired certificates with no alert.** Monitor expiry (or use a platform that does) â€” this is a self-inflicted outage.

### Real-World Deal-Breakers
- **No HSTS** → users can be downgraded to HTTP via MITM.
- **Mixed content** → HTTPS page loads HTTP assets → browser blocks them, breaks the page.
- **No `Secure` on cookies** → session cookies sent over HTTP.
- **Certificate expiry** → site goes down. Use auto-renewal (Let's Encrypt, ACM).
