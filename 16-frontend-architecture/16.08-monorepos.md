### Why Monorepos
- **Atomic changes** - change a shared package and its consumer in one PR.
- **Single CI pipeline** - one place to configure.
- **Consistent tooling** - one ESLint config, one TS version.
- **Easy refactoring** - rename a function; all consumers update in one commit.
- **Code discovery** - grep across the entire codebase.

### Tool Comparison

| Tool | Purpose | Works with |
|------|---------|-----------|
| **pnpm workspaces** | Package linking | Any monorepo |
| **Turborepo** | Task orchestration, caching | npm/pnpm/Yarn/Bun |
| **Nx** | Task orchestration, plugins, codegen | Anything |
| **Bazel** | Build system at Google scale | Anything (steep learning curve) |
| **Changesets** | Versioning + changelog + publishing | Any monorepo |

### Turborepo Example
```json
// turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "cache": true
    },
    "lint": { "cache": true }
  }
}
```
`turbo run build` builds only affected packages, in dependency order, with local and remote caching.

### Real-World Deal-Breakers
- **Monorepo without a task runner** → `npm run build` in every package every time. Slow CI.
- **No remote cache** → CI rebuilds everything on every push.
- **Shared code with no boundaries** → monorepo becomes a big ball of mud.
- **Monorepo with 50 unrelated teams** → coordination overhead outweighs benefits. Consider polyrepo or multi-repo with shared packages.
- **No `affected` commands** → 2-hour CI for a 1-line README change.
