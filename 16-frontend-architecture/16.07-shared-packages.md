## 16.7 Shared Packages

### Subtopic Tree
- Shared UI packages
- Shared utilities
- Shared types
- Shared config (ESLint, TypeScript, Tailwind)
- Shared API clients
- Shared hooks
- Package boundaries
- Versioning shared packages
- Publishing vs internal-only

### Typical Shared Package Structure
```text
packages/
├── ui/                 # React components
├── utils/              # Pure utilities (no React)
├── types/              # Shared TypeScript types
├── api-client/         # API SDK
├── config-eslint/      # Shared ESLint config
├── config-tsconfig/    # Shared TS config
└── config-tailwind/    # Shared Tailwind preset
```

### Configuration Packages Pattern
```json
// packages/config-eslint/package.json
{
  "name": "@acme/eslint-config",
  "main": "index.js",
  "peerDependencies": { "eslint": ">=8" }
}
```

```json
// apps/web/.eslintrc.json
{ "extends": ["@acme/eslint-config/react"] }
```

This ensures every app uses the same rules. When you add a rule, you update one package.

### Real-World Deal-Breakers
- **`utils` package becomes a dumping ground** → 200 unrelated helpers. Split by domain.
- **UI package imports `utils` package which imports `ui`** → circular dependency.
- **No shared TS config** → each app has different `strict` settings; types drift.
- **Publishing internal packages to npm** → accidental public exposure. Use private registries.
- **Versioning shared packages independently** → dependency hell. Version them together (fixed versioning).
