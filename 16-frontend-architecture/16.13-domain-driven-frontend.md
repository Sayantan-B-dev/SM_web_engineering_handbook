### Bounded Contexts
A **bounded context** is a boundary within which a particular domain model applies. `User` in the **auth** context (email, password) is different from `User` in the **billing** context (customer ID, invoice address) and **social** context (handle, avatar).

```typescript
// features/auth/types.ts
export type User = { id: string; email: string; roles: Role[] };

// features/billing/types.ts
export type User = { id: string; customerId: string; plan: Plan };

// features/social/types.ts
export type User = { id: string; handle: string; avatarUrl: string };
```

These are **different types with the same name** - and that's correct. Trying to unify them into one `User` type creates a god object that serves no context well.

### Ubiquitous Language
Code should use the same vocabulary as domain experts. If the business calls it a "Membership", don't call it `Subscription` in code. If they say "Cancel enrollment", don't call it `unsubscribe()`.

```typescript
// ❌ Developer language
function processUserData(data) { ... }

// ✅ Domain language
function enrollMemberInProgram(member: Member, program: Program) { ... }
```

### Anti-Corruption Layer
When integrating with an external API that doesn't match your domain, build an anti-corruption layer that translates.

```typescript
// The payment provider's API shape
type StripeCharge = { id: string; amount_cents: number; currency: 'usd' };

// Our domain
type Payment = { id: string; amount: Money; status: PaymentStatus };

// Anti-corruption layer
function fromStripeCharge(charge: StripeCharge): Payment {
  return {
    id: charge.id,
    amount: { value: charge.amount_cents / 100, currency: charge.currency },
    status: 'succeeded',
  };
}
```

Now if you switch from Stripe to Adyen, you write one new adapter. The domain doesn't change.

### When DDD Is Overkill on the Frontend
DDD shines in **complex business domains** (insurance, banking, healthcare). For a marketing site or a CRUD dashboard, DDD is a lot of ceremony for very little benefit. Use it when the domain has meaningful rules and terminology.

### Real-World Deal-Breakers
- **One `User` type across all features** → god object with 40 optional fields.
- **No ubiquitous language** → code terms diverge from business terms; new engineers are lost.
- **No anti-corruption layer** → external API shapes leak into the domain.
- **DDD for a CRUD app** → over-engineering; slower velocity with no benefit.
