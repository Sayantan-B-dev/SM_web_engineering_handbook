## 16.4 Modular Monolith

### Subtopic Tree
- Definition: single deployable, multiple internal modules
- vs traditional monolith ("big ball of mud")
- vs microservices
- Module boundaries enforced at build time
- Shared database (single schema, module-specific tables)
- In-process communication (function calls, events)
- Migration path to microservices

### What a Modular Monolith Is
A **single deployable unit** (one app, one build, one deploy) with **strong internal module boundaries**. Modules communicate through explicit interfaces, not by reaching into each other's internals.

```text
Single Deployment Unit
├── module: auth      (own tables: users, sessions)
├── module: posts     (own tables: posts, comments)
├── module: billing   (own tables: invoices, payments)
└── module: shared    (utils, types, UI kit)
```

Each module:
- Has a public API.
- Owns its data.
- Doesn't import another module's internals.

### Modular Monolith vs Microservices

| Feature | Modular Monolith | Microservices |
|---------|-----------------|---------------|
| Deployment | One unit | Many units |
| Communication | In-process function calls | Network (HTTP, gRPC, queues) |
| Transactions | ACID across modules | Distributed (sagas) |
| Latency | Nanoseconds | Milliseconds |
| Complexity | Low | High |
| Team scaling | Moderate | High |
| Debugging | Single stack trace | Distributed tracing |

**The modular monolith is the right default.** Microservices are a scaling solution for **orgs**, not for code.

### Real-World Deal-Breakers
- **"Monolith" without boundaries** → big ball of mud. It's a traditional monolith, not modular.
- **Modules reaching into each other's tables** → you have a distributed monolith (worst of both).
- **Premature microservices** → a 5-person team running 20 services. Operational burden kills velocity.
- **No enforcement** → module boundaries decay over time. Enforce with lint rules and CI checks.
