## 16.14 Frontend Scalability

### Subtopic Tree
- Team scalability (more engineers, same codebase)
- Code scalability (more features, same codebase)
- Performance scalability (more users, more data)
- Organizational scalability (Conway's Law)
- Horizontal vs vertical team structure
- Ownership models
- "You build it, you run it"
- Onboarding time as a metric

### Types of Scalability

| Dimension | Question | Bottleneck |
|-----------|---------|-----------|
| **Team** | Can 50 engineers work here? | Code ownership, merge conflicts |
| **Code** | Can we add 200 features? | Architecture, boundaries |
| **Performance** | Can we handle 10M users? | Bundle size, caching, CDN |
| **Org** | Can we onboard 5 devs/month? | Docs, conventions, dev environment |

### Ownership Models

| Model | Description | Best for |
|-------|-------------|----------|
| **Code owners** | Each file/folder has an owner | Clear accountability |
| **Feature teams** | Team owns end-to-end features | Product-aligned |
| **Platform team** | Central team owns shared libraries | Small companies, shared infra |
| **Guilds** | Cross-team interest groups | Knowledge sharing, standards |

```text
# .github/CODEOWNERS
/features/auth/     @acme/auth-team
/features/posts/    @acme/content-team
/packages/ui/       @acme/design-system-team
/packages/config/   @acme/platform-team
```

### Onboarding Time as a Metric
**How long does it take a new engineer to merge their first PR?** If it's >1 week, something is wrong: docs, dev setup, or architecture. Track it. Improve it.

### Real-World Deal-Breakers
- **No ownership** → no one fixes the bug. "Not my code."
- **Feature team owns 50% of the codebase** → bottleneck.
- **No docs** → every new hire asks the same questions. Slows everyone.
- **Onboarding > 2 weeks** → architecture and tooling need attention.
- **Conway's Law ignored** → org structure and system structure fight each other.
