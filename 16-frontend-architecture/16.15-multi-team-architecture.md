### Team Topologies (Matthew Skelton & Manuel Pais)
Four fundamental team types:

| Team | Purpose | Example |
|------|---------|---------|
| **Stream-aligned** | Owns a business domain end-to-end | Checkout team |
| **Platform** | Provides self-service platforms | Frontend platform team |
| **Enabling** | Helps other teams adopt new practices | DX team, testing coaches |
| **Complicated-subsystem** | Owns deeply specialized components | Search team, ML team |

Three interaction modes:
- **Collaboration** - two teams work closely for a period.
- **X-as-a-Service** - one team provides, another consumes (e.g., design system).
- **Facilitating** - one team helps another learn.

### Architecture Decision Records (ADRs)
An ADR is a short markdown file documenting a significant decision.

```markdown
# ADR-0012: Use TanStack Query for Server State

## Status
Accepted

## Context
We fetch server data via useEffect + useState in 40+ components. No caching, no deduplication.

## Decision
Adopt TanStack Query for all server state. Keep Zustand for client state.

## Consequences
- + Caching, deduplication, background refetch
- - New dependency, learning curve
- - Existing useEffect fetches need migration
```

**Why ADRs matter:** In 2 years, when someone asks "why TanStack Query?", the answer is in the repo.

### Real-World Deal-Breakers
- **No platform team** → every team reinvents the design system, CI, deployment.
- **Platform team as gatekeepers** → slow, blocks stream teams.
- **No ADRs** → decisions are forgotten; the same debate happens every 6 months.
- **No RFC process** → big changes happen without cross-team visibility.
