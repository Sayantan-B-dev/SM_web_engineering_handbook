### Integration Approaches

| Approach | When | Pros | Cons |
|----------|------|------|------|
| **Build-time** | Packages published as npm | Simple, type-safe | Full rebuild to update |
| **Run-time (Module Federation)** | Independent deploys | True independence | Complex setup |
| **iframes** | Strong isolation needed | Perfect isolation | Poor UX, no shared state |
| **Web Components** | Framework-agnostic | Framework-agnostic | Limited ecosystem |
| **Edge-side composition** | CDN-driven | Fast, cached | Requires edge infra |

### Module Federation Example
```javascript
// host/webpack.config.js
new ModuleFederationPlugin({
  name: 'host',
  remotes: {
    checkout: 'checkout@https://checkout.example.com/remoteEntry.js',
    profile: 'profile@https://profile.example.com/remoteEntry.js',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^19.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^19.0.0' },
  },
});
```

```jsx
// host app
const Checkout = React.lazy(() => import('checkout/Cart'));
<React.Suspense fallback={<Spinner />}>
  <Checkout />
</React.Suspense>
```

### When Micro-Frontends Make Sense
✅ **Multiple teams** that need to deploy independently.
✅ **Heterogeneous stacks** (one team on React, one on Vue - legacy acquired product).
✅ **Very large app** where a single deploy is too slow.

❌ **Small team** (1-5 devs) → overhead dominates.
❌ **Homogeneous stack** → no benefit over a modular monolith.
❌ **Tight coupling between features** → constant cross-team coordination.

### Real-World Deal-Breakers
- **Micro-frontends as a first choice** → 10× complexity for a 3-person team.
- **No shared design system** → each micro-frontend looks different. Poor UX.
- **Multiple React versions** → "Invalid hook call" errors. Enforce singleton shared deps.
- **No shared routing strategy** → URL collisions, broken back button.
- **No observability** → distributed failures are impossible to debug.
