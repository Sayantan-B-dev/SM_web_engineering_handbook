### Distribution Options

| Approach | Pros | Cons |
|----------|------|------|
| **npm package** | Clean versioning, works across repos | Publish cycle slows iteration |
| **Monorepo package** | Instant iteration, atomic changes | Requires monorepo tooling |
| **Git submodule** | Simple | Painful to update, easy to forget |
| **Copy-paste (shadcn/ui)** | Full ownership, no dependency | No updates, code duplication |

### shadcn/ui Model
shadcn/ui isn't a component library - it's a **collection of copy-paste components**. You install the code into your repo and own it. This flips the traditional model: no npm dependency, no versioning pain, full customization. The trade-off is you don't get updates automatically.

### Styling Approaches

| Approach | Runtime cost | DX | Theming |
|----------|-------------|-----|---------|
| CSS Modules | Zero | Good | CSS variables |
| Tailwind | Zero | Excellent | Config + CSS variables |
| CSS-in-JS (styled-components) | Runtime | Excellent | ThemeProvider |
| Zero-runtime CSS-in-JS (Vanilla Extract, Linaria) | Zero | Good | CSS variables |

### Real-World Deal-Breakers
- **No peer dependency on React** → two React copies in the app → hooks break ("Invalid hook call").
- **No tree-shaking** → importing one Button pulls the entire library.
- **Breaking changes without major version bump** → downstream apps break silently.
- **No accessibility baseline** → every consumer fixes the same a11y bugs.
- **No Storybook or visual tests** → components break without anyone noticing.
