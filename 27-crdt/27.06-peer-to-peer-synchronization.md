### P2P CRDT Architecture
RDX fully supports local-first, offline-first and peer-to-peer replication, **with no central server required**, as any two replicas can merge their data. The default syncing protocol generally relies on **version vectors** for efficient delta exchange.

```text
Peer A ◄──── WebRTC data channel ────► Peer B
   │                                        │
   │  Yjs / Automerge / Loro updates       │
   │  (delta-state, encrypted)             │
   │                                        │
   ▼                                        ▼
Local state                            Local state
```

### WebRTC for Transport
A CRDT-based peer-to-peer collaboration editor can be built using Yjs and peer-to-peer communication over WebRTC. The WebRTC layer establishes secure data channels across distributed clients.

### RDX (Replicated Data Interchange)
RDX is like Protobuf, but for CRDTs. It supports local-first, offline-first, and peer-to-peer replication, with no central server required. By installing RDX data types as merge operators in an LSM database (LevelDB, RocksDB, Pebble, Cassandra), one can effectively have a CRDT database.

### Security: End-to-End Encryption
CRDTs are suitable for deployment on mobile devices with poor network connectivity, in peer-to-peer networks, and in messaging systems with **end-to-end encryption**. The CRDT layer is agnostic to encryption - the transport layer handles it.

### Group Membership and View Changes
To achieve reliability beyond point-to-point or small groups, a **group membership mechanism** is necessary to properly handle view changes. Tools like Spread can provide reliable causal ordering and possibly overcome the need for vector clocks.

### Deeper Explanation: Peer-to-peer Needs Discovery, Then Anti-Entropy

P2P CRDT sync has two independent problems: **finding peers** and **exchanging state with them**. Discovery options range from a websocket room (technically still a server, but only for presence and signalling), to WebRTC data channels (browser-to-browser), to local network discovery. Once connected, the sync protocol is the same in all cases:

1. **Exchange heads/version summaries** â€” small digests of what each side has.
2. **Compute the missing deltas** â€” send only what the peer lacks.
3. **Apply, then re-acknowledge** â€” with anti-entropy for anything the peer missed while offline.
4. **Keep a durable local log** â€” so a peer that reappears later can still catch up.

Because CRDT merges are commutative and idempotent, this protocol does not need global ordering, which is exactly why local-first apps can sync over ad-hoc networks. What it does need is authentication (who may sync this document) and encryption (the relay should not read content).

### Additional Pitfalls
- **Assuming a peer will stay connected.** Sync must be incremental and resumable; treat each session as short-lived.
- **Broadcasting full state on every connect.** It works for small documents and destroys large ones; exchange heads first.
- **No authorisation on the relay.** A signalling server that will connect anyone to any document id is an access-control hole.
- **Ignoring NAT reality.** WebRTC P2P still needs TURN for a meaningful share of pairs; budget for relay bandwidth.
- **No encryption.** The relay operator (and anyone on the path) can read content unless you encrypt per document.

### Real-World Deal-Breakers
- **No group membership mechanism** → P2P CRDTs work for 2-3 peers but break down at larger scales. You need a way to handle peers joining and leaving.
- **No encryption** → P2P data is visible to any peer on the network. Use end-to-end encryption.
- **No version vectors for sync** → full-state comparison over the network is prohibitively slow.
- **Non-commutative operations in P2P** → without a central server to order operations, non-commutative operations (like 3D rotations) diverge. Use canonical ordering or specialized handling.
