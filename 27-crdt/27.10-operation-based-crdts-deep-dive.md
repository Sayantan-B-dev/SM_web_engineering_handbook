## 27.4 Operation-Based CRDTs (CmRDT) - Deep Dive

### Subtopic Tree
- Operations must be commutative
- Reliable messaging layer required
- Causal delivery requirement
- Exactly-once delivery for non-idempotent operations

### The Commutativity Requirement
In operation-based CRDTs, the operations used to modify the state must be **commutative** with regard to a different operation issued at the same time (concurrently). The replicas broadcast the operations and not the states. If two operations happen at the same time in two replicas, the order in which other replicas apply them does not matter: the resulting states will be the same.

### Op-Based Counter
```typescript
class OpCounter {
  private value: number = 0;

  increment(): number {
    this.value++;
    return +1; // operation: delta
  }

  decrement(): number {
    this.value--;
    return -1; // operation: delta
  }

  apply(op: number): void {
    this.value += op;
  }
}
```

**Why it works:** Addition is commutative and associative. `+1` and `-1` in any order produce the same result.

### Op-Based Text (Insert/Delete)
For text, operations are `insert(position, character)` and `delete(position)`. The challenge is that positions shift as other operations are applied. This is where CRDTs differ from OT: instead of transforming positions, CRDTs use **stable position identifiers** that do not change when other characters are inserted or deleted.

```typescript
// Simplified RGA (Replicated Growable Array) approach
// Each character has a unique ID that never changes
type Char = {
  id: string;          // unique identifier
  value: string;       // the character
  leftOrigin: string | null; // ID of the character to its left
};

class RGAText {
  private chars: Char[] = [];

  insert(char: Char): Char {
    // Find the position after leftOrigin
    const index = this.findIndexAfter(char.leftOrigin);
    this.chars.splice(index, 0, char);
    return char;
  }

  delete(id: string): void {
    this.chars = this.chars.filter((c) => c.id !== id);
  }

  apply(operation: { type: 'insert' | 'delete'; char?: Char; id?: string }): void {
    if (operation.type === 'insert') this.insert(operation.char!);
    else this.delete(operation.id!);
  }
}
```

**Why it works:** Each character's position is determined by its `leftOrigin` (the character it was inserted after), not by a numeric index. Concurrent inserts at the same position are ordered by their unique IDs, which are globally consistent.

### The Reliability Requirement
Unlike state-based CRDTs, eventual consistency in operation-based CRDTs requires a **reliable messaging layer** that eventually delivers all operations. If an operation is lost, the replica will never be able to apply it and the states will not converge.

Additional constraints may be necessary:
- **Exactly-once delivery** if operations are not idempotent (e.g., a counter increment).
- **Causal delivery** if operations depend on each other: if replica sends operation `a` before `b`, then `a` should always be delivered before `b` to other replicas.

---

### Deeper Explanation: Delivery Guarantees Are The Hidden Dependency

Op-based CRDTs assume **reliable causal broadcast**: operations must not be lost, and they must be applied only when their causal predecessors have been applied. That is the part implementers underestimate. In a browser setting you rarely have exactly-once delivery, so real systems pick one of three accommodations:

1. **Queue and dedupe** â€” keep an ordered outbox with operation ids, retry until acked, and have receivers ignore duplicates.
2. **Causal readiness** â€” tag operations with a dotted version vector and buffer those whose dependencies have not arrived (this is how Yjs-style updates stay safe over lossy links).
3. **Delta/interleaved fallback** â€” send state deltas for anything that might have been dropped.

The payoff is compact operations: 100 characters typed produces 100 tiny inserts rather than a copy of the document, and the merge logic is a simple apply-if-ready.

### Additional Pitfalls
- **Assuming causal delivery from a websocket.** A reconnect loses in-flight messages; the queue and dedupe are mandatory.
- **Applying unprepared operations.** Without dependency checks, replicas diverge permanently and silently.
- **Unbounded duplicate-detection memory.** Track operation ids with a compact structure and prune acknowledged ranges.
- **No operation versioning.** A deploy that changes operation payloads breaks every open client; version the protocol and keep the old applier.

### Real-World Deal-Breakers
- **No reliable messaging layer** → lost operations cause permanent divergence.
- **No causal delivery** → operations applied out of causal order produce incorrect results.
- **Non-commutative operations** → rotating an object in 3D is non-commutative. Applying rotations in different orders produces different orientations. Use canonical ordering (LWW) or specialized handling (averaging).
- **No exactly-once delivery for counters** → a duplicated increment produces the wrong count.
