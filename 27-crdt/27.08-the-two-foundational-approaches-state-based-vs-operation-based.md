## 27.1 The Two Foundational Approaches: State-Based vs Operation-Based

### Subtopic Tree
- State-based (CvRDT): broadcast full state, merge with join
- Operation-based (CmRDT): broadcast operations, apply commutatively
- Delta-state: broadcast only the delta (changed part)
- Pure operation-based: no state, only operations
- Message size, network overhead, and reliability requirements
- Causal delivery requirements
- The transformation between approaches

### State-Based CRDTs (Convergent Replicated Data Types)
In state-based CRDTs, replicas modify their state - or **inflate** it - and broadcast the resulting state to other replicas. Upon receiving the state, other replicas merge it with their local state using the join operation (⊔). The properties of the semilattice ensure eventual convergence.

```text
Replica A state: {1, 2, 3}       Replica B state: {3, 4, 5}
                    │                            │
                    └──────── merge ─────────────┘
                                 │
                                 ▼
                         {1, 2, 3, 4, 5}
                    (join = set union for a G-Set)
```

**Advantages:** Simple. No reliable messaging layer required. Idempotent - duplicates are harmless. Works with any network (even lossy).

**Disadvantages:** The entire state must be transmitted. For large states (e.g., a text document with 100,000 characters), this is expensive.

### Operation-Based CRDTs (Commutative Replicated Data Types)
In operation-based CRDTs, replicas broadcast **operations**, not states. If two operations happen at the same time on two replicas, the order in which other replicas apply them does not matter: the resulting states will be the same.

```text
Replica A: insert(0, "Hello")    Replica B: insert(0, "World")
                    │                            │
                    └────── broadcast ops ───────┘
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
             apply both ops              apply both ops
             (order doesn't              (order doesn't
              matter)                     matter)
                    │                         │
                    ▼                         ▼
              "WorldHello"              "WorldHello"
```

**Advantages:** Small messages (only the operation, not the full state). Frequently have smaller states, independent of the number of replicas.

**Disadvantages:** Requires a **reliable messaging layer** that eventually delivers all operations. If an operation is lost, replicas will never converge. Some operations require **causal delivery**: if replica sends operation `a` before `b`, then `a` should always be delivered before `b` to other replicas.

### Delta-State CRDTs - The Best of Both Worlds
Delta-state CRDTs aim to achieve, in a way, "the best of both worlds". Instead of broadcasting the full state or individual operations, they broadcast **deltas** - the minimal change to the state. This combines the small message size of operation-based CRDTs with the reliability and simplicity of state-based CRDTs.

```text
State-based:   send {1, 2, 3, 4, 5} (full state)
Op-based:      send "add(4)" + "add(5)" (operations)
Delta-state:   send {4, 5} (delta - only the changed part)
```

### Pure Operation-Based CRDTs
Pure operation-based CRDTs are a relevant point in the design space where no state is stored at the replica - only the operations themselves. This is useful for append-only logs and event-sourced systems.

### The Transformation Between Approaches
It is possible to transform a state-based CRDT into an operation-based CRDT and vice versa. The two approaches define two transformations: one that constructs an op-based CRDT given a state-based CRDT, and one that constructs a state-based CRDT given an op-based CRDT. This means the choice is about **engineering trade-offs**, not fundamental capability.

### Deeper Explanation: What Crosses The Wire Decides The Failure Modes

The split between state-based (CvRDT) and operation-based (CmRDT) CRDTs is really about what you replicate:

| | State-based (CvRDT) | Op-based (CmRDT) |
|---|---|---|
| Sends | The whole (join-semilattice) state | The operation and its causal context |
| Merge | `join(state, remoteState)` â€” LUB | Apply op if causally ready |
| Network needs | Any, including unreliable/lossy, no ordering | Reliable causal broadcast (exactly once) |
| Metadata | Grows with state (e.g. version vectors per element) | Grows with pending ops |
| Typical size | Large messages | Small messages, but must not be lost |

Modern implementations blur the line deliberately: **delta-state** CRDTs send only the changed part of the state (small messages, still robust to loss and reordering), and **pure op-based** designs compress the causal context (for example with dotted version vectors) so the metadata stays manageable.

### Additional Pitfalls
- **Op-based CRDT over a lossy transport.** Dropped updates never converge; if delivery is not reliable, send state or deltas.
- **State-based with a huge state per message.** Bandwidth and parse cost explode; use deltas.
- **Mixing models per field without a rule.** The composition must still be a join-semilattice or causally delivered.
- **Forgetting the causal context.** Applying an op whose dependency is missing produces a divergent replica.

### Real-World Deal-Breakers
- **Choosing operation-based without reliable delivery** → if any operation is lost, replicas never converge. Use delta-state CRDTs or a reliable messaging layer.
- **Choosing state-based for large documents** → transmitting the full state on every change is prohibitively expensive. Use delta-state or operation-based.
- **Assuming causal delivery is free** → operation-based CRDTs require causal delivery, which adds latency and complexity. State-based CRDTs do not.
- **Forgetting that CRDTs are just data types** → the transmission policy is independent. Some CRDTs are better suited to some broadcasting mechanisms than others.
