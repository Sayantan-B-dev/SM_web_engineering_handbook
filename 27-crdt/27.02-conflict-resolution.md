### The Three Conflict Shapes
Almost every merge bug is one of three patterns, and each needs a different answer:

1. **Lost update** â€” two writers read the same base and each writes a full record; whoever writes last erases the other's change. Fix: send *diffs*, not full records, or merge at field level.
2. **Ordering** â€” operations arrive out of order (update before create, move before insert). Fix: causal metadata (vector clocks) and a queue that defers operations whose dependencies have not arrived.
3. **Delete vs edit** â€” one replica deletes while another edits. Fix: tombstones with a deterministic rule (delete wins, or delete is a flag that edit can clear, or the delete is deferred for user confirmation).

### Detecting Concurrency, Not Just "Who Was Later"
Wall-clock timestamps are the wrong tool: devices drift, clock changes are user-triggered, and timezones confuse comparisons. Version-based detection is deterministic:

```ts
// Version vectors: one counter per replica. Concurrent = neither dominates.
export type VersionVector = Record<string, number>;

export function compare(a: VersionVector, b: VersionVector): 'a-dominates' | 'b-dominates' | 'concurrent' | 'equal' {
  let aGreater = false;
  let bGreater = false;
  for (const key of new Set([...Object.keys(a), ...Object.keys(b)])) {
    const av = a[key] ?? 0;
    const bv = b[key] ?? 0;
    if (av > bv) aGreater = true;
    if (bv > av) bGreater = true;
  }
  if (aGreater && bGreater) return 'concurrent';
  if (aGreater) return 'a-dominates';
  if (bGreater) return 'b-dominates';
  return 'equal';
}
```

```ts
// Deterministic tiebreak for genuinely concurrent writes: id breaks the tie identically everywhere
function pickLatest<W extends { clock: number; replica: string }>(a: W, b: W): W {
  if (a.clock !== b.clock) return a.clock > b.clock ? a : b;
  return a.replica > b.replica ? a : b;   // same decision on every device, in any order
}
```

### User-Visible Resolution
For text and structured documents, convergent data structures resolve silently. For records where intent matters (an order being cancelled while being edited, two different shipping addresses), resolve in the open:

```tsx
function ConflictDialog({ mine, theirs, onKeep }: { mine: Version; theirs: Version; onKeep: (v: Version) => void }) {
  return (
    <dialog open>
      <h2>This item changed on another device</h2>
      <section>{/* field-by-field diff of mine vs theirs */}</section>
      <button onClick={() => onKeep(mine)}>Keep mine</button>
      <button onClick={() => onKeep(theirs)}>Keep theirs</button>
    </dialog>
  );
}
```

### Real-World Deal-Breakers
- **Last-write-wins on whole records.** Field-level merges are what stop unrelated edits from eating each other.
- **Client timestamps as the merge key.** Skew makes outcomes random; use logical clocks plus an id tiebreak.
- **No tombstones.** A delayed update resurrects deleted rows and users see ghosts.
- **Non-deterministic merge functions.** The same pair of versions must produce the same result on every device.
- **Silent conflicts on expensive data.** Anything the user typed at length needs an explicit resolution UI.
- **Assuming at-most-once delivery.** Real networks duplicate; make every operation idempotent by operation id.
