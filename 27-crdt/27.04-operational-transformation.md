### The Mental Model
OT keeps a **single canonical document plus a log of intent-carrying operations**. When two operations are concurrent, they are transformed against each other so that applying them in different orders converges to the same document:

```ts
type Op = { type: 'insert'; pos: number; text: string } | { type: 'delete'; pos: number; len: number };

// A arrives at the server first; transform B against A before broadcasting.
function transform(b: Op, a: Op): Op {
  if (a.type === 'insert') {
    return b.pos >= a.pos ? { ...b, pos: b.pos + a.text.length } : b;
  }
  // A deleted a range: shift or clamp B
  const end = a.pos + a.len;
  if (b.pos <= a.pos) return b;                                    // before the deletion
  if (b.pos >= end) return { ...b, pos: b.pos - a.len };           // after it
  return { ...b, pos: a.pos, len: Math.max(1, b.len - (end - b.pos)) }; // overlapping
}
```

The server assigns each operation a revision, transforms incoming operations against the ones already applied, and sends the transformed operation back to the originating client (or lets the client rebase locally). That is why OT needs a **central authority** in practice: transformation matrices must be applied in a consistent order, and distributed OT is genuinely hard to get right.

### OT vs CRDT In One Table

| Aspect | OT | CRDT |
|---|---|---|
| Topology | Central server orders operations | Any topology; peers merge |
| Server role | Transformation engine | Storage/relay |
| Complexity | Many edge cases (TP1/TP2), hard to prove | Provable convergence, heavier metadata |
| Offline | Poor (needs the server's order) | Excellent (local-first) |
| Maturity of libraries in JS | Few maintained | Many (Yjs, Automerge, Loro) |

### Real-World Deal-Breakers
- **Implementing OT from scratch.** The transformation matrix has subtle edge cases; a dozen implementations exist because the first eleven were wrong.
- **Client-side transformation with no canonical order.** Without a server arbiter you reinvent CRDTs, badly.
- **Not handling delete-inside-insert.** Nodes vanish or duplicate on convergence; every operation pairing needs a defined transform.
- **Using OT for offline-first.** Reconnection rebasing is where OT implementations break.
- **Ignoring operation history size.** OT logs need periodic snapshots and compaction exactly like CRDT updates.
- **Choosing OT for a new product in 2026.** Unless you already run an OT stack, a CRDT library gets you convergence with less risk.
