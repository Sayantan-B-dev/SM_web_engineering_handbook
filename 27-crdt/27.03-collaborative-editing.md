### YATA Algorithm (Yjs)
YATA (Yet Another Transformation Approach) is the sequence CRDT used by Yjs. It's faster than Automerge for text operations. The key insight is that each character has a **left origin** and a **right origin**, and concurrent inserts between the same pair are ordered by their unique IDs.

### Automerge's JSON CRDT
Automerge implements a **JSON-like CRDT** based on the paper "A Conflict-Free Replicated JSON Datatype" (Kleppmann et al., 2017). It supports maps, arrays, text, and counters - all mergeable.

### Rich Text CRDTs
Rich text requires tracking formatting (bold, italic, links) in addition to characters. Loro supports rich text with formatting (bold, italic, links) and movable trees (reorderable nested structures).

### Cursor/Presence Synchronization
Yjs provides **awareness/presence tracking** for cursors and selections. This is separate from the document state - presence is ephemeral and does not need to be persisted or merged.

### Undo/Redo in CRDTs
Undo/redo is non-trivial in CRDTs because operations from different users are interleaved. A user's "undo" should undo only their own operations, not another user's. This requires tracking the causal context of each user's operations.

### The Interleaving Problem
Most existing algorithms for replicated lists suffer from **interleaving**: concurrent inserts can be interleaved in a way that produces nonsensical results.

```text
User A types: "Hello"
User B types: "World"

Interleaved result: "HWeolrllod"  ← wrong!
Desired result:     "HelloWorld"  ← correct
```

Fugue and FugueMax are CRDT algorithms that address this. FugueMax satisfies **maximal non-interleaving**.

### Eg-walker (2025 Hybrid)
Eg-walker is a hybrid CRDT/OT algorithm that merges concurrent edits with optimal efficiency and reduced memory usage. It merges documents in milliseconds, requires significantly less memory than standard CRDTs, and operates effectively in peer-to-peer environments.

### AegisSheet (2026 Spreadsheet CRDT)
AegisSheet is a compositional CRDT for collaborative spreadsheets, derived from first principles. Spreadsheets have unique challenges: formulas that reference other cells, circular dependencies, and recalculation ordering.

### Semantic Conflict Model (2026)
A new conflict model for collaborative data structures enables **explicit, local-first conflict resolution without central coordination**. Instead of CRDTs silently resolving conflicts, this model surfaces them to the user for explicit resolution.

### Deeper Explanation: A Collaborative Editor Is Four Layers Plus Presence

The visible feature (two cursors, live text) rests on a stack:

1. **Document model** â€” a CRDT (Yjs/Automerge/Loro) holding text and structure; the source of truth on each client.
2. **Local persistence** â€” updates appended to IndexedDB so a reload or a crash does not lose work.
3. **Sync transport** â€” websocket/WebRTC provider exchanging binary deltas, with resync on reconnect (and awareness of the version summary exchange).
4. **Editor binding** â€” an editor (ProseMirror/Tiptap, CodeMirror, Slate) bound to the CRDT, translating local edits into CRDT operations and remote operations into decorations/transactions.
5. **Presence/awareness** â€” ephemeral, non-persisted state (cursor, selection, name, colour) on a separate short-TTL channel.

The layering matters because each has a different consistency requirement: document content must converge, presence may be lossy, and permissions must be authoritative on the server.

### Additional Pitfalls
- **Binding the CRDT to the editor on every render.** Editors need one binding per document instance; re-binding loses selection and history.
- **Mixing document and awareness channels.** Cursor storms drown edits and bloat the log; awareness must never persist.
- **No undo semantics.** Collaborative undo must undo *your* last change, not the document's; use the CRDT library's undo manager.
- **Server-side validation absent.** Convergent text still needs authorisation, rate limiting, and payload limits on the relay.
- **Testing only two connected clients.** Verify one offline, one editing, then reconnecting, with a merge and a delete in between.
- **Ignoring mobile performance.** Large documents plus rich bindings can drop frames; lazy-load and virtualise.

### Real-World Deal-Breakers
- **No interleaving prevention** → concurrent text inserts produce garbled output. Use Fugue/FugueMax or Yjs.
- **No undo/redo scoping** → undoing another user's changes. Track per-user operation history.
- **No spreadsheet CRDT** → collaborative spreadsheets need formula-aware merging, not just cell-value merging.
- **No semantic conflict surfacing** → CRDTs silently resolve conflicts, but the result may be semantically wrong. Consider surfacing conflicts to the user.
