## 27.7 CRDT Libraries and Ecosystem (2026)

### Subtopic Tree
- Yjs (YATA algorithm, most widely used)
- Automerge (JSON-like, Rust core)
- Loro (rich text, movable trees)
- pycrdt (Python bindings for Yrs)
- Collabs (TypeScript framework)
- Ron (Replicated Object Notation)
- Diamond Types (plain text)
- json-joy (JSON CRDT)
- CRDT-enabled databases (AntidoteDB, Riak)

### Yjs - The Most Widely Used
Yjs is the most widely used CRDT library, optimized for collaborative text editing using the **YATA algorithm**. Written in JavaScript/TypeScript with a modular architecture.

**Key features:**
- YATA sequence CRDT (faster than Automerge for text operations)
- Delta-state sync with state vectors
- Awareness/presence tracking (cursors, selections)
- Bindings for CodeMirror, Monaco, Quill, ProseMirror
- Encoded binary updates (compact network messages)

```javascript
import * as Y from 'yjs';

const doc = new Y.Doc();
const text = doc.getText('shared');
text.insert(0, 'Hello');
text.insert(5, ' World');

// Sync: emit updates on local changes
doc.on('update', (update) => sendToPeers(update));

// Apply remote updates
function onRemoteUpdate(update) {
  Y.applyUpdate(doc, update);
}
```

**Used by:** JupyterLab, Nimbus Note, Serenity Notes, PeerPad, Room.sh.

### Automerge - JSON-Like CRDT
Automerge implements a **JSON-like CRDT data model**. Originally JavaScript, rewritten in Rust with WebAssembly bindings for performance. Uses columnar encoding for efficient storage.

**Key features:**
- JSON-compatible data model (maps, arrays, text, counters)
- Conflict-free merging of concurrent edits
- Change history (can replay, fork, or inspect document history)
- `automerge-repo` layer handles networking and persistence separately
- Rust core with JS/Python bindings

```javascript
import { change, merge } from 'automerge';

let doc = change(automerge.init(), (doc) => {
  doc.title = 'Hello';
  doc.tags = ['crdt', 'collaboration'];
});

// Merge concurrent edits
let merged = merge(doc1, doc2);
```

**Used by:** PushPin, PixelPusher, Trellis, Capstone, Archbee.

### Loro - Rich Text and Movable Trees
Loro is a newer CRDT library based on **Replayable Event Graph**, supporting rich text, lists, maps, and **movable trees**. Implemented in Rust with JavaScript bindings.

**Key features:**
- Rich text with formatting (bold, italic, links)
- **Movable tree** (reorderable nested structures) - critical for Notion-like editors
- Delta-state sync
- Designed for document collaboration

### Deeper Explanation: Choose By Data Type And Transport, Not By Star Count

The library you adopt is a decision about four things: which data types it implements, how it transports updates, whether it persists and compacts efficiently, and how it handles encryption/permissions (or delegates them). The 2026 landscape breaks down roughly as:

| Library | Strength | Fits |
|---|---|---|
| **Yjs** | Battle-tested shared types (text, arrays, maps), small updates, huge ecosystem of providers (y-websocket, y-indexeddb, y-webrtc, Liveblocks) | Collaborative editors, rich text, offline-first apps |
| **Automerge** | Rich document model, history as a first-class feature, easy time travel, Rust core with WASM bindings | Local-first apps that value history and simplicity |
| **Loro** | Modern, compact encoding, rich text plus movable lists, fast | New projects wanting performance and richer types |
| **json-joy / JSON CRDT** | JSON Patch-like operations over JSON | Structured documents, JSON-centric sync |
| **SyncedStore** | Reactive wrappers over Yjs for React | Fast prototyping of collaborative state |

Integration rules that survive contact with production: keep the CRT document in a ref/module (never React state), persist updates to IndexedDB, run sync in a worker when documents are large, and treat the CRDT as the source of truth for document content while keeping permissions and money on the server.

### Additional Pitfalls
- **Adopting a library without a persistence story.** Updates must be durably stored (IndexedDB) and snapshotted, or load time grows forever.
- **Storing the CRDT in React state.** Deep proxying defeats memoisation and triggers enormous re-render storms.
- **One document per app.** Documents should match user-perceived units (a file, a board) for load time and permissions.
- **Ignoring encryption.** CRDTs are not secure by themselves; end-to-end encryption needs careful key handling per document.
- **No migration path.** Plan an export format; local-first promises longevity.

### Real-World Deal-Breakers
- **Choosing Yjs for JSON-heavy apps** → Yjs is optimized for text. Automerge is better for JSON-shaped data.
- **Choosing Automerge for text-heavy apps** → Yjs has up to a 3× speed advantage for text operations.
- **No conflict resolution strategy** → all these libraries provide CRDT merging, but you still need to decide what the merged result means for your UX.
- **Ignoring memory** → Automerge 2.0's Rust rewrite cut memory from 1.1 GB to ~44.5 MB on the same trace. Library choice has massive performance implications.
