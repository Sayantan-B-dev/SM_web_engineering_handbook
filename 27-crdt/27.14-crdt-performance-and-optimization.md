### The Metadata Overhead Problem
CRDTs carry significantly more metadata than plain data structures. A CRDT text document tracks:
- Unique IDs for every character
- Tombstones for deleted characters
- Causal context (version vectors, vector clocks)
- Formatting metadata

A 10KB plain text document can become a 100KB+ CRDT document. This is the **fundamental cost** of conflict-free merging.

### Snapshot Compaction (Garbage Collection)
To bound the size, CRDTs periodically create **full snapshots** of the current state and garbage-collect tombstones and old operations.

```text
1. Create full snapshot of current CRDT state
2. Ensure all clients have acknowledged the snapshot
3. Garbage-collect tombstones that are no longer needed
4. Prune operation log up to snapshot point
```

### Tombstone TTL
A deleted key is protected by a tombstone for the **tombstone TTL**. If all nodes holding the tombstone expire, a node that was offline can bring the key back when it returns. This is a trade-off between storage and correctness.

### Causal Materialization Planning
MindooDB uses **causal materialization planning** to determine the minimal set of entries needed to reconstruct each document, using the dependency graph rather than timestamps. This speeds up database opens and keeps sync throughput high.

### Merkle-CRDTs
Merkle-CRDTs combine Merkle-DAGs with CRDTs to enable efficient synchronization. Instead of comparing full states, replicas compare Merkle roots and exchange only the differing subtrees. This makes sync **O(log n)** instead of **O(n)**.

### Performance Benchmarks (crdt_lf 3.1.0)
The Dart `crdt_lf` package 3.1.0 release shows dramatic performance improvements:
- OR-Set handler benchmark: **180ms → 27ms** for 1000 operations on a fresh document
- `ChangeStore.exportChangesNewerThan`: **~500× faster** on a 50k-change store
- `DAG.getLCA`: filters through children sets instead of re-running full ancestor walks

### Deeper Explanation: The Four Cost Centres

CRDT performance is not one number; it is four, and each has a different fix:

1. **Update size** â€” per-character ids and tombstones inflate small edits. Fix: delta updates, compact encodings (`Uint8Array` binary, not JSON), and library features such as run-length encoding of sequential inserts.
2. **Memory footprint** â€” the in-memory document plus history can be 10-100Ã- the visible text. Fix: snapshots with history pruning, loading documents lazily, and keeping documents small in scope.
3. **Sync cost** â€” encoding, encryption, and network per update. Fix: batch updates per frame (or per ~100 ms), compress, and use binary encoding.
4. **Rendering cost** â€” the real bottleneck in most React apps. Fix: subscribe to fine-grained changes and render only affected ranges; never re-render a whole document per keystroke.

Measure with realistic documents (not a hello-world scratchpad), realistic concurrency (two authors, one offline), and realistic hardware (a mid-tier laptop, not CI).

### Additional Pitfalls
- **JSON-encoding CRDT updates.** Binary encodings are several times smaller and much faster to parse.
- **Rendering on every update.** Debounce or batch and use fine-grained subscriptions; the CRDT is rarely the bottleneck, React is.
- **Treating undo as free.** Undo in a CRDT is itself an operation with intent semantics; use the library's undo manager.
- **Ignoring GC/compaction.** Documents that grow for months eventually take seconds to open.
- **Benchmarking without concurrency.** Single-author benchmarks miss the metadata path entirely.

### Real-World Deal-Breakers
- **No snapshot compaction** → the CRDT document grows indefinitely. Tombstones and old operations accumulate.
- **No tombstone TTL** → deleted keys can be resurrected by offline nodes.
- **No Merkle-DAG for sync** → full-state comparison for large documents is O(n). Use Merkle-CRDTs for O(log n).
- **Ignoring memory** → CRDTs can consume 10-100× the memory of plain data. Profile and optimize.
