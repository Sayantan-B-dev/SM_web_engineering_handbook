## 27.11 CRDT Limitations and Challenges

### Subtopic Tree
- Metadata overhead
- Memory consumption
- Garbage collection complexity

### Metadata Overhead
CRDTs carry significantly more metadata than plain data structures. A CRDT text document tracks unique IDs, tombstones, causal context, and formatting metadata. A 10KB plain text document can become a 100KB+ CRDT document.

### Memory Consumption
Automerge 2.0's Rust rewrite cut memory from **1.1 GB to ~44.5 MB** on the same trace. This shows the massive memory implications of CRDT design decisions.

### Garbage Collection Complexity
Tombstones (records of deletions) cannot be immediately removed because offline replicas may need them to correctly merge. You need a garbage collection strategy that balances correctness against storage.

### Causal Delivery Requirements (Op-Based)
Operation-based CRDTs require reliable causal delivery. In practice, reliable channels are hard to come by and can be a source of extra latency. Vector clocks add overhead.

### Non-Commutative Operations
Rotating a 3D object is non-commutative: the order of rotations affects the final orientation. Within operation-based CRDTs, this issue can be tackled using canonical ordering (LWW) or specialized handling (averaging), but these approaches are **inherently limited**.

### GUI Coupling Bottlenecks
In a real-time co-editing system for high-vertex-count geometries, key performance bottlenecks were identified in the **GUI coupling and CRDT integration mechanisms**. While the core CRDT mechanisms remained performant, GUI limitations emerged as the primary constraint at higher vertex counts.

### Lack of Extensibility
The lack of extensibility of CRDTs limits their applicability. This is a particularly important problem in settings relying on complex, non-linear data types.

### CRDTs Are Difficult to Design
CRDTs are **difficult to design, prone to subtle bugs**, but allow the majority of distributed application programmers to use them from a library with little effort, while only a minority of expert CRDT designers need to go through the intricate process of creating new CRDTs.

### Real-World Implementations Still Require Centralized Services
Despite the theoretical promise, many real-world implementations of CRDTs still require **centralized services** to merge and synchronize changes. Examples include popular databases such as Riak.

### Real-World Deal-Breakers
- **No garbage collection strategy** → tombstones accumulate indefinitely, consuming storage and memory.
- **No causal delivery for op-based CRDTs** → replicas diverge permanently.
- **Non-commutative operations without a strategy** → divergent outcomes. Use canonical ordering or specialized handling.
- **GUI coupling bottleneck** → the CRDT is fast, but the UI rendering is the bottleneck. Profile the entire stack.
- **Assuming CRDTs eliminate centralization** → most production CRDT systems still use a central sync server.
