### What Delta-State CRDTs Are
Delta-state CRDTs aim to achieve "the best of both worlds" between state-based and operation-based CRDTs. Instead of broadcasting the full state (state-based) or individual operations (operation-based), they broadcast **deltas** - the minimal change to the state.

```text
State-based:   send {1, 2, 3, 4, 5} (full state, 5 elements)
Op-based:      send "add(4)" + "add(5)" (2 operations)
Delta-state:   send {4, 5} (delta, 2 elements)
```

### The Delta-Mutator
A delta-mutator is a function that takes a state and returns both the new state and a delta that, when merged with the old state, produces the new state.

```typescript
type DeltaMutator<S, D> = (state: S, ...args: any[]) => [S, D];

// For a G-Set
const addElement = <T>(state: Set<T>, element: T): [Set<T>, Set<T>] => {
  const newState = new Set([...state, element]);
  const delta = new Set([element]);
  return [newState, delta];
};
```

### Delta-State Sync Protocol
1. Replica A makes a local change. It computes the delta.
2. A broadcasts the delta to its neighbors.
3. Each neighbor merges the delta into its local state and forwards it to its neighbors.
4. The delta is idempotent, commutative, and associative, so the order of merging does not matter.

### Bandwidth Efficiency
ConflictSync (2026) proposes a digest-driven synchronization algorithm that reduces total data transfer by **up to 18× compared to full-state transmissions**. This is critical for large CRDT documents.

### Deeper Explanation: The Best Of Both, At A Metadata Price

Delta-state CRDTs send **only the changed part** of the state, and keep the merge operation from state-based CRDTs. The guarantee is that a delta is itself a lattice element, so applying deltas in any order, repeatedly, or partially still converges. That is why delta CRDTs are the practical default in modern libraries: small messages (like op-based) with robustness to loss and reordering (like state-based).

Implementation reality:

- **Deltas are joinable**: `merge(state, deltaA, deltaB) === merge(merge(state, deltaA), deltaB)`.
- **You still need buffering for peers that were away**: keep a bounded delta buffer per peer, or fall back to a full state sync.
- **Composition for text** uses per-character identities with RGA/YATA ordering; the "delta" is the new element with its predecessor reference, so late arrivals can still be ordered correctly.
- **Anti-entropy** (periodic state exchange) complements deltas to repair any lost message.

### Additional Pitfalls
- **Unbounded per-peer delta buffers.** Memory grows with the peer's lag; cap it and trigger a snapshot sync instead.
- **Assuming a delta is always small.** A delete of a large subtree or a full-text replace is a big delta; that is acceptable but should be measured.
- **Skipping anti-entropy.** Deltas alone cannot repair a long-broken link; periodic reconciliation is the safety net.
- **Mixing delta and full-state merges carelessly.** Both must remain lattice joins, or convergence breaks in ways that only appear on unusual orderings.

### Real-World Deal-Breakers
- **No delta computation** → falling back to full-state broadcast wastes bandwidth.
- **No delta compaction** → deltas accumulate indefinitely. Periodically compute a full state and garbage-collect old deltas.
- **No digest for sync** → full-state comparison for large documents is slow. Use Merkle-DAGs or digests for efficient sync.
