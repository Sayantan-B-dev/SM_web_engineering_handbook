## 27.6 Pure Operation-Based CRDTs

### Subtopic Tree

- Use cases: audit logs, blockchain-like systems

### What Pure Operation-Based CRDTs Are
Pure operation-based CRDTs are a relevant point in the design space where no state is stored at the replica - only the operations themselves. The state is derived by replaying the operation log.

```typescript
class PureOpLog {
  private operations: Operation[] = [];

  append(op: Operation): void {
    this.operations.push(op);
  }

  merge(other: PureOpLog): PureOpLog {
    // Merge operation logs (union of operations, deduplicated by ID)
    const merged = new PureOpLog();
    const seen = new Set<string>();
    for (const op of [...this.operations, ...other.operations]) {
      if (!seen.has(op.id)) {
        merged.operations.push(op);
        seen.add(op.id);
      }
    }
    return merged;
  }

  state(): State {
    let state = initialState();
    for (const op of this.operations) {
      state = apply(state, op);
    }
    return state;
  }
}
```

**Advantages:** The operation log is the complete history. You can replay it to any point in time. You can verify it cryptographically. It's naturally append-only.

**Disadvantages:** The log grows indefinitely. You need periodic snapshots to bound the size.

---

### Deeper Explanation: Compressing The Causal Context

The awkward part of op-based CRDTs has always been the causal context: to know whether an operation is ready, you need to know which operations preceded it. Naive solutions carry a version vector per operation, which grows with the number of replicas. Pure op-based CRDTs use compact structures â€” **dotted version vectors**, causal dots, and interval trees â€” so an operation carries a small, bounded amount of causality metadata while still preventing duplication and premature application.

For a frontend team the relevance is practical: this is what lets a browser client hold thousands of pending operations after a long offline period, reconnect, and reconcile without sending megabytes of duplicate metadata.

### Additional Pitfalls
- **Rolling your own dotted-version-vector logic.** The edge cases around gaps and intervals are subtle; use a library.
- **Pruning metadata too eagerly.** Losing causal history too soon lets duplicates apply twice or operations apply prematurely.
- **Not measuring metadata separately.** Bytes of payload plus bytes of context is the real cost; context often dominates.
- **Assuming all peers need the full context.** A single-author replica can often work with a much smaller footprint.

### Real-World Deal-Breakers
- **No snapshot compaction** → the operation log grows forever. Periodically create full snapshots and prune old operations.
- **No cryptographic verification** → any replica can inject fake operations. Use signatures or Merkle-DAGs.
- **Replaying the entire log on every read** → O(n) time for every query. Materialize snapshots.
