## 27.2 CRDT vs OT (Operational Transformation)

### Subtopic Tree
- OT: transform operations against concurrent operations
- CRDT: design data structures so operations commute
- Correctness: TP1/TP2 properties in OT
- Complexity: time and space
- Central server requirement (OT) vs peer-to-peer (CRDT)
- Real-world adoption: OT vs CRDT in production
- The myths and the facts
- Hybrid approaches (Eg-walker)

### What OT Is
OT (Operational Transformation) was invented for supporting real-time co-editors in the late 1980s and has evolved to become the core technique widely used in today's working co-editors and adopted in industrial products. OT works by **transforming operations** against concurrent operations so they can be applied in any order.

```text
User A: insert(0, "Hello")        User B: insert(0, "World")

OT transforms A against B: insert(5, "Hello")  // shift by length of B's insert
OT transforms B against A: insert(0, "World")  // no shift needed

Result: "WorldHello"
```

### What CRDT Is
CRDT (originally "Commutative Replicated Data Type") for co-editors was first proposed around 2006, under the name of WOOT (WithOut Operational Transformation). Follow-up CRDT variations are commonly labeled as "post-OT" techniques capable of making concurrent operations **natively commutative** in co-editors.

### The Reality Check
CRDT solutions have made broad claims of superiority over OT solutions, and often portrayed OT as an incorrect and inefficient technique. Over one decade later, however, **CRDT is rarely found in working co-editors; OT remains the choice for building the vast majority of today's co-editors**. Contradictions between the reality and CRDT's purported advantages have been the source of much confusion and debate.

### The Hidden Complexity of CRDTs
A comprehensive critical review revealed facts and evidence that **refute CRDT claims over OT on all accounts**. Representative CRDT solutions have **hidden complexity and algorithmic flaws**. Common myths about CRDT superiority are not supported by working systems.

### CRDT vs OT Comparison Table

| Feature | CRDT | OT |
|---------|------|-----|
| **Central server** | Not required (P2P possible) | Required (for transformation) |
| **Convergence** | Deterministic by design | Depends on transform correctness |
| **Complexity** | Higher (data structure) | Lower (transformation logic) |
| **Memory** | High (metadata per character) | Lower |
| **Offline editing** | Excellent (merges long branches) | Slow (OT algorithms are slow to merge diverged files) |
| **Production adoption** | Limited in co-editors | Dominant in co-editors |
| **Correctness** | Mathematically guaranteed | Depends on TP1/TP2 correctness |

### The Eg-walker Hybrid (2025)
A new class of algorithm has emerged: **Eg-walker**, a hybrid CRDT/OT algorithm that merges concurrent edits with optimal efficiency and reduced memory usage. It merges documents in milliseconds, requires significantly less memory than standard CRDTs, and operates effectively in peer-to-peer environments. This suggests the future is not "CRDT vs OT" but **CRDT + OT hybrids**.

---

### Deeper Explanation: The Choice Is About Topology And Offline Reality

OT and CRDTs both converge, so the deciding factors are operational: does a central server order everything, and must the app work offline for long stretches?

- **OT** needs a canonical order. In practice that means a single coordinating server, which is fine for a hosted collaborative editor and hostile to local-first. It also has famously subtle transformation edge cases, so you should use an existing implementation.
- **CRDTs** need no order and no server, which makes offline and peer-to-peer natural. The bill arrives as metadata size, memory, and merge semantics you must respect.
- **Hybrid reality**: many products use CRDTs for document content (convergent text) and a server-authoritative model for everything else (permissions, billing, quotas), because security and money cannot be eventually consistent.

The 2026 default for a new collaborative feature is a CRDT library; the reason to pick OT is that you already operate an OT stack (for example a Docs-like editor with server-side history and access control).

### Additional Pitfalls
- **Choosing on features instead of topology.** "Offline for three days on two devices" eliminates OT immediately.
- **Judging CRDTs by raw memory without GC.** Modern libraries compact; a naive implementation is a scarecrow.
- **Judging OT by a naive implementation.** Real OT is careful work; the difficulty is real, not imagined.
- **Mixing both without boundaries.** Pick one model per data category and document the boundary.

### Real-World Deal-Breakers
- **Choosing CRDT because it's "newer"** → OT remains the choice for the vast majority of working co-editors. Production systems like Google Docs use OT, not CRDT.
- **Assuming CRDT is always correct** → representative CRDT solutions have algorithmic flaws. CRDTs are difficult to design and prone to subtle bugs.
- **Ignoring OT's offline limitations** → OT algorithms are slow to merge files that have diverged substantially due to offline editing. This is where CRDTs shine.
- **Forgetting that CRDTs require a reliable messaging layer** → operation-based CRDTs need reliable causal delivery, which OT does not require (the central server provides ordering).
