## 40.8 Semantic Versioning (SemVer)

### Subtopic Tree
- Format: `MAJOR.MINOR.PATCH`
- MAJOR: incompatible API changes
- MINOR: backward-compatible functionality
- PATCH: backward-compatible bug fixes
- Pre-release: `2.0.0-alpha.1`
- Build metadata: `2.0.0+20260529`
- `0.y.z` - initial development
- SemVer ranges in package managers

### The Specification
Semantic versioning is a convention for numbering software releases as `MAJOR.MINOR.PATCH`, where each of the three numbers signals how risky upgrading to that release is for the projects that depend on it. The current specification, SemVer 2.0.0, ties each number to a category of change in a project's public API.

| Number | Increments on | Example |
|--------|--------------|---------|
| **MAJOR** | Incompatible changes that can break existing callers | 2.4.1 → 3.0.0 |
| **MINOR** | Backward-compatible functionality | 2.4.1 → 2.5.0 |
| **PATCH** | Backward-compatible bug fixes | 2.4.1 → 2.4.2 |

### Pre-release Versions
A pre-release appends a hyphen, as in `2.0.0-alpha.1` or `2.0.0-rc.1`, and always sorts **below** the matching final version. That `2.0.0-rc.1` is the release candidate a team promotes through a staging environment before cutting `2.0.0`.

### Build Metadata
Build metadata can follow a plus sign, as in `2.0.0+20260529`, and is **ignored when versions are compared**.

### The `0.y.z` Rule
Any `0.y.z` version marks **initial development**, where the spec says anything may change at any time. A library still on `0.x` isn't promising a stable API yet.

### SemVer Ranges in package.json
```json
{
  "dependencies": {
    "react": "^19.0.0",     // Accepts 19.x.x (major locked)
    "express": "~4.18.0",   // Accepts 4.18.x (minor locked)
    "lodash": "4.17.21"     // Exact version
  }
}
```

---

### Deeper Explanation: SemVer Is A Promise About Compatibility

SemVer communicates what a consumer must do: patch (bug fix, drop-in), minor (new capability, drop-in), major (must adjust). The difficulty is not the numbering, it is defining what counts as breaking for your API surface: removed/renamed exports, changed defaults, widened/narrowed peer ranges, behaviour changes under the same signature, and even stricter input validation can all break consumers.

For libraries, the safe habits are: additive changes only in minors, deprecate before removing (with a runtime warning and docs), keep peer dependency ranges honest, and automate the bump decision from commit types. For apps, SemVer usually matters only for your own API consumers or internal packages.

### Additional Pitfalls
- **"Minor" that changes behaviour under the same signature.** Consumers break without a major bump.
- **Peer ranges wider than what is tested.** Claiming React 19 support without testing it fails at runtime.
- **Removing exports without deprecation.** Downstream builds break immediately.
- **`0.x` used forever as a "beta" escape hatch.** Consumers still need to know when things break.
- **Version numbers reused or unpublished.** npm caches and mirrors make removal unreliable; publish a fix.

### Real-World Deal-Breakers
- **Breaking change without MAJOR bump** → consumers' code breaks silently.
- **PATCH for a new feature** → consumers miss the feature because they don't upgrade.
- **`0.x` for production libraries** → the API may change at any time; consumers can't trust it.
- **Not using SemVer ranges** → you miss security patches and bug fixes.
