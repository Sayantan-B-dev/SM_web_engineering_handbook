## 40.9 Open Source Licensing

### The Three Families

| Family | Examples | Key rule |
|--------|----------|----------|
| **Permissive** | MIT, Apache 2.0, BSD | Keep the copyright notice; do anything else |
| **Weak copyleft** | LGPL, MPL | Modifications to the library must stay open; linking is OK |
| **Strong copyleft** | GPL, AGPL | Derivative works must be open source under the same license |
| **Source-available** | BSL, SSPL | Source is visible but usage is restricted |

### Permissive Licenses
Permissive licences dominate GitHub in 2026. The most common is the **BSD 2-Clause ("Simplified")**, virtually identical to MIT. These allow companies to embed your code in proprietary products.

**MIT:** "Do whatever you want, just keep the copyright notice."
**Apache 2.0:** Same as MIT, plus an **express patent grant** - important for enterprise adoption.

### Copyleft Licenses
Copyleft licenses enforce reciprocity through the "share-alike" principle. The GPL family mandates derivative works remain open source under identical terms, **preventing proprietary forks**. The **AGPL** extends this to network use - if you run modified AGPL software as a service, you must release your modifications.

### The License Decision Matrix

| Question | Answer | License |
|----------|--------|---------|
| Do you want modifications to remain open? | No | MIT / Apache 2.0 |
| Do you want modifications to remain open? | Yes | GPL / AGPL |
| Do you need patent protection? | Yes | Apache 2.0 |
| Will it be used via cloud/SaaS? | Yes | AGPL (if you want copyleft) |
| Do you want to monetize later? | Yes | Consider open-core or BSL |

### Deeper Explanation: The Licence Decides Who Can Use Your Work

Licensing is the mechanism by which a repository becomes usable by others, and the choice is strategic:

| Licence | Type | Practical effect |
|---|---|---|
| MIT / ISC / BSD | Permissive | Anyone can use, modify, and ship closed source with attribution |
| Apache-2.0 | Permissive + patent grant | Preferred by many enterprises; explicit patent protection |
| MPL-2.0 | Weak copyleft | File-level copyleft; safe to link from proprietary code |
| LGPL | Weak copyleft | Dynamic linking allowed; modifications to the library shared |
| GPL / AGPL | Strong copyleft | Derivative works must be released; AGPL extends to network use |
| Unlicensed (no file) | All rights reserved | Not usable by anyone |

Two practical rules: verify the licences of your **dependencies** (a GPL transitive dependency can constrain your distribution), and record attribution/notices in your product (most permissive licences require it). For dual licensing or contribution, a CLA or DCO determines whether you can relicense later.

### Additional Pitfalls
- **No `LICENSE` file.** Public code is not open source; companies will not adopt it.
- **Copied code without its licence.** It contaminates your distribution model.
- **Ignoring transitive licences.** Audits fail at the worst moment; use automated licence checks in CI.
- **A CLA nobody reads before contributing.** Relicensing later becomes impossible without consent.
- **Confusing open source with "public on GitHub".** Visibility is not a licence.

### Real-World Deal-Breakers
- **No license** → no one can legally use your code. It's "all rights reserved" by default.
- **GPL for a library** → many companies won't touch it. They can't link it into proprietary software.
- **MIT for a SaaS product** → competitors can take your code and run it as a service without contributing back. Use AGPL.
- **License incompatibility** → combining GPL code with proprietary code is a violation. Understand compatibility before merging.
- **Changing licenses retroactively** → HashiCorp, Redis, and Elastic all faced community backlash for license changes.
