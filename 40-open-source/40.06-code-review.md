### GitHub Review Statuses

| Status | Meaning | When to use |
|--------|---------|-------------|
| **Comment** | Feedback without approval/rejection | Questions, suggestions |
| **Approve** | Formal sign-off | Code is ready to merge |
| **Request Changes** | Blocking issues | Critical bugs, security issues |

### Constructive Feedback Examples
```markdown
# ❌ Destructive
"This is wrong."

# ✅ Constructive
"This will throw if `user` is null. Consider adding a null check or using optional chaining: `user?.name`."

# ✅ Nitpick (non-blocking)
"nit: Could we rename `data` to `userData` for clarity?"

# ✅ Question
"Why did we choose `useEffect` here instead of a derived value?"
```

### Author Responsibilities
- Read all feedback carefully
- Ask questions if feedback is unclear
- Make requested changes or discuss alternatives
- **Respond to all comments** (even if just "Fixed" or "Done")
- Request re-review after changes

Source: 

### Review Timelines
- **Target response**: within 24 hours
- **Follow up**: if no response after 14 days, reviewer returns to the PR
- **Stale PRs**: close after a defined period (e.g., 30 days) if no activity

### Deeper Explanation: Review Is A Quality Gate And A Teaching Channel

Effective review has two purposes and gets both by being specific and non-personal: catching defects (correctness, security, edge cases) and transferring context (conventions, design intent, history). Comments should therefore state severity and reason â€” "nit: this name shadows the outer `items`" â€” so the author knows what is a blocker and what is a preference.

Reviewer priorities, in order: correctness and safety, data/security boundaries, tests that would catch the bug if it regressed, readability and naming, then style (mostly automated). Author priorities: keep the diff small, explain the why, respond to every comment, and prefer a follow-up PR over scope creep in this one.

### Additional Pitfalls
- **Style debates in review.** Automate formatting and linting; reserve human attention for substance.
- **Rubber-stamp approvals.** An approval that never engaged with the code is a liability.
- **Blocking on preferences.** "Blocking" should mean the code is wrong, unsafe, or unsound.
- **No time budget.** Reviews that sit for days block work and encourage bigger, riskier batches.
- **Reviewing the author.** Language matters; comment on the code, not the person.

### Real-World Deal-Breakers
- **Approving without reading** → bugs ship to production. Don't merge PRs you've only skimmed.
- **Requesting changes without explanation** → author doesn't know what to fix.
- **Not responding to review comments** → PR stalls indefinitely.
- **Taking review personally** → review feedback is the process working, not a personal attack.
- **Reviewing your own PR and self-approving** → defeats the purpose of review.
