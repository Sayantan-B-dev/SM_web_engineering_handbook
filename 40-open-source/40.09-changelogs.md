## Changelogs

### Subtopic Tree
- Changelogs vs release notes vs commit logs
- Keep a Changelog conventions (`Added`, `Changed`, `Fixed`, `Removed`, `Deprecated`, `Security`)
- Unreleased section and version headers with dates
- Generating from Conventional Commits (changesets, semantic-release)
- Audience: users of a library vs operators of an app
- Linking to PRs, issues and migration guides
- Breaking changes called out explicitly

### The Mental Model
A changelog answers one question for a reader who does not read commits: **what changed for me, and what do I have to do about it?** That means grouping by impact, not by file, and putting breaking changes and migrations first. The version header and date give it audit value; the categories give it scan value.

```markdown
## [Unreleased]

### Added
- `useDebouncedValue` hook for debouncing any state value (#482)

### Fixed
- Prevent stale cache entries when query keys change (#491)

## [1.4.0] - 2026-10-13

### Changed
- **BREAKING**: `createClient` now requires an explicit `transport` option
  Migrate with `createClient({ transport: http(url) })` â€” see docs/migration.md
```

### Generation Workflow
Use Changesets (for libraries in a monorepo) or semantic-release (for apps) so the changelog is derived from the commits that already exist, and keep a human edit pass for the summary paragraph. Every breaking change should link to a migration guide, not only to a PR.

### Real-World Deal-Breakers
- **Dumping commit messages.** Readers cannot tell impact from noise; categorise by effect.
- **No breaking-change section.** Users discover the break in production.
- **Undated versions.** Changelogs double as an audit trail; dates are part of the contract.
- **Changelog written after release, from memory.** Generate from commits at release time, then edit.
- **Internal-only notes in a public changelog.** "Refactored the store" means nothing to consumers.
