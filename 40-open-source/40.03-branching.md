## 40.4 Branching Strategies

### GitHub Flow (The Open Source Standard)
```text
main ─────●─────────●─────────●────── (always deployable)
           \       / \       /
            ●─────●   ●─────●
          feature  feature
```

**Rules:**
- `main` is always deployable.
- Every change is a branch.
- Branches are short-lived.
- PRs are reviewed before merge.

### Git Flow (More Complex)
```text
main      ─────●───────────────●─────────
                \             /
develop   ───●───●───●───●───●───●───●───
              \     / \     /
feature        ●───●   ●───●
```

**Branches:**
- `main` - production releases only
- `develop` - integration branch
- `feature/*` - new features
- `release/*` - release preparation
- `hotfix/*` - emergency fixes

### Trunk-Based Development
```text
main ─────●───●───●───●───●───●───●───
          (small commits, no long-lived branches)
```

**Rules:**
- Everyone commits to `main` (or short-lived branches < 1 day).
- Feature flags hide incomplete work.
- Requires strong CI/CD.

---

### Deeper Explanation: Branching Strategy Is A Release Cadence In Disguise

Branching models differ in how long a branch lives and what `main` means: trunk-based (short branches, frequent merges, deploy on merge), GitHub flow (feature branches off `main`, PRs, deploy from `main`), and GitFlow (long-lived `develop`/`release` branches for scheduled releases). The right one follows from how you release, not from a preference for tidiness.

| Model | Branch lifetime | Fits |
|---|---|---|
| Trunk-based | Hours | Continuous delivery, strong tests, feature flags |
| GitHub flow | Days | Most product teams with PR review |
| GitFlow | Weeks | Versioned software with scheduled releases and long support windows |

The costs to weigh: long-lived branches accumulate merge conflicts and defer integration risk (GitFlow's real problem), while trunk-based needs feature flags and discipline to keep `main` releasable.

### Additional Pitfalls
- **Feature branches that live for weeks.** Integration becomes a project of its own.
- **A `develop` branch nobody deploys from.** It drifts from `main` and invalidates testing.
- **No naming convention.** `fix/x`, `feat/y`, and ticket ids make automation and search possible.
- **Branch protection that allows direct pushes "just for hotfixes".** The exception becomes the norm.
- **Deleting branches without tags/releases.** Recovery relies on the reflog and luck.

### Real-World Deal-Breakers
- **Long-lived feature branches** → merge hell. Branch should live days, not weeks.
- **Committing to `main` directly** → no review, no CI. Always use a branch.
- **Not using feature flags** → trunk-based development is impossible.
- **Mixing Git Flow with open source** → overkill for most projects. GitHub Flow is the standard.
