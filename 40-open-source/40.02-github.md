### The Standard Contribution Workflow
1. **Fork** the repository to your own GitHub account.
2. **Clone** your fork locally.
3. **Create a branch** with a descriptive name.
4. **Make changes**, commit with clear messages.
5. **Push** the branch to your fork.
6. **Open a pull request** against the original repository.
7. **Respond to review feedback**.
8. **Merge** (maintainer action) and clean up your branch.

### CODEOWNERS - Automatic Review Assignment
```
# .github/CODEOWNERS
/frontend/   @frontend-team
/backend/    @backend-team
/docs/       @docs-team
```
When a pull request changes a file under `/frontend/`, the `@frontend-team` is automatically requested as reviewer.

### Issue Labels Every Project Needs
- **`good first issue`** - beginner-friendly, well-scoped
- **`help wanted`** - maintainers want outside help
- **`bug`** - something is broken
- **`enhancement`** - new feature request
- **`documentation`** - docs improvement
- **`triage`** - needs initial assessment

### Deeper Explanation: GitHub Is A Collaboration Workflow, Not Just Hosting

The features that matter in daily work are the ones that encode process: pull requests as the review unit, protected branches as policy, required status checks as gates, CODEOWNERS as routing, issues and projects as triage, Actions as automation, and releases as distribution. Understanding them as *policy instruments* is what makes a repository self-managing rather than manually policed.

The configuration most teams eventually want: protected `main` (no direct pushes, linear history optional), required checks (lint, typecheck, test, build), required review (1-2 approvals, code-owner review for critical paths), conventional PR titles, auto-merge when green, and a release workflow that publishes from tags.

### Additional Pitfalls
- **Unprotected default branch.** Someone force-pushes or merges a red build; history becomes unreliable.
- **Required checks nobody maintains.** A flaky check trains people to bypass gates.
- **No CODEOWNERS.** Reviews land on whoever notices, not the responsible owner.
- **Manual release steps.** Automation (tag â†’ publish â†’ changelog) removes a whole class of mistakes.
- **Fork PR secrets exposure.** `pull_request_target` plus fork code is the classic CI security hole.

### Real-World Deal-Breakers
- **Opening a PR without an issue** → maintainers may reject it outright. Many projects require an issue first.
- **Not reading `CONTRIBUTING.md`** → your PR violates project conventions and is closed without review.
- **PR without tests** → maintainers won't merge untested code.
- **PR touching 50 files** → impossible to review. Keep PRs small and focused.
- **No CODEOWNERS** → PRs sit unreviewed because no one knows who should review them.
