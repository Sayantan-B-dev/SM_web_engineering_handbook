### The Mental Model
A monorepo makes **cross-package changes atomic**: you can change a shared component and every consumer in one commit, in one CI run, with one review. That is its whole value. Its costs are tooling complexity, build orchestration, and a tendency to create an implicit mega-coupling where every package depends on everything.

The discipline that keeps it healthy: explicit package boundaries (no deep imports), a dependency graph you can inspect (`pnpm why`, Nx graph), task caching (local and remote), affected-only CI (`turbo run test --filter='...[origin/main]'`), and per-package ownership in `CODEOWNERS`.

```json
// turbo.json â€” declare the dependency graph once; everything else reuses it
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "test": { "dependsOn": ["build"], "inputs": ["src/**", "test/**"] },
    "lint": { "cache": true }
  }
}
```

```yaml
# CI: only build and test what the change actually affects
- run: pnpm turbo run test --filter='...[origin/main]' --cache-dir=.turbo
```

### Real-World Deal-Breakers
- **No affected-only task selection.** Every CI run builds everything; feedback time grows linearly with repository size.
- **Deep imports between packages.** They bypass interfaces and make extraction impossible.
- **A shared "utils" package everything depends on.** It becomes the coupling hub that makes the monorepo feel like a monolith.
- **Independent versioning without automation.** Manual version bumps drift; use changesets.
- **No ownership.** A monorepo without CODEOWNERS means nobody reviews cross-cutting changes.
- **Local-only caching.** CI still rebuilds everything; remote caching is the main win.
