## 40.7 Conventional Commits

### Subtopic Tree
- Format: `<type>[optional scope]: <description>`
- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`
- Breaking changes: `!` or `BREAKING CHANGE:`
- Commit body and footer
- SemVer correlation
- Commitlint (automated enforcement)
- Commitizen (interactive CLI)

### The Specification
Conventional Commits is a lightweight convention on top of commit messages. It provides an easy set of rules for creating an explicit commit history, which makes it easier to write automated tools on top of. This convention dovetails with SemVer, by describing the features, fixes, and breaking changes made in commit messages.

**Format:**
```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### Types and Their SemVer Impact

| Type | Description | SemVer Impact |
|------|-------------|---------------|
| `feat` | New feature | **MINOR** |
| `fix` | Bug fix | **PATCH** |
| `docs` | Documentation only | None |
| `style` | Formatting, missing semicolons | None |
| `refactor` | Code change (no feature, no bug fix) | None |
| `perf` | Performance improvement | **PATCH** |
| `test` | Adding or correcting tests | None |
| `build` | Build system or dependencies | None |
| `ci` | CI configuration | None |
| `chore` | Other changes (no src or test) | None |

### Breaking Changes
```bash
# Using ! after type
feat!: send an email to the customer when a product is shipped

# Using BREAKING CHANGE footer
feat: allow provided config object to extend other configs

BREAKING CHANGE: `extends` key in config file is now used for extending other config files
```

### Rules
- Description: **imperative mood, lowercase, no period** (e.g., "add feature" not "added feature")
- Subject line: **under 72 characters**
- Body: explain **what** and **why** (not how)
- Footer: reference issues (`Fixes #123`), co-authors

### Deeper Explanation: Structure That Machines Can Read

Conventional Commits standardise a commit's first line (`type(scope): summary`) so tooling can generate changelogs and decide version bumps automatically. The value is not aesthetic purity; it is that **release automation becomes possible** and history becomes searchable.

The practical rules: one logical change per commit, an imperative summary under ~72 characters, a body explaining why (not what), and `BREAKING CHANGE:` in the footer for incompatible changes â€” with `feat:`/`fix:` driving semver bumps in most tooling. Enforce with commitlint on the commit-msg hook and in CI, and let `cz`/`commitizen` help authors instead of nagging them.

### Additional Pitfalls
- **Types that mean nothing.** `chore:` for everything defeats the automation.
- **Huge "wip" commits squashed at the end.** You lose the reasoning that made the change reviewable.
- **Breaking changes only mentioned in the body.** Tooling and consumers read the footer.
- **Convention enforced in review instead of tooling.** commitlint is cheaper and more consistent.
- **Unnecessary scopes.** Scopes are most useful when they map to real packages or areas.

### Real-World Deal-Breakers
- **Non-conventional commits** → automated tools can't generate changelogs or determine version bumps.
- **`fix` for a breaking change** → consumers don't know their code will break.
- **No body** → future maintainers don't know why the change was made.
- **Imperfect mood** ("fixed" instead of "fix") → inconsistent history; tooling may fail.
