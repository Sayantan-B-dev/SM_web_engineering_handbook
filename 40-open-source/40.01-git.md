### Essential Git Commands for Open Source
```bash
# Fork the repo on GitHub, then clone your fork
git clone https://github.com/YOUR_USERNAME/project.git
cd project

# Add upstream (the original repo)
git remote add upstream https://github.com/ORIGINAL_OWNER/project.git

# Create a feature branch
git checkout -b fix/issue-123

# Make changes, stage, and commit
git add .
git commit -m "fix: resolve null pointer in user service"

# Keep your fork in sync with upstream
git fetch upstream
git checkout main
git merge upstream/main
git push origin main

# Push your branch and open a PR
git push origin fix/issue-123
```

### `git log` - Understanding Project History
```bash
# See the 10 most frequently modified files (from KDnuggets guide)
git log --pretty=format: --name-only | sort | uniq -c | sort -rg | head -10

# See who last changed each line (git blame)
git blame src/services/user.ts

# Find which commit introduced a bug (binary search)
git bisect start
git bisect bad              # current commit is broken
git bisect good v1.2.0      # this tag was working
```

### Deeper Explanation: Git As A Directed Graph You Can Rewrite

Git is not a list of snapshots; it is a DAG of commits (with a content-addressed object store, branches as movable pointers, and the reflog as your safety net). Understanding three facts explains nearly every confusing situation: commits are immutable, branches are just pointers, and history rewriting changes the graph rather than the files.

The commands that follow from it: `git log --graph --oneline` to see shape, `git reflog` to recover work you thought you lost, `git reset --soft/--mixed/--hard` for the three "undo" meanings, `git restore --staged` to unstage, `git revert` for safe undo of published commits, and `git bisect` for finding a regression by binary search.

### Additional Pitfalls
- **Rewriting published history.** Anyone who pulled the old commits gets a mess; rewrites are for local branches and PRs.
- **`git reset --hard` on uncommitted work.** It is the only common command that truly loses data; commit or stash first.
- **Merging instead of rebasing (or the reverse) as dogma.** Both are tools; the team convention decides which.
- **Committing generated files.** `.gitignore` hygiene keeps diffs meaningful.
- **Ignoring the reflog.** It recovers most mistakes; learn it before you need it.

### Real-World Deal-Breakers
- **Committing directly to `main`** → upstream maintainers can't review your changes. Always branch.
- **Not syncing your fork** → your branch is based on stale code; the PR has conflicts.
- **Force-pushing to a shared branch** → destroys others' work. Never force-push to `main`.
- **Giant commits** → impossible to review. One logical change per commit.
- **Not using `git bisect`** → spending hours manually finding a regression. `git bisect` finds it in minutes.
