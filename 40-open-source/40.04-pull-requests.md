### Writing a Good PR Description
```markdown
## What
Adds dark mode toggle to the settings page.

## Why
Closes #456. Users have requested this feature for months.

## How
- Added `useDarkMode` hook with localStorage persistence
- Added toggle component to Settings page
- Added `dark` class to `<html>` element
- Updated Tailwind config with dark mode variants

## Screenshots
| Light | Dark |
|-------|------|
| ![light](...) | ![dark](...) |

## Checklist
- [x] Tests added
- [x] Documentation updated
- [x] No breaking changes
```

### Linking Issues
```markdown
Fixes #456
Closes #456
Resolves #456
```
When the PR merges, GitHub automatically closes the linked issue.

### Draft PRs
Open a PR as **Draft** when you want early feedback but aren't ready for review. This signals "don't merge yet."

### Merge Strategies

| Strategy | How it works | When to use |
|----------|-------------|-------------|
| **Squash and merge** | All commits squashed into one | Open source default - clean history |
| **Merge commit** | Preserves all commits + merge commit | When individual commits matter |
| **Rebase and merge** | Replays commits onto base | Linear history without merge commit |

### Deeper Explanation: A PR Is An Argument, Not A Diff

The diff shows what changed; the description explains why, what alternatives were considered, and how it was verified. Reviewers spend their scarce attention there, so a PR description that answers those questions gets reviewed faster and with better comments.

The structure that works: context (the problem and an issue link), the approach in two sentences, the notable trade-offs, how to test it (including a screenshot or a preview link), and the checklist (tests, docs, migration notes). ### Additional Pitfalls
- **A PR that changes three unrelated things.** Reviewers cannot reason about it; split it.
- **No description.** "Fixes stuff" pushes the discovery work onto the reviewer.
- **Screenshots for a visual change missing.** Reviewers cannot verify UI without running it locally.
- **Draft PRs merged unready.** Use draft or stacked PRs to keep intent explicit.
- **Review comments resolved without a reply.** The thread is the record; answer and then resolve.

### Real-World Deal-Breakers
- **PR without a description** → reviewers don't know what changed or why.
- **PR with no linked issue** → maintainers can't trace the context.
- **Screenshots missing for UI changes** → reviewers can't verify the change.
- **PR too large (>500 lines)** → reviewers skim instead of review. Keep PRs under 300 lines.
- **No CI passing** → maintainers won't review until CI is green.
- **Force-pushing after review** → reviewer comments become stale; they can't see what changed.
