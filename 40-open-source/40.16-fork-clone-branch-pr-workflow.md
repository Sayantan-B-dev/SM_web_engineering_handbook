## 40.3 Fork → Clone → Branch → PR Workflow

### Subtopic Tree
- Forking (creating your own copy)
- Cloning (downloading to local machine)
- Branching (isolating your changes)
- Committing (with conventional commit messages)
- Pushing (uploading to your fork)
- Pull Request (requesting merge)
- Review cycle (feedback → changes → re-review)
- Merge (maintainer action)

### The Complete Workflow (Step by Step)
```bash
# 1. Fork on GitHub (click the "Fork" button)

# 2. Clone your fork
git clone https://github.com/YOUR_USERNAME/project.git

# 3. Add upstream
git remote add upstream https://github.com/ORIGINAL_OWNER/project.git

# 4. Create a feature branch
git checkout -b feat/add-dark-mode

# 5. Make your changes
# ... edit files ...

# 6. Stage and commit
git add .
git commit -m "feat(ui): add dark mode toggle"

# 7. Push to your fork
git push origin feat/add-dark-mode

# 8. Open a PR on GitHub
# Go to the original repo → "New Pull Request" → select your branch

# 9. Respond to review feedback
# ... make changes ...
git add .
git commit -m "fix: address review feedback"
git push origin feat/add-dark-mode

# 10. After merge, clean up
git checkout main
git pull upstream main
git branch -d feat/add-dark-mode
```

### The "Say Hello Before Committing" Principle
The Linux Foundation's 2026 guide emphasizes **saying hello before committing** - introduce yourself in the issue or discussion before starting work. This prevents duplicate effort and confirms the maintainer wants the change.

---

### Deeper Explanation: Why Forks Exist And When Not To Use Them

Forking exists because contributors do not always have write access: a fork gives them a copy they control, and the PR becomes a comparison between two branches on different repositories. Maintainers use the same flow for external contributions; for team members with write access, a branch in the same repository is simpler (shared CI caches, easier rebasing, no upstream sync).

```bash
# The canonical external-contributor flow, with an explicit upstream remote
git clone git@github.com:you/project.git && cd project
git remote add upstream https://github.com/org/project.git
git switch -c fix/format-currency-locale

# ...commit your work, then keep the fork current before opening the PR
git fetch upstream
git rebase upstream/main
git push -u origin fix/format-currency-locale
```

Once a PR is merged, GitHub can offer to delete the branch; either way, sync `main` from upstream and rebase (not merge) your working branch to keep the PR clean.

### Additional Pitfalls
- **Starting from a stale fork.** Conflicts multiply; rebase on `upstream/main` before opening the PR.
- **Branch on `main` of the fork.** You lose the ability to sync cleanly; branch per change.
- **Merge commits inside a PR branch.** They bury your change; rebase to keep the diff readable unless the project requires merges.
- **PRs from the wrong base branch.** Cross-fork base mistakes produce huge, confusing diffs.
- **Missing upstream remote.** Then "sync" becomes a manual re-clone.

### Real-World Deal-Breakers
- **Starting work without saying hello** → someone else may already be working on it, or the maintainer may not want it.
- **Branching from stale `main`** → your PR has merge conflicts. Always sync with upstream first.
- **Committing generated files** → bloats the repo. Add them to `.gitignore`.
- **Not updating your branch** → the maintainer can't merge; you must rebase or merge upstream.
