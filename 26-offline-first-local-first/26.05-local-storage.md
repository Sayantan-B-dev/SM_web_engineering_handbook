## 26.4 Local Storage

### Subtopic Tree
- `localStorage` (synchronous, 5MB, strings only)
- `sessionStorage` (tab-scoped)
- Cookies (sent with every request)
- When NOT to use each
- IndexedDB vs localStorage vs OPFS
- Cookie-based auth and offline-first

### Why `localStorage` Is Not for Offline Data
> "Avoid `localStorage` because it is synchronous and blocks the main thread. Size limit is about 5 MB, and it can only contain strings. Web Workers and Service Workers cannot access `localStorage`."

```javascript
// ❌ localStorage blocks the main thread
localStorage.setItem('largeData', JSON.stringify(hugeArray)); // synchronous, blocks UI

// ✅ IndexedDB is asynchronous
await db.data.put(hugeArray); // doesn't block UI
```

### When `localStorage` Is Still OK
- Small config values (theme, locale, feature flags)
- Non-critical UI state
- Values under 5KB

```javascript
// ✅ Acceptable use of localStorage
localStorage.setItem('theme', 'dark');
const theme = localStorage.getItem('theme') ?? 'light';
```

---

### Deeper Explanation: Where `localStorage` Still Belongs

`localStorage` is synchronous, strings-only, per-origin, and typically 5-10 MB. Synchronous means every read blocks the main thread and every write flushes to disk (with storage pressure, this can be measurable). So its legitimate uses are narrow but real: small, read-once-at-boot preferences; a last-known theme; a locale; an A/B assignment; a feature-flag cache. Anything larger, structured, or hot belongs in IndexedDB or memory.

The other reason to keep it small is failure modes: it throws on quota (private mode in some browsers historically threw on every write), it is readable by any script on the origin (so never tokens), and it can be cleared at any moment.

### Additional Pitfalls
- **Storing auth tokens.** Any XSS reads them; use httpOnly cookies.
- **JSON-stringifying large objects.** Parsing megabytes on boot is a visible delay; use IndexedDB.
- **Reading it in a render loop.** Each `getItem` is a synchronous hit; read once and keep in React state (or a module constant).
- **No try/catch.** Quota and disabled-storage errors crash the app.
- **Using it as a cache for API responses.** That is a schema, an invalidation policy, and a size problem â€” all of which IndexedDB already solves.

### Real-World Deal-Breakers
- **`localStorage` for offline data** → 5MB limit, synchronous, blocks main thread.
- **`localStorage` in a Worker** → not available. Use IndexedDB.
- **`localStorage` for auth tokens** → XSS can read them. Use `HttpOnly` cookies.
- **Cookies for offline data** → cookies are sent with every request; 4KB limit. Never store data in cookies.
