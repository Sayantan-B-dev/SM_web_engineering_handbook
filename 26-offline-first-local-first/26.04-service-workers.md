## 26.5 Service Workers

### Subtopic Tree
- Network proxy (intercepts all requests)
- Lifecycle: install → activate → fetch → idle → terminated
- Cache Storage API (HTTP request/response pairs)
- Precache (app shell) vs runtime cache
- Versioned caches
- `skipWaiting()` and `clients.claim()`
- Update flow (new SW waits until tabs close)
- Debugging (Chrome DevTools Application tab)

### Service Worker Lifecycle
```text
1. Register: navigator.serviceWorker.register('/sw.js')
2. Install: precache app shell
3. Waiting: new SW waits until all tabs close
4. Activate: clean up old caches
5. Fetch: intercept requests
6. Idle: browser terminates the SW to save memory
7. Restart: next fetch event wakes it up
```

### Precache App Shell
```javascript
const CACHE = 'app-v1';
const PRECACHE_URLS = [
  '/', '/index.html', '/app.js', '/styles.css',
  '/fonts/inter.woff2', '/icons/logo.svg',
];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE).then((cache) => cache.addAll(PRECACHE_URLS))
  );
});
```

### Runtime Cache (Stale-While-Revalidate)
```javascript
self.addEventListener('fetch', (event) => {
  const { request } = event;
  if (request.method !== 'GET') return;

  const url = new URL(request.url);

  // API requests: network-first with cache fallback
  if (url.pathname.startsWith('/api/')) {
    event.respondWith(
      fetch(request)
        .then((response) => {
          const clone = response.clone();
          caches.open(CACHE).then((cache) => cache.put(request, clone));
          return response;
        })
        .catch(() => caches.match(request))
    );
    return;
  }

  // Static assets: cache-first
  event.respondWith(
    caches.match(request).then((cached) => cached || fetch(request))
  );
});
```

---

### Deeper Explanation: The Service Worker Is The Offline Contract

Offline support starts and ends with the service worker, because it is the only thing that can serve a response when the network is gone. Three responsibilities, in order of importance:

1. **Keep the app bootable.** Precache the HTML shell and the hashed JS/CSS/asset manifest. If boot fails, nothing else matters.
2. **Serve data sensibly.** Cache read responses with an explicit strategy per class of request (network-first for fresh data, cache-first for immutable assets, stale-while-revalidate for feed-like data), and never cache personalised or authenticated payloads into a shared cache.
3. **Own updates.** Version caches, delete old ones in `activate`, and surface a "new version available" prompt rather than silently mixing bundles.

The subtlety that causes production incidents: a waiting worker plus a long-lived tab can serve an old bundle whose chunks no longer exist. `skipWaiting` plus a controlled reload prompt is the standard fix, and the reload must happen *after* the user saves work.

### Additional Pitfalls
- **Caching HTML aggressively.** Users get a stale shell pointing at purged asset hashes; revalidate the entry point.
- **Precaching incompletely.** A missing chunk breaks the offline route on the first cold start.
- **`skipWaiting()` with no reload coordination.** The running page keeps old JS while the server serves new assets, causing mystery errors.
- **No cache versioning or cleanup.** Storage grows until the browser evicts everything, including your precache.
- **Caching API responses with cookies.** Shared caches plus personalised responses is a data-leak bug.
- **Debugging with the worker enabled and a stale cache.** Always test in a private window or with "Bypass for network".

### Real-World Deal-Breakers
- **No cache versioning** → old assets served forever. Use `app-v1`, `app-v2`, etc., and delete old caches on activate.
- **`skipWaiting()` without user consent** → the new SW activates immediately, potentially breaking the running app. Wait for user confirmation before skipping.
- **No `clients.claim()`** → the new SW doesn't control existing tabs until they reload.
- **Caching everything** → storage bloat, stale content. Cache selectively with versioned caches.
- **No offline fallback page** → when offline and a page isn't cached, the user sees the browser's error page. Always provide an offline fallback.
