  │── GET /sync?since=42 ──────────────────► │

  │                                          │

### Delta Sync (Only Changed Data)
```typescript
// Track last sync timestamp/sequence
let lastSyncSeq = await db.meta.get('lastSyncSeq');

// Pull changes since last sync
const res = await fetch(`/api/sync?since=${lastSyncSeq}`);
const { changes, newSeq } = await res.json();

// Apply changes to local database
for (const change of changes) {
  if (change.type === 'UPSERT') {
    await db.todos.put(change.data);
  } else if (change.type === 'DELETE') {
    await db.todos.delete(change.id);
  }
}

await db.meta.put({ key: 'lastSyncSeq', value: newSeq });
```

### Snapshot + Delta
```typescript
// For large datasets, send a snapshot on first sync, then deltas
if (isFirstSync) {
  const snapshot = await fetch('/api/sync/snapshot').then((r) => r.json());
  await db.todos.bulkPut(snapshot.todos);
  await db.meta.put({ key: 'lastSyncSeq', value: snapshot.seq });
} else {
  // Delta sync as above
}
```

### Deeper Explanation: Sync Is Ordering, Idempotency, And Progress

Sync quality is decided by four mechanics:

1. **Cursors, not timestamps.** The server exposes a monotonic revision (or a per-stream cursor). The client stores the last applied cursor and requests everything after it. Timestamps cannot survive clock skew or transaction ordering.
2. **Idempotency keys.** Every write carries a client-generated id so replays are safe. Without this, retries duplicate.
3. **Snapshot plus delta.** Deltas alone mean an unbounded replay for new or returning clients; periodic snapshots bound the work (and let a client that lost its cursor recover cheaply).
4. **Explicit pending/failed state.** The UI must distinguish synced, pending, and failed records, with retry and conflict resolution paths a user can act on.

And an honest fallback: when a device has been offline beyond the server's retention window (or the schema changed), the only correct move is to fetch a fresh snapshot and re-apply the outbox, not to keep poking at a stale cursor.

### Additional Pitfalls
- **Full refetch on reconnect.** It works until the dataset grows; use cursors and deltas with periodic snapshots.
- **Timestamps as ordering.** Clocks drift; sequences are cheap and correct.
- **Silent conflicts.** A merge without telling the user loses their intent unless the model is convergent (CRDT).
- **No retry budget or backoff.** Offline devices retry aggressively and drain battery.
- **Unbounded outbox.** Cap it, and tell the user when the queue is full rather than quietly dropping writes.

### Real-World Deal-Breakers
- **Full sync every time** → slow, wasteful. Use delta sync with sequence numbers.
- **No sequence numbers** → you can't detect gaps or request missed changes.
- **No snapshot mechanism** → replaying 100,000 changes on first sync is slow.
- **Sync without conflict resolution** → concurrent edits overwrite each other. Use CRDTs or last-write-wins with timestamps.
