## 26.0 Offline-First vs Local-First - The Fundamental Distinction

### Subtopic Tree
- **Offline-first**: the app works without a network connection, but the server remains the source of truth
- **Local-first**: the user's device is the primary source of truth; the server is a sync relay
- Local-first is a superset of offline-first
- The seven ideals of local-first software (Kleppmann et al., 2019)
- CRDTs as the enabling technology
- The sync engine as the core architectural component

### The Core Mental Model
**Offline-first** means the app doesn't break when the network is gone. You cache responses, queue mutations, and replay them when connectivity returns. The server is still authoritative - the client is a cache.

**Local-first** goes further: the user's device holds the authoritative copy of their data. The server exists only to sync changes between devices and users. There is no "source of truth" on the server - every device is a peer. This is why local-first requires **CRDTs (Conflict-free Replicated Data Types)** - they allow concurrent edits on different devices to be merged deterministically without a central coordinator.

```text
Offline-first:   Client (cache) ──► Server (source of truth)
Local-first:     Device A (authoritative) ◄──► Device B (authoritative)
                 ↑ sync engine (CRDTs, no central authority)
```

### The Seven Ideals of Local-First Software
1. **No spinners** - your work lives on your device; there's nothing to wait for.
2. **Your work is not trapped on one device** - sync across devices when you want.
3. **The network is optional** - everything works offline.
4. **Seamless collaboration** - multiple users edit the same data concurrently.
5. **The long now** - data persists for decades, independent of any company's servers.
6. **Security and privacy by default** - end-to-end encryption is the norm.
7. **You retain ultimate ownership** - no vendor can revoke access to your data.

### Deeper Explanation: Where The Truth Lives

The distinction is not "does it work offline" â€” it is **which copy of the data is authoritative when they disagree**.

- **Offline-first**: the server owns the truth; the client keeps a cache and a queue so the app *survives* being offline, then syncs. Conflicts are resolved in the server's favour (or by a merge rule you define). Most CRUD products live here.
- **Local-first**: the user's device holds a first-class replica; sync is a background reconciliation between peers and a server. The app is fully functional with no server at all, and merges must be conflict-free (CRDT or explicit merge functions). Ink & Switch's seven ideals frame it: no spinners, multi-device, offline, collaboration, longevity, privacy, user ownership.

The engineering consequences differ sharply: offline-first can use a request queue with last-write-wins; local-first needs convergent data structures, durable local storage, and sync that tolerates arbitrary interleavings. Choosing wrongly means either a fragile CRDT stack you did not need, or a "works offline" claim that loses data the moment two devices edit.

### Additional Pitfalls
- **Calling a cache "local-first".** If a network call is required for the app to be usable, it is offline-first at best.
- **Assuming sync is optional.** Both models need an explicit sync design: what is queued, what is merged, what is dropped.
- **No conflict policy.** Undefined behaviour under concurrent edits is how users lose work.
- **Ignoring storage limits and eviction.** Local-first correctness depends on durable storage; request persistence and plan for eviction.

### Real-World Deal-Breakers
- **Calling it "local-first" when it's actually offline-first** → the server is still authoritative; you don't get the benefits of peer-to-peer sync or CRDT-based conflict resolution.
- **Choosing local-first for server-authoritative data** → financial transactions, inventory counts, and anything requiring a single source of truth should stay server-authoritative.
- **Ignoring the sync engine** → local-first without a robust sync engine is just a local database. The sync engine is the hard part.
