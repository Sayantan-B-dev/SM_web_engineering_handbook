### Optimistic Update Pattern (TanStack Query)
```typescript
const mutation = useMutation({
  mutationFn: updateTodo,
  onMutate: async (newTodo) => {
    await queryClient.cancelQueries({ queryKey: ['todos'] });
    const previous = queryClient.getQueryData(['todos']);
    queryClient.setQueryData(['todos'], (old) =>
      old.map((t) => (t.id === newTodo.id ? newTodo : t))
    );
    return { previous };
  },
  onError: (err, newTodo, context) => {
    queryClient.setQueryData(['todos'], context.previous); // rollback
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['todos'] }); // sync with server
  },
});
```

### Optimistic Update with IndexedDB (Offline-First)
```typescript
async function addTodo(text: string) {
  const tempId = crypto.randomUUID();
  const todo = { id: tempId, text, done: false, status: 'pending' };

  // 1. Write to local IndexedDB immediately
  await db.todos.put(todo);

  // 2. Queue mutation for sync
  await db.mutations.add({
    type: 'CREATE_TODO',
    tempId,
    body: { text },
    createdAt: Date.now(),
  });

  // 3. Update UI (from IndexedDB via useLiveQuery)
  return todo;
}

// When sync completes, replace tempId with server ID
async function onSyncComplete(tempId: string, serverId: string) {
  await db.todos.update(tempId, { id: serverId, status: 'synced' });
  await db.mutations.where('tempId').equals(tempId).delete();
}
```

### Deeper Explanation: Optimism Is A UX Contract With A Rollback Clause

An optimistic update renders the *predicted* result before the server confirms it. Doing it well means defining four things for every mutation: the predicted state, the confirmation (ack), the failure path (rollback plus a message), and the concurrency rule (what happens if another update touched the same data).

Concretely, with TanStack Query the API is built for this: `onMutate` cancels in-flight queries for the key, snapshots the previous value, applies the optimistic write, and returns the snapshot as context; `onError` restores it; `onSettled` invalidates. The hard parts are not the API but the semantics: server-generated ids (use a temporary id and reconcile), ordering of rapid edits, and the UX for "we could not save that".

Also: not every action should be optimistic. Anything with a real chance of rejection and a high cost of being wrong (payments, destructive operations) is better as a blocking action with a spinner and a clear success state.

### Extended Example: Snapshot, Predict, Rollback, Reconcile

```ts
const toggleDone = useMutation({
  mutationFn: ({ id, done }: { id: string; done: boolean }) =>
    api.patch(`/todos/${id}`, { done }),

  onMutate: async ({ id, done }) => {
    await queryClient.cancelQueries({ queryKey: ['todos'] });
    const previous = queryClient.getQueryData<Todo[]>(['todos']);
    queryClient.setQueryData<Todo[]>(['todos'], (old = []) =>
      old.map((t) => (t.id === id ? { ...t, done } : t)),
    );
    return { previous };
  },
  onError: (_err, _vars, ctx) => {
    queryClient.setQueryData(['todos'], ctx?.previous);   // rollback
    toast.error('Could not save that change.');
  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['todos'] }),
});
```

### Additional Pitfalls
- **Optimistic creates with server ids.** Generate a temporary id and replace it on ack, or keys and links break.
- **No rollback.** Failed optimistic writes that stay on screen are worse than a spinner.
- **Invalidating before the mutation settles.** The refetch overwrites the optimistic state with stale data and the UI flickers backwards.
- **Optimistic updates on high-risk actions.** Payments and deletions belong behind explicit confirmation.
- **No offline interaction.** When offline, the mutation must enter the outbox rather than fail.

### Real-World Deal-Breakers
- **No rollback on failure** → UI shows data that was never persisted.
- **No idempotency keys** → retried mutations create duplicates.
- **No temp ID reconciliation** → optimistic items with temp IDs never get replaced by server IDs.
- **Optimistic updates for operations that can fail unpredictably** → server assigns IDs, timestamps, prices, etc. Optimistic data may be wrong.
