## 26.2 Local-First Architecture

### Subtopic Tree
- The device is the source of truth
- CRDTs for conflict-free merging
- Sync engine (electric-sql, Replicache, Automerge, Yjs, TinyBase)
- Local database (SQLite via WASM, IndexedDB)
- Peer-to-peer sync (optional)
- End-to-end encryption
- The "long now" - data persistence independent of servers
- Sync server as a relay, not an authority

### The Local-First Stack

| Component | Purpose | Examples |
|-----------|---------|----------|
| **Local database** | Store data on device | SQLite (WASM), IndexedDB, PGlite |
| **CRDT layer** | Conflict-free merging | Yjs, Automerge, Loro |
| **Sync engine** | Replicate changes across devices | ElectricSQL, Replicache, TinyBase, Triplit |
| **Sync server** | Relay changes between devices | ElectricSQL, custom WebSocket server |
| **Auth** | Identify users | JWT, OAuth, passkeys |

### CRDTs - The Enabling Technology
A CRDT is a data structure that can be replicated across multiple devices and merged deterministically without conflicts. Two devices editing the same list or text concurrently will converge to the same state, regardless of the order in which changes are applied.

```javascript
// Yjs - a CRDT for collaborative text
import * as Y from 'yjs';

const doc = new Y.Doc();
const text = doc.getText('content');

// Device A
text.insert(0, 'Hello');
// Device B (concurrently)
text.insert(0, 'World');

// After sync, both devices converge to the same result
// (CRDT merges the concurrent inserts deterministically)
```

### ElectricSQL - Sync Engine for Postgres
```typescript
// ElectricSQL syncs a subset of Postgres to the client
import { electrify } from 'electric-sql/wa-sqlite';

const conn = await electrify(serverUrl, token);

// Query local data (instant, no network)
const { rows } = await conn.db.query('SELECT * FROM projects');

// Mutations are local-first and sync in the background
await conn.db.query('INSERT INTO projects (name) VALUES ($1)', ['New Project']);
```

### Replicache - Client-Side Sync
```typescript
const rep = new Replicache({
  name: 'user-123',
  pushURL: '/api/replicache/push',
  pullURL: '/api/replicache/pull',
  mutators: {
    async createTodo(tx, { id, text }) {
      await tx.put(`todo/${id}`, { id, text, done: false });
    },
  },
});

// Mutations run locally immediately
await rep.mutate.createTodo({ id: '1', text: 'Buy milk' });

// Subscribe to local changes (instant)
rep.subscribe((tx) => tx.scan({ prefix: 'todo/' }).toArray(), (todos) => {
  renderTodos(todos);
});
```

### Deeper Explanation: Sync Is A Replication Problem

Local-first means each device is a replica, and replicas that can diverge need a convergence rule. That rule is the architecture, and everything else (storage, transport, UI) follows from it:

- **CRDT data types** for convergent state (Yjs/Automerge for text and maps) â€” no central ordering required.
- **A durable local database** (IndexedDB with a library such as Dexie, or SQLite via WASM/OPFS for relational workloads) as the source of truth on the device.
- **An optional relay server** for discovery, persistence, and access control â€” not for canonical truth.
- **The sync protocol**: exchange updates, verify they are causally ready (vector clocks / version vectors), apply or defer.

The user-visible guarantees are the point: instant interaction with no spinners, multi-device continuity, and data that survives the vendor disappearing (longevity). The price is bounded but real: larger local storage, garbage-collection logic for tombstones, and merge semantics you now own.

### Additional Pitfalls
- **A schema that cannot merge.** Relational rows with `updatedAt` and LWW still lose concurrent edits; model state as mergeable data.
- **Treating the server as canonical "just for safety".** You reintroduce central ordering and lose offline writes.
- **No compaction policy.** Update logs and tombstones grow forever unless you snapshot and prune.
- **Ignoring multi-device identity.** Two devices editing while offline is the normal case, not the edge case.
- **No export path.** Local-first promises longevity; without export you still lose data when storage is cleared.

### Real-World Deal-Breakers
- **No CRDT for collaborative editing** → concurrent edits overwrite each other. Last-write-wins loses data.
- **Server as source of truth in a local-first app** → you're building offline-first, not local-first. The device must be authoritative.
- **No end-to-end encryption** → the sync server can read all user data. Local-first should default to E2EE.
- **Ignoring the "long now"** → if your sync server shuts down, users lose access to their data. Design for data portability and export.
- **CRDT for server-authoritative data** → financial transactions, inventory, and anything requiring a single source of truth should stay server-authoritative.
