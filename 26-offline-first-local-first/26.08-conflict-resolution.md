## 26.8 Conflict Resolution

### Subtopic Tree
- Last-Write-Wins (LWW) - simple, lossy
- CRDTs - deterministic merge, no data loss
- Operational Transformation (OT) - used by Google Docs
- CRDT vs OT comparison
- Conflict resolution strategies per data type
- Vector clocks / Lamport timestamps
- Manual conflict resolution (show both versions to the user)

### LWW (Last-Write-Wins)
```typescript
// Each record has an updatedAt timestamp
// On conflict, the record with the latest timestamp wins
function resolveConflict(local, remote) {
  return local.updatedAt > remote.updatedAt ? local : remote;
}
```
**Problem:** LWW silently discards one of the conflicting writes. For collaborative editing, this loses data.

### CRDTs (Conflict-Free Replicated Data Types)
```javascript
// Yjs - CRDT for collaborative text
import * as Y from 'yjs';

const doc = new Y.Doc();
const text = doc.getText('content');

// Two users edit concurrently
text.insert(0, 'Hello'); // User A
text.insert(0, 'World'); // User B

// After sync, both converge deterministically
// Result: "WorldHello" (order determined by CRDT, not by timestamp)
```

### OT (Operational Transformation)
OT transforms operations so they can be applied in any order. Google Docs uses OT.

```text
User A: insert(0, "Hello")
User B: insert(0, "World")

Transform A against B: insert(5, "Hello")  // shift by length of B's insert
Transform B against A: insert(0, "World")  // no shift needed

Result: "WorldHello"
```

### CRDT vs OT

| Feature | CRDT | OT |
|---------|------|-----|
| Central server | Not required | Required (for transformation) |
| Complexity | Higher (data structure) | Lower (transformation logic) |
| P2P support | Yes | No |
| Data loss | No | No (if transforms are correct) |
| Used by | Yjs, Automerge, Loro | Google Docs, ShareDB |

---

### Deeper Explanation: Choose Semantics Per Field, Not Per App

Conflict resolution is a data-modelling decision. The same app usually needs several strategies:

| Strategy | Semantics | Good for |
|---|---|---|
| Server wins | Central order | Config, permissions, inventory counts |
| Last-write-wins | Timestamps + tiebreak | Simple scalar fields (theme, nickname) |
| Field-level merge | Non-overlapping fields merge | Record editing (title vs body) |
| CRDT (convergent) | Any interleaving converges | Text, rich collaborative state |
| Manual | Present both versions to the user | Anything where intent matters |

Two rules make whatever you choose defensible: **never silently drop a user's edit** (if you must, tell them), and **make the merge deterministic** (the same two versions must always produce the same result, on every device and in any order).

### Additional Pitfalls
- **Timestamps from the client.** A device six minutes behind wins or loses every conflict at random; use server time or logical clocks.
- **Versions compared per record with no field information.** Concurrent edits to different fields are lost; merge at field granularity.
- **No user-visible resolution for destructive conflicts.** Show "your version" and "their version" for anything expensive to recreate.
- **Assuming conflicts are rare.** Multi-device and offline usage make them routine; test them deliberately.
- **Deleting tombstones too early.** Without them, a delayed update resurrects deleted records.

### Real-World Deal-Breakers
- **LWW for collaborative text** → data loss. Use CRDT or OT.
- **CRDT for financial data** → overkill and incorrect. Financial data needs server-authoritative transactions.
- **No conflict resolution at all** → concurrent edits overwrite each other silently.
- **OT without a central server** → OT requires a central server to order and transform operations. CRDTs work peer-to-peer.
