## 33.8 In-Browser AI Tools and Libraries (2026)

### Subtopic Tree
- **Transformers.js v4** - Hugging Face's library; WebGPU runtime rewritten in C++; 4× speedup for BERT; supports 20-billion parameter models at 60 tokens/second
- **WebLLM** - MLC Community's high-performance in-browser LLM inference engine
- **LiteRT.js** - Google's cross-platform edge AI runtime for the web; WebGPU + upcoming WebNN; WASM fallback
- **ONNX Runtime Web** - Microsoft's versatile runtime; WASM, WebGPU, WebGL, WebNN execution providers
- **TensorFlow.js** - WebGPU, WebGL, WASM, CPU backends; WebGPU is opt-in via separate package
- **pocket-llm** - Feature-detects the fastest engine (Prompt API → WebLLM → wllama)
- **agentic-stack-js-web-components** - Google's Edge AI Web Components for LLMs, embeddings, RAG, tool use

---

### Deeper Explanation: Pick By Model Family And Runtime Needs

The library choice follows from what you are running:

| Library | Sweet spot | Notes |
|---|---|---|
| **Transformers.js** | Text/vision transformers from Hugging Face | ONNX Runtime Web under the hood; WebGPU/WASM; huge model catalogue |
| **ONNX Runtime Web** | Arbitrary ONNX models, custom pipelines | Most control over execution providers and sessions |
| **WebLLM** | Local chat LLMs (Llama/Qwen-class, quantised) | WebGPU-only; memory-hungry; desktop-first |
| **MediaPipe Tasks** | Vision, audio, gestures, face/pose | Tuned, small, task-specific models |
| **TensorFlow.js** | Legacy and custom JS-native models | Broad docs; slower than WebGPU paths for large models |
| **MLC / WebLLM-style compilers** | Compiling models for WebGPU | Best performance, most setup |
| **Chrome built-in AI (Prompt API)** | Zero-download summaries and prompts | Chromium-only, browser-managed model |

The practical default for a React app: Transformers.js for task models (classification, embeddings, summarisation, ASR) inside a worker, with WebGPU enabled when available and a server fallback for quality-critical paths.

### Additional Pitfalls
- **Choosing a library before choosing a model.** The runtime must support the model's operators, precision, and device.
- **Ignoring bundle impact.** Some libraries are large; load them dynamically with the feature, not in the main bundle.
- **Bundler friction with WASM and workers.** Vite/webpack need explicit worker and wasm asset handling; test the production build.
- **No version pinning for models.** A moving `main` revision can silently change behaviour; pin the revision.
- **Skipping the server fallback.** Quality and device variance both require one.

### Real-World Deal-Breakers
- **TensorFlow.js WebGPU is not bundled** → WebGPU support is a separate, optional package; neither `tfjs-core` nor the full `tfjs` package includes it.
- **No engine fallback** → pocket-llm's approach is correct: feature-detect Prompt API → WebLLM → wllama based on browser capabilities.
- **Ignoring model compatibility** → Gemma 4 requires models ≥4; Transformers.js v3 does not support WebGPU (use v4).
