## 33.0 The In-Browser AI Landscape (2026)

### Subtopic Tree
- Definition: running ML inference directly on the client device, inside the browser, with no data leaving the user's machine
- The shift from server-side inference to client-side execution
- Three execution paths: WebGPU, WebAssembly, and high-level APIs (window.ai, Prompt API)
- The 2026 default: local-first AI as a production reality, not a demo
- Cost economics: running a quantized 3B-parameter model in the browser now outperforms round-trip API calls for single-turn summarization under 2K tokens, text classification, form-field autocompletion, short translation tasks, and FAQ-style question answering
- Regulatory pressure: EU AI Act enforcement, expanding US state privacy laws
- API cost escalation: per-token pricing from major providers increasing 15-30% year-over-year since 2024

### The Three Execution Paths

| Path | Hardware | Best for | Browser support |
|------|----------|----------|----------------|
| **WebGPU** | GPU (compute shaders) | Large models, autoregressive generation, batched inference | Chrome 113+, Edge stable; Firefox behind flag; Safari experimental |
| **WebAssembly (WASM)** | CPU (SIMD + threads) | Small models (<100M params), single-pass tasks (embedding, classification) | All major browsers (broad, stable support) |
| **Prompt API / window.ai** | NPU/GPU (managed) | Zero-configuration LLM tasks, no model download | Chrome Canary/Dev (version 130+) |

### Deeper Explanation: Three Compute Backends, One Feature

The browser AI stack has three interchangeable compute backends, and the right architecture lets the app express the feature once and pick the fastest available:

| Backend | Reach | Strengths | Limits |
|---|---|---|---|
| WASM (SIMD, threads) | Universal | Portable, predictable | Slowest; threads need isolation |
| WebGPU | Modern desktop + recent mobile | 5-50Ã- faster for transformer inference | Adapter availability, blocklists |
| WebNN | Growing (Chromium-first) | Can hit NPUs; efficient power use | Fragmented support |

Add the platform's own built-in models (Chrome's Prompt API and task APIs) as a fourth path, which is attractive because the model ships with the browser rather than your bundle.

### Additional Pitfalls
- **Probing with user-agent strings.** Feature-detect (`'gpu' in navigator`, `WebNN` interfaces) and handle asynchronous adapter requests.
- **Assuming a probe implies performance.** WebGPU on an old integrated GPU can be slower than WASM with SIMD.
- **One code path with no fallback.** Devices without a backend must still get a usable product.
- **Ignoring power.** Sustained GPU inference drains batteries; debounce and batch.

### Real-World Deal-Breakers
- **Assuming one backend fits all** → the difference between WebGPU and WASM can be **10-15× performance** depending on model size and task shape.
- **Ignoring the cold-start penalty** → WebGPU has a 1-5 second shader compilation on first run; WASM has negligible cold-start.
- **Assuming WebGPU works everywhere** → as of March 2026, global WebGPU support is around **85%**, meaning some users cannot use the API.
- **Not measuring** → most developers never measure which backend they're running.
