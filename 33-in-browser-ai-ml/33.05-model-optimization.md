## 33.5 Model Optimization

### Subtopic Tree
- Quantization: INT8, Q4F16, Q5_K_XL
- Graph optimization level: 'all' for ONNX Runtime Web
- ORT format: convert to `.ort` for faster loading
- Kernel fusion: reduce dispatch count at batch size 1
- Web Worker offloading to eliminate cold-start jank
- React-specific memory teardown hooks

---

### Deeper Explanation: Four Levers, Applied In Order

- **Quantisation** (int8, int4, fp16): 2-8Ã- smaller and 2-4Ã- faster, with small accuracy cost. The default first move.
- **Distillation / smaller architectures**: a distilled 66M-parameter model often suffices for classification and short summarisation, and it fits mobile budgets.
- **Pruning and structured sparsity**: fewer weights, but the runtime must support the sparsity pattern to gain speed.
- **Graph-level optimisation**: operator fusion and constant folding come free from ONNX Runtime's optimiser; make sure you are using the optimised graph rather than the training export.

Then align the model to the task: cropping/resizing inputs to the exact shape the model expects, truncating to the model's context length, batching, and caching results for repeated inputs are usually worth more than any further model surgery.

### Additional Pitfalls
- **Quantising without measuring quality.** Re-run your eval set; some tasks degrade far more than others.
- **Assuming int4 works everywhere.** Some operators are unsupported at low precision; check the runtime's operator coverage.
- **Ignoring input shape.** Feeding 1080p frames to a 224Ã-224 model wastes most of the compute on preprocessing.
- **Skipping the export optimiser.** ONNX Runtime's graph optimisations are free performance.
- **Optimising the model before the pipeline.** Preprocessing and postprocessing often dominate total time.

### Real-World Deal-Breakers
- **No quantization** → INT8 quantization is essential for reducing bandwidth and memory pressure.
- **No graph optimization** → enable `graphOptimizationLevel: 'all'` for ONNX Runtime Web.
- **No Web Worker** → WASM execution on the main thread makes the UI feel frozen during model execution.
- **No memory teardown** → garbage collection pauses on 150-300MB allocations cause visible frame drops.
