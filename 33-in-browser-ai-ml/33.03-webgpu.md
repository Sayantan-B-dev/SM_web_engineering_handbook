## 33.1 WebGPU

### Subtopic Tree
- Purpose-built for rendering AND general-purpose GPU computation
- Compute shaders (general-purpose programs on GPU, no connection to graphics)
- Storage buffers (up to 256MB+ per buffer, no texture packing)
- WGSL (WebGPU Shading Language) for compute shaders
- The compute pipeline: create buffers → upload weights → dispatch shaders → read output
- Memory model: Float32/Float16 arrays stored directly in typed arrays
- Dispatch overhead: at batch size 1, per-operation overhead dominates regardless of kernel quality

### Performance Benchmarks

### Deeper Explanation: Compute Shaders Without The Graphics

WebGPU is the modern GPU API for the web: devices, adapters, queues, command buffers, and (for ML) compute pipelines with workgroups over storage buffers. For AI work you rarely write WGSL by hand â€” runtimes (ONNX Runtime Web, Transformers.js, WebLLM, MLC) generate and manage kernels â€” but understanding the shape explains the performance characteristics:

- **Transfer cost matters.** Weights and inputs live in `GPUBuffer`s; moving data in and out has cost, so keep tensors on the GPU across steps.
- **Workgroup sizing and tiling dominate performance.** Runtimes tune this; that is why hand-rolled WebGPU inference is usually slower.
- **Adapter limits are real.** Max buffer size, storage binding size, and max compute workgroup dimensions differ per device and can reject a model outright.
- **Asynchrony is everywhere.** `requestAdapter`, `requestDevice`, buffer mapping, and command submission are all async â€” errors surface late, so validate limits explicitly.

### Additional Pitfalls
- **Assuming WebGPU is available.** Check `navigator.gpu`, request an adapter, and handle `null`; keep a WASM fallback.
- **Ignoring adapter limits.** A large model can fail on `maxBufferSize`; query limits and pick a smaller quantisation.
- **Per-inference device creation.** Create the device once per worker and reuse buffers.
- **Debugging without tooling.** Use the WebGPU inspector and device-lost callbacks; silent GPU errors are common.

### Real-World Deal-Breakers
- **Naive single-operation measurements** → wall-clock measurements overestimate per-dispatch cost by **20×** by conflating dispatch with synchronization. At batch size 1, the effective approach to LLM inference optimization in WebGPU is **reducing dispatch count** (kernel fusion).
- **Assuming WebGPU is always faster** → for small tensors (<1000 elements), WebGPU may not be beneficial; WebGL delegates to CPU for tensors <128 elements.
- **No fallback strategy** → the correct hierarchy is WebGPU (fastest) → WebGL (fast) → WASM + SIMD (baseline).
- **Ignoring memory overhead** → WebGPU consumes nearly **2.6× more memory** than WebGL in some scenarios.
