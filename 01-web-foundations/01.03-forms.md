## 1.3 Forms

### Subtopic Tree
- Form structure (`<form>`, `<fieldset>`, `<legend>`)
- Input types (text, email, password, number, date, file, etc.)
- Labels (`<label for>`, wrapping labels, `aria-label`)
- Validation: `required`, `pattern`, `min`/`max`, `minlength`/`maxlength`
- Constraint Validation API (`checkValidity()`, `setCustomValidity()`)
- Native error UI vs custom error messages
- Autocomplete attributes
- `novalidate` attribute
- Accessible form errors (`aria-describedby`, `aria-invalid`, `aria-live`)

### Syntax & Validation
HTML5 introduced semantic input types and constraint validation that work **without JavaScript**. Choosing `type="email"` automatically creates a constraint that checks for a valid email format. `type="url"` requires an absolute URL.

```html
<form novalidate>
  <fieldset>
    <legend>Contact</legend>

    <label for="email">Email *</label>
    <input type="email" id="email" name="email"
           required autocomplete="email"
           aria-describedby="email-error">
    <span id="email-error" role="alert" hidden>Please enter a valid email</span>

    <label for="zip">ZIP Code</label>
    <input type="text" id="zip" name="zip"
           inputmode="numeric" pattern="[0-9]{5}"
           title="Five digit ZIP code">
  </fieldset>
</form>
```

### Validation Attributes Table

| Attribute | Purpose | Example |
|-----------|---------|---------|
| `required` | Field cannot be empty | `<input required>` |
| `pattern` | Regex validation | `pattern="[A-Za-z]{3}"` |
| `min`/`max` | Numeric/date range | `min="18" max="99"` |
| `minlength`/`maxlength` | String length | `minlength="8"` |
| `type="email"` | Built-in email format check | Auto-validates |
| `type="url"` | Absolute URL check | Auto-validates |

### Real-World Tricks
- **`inputmode="numeric"`** → mobile keyboards show numbers without enforcing numeric type (better for ZIP codes).
- **`autocomplete` values** (`email`, `current-password`, `new-password`, `one-time-code`) → browsers autofill reliably; dramatically improves conversion on mobile.
- **`novalidate` on form + custom JS** → take over validation while keeping native APIs (`checkValidity()`).
- **Cross-field validation**: Use `setCustomValidity()` on one field based on another's value (e.g., password confirm).

### Real-World Deal-Breakers
- **No server-side validation** → HTML validation is trivially bypassed via DevTools, raw HTTP requests, or JS injection. Always validate server-side.
- **No `<label>`** → screen readers announce "edit text" with no context. Placeholder text is **not** a label.
- **`<input type="number">` for ZIP/phone** → allows `e`, `+`, `-`, and scroll-wheel accidental changes.
- **Error messages not announced** → use `aria-live="polite"` or `role="alert"` on error containers.
- **`disabled` submit button** → users can't trigger validation feedback. Prefer enabling submit and showing errors on click.
