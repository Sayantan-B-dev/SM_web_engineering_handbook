## 1.8 Browser Rendering Pipeline (Critical Rendering Path)

### Subtopic Tree
1. **HTML Parsing** → bytes → tokens → nodes → DOM tree
2. **CSS Parsing** → bytes → CSSOM tree (render-blocking)
3. **JavaScript Execution** → can block parsing (unless `defer`/`async`)
4. **Render Tree Construction** → DOM + CSSOM → visible nodes only
5. **Layout (Reflow)** → compute size and position of every node
6. **Paint** → convert to display list of drawing commands
7. **Commit** → hand off to compositor thread
8. **Rasterization** → decode pixels (often on GPU)
9. **Compositing** → layerize, composite, draw to screen

### Step-by-Step Breakdown

**DOM Construction (Incremental)**: The browser parses HTML into tokens, tokens into nodes, nodes into a tree. A node starts with a startTag token and ends with an endTag token. Nodes are connected based on token hierarchy — nested tokens create parent-child relationships.

**CSSOM Construction (Blocking, Not Incremental)**: CSS is **render-blocking**. The browser must fully parse all CSS before constructing the render tree. Unlike DOM, CSSOM cannot be built incrementally because later rules can override earlier ones.

**Render Tree**: Combines DOM and CSSOM. Only **visible** nodes are included — `display: none` elements are excluded; `visibility: hidden` elements are included (they take up space).

**Layout (Reflow)**: Computes the exact size and position of every render tree node. This is expensive. It's triggered by:
- DOM changes (add/remove elements)
- Content changes (text, images)
- Style changes (width, height, font-size, margin, padding)
- Window resize
- Reading layout properties (`offsetHeight`, `getBoundingClientRect`)

**Paint**: Converts styled nodes into a display list (drawing commands like "draw rect at (x,y) with color Z").

**Compositing**: Layers are rasterized (often on GPU) and composited together. `transform` and `opacity` changes can skip layout and paint entirely, running only on the compositor thread — this is why `transform: translateX()` is faster than `left: 100px` for animations.

### Optimization Techniques
- **Minimize critical resources**: Reduce number of render-blocking CSS and JS files.
- **Defer non-critical JS**: `<script defer>` (executes after parsing) or `<script async>` (executes when downloaded, may interrupt parsing).
- **Inline critical CSS**: Above-the-fold styles in `<style>` in `<head>`; load rest with `media="print" onload="this.media='all'"`.
- **Lazy load below-fold images**: `loading="lazy"` shortens the critical rendering path.
- **Preconnect/preload**: `<link rel="preconnect">` for origins; `<link rel="preload">` for critical assets.
- **Code splitting**: Load only the JS needed for the current page.
- **Minify & compress**: Gzip/Brotli for text, modern formats (AVIF/WebP) for images.
- **Avoid layout thrashing**: Batch reads, then writes. Use `requestAnimationFrame` for DOM mutations before paint.
- **Use `content-visibility: auto`** → browser skips rendering offscreen content until needed.

### Real-World Deal-Breakers
- **Render-blocking JS in `<head>`** → page appears blank until script downloads and executes. Use `defer` or move to end of body.
- **Synchronous XHR** → blocks the main thread entirely; never use it.
- **Large CSS files with unused rules** → CSSOM construction slowed; render tree delayed.
- **Forced synchronous layout** → reading `offsetHeight` after a DOM write forces the browser to recalculate layout immediately.
- **Animating `width`/`height`/`top`/`left`** → triggers layout + paint + composite on every frame. Use `transform` and `opacity` for 60fps animations.
- **Too many DOM nodes** → slower parsing, style calculation, layout, and memory usage. Use virtualization (react-window, TanStack Virtual) for long lists.
- **No `width`/`height` on images** → causes Cumulative Layout Shift (CLS) when image loads. Always set `width` and `height` attributes or use `aspect-ratio` CSS.
