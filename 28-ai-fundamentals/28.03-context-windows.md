### What a Context Window Is
A context window is the total number of tokens a model can process in a single request. This guide covers how they work, why they degrade, what the real limits are, and how to manage them in production. It is the model's working memory: your prompt, system instructions, conversation history, tool outputs, and the model's own response all share the same budget.

### The "Lost in the Middle" Problem
Models are significantly better at recalling information from the **beginning and end** of their context window than from the middle. Accuracy can drop by **30% or more** for information buried in the middle.

```text
Recall accuracy:
[High] Beginning ████████████████████
[Medium] Middle  ██████████
[High] End      ████████████████████
```

### The Hidden Cost of Long Context
Bigger does not mean better. The number on a model card is not the number you actually get. Production systems lose accuracy as context grows. Challenges include increased processing time and costs, potential for information overload, and risk of conflicting information leading to inconsistent responses.

### Context Compaction
```typescript
// Naive: send entire conversation history every time
const messages = [...fullHistory, { role: 'user', content: query }];

// Better: summarize old turns, keep only recent turns + summary
const summary = await summarize(fullHistory.slice(0, -10));
const messages = [
  { role: 'system', content: `Previous conversation summary: ${summary}` },
  ...fullHistory.slice(-10),
  { role: 'user', content: query },
];
```

### Long Context vs RAG

| Long Context | RAG |
|--------------|-----|
| Send everything in the prompt | Retrieve only relevant chunks |
| Simple architecture | More complex pipeline |
| High token cost | Lower token cost |
| Degrades with size | Scales with corpus |
| No setup needed | Requires vector DB + embeddings |

---

### Deeper Explanation: The Window Is A Budget, Not A Container

A large context window does not mean "put everything in it". Three effects punish careless stuffing: **cost** (you pay for every token, every call), **latency** (prefill time grows with input length), and **attention dilution** (models retrieve less reliably from the middle of a long context â€” the well-documented "lost in the middle" effect).

The engineering discipline is a context budget with an allocation policy:

| Slot | Budget | Notes |
|---|---|---|
| System/instructions | 5-15% | Stable, cacheable |
| Retrieved context (RAG) | 20-40% | Rank, dedupe, truncate per document |
| Conversation history | 20-40% | Summarise older turns, keep last N verbatim |
| User input + output space | rest | Always leave room for the answer |

Also exploit **prompt caching**: providers price cached prefixes far cheaper, so keeping a stable system prompt and stable early context produces large savings with no quality change.

### Additional Pitfalls
- **Overflow handled by silent truncation.** Long chats start silently answering the wrong question; implement explicit summarisation and window management.
- **Reordering the prompt every call.** You destroy prefix caching and pay full price.
- **Stuffing 50 documents "just in case".** Rank and keep the best 5-8; relevance beats volume.
- **Assuming long context replaces retrieval.** It is a capacity, not a search strategy.
- **Ignoring the attention curve.** Put critical instructions at the start and repeat the key ask at the end.

### Real-World Deal-Breakers
- **Assuming the context window is persistent memory** → every API call starts from scratch. You must re-send the entire conversation history.
- **Filling the context window** → accuracy drops in the middle. Put critical instructions at the beginning and end.
- **Using 1M-token context for everything** → expensive and slower. Use RAG for large corpora.
- **Not compacting context** → long sessions accumulate tokens fast. Summarize old turns.
- **Assuming the model "remembers"** → it doesn't. Every request is stateless.
