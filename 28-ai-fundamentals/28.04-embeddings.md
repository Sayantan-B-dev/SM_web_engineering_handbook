### What an Embedding Is
An embedding is a **dense vector of floating-point numbers** that represents the semantic meaning of text. Similar texts have similar vectors. The classic example: `embedding("king") - embedding("man") + embedding("woman") ≈ embedding("queen")`.

### Cosine Similarity
```typescript
function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, magA = 0, magB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    magA += a[i] * a[i];
    magB += b[i] * b[i];
  }
  return dot / (Math.sqrt(magA) * Math.sqrt(magB));
}

// Similar texts → similarity close to 1
cosineSimilarity(embed('React performance'), embed('Optimizing React')); // 0.89
cosineSimilarity(embed('React performance'), embed('Baking a cake')); // 0.12
```

### Deeper Explanation: Embeddings Are Geometry, And Geometry Is Only As Good As The Model

An embedding maps text to a vector so that semantic similarity becomes distance. Everything that follows â€” retrieval quality, clustering, deduplication â€” depends on the embedding model's training, its dimensionality, and the *task it was trained for*.

Rules that avoid the common disasters:

- **Same model for index and query.** Mixing embeddings from two models produces meaningless distances.
- **Normalise and pick a metric deliberately.** Cosine similarity is the default; dot product only after normalisation; Euclidean rarely for text.
- **Chunk before embedding.** A 5 000-word document embedded as one vector has a blurry meaning; 200-500 token chunks with overlap retrieve far better.
- **Store metadata alongside vectors** â€” source, section, timestamp, permissions â€” because filtering is half of retrieval quality.
- **Version your index.** Changing the model means re-embedding the entire corpus; make that a routine operation, not an emergency.

### Additional Pitfalls
- **Embedding the query differently from the documents.** Prefixes and instructions differ by model (query vs passage); read the model card.
- **Very long inputs silently truncated.** Most embedding models cap at 512-8 192 tokens; longer text is cut.
- **Assuming embeddings capture facts.** They capture similarity; exact-match and numeric constraints belong in keyword/hybrid search.
- **No re-embedding plan.** A deprecated model makes your index stale and your retrieval quality unknowable.

### Real-World Deal-Breakers
- **Using embeddings for exact match** → embeddings capture semantics, not exact strings. "React" and "react" are similar, but "React 18" and "React 19" are also similar. Use hybrid search.
- **Not caching embeddings** → re-embedding the same text wastes money. Cache by content hash.
- **Using the wrong model for the language** → embedding models are trained on specific languages. Check language support.
- **Ignoring dimensionality** → higher dimensions are more accurate but cost more to store and query.
