## 28.5 Vector Databases

### Subtopic Tree
- Purpose: store and query embeddings at scale
- Approximate Nearest Neighbor (ANN) search
- HNSW (Hierarchical Navigable Small World)

### pgvector Example
```sql
-- Enable extension
CREATE EXTENSION vector;

-- Create table with vector column
CREATE TABLE documents (
  id SERIAL PRIMARY KEY,
  content TEXT,
  embedding vector(1536)
);

-- Create HNSW index for fast search
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);

-- Query: find 5 most similar documents
SELECT content, 1 - (embedding <=> $1) AS similarity
FROM documents
ORDER BY embedding <=> $1
LIMIT 5;
```

### Deeper Explanation: Choose By Where The Data Already Lives

A vector database stores embeddings and answers nearest-neighbour queries, usually with metadata filters. The decision is rarely "which ANN algorithm" â€” it is where you want your vectors to live:

| Option | Good for | Trade-off |
|---|---|---|
| **pgvector on Postgres** | Teams that already run Postgres; transactional consistency with source rows | Tuning and scale limits at very high dimensions/volume |
| **Dedicated vector DB** (Pinecone, Weaviate, Qdrant, Milvus) | Large corpora, heavy filtering, hybrid search, managed scaling | Another system, another consistency boundary |
| **SQLite/libSQL + vector extension** | Local-first and edge RAG | Operational maturity, size limits |
| **In-memory (FAISS, hnswlib WASM)** | Small corpora, prototypes, browser-side search | No durability, memory-bound |

Two properties matter more than the benchmark: **hybrid search** (BM25 + vector, fused with reciprocal rank fusion) and **metadata filtering that is applied *during* ANN search**, not after.

### Additional Pitfalls
- **Vector-only retrieval.** Exact identifiers, names, and codes need keyword search; hybrid wins consistently.
- **Filters applied after the search.** Recall collapses: you get the top-10 of everything, then filter to nothing.
- **No idempotent upsert key.** Re-indexing duplicates documents and pollutes results.
- **Forgetting to store the source text or link.** Retrieval without citation is unverifiable and undebuggable.
- **Ignoring deletion and permission semantics.** Rows removed from the source must disappear from the index, per user.

### Real-World Deal-Breakers
- **Using a vector DB when Postgres already works** → pgvector is sufficient for millions of vectors. Don't add infrastructure you don't need.
- **No metadata filtering** → you retrieve irrelevant results from the wrong category. Always filter.
- **No hybrid search** → pure vector search misses exact keyword matches. Combine vector + BM25.
- **Ignoring index build time** → Qdrant has the fastest index build times but slowest search; pgvector is the opposite.
