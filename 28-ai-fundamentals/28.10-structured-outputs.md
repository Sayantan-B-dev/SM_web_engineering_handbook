### How Structured Outputs Work
Modern structured outputs fundamentally change output reliability through **grammar-constrained decoding**. Libraries or native features mathematically restrict the token probabilities at generation time. If the chosen schema dictates that the next token must be a quotation mark or a specific boolean value, the probabilities of all non-compliant tokens are masked out. This is a single-turn generation strictly focused on form.

```typescript
const response = await openai.chat.completions.create({
  model: 'gpt-4.1',
  messages: [
    { role: 'user', content: 'Extract the name and age from: Alice is 30 years old.' },
  ],
  response_format: {
    type: 'json_schema',
    json_schema: {
      name: 'person',
      strict: true,
      schema: {
        type: 'object',
        properties: {
          name: { type: 'string' },
          age: { type: 'integer' },
        },
        required: ['name', 'age'],
        additionalProperties: false,
      },
    },
  },
});

const person = JSON.parse(response.choices[0].message.content);
// { name: 'Alice', age: 30 } - guaranteed valid
```

---

### Deeper Explanation: Constrain Decoding, Then Still Validate

Structured output exists because free-form text is unusable as an interface. There are three escalating techniques and you should use the strongest one the provider supports:

1. **Prompt-only JSON** â€” "respond with JSON matching this schema". Cheapest, most fragile; strip code fences and retry on parse failure.
2. **JSON mode** â€” the provider guarantees syntactically valid JSON, but not your shape.
3. **Constrained/strict decoding** â€” the grammar is enforced during generation so the output *must* match the schema. This is what "strict: true" or a JSON-Schema response format gives you.

Even with strict decoding, validate at the boundary: providers version schemas, and union/optional fields can be emitted in unexpected ways. Treat the model like any external system â€” parse, validate with Zod, then trust.

### Extended Example: Strict Decoding Plus Runtime Validation

```ts
const Summary = z.object({
  headline: z.string().max(80),
  severity: z.enum(['low', 'medium', 'high']),
  actions: z.array(z.string()).max(5),
});

const res = await llm.chat({
  model: 'gpt-5-mini',
  messages,
  response_format: { type: 'json_schema', json_schema: { name: 'summary', schema: z.toJSONSchema(Summary), strict: true } },
});

const parsed = Summary.safeParse(JSON.parse(res.content));
if (!parsed.success) {
  // one repair attempt with the validation error, then fall back to a safe default
  return { headline: 'Summary unavailable', severity: 'low', actions: [] } as const;
}
```

### Additional Pitfalls
- **Trusting JSON mode for shape.** Valid JSON is not your schema; validate.
- **Unbounded arrays and long strings.** A schema like `z.array(z.string())` invites 5 000 items; constrain with `.max()`.
- **Deep optional nesting.** Small models fail at deep optionality; flatten the schema where you can.
- **No fallback path.** When validation fails twice, degrade to a deterministic default instead of crashing the feature.
- **Changing the schema without versioning.** Cached outputs and logs must map to the schema version that produced them.

### Real-World Deal-Breakers
- **No `strict: true`** → schema compliance is not guaranteed. The model may add extra fields.
- **Non-serializable schemas** → not all JSON Schema features are supported. Check the model's docs.
- **No retry logic** → even with strict mode, API errors happen. Always retry with backoff.
- **Using structured outputs for actions** → structured outputs are for data extraction, not tool invocation.
