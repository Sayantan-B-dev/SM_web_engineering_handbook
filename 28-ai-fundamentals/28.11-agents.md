### What an Agent Is
An autonomous software agent built on large language models. Agents have moved from research demonstrations to production systems in under three years. An agent is not a single LLM call - it's a **loop**: the model reasons about the task, decides on an action, executes it (via tools), observes the result, and repeats until the task is complete.

```text
User: "Book me a flight to Kolkata"
  ↓
Agent (LLM): "I need to search flights"
  → Tool: search_flights(destination="Kolkata")
  ← Result: [flight1, flight2]
  ↓
Agent (LLM): "I need to check prices"
  → Tool: get_price(flight1)
  ← Result: $450
  ↓
Agent (LLM): "I should book flight1"
  → Tool: book_flight(flight1)
  ← Result: Confirmation #12345
  ↓
Agent (LLM): "Your flight is booked. Confirmation #12345"
```

### The ReAct Loop
```typescript
async function agentLoop(task: string, tools: Tool[], maxSteps = 10) {
  const messages = [
    { role: 'system', content: 'You are a helpful agent. Use tools to complete the task.' },
    { role: 'user', content: task },
  ];

  for (let step = 0; step < maxSteps; step++) {
    const response = await openai.chat.completions.create({
      model: 'gpt-4.1',
      messages,
      tools,
      tool_choice: 'auto',
    });

    const message = response.choices[0].message;
    messages.push(message);

    // If no tool calls, the agent is done
    if (!message.tool_calls) {
      return message.content;
    }

    // Execute tool calls
    for (const call of message.tool_calls) {
      const result = await executeTool(call.function.name, call.function.arguments);
      messages.push({
        role: 'tool',
        tool_call_id: call.id,
        content: JSON.stringify(result),
      });
    }
  }

  throw new Error('Agent exceeded max steps');
}
```

### Deeper Explanation: An Agent Is A Loop With Tools, Memory, And A Budget

The difference between a chat completion and an agent is that the agent decides **what to do next**, repeatedly, using tools and observations. That single fact creates all the engineering requirements: a bounded loop, tool permissions, a scratchpad, error recovery, and a stopping rule.

The essential components of a credible agent:

- **Goal + plan** â€” an explicit task, decomposed into steps it can revise.
- **Tools** â€” narrow, validated, idempotent, with bounded outputs.
- **Memory** â€” short-term (the loop's messages), working (files/notes/KV), long-term (vector retrieval over past sessions).
- **Control** â€” max steps, max tool calls, max tokens, and timeout; plus human approval for side effects.
- **Observation loop** â€” the result of each action must feed back into the next decision, or it is not an agent.

Cost discipline is the product discipline: measure steps per task, tokens per step, and success rate; an agent that solves a task in 4 steps instead of 14 is a 3Ã- cost reduction with the same value.

### Additional Pitfalls
- **Unbounded loops.** Every agent needs a hard step limit; "it will stop when done" is how bills explode.
- **Side effects without approval.** Sending email, moving money, or writing to shared systems needs human-in-the-loop or a dry-run mode.
- **Tools that are too broad.** One `run_any_sql` tool is an incident; scoped tools with validated parameters are auditable.
- **No memory management.** Long sessions overflow the context; summarise, checkpoint, and externalise to files.
- **Measuring only success, not cost or steps.** Both are product metrics for anything that runs per user request.

### Real-World Deal-Breakers
- **No max steps** → the agent loops forever. Always cap iterations.
- **No tool validation** → the agent hallucinates tool names and arguments. Validate against your tool registry.
- **No human-in-the-loop for destructive actions** → the agent deletes production data. Require confirmation for destructive tools.
- **No observability** → you can't see what the agent did or why. Log every step, tool call, and result.
- **Too many tools** → the agent gets confused. Keep tool count under 10-15.
