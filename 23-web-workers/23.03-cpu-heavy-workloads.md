### When to Use a Worker
Web workers should be considered for tasks that take **more than 100 milliseconds** or block user inputs. Ideal candidates include data processing, complex calculations, and tasks that do not require direct DOM access.

### Common CPU-Heavy Workloads
- **Image processing/filtering** - applying filters, resizing, format conversion.
- **Parsing large JSON/CSV files** - `JSON.parse` of a 50MB payload blocks for seconds.
- **Complex cryptographic calculations** - key derivation, hashing large data.
- **Syntax highlighting in editors** - tokenizing large source files.
- **Data transformation** - sorting, filtering, aggregating large datasets.
- **Video/audio processing** - decoding, encoding, effects.
- **WebAssembly compute** - heavy numerical simulation.

### Progress Reporting
```javascript
// worker.js
function processData(data) {
  for (let i = 0; i < data.length; i++) {
    // expensive computation
    if (i % 1000 === 0) {
      self.postMessage({ type: 'PROGRESS', value: (i / data.length) * 100 });
    }
  }
  return result;
}
```

### Cancellation
```javascript
// worker.js
let shouldCancel = false;

self.onmessage = (e) => {
  if (e.data.type === 'CANCEL') {
    shouldCancel = true;
    return;
  }
  if (e.data.type === 'START') {
    shouldCancel = false;
    const result = processData(e.data.payload, () => shouldCancel);
    if (!shouldCancel) self.postMessage({ type: 'RESULT', value: result });
  }
};
```

### Deeper Explanation: Find The Long Task, Then Decide Where It Goes

CPU-heavy work is anything that holds the main thread long enough to drop a frame or delay an interaction. The method is always the same: **profile first, then classify**:

1. Record a performance trace and look for long tasks (>50 ms) â€” those are your candidates.
2. Classify each: pure computation (parsing, sorting, diffing, image processing, crypto, compression, pathfinding) â†’ move off-thread. DOM-dependent (measuring, layout, animation) â†’ keep on the main thread but reduce work.
3. Offload with a worker and measure again. If the task is under ~5 ms, the round trip is a net loss; if it is over ~20 ms and repeats, the worker usually wins.

For work that cannot move, break it up: `scheduler.yield()` (or `setTimeout` as a fallback) between chunks keeps every frame responsive at the cost of a little throughput.

### Additional Pitfalls
- **Moving DOM work to a worker.** It cannot touch the DOM; only the *data* computation can move.
- **Optimising a task that is not on the critical path.** Profile first; a 200 ms task that runs once after idle does not matter.
- **Forgetting to re-measure.** Offloading adds complexity; if INP did not improve, revert it.
- **Serialising per item.** Batch a thousand items into one message, not a thousand messages.
- **Ignoring memory pressure.** Workers double peak memory during clone; on mobile this can force a reload.

### Real-World Deal-Breakers
- **Offloading a 5ms task** → spawn overhead (0.5-1ms) + message latency (0.1-0.3ms) makes it slower than doing it on the main thread.
- **No progress reporting** → user stares at a frozen UI with no feedback.
- **No cancellation** → a long-running task can't be stopped; the worker must be terminated.
- **`JSON.parse` in a worker without streaming** → even in a worker, a 100MB `JSON.parse` is slow. Use streaming parsers.
