## 23.1 Worker Types

### Subtopic Tree
- Dedicated Workers
- Shared Workers
- Service Workers
- Worklets (Audio, Paint, Animation)
- Worker type comparison

### Dedicated Workers
A dedicated worker is used by a single script. Its context is represented by the `DedicatedWorkerGlobalScope` object. Only the script that spawned it can access it.

```javascript
// main.js
const worker = new Worker('worker.js');
worker.postMessage({ type: 'CALCULATE', data: 100 });
worker.onmessage = (e) => console.log(e.data);
```

### Shared Workers
A shared worker can be used by multiple scripts running in different windows, iframes, etc., as long as they are on the same origin as the worker. They communicate through an active port.

```javascript
// main.js
const worker = new SharedWorker('shared-worker.js');
worker.port.start();
worker.port.postMessage({ type: 'PING' });
worker.port.onmessage = (e) => console.log(e.data);
```
Shared workers are ideal for centralized tasks, result caching, or cross-context communication. They share context across tabs.

### Service Workers
Service Workers essentially act as proxy servers that sit between web applications, the browser, and the network (when available). They are intended to enable effective offline experiences, intercept network requests, and take appropriate action based on network availability.

### Worklets
Worklets are lightweight, highly constrained worker-like scripts for specific rendering tasks:
- **AudioWorklet** - custom audio processing.
- **PaintWorklet** - CSS Paint API (programmatic images).
- **AnimationWorklet** - scroll-linked and custom animations.

### Comparison Table

| Feature | Dedicated Worker | Shared Worker | Service Worker |
|---------|-----------------|---------------|----------------|
| **Instances** | Many per tab | One per origin | One for all tabs |
| **Lifespan** | Same as tab | Same as tab | Independent of tabs |
| **Network interception** | No | No | Yes (`fetch` event) |
| **Push notifications** | No | No | Yes (`push` event) |
| **DOM access** | No | No | No |
| **Storage access** | IndexedDB, Cache API | IndexedDB, Cache API | IndexedDB, Cache API |
| **Use case** | CPU-heavy computation | Cross-tab shared state | Offline, caching, push |

---

### Deeper Explanation: Ownership Models, Not Just Variants

The four worker types differ in *who owns the instance* and *what it can reach*: dedicated (one document), shared (all tabs of an origin), service (the origin's network/cache/push), and worklets (rendering/audio pipeline, minimal APIs). Choosing wrongly produces either leaks or unusable APIs, not merely a slower app.

| Choose | When | Watch out for |
|---|---|---|
| Dedicated | One tab needs heavy compute | One instance per tab multiplies memory |
| Shared | Cross-tab singleton (socket, cache warmup) | Safari lifecycle differences |
| Service | Offline, push, background sync | Proxy semantics and update flows |
| Worklet | Audio, animation, layout/paint work | No timers, no DOM, tiny API surface |

Module workers (`new Worker(url, { type: 'module' }))` are supported in all modern browsers and are the sane default because they let you share code with the main bundling graph.

### Additional Pitfalls
- **`type: 'module'` forgotten.** You get a confusing syntax error the moment you write an `import`.
- **Service worker used as a general-purpose worker.** It can be terminated at any time and cannot hold session state.
- **Dedicated worker per component instance.** Instantiate one per *concern*, then queue jobs.
- **Not terminating idle workers.** Idle workers still hold memory, and a page with 20 tabs holds 20 copies.
- **Assuming a worker keeps running in a background tab.** Browsers throttle or suspend them heavily.

### Real-World Deal-Breakers
- **Using a Service Worker for CPU work** → Service Workers are designed for network interception, not computation. They can be killed at any time.
- **Shared Worker without port management** → `SharedWorker` uses `port` objects, not the global `onmessage`. Forgetting `.port.start()` means messages never arrive.
- **Assuming Worklets have the same API as Workers** → Worklets are extremely restricted; no `fetch`, no `postMessage` in the Worker sense.
