### Structured Clone (Deep Copy)
Data passed between threads is **cloned** (structured clone algorithm). Not shared. The clone is a deep copy of the data.

```javascript
// This CLONES the object (deep copy)
worker.postMessage({ user: { name: 'Alice', address: { city: 'Kolkata' } } });
// The original object is unchanged in the main thread.
```

**Structured clone supports:** primitives, plain objects, arrays, `Date`, `Map`, `Set`, `RegExp`, `Blob`, `File`, `ArrayBuffer`, `TypedArray`, `ImageData`, and more.

**Cannot be cloned:** functions, DOM nodes, `WeakMap`, `WeakSet`, `Error` objects (become plain objects), class instances (lose prototype).

### Transferable Objects (Zero-Copy)
Structured clone is still a copy operation. Passing a 32MB `ArrayBuffer` to a worker can cost up to hundreds of milliseconds. Transferable objects make data movement **zero-copy** by transferring ownership of the buffer from one context to another.

```javascript
// ❌ Structured clone: copies 32MB (slow)
worker.postMessage(arrayBuffer);

// ✅ Transferable: transfers ownership (zero-copy, fast)
worker.postMessage(arrayBuffer, [arrayBuffer]);
// After transfer, arrayBuffer.byteLength === 0 in the main thread
// The worker now owns the buffer
```

### The Benchmark
> "On a MacBook Pro, sending a 32MB `ArrayBuffer` to a worker and back took **302ms** (RTT) with structured clone. With transferables, the same test took **6.6ms**."

That's a **45× speedup**. For WebGL textures, mesh data, and large binary payloads, transferables are essential.

### Feature Detection
```javascript
const ab = new ArrayBuffer(1);
worker.postMessage(ab, [ab]);
if (ab.byteLength) {
  console.warn('Transferables are not supported in this browser!');
} else {
  // Transferables are supported.
}
```
If the buffer is transferred rather than copied, its `.byteLength` becomes 0.

---

### Deeper Explanation: Copy Or Move â€” Choose Deliberately

Structured clone copies a value graph between threads (or into IndexedDB). It preserves `Map`, `Set`, `Date`, `RegExp`, typed arrays, `Blob`, `File`, `Error`, and cyclic references â€” and drops functions, prototypes, and DOM nodes. Cost scales with the graph: cloning 10 MB takes milliseconds and temporarily doubles memory.

**Transferables** change the economics: the buffer is *moved*, the sender's view becomes unusable, and the cost is O(1) regardless of size. `ArrayBuffer`, `MessagePort`, `ReadableStream`/`WritableStream`, `ImageBitmap`, and `OffscreenCanvas` are transferable.

```ts
// Copy: 20 ms for 50 MB, 2x peak memory
worker.postMessage({ buffer: bigArrayBuffer });

// Move: O(1), sender's buffer is detached afterwards (byteLength === 0)
worker.postMessage({ buffer: bigArrayBuffer }, [bigArrayBuffer]);

// Shared: no copy and no move â€” both sides see the same memory
const sab = new SharedArrayBuffer(1024 * 1024 * 64);
worker.postMessage({ sab });
```

### Additional Pitfalls
- **A detached buffer used after transfer.** `byteLength` becomes 0 and every read throws or returns empty; transfer ownership deliberately.
- **Sending an `ImageData` instead of an `ImageBitmap`.** The latter is transferable and cheaper to draw.
- **Assuming cloning deep-copies everything cheaply.** Large graphs of small objects are the worst case per byte.
- **Transferring a stream you still need.** After transfer the original is locked; keep a `tee()`d branch if two consumers require it.
- **Serialising to JSON to "make it cloneable".** You pay double serialisation and lose types such as `Date` and typed arrays.

### Real-World Deal-Breakers
- **Passing a 100MB buffer without transferring** → hundreds of milliseconds of copying; UI freezes.
- **Using a transferred buffer in the main thread** → `byteLength === 0`; the buffer is detached. The main thread can no longer access it.
- **Trying to transfer non-transferable objects** → only `ArrayBuffer`, `MessagePort`, `ImageBitmap`, `OffscreenCanvas`, and a few others are transferable.
- **Cloning functions** → throws `DataCloneError`. Functions cannot be cloned.
