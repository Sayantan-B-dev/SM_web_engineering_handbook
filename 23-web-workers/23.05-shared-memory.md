### Lock-Free Ring Buffer
```javascript
// Shared ring buffer between main thread and worker
class RingBuffer {
  constructor(sab, capacity) {
    this.header = new Int32Array(sab, 0, 4); // [writePos, readPos, count, capacity]
    this.data = new Uint8Array(sab, 16, capacity);
    this.header[3] = capacity;
  }

  write(bytes) {
    const writePos = Atomics.load(this.header, 0);
    for (let i = 0; i < bytes.length; i++) {
      this.data[(writePos + i) % this.header[3]] = bytes[i];
    }
    Atomics.store(this.header, 0, (writePos + bytes.length) % this.header[3]);
    Atomics.add(this.header, 2, bytes.length);
    Atomics.notify(this.header, 2);
  }

  read(count) {
    while (Atomics.load(this.header, 2) < count) {
      Atomics.wait(this.header, 2, Atomics.load(this.header, 2));
    }
    const readPos = Atomics.load(this.header, 1);
    const bytes = new Uint8Array(count);
    for (let i = 0; i < count; i++) {
      bytes[i] = this.data[(readPos + i) % this.header[3]];
    }
    Atomics.store(this.header, 1, (readPos + count) % this.header[3]);
    Atomics.sub(this.header, 2, count);
    return bytes;
  }
}
```

### Deeper Explanation: Where Shared Memory Earns Its Risk

Shared memory is worth the complexity when the alternative (copying) dominates the runtime. That happens in three shapes:

| Shape | Example | Pattern |
|---|---|---|
| High-frequency numeric updates | Simulation, physics, audio DSP | One shared `Float64Array`, single writer, atomic frame flag |
| Large read-mostly datasets | Parsed index/catalogue | Write once at startup, read from many workers |
| Streaming buffers | WASM pipelines, video decode | Ring buffer with monotonic read/write indices |

Outside those, prefer transferables: no headers to configure, no races, no `Atomics` reasoning. And remember the price of admission â€” COOP/COEP headers, CORS-correct resources, and no third-party embeds that cannot send CORP headers. The last point alone makes shared memory a last resort for marketing-heavy sites.

### Additional Pitfalls
- **Ring buffers without wraparound discipline.** Overwriting unread data loses frames silently; the writer must respect the reader index.
- **Atomics used only for reads.** Writers must be atomic too, or reads race with writes.
- **Assuming ordering across threads.** Without `Atomics.notify`, nothing wakes a waiting consumer.
- **Forgetting the fallback.** Without isolation headers the whole path must degrade gracefully, usually to a worker with transferables.
- **Long-lived shared buffers growing unbounded.** They are fixed-size; plan the maximum frame count explicitly.

### Real-World Deal-Breakers
- **Shared memory without atomics** → data races. Concurrent writes are undefined behavior.
- **Forgetting memory barriers** → CPU reordering means a thread may see partial writes.
- **Using shared memory for low-frequency communication** → complexity without benefit. Use `postMessage` with transferables.
- **Assuming `SharedArrayBuffer` works without COOP/COEP** → throws in modern Chrome.
