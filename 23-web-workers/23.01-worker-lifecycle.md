## 23.2 Worker Lifecycle

### Subtopic Tree
- Creating a worker (`new Worker()`)
- Worker script execution
- Message event loop
- `worker.terminate()`
- `self.close()` (from inside the worker)
- `error` event
- `messageerror` event
- Reusing workers vs spawning per task
- Worker pool pattern

### Lifecycle Stages
```text
1. Main thread: new Worker('worker.js')
2. Browser fetches worker.js (network or cache)
3. Worker thread starts, evaluates worker.js
4. Worker enters message loop (waiting for postMessage)
5. Main thread: worker.postMessage(data)
6. Worker: self.onmessage fires, processes, self.postMessage(result)
7. Main thread: worker.onmessage fires
8. Termination:
   a. Main thread: worker.terminate()  ← immediate
   b. Worker: self.close()             ← graceful
   c. Tab closes                        ← automatic
```

### Creating and Terminating
```javascript
// Create
const worker = new Worker('worker.js', { type: 'module' }); // ESM worker

// Send data
worker.postMessage({ action: 'start', payload: [1, 2, 3] });

// Receive data
worker.onmessage = (e) => {
  console.log('Result:', e.data);
};

// Error handling
worker.onerror = (err) => {
  console.error('Worker error:', err.message, err.filename, err.lineno);
};

// Terminate (immediate, no cleanup)
worker.terminate();
```

### Worker Pool Pattern
Spawn overhead is ~0.5-1ms per worker. For many small tasks, a pool avoids repeated spawn cost.

```typescript
class WorkerPool {
  private workers: Worker[] = [];
  private queue: Array<{ data: any; resolve: (v: any) => void }> = [];
  private available: Worker[] = [];

  constructor(url: string, size: number) {
    for (let i = 0; i < size; i++) {
      const w = new Worker(url);
      w.onmessage = (e) => this.onWorkerDone(w, e.data);
      this.workers.push(w);
      this.available.push(w);
    }
  }

  private onWorkerDone(worker: Worker, result: any) {
    const next = this.queue.shift();
    if (next) {
      worker.postMessage(next.data);
      // Keep worker busy
      const originalResolve = next.resolve;
      worker.onmessage = (e) => {
        originalResolve(e.data);
        this.onWorkerDone(worker, null); // reuse
      };
    } else {
      this.available.push(worker);
    }
  }

  run(data: any): Promise<any> {
    return new Promise((resolve) => {
      const worker = this.available.pop();
      if (worker) {
        worker.postMessage(data);
        worker.onmessage = (e) => {
          resolve(e.data);
          this.available.push(worker);
        };
      } else {
        this.queue.push({ data, resolve });
      }
    });
  }
}
```

### Deeper Explanation: A Worker Is A State Machine You Must Drive

A dedicated worker has five states: constructing â†’ running â†’ (message loop) â†’ terminating â†’ terminated. Two of them are yours to manage:

- **Startup** â€” the worker is not ready to receive the first message until its script has evaluated. Messages posted before that are queued by the browser, so it is safe to `postMessage` immediately, but the *first job's latency* includes startup. Warm up long-lived workers once at idle with a no-op message so the cost lands off the critical path.
- **Termination** â€” a worker never stops on its own. An unused active worker keeps its memory and any WASM instance loaded, and a page that creates workers per route leaks one per navigation unless you `terminate()`.

For a shared worker, add "last client disconnects â†’ instance dies", and for a service worker, "browser decides to terminate". Both mean state you want to keep must live outside the worker's memory.

### Additional Pitfalls
- **Creating a worker per render or per route.** Each one costs startup and never gets collected while referenced.
- **Assuming state survives reloads or worker restarts.** Persist to IndexedDB; workers are stateless across lifetimes.
- **Never calling `terminate()`.** React StrictMode double-invocation in development makes this brutally visible; guard with cleanup.
- **Doing heavy work in a worker's top-level script.** It blocks the first message; do it lazily on demand.
- **Ignoring termination in tests.** Leftover workers keep the process alive and produce hanging test runs.

### Real-World Deal-Breakers
- **Spawning a worker per task** → 0.5-1ms overhead per spawn. Use a pool.
- **No `onerror` handler** → worker errors are silently swallowed.
- **`terminate()` without cleanup** → worker is killed mid-task; resources aren't released gracefully.
- **No `self.close()` in the worker** → worker stays alive after work is done; memory leak.
- **Reusing a terminated worker** → `postMessage` on a terminated worker silently does nothing.
