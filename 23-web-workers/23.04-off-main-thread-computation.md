### The Main Thread Problem
The browser uses a single thread to run all the JavaScript in a web page, as well as to perform tasks like rendering the page and performing garbage collection. Running excessive JavaScript code can block the main thread, delaying the browser from performing these tasks and leading to a poor user experience.

### Long Tasks
The Long Tasks API lets you monitor tasks that occupy the main thread for **50 milliseconds or more**. Long tasks cause responsiveness problems: if a user tries to interact with a page but the main thread is busy with a long task, the user interaction is delayed.

### OffscreenCanvas
`OffscreenCanvas` allows rendering tasks like animations and charts to be moved off the main thread, which helps maintain smooth performance even when the main thread is busy. This is particularly useful for real-time visualizations and complex animations.

```javascript
// main.js - transfer canvas to worker
const canvas = document.getElementById('chart');
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ type: 'INIT', canvas: offscreen }, [offscreen]);

// worker.js
self.onmessage = (e) => {
  if (e.data.type === 'INIT') {
    const canvas = e.data.canvas;
    const ctx = canvas.getContext('2d');
    renderChart(ctx);
  }
};
```

### Deeper Explanation: Architect For The Main Thread's Interactivity

The main thread's only job is to stay interactive. Everything else is a candidate for elsewhere. A design pattern that scales is the **compute pipeline**: main thread owns the UI and the source of truth for interaction state, a worker owns the expensive derivation, and results flow back as immutable snapshots.

```ts
// worker.ts â€” one job type per message, results streamed back as they complete
import { parseLog, analyse } from './lib';

self.onmessage = ({ data }: MessageEvent<{ id: number; text: string }>) => {
  const entries = parseLog(data.text);          // 40 ms of parsing
  const summary = analyse(entries);             // 60 ms of aggregation
  self.postMessage({ id: data.id, summary });   // one cheap message out
};
```

```ts
// main.ts â€” request/response with cancellation and stale-response protection
const worker = new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' });
const pending = new Map<number, (s: Summary) => void>();
let seq = 0;

worker.onmessage = ({ data }) => {
  pending.get(data.id)?.(data.summary);
  pending.delete(data.id);
};

export function analyseLog(text: string): Promise<Summary> {
  const id = ++seq;
  return new Promise((resolve) => {
    pending.set(id, resolve);
    worker.postMessage({ id, text });
  });
}
```

Beyond workers, the same principle applies inside the browser: `OffscreenCanvas` for rendering, `WebGPU`/WASM for number crunching, and IndexedDB for IO.

### Additional Pitfalls
- **Two sources of truth.** If both threads mutate the same logical state, you have built a distributed system without consensus; keep mutation on one side.
- **No cancellation.** A stale job's result can overwrite a newer one; sequence numbers or `AbortSignal` are mandatory.
- **Blocking the worker with a long synchronous import.** Top-level work delays the first response; do it lazily.
- **Pooling one worker for heterogeneous jobs.** A 2 s job blocks a 5 ms one; use a pool sized to `navigator.hardwareConcurrency - 1`.
- **No fallback.** Some environments restrict workers; keep a synchronous path for small inputs.

### Real-World Deal-Breakers
- **Heavy work on the main thread** → blocks rendering, input, and GC. Move to a worker.
- **Animating on the main thread** → use OffscreenCanvas + a worker, or `transform`/`opacity` (compositor thread).
- **No offloading for image processing** → a single 4000×3000 image filter can block for 2+ seconds.
- **OffscreenCanvas not supported everywhere** → Safari support is recent; check compatibility.
