### What SharedArrayBuffer Is
`SharedArrayBuffer` allows **shared memory** between the main thread and workers. Unlike `ArrayBuffer`, which is copied or transferred, `SharedArrayBuffer` memory is accessible from both threads simultaneously. Writes from one thread are visible to the other.

```javascript
// main.js
const sab = new SharedArrayBuffer(1024);
const view = new Int32Array(sab);
worker.postMessage(sab); // shared, not copied

Atomics.store(view, 0, 42); // write from main thread
Atomics.notify(view, 0);    // wake up worker
```

```javascript
// worker.js
self.onmessage = (e) => {
  const view = new Int32Array(e.data);
  Atomics.wait(view, 0, 0); // block until value changes
  const value = Atomics.load(view, 0); // 42
};
```

### Cross-Origin Isolation (Required)
`SharedArrayBuffer` usage is **restricted to cross-origin isolated sites** because shared memory can be used to construct high-resolution timers, which simplify Spectre attacks on cross-origin resources. Starting with Chrome 91 (May 2021), `SharedArrayBuffer` is gated behind cross-origin isolated contexts.

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

These headers block loading cross-origin resources unless they explicitly opt in via CORS or CORP.

### `Atomics` for Synchronization
`Atomics` provides atomic operations on `SharedArrayBuffer` memory:
- `Atomics.load(ta, index)` - read a value.
- `Atomics.store(ta, index, value)` - write a value.
- `Atomics.add(ta, index, value)` - atomic increment.
- `Atomics.wait(ta, index, value)` - block until notified.
- `Atomics.notify(ta, index, count)` - wake up waiters.
- `Atomics.compareExchange(ta, index, expected, replacement)` - CAS.

---

### Deeper Explanation: Shared Memory Is A Contract, Not A Feature

`SharedArrayBuffer` gives two threads the same bytes with no copying, which is why it unlocks real parallel algorithms (and WASM threads). It also requires **cross-origin isolation** (`COOP: same-origin` + `COEP: require-corp` or `credentialless`) because shared memory plus a precise timer would otherwise leak data across origins.

Three things follow from shared memory:

- **Synchronisation is manual.** `Atomics.load`/`store`/`add` are atomic operations, and `Atomics.wait`/`notify` are the blocking/notifying primitives â€” available in workers, not on the main thread.
- **Torn reads are a real bug class.** Without `Atomics` you can read half of a value written by another thread.
- **Data races are your problem now.** The careful design pattern is single-writer per region plus atomic flags, or a lock-free ring buffer with monotonic indices.

### Additional Pitfalls
- **Forgetting the isolation headers.** `SharedArrayBuffer` is simply undefined without them â€” and each embedded resource must be CORS-correct.
- **Mixing atomic and non-atomic access.** One plain write next to atomic reads is still a race.
- **`Atomics.wait` on the main thread.** It throws; only workers may block.
- **Growing a shared buffer.** It is fixed size at creation; size it for the worst case or use double buffering.
- **Using SAB when transferables suffice.** If each job owns its data, transferring is simpler and safer than sharing.

### Real-World Deal-Breakers
- **`SharedArrayBuffer` without COOP/COEP** → throws in Chrome 91+. Always check `crossOriginIsolated` before using.
- **No `Atomics` for synchronization** → data races. Without atomics, concurrent writes are undefined behavior.
- **Using `SharedArrayBuffer` when transferables suffice** → complexity without benefit. Transferables are simpler for one-directional data.
- **Assuming `SharedArrayBuffer` works everywhere** → requires cross-origin isolation, which breaks third-party iframes and scripts that don't opt in.
