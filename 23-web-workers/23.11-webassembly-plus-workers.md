### Loading WASM in a Worker
```javascript
// worker.js
let wasm;

async function initWasm() {
  const response = await fetch('module.wasm');
  const { instance } = await WebAssembly.instantiateStreaming(response);
  wasm = instance.exports;
}

self.onmessage = async (e) => {
  if (!wasm) await initWasm();
  const result = wasm.process(e.data.input, e.data.input.length);
  self.postMessage(result);
};
```

### WASM + SharedArrayBuffer
WASM memory can be backed by a `SharedArrayBuffer`, enabling zero-copy sharing between the main thread and workers.

```javascript
const memory = new WebAssembly.Memory({
  initial: 256,
  maximum: 256,
  shared: true, // requires cross-origin isolation
});

worker.postMessage(memory); // shared memory
```

---

### Deeper Explanation: WASM Inside A Worker Is The Real Compute Story

WASM on the main thread is a faster interpreter; WASM in a worker is actual parallel compute. Combining them gives you near-native throughput without touching the UI thread, which is why codecs, image pipelines, parsers, and ML runtimes all ship that way. The pattern:

1. Instantiate the module **inside the worker** (compilation is the slow part â€” cache the compiled module with `WebAssembly.compileStreaming` plus IndexedDB or the browser's own code cache).
2. Keep the module's memory in the worker and transfer results out (`ArrayBuffer` transfer) rather than returning views into live WASM memory.
3. For threads, enable WASM threads and create a `SharedArrayBuffer`-backed memory so wasm-bindgen's threads can spawn real parallel instances (requires cross-origin isolation).
4. For very large jobs, stream work in chunks and post progress so the UI can show it.

### Extended Example: Image Pipeline In A Worker

```ts
// worker.ts
import init, { resize_rgba } from './pkg/image_wasm.js';

let ready: Promise<void> | undefined;
const ensure = () => (ready ??= init());   // instantiate once per worker

self.onmessage = async ({ data }: MessageEvent<{ id: number; pixels: Uint8ClampedArray; w: number; h: number; tw: number; th: number }>) => {
  await ensure();
  const out = resize_rgba(data.pixels, data.w, data.h, data.tw, data.th); // returns Uint8ClampedArray
  const buffer = out.buffer as ArrayBuffer;
  self.postMessage({ id: data.id, buffer, width: data.tw, height: data.th }, [buffer]); // transfer, not copy
};
```

### Additional Pitfalls
- **Instantiation per job.** Compilation is 50-500 ms; instantiate once per worker and reuse.
- **Returning views into WASM memory.** The next call overwrites them; copy or transfer out.
- **Assuming WASM memory grows freely.** Growing a memory can detach existing views; pre-size or re-acquire views.
- **Skipping the isolation headers for threads.** Threads need `SharedArrayBuffer`, which needs COOP/COEP.
- **No bundler support plan.** Loading `.wasm` needs explicit asset handling (Vite `?url`, webpack `asyncWebAssembly`).

### Real-World Deal-Breakers
- **WASM without workers** → WASM still blocks the main thread. Run it in a worker.
- **`WebAssembly.instantiateStreaming` with wrong MIME type** → fails. Server must serve `application/wasm`.
- **Shared WASM memory without COOP/COEP** → `shared: true` throws.
