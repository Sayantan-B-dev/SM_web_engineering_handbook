### Profiling in Chrome DevTools
You can navigate to the Performance tab to understand where CPU time is spent in your Worker. Profiling in DevTools can help you identify and fix code that uses too much CPU.

```text
Chrome DevTools → Performance tab → Record → Interact → Stop
→ Look for "Worker" track alongside "Main" track
→ Worker tasks are shown as "Task" entries on the worker thread
→ Long worker tasks still block the worker, but not the main thread
```

### `navigator.hardwareConcurrency`
```javascript
const cores = navigator.hardwareConcurrency || 4;
const poolSize = Math.max(1, cores - 1); // leave one core for the main thread
```
`navigator.hardwareConcurrency` is a **hint** about concurrency, not a promise that the page can run that many tasks at once.

### Deeper Explanation: Measure Across The Boundary

Worker performance has two halves and both must be measured: **time on the worker** (the work you moved) and **time on the main thread** (clone cost, message handling, result application). The second half is the one people forget, and it is where offloading sometimes makes things worse.

A practical measurement loop:

1. Trace the main thread and confirm the long task disappeared. If a long task remains, the cost moved rather than vanished.
2. Time the clone explicitly: `performance.measure` around `postMessage` with a large payload.
3. Check memory in the DevTools memory panel â€” workers with WASM modules and caches hold tens of MB each.
4. Check the worker's own timeline (DevTools shows each worker as a separate thread) for serialisation stalls and GC.
5. Test on a mid-tier device; worker startup is proportionally more expensive there.

Budget rule: offload when `work > 20 ms` and the payload is under a few MB, or when the payload can be **transferred** rather than copied. Otherwise keep it on the main thread and chunk it.

### Additional Pitfalls
- **Measuring only the worker side.** The clone and the result application are main-thread costs that flake your INP.
- **Assuming N workers gives NÃ- speedup.** Startup, cloning, and memory bandwidth cap the gain; measure the pool size that actually helps.
- **Ignoring cold start.** The first job pays parse plus compile; warm workers during idle time.
- **Leaving instrumentation in production unconditionally.** Worker timing logs are high-volume; sample them.
- **Not cleaning up in tests.** Orphaned workers hang test runners and hide leaks until CI timeouts.

### Real-World Deal-Breakers
- **Not profiling workers** → you don't know if the worker is the bottleneck or the main thread.
- **Pool size = hardwareConcurrency** → oversubscription; the main thread starves. Leave one core free.
- **No long-task detection in workers** → workers can also have long tasks; they block worker responsiveness.
- **Assuming workers are always faster** → for small tasks, spawn + message overhead makes workers slower.
