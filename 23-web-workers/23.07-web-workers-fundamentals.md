### The Core Mental Model
A Web Worker is an **entire JavaScript scope running on a separate thread, without any shared memory** by default. The browser uses a single thread - the main thread - to run all JavaScript, render the page, and perform garbage collection. Running excessive JavaScript blocks the main thread, delaying rendering and causing a poor user experience. Web Workers move computation off the main thread entirely.

```text
Main thread:  UI events, DOM, style, layout, paint, GC, and... your JS
              │
              ├── postMessage() ──► Worker thread: your JS (no DOM)
              │                      │
              ◄── postMessage() ─────┘

Data is COPIED between threads by default (structured clone).
```

### What Workers CAN Do
- **Compute** - run CPU-intensive calculations.
- **Fetch** - make network requests independently.
- **IndexedDB** - access browser storage.
- **WebAssembly** - run WASM modules for max performance.
- **postMessage** - communicate with the main thread.
- **importScripts** - load additional JavaScript files.

### What Workers CANNOT Do
- **DOM** - access or manipulate the DOM.
- **window** - access the `window` object or globals.
- **localStorage** - use `localStorage` (use IndexedDB instead).
- **React** - use React components or hooks directly.

### Performance Characteristics
- **Spawn overhead** - ~0.5-1ms to spawn a worker.
- **Message latency** - ~0.1-0.3ms for `postMessage`.
- **Memory** - separate heap, typically 10-50MB baseline.
- **Concurrency** - true parallel execution on multi-core CPUs.

---

### Deeper Explanation: The Boundary Is The Cost

Web Workers give you a second JS thread with no DOM, reached by message passing. The performance question is never "is the worker fast?" â€” it is **whether the offloaded work costs more than the round trip**. Three numbers frame every decision:

- **Startup**: 5-50 ms per worker (parse + instantiate), more for module workers and WASM.
- **Message**: structured clone is proportional to payload size â€” roughly 1 MB per 1-3 ms, and it happens *on the sending thread*.
- **Latency**: a round trip is at least two task boundaries (post â†’ receive â†’ post back), typically 1-5 ms.

So the profitable pattern is **coarse-grained jobs**: one message in, one message out, kilobytes to megabytes of work per message. Offloading a 0.6 ms computation costs more than it saves; offloading a 60 ms parse that would drop three frames is a huge win.

### Additional Pitfalls
- **Chatty messaging.** Thousands of small messages per second cost more main-thread time than the work being offloaded.
- **Structured-clone-heavy payloads.** Cloning a 50 MB object graph per message both costs time and doubles peak memory.
- **A single worker for everything.** One long job blocks every other job and every queued message; pool by concern.
- **No error path.** An exception in the worker is silent without `onerror`/`onmessageerror` handlers that report it.
- **Assuming DOM access.** `document` and `window` do not exist; anything visual must return to the main thread first.

### Real-World Deal-Breakers
- **Trying to access the DOM in a worker** → `document` is `undefined`. Workers have no DOM.
- **Trying to use `localStorage`** → not available in workers. Use IndexedDB.
- **Passing massive objects repeatedly** → serialization cost dominates. Use Transferable Objects.
- **Spawning a worker for every task** → spawn overhead (0.5-1ms) adds up. Reuse workers.
- **Forgetting to terminate workers** → memory leaks and CPU waste.
