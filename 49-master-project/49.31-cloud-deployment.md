### A Realistic Topology

```text
                 ┌──────────────────────────────┐
   users ──────► │ CDN + edge cache             │
                 └───────────────┬──────────────┘
                                 │
                 ┌───────────────▼──────────────┐
                 │ Next.js app (serverless)     │  reads, server actions,
                 │  - RSC, actions, AI routes   │  SSE
                 └───────┬──────────────┬───────┘
                         │              │
        ┌────────────────▼──┐   ┌───────▼─────────────┐
        │ Managed Postgres  │   │ Managed Redis       │
        │ (pooled)          │   │ cache/sessions/fan  │
        └───────────────────┘   └───────┬─────────────┘
                                        │ Pub/Sub
                                ┌───────▼─────────────┐
                                │ Sync servers (ws)    │  long-lived containers,
                                │ 2+ replicas, sticky  │  autoscaled on connections
                                └──────────────────────┘
```

The split is forced by the runtime: serverless functions cannot hold sockets, so realtime runs on its own long-lived service. Plan for this on day one; retrofitting it later invalidates the auth path (49.18).

### Connection Pooling

```typescript
import { Pool } from 'pg';
import { attachDatabasePool } from '@vercel/functions';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 5,                          // per function instance, not per region
  idleTimeoutMillis: 10_000,
  connectionTimeoutMillis: 5_000,
});

// Tell the platform to release idle connections before the function freezes
attachDatabasePool(pool);
```

Without a pooler in front of Postgres, 200 concurrent functions each opening a pool exhaust the server's connection limit and every request starts failing - typically right after a traffic spike, which is the worst possible moment.

### Environments And Promotion

```bash
# Build once, tag by SHA, promote the same digest forward
docker build -t registry/atlas-sync:$GITHUB_SHA .
docker push registry/atlas-sync:$GITHUB_SHA

# staging
flyctl deploy --image registry/atlas-sync:$GITHUB_SHA --app atlas-sync-staging
# production (same digest, after staging smoke tests)
flyctl deploy --image registry/atlas-sync:$GITHUB_SHA --app atlas-sync-prod
```

Promoting a digest rather than rebuilding is what makes "it passed in staging" a meaningful statement.

### Zero-Downtime WebSocket Deploys

```text
1. Start new instances (v2) alongside old (v1)
2. Readiness probe passes -> new instances accept NEW connections
3. Old instances stop accepting new connections (drain)
4. Old instances close sockets gracefully: send "server_restarting", let clients reconnect
5. After the drain window, terminate old instances
```

```typescript
// Graceful client handling: reconnect fast when told to, so users barely notice
ws.send(JSON.stringify({ v: 1, t: 'error', code: 'SERVER_RESTART' }));
setTimeout(() => ws.close(1001, 'deploy'), 800);      // let the client reconnect first
```

Without this, a deploy drops every socket at once and the whole user base reconnects simultaneously into a stampede.

### Cost Model

| Component | Cost driver | Lever |
|---|---|---|
| Serverless app | invocations + duration | reduce client JS, cache reads |
| Postgres | compute + storage + connections | pooling, indexes, retention |
| Redis | memory | TTLs, avoid storing blobs |
| Sync servers | time + memory per connection | connection reuse, multiplexing |
| AI | tokens | rate limits, caching, budget caps |
| Storage/egress | GB stored + served | compression, CDN, signed URLs |

The two lines that surprise teams are **sync server memory** (autoscaling on connections, not CPU) and **AI tokens** (which scale with user enthusiasm, not users).

### Deeper Explanation: Deployability Is A Design Property

A system is production-ready when a routine change can be shipped on a Friday afternoon without fear. That property does not come from the platform; it comes from the design: stateless request handling, graceful shutdown, expand-contract migrations, drains on deploy, and rollback by digest.

Every one of those is a decision made in the code, not in a console. Teams that choose a platform first and design later end up with a system that can only be released by the person who built it.

### Additional Pitfalls

- **No connection pooler.** Serverless concurrency exhausts Postgres connections under exactly the load you want.
- **Single-region with a global audience.** 300ms round trips to every user outside that region; fix with edge reads or replicas.
- **Autoscaling the sync tier on CPU.** WebSocket servers are memory- and connection-bound; scale on connection count.
- **Backups without a restore drill.** An untested restore is an assumption, and it is usually wrong the first time.
- **No data-residency plan.** Enterprise deals stall when you cannot answer where the data lives.

### Real-World Deal-Breakers
- **Deploying the socket server to a serverless platform** - the core realtime feature works locally and never in production.
- **No graceful drain** - every deploy is a global disconnect storm and users lose in-flight input.
- **Unpooled database connections** - an outage under load, precisely when uptime matters most.
- **No rollback path** - a bad deploy is fixed by forward-fixing under pressure, in production.
- **Untested backups** - RPO/RTO are fiction until a restore has succeeded against real data.
