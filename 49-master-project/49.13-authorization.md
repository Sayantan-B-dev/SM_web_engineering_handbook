### Model The Hierarchy Explicitly

Permissions in Atlas resolve along a path. A user's ability to edit a block depends on the block's document, the document's workspace and their membership in it:

```typescript
export type Role = 'owner' | 'admin' | 'editor' | 'viewer';

const RANK: Record<Role, number> = { owner: 40, admin: 30, editor: 20, viewer: 10 };

export type Action =
  | 'document:read' | 'document:write' | 'document:delete'
  | 'membership:invite' | 'membership:remove'
  | 'workspace:delete' | 'billing:manage';

const MATRIX: Record<Action, Role> = {
  'document:read': 'viewer',
  'document:write': 'editor',
  'document:delete': 'admin',
  'membership:invite': 'admin',
  'membership:remove': 'admin',
  'workspace:delete': 'owner',
  'billing:manage': 'owner',
};

export function roleCan(role: Role, action: Action): boolean {
  return RANK[role] >= RANK[MATRIX[action]];
}
```

One table, one comparison. Adding an action forces a decision about its minimum role, and there is exactly one place to audit.

### Check In One Function, Call It Everywhere

```typescript
export async function authorize(
  action: Action,
  resource: { workspaceId: string; documentId?: string },
  userId: string,
): Promise<Result<Role>> {
  const membership = await db.memberships.find(resource.workspaceId, userId);
  if (!membership) return { ok: false, error: { code: 'FORBIDDEN', action } };

  if (resource.documentId) {
    const doc = await db.documents.find(resource.documentId);
    // A document ID from another workspace must never be reachable
    if (!doc || doc.workspaceId !== resource.workspaceId) {
      return { ok: false, error: { code: 'NOT_FOUND', resource: 'document' } };
    }
    // Per-document share grants can raise, never lower, the workspace role
    const grant = await db.documentGrants.find(resource.documentId, userId);
    const effective = maxRole(membership.role, grant?.role);
    return roleCan(effective, action)
      ? { ok: true, value: effective }
      : { ok: false, error: { code: 'FORBIDDEN', action } };
  }

  return roleCan(membership.role, action)
    ? { ok: true, value: membership.role }
    : { ok: false, error: { code: 'FORBIDDEN', action } };
}
```

Return `NOT_FOUND` rather than `FORBIDDEN` when the resource belongs to another tenant. `FORBIDDEN` confirms the ID exists, which is an enumeration leak.

### Three Enforcement Points, One Policy

| Layer | Purpose | Why it is not enough alone |
|---|---|---|
| Server function / action | the real gate | a missed call site is a hole |
| Postgres RLS | defence in depth | a missing `where` cannot leak |
| UI | user experience | hides what would fail anyway |

The UI's job is to not show a Delete button that will 403. Its job is **not** to secure anything: `curl` ignores your JSX.

```tsx
// UI: hide, do not rely on
{roleCan(role, 'document:delete') && <DeleteDocumentButton id={doc.id} />}
```

```typescript
// Server: the gate, always re-checked
'use server';
export async function deleteDocument(input: { documentId: string; workspaceId: string }) {
  const session = await requireSession();
  const auth = await authorize('document:delete', input, session.userId);
  if (!auth.ok) return auth;                       // no data, no side effect

  await db.documents.softDelete(input.documentId);
  await audit({ actor: session.userId, action: 'document:delete', target: input.documentId });
  revalidateTag(`doc:${input.documentId}`);
  return { ok: true as const, value: undefined };
}
```

### Deeper Explanation: The IDOR Bug Is Always The Same Bug

Almost every serious authorisation incident in a multi-tenant SaaS is one shape: **the code trusts an identifier that came from the client** without re-resolving it against the caller's rights.

`PATCH /api/documents/9f2c...` where the handler reads the row by ID and writes it. The caller changed the ID. Nothing checked that the caller belongs to that workspace.

The structural fix is not more careful code - it is to make the *shape* of the code force the check. Every handler in Atlas receives `(input, session)` and its first line is `authorize(...)`. A code review rule can then be as blunt as: *"no database write before an authorize call in the same function"*. That is enforceable, greppable, and it survives staff turnover.

### Additional Pitfalls

- **Authorising in middleware only.** Middleware cannot know which document ID is being mutated inside the body.
- **Role from the client.** A hidden input with `role=admin`, or a JWT claim the client can influence, is a privilege escalation.
- **Conflating "not found" and "forbidden"** in the response, leaking existence of other tenants' records.
- **Permission checks per-endpoint with copy-pasted logic.** They drift; one stale copy is a hole.
- **No audit log on privilege changes.** You cannot investigate an incident without a record of who granted what, when.

### Real-World Deal-Breakers
- **Trusting a client-supplied `workspaceId`/`documentId`** - the classic cross-tenant read and write.
- **UI-only permission checks** - anyone with devtools or `curl` bypasses them immediately.
- **Role escalation through a mass-assignment update** - `update(user, req.body)` lets a user set `role: 'owner'`.
- **No RLS and no tenant predicate** - a single forgotten `where` becomes a customer-visible data breach.
- **Stale cached permissions** - a removed member keeps editing for the cache TTL; revocation must invalidate immediately.
- **Invite links with no expiry or single-use** - a leaked link grants permanent access to the workspace.
