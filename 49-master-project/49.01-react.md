### How It Fits The Master Project

Atlas is a collaborative document workspace: multiple people edit the same page at the same time, an AI assistant can draft and summarise inside the document, and the whole thing keeps working on a plane with no Wi-Fi. Every later file in this chapter - TypeScript, Next.js, Postgres, WebSockets, CRDTs, offline-first, observability - plugs into the component tree you design here.

The mistake almost every junior makes is treating React as "the framework". React is the **rendering layer**. Your architecture is the shape of your data, your boundaries, and your component contracts. React just draws it.

### Component Taxonomy

Decide which of the four kinds a component is before you write it. Mixing them is the single largest source of "why is this file 900 lines" pain.

```tsx
// 1. Shell - never re-renders, owns no data, composes the frame
export function AppShell({ children }: { children: React.ReactNode }) {
  return (
    <div className="grid h-dvh grid-cols-[260px_1fr]">
      <Sidebar />
      <main className="overflow-y-auto">{children}</main>
    </div>
  );
}

// 2. Route - one per URL segment, fetches at the boundary, streams
export default async function DocumentPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;                 // React 19: params is a Promise
  const doc = await getDocument(id);            // server-side, no waterfall
  return (
    <Suspense fallback={<EditorSkeleton />}>
      <Editor documentId={doc.id} initialContent={doc.content} />
    </Suspense>
  );
}

// 3. Feature - owns behaviour, may be a client island
'use client';
export function Editor({ documentId, initialContent }: EditorProps) {
  const { content, applyRemote } = useYjsDocument(documentId, initialContent);
  const { status } = useSyncStatus();
  return (
    <>
      <Toolbar status={status} />
      <TextSurface value={content} onChange={applyRemote} />
    </>
  );
}

// 4. Primitive - dumb, reusable, no domain knowledge
export function IconButton({ label, onClick, children }: IconButtonProps) {
  return (
    <button aria-label={label} onClick={onClick} className="rounded p-1.5 hover:bg-accent">
      {children}
    </button>
  );
}
```

### Server-First Composition

React 19 with Next.js App Router inverts the default: components are **server components** unless marked `'use client'`. That is the correct default for Atlas, because most of a document workspace is read-heavy and SEO/load-time sensitive.

```tsx
// Server: zero JS shipped for the sidebar
async function Sidebar() {
  const pages = await listPages();              // direct DB call, no API hop
  return (
    <nav>
      {pages.map((p) => (
        <Link key={p.id} href={`/doc/${p.id}`}>{p.title}</Link>
      ))}
    </nav>
  );
}
```

Push `'use client'` as far down the tree as it will go. A common junior pattern is marking the page client so one button can call `onClick`. Instead, isolate the interactivity:

```tsx
// Server page (stays a server component)
export default async function Page() {
  const [doc, user] = await Promise.all([getDocument(id), getUser()]);
  return (
    <article>
      <Prose content={doc.content} />
      <ShareButton documentId={doc.id} />   {/* tiny client island */}
      <Avatar user={user} />
    </article>
  );
}
```

The rule: **a component only becomes a client component if it needs state, an effect, an event handler, or a browser API.** Everything else stays on the server and ships zero JavaScript.

### State Ownership

Before writing a component, answer: *who owns this state, and who is allowed to change it?* Get this wrong and you will reach for a global store to patch a design mistake.

| State | Owner | Tool |
|---|---|---|
| Document content | Document session | Yjs CRDT (see 49.22) |
| Server data (pages, users) | Query cache | TanStack Query (49.09) |
| UI state (open panel, hover) | Nearest common parent | `useState` |
| Session identity | Root provider | Auth context (49.12) |
| Sync status | Sync layer | External store + `useSyncExternalStore` |

```tsx
// UI state stays local. Do not put "is this popover open" in Redux.
function ShareMenu() {
  const [open, setOpen] = useState(false);
  return (
    <Popover open={open} onOpenChange={setOpen}>
      <PopoverTrigger asChild><IconButton label="Share"><Share /></IconButton></PopoverTrigger>
      <PopoverContent>{open && <ShareForm />}</PopoverContent>
    </Popover>
  );
}
```

### Deeper Explanation: Rendering Cost Is A Product Constraint

In a collaborative editor, every keystroke is a render. A naive controlled `textarea` that lifts content into React state at the page level re-renders the sidebar, the toolbar, the avatar list and the comment thread on every character typed. On a 3,000-word document on a mid-range Android phone that is visible lag.

React 19 gives you three tools and you should use all three:

1. **Controlled at the leaves.** The text surface manages its own text; only *committed* changes (debounced or on blur) travel upward.
2. **`useTransition`** for anything that changes a large tree as a consequence of a cheap input (filtering a page list, switching documents).
3. **The React Compiler** (49.06) so you stop hand-writing `useMemo`/`useCallback` for correctness.

```tsx
function DocumentFilter({ pages }: { pages: Page[] }) {
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();
  const [visible, setVisible] = useState(pages);

  function onSearch(value: string) {
    setQuery(value);                                  // urgent: keep the input responsive
    startTransition(() => {                            // non-urgent: recompute the list
      setVisible(pages.filter((p) => p.title.toLowerCase().includes(value.toLowerCase())));
    });
  }

  return (
    <>
      <SearchInput value={query} onChange={onSearch} />
      {isPending && <Shimmer />}
      <PageList pages={visible} />
    </>
  );
}
```

### Additional Pitfalls

- **`useEffect` for derived data.** If a value can be computed from props or state during render, compute it during render. An effect that mirrors state creates a render-then-correct flash and a second commit.
- **Keying lists by array index.** With collaborator cursors and inserts, index keys make React recycle the wrong DOM node and users see text jump between lines. Key by stable ID.
- **Context as a global store.** Every consumer of a context re-renders on any change to the value object. Split contexts by concern, or use an external store with `useSyncExternalStore`.
- **`useMemo` as a correctness tool.** Memoisation is a performance hint only. If removing it changes behaviour, your design is broken.
- **Fetching in a client component on mount.** That is a waterfall: HTML, then JS, then effect, then request, then paint. Fetch on the server where the data lives.

### Real-World Deal-Breakers
- **`'use client'` at the page root** - ships the whole tree to the browser and kills streaming. Push the boundary down.
- **State lifted too high** - every keystroke re-renders unrelated trees; the editor becomes unusable on mobile.
- **Index keys in a collaborative list** - collaborator inserts and deletes cause content to swap between rows.
- **No Suspense or error boundary per route segment** - one slow query blocks the entire page, and one throw blanks the app.
- **Storing server data in `useState`** - you now own cache invalidation by hand, and you will get it wrong. Use a query cache.
- **Components that fetch their own data deep in the tree** - N+1 waterfalls. Fetch at the route boundary, pass down.
