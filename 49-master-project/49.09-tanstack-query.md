## 49.9 TanStack Query

### Subtopic Tree
- Server state vs client state (the distinction that matters)
- `QueryClient` and provider setup on the client boundary
- Query keys as a cache schema, not ad-hoc strings
- `staleTime` vs `gcTime` (formerly `cacheTime`)
- Mutations, optimistic updates and rollback
- Invalidation strategy: precise tags, not `invalidateQueries()` wholesale
- Pagination and infinite queries for large document lists
- Prefetching for instant navigation
- Hydration/dehydration with server components
- Error and retry policy per query
- When *not* to use it (server components already fetched it)

### The Problem It Solves

Atlas has two kinds of state and they behave nothing alike:

| | Client state | Server state |
|---|---|---|
| Owner | the browser | the server |
| Truth | current | a snapshot, possibly stale |
| Examples | open panel, draft text | pages, users, permissions |
| Tooling | `useState`, URL | TanStack Query |

Copying server state into `useState` means you now own staleness, cache invalidation and refetching by hand. You will get it wrong. TanStack Query exists so you never write that code.

### Keys Are A Cache Schema

Treat query keys as an addressable hierarchy, so invalidation can be precise:

```typescript
export const qk = {
  workspaces: () => ['workspaces'] as const,
  workspace: (id: string) => ['workspaces', id] as const,
  documents: (workspaceId: string) => ['workspaces', workspaceId, 'documents'] as const,
  document: (id: string) => ['documents', id] as const,
  comments: (documentId: string) => ['documents', documentId, 'comments'] as const,
  permissions: (documentId: string) => ['documents', documentId, 'permissions'] as const,
};
```

With that shape, `queryClient.invalidateQueries({ queryKey: ['documents', id] })` invalidates every cached facet of that document, and nothing else.

### Cache Lifetime

```typescript
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,       // fresh for 30s: no refetch on remount
      gcTime: 5 * 60_000,      // keep unused cache 5 min (back/forward speed)
      refetchOnWindowFocus: true,
      retry: (failureCount, error) => {
        // Never retry auth or validation failures - they will not succeed
        if (isAuthError(error) || isValidationError(error)) return false;
        return failureCount < 2;
      },
      refetchOnReconnect: true, // offline-first: catch up after a plane (49.21)
    },
  },
});
```

Two traps here: a `staleTime` of `0` makes every mount hit the network, and infinite `retry` turns a 403 into a request loop.

### Optimistic Updates

In a collaborative app the optimistic path is the default user experience:

```typescript
function useRenameDocument() {
  const qc = useQueryClient();

  return useMutation({
    mutationFn: ({ id, title }: { id: string; title: string }) =>
      renameDocument({ id, title }),

    onMutate: async ({ id, title }) => {
      await qc.cancelQueries({ queryKey: qk.document(id) });   // stop in-flight overwrite
      const previous = qc.getQueryData(qk.document(id));

      qc.setQueryData(qk.document(id), (old: Doc | undefined) =>
        old ? { ...old, title } : old,
      );

      return { previous };                          // context for rollback
    },

    onError: (_err, { id }, context) => {
      qc.setQueryData(qk.document(id), context?.previous);   // rollback
      toast.error('Could not rename the document.');
    },

    onSettled: (_data, _err, { id }) => {
      qc.invalidateQueries({ queryKey: qk.document(id) });   // reconcile with truth
    },
  });
}
```

The three-part pattern - cancel, snapshot, restore on error - is the whole recipe. Skipping `cancelQueries` produces the classic bug where a slow in-flight GET overwrites your optimistic write.

### Hydration From The Server

When a server component already fetched the data, hand it to the query cache instead of refetching:

```tsx
// app/providers.tsx
'use client';
export function Providers({ children }: { children: React.ReactNode }) {
  const [client] = useState(() => new QueryClient({ defaultOptions: { /* ... */ } }));
  return <QueryClientProvider client={client}>{children}</QueryClientProvider>;
}
```

```tsx
// server component
const document = await getDocument(id);
return (
  <HydrationBoundary state={dehydrate(makeQueryClient(), { queries: [{ queryKey: qk.document(id), queryFn: () => document }] })}>
    <DocumentEditor id={id} />
  </HydrationBoundary>
);
```

Now the client's first render has data: no spinner, no waterfall.

### Deeper Explanation: The Boundary Between Cache And Source Of Truth

The subtlest architectural decision in Atlas is: **for the document body, TanStack Query is not the source of truth - the CRDT is** (49.22). Query owns everything *around* the document (metadata, permissions, comment counts, the page list). Yjs owns the text.

Getting that split wrong causes a very specific bug: the editor autosaves into the query cache, a collaborator's op arrives over the socket, both write to the same cache entry, and the two writers fight. Text flickers and eventually one side loses content.

So the rule is explicit in Atlas:

```text
TanStack Query  ->  page lists, metadata, permissions, comments, members
Yjs / CRDT      ->  the document body and collaborative cursors
WebSocket       ->  transport for CRDT updates and presence
```

Two writers, two mechanisms, one clear owner per piece of state.

### Additional Pitfalls

- **`useEffect` to sync query data into `useState`.** You have re-created the cache, badly. Derive from `data` during render.
- **Invalidating the entire cache after every mutation.** Everything refetches, the UI flickers, and the network graph looks like a DDoS.
- **Keys missing parameters.** `['document']` shared across all documents means every edit invalidates every page.
- **`enabled: false` forgotten on dependent queries.** The query fires with `undefined` ids and 404s.
- **Refetching on focus for a 10k-row list.** Bound the payload or paginate; otherwise a tab switch costs a megabyte.

### Real-World Deal-Breakers
- **Server state duplicated into `useState`** - stale data, manual invalidation bugs, and a cache that drifts from the database.
- **Mutating the CRDT through the query cache** - two writers on the same state; content flicker and data loss.
- **`invalidateQueries()` with no key** - thundering herd of refetches; the app appears to hang after every save.
- **Infinite retry on a 401/403** - a request loop that burns quota and delays the login redirect.
- **No `cancelQueries` before an optimistic write** - a slow in-flight response silently reverts the user's change.
