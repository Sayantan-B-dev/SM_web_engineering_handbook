## 49.3 Next.js

### Subtopic Tree
- App Router: the folder is the route
- Server components as the default, client islands as the exception
- Route segments and their special files (`page`, `layout`, `loading`, `error`, `not-found`)
- Server actions for mutations
- Route handlers for webhooks, sync and long-lived streams
- Middleware for auth, tenant routing and redirects
- Caching layers: request memoisation, data cache, full route cache
- `revalidatePath` / `revalidateTag` and cache invalidation strategy
- Dynamic vs static rendering per route
- Parallel routes for split-pane editor + sidebar
- Intercepting routes for in-app modals
- Streaming shells for a fast first paint
- Edge vs Node runtime per route

### Why Next.js In The Master Project

Atlas needs three things at once: fast server-rendered reads, secure server-side mutations, and a small JavaScript payload. Next.js App Router provides all three in one project, and - crucially - it puts the *network boundary* in the same place as the *component boundary*. That means you never wire up a REST API to talk to your own database.

### Layouts Are Persistent, Pages Are Not

A layout does not re-render when navigating between its children. Use that: the workspace sidebar keeps its scroll position, open folders and connection badge while the user moves between documents.

```tsx
// app/(app)/w/[workspaceId]/layout.tsx  - server component
export default async function WorkspaceLayout({
  children, params,
}: { children: React.ReactNode; params: Promise<{ workspaceId: string }> }) {
  const { workspaceId } = await params;
  const session = await requireSession();                       // redirects if absent
  const workspace = await getWorkspace(workspaceId, session.userId);
  if (!workspace) notFound();

  return (
    <div className="grid grid-cols-[260px_1fr] h-dvh">
      <WorkspaceSidebar workspace={workspace} />
      <section className="overflow-hidden">{children}</section>
    </div>
  );
}
```

### Server Actions For Every Mutation

There is no reason to hand-roll `fetch('/api/rename')` for a form in your own app. A server action is a typed function that runs on the server, and it composes with cache invalidation:

```tsx
// app/(app)/w/[workspaceId]/actions.ts
'use server';

import { revalidatePath, revalidateTag } from 'next/cache';

export async function renameDocument(input: { id: string; title: string }) {
  const session = await requireSession();
  const parsed = renameSchema.safeParse(input);
  if (!parsed.success) return { ok: false, error: parsed.error.flatten() };

  const allowed = await canEdit(parsed.data.id, session.userId);
  if (!allowed) return { ok: false, error: { formErrors: ['FORBIDDEN'] } };

  await db.update(parsed.data.id, { title: parsed.data.title });
  revalidateTag(`doc:${parsed.data.id}`);
  revalidatePath(`/w/${parsed.data.workspaceId}/doc/${parsed.data.id}`);
  return { ok: true };
}
```

Note the order: **re-check auth inside the action**. A server action is a public HTTP endpoint; the fact that it is called from your UI proves nothing.

### Route Handlers For Non-Form Traffic

Use route handlers for webhooks, file uploads, streaming responses and the sync upgrade. They are the only place where you control the raw `Request`/`Response`.

```typescript
// app/api/webhooks/stripe/route.ts
import { headers } from 'next/headers';

export async function POST(req: Request) {
  const body = await req.text();                       // raw text: signature needs exact bytes
  const sig = (await headers()).get('stripe-signature');
  if (!sig) return new Response('missing signature', { status: 400 });

  const event = verifyStripeSignature(body, sig, process.env.STRIPE_WEBHOOK_SECRET!);
  if (!event) return new Response('bad signature', { status: 400 });

  await handleStripeEvent(event);                      // idempotent by event.id
  return new Response(null, { status: 204 });
}

export const runtime = 'nodejs';                       // crypto + SDK need Node
```

### Caching: Know Which Layer You Are Fighting

| Layer | Lifetime | Cleared by |
|---|---|---|
| Request memoisation | one render pass | nothing (automatic) |
| Data cache | across requests | `revalidateTag`, `revalidatePath`, time |
| Full route cache | static routes | revalidation |
| Router cache (client) | session | `router.refresh()`, revalidation |
| CDN / `Cache-Control` | seconds to years | deploy, purge |

The junior failure mode is debugging the wrong layer. If a value is stale in the browser but fresh in `curl`, you are looking at the client router cache, not your database.

```tsx
// Explicit, tag-based fetching: one tag per entity, invalidated precisely
const doc = await fetch(`${API}/documents/${id}`, {
  next: { tags: [`doc:${id}`, 'documents'] },
});
```

### Deeper Explanation: Where The Boundary Lives

The App Router's real contribution is not routing - it is that it makes the client/server boundary *syntactic*. You write one tree; you mark the leaves that must run in the browser; the compiler enforces what may cross.

That enforcement is what keeps Atlas fast. Every `'use client'` you avoid is JavaScript not shipped, a hydration boundary not created, and a class of "works on my machine, blank page on the user's phone" bugs not written.

Two consequences worth internalising:

1. **Serialisation is the real boundary.** Server components can pass only serialisable props to client components. Passing a live database row is fine; passing a Drizzle query builder or a class instance is not.
2. **Auth is a re-check, not an inheritance.** Because server actions and route handlers are HTTP endpoints, every one of them re-authorises from the session cookie. Treating "the layout already checked" as sufficient is an IDOR vulnerability (49.13).

### Additional Pitfalls

- **`'use client'` in `layout.tsx`.** Kills server rendering for the entire subtree and disables streaming beneath it.
- **Fetching user data in middleware.** Middleware runs on every request including static assets and should stay tiny; do auth checks in the segment layout.
- **Reading `params` synchronously.** In App Router 15+, `params` is a Promise. `await` it, or props silently arrive undefined in client components.
- **Caching an authenticated response.** A cached page containing user A's data served to user B is the most severe bug in this chapter. Anything personalised must be dynamic or explicitly uncached.
- **`revalidatePath('/')` as a blunt instrument.** It nukes the whole route cache and hides a missing invalidation strategy; invalidate the narrowest tag that is correct.
- **Long-running work in a route handler.** Platform timeouts will kill it mid-flight. Enqueue a job (49.26).

### Real-World Deal-Breakers
- **No auth check inside server actions** - they are public endpoints; UI-only checks are trivially bypassed.
- **Caching personalised pages** - cross-user data leakage, the worst possible incident for a multi-tenant product.
- **Client components at the route root** - the whole page hydrates, TTI collapses, and streaming is dead.
- **Business logic in middleware** - it runs per request at the edge with a hostile timeout; DB queries there will fail unpredictably.
- **Skipping `error.tsx` per segment** - one bad document makes the entire workspace blank instead of one panel failing.
- **Doing the slow thing in `page.tsx` without `loading.tsx`** - no streamed shell, so the user stares at a white screen instead of the app frame.
