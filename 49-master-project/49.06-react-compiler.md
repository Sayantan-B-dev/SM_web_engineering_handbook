### The Idea

The React Compiler analyses your components at build time and inserts the memoisation that you used to write by hand. Dependencies are inferred, not declared, so the entire class of "I forgot to add `x` to the dep array" bugs disappears.

For Atlas it matters most in one place: **the editor re-renders on every keystroke while collaborators type**. Toolbars, presence bars and comment threads that previously re-rendered dozens of times per second now re-render only when their inputs actually change.

```tsx
// Before: manual memoisation, easy to get wrong
function PresenceBar({ peers, selfId }: Props) {
  const others = useMemo(() => peers.filter((p) => p.id !== selfId), [peers, selfId]);
  const label = useMemo(() => `${others.length} editing`, [others.length]);
  const handleClick = useCallback(() => scrollToFirstPeer(others[0]), [others]);
  return <div onClick={handleClick}>{label}</div>;
}

// After: write the straightforward version, the compiler memoises it
function PresenceBar({ peers, selfId }: Props) {
  const others = peers.filter((p) => p.id !== selfId);
  const label = `${others.length} editing`;
  const handleClick = () => scrollToFirstPeer(others[0]);
  return <div onClick={handleClick}>{label}</div>;
}
```

Same runtime performance as a correctly-memoised version, a fraction of the code, and none of the staleness risk.

### Setup

```bash
npm install -D babel-plugin-react-compiler
```

```js
// next.config.ts
const nextConfig = {
  experimental: {
    reactCompiler: true,     // or { compilationMode: 'annotation' } for opt-in
  },
};
export default nextConfig;
```

`annotation` mode only compiles components marked `'use memo'`, which is how you roll it out incrementally on a large codebase:

```tsx
export function ExpensiveTree({ items }: Props) {
  'use memo';
  // opt this component into compilation
}
```

### The Rules Of React Are Now Load-Breaking

The compiler can only optimise components that follow the rules. Violating them does not throw - it silently bails out of optimisation.

The four that break the compiler most often:

```tsx
// 1. Mutating props/state during render - BAILS OUT
function Bad({ items }: Props) {
  items.sort();                     // mutating a prop
  return <List items={items} />;
}
function Good({ items }: Props) {
  const sorted = [...items].sort();
  return <List items={sorted} />;
}

// 2. Mutating a value after it has been passed somewhere
const config = { theme };
writeToConfig(config);              // mutation -> bailout
render(<Panel config={config} />);

// 3. Conditional hooks
if (isEditing) { useState(0); }     // never legal, and it breaks compilation

// 4. Reading/writing refs during render
function Bad2() {
  const ref = useRef(0);
  ref.current++;                    // render side effect
  return <span>{ref.current}</span>;
}
```

Run the compiler-aware ESLint plugin (`eslint-plugin-react-hooks` with the compiler rules) so you learn about these before the build does:

```js
// eslint.config.js
export default [
  { rules: { 'react-hooks/react-compiler': 'error' } },
];
```

### Deeper Explanation: Optimise The Failure Model, Not Just The Speed

The compiler's real value in a collaborative app is **predictability**. Manual memoisation is a promise about values that a human maintains; every new prop is a chance to forget a dependency and ship a component that renders stale data.

A stale presence bar is a nasty bug: the user sees a collaborator who already left, keeps typing, and gets a conflict they cannot explain. The compiler removes that failure mode entirely, because dependencies are derived from the code, not from a human's memory.

The trade-off to be honest about: **compilation is not free**. Build times rise, and the generated code is harder to read in a debugger. For a 200-component project like Atlas that is a good trade; for a 20-component marketing site it is not worth the build cost.

### Additional Pitfalls

- **Expecting the compiler to fix a bad data flow.** It memoises pure functions. If your component fetches in `useEffect` on every render, it will faithfully memoise the bug.
- **Mixing compiler output with hand memoisation on the same component.** Double memoisation adds noise with no benefit; remove the manual hooks once compiled.
- **Assuming "no error" means "optimised".** You need build-time diagnostics to see bailouts. Wire them into CI.
- **Mutating class instances shared across renders.** The compiler assumes immutability; a mutable singleton defeats it and reintroduces staleness.
- **Compiling tests differently from production.** A bailout that only appears in one configuration yields "works in dev, slow in prod" mysteries.

### Real-World Deal-Breakers
- **Shipping manual memoisation *and* the compiler without measuring** - you pay build cost and carry code noise for zero gain.
- **Rule violations left in place** - the compiler silently bails out across the codebase; you believe you are optimised and you are not.
- **Compiler enabled without ESLint enforcement** - violations only surface as performance regressions in production.
- **Refactoring for the compiler instead of the reader** - the compiler serves the code, not the other way round.
- **Trusting memoisation over architecture** - a component re-rendering 10,000 children will still be slow; fix the tree, not the hook.
