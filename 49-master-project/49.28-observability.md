## 49.28 Observability

### Subtopic Tree
- The three pillars applied to a collaborative app
- Structured logs with correlation IDs across client, server and socket
- Metrics that matter: sync latency, merge conflicts, socket churn
- Distributed tracing across the editor, the API and the sync server
- Error monitoring with source maps and release tagging
- Core Web Vitals as product metrics
- SLOs for the features that define the product
- Alerting on symptoms, not causes
- PII redaction and privacy in telemetry
- Debugging a production incident with the data you have

### What To Instrument In Atlas

| Signal | Why it matters |
|---|---|
| Time to interactive editor | the product's first impression |
| Sync round-trip (op -> peer visible) | defines the "feels live" property |
| Merge conflict rate | quality of the CRDT and binding integration |
| Socket reconnect rate | network health and deploy quality |
| AI latency, token cost, error rate | cost control and trust |
| Auth failures by reason | security signal and UX friction |
| Client error rate by release | regressions per deploy |

### Structured Logs With Correlation

```typescript
import { randomUUID } from 'node:crypto';

export function withRequestLogging<T>(handler: (ctx: Ctx) => Promise<T>) {
  return async (req: Request): Promise<T> => {
    const requestId = req.headers.get('x-request-id') ?? randomUUID();
    const started = performance.now();
    const log = logger.child({ requestId, route: new URL(req.url).pathname });

    try {
      const result = await handler({ req, requestId, log });
      log.info({ ms: Math.round(performance.now() - started), status: 'ok' }, 'request');
      return result;
    } catch (err) {
      log.error({ ms: Math.round(performance.now() - started), err: serialiseError(err) }, 'request failed');
      throw err;
    }
  };
}
```

The client sends an `x-request-id` it generated, so the browser error, the server log and the trace share one identifier. Without that, correlating a user report to a backend event is archaeology.

```typescript
export function recordSyncLatency(ms: number, documentId: string) {
  histogram.record(ms, { documentId: hashForCardinality(documentId) });   // bound cardinality
```

Never use a raw document ID as a metric label: cardinality explodes and the metrics backend becomes the outage.

### Deeper Explanation: Measure The Product, Not The Server

A CPU graph at 30% tells you nothing about whether users are succeeding. The observability that changes decisions in Atlas measures *experiences*: how long until the editor is usable, how long until a collaborator sees a change, how often a save is rejected.

That shift - from resource metrics to user-journey metrics - is what distinguishes a dashboard someone looks at during an incident from a dashboard that tells you about a problem before a customer reports it.

### Additional Pitfalls

- **Logging the document body or user email.** Telemetry is not a database; it is replicated, retained and often unencrypted.
- **High-cardinality labels.** IDs in metric labels melt your metrics bill and drop data.
- **No source maps in production.** Every stack trace is minified and useless.
- **Alerting on every error.** Alarm fatigue makes the on-call engineer ignore the one that matters.
- **Sampling traces at 1% for a rare critical path.** The slow request you need is the one you did not keep.

### Real-World Deal-Breakers
- **No error monitoring with release tags** - you cannot tell whether a deploy caused the spike or ended it.
- **PII in logs** - document contents and emails in telemetry is a compliance incident waiting for an audit.
- **No sync-latency metric** - the product's defining quality degrades invisibly for months.
- **Alerting on causes (CPU) instead of symptoms (users cannot save)** - the page fires while the product is broken, and stays silent when it is not.
