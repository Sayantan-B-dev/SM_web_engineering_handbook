### Sessions, Not JWTs, For This App

Atlas is a first-party web app with a server-rendered UI. That means **server-side sessions in an `HttpOnly` cookie** are the better default: instant revocation, no token-in-JS exposure, and no need to invent refresh rotation.

Use JWTs only where a stateless third party must verify identity offline (a separate API, an edge worker, a webhook consumer). Do not use them just because a tutorial did.

```typescript
// Login: create a session row, then set an opaque cookie
import { cookies } from 'next/headers';
import { randomBytes, createHash } from 'node:crypto';

const SESSION_DAYS = 30;

export async function createSession(userId: string) {
  const token = randomBytes(32).toString('base64url');          // the secret
  const tokenHash = createHash('sha256').update(token).digest('hex');

  const expiresAt = new Date(Date.now() + SESSION_DAYS * 86_400_000);
  await db.insert(sessions).values({ userId, tokenHash, expiresAt });

  (await cookies()).set('__Host-atlas_session', token, {
    httpOnly: true,                 // JavaScript cannot read it: XSS cannot steal it
    secure: true,                   // HTTPS only
    sameSite: 'lax',                // blocks cross-site POST CSRF; allows top-level nav
    path: '/',
    expires: expiresAt,
  });

  return { token: token.slice(0, 8) + '...', expiresAt };        // never log the full token
}
```

**Store the hash, not the token.** A leaked database dump must not be a set of live sessions. `__Host-` forces `Secure`, `Path=/` and no `Domain`, which prevents a subdomain from overwriting the cookie.

### Password Hashing

```typescript
import { hash, verify, argon2id } from 'argon2';

const OPTS = { type: argon2id, memoryCost: 19456, timeCost: 2, parallelism: 1 };  // OWASP 2026

export const hashPassword = (plain: string) => hash(plain, OPTS);

export async function verifyPassword(stored: string, plain: string, userId: string) {
  const ok = await verify(stored, plain);
  if (!ok) await recordFailedAttempt(userId);      // for lockout + alerting
  return ok;
}
```

Never use `bcrypt` for new work (72-byte truncation, weak memory hardness), never `sha256(password)` in any form, and never a per-app global salt.

### Constant-Time Login And Enumeration

The response must be indistinguishable whether or not the account exists. Otherwise you have built a user-list oracle:

```typescript
export async function login(email: string, password: string) {
  const user = await db.users.byEmail(email.toLowerCase().trim());

  // Always do the expensive work, even when the user is missing
  const stored = user?.passwordHash ?? DUMMY_ARGON2_HASH;
  const ok = await verifyPassword(stored, password, user?.id ?? 'unknown');

  if (!user || !ok) {
    // Same error text, same timing, same status for both cases
    return { ok: false as const, error: 'INVALID_CREDENTIALS' };
  }
  if (!user.emailVerifiedAt) {
    return { ok: false as const, error: 'VERIFY_EMAIL' };
  }
  return { ok: true as const, session: await createSession(user.id) };
}
```

### CSRF Against Server Actions

Cookies are sent automatically, so a cross-site form can hit your server action. Next.js compares `Origin` with `Host` for server actions, which covers most cases, but you should still be explicit:

```typescript
// lib/csrf.ts
export async function assertSameOrigin(req: Request) {
  const origin = req.headers.get('origin');
  const host = req.headers.get('host');
  if (!origin || new URL(origin).host !== host) throw new Error('CSRF_BLOCKED');
}
```

`SameSite=Lax` plus an origin check is the modern baseline. Avoid `SameSite=None` unless you genuinely need cross-site cookies, and if you do, add a double-submit token.

### OAuth Done Correctly

```typescript
// 1. Start: generate state + PKCE verifier, store in a short-lived HttpOnly cookie
const state = randomBytes(16).toString('base64url');
const verifier = randomBytes(32).toString('base64url');
await setAuthFlowCookie({ state, verifier }, { maxAge: 600 });

// 2. Redirect with S256 challenge (never plain)
const challenge = createHash('sha256').update(verifier).digest('base64url');

// 3. Callback: state MUST match, and the code is exchanged server-side
const { state: expected } = await readAuthFlowCookie();
if (state !== expected) throw new Error('OAUTH_STATE_MISMATCH');
```

Skipping the state check is a login-CSRF vulnerability: an attacker completes the flow with their own account and the victim's browser links it.

### Deeper Explanation: Authentication Is The One Thing You Must Not Invent

Every other part of Atlas is a design decision. Authentication is a security decision with a well-known failure catalogue: token leakage, session fixation, enumeration, replay, CSRF. Each of those has a standard mitigation, and the mitigations are cheap only if applied from the start.

The practical rule: **use a vetted library for the protocol and write only the policy.** Let Better Auth (or Auth.js, or Clerk) handle OAuth, PKCE, TOTP and cookie hygiene. Write your own *workspace membership* logic, because that is your product and no library can know it.

### Additional Pitfalls

- **Token in `localStorage`.** Any XSS - including one in a third-party widget - exfiltrates every session.
- **Session not rotated after login.** Session fixation: a pre-set cookie becomes an authenticated session.
- **Enumeration via a "this email is already registered" message.** It is a user-list for spammers and credential stuffing.
- **No rate limit on login, magic links or password reset.** Unbounded guesses and unbounded email spend.
- **Long-lived sessions with no rotation.** Stolen cookies stay valid for a month; rotate and rotate on privilege change.
- **`SameSite=None` set casually.** Cross-site request forgery reopens because `Secure` alone does not stop it.

### Real-World Deal-Breakers
- **Unhashed or weakly hashed passwords** - one dump compromises every user, including on other sites via reuse.
- **Session token stored in plaintext in the database** - a read-only DB leak becomes full account takeover.
- **No CSRF protection on cookie-authenticated mutations** - third-party pages perform actions as your users.
- **JWT with `alg: none` accepted, or a symmetric algorithm on the client side** - trivially forged tokens.
- **No account lockout or alerting** - credential stuffing runs to completion unnoticed.
- **Auth logic duplicated in middleware only** - route handlers and server actions are public endpoints and must re-check.
