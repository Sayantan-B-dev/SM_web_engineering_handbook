### Contribute To What You Depend On

Atlas depends on Yjs, Tiptap, TanStack Query, Radix, Drizzle and Zod. Every one of them has an issue tracker, and every unresolved issue you work around is a permanent tax in your own codebase.

The professional move: when you write a workaround for a library, open an upstream issue with a minimal reproduction. You either get a fix (and delete the workaround) or you learn why the behaviour is intentional (and document it once).

### Read Before You Write

```text
1. CONTRIBUTING.md            - the rules, including how to run tests
2. The test suite for the area - it documents intended behaviour
3. Git history of the file    - why the code looks the way it does
4. Open issues and PRs        - someone may already be on it
5. The architecture doc       - where the maintainers want the change to live
```

Skipping step 3 is the most common junior mistake. That "obvious bug" often has a commit explaining exactly why the naive fix cannot work.

### A Minimal Reproduction Is The Real Contribution

```markdown
### Bug
`Y.UndoManager` restores a remote client's edit when `trackedOrigins` is set from `awareness.clientID`.

### Minimal reproduction
https://github.com/user/repro-undo-origin   (12 lines, deterministic, no network)

    const doc = new Y.Doc();
    const um = new Y.UndoManager(doc.getText('t'), { trackedOrigins: new Set([doc.clientID]) });
    // ... apply a remote update ...
    um.undo();   // expected: no-op   actual: reverts the remote change

### Environment
yjs 13.6.x, Node 22, Chromium 128
```

A maintainer with a reproducible failing case can fix a bug in minutes. A bug report without one can sit for months - and the reproduction is often ninety percent of the work anyway.

### The Pull Request

| Property | Why it matters |
|---|---|
| One logical change | reviewable in ten minutes |
| Tests included | maintainers merge what is verified |
| Commit messages in repo style | respect for the project's conventions |
| Failure case in the description | proves you understand the problem |
| No unrelated reformatting | keeps the diff honest |

```markdown
Fixes a case where `trackedOrigins` used a numeric client id, so remote
updates were treated as local and were reverted by `undo()`.

Previously: undo after a remote update reverted the remote change.
Now: undo only affects locally-originated changes.

Test: `test/undo.test.ts` - "ignores remote updates when tracking a client id"
```

### Handling Review

Review comments are about the code. The productive loop is: understand the concern, ask if unclear, change the code, and reply with what changed. Arguing on the first round is a reliable way to have a PR closed unread.

### Deeper Explanation: Contribution Is The Fastest Way To Senior

Working inside Atlas teaches you This Codebase. Contributing upstream teaches you how libraries are *designed*: what a breaking change costs, how compatibility is maintained across versions, why an API was shaped the way it was.

That knowledge is what makes a senior engineer able to choose a library in an afternoon and justify it, and to estimate a migration rather than guess at one. It also builds a public record of competence that no interview can fabricate.

### Additional Pitfalls

- **A giant PR that does five things.** It cannot be reviewed and will be closed.
- **Driving-by commits to fix formatting.** They create rebase conflicts for the branch authors and buy no goodwill.
- **Silence after review feedback.** Maintainers assume you abandoned it.
- **Ignoring the DCO/CLA.** The PR cannot be merged no matter how good it is.
- **Never updating your own workaround.** The fix ships upstream and your workaround stays for years.

### Real-World Deal-Breakers
- **PRs without tests** - not merged, regardless of correctness.
- **Filing a bug without a reproduction** - it sits in the backlog and you keep paying the tax.
- **Force-pushing during review** - reviewers lose the incremental diff and stop reviewing.
- **Ignoring the project's coding conventions** - your PR signals that you did not read the rules.
- **Contributing to a project with an unfit license for your employer's policy** - a legal problem, not a technical one.
