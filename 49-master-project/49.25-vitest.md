### Configuration

```typescript
// vitest.config.ts
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: ['./vitest.setup.ts'],
    coverage: { provider: 'v8', reporter: ['text', 'lcov'], include: ['src/**'], exclude: ['**/*.d.ts', '**/generated/**'] },
    restoreMocks: true,
    clearMocks: true,
    testTimeout: 10_000,
  },
  // Separate projects: node for the server, jsdom for the client
  projects: [
    { test: { name: 'unit', environment: 'node', include: ['src/server/**/*.test.ts'] } },
    { test: { name: 'ui', environment: 'jsdom', include: ['src/components/**/*.test.tsx'] } },
  ],
});
```

```typescript
// vitest.setup.ts
import '@testing-library/jest-dom/vitest';
import 'fake-indexeddb/auto';          // real IndexedDB semantics in tests (49.20)
import { server } from './src/test/msw-server';

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));   // fail on unmocked calls
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

`onUnhandledRequest: 'error'` is the important line: an unexpected real request in a unit test is a bug, not a warning.

### Mocking At The Right Level

| Level | Tool | Use when |
|---|---|---|
| Network | MSW | testing UI against realistic API responses |
| Module | `vi.mock` | an unavoidable external side effect (email, payment) |
| Function | `vi.spyOn` | asserting a collaborator was called |
| Time | `vi.useFakeTimers` | debounce, backoff, TTL expiry |

Prefer MSW. A component tested against MSW exercises its real fetch, serialisation and error paths. A component tested against a mocked `fetch` function exercises almost nothing.

```typescript
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/documents/:id', ({ params }) =>
    HttpResponse.json({ id: params.id, title: 'Design notes', content: 'Hello' })),
];

// Per-test override
server.use(
  http.get('/api/documents/:id', () => HttpResponse.json({ error: 'NOT_FOUND' }, { status: 404 })),
);
```

### Component Tests That Survive Refactors

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test } from 'vitest';

test('a viewer does not see the delete action', async () => {
  render(<DocumentToolbar role="viewer" documentId="d1" />);
  expect(screen.queryByRole('button', { name: /delete/i })).not.toBeInTheDocument();
});

test('an editor can rename the document', async () => {
  const user = userEvent.setup();
  render(<DocumentTitle documentId="d1" initialTitle="Draft" />);

  await user.click(screen.getByRole('button', { name: /rename/i }));
  const input = screen.getByRole('textbox', { name: /title/i });
  await user.clear(input);
  await user.type(input, 'Final spec');
  await user.keyboard('{Enter}');

  expect(await screen.findByRole('heading', { name: 'Final spec' })).toBeInTheDocument();
});
```

These assert what a user does and sees. They keep passing through a state-management refactor, which is when tests earn their keep.

### Fake Timers Without Breaking Promises

```typescript
test('flushes queued operations after the debounce', async () => {
  vi.useFakeTimers();
  const flush = vi.fn();
  const queue = createOpQueue({ flush, debounceMs: 400 });

  queue.push(op('insert'));
  queue.push(op('delete'));
  expect(flush).not.toHaveBeenCalled();

  await vi.advanceTimersByTimeAsync(400);      // async variant flushes microtasks too
  expect(flush).toHaveBeenCalledOnce();
  expect(flush.mock.calls[0][0]).toHaveLength(2);   // coalesced into one flush

  vi.useRealTimers();
});
```

Use `advanceTimersByTimeAsync`, not the sync variant: the sync one does not drain the microtask queue, so awaits inside your debounce never resolve and the test hangs.

### Coverage Policy

Coverage is a diagnostic, not a target. Atlas enforces thresholds only on the modules where a bug is an incident:

```typescript
coverage: {
  thresholds: {
    'src/server/authz/**':  { statements: 95 },
    'src/lib/crdt/**':      { statements: 90 },
    'src/lib/sync/**':      { statements: 90 },
  },
},
```

Globally enforced line coverage produces tests for getters. Targeted thresholds produce tests for the code that can lose data or leak a tenant.

### Deeper Explanation: Fast Feedback Changes Behaviour

The professional reason to choose Vitest over Jest in a Vite project is not features - it is *speed*. A suite that runs in two seconds is run on every save. A suite that takes ninety seconds is run before pushing, and then before releasing, and then not at all.

Test speed is not a comfort feature. It directly determines how much of your system is checked by machine rather than by hope.

### Additional Pitfalls

- **`vi.mock` with a factory that omits exports.** Unrelated tests fail with "is not a function" and the cause looks like a bug in app code.
- **`jsdom` for everything.** Server code tested in a browser-like environment hides Node-specific failures.
- **Global mocks not restored.** `restoreMocks: true` prevents cross-test leakage that shows up as random ordering-dependent failures.
- **Snapshot tests as assertions.** They lock in current output, including its bugs, and reviewers approve without reading.
- **Testing private functions.** They are private; test the public behaviour instead, or stop hiding them.

### Real-World Deal-Breakers
- **No MSW, only mocked modules** - the serialisation and error paths are never exercised and break in production.
- **Real network in unit tests** - the suite fails on the plane, on CI without network, and against a flaky API.
- **No fake-indexeddb** - the offline layer is untested and its quota and migration bugs ship.
- **Sync fake timers** - hanging tests that get `.skip`ped and stay that way.
- **Coverage gates with no policy** - noise that gets disabled, taking the useful thresholds with it.
