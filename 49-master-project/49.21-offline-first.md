### Offline-Capable Is Not Offline-First

An *offline-capable* app shows a cached error page when the network drops. An *offline-first* app keeps working: the editor accepts edits, the sidebar lists recently opened documents, comments post to a local queue, and everything reconciles when connectivity returns.

Atlas is offline-first because its users write on trains. Anything less is a broken product for a large fraction of sessions.

### Detect Connectivity Properly

```typescript
/** navigator.onLine only tells you a network interface exists. Probe the API. */
export function useConnectivity(apiUrl: string) {
  const [state, setState] = useState<'online' | 'degraded' | 'offline'>('online');

  useEffect(() => {
    let cancelled = false;
    const probe = async () => {
      try {
        const t0 = performance.now();
        const res = await fetch(`${apiUrl}/health`, { method: 'HEAD', cache: 'no-store' });
        const rtt = performance.now() - t0;
        if (cancelled) return;
        setState(!res.ok ? 'offline' : rtt > 2000 ? 'degraded' : 'online');
      } catch {
        if (!cancelled) setState('offline');
      }
    };

    probe();
    const interval = setInterval(probe, 15_000);
    window.addEventListener('online', probe);
    window.addEventListener('offline', probe);
    return () => {
      cancelled = true;
      clearInterval(interval);
      window.removeEventListener('online', probe);
      window.removeEventListener('offline', probe);
    };
  }, [apiUrl]);

  return state;
}
```

`navigator.onLine === true` on a hotel captive portal, on a VPN that dropped, and on a 2G connection. Treat "degraded" as a real third state: writes should queue rather than fail.

### The Sync Engine

```typescript
export class SyncEngine {
  private state: SyncState = 'idle';

  /** Pull remote ops, apply, then push local ops. Never the reverse. */
  async cycle(documentId: string) {
    if (!navigator.onLine) return this.setState('offline');

    try {
      this.setState('syncing');

      // 1. PULL first: we must know the remote state before we publish ours
      const { updates, seq } = await api.pull(documentId, this.lastSeq);
      for (const u of updates) applyUpdate(this.ydoc, u);
      this.lastSeq = seq;

      // 2. PUSH queued local ops, marked synced only after server ack
      const pending = await db.ops.where({ docId: documentId, synced: 0 }).toArray();
      if (pending.length) {
        await api.push(documentId, pending.map((o) => o.update));
        await db.ops.bulkUpdate(pending.map((o) => ({ key: o.seq!, changes: { synced: 1 as const } })));
      }

      // 3. Compact: fold synced ops into the local snapshot
      await compact(documentId);
      this.setState('idle');
    } catch (err) {
      if (isAuthError(err)) return this.setState('error');
      this.setState('offline');           // network failure: retry on the next cycle
      setTimeout(() => this.cycle(documentId), backoff());
    }
  }
}
```

Pull before push is the ordering rule. Push-first publishes operations based on a view of the document that may be stale, producing merges that look like lost edits.

### Service Worker Strategies

| Resource | Strategy | Rationale |
|---|---|---|
| App shell (HTML, JS, CSS) | stale-while-revalidate | instant start, updates on next load |
| Document list | network-first, cache fallback | fresh when possible, usable offline |
| Document snapshots | cache-first, revalidate | large and rarely changing |
| Attachments | cache-first, LRU eviction | expensive to refetch |
| API mutations | never cached | queue in IndexedDB instead |
| `/health` | network-only | must reflect reality |

```typescript
// service-worker.ts
const API_MUTATION = (url: URL) =>
  url.pathname.startsWith('/api/') && !['GET', 'HEAD'].includes('GET');

self.addEventListener('fetch', (event: FetchEvent) => {
  const url = new URL(event.request.url);

  // Mutations are never served from cache: they are queued by the sync engine
  if (API_MUTATION(url)) return;

  if (event.request.mode === 'navigate') {
    event.respondWith(
      fetch(event.request).catch(() => caches.match('/offline.html')),   // honest fallback
    );
    return;
  }

  if (url.pathname.startsWith('/assets/')) {
    event.respondWith(
      caches.open('assets').then(async (cache) => {
        const cached = await cache.match(event.request);
        const network = fetch(event.request).then((res) => {
          cache.put(event.request, res.clone());
          return res;
        });
        return cached ?? network;                       // stale-while-revalidate
      }),
    );
  }
});
```

### Conflict Policy Per Data Type

There is no single correct merge rule. Decide per field and write it down:

| Data | Policy | Mechanism |
|---|---|---|
| Document text | automatic merge | CRDT (49.22) |
| Document title | last-write-wins with version guard | optimistic concurrency (49.10) |
| Comments | append-only, no conflict | insert-only log |
| Membership | server-authoritative | client cannot change it offline |
| Billing | server-authoritative | never queued offline |

### Deeper Explanation: Honesty Is The Feature

The hardest part of offline-first is not the sync engine - it is the user interface. If the app silently queues a rename, the user believes it is saved. If it shows a red "OFFLINE" banner, they stop trusting the product and reload, which is the worst thing they can do.

The professional design is a small, calm, always-visible sync indicator with three states and no alarm: *Saved*, *Saving…*, *Offline - will sync*. It must be truthful: never show "Saved" for something that is only in a local queue.

### Additional Pitfalls

- **Queueing mutations for server-authoritative data.** An offline membership change or payment must be rejected, not queued and applied later.
- **Marking ops synced before the server acknowledges.** A crash between send and ack loses the update permanently.
- **Infinite retry with no backoff.** Drains the battery and hammers a recovering server.
- **No compaction.** The local op log grows without bound until quota is exceeded.
- **Testing only with devtools "offline".** It does not reproduce quota pressure, partial requests or a captive portal.

### Real-World Deal-Breakers
- **Silent data loss on reconnect** - queued edits discarded because the push failed and nobody surfaced it.
- **Showing "All changes saved" while offline** - users close the tab believing work is safe; it never existed on the server.
- **Replaying the whole queue non-idempotently** - duplicate comments, duplicate notifications, duplicate AI calls.
- **Caching mutation responses** - a later duplicate request is served a stale success and the write never happens.
- **No storage-eviction recovery** - the offline copy is cleared and the app boots into an empty, broken state with no re-fetch path.
