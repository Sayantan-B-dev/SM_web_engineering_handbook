### The Rule Before The Tools

Redis is for **derived, disposable and ephemeral** data. If losing it would lose a fact the business needs, it belongs in Postgres. Atlas uses Redis for four jobs and nothing else.

| Job | Data | Loss impact |
|---|---|---|
| Cache | rendered document HTML, permission lookups | slower, correct |
| Sessions | session IDs, refresh tokens | users re-login |
| Rate limits | counters per key/route | abuse window |
| Presence | who is in which document | reconnect |

### Caching With Stampede Protection

```typescript
import { Redis } from '@upstash/redis';

const redis = Redis.fromEnv();
const TTL = 60;
const JITTER = 15;

export async function cachedDocumentHtml(id: string): Promise<string> {
  const key = `doc:html:${id}`;

  const hit = await redis.get<string>(key);
  if (hit) return hit;

  // Single-flight lock: one request recomputes, the others wait briefly
  const lock = await redis.set(`lock:${key}`, '1', { nx: true, px: 5_000 });
  if (!lock) {
    await new Promise((r) => setTimeout(r, 120));
    return (await redis.get<string>(key)) ?? renderDocumentHtml(id);   // fall back to DB
  }

  try {
    const html = await renderDocumentHtml(id);
    // Jittered TTL prevents a synchronised expiry wave
    await redis.set(key, html, { ex: TTL + Math.floor(Math.random() * JITTER) });
    return html;
  } finally {
    await redis.del(`lock:${key}`);
  }
}
```

Without the lock, 500 concurrent requests after an expiry all miss and all hit Postgres: the stampede that takes the database down at exactly the traffic peak when you cannot afford it.

### Rate Limiting

```typescript
/** Sliding-window counter: accurate, cheap, and monotonic per second-bucket. */
export async function rateLimit(key: string, limit: number, windowSec: number) {
  const now = Math.floor(Date.now() / 1000);
  const bucket = `${key}:${now}`;

  const count = await redis.incr(bucket);
  if (count === 1) await redis.expire(bucket, windowSec);

  if (count > limit) {
    const retryAfter = windowSec - (now % windowSec);
    return { ok: false as const, retryAfter };
  }
  return { ok: true as const, remaining: limit - count };
}
```

```typescript
// In the route handler
const { ok, retryAfter } = await rateLimit(`ai:${userId}`, 20, 60);
if (!ok) {
  return new Response('Too many requests', {
    status: 429,
    headers: { 'Retry-After': String(retryAfter) },
  });
}
```

AI endpoints need this more than any other (49.14): an unmetered LLM route is an unbounded bill.

### Presence With Ephemeral Keys

Presence must expire on its own, or a crashed tab leaves a ghost cursor forever:

```typescript
export async function heartbeat(documentId: string, userId: string, cursor: Cursor) {
  const key = `presence:${documentId}`;
  // Avoid a JSON blob per user: one hash field per user, TTL on the whole key
  await redis.hset(key, { [userId]: JSON.stringify({ cursor, at: Date.now() }) });
  await redis.expire(key, 30);            // refreshed by the 10s heartbeat
}

export async function presence(documentId: string) {
  const raw = await redis.hgetall<Record<string, string>>(`presence:${documentId}`) ?? {};
  const cutoff = Date.now() - 25_000;
  return Object.entries(raw)
    .map(([userId, json]) => ({ userId, ...JSON.parse(json) }))
    .filter((p) => p.at > cutoff);
}
```

### Fan-Out To Socket Servers

A single WebSocket server holds the sockets it owns. When one server must notify the others (49.18), Redis Pub/Sub carries the message:

```typescript
const pub = redis;                                     // publisher
const sub = redis;                                     // subscriber

// Publishing server
await pub.publish(`doc:${documentId}`, JSON.stringify({ type: 'update', update: base64 }));

// Every socket server
await sub.subscribe(`doc:${documentId}`, (message) => {
  for (const socket of localSockets(documentId)) socket.send(message);
});
```

Pub/Sub is fire-and-forget: a server that is restarting misses the message. If a missed message means data loss, use Streams with consumer groups and acknowledgements instead of Pub/Sub.

### Deeper Explanation: The Two Hard Problems Are Still Hard

There is no cache design that avoids invalidation, only designs that make it safe. Atlas uses three complementary mechanisms:

1. **Short TTLs with jitter** - bounds staleness automatically; no explicit invalidation needed.
2. **Explicit invalidation on write** - `del` the affected keys inside the mutation that changed the data.
3. **Version-stamped keys** - `doc:html:${id}:v${version}` means an old entry is orphaned by construction rather than deleted.

The third is the professional move: it turns invalidation from a *race* into a *non-event*. An old key is simply never read again and expires on its own.

### Additional Pitfalls

- **Caching errors.** Redis-caching a `null` because the DB call failed extends a blip into a TTL-long outage.
- **No TTL anywhere.** Unbounded keys exhaust memory; Redis starts evicting live sessions.
- **Using Redis as the primary store.** It is memory-bound, often not durable, and eviction is silent.
- **`KEYS *` in production.** It blocks the single-threaded server; use `SCAN`.
- **Per-user cache keys without versioning.** A deploy that changes rendering serves stale HTML for the whole TTL.

### Real-World Deal-Breakers
- **No rate limit on AI or auth routes** - credential stuffing and unbounded LLM spend.
- **Cache with no stampede protection** - the first expiry after a deploy stampedes the database and takes the site down.
- **Presence keys without TTL** - ghost collaborators in the UI; users distrust the editor.
- **Session data as the only copy** - a Redis eviction logs everyone out mid-session.
- **Pub/Sub for state that must not be lost** - silent message drops that surface as divergent documents.
