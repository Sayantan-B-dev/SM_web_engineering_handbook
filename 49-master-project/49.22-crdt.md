### The Property You Get

A CRDT guarantees **strong eventual consistency**: any two replicas that have seen the same set of operations have identical state, regardless of order or duplicates.

```text
Replica A: [a][b][c]      Replica B: [a][c][b]
             \               /
              network shuffles
                   ↓
            both converge to the same text
```

No leader election, no locks, no server deciding who wins. That is the whole reason Atlas can edit offline and merge cleanly on reconnect.

### State-Based vs Operation-Based

| | State-based (CvRDT) | Operation-based (CmRDT) |
|---|---|---|
| Sends | full state / delta | individual ops |
| Merge | `merge(local, remote)` idempotent | must be exactly-once, causally ordered |
| Transport | tolerant of loss and duplication | needs reliable delivery |
| Overhead | higher per message | lower per message |
| Yjs | updates ARE state deltas | - |

Yjs is operation-based in spirit but sends *encoded state updates*, which makes its transport tolerant of loss - which is exactly what you need over a flaky mobile connection.

### Clocks, Not Timestamps

```typescript
type Clock = { clientId: string; seq: number };   // logical, per-replica

// WRONG: wall-clock ordering. Two devices disagree, and NTP corrections move "now" backwards.
if (opA.timestamp > opB.timestamp) applyA();

// RIGHT: CRDT ties are broken by a deterministic, total order
function compareOp(a: Op, b: Op): number {
  if (a.clock.seq !== b.clock.seq) return a.clock.seq - b.clock.seq;
  return a.clock.clientId < b.clock.clientId ? -1 : 1;   // deterministic tiebreak
}
```

The classic production bug: two users edit from devices whose clocks differ by 40 seconds. With timestamp ordering, edits "from the future" win permanently and the other user's changes vanish.

### Structuring The Document

```typescript
const ydoc = new Y.Doc();

// Shared types are created once and addressed by name
const meta        = ydoc.getMap('meta');            // title, icon, updatedAt
const content     = ydoc.getText('content');        // the prose
const blocks      = ydoc.getArray('blocks');        // ordered block IDs
const comments    = ydoc.getMap('comments');        // commentId -> comment
const suggestions = ydoc.getArray('suggestions');   // pending review items

// Nesting for per-block isolation: a large document as one Y.Text merges the whole doc
const block = new Y.Text();
blocks.insert(0, [block]);

// Transactions group related edits into one atomic, broadcastable unit
ydoc.transact(() => {
  meta.set('title', 'Q3 Architecture Notes');
  content.insert(content.length, '\n\n## Decisions\n');
}, 'local');                                          // origin tag -> undo manager scope
```

Use nested types (a `Y.Text` per block) for large documents. One giant `Y.Text` means every update touches the whole structure's index space, and every remote client rewrites its index mapping.

### Snapshots And Sync

```typescript
// Server sends: a compacted snapshot the client can boot from
const snapshot = Y.encodeStateAsUpdate(ydoc);            // Uint8Array

// Client tells the server what it already has, so only the delta is sent
const sv = Y.encodeStateVector(clientDoc);
const missing = Y.encodeStateAsUpdate(serverDoc, sv);    // minimal update

// Applying is idempotent: applying the same update twice changes nothing
Y.applyUpdate(ydoc, missing);
```

`encodeStateAsUpdate(doc, stateVector)` is the bandwidth optimisation that makes reconnect cheap. Asking for the full state on every reconnect is the most common performance mistake in first CRDT implementations.

### Garbage Collection And Growth

```typescript
// Deleted content is a tombstone, not a gap. History grows monotonically.
ydoc.on('afterTransaction', (tr) => {
  if (tr.changed.size === 0) return;
  scheduledCompact();
});

/** Compaction: snapshot, then trim the op log up to that snapshot. */
async function compact(documentId: string) {
  const snapshot = Y.encodeStateAsUpdate(ydoc);
  await db.documents.update(documentId, { crdtState: snapshot });
  await db.documentOps.deleteUpTo(documentId, currentSeq());   // history is now in the snapshot
}
```

Compaction is a product decision as much as a technical one: trimming the op log limits version history. Decide the retention window deliberately and tell users what it is.

### Deeper Explanation: Convergence Is Not Intent

Two replicas converge on the same string. That string may be nonsense. If Alice rewrites a paragraph while Bob deletes its first sentence, the merge is valid and unreadable.

CRDTs solve the *mechanical* problem, completely and provably. Everything that remains - presence, comments, suggestion mode, review workflow - exists to solve the *human* problem, and that is where the product value lives.

### Additional Pitfalls

- **One `Y.Doc` per component render.** History is silently reset on every render.
- **Sending full state on every keystroke.** Bandwidth explodes; use state vectors and debounce.
- **Persisting awareness as data.** Cursors and selections are ephemeral; persisting them corrupts the shared document.
- **Mixing raw DOM edits with the CRDT.** The editor binding must own the DOM; direct writes desynchronise the model.
- **No convergence test.** Without a deterministic two-replica test, a merge regression ships unnoticed.

### Real-World Deal-Breakers
- **Wall-clock ordering of operations** - clock skew makes one device's edits permanently win and destroys the other's work.
- **Never compacting** - document size grows forever, load times increase, and the browser eventually OOMs.
- **Reusing a `clientId` across tabs** - two replicas under one identity produce corrupt, non-convergent state.
- **Applying unvalidated remote updates** - a hostile client can inject an update that crashes every peer.
- **Assuming CRDTs remove the need for a server** - persistence, authorisation and access control all still live server-side.
