## 49.26 CI/CD

### Subtopic Tree
- CI (verify) vs CD (deliver): separate concerns
- A pipeline that fails fast: cheap checks first
- Caching dependencies and build artefacts
- Preview deployments per pull request
- Database migrations in the pipeline (expand-contract)
- Secrets management: OIDC over long-lived keys
- Environments: preview, staging, production
- Progressive delivery: canary, feature flags, gradual rollout
- Rollback as a first-class path
- Required checks and branch protection
- Deploy frequency as a health metric
- Supply-chain hygiene (lockfiles, provenance, pinning actions)

### A Pipeline That Fails Fast

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push: { branches: [main] }

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true          # superseded runs waste minutes

permissions:
  contents: read                    # least privilege by default

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 22, cache: npm }

      - run: npm ci                  # lockfile-exact, reproducible

      # cheapest -> most expensive, so failures surface in seconds
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test -- --coverage
      - run: npm run build

      - if: always()                 # surface the report even when tests fail
        uses: actions/upload-artifact@v4
        with: { name: coverage, path: coverage/ }
```

Ordering is a cost decision: lint and typecheck finish in seconds and catch a large share of mistakes before the expensive build starts.

### Preview Deployments

```yaml
  preview:
    if: github.event_name == 'pull_request'
    needs: verify
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - run: npx vercel deploy --prebuilt --token=${{ secrets.VERCEL_TOKEN }} > url.txt
      - run: echo "url=$(cat url.txt)" >> "$GITHUB_OUTPUT"
        id: deploy
      - uses: marocchino/sticky-pull-request-comment@v2
        with:
          message: "Preview: ${{ steps.deploy.outputs.url }}"
```

Every PR gets a real URL. Reviewers click, not imagine. Run the E2E suite (49.24) against the preview rather than a local build.

### Migrations In The Pipeline

```yaml
  migrate:
    if: github.ref == 'refs/heads/main'
    needs: verify
    environment: production
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - run: npm ci
      # Expand step only is safe to run before the new code deploys
      - run: npm run db:migrate:expand
        env: { DATABASE_URL: ${{ secrets.DATABASE_URL }} }
```

Destructive migrations (the *contract* step) run only after the new version is fully deployed and stable, in a separate workflow. Running a `DROP COLUMN` in the same pipeline stage as the deploy guarantees that in-flight requests from the old version break.

### Secrets Without Static Keys

```yaml
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/gh-deploy
          aws-region: eu-central-1
          # no static access keys: short-lived credentials from OIDC
```

Never store long-lived cloud credentials in repository secrets. They leak through logs, forks and screenshots and never expire.

### Rollback As A Default

```yaml
  rollback:
    if: failure()
    needs: [deploy]
    runs-on: ubuntu-latest
    steps:
      - run: npx vercel rollback --token=${{ secrets.VERCEL_TOKEN }}
```

A pipeline that can deploy but not roll back is a one-way door. Automated rollback on failed post-deploy smoke tests converts a potential incident into a non-event.

### Deeper Explanation: Deploy Throughput Is A Quality Lever

Small, frequent deploys are safer than large, rare ones, and not because of fashion: a ten-line change has a small blast radius and an obvious rollback, while a three-week branch has neither.

CI/CD is what makes that possible. When verification is automatic, review is fast and rollback is one command, releasing daily becomes the low-risk option. Teams that deploy quarterly have large, risky releases precisely because their tooling makes each release expensive.

### Additional Pitfalls

- **`npm ci` replaced with `npm install`.** The lockfile stops being authoritative and a dependency drift breaks a build nobody changed.
- **Unpinned actions (`@main`).** A compromised upstream action runs in your pipeline with your secrets.
- **Long-lived deploy tokens in secrets.** Rotate to OIDC; tokens leak via logs and forks.
- **Running migrations and deploys in one stage.** Old code and new schema coexist for seconds; one is always wrong.
- **No `cancel-in-progress`.** Every push queues a full run; minutes are burned on obsolete commits.

### Real-World Deal-Breakers
- **No preview deployments** - review is guesswork and regressions are found by users.
- **Destructive migrations in the deploy stage** - the old version is still serving traffic and starts erroring immediately.
- **Static cloud credentials in CI** - a single leaked log line grants production access indefinitely.
- **No automated rollback** - incidents last as long as a human takes to notice, decide and act.
- **Tests not required to merge** - the suite exists but nobody is blocked by it, so it rots.
