## 49.5 Client Components

### Subtopic Tree
- What genuinely requires the client
- `'use client'` marks a module boundary, not a single component
- Hydration: matching server HTML to client state
- Browser APIs: `window`, `localStorage`, `IntersectionObserver`, `ResizeObserver`
- Event handlers, refs and imperative DOM access
- `useSyncExternalStore` for external state (Yjs, WebSocket)
- Third-party libraries that assume the DOM
- Hydration mismatch causes and fixes
- Deferring expensive client work with `useTransition` and dynamic import
- Keeping the island small: wrappers, not page-level directives

### What Actually Needs The Client

Only five things:

1. State (`useState`, `useReducer`).
2. Effects (`useEffect`, `useLayoutEffect`).
3. Event handlers (`onClick`, `onChange`).
4. Browser-only APIs (`window`, `document`, `navigator`).
5. Libraries built on the above (Yjs bindings, chart engines, rich-text editors).

Everything else is a server component. In Atlas, that list is short and deliberate: the editor surface, the presence indicator, the connection banner, the comment composer, and a handful of menus.

### `'use client'` Is A Module Boundary

The directive marks every import in that file's graph as client code. This is why placement matters more than people expect:

```tsx
// BAD: one onClick turns the whole page into a client bundle
'use client';
export default function DocumentPage() {
  const [expanded, setExpanded] = useState(false);
  return (
    <>
      <Header />
      <HeavyServerRenderedBody />
      <button onClick={() => setExpanded(!expanded)}>Toggle</button>
    </>
  );
}
```

```tsx
// GOOD: the interactive part is its own tiny island
// app/.../page.tsx (server)
import { ToggleSection } from './toggle-section';
export default function DocumentPage() {
  return (
    <>
      <Header />
      <HeavyServerRenderedBody />
      <ToggleSection />
    </>
  );
}

// toggle-section.tsx
'use client';
export function ToggleSection() { /* only this ships */ }
```

### The Editor Island

The real client component in Atlas is the text surface plus presence. It needs the DOM, it needs Yjs, and it needs to respond to keystrokes:

```tsx
'use client';

import { useEffect, useRef, useSyncExternalStore } from 'react';

export function EditorSurface({ docId, initialContent }: { docId: string; initialContent: string }) {
  const ref = useRef<HTMLDivElement>(null);
  const session = useDocumentSession(docId, initialContent);

  // External store subscription - presence peers come from the Yjs awareness protocol
  const peers = useSyncExternalStore(
    session.subscribeAwareness,
    session.getAwarenessSnapshot,
    session.getAwarenessServerSnapshot,   // SSR snapshot: always empty
  );

  useEffect(() => {
    // Browser-only: everything above ran on the server, this only runs in the browser
    if (!ref.current) return;
    const teardown = session.attachTo(ref.current);
    return teardown;
  }, [session]);

  return (
    <div className="relative">
      <div ref={ref} contentEditable suppressContentEditableWarning className="prose min-h-[60rem]" />
      <PresenceBar peers={peers} />
    </div>
  );
}
```

Three details carry the weight:

- `useSyncExternalStore` is the correct way to read mutable external state (Yjs is exactly that). `useState` + `useEffect` would tear and drop frames.
- The third argument is the **server snapshot**. Without it, the server and client disagree on render and you get a hydration mismatch.
- The `useEffect` is the only place `document` is touched, which is why the component can still be server-rendered as HTML first.

### State That Survives Renders

```tsx
'use client';
import { useOptimistic, useTransition } from 'react';

export function CommentComposer({ documentId, onPosted }: Props) {
  const [pending, startTransition] = useTransition();
  const [optimistic, addOptimistic] = useOptimistic<string[]>([]);

  async function post(formData: FormData) {
    const body = String(formData.get('body') ?? '');
    if (!body.trim()) return;

    startTransition(async () => {
      addOptimistic((prev) => [...prev, body]);   // appears instantly
      await createComment({ documentId, body });  // server action
      onPosted();
    });
  }

  return (
    <form action={post}>
      <textarea name="body" disabled={pending} />
      <ul>{optimistic.map((c, i) => <li key={i} className="opacity-60">{c}</li>)}</ul>
      <button disabled={pending}>Comment</button>
    </form>
  );
}
```

`useOptimistic` is what makes a collaborative app feel instant without lying to the user: the comment appears greyed while the server confirms it, and disappears if the server rejects it.

### Deeper Explanation: Hydration Is A Contract

Hydration is React re-running your client components in the browser and attaching to the HTML the server produced. A mismatch means the server drew one thing and the client drew another - React then throws away the server HTML and re-renders, which is a silent performance cliff.

The four causes, in order of frequency:

| Cause | Example | Fix |
|---|---|---|
| Non-deterministic output | `new Date().toLocaleString()`, `Math.random()` | Render on the client only, or pass the value down |
| Browser-only API during render | `window.innerWidth` in the render body | Read in `useEffect`, start from a server-safe default |
| Stored client state | Reading `localStorage` during render | `useSyncExternalStore` with a server snapshot |
| Invalid HTML nesting | `<div>` inside `<p>`, `<a>` inside `<a>` | Fix the markup; the browser repairs it differently than React expects |

```tsx
// Wrong: server and client produce different strings
<span>{new Date(updatedAt).toLocaleTimeString()}</span>

// Right: stable on the server, refined after hydration
'use client';
function LocalTime({ iso }: { iso: string }) {
  const [text, setText] = useState(iso);           // server-safe initial value
  useEffect(() => setText(new Date(iso).toLocaleTimeString()), [iso]);
  return <time dateTime={iso} suppressHydrationWarning>{text}</time>;
}
```

### Additional Pitfalls

- **Reading `localStorage` during render.** Guarantees a mismatch and, in some setups, a crash on the server.
- **`useEffect` for data fetching on a client island.** You now own caching, deduplication, races and abort logic. Use TanStack Query (49.09) or fetch on the server.
- **Passing functions as props from a server component.** Only server actions cross; a normal function becomes a runtime error.
- **A client component importing a server-only module.** Server code leaks into the client bundle or the build fails with an opaque error.
- **Dynamic `import()` with no fallback.** The island pops in after a delay; give it a skeleton so the layout does not shift.
- **`suppressHydrationWarning` as a blanket fix.** It hides the symptom and keeps the double-render cost. Diagnose the cause.

### Real-World Deal-Breakers
- **`'use client'` at a layout or page root** - the entire subtree hydrates; the app is an SPA that pretends to be server-rendered.
- **Hydration mismatch ships to production** - React discards server HTML and re-renders everything on the client; LCP and INP degrade together and nobody knows why.
- **Secrets imported into a client module** - bundled, served to the browser, scraped.
- **`window` accessed at module scope** - the server render throws and the route 500s only in production.
- **Editor state in `useState`** - every keystroke re-renders the parent tree; on mid-range devices the editor visibly lags.
- **No server snapshot in `useSyncExternalStore`** - SSR crashes with "getServerSnapshot is not defined" or hydrates into a different UI.
