## 49.15 RAG

### Subtopic Tree
- Why retrieval beats a giant context window for this app
- Chunking strategy for prose vs code vs tables
- Embeddings: model choice, dimensions, storage
- `pgvector` in the same Postgres as your data
- Hybrid search: vector plus full-text (BM25), ranked together
- Metadata filters as a permission boundary
- Reranking the top candidates
- Citations: grounding every answer in a source span
- Freshness and reindexing when a document changes
- Evaluating retrieval quality (recall@k, faithfulness)

### The Pipeline

```text
document write -> chunk -> embed -> upsert into pgvector
user question  -> embed -> hybrid retrieve -> filter by ACL -> rerank -> prompt -> answer + citations
```

Each arrow is a place this feature fails quietly. The most common failure is not the model: it is that retrieval returns a *near-duplicate of the question* from a different workspace, and the answer is confidently wrong.

### Schema With Permissions Built In

```sql
create extension if not exists vector;

create table document_chunks (
  id           bigserial primary key,
  document_id  uuid not null references documents(id) on delete cascade,
  workspace_id uuid not null references workspaces(id) on delete cascade,
  ordinal      int  not null,
  content      text not null,
  token_count  int  not null,
  embedding    vector(1024) not null,
  tsv          tsvector generated always as (to_tsvector('english', content)) stored,
  updated_at   timestamptz not null default now()
);

create index chunks_embedding_idx on document_chunks using hnsw (embedding vector_cosine_ops);
create index chunks_tsv_idx       on document_chunks using gin (tsv);
create index chunks_doc_idx       on document_chunks (document_id, ordinal);
```

Storing `workspace_id` **on the chunk** is what makes the ACL filter cheap and safe. Filtering after retrieval means the model has already seen foreign text in the candidates.

### Chunking

```typescript
/** Split on structural boundaries; never split mid-sentence or mid-code-block. */
export function chunkDocument(markdown: string, targetTokens = 400, overlap = 60) {
  const blocks = splitOnHeadingsAndFences(markdown);   // headings + code fences are atomic
  const chunks: { content: string; ordinal: number }[] = [];
  let buffer: string[] = [];
  let ordinal = 0;

  const flush = () => {
    if (!buffer.length) return;
    chunks.push({ content: buffer.join('\n\n'), ordinal: ordinal++ });
    // carry the tail forward so a fact spanning the boundary stays retrievable
    const tail = buffer.join('\n\n').split('\n').slice(-3).join('\n');
    buffer = tail ? [tail] : [];
  };

  for (const block of blocks) {
    buffer.push(block);
    if (countTokens(buffer.join('\n\n')) >= targetTokens) flush();
  }
  flush();
  return chunks;
}
```

Chunking rules that matter in practice: keep headings with their content, never split a code block or a table, and use 10-15% overlap so a sentence spanning a boundary is retrievable from either side.

### Hybrid Retrieval With ACL Filtering

```typescript
export async function retrieve(question: string, workspaceId: string, userId: string, k = 20) {
  const [queryEmbedding] = await embed([question]);

  const rows = await sql`
    with allowed as (
      -- ACL applied BEFORE scoring: no foreign chunk ever reaches the model
      select d.id
        from documents d
        join memberships m on m.workspace_id = d.workspace_id and m.user_id = ${userId}
       where d.workspace_id = ${workspaceId} and d.deleted_at is null
    ),
    vec as (
      select c.id, 1 - (c.embedding <=> ${queryEmbedding}) as score
        from document_chunks c
       where c.document_id in (select id from allowed)
       order by c.embedding <=> ${queryEmbedding}
       limit ${k}
    ),
    txt as (
      select c.id, ts_rank_cd(c.tsv, websearch_to_tsquery('english', ${question})) as score
        from document_chunks c
       where c.document_id in (select id from allowed)
         and c.tsv @@ websearch_to_tsquery('english', ${question})
       limit ${k}
    )
    -- Reciprocal Rank Fusion: robust without tuning score scales
    select c.id, c.document_id, c.content,
           coalesce(1.0/(60 + v.rk), 0) + coalesce(1.0/(60 + t.rk), 0) as rrf
      from document_chunks c
      left join (select id, row_number() over (order by score desc) rk from vec) v on v.id = c.id
      left join (select id, row_number() over (order by score desc) rk from txt) t on t.id = c.id
     where v.id is not null or t.id is not null
     order by rrf desc
     limit ${k};
  `;
  return rows;
}
```

Hybrid matters because embeddings are bad at exact tokens: a question about `REACT_COMPILER_BAILOUT` or an error code retrieves nothing useful from vectors alone, while full-text nails it. Fusing both with reciprocal rank fusion is the pragmatic default.

### Reranking And Citations

```typescript
const candidates = await retrieve(question, workspaceId, userId, 20);
const reranked = await rerank(question, candidates, { topN: 5 });   // cross-encoder

const answer = await streamText({
  model: anthropic('claude-sonnet-4-6'),
  system: `Answer only from the provided sources. Cite each claim as [n]. If the sources do not contain the answer, say so.`,
  messages: [{
    role: 'user',
    content: reranked.map((c, i) => `[${i + 1}] (${c.documentId})\n${c.content}`).join('\n\n')
      + `\n\nQuestion: ${question}`,
  }],
});
```

Retrieve ~20, rerank to ~5. Reranking is cheap relative to the answer call and is the highest-leverage quality improvement in the whole pipeline.

### Deeper Explanation: Grounding Is A Product Property

An assistant that answers from the model's general knowledge inside a company's workspace is a liability: it invents policy, invents API names, invents an incident postmortem. An assistant that answers **only from retrieved spans and cites them** is auditable - a user can click the citation and check.

That means two non-negotiable behaviours: refuse when retrieval is empty, and cite every claim. "I could not find that in your workspace" is a feature, not a failure.

### Additional Pitfalls

- **Embedding the question without the document's context.** "It" refers to different things in different chunks; prepend the heading path to each chunk before embedding.
- **Reindexing the whole corpus on every edit.** Chunk-level upsert keyed by `(document_id, ordinal)` is enough.
- **No staleness handling.** Deleted documents leave chunks that still answer questions - delete chunks with the document.
- **Cosine vs inner product mismatch.** The index op class must match the query operator, or you silently rank by the wrong metric.
- **No evaluation.** You cannot tell a retrieval regression from a prompt regression without a labelled set.

### Real-World Deal-Breakers
- **ACL applied after retrieval** - foreign content is embedded in the prompt and can be surfaced; a cross-tenant leak.
- **Deleted documents still indexed** - the assistant answers from content the user deleted, undermining trust in the product.
- **Vector-only retrieval** - error codes, identifiers and exact names become unfindable.
- **No citations** - users cannot verify, so they either over-trust or stop using it; both kill adoption.
- **Unbounded chunk size** - a 50k-token chunk blows the context window and drowns the signal.
- **Embedding model changed without reindexing** - vectors from two models in one index produce meaningless rankings.
