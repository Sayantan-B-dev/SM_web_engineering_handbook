### Layers Of Tokens

The most common design-system failure is one layer of tokens. You need two:

```css
/* Layer 1 - primitives: raw values, no meaning */
:root {
  --blue-500: oklch(0.62 0.18 265);
  --gray-50:  oklch(0.99 0.002 250);
  --gray-900: oklch(0.22 0.01 250);
}

/* Layer 2 - semantic: meaning, and the only thing components may use */
@theme {
  --color-surface: var(--gray-50);
  --color-ink: var(--gray-900);
  --color-accent: var(--blue-500);
}
```

Components reference layer 2 only. Then dark mode, high contrast and white-labelling are layer-2 overrides, and no component file changes.

```css
.dark {
  --color-surface: var(--gray-900);
  --color-ink: var(--gray-50);
}
```

### Headless Primitives Plus Styled Wrappers

Never build focus management, escape handling or ARIA wiring yourself. Use Radix primitives for behaviour and put your design on top:

```tsx
'use client';
import * as Dialog from '@radix-ui/react-dialog';
import { cva, type VariantProps } from 'class-variance-authority';
import { cn } from '@/lib/cn';

const dialogContent = cva(
  'fixed left-1/2 top-1/2 -translate-x-1/2 -translate-y-1/2 bg-surface text-ink shadow-lg',
  {
    variants: {
      size: {
        sm: 'w-[min(92vw,28rem)] rounded-[--radius-card] p-4',
        lg: 'w-[min(94vw,52rem)] rounded-[--radius-card] p-6',
        full: 'inset-0 h-dvh w-screen translate-x-0 translate-y-0 rounded-none p-8',
      },
    },
    defaultVariants: { size: 'sm' },
  },
);

export function Modal({ size, ...props }: Dialog.DialogProps & VariantProps<typeof dialogContent>) {
  return (
    <Dialog.Root {...props}>
      <Dialog.Portal>
        <Dialog.Overlay className="fixed inset-0 bg-black/40 backdrop-blur-sm" />
        <Dialog.Content className={cn(dialogContent({ size }))}>{props.children}</Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

Radix gives you: focus trap, focus restoration on close, escape to dismiss, `aria-modal`, portal handling and screen-reader labelling. Writing that by hand is weeks of work and usually still broken.

### Component API As A Public Interface

A design-system component is a public API. Treat changes to its props as breaking changes:

```tsx
// v1
export function Badge({ label }: { label: string }) { /* ... */ }

// v2 - NEVER do this silently
export function Badge({ children }: { children: React.ReactNode }) { /* ... */ }

// v2 done correctly: both supported during a deprecation window
export function Badge(props: { label?: string; children?: React.ReactNode }) {
  const content = props.children ?? props.label;
  if (props.label && !props.children) {
    console.warn('[Badge] `label` is deprecated; pass children instead.');
  }
  return <span className="inline-flex rounded-full px-2 py-0.5 text-xs">{content}</span>;
}
```

### Deeper Explanation: A Design System Is A Contract Between Teams

Atlas has four contributors: a designer, two front-end engineers and a back-end engineer. Without a design system, "the designer changed the corner radius" becomes a five-file hunt and a merge conflict.

With a system, the same change is a one-line token edit and a screenshot diff. That is the professional payoff: **the design system moves style decisions out of code review and into a shared, versioned vocabulary.**

The second payoff is behavioural. Every modal in the app traps focus correctly because `Modal` wraps Radix, and nobody can accidentally reimplement it badly. Consistency is not a matter of discipline - it is structural.

### Additional Pitfalls

- **Three tiers where two suffice.** Component-level tokens multiply fast; add only when a component genuinely needs its own knob.
- **Styling Radix internals.** They are unstyled by design. Style your wrapper; keep DOM structure as a private detail.
- **Boolean prop explosion.** `isPrimary isLarge isDanger` produces 8 states and 3 of them are invalid. Use a `variant` union.
- **Shipping the docs to production bundle size.** Documentation routes belong in a separate app or lazily built page.
- **Copy-in components with no upgrade path.** If you copy shadcn components, record the upstream version and re-diff on upgrade.

### Real-World Deal-Breakers
- **Hard-coded colours in components** - theming and dark mode break project-wide; the design system is bypassed.
- **Custom modals with `useEffect` focus hacks** - keyboard users get trapped or lose focus; accessibility failures reach users.
- **Silent breaking changes to component props** - 60 call sites break in one deploy and the app is down while you fix them.
- **No visual regression coverage** - a token change quietly breaks a dashboards' contrast and nobody notices until users complain.
- **Diverging `Button` implementations per feature** - visual inconsistency and duplicate accessibility bugs, with no single owner.
- **Design system owned by nobody** - it rots into "legacy components" that new work refuses to use.
