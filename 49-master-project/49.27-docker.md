### The Multi-Stage Build

```dockerfile
# syntax=docker/dockerfile:1.7

# ---- deps: install once, cache aggressively ----
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --ignore-scripts

# ---- build ----
FROM node:22-slim AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

# ---- runtime: only what is needed to run ----
FROM node:22-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production
RUN useradd --system --uid 10001 app

# standalone output: the traced subset of node_modules
COPY --from=build --chown=app:app /app/.next/standalone ./
COPY --from=build --chown=app:app /app/.next/static ./.next/static
COPY --from=build --chown=app:app /app/public ./public

USER app
EXPOSE 3000
HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/api/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

CMD ["node", "server.js"]
```

Two decisions carry most of the value: **`--ignore-scripts` on install** (a compromised dependency postinstall cannot run in your build) and **standalone output** (the runtime image carries only the traced modules instead of a full `node_modules`).

### Layer Caching

```dockerignore
node_modules
.next
.git
.github
**/*.test.ts
**/*.test.tsx
e2e
coverage
*.md
.env*
```

Copying the lockfile before the source is what makes caching work: as long as dependencies do not change, `npm ci` is a cache hit and rebuilds take seconds instead of minutes.

### Healthcheck And Shutdown

const server = createSyncServer();

process.on('SIGTERM', async () => {
  console.log('SIGTERM: draining');
  server.stopAccepting();                        // stop new connections
  await server.drain({ timeoutMs: 15_000 });     // let live sessions finish a message
  await db.close();

  process.exit(0);

### Deeper Explanation: Same Artefact Everywhere

The point of a container for this project is not isolation - it is **artefact identity**. The image that ran in CI with green tests is byte-for-byte the image in production. No "works on my machine", no dependency drift between environments, no rebuild that silently picks up a newer patch version.

The professional habit that follows: build the image once, tag it by commit SHA, promote that exact digest through staging and production. Any process that rebuilds per environment reintroduces the gap containers exist to close.

### Additional Pitfalls

- **`COPY . .` before `npm ci`.** Every source edit invalidates the dependency layer; builds take minutes forever.
- **Alpine for a native module.** musl vs glibc breaks prebuilt binaries (canvas, sharp); use `-slim` Debian.
- **Secrets via `ENV` or `ARG`.** They persist in image layers and are readable with `docker history`.
- **Running as root.** A container escape is now a host escape; `USER app` is one line.
- **No `SIGTERM` handling.** Every deploy drops in-flight WebSocket sessions and users see a reconnect storm.

### Real-World Deal-Breakers
- **Secrets baked into an image** - anyone who can pull the image has your database credentials.
- **Root user in production** - any RCE is escalation to the host, and it violates most compliance regimes.
- **No healthcheck** - the orchestrator routes traffic to a container that is not ready and users get 502s.
- **Untagged `latest` in production** - a redeploy silently changes the running software with no version to roll back to.
- **Unpinned base images** - a base-image update changes runtime behaviour between two deploys of identical code.
