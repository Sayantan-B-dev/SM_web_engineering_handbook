### `git bisect` - Binary Search for Bugs
Git bisect uses binary search through commit history to find the commit that introduced a bug.

```bash
# Start bisect
git bisect start

# Mark current commit as bad
git bisect bad

# Mark a known-good commit
git bisect good v1.2.0

# Git checks out a middle commit - test it
# Then mark it:
git bisect good   # or git bisect bad

# Repeat until Git identifies the first bad commit

# End bisect
git bisect reset
```

Source: 

**Real-world trick**: Automate bisect with a test script: `git bisect run npm test`. Git runs the script on each commit and marks it good/bad automatically.

### `git worktree` - Multiple Working Directories
A Git worktree is a **linked working directory that shares the same `.git` data** as your main checkout. This lets you have multiple branches checked out simultaneously in different directories.

```bash
# Create a new worktree for a feature branch
git worktree add ../my-feature feat/user-auth

# List worktrees
git worktree list

# Remove a worktree
git worktree remove ../my-feature
```

Source: 

**Use case**: Parallel development without `git stash`. Work on a hotfix while a feature branch is still checked out. Also useful for parallel AI coding agents.

### `git subtree` vs `git submodule`

| | Submodule | Subtree |
|--|-----------|---------|
| **How it works** | Pointer to a specific commit in another repo | Copies the entire external repo into a subdirectory |
| **Metadata** | `.gitmodules` file | None |
| **User experience** | Requires `git submodule init && git submodule update` | Just `git clone` |
| **Editing** | Can edit in the submodule | Can edit directly in the subtree |
| **Best for** | Referencing a library you don't edit | Embedding a library you might edit |

Subtrees do not need any special constructions (like `.gitmodules` files or gitlinks) to be present in your repository, and do not force end-users to know about the subproject.

### `git LFS` - Large File Storage
Git LFS stores **pointer files** in the repository while storing the actual file contents on a Git LFS server. This keeps the repository small while versioning large binaries.

```bash
# Install Git LFS
git lfs install

# Track large files
git lfs track "*.psd"
git lfs track "*.zip"

# This creates .gitattributes - commit it
git add .gitattributes

# Add and commit as normal
git add large-file.psd
git commit -m "feat: add design asset"
```

Source: 

**Use cases**: Design assets (PSD, AI), datasets (CSV, parquet), videos, ML models, compiled binaries.

**Warning**: Git LFS is **not a panacea**. LFS file sizes count toward your repository's total size. GitHub's free tier includes 1GB LFS storage and 1GB bandwidth per month.

### Deeper Explanation: The Recovery And Investigation Toolkit

These commands turn Git from a version control system into a forensic tool:

| Tool | Answers |
|---|---|
| `git bisect` (with `run`) | Which commit introduced the bug? |
| `git blame -w -C -L` | Who last changed these lines, and which commit moved them? |
| `git log -S"symbol"` (pickaxe) | When did this string appear or disappear? |
| `git worktree add` | How do I work on two branches at once? |
| `git stash --include-untracked` / `git worktree` | Park work safely while switching |
| `git rerere` | Reuse a conflict resolution |
| `git reflog` + `git fsck` | Recover "lost" commits |
| `git notes` / `git range-diff` | Annotate commits; compare rebased series |

`git bisect run pnpm test` is the highest-leverage one: it binary-searches a regression to a single commit automatically, which is often faster than reasoning about the code.

### Additional Pitfalls
- **Manual bisect guessing.** Use `bisect run` with a fast, deterministic test.
- **`git blame` read as authorship.** It reports the last touching commit; moves and reformat dominate.
- **Feature-branch work blocked on a dirty tree.** Worktrees are the clean answer.
- **Rewrite recovery without the reflog.** It is time-limited by GC; recover promptly.
- **Ignore `range-diff` when reviewing a rebased PR.** It shows what actually changed between versions.

### Real-World Deal-Breakers
- **No `git bisect`** → spending hours manually finding a regression. `git bisect` finds it in minutes.
- **Using `git stash` for parallel work** → stash is error-prone and easy to forget. Use `git worktree` instead.
- **Submodule for a library you edit** → painful workflow. Use subtree or a monorepo.
- **Large binaries in Git without LFS** → repository becomes gigabytes. Clone takes minutes. Use LFS.
