## 41.4 Conventional Commits

### Subtopic Tree
- Format: `<type>[optional scope]: <description>`
- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`
- Breaking changes: `!` or `BREAKING CHANGE:`
- Commit body and footer
- SemVer correlation
- Commitlint (automated enforcement)
- Commitizen (interactive CLI)

### The Specification
Conventional Commits is a lightweight convention on top of commit messages. It provides an easy set of rules for creating an explicit commit history, which makes it easier to write automated tools on top of. This convention dovetails with SemVer, by describing the features, fixes, and breaking changes made in commit messages.

### Types and SemVer Impact

| Type | Description | SemVer Impact |
|------|-------------|---------------|
| `feat` | New feature | **MINOR** |
| `fix` | Bug fix | **PATCH** |
| `docs` | Documentation only | None |
| `style` | Formatting, missing semicolons | None |
| `refactor` | Code change (no feature, no bug fix) | None |
| `perf` | Performance improvement | **PATCH** |
| `test` | Adding or correcting tests | None |
| `build` | Build system or dependencies | None |
| `ci` | CI configuration | None |
| `chore` | Other changes (no src or test) | None |

### Breaking Changes
```bash
# Using ! after type
feat!: send an email to the customer when a product is shipped

# Using BREAKING CHANGE footer
feat: allow provided config object to extend other configs

BREAKING CHANGE: `extends` key in config file is now used for extending other config files
```

### Automated Enforcement with Commitlint
```json
// commitlint.config.js
module.exports = {
  extends: ['@commitlint/config-conventional'],
};
```

```yaml
# .github/workflows/commitlint.yml
name: Commitlint
on: [pull_request]
jobs:
  commitlint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: wagoid/commitlint-github-action@v6
```

### Deeper Explanation: Conventions Enable Automation

A commit convention (Conventional Commits being the common one) is only worth adopting if something consumes it: changelog generation, semantic version bumps, release automation, or search. That is the argument to make when introducing it â€” the benefit is automation, not tidiness.

Rolling it out safely: add commitlint in a non-blocking mode first, provide a commitizen-style prompt or a message template, enforce on PR titles as well (squash-merge users only produce one commit), and keep types small and meaningful. If your tooling needs `feat`/`fix` for semver, document which types trigger which bumps.

### Additional Pitfalls
- **Enforcing only locally.** Commits made in the GitHub UI bypass hooks; enforce in CI too.
- **Squash-merge projects ignoring PR titles.** The PR title becomes the commit message â€” validate it.
- **Types that nobody uses consistently.** Fewer, clearer types with examples beat a long taxonomy.
- **Convention without automation.** You get the overhead without the changelog.
- **Retro-fitting to a huge history.** Apply going forward; tools can normalise old history if needed.

### Real-World Deal-Breakers
- **Non-conventional commits** → automated tools can't generate changelogs or determine version bumps.
- **`fix` for a breaking change** → consumers don't know their code will break. Use `feat!` or `BREAKING CHANGE:`.
- **No body** → future maintainers don't know why the change was made.
- **Subject line over 72 characters** → truncated in `git log --oneline` and GitHub's UI.
