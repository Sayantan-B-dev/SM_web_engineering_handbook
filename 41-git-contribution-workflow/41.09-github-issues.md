### Issue Template Locations
GitHub scans the following locations for templates on the repository's **default branch**:

```
/.github/ISSUE_TEMPLATE/bug_report.md
/.github/ISSUE_TEMPLATE/config.yml
/.github/PULL_REQUEST_TEMPLATE.md
/.github/ISSUE_TEMPLATE/feature_request.md
```

Templates on non-default branches are **ignored**.

### When to Use Issue Templates
Use issue templates when you need **structured input from reporters** (bug reports, feature requests, support questions). Use pull request templates when you want every proposed change to follow a checklist that enforces testing, documentation, changelog updates, and links to related issues.

### Bug Report Template (Markdown)
```markdown
---
name: Bug report
about: Create a report to help us improve
title: '[BUG] '
labels: bug
assignees: ''
---

**Describe the bug**
A clear description of what the bug is.

**To Reproduce**
Steps to reproduce the behavior:
1. Go to '...'
2. Click on '....'
3. See error

**Expected behavior**
What you expected to happen.

**Screenshots**
If applicable, add screenshots.

**Environment:**
- OS: [e.g. macOS]
- Browser: [e.g. Chrome 131]
- Node: [e.g. 22.11.0]
```

### Issue Forms (YAML)
Structured issue forms use YAML and must be placed in `.github/ISSUE_TEMPLATE/`. These forms let you define fields, types, and validation to guide reporters more strictly.

Source: 

### `config.yml` for Template Chooser
When using multiple issue templates, include a `config.yml` inside `.github/ISSUE_TEMPLATE/` to control the template chooser, contact links, and whether blank issues are allowed.

Source: 

```yaml
# .github/ISSUE_TEMPLATE/config.yml
blank_issues_enabled: false
contact_links:
  - name: Community Support
    url: https://discord.gg/example
    about: Please ask questions here.
```

### Labels Every Project Needs
- **`good first issue`** - beginner-friendly, well-scoped
- **`help wanted`** - maintainers want outside help
- **`bug`** - something is broken
- **`enhancement`** - new feature request
- **`documentation`** - docs improvement
- **`triage`** - needs initial assessment

### Deeper Explanation: Issues Are A Work Queue And A Knowledge Base

An issue tracker has two jobs: queue work and record knowledge. The second is why closing with a reason matters â€” the next person searching for the same symptom should find the answer, not an empty thread. Good hygiene: link PRs, label consistently, and convert recurring questions into documentation so they stop arriving.

For engineering use, issues connect to commits through references (`Fixes #123`), which gives traceability from behaviour to code and back. For planning, milestones and projects convert a flat list into a schedule.

### Additional Pitfalls
- **Vague titles.** They make search useless; the title should describe the observable problem.
- **Issues closed without a reason or a link to the fix.**
- **Duplicates left open.** Link them so the discussion converges.
- **No triage labels.** Nobody can find the actionable work.
- **Feature requests accepted without scope discussion.** They sit forever and mislead users.

### Real-World Deal-Breakers
- **No issue templates** → vague bug reports ("it doesn't work"). Maintainers can't reproduce.
- **Templates on non-default branch** → GitHub ignores them. Always commit templates to `main`.
- **No `config.yml` with multiple templates** → users see a confusing template list without guidance.
- **No labels** → issues pile up untriaged. Contributors don't know which issues to pick.
