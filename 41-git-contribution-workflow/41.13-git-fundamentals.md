### The Three States of Git
```text
Working Directory → Staging Area (Index) → Repository (.git)
     git add              git commit
```

Git is a **distributed version control system**. Every clone is a full repository with complete history. There is no central server that holds the "real" copy - only conventions about which remote is authoritative.

### Core Commands
```bash
# Initialize a repository
git init

# Clone a repository
git clone https://github.com/user/repo.git

# Check status
git status

# Stage changes
git add file.txt
git add .           # stage everything

# Commit
git commit -m "feat: add user authentication"

# View history
git log --oneline --graph --all

# See who changed what
git blame src/services/user.ts

# Temporarily save work
git stash push -m "WIP: user service refactor"
git stash pop

# Apply a specific commit from another branch
git cherry-pick abc1234
```

### `git reflog` - The Safety Net
Git never truly deletes commits. Even after a `reset --hard` or a bad `rebase`, the commits remain in the reflog for ~90 days.

```bash
# See every position HEAD has been in
git reflog

# Recover a "lost" commit
git checkout HEAD@{5}
# Or create a branch from it
git branch recovery HEAD@{5}
```

**Real-world trick**: If you ever lose work to a bad rebase or reset, `git reflog` is the first place to look. It records every commit, checkout, merge, rebase, and reset.

### Deeper Explanation: The Three Trees And The Index

Git's day-to-day confusion comes from three places a file can be: the **working tree** (your edits), the **index/staging area** (what the next commit will contain), and **HEAD** (the last commit). ### Additional Pitfalls
- **`git add .` with generated files present.** Stage intentionally, or `.gitignore` them.
- **Mixing unrelated changes in one commit.** Split with `git add -p`; history stays reviewable.
- **Confusing `git restore` and `git reset`.** Reset moves HEAD (and optionally the index/working tree); restore only copies files.
- **Assuming a deleted branch is gone.** The reflog and `git fsck --lost-found` usually recover it.
- **Ignoring `.gitattributes`.** Line endings and binary handling differences cause enormous noise in diffs.

### Real-World Deal-Breakers
- **`git add .` without checking `git status`** → staging `.env`, build artifacts, or large binaries. Always review what you're staging.
- **Committing directly to `main`** → no review, no CI. Always use a feature branch.
- **Force-pushing to a shared branch** → destroys others' work. Never force-push to `main` or any branch others have pulled.
- **Not using `.gitignore`** → `node_modules/`, `.env`, `dist/`, `.DS_Store` committed to the repo. Bloats the repository and leaks secrets.
