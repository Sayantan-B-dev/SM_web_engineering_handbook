### Default PR Template
Create `.github/PULL_REQUEST_TEMPLATE.md`. When a new PR is created, the template content automatically populates the PR description.

Source: 

```markdown
## What
<!-- Describe the change -->

## Why
<!-- Link to the issue: Fixes #123 -->

## How
<!-- Describe the approach -->

## Checklist
- [ ] Tests added/updated
- [ ] Documentation updated
- [ ] No breaking changes
- [ ] Changelog updated (if applicable)

## Screenshots
<!-- For UI changes -->
```

### Multiple PR Templates
GitHub supports multiple PR templates, but they're less common than multiple issue templates. You can place them in `.github/PULL_REQUEST_TEMPLATE/` and select them via query parameter (`?template=bugfix.md`).

---

### Deeper Explanation: The Template Is The Review Contract

A PR template encodes the checklist reviewers would otherwise repeat: what changed, why, how it was verified, and what risk it carries. Because it is rendered into every PR body, it is also the cheapest way to make the description non-empty.

Practical design: keep it short enough to be filled honestly (five sections maximum), use checkboxes for things the author must confirm, and vary it by path when needed (`.github/PULL_REQUEST_TEMPLATE/` for a frontend template vs a migration template). ### Additional Pitfalls
- **A 20-item template.** Authors delete it or tick everything without reading.
- **Checkboxes for things CI already verifies.** Redundant and easy to fake.
- **No "how to test".** The most valuable section is the one most often missing.
- **One template for every change type.** Migrations and docs need different prompts.
- **Template drift.** Review it when the review process changes.

### Real-World Deal-Breakers
- **No PR template** → every PR has a different structure. Reviewers don't know what to expect.
- **Template with too many checkboxes** → contributors ignore them. Keep the checklist short and meaningful.
- **Template not on default branch** → GitHub ignores it. Commit to `main`.
