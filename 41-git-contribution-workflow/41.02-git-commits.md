### Atomic Commits
A commit should represent **one logical change**. This makes the history bisectable, reviewable, and revertable.

```bash
# ❌ BAD - multiple unrelated changes in one commit
git commit -m "fix login, update deps, add dark mode"

# ✅ GOOD - separate commits
git commit -m "fix(auth): resolve redirect loop on login"
git commit -m "chore(deps): upgrade react to 19.2"
git commit -m "feat(ui): add dark mode toggle"
```

**Rule**: If you need to use "and" in the commit message, it should be two commits.

### Commit Message Format
```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

**Subject line rules:**
- Maximum 50 characters (soft limit)
- Imperative mood: "add feature" not "added feature"
- No period at the end
- Lowercase first word (unless proper noun)

**Body rules:**
- Explain the **problem** the change solves
- Justify **why** the solution is better
- Note alternate solutions considered but discarded
- Use present tense for current state, imperative for changes

### Amending Commits
```bash
# Fix the last commit message
git commit --amend

# Add forgotten files to the last commit
git add forgotten-file.ts
git commit --amend --no-edit

# ⚠️ Only amend commits that haven't been pushed to a shared branch
```

### Reverting vs Resetting

| Command | What it does | Safe for shared branches? |
|---------|-------------|--------------------------|
| `git revert <commit>` | Creates a **new** commit that undoes the changes | ✅ Yes |
| `git reset --soft` | Moves HEAD, keeps changes staged | ❌ Rewrites history |
| `git reset --mixed` | Moves HEAD, unstages changes | ❌ Rewrites history |
| `git reset --hard` | Moves HEAD, **discards** changes | ❌ Dangerous |

**Rule**: Use `git revert` on shared branches. Use `git reset` only on local, unpushed commits.

### Signed Commits
```bash
# GPG signing
git config --global user.signingkey <GPG_KEY_ID>
git commit -S -m "feat: add feature"

# SSH signing (simpler)
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git commit -S -m "feat: add feature"
```

### Signed-off-by (DCO)
The Developer Certificate of Origin is a lightweight alternative to a CLA. Adding `Signed-off-by` certifies that you have the right to submit the contribution.

```bash
git commit -s -m "feat: add feature"
# → Signed-off-by: Random J Developer <random@developer.example.org>
```

### Deeper Explanation: Commits Are The Project's Reasoning

A commit is a unit of reasoning: it should contain one logical change with a message that explains **why**. History is read far more often than it is written (bisect, blame, incident forensics), and a well-formed message is the cheapest documentation you will ever produce.

The practical standard: imperative summary under ~72 characters, a body explaining context and alternatives when it is non-obvious, and references (`Refs #123`) in the footer. Commit early and often locally, then tidy with an interactive rebase before sharing â€” you get safety during work and clarity in history after.

### Additional Pitfalls
- **Giant "misc fixes" commits.** They break bisect and make revert impossible.
- **Messages that restate the diff.** "Add `useMemo`" adds nothing; say why the render was slow.
- **Committing generated artifacts and lockfile churn with source changes.**
- **Rewriting shared history.** Rebase before pushing, not after others pulled.
- **Losing reasoning in squashes.** If you squash, put the reasoning in the final message.

### Real-World Deal-Breakers
- **Non-atomic commits** → impossible to revert one change without affecting others.
- **Vague commit messages** ("fix bug", "update") → history is useless. Six months later, no one knows what changed.
- **Amending pushed commits** → rewriting shared history breaks everyone who pulled. Only amend unpushed commits.
- **No signed commits** → you can't verify who actually authored a commit. Sign commits for security-critical projects.
