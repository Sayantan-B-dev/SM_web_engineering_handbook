### What Rebase Does
`git rebase origin/main` takes your branch's commits, rewinds them, applies `main`'s new commits on top of the base, and then reapplies your commits one by one. The history becomes a straight line. The merge commit is gone because the commit graph no longer has a fork.

### Rebase vs Merge

| | Merge | Rebase |
|--|-------|--------|
| **History** | Preserves branch structure | Linear |
| **Merge commit** | Yes | No |
| **Commit SHAs** | Unchanged | Rewritten |
| **Safe for shared branches** | ✅ Yes | ❌ No |
| **Audit trail** | Concrete | Lost |

### Interactive Rebase
```bash
# Rebase the last 5 commits interactively
git rebase -i HEAD~5
```

This opens an editor with a list of commits:
```
pick abc1234 feat: add user model
pick def5678 fix: handle null email
pick ghi9012 chore: update deps
pick jkl3456 feat: add auth middleware

# Commands:
# p, pick   = use commit
# r, reword = use commit, edit message
# e, edit   = use commit, stop to amend
# s, squash = use commit, meld into previous
# f, fixup  = like squash, discard message
# d, drop   = remove commit
```

**Squashing commits:**
```
pick abc1234 feat: add user model
squash def5678 fix: handle null email  # melds into previous
pick ghi9012 chore: update deps
drop jkl3456 feat: add auth middleware   # removed
```

### The Golden Rule of Rebasing
**Never rebase a branch that others have pulled.** Rebase rewrites commit SHAs. If someone else has your old commits, their history diverges from yours, and the recovery is awkward.

Source: 

### `git pull --rebase`
```bash
# Instead of merge-based pull, rebase your local commits on top of remote
git pull --rebase origin main
```
This keeps your local history linear instead of creating unnecessary merge commits.

---

### Deeper Explanation: Rebase Rewrites, Merge Records

Rebase replays your commits onto a new base, producing new commit objects: history becomes linear and each commit appears to have been written against the latest base. Merge preserves what actually happened, including when branches diverged. Neither is "correct"; the choice is about what your history should communicate.

The rules that keep rebasing safe: rebase your own unpushed (or PR-scoped) history freely, rebase before requesting review to resolve conflicts with `main`, never rebase a branch someone else has built on, and use `--force-with-lease` (never plain `--force`) when pushing a rebased branch so you cannot clobber unseen work. `git rebase -i` for tidying, `--onto` for moving a branch, `--autosquash` with `fixup!` commits for a fast review-fix cycle.

### Additional Pitfalls
- **`--force` instead of `--force-with-lease`.** You can overwrite a colleague's commits.
- **Rebasing a long branch repeatedly.** Conflict resolution cost grows; rebase often or merge.
- **Rebasing after review approval.** The approval may now refer to different commits; re-request review.
- **Losing a conflict resolution mid-rebase.** Use `git rerere` and understand `--abort`/`--continue`.
- **Interactive rebase on shared branches.** Rewriting published commits breaks everyone's clone.

### Real-World Deal-Breakers
- **Rebasing a shared branch** → everyone who pulled the branch now has divergent history. The recovery is painful.
- **Force-pushing after rebase without `--force-with-lease`** → overwrites others' work on the remote. Always use `--force-with-lease`.
- **Rebasing `main` onto a feature branch** → wrong direction. You rebase your feature branch onto `main`, not the other way around.
- **Not using `--force-with-lease`** → `git push --force` overwrites remote even if someone else pushed. `--force-with-lease` refuses if the remote has changed.
