### Versioning
Use **Semantic Versioning** (`MAJOR.MINOR.PATCH`) so the number means something. Keep a human-readable changelog in a `CHANGELOG.md` with an `## [Unreleased]` section you fill in as you go, so cutting a release is just renaming a heading. Let a **tag trigger the build** - publishing artifacts by hand is how you ship the wrong binary at 2 a.m.

### Git Tags

| Type | Command | When to use |
|------|---------|-------------|
| **Lightweight** | `git tag v1.0.0` | Temporary, local tags |
| **Annotated** | `git tag -a v1.0.0 -m "Release 1.0.0"` | Releases - includes metadata |

```bash
# Create annotated tag
git tag -a v1.2.0 -m "Release 1.2.0"

# Push tag to remote
git push origin v1.2.0

# List tags
git tag -l

# Delete a tag
git tag -d v1.2.0
git push origin --delete v1.2.0
```

### Tag-Only Versioning
A modern approach: **eliminate committed version files entirely**. Version is derived from git tags via the GitHub Releases API. When CI needs to record metadata (version numbers, changelogs), prefer API artifacts (tags, releases) over committed files. Committed files require write access to protected branches and create merge conflicts.

### Automated Release Workflow (GitHub Actions)
```yaml
name: Release
on:
  push:
    tags:
      - 'v*'
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
```

### Monorepo Releases
For monorepo releases with **2-3 app components**, the reusable workflow pattern is justified. Use a single GitHub Action that runs at merge time: reads the label, bumps version files, auto-computes counts, commits atomically, creates a GitHub Release, and posts to Discord.

### Deeper Explanation: A Release Is A Reproducible Artifact Plus Communication

Release management is three activities: cut a version from a known-good commit, publish the artifact and its notes, and be able to roll back. Automating all three is what makes frequent releases safe.

```bash
# Tag-driven release: the tag is the source of truth
git tag -a v1.4.0 -m "v1.4.0" && git push origin v1.4.0
# CI then: build once -> attest/provenance -> publish -> create GitHub release with the changelog
```

```yaml
# Release workflow on a tag, using the same artifact CI already verified
on:
  push:
    tags: ['v*']
jobs:
  publish:
    runs-on: ubuntu-latest
    permissions: { contents: write, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install --frozen-lockfile && pnpm build
      - run: npm publish --provenance --access public
        env: { NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }} }
```

### Additional Pitfalls
- **Rebuilding at release time.** The artifact must be the one you tested; promote, do not rebuild.
- **Manual version bumps.** They drift from tags and changelogs; automate from commit types.
- **No rollback plan for a published version.** Deprecate with a message pointing to the fix.
- **Release notes written by hand late.** Generate from commits, then edit the summary.
- **No provenance/attestation.** Consumers cannot verify what they installed.

### Real-World Deal-Breakers
- **Manual artifact publishing** → you ship the wrong binary at 2 a.m. Let a tag trigger the build.
- **Committed version files** → merge conflicts and require write access to protected branches. Use tag-only versioning.
- **No changelog** → users don't know what changed between versions.
- **No pre-release cycle** → users get broken releases. Use `alpha`, `beta`, `rc` tags before final release.
