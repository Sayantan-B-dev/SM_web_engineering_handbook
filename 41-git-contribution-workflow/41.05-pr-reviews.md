### GitHub Review Statuses

| Status | Meaning | When to use |
|--------|---------|-------------|
| **Comment** | Feedback without approval/rejection | Questions, suggestions |
| **Approve** | Formal sign-off | Code is ready to merge |
| **Request Changes** | Blocking issues | Critical bugs, security issues |

### Reviewer Responsibilities

**What to check:**
- **Correctness** - Does the code do what it claims?
- **Quality** - Is it readable, maintainable, well-structured?
- **Standards** - Does it follow team conventions?
- **Edge cases** - Are errors and edge cases handled?
- **Security** - Are there security concerns?
- **Performance** - Any obvious performance issues?

Source: 

**Review etiquette:**
- Be kind and constructive
- Ask questions rather than make demands
- Explain the "why" behind suggestions
- Approve if changes are good enough (don't be a perfectionist)
- Respond within 1 business day if able

Source: 

### Constructive Feedback Examples
```markdown
# ❌ Destructive
"This is wrong."

# ✅ Constructive
"This will throw if `user` is null. Consider adding a null check or using optional chaining: `user?.name`."

# ✅ Nitpick (non-blocking)
"nit: Could we rename `data` to `userData` for clarity?"

# ✅ Question
"Why did we choose `useEffect` here instead of a derived value?"
```

### Author Responsibilities
- Read all feedback carefully
- Ask questions if feedback is unclear
- Make requested changes or discuss alternatives
- **Respond to all comments** (even if just "Fixed" or "Done")
- Request re-review after changes

Source: 

### Review Timelines
- **Target response**: within 24 hours
- **Follow up**: if no response after 14 days, reviewer returns to the PR
- **Stale PRs**: close after a defined period (e.g., 30 days) if no activity

### Self-Review Before Requesting Review
Authors should **review their own diff** before requesting review and check whether the PR is understandable, sufficiently scoped, and small enough.

### Deeper Explanation: Reviews Are A Service With An SLA

Review latency is throughput: a PR waiting two days blocks a person, discourages small PRs, and encourages bigger batches. Treat review as a scheduled activity with a commitment â€” for example, first response within one business day â€” and make the review itself specific and prioritised: correctness first, then safety, tests, readability, and style (mostly automated).

Two habits keep it constructive: ask questions rather than issuing verdicts ("what happens if `items` is empty?"), and separate blocking from non-blocking with explicit prefixes. As an author, reduce the reviewer's work: a small diff, a clear description, and a self-review pass before requesting.

### Additional Pitfalls
- **Silent approvals.** No comments is not review; at minimum confirm what you checked.
- **Blocking on preference.** Distinguish "this is wrong" from "I would have written it differently".
- **Reviewing after the fact (merged).** The feedback becomes archaeology.
- **No priority signalling.** Without "blocking"/"nit", authors guess and either overreact or ignore.
- **Never reviewing, only opening PRs.** Reciprocity is what keeps a review culture alive.

### Real-World Deal-Breakers
- **Approving without reading** → bugs ship to production. Don't merge PRs you've only skimmed.
- **Requesting changes without explanation** → author doesn't know what to fix.
- **Not responding to review comments** → PR stalls indefinitely.
- **Taking review personally** → review feedback is the process working, not a personal attack.
- **Reviewing your own PR and self-approving** → defeats the purpose of review.
