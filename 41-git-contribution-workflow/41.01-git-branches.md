## 41.1 Git Branches

### What a Branch Is
A branch in Git is simply a **lightweight movable pointer to a commit**. The default branch is `main` (formerly `master`). Creating a branch is O(1) - it writes a 41-byte file.

```bash
# Create and switch to a new branch
git switch -c feat/user-auth

# Create a branch without switching
git branch feat/user-auth

# List branches
git branch          # local
git branch -r       # remote
git branch -a       # all

# Switch branches
git switch main
git checkout main   # older syntax

# Delete a local branch
git branch -d feat/user-auth      # safe (merged)
git branch -D feat/user-auth      # force

# Delete a remote branch
git push origin --delete feat/user-auth

# Rename a branch
git branch -m old-name new-name
```

### Tracking Branches
A local branch can **track** a remote branch, so `git pull` and `git push` know where to go.

```bash
# Set upstream tracking
git push -u origin feat/user-auth

# Check tracking
git branch -vv

# Change upstream
git branch -u origin/main
```

### Detached HEAD
When you checkout a commit hash directly (not a branch), you're in "detached HEAD" state. New commits are not attached to any branch and can be lost.

```bash
# Detached HEAD - viewing a specific commit
git checkout abc1234

# Recovery: create a branch from here
git switch -c recovery-branch

# Or discard and return
git switch main
```

### Branch Naming Conventions

| Pattern | Example | Use |
|---------|---------|-----|
| `feature/` or `feat/` | `feat/user-auth` | New features |
| `fix/` or `bugfix/` | `fix/login-redirect` | Bug fixes |
| `hotfix/` | `hotfix/payment-crash` | Urgent production fixes |
| `chore/` | `chore/upgrade-deps` | Maintenance |
| `docs/` | `docs/api-reference` | Documentation |
| `refactor/` | `refactor/auth-service` | Code restructuring |
| `test/` | `test/user-service` | Tests only |

**Real-world trick**: Prefix branch names with the GitHub issue number when one exists: `feat/123-user-auth`. This creates an automatic link between the branch and the issue.

### Deeper Explanation: Cheap Pointers, Expensive Coordination

A branch costs nothing technically; the cost is coordination â€” merges, reviews, deployment timing, and the divergence that grows with time. That is why branch strategy is a process decision: short-lived branches keep integration risk low, long-lived ones accumulate it.

Useful mechanics: `git switch -c` to create, `git branch -vv` to see tracking and divergence, `git fetch --prune` to remove stale remote references, and `git push -u origin HEAD` to publish. For stacked work, keep each branch small and based on its parent so reviewers see isolated diffs.

### Additional Pitfalls
- **Branches that live for weeks.** Rebase or merge `main` frequently, or the eventual integration is a rewrite.
- **No naming convention.** Automation (ticket linking, environments) relies on predictable names.
- **Local branches that shadow remote ones confusingly.** Prune aggressively.
- **Force-pushing a shared branch.** Anyone who based work on it loses their base; coordinate first.
- **Forgetting to delete merged branches.** Clutter hides real work and slows tooling.

### Real-World Deal-Breakers
- **Long-lived feature branches** → merge hell. Branches should live days, not weeks. If a branch lives more than a week, it's too large or the team is too slow to review.
- **No branch protection** → anyone can force-push to `main`, delete branches, or merge without review. Enable branch protection rules.
- **Not deleting merged branches** → branch list becomes unmanageable. Delete after merge.
- **Working in detached HEAD** → commits not attached to any branch; lost when you switch away. Always create a branch before committing.
