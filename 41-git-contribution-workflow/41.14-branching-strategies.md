## 41.2 Branching Strategies

### Subtopic Tree
- GitHub Flow (simple, branch-based)
- Git Flow (develop, release, hotfix branches)
- Trunk-Based Development
- GitLab Flow (environment-based)
- One-Flow (simplified Git Flow)
- Stacked PRs
- Choosing a strategy by team size, release cadence, and CI/CD maturity

### Strategy Comparison

| Factor | Git Flow | GitHub Flow | Trunk-Based |
|--------|----------|-------------|-------------|
| **Release frequency** | Monthly+ | Weekly | Multiple/day |
| **Team size** | Large (10+) | Medium (5-15) | Small-Medium (3-10) |
| **CI/CD maturity** | Basic | Intermediate | Advanced |
| **Complexity** | High | Low | Low |
| **Long-lived branches** | Yes (`main`, `develop`) | No | No |
| **Best for** | Regulated, scheduled releases | Web apps, SaaS | High-performing teams |

### GitHub Flow (The Default for Most Teams)
```text
main ─────●─────────●─────────●────── (always deployable)
           \       / \       /
            ●─────●   ●─────●
          feature  feature
```

**Rules:**
- `main` is always deployable.
- Every change is a short-lived branch.
- PRs are reviewed and CI-validated before merge.
- Merge to `main` triggers immediate deployment.

Source: 

### Git Flow (For Regulated/Scheduled Releases)
```text
main      ─────●───────────────●─────────
                \             /
develop   ───●───●───●───●───●───●───●───
              \     / \     /
feature        ●───●   ●───●
```

**Branches:**
- `main` - production releases only
- `develop` - integration branch
- `feature/*` - new features
- `release/*` - release preparation
- `hotfix/*` - urgent production fixes

Source: 

### Trunk-Based Development (For High-Performing Teams)
```text
main ─────●───●───●───●───●───●───●───
          (small commits, no long-lived branches)
```

**Rules:**
- Everyone commits to `main` (or short-lived branches <1 day).
- Feature flags hide incomplete work.
- Requires strong CI/CD.

### One-Flow (Simplified Git Flow)
For teams that need Git Flow's structure but find it too complex: **removes the `develop` branch**. Features and hotfixes all branch off and merge back into `main`.

Source: 

### Stacked PRs
For large features, **stacked PRs** break work into a chain of small, dependent PRs. Each PR is reviewable independently, and they merge in order. Best for expert teams and large features.

Source: 

### Decision Guide

| Situation | Recommended strategy |
|-----------|---------------------|
| Default | Trunk-Based with feature flags |
| Multiple environments (staging, prod) | GitLab Flow |
| Scheduled releases | Git Flow or One-Flow |
| Large features | Stacked PRs on trunk-based |
| Web apps, startups | GitHub Flow |

### Deeper Explanation: Release Topology Decides The Model

The model follows from two questions: how often do you deploy, and do you maintain multiple released versions?

| Model | Deploy cadence | Multi-version support | Cost |
|---|---|---|---|
| Trunk-based with flags | Continuous | No | Discipline, flags to clean up |
| GitHub flow | Continuous/weekly | No | Modest; needs strong tests |
| Release branches | Scheduled | Limited | Cherry-picks and drift |
| GitFlow | Scheduled | Yes (long LTS) | Complex, `develop` drifts from `main` |

For frontend products, trunk-based or GitHub flow with feature flags covers almost everything, and flags replace the need for long-lived branches. Reserve release branches (and GitFlow) for libraries or products with supported older versions that must receive fixes.

### Additional Pitfalls
- **Cherry-picking as the standard release path.** Conflicts and missed fixes follow.
- **A `develop` branch that is never deployed.** Tests lose meaning; production truth lives on `main`.
- **Feature flags with no expiry.** They become permanent branches in code; track and delete them.
- **No hotfix path defined.** During an incident people invent one, usually unsafely.
- **Mixed strategy per team.** Without one documented model, automation cannot be written.

### Real-World Deal-Breakers
- **Git Flow for a 5-person startup** → overkill. The `develop` branch adds ceremony without benefit. Use GitHub Flow.
- **Long-lived feature branches** → merge hell. Branch should live days, not weeks.
- **No feature flags for trunk-based** → incomplete work ships to production.
- **No branch protection** → force-pushes to `main`, direct commits, no CI. Enable protection rules.
