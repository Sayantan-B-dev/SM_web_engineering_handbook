### Writing a Good PR Description
```markdown
## What
Adds dark mode toggle to the settings page.

## Why
Closes #456. Users have requested this feature for months.

## How
- Added `useDarkMode` hook with localStorage persistence
- Added toggle component to Settings page
- Added `dark` class to `<html>` element
- Updated Tailwind config with dark mode variants

## Screenshots
| Light | Dark |
|-------|------|
| ![light](...) | ![dark](...) |

## Checklist
- [x] Tests added
- [x] Documentation updated
- [x] No breaking changes
```

### Linking Issues
```markdown
Fixes #456
Closes #456
Resolves #456
```
When the PR merges, GitHub automatically closes the linked issue.

### Draft PRs
Open a PR as **Draft** when you want early feedback but aren't ready for review. This signals "don't merge yet."

### PR Size
**Keep PRs small and focused.** One feature or fix per PR. Administration PRs should stay **below 500 changed lines**. Larger changes should be split into **stacked PRs** with a clear review order.

### Merge Strategies

| Strategy | How it works | When to use |
|----------|-------------|-------------|
| **Squash and merge** | All commits squashed into one | Open source default - clean history |
| **Merge commit** | Preserves all commits + merge commit | When individual commits matter |
| **Rebase and merge** | Replays commits onto base | Linear history without merge commit |

### Deeper Explanation: The PR Is The Unit Of Review And Deploy

In most teams, the pull request is where quality is decided and (with merge-on-green) where deployment is triggered. That makes the PR description, the diff size, and the CI signal the three levers that determine review quality.

```markdown
## What
Adds locale-aware currency formatting to `formatCurrency`.

## Why
`formatCurrency(10, 'EUR', 'de-DE')` returned `$10.00`, producing wrong prices for
German users (issue #412).

## How to test
- `pnpm test utils/formatCurrency`
- `/checkout` on a German locale: totals should render as `10,00 â‚¬`

## Checklist
- [x] Tests added for en-US, de-DE, ja-JP
- [x] Docs example updated
- [ ] Migration note needed? (no API change)
```

### Additional Pitfalls
- **PRs over ~400 lines.** Reviewer defect detection drops; split by concern.
- **No "how to test".** Reviewers guess, or approve without running it.
- **Mixed concerns.** Formatting plus logic changes hide the meaningful diff.
- **Approvals without engagement.** Required approvals only help if reviewers actually read.
- **Merge-on-green without required checks.** Automation is only as good as the checks behind it.

### Real-World Deal-Breakers
- **PR without a description** → reviewers don't know what changed or why.
- **PR with no linked issue** → maintainers can't trace the context.
- **PR too large (>500 lines)** → reviewers skim instead of review. Split into stacked PRs.
- **No CI passing** → maintainers won't review until CI is green.
- **Force-pushing after review** → reviewer comments become stale. Use `--force-with-lease` and add a comment explaining what changed.
