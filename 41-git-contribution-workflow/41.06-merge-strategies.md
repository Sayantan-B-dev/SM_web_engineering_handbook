## 41.6 Merge Strategies

### Subtopic Tree
- Merge commit (`--no-ff`)
- Squash merge (`--squash`)
- Rebase and merge (`--rebase`)
- Fast-forward merge
- When to use each

### The Three Strategies

| Strategy | How it works | When to use |
|----------|-------------|-------------|
| **Merge commit** | Preserves all commits + adds a merge commit | When individual commits matter and full history is wanted |
| **Squash and merge** | All commits squashed into one on the base branch | A PR represents one logical change |
| **Rebase and merge** | Replays commits onto base with no merge commit | The team wants a clean, linear log |

### Merge Commit (`--no-ff`)
```bash
git checkout main
git merge --no-ff feature-branch
```
Creates a merge commit even if fast-forward is possible. Preserves the branch structure. Useful for GitFlow and long-lived features.

Source: 

### Squash Merge (`--squash`)
```bash
git checkout main
git merge --squash feature-branch
git commit -m "feat: add user authentication (#123)"
```
All commits from the feature branch become **one commit** on `main`. Clean history, one commit per feature. The default on GitHub for many projects.

Source: 

### Rebase and Merge (`--rebase`)
```bash
git checkout feature-branch
git rebase main
git checkout main
git merge feature-branch  # fast-forward
```
Replays the feature branch commits onto `main` with **no merge commit**. Linear history. Each commit is preserved.

Source: 

### Fast-Forward Merge
```bash
git checkout main
git merge feature-branch  # fast-forwards if main hasn't diverged
```
If `main` hasn't moved since the feature branch was created, Git simply moves the `main` pointer forward. No merge commit. Only possible when there's no divergence.

### Deeper Explanation: History Shape Is A Communication Choice

| Strategy | History | Use when |
|---|---|---|
| Merge commit | Preserves branch topology | You want the decision context and branch boundaries |
| Squash | One commit per PR | Linear history, PRs are the unit of change |
| Rebase + merge (fast-forward) | Linear, each commit kept | Commits are individually meaningful and clean |
| Rebase + merge commit | Linear plus a merge node | You want grouping without losing individual commits |

The practical rules: pick one per repository and document it, ensure that squash-merged PR titles follow the commit convention (they become the message), and never rebase commits that others have based work on. `git rerere` (reuse recorded resolution) is a small quality-of-life win when rebasing frequently.

### Additional Pitfalls
- **Mixed strategies.** History becomes unreadable and automation unreliable.
- **Squashing work-in-progress commits without editing the message.** The junk message becomes permanent.
- **Rebasing a branch others pulled.** Everyone's next pull becomes a conflict nightmare.
- **Merge conflicts resolved by taking "ours" wholesale.** Silent regressions; review the resolution.
- **Lost context from over-squashing.** Large features lose the reasoning of intermediate steps.

### Real-World Deal-Breakers
- **Merge commits on `main`** → cluttered history. If the team wants linear history, use squash or rebase.
- **Squash merge for multi-commit PRs** → individual commits lost. If the individual commits matter, use rebase.
- **Rebase and merge on a shared branch** → rewrites history. Only rebase branches that no one else has pulled.
- **No merge strategy documented** → every developer does it differently. Document the strategy in `CONTRIBUTING.md`.
