### What a Merge Conflict Is
A conflict occurs when the same lines were changed in both branches. Git stops and asks you to resolve it.

```text
<<<<<<< HEAD
const API_URL = 'https://api.example.com';
=======
const API_URL = 'https://api-v2.example.com';
>>>>>>> feature-branch
```

- `<<<<<<< HEAD` → your current branch's version
- `=======` → separator
- `>>>>>>> feature-branch` → incoming branch's version

### Resolving Conflicts
```bash
# See which files are conflicted
git status

# Edit the file to resolve
# Remove the markers and choose the correct code

# Stage the resolved file
git add --resolved recipe.txt  # Git 2.56+

# Continue the merge/rebase
git merge --continue
# Or for rebase:
git rebase --continue
```

### `git add --resolved` (Git 2.56+)
Git 2.56 introduced a safer way to stage resolved conflicts. `git add --resolved` considers **only paths that are currently unmerged** in the index. Before staging anything, it scans unmerged regular files for leftover conflict markers. If it finds one, it reports the affected paths and **leaves the index unchanged**.

```bash
# ❌ DANGEROUS - stages everything, including unrelated changes
git add -u

# ✅ SAFE - stages only resolved conflict files
git add --resolved
```

### Aborting a Merge or Rebase
```bash
# Abort merge
git merge --abort

# Abort rebase
git rebase --abort

# Abort cherry-pick
git cherry-pick --abort
```

### `git rerere` (Reuse Recorded Resolution)
`git rerere` records how you resolved a conflict and **automatically applies the same resolution** the next time it sees the same conflict. This is invaluable for long-lived branches that repeatedly merge `main`.

```bash
# Enable rerere globally
git config --global rerere.enabled true

# Or per-repository
git config rerere.enabled true
```

### Conflict Resolution Strategies
```bash
# Resolve all conflicts by taking your version
git merge -X ours feature-branch

# Resolve all conflicts by taking their version
git merge -X theirs feature-branch
```

Source: 

**Warning**: These strategies silently discard one side's changes. Use them only for files where you're certain one version is correct (e.g., lock files, generated code).

### Escalation
Conflicts must be **detected early and resolved intentionally** through ownership routing (CODEOWNERS) and explicit escalation. **Escalate when conflicts repeat** or when automated resolution fails twice.

### Deeper Explanation: Conflicts Are Information, Resolutions Are Decisions

A merge conflict means two changes touched the same lines; the resolution is a decision about intent, not a mechanical choice between "ours" and "theirs". The disciplined approach: understand both sides (read the base with `git log --merge` and the diff of each side), decide the correct combined result, then verify by building and running tests â€” since a syntactically valid resolution can still be semantically wrong.

Tools worth knowing: `git rerere` to reuse resolutions, `git mergetool`/editor three-pane views, `git checkout --ours/--theirs` for genuinely one-sided files (careful: their meaning inverts during rebase), and `git diff --diff-filter=U` to list unmerged paths.

### Additional Pitfalls
- **Resolving without reading the other side.** Regressions that appear only in production.
- **Assuming "ours"/"theirs" is stable.** In a rebase, "ours" is the branch you are rebasing onto.
- **Not running tests after resolution.** A valid-looking merge can break the build.
- **Binary/lockfile conflicts resolved by picking one side.** Regenerate lockfiles instead.
- **Huge conflicts from long-lived branches.** Prevent by rebasing frequently; resolution cost is superlinear.

### Real-World Deal-Breakers
- **`git add .` during a conflict** → stages unrelated changes and files with leftover conflict markers. Use `git add --resolved`.
- **Resolving conflicts without understanding both sides** → silent bugs. Read both versions and understand what changed.
- **`-X ours` or `-X theirs` for all conflicts** → silently discards one side's changes. Only use for generated files.
- **No `rerere`** → resolving the same conflict repeatedly on long-lived branches. Enable it.
- **Rebasing without `--abort` option** → stuck in rebase state. Know how to abort.
