### What Expo Is
Expo is a **framework and platform for React Native apps**. It provides:
- A set of pre-built native modules (`expo-camera`, `expo-location`, etc.)
- A file-based router (`expo-router`)
- Cloud build services (`EAS Build`)
- OTA updates (`expo-updates`)
- Development tools (`expo-dev-client`)

### Expo Modules API
As of SDK 53, **all `expo-*` packages support the New Architecture** (including bridgeless). All modules written using the **Expo Modules API** support the New Architecture **by default** - no additional work needed.

### Expo Go Limitations (2026)
Push notifications and Google Maps are **no longer supported in Expo Go** (warned in SDK 52, removed in SDK 53). For production apps, use **development builds** (`expo-dev-client`) which include your custom native modules.

### OTA Updates with Expo
OTA updates work with the New Architecture. The delivery mechanism is unaffected by JSI, TurboModules, and Fabric. The JavaScript bundle delivery mechanism is unchanged - `expo-updates` replaces the bundle on device, and the New Architecture handles the runtime communication.

### Deeper Explanation: The Managed-To-Native Spectrum

Expo's value is a curated toolchain: a managed workflow with prebuilt native modules, over-the-air updates (EAS Update), build services (EAS Build), and a consistent upgrade path. The engineering decision is where on the managed-to-bare spectrum to sit: fully managed is fastest to ship, custom native code requires a development build (bare-ish) but keeps Expo's tooling.

What this means in practice: start managed, add config plugins for native changes, create a development build as soon as a native module requires it, and treat OTA updates as a deployment channel with its own compatibility rules (an update must match the native binary's runtime version, or it will crash).

### Additional Pitfalls
- **OTA update published against a mismatched runtime version.** Instant crash on next launch; pin and test runtime versions.
- **Mixing conflicting native modules.** Version skew between Expo SDK and community modules is the most common build failure.
- **Ignoring EAS build caching and credentials.** Builds get slow and credentials drift; manage them explicitly.
- **Assuming Expo equals "no native code".** Anything non-standard requires a development build and prebuild.

### Real-World Deal-Breakers
- **Using Expo Go for production** → push notifications and Google Maps are unsupported. Use development builds.
- **Migrating from SDK 54 to SDK 55** → New Architecture is mandatory; legacy architecture is completely removed. Migrate all dependencies first.
- **Using `expo-av`** → deprecated in SDK 54. Migrate to `expo-audio` and `expo-video`.
- **Ignoring `expo-doctor`** → incompatible dependencies cause crashes in the New Architecture. Run `npx expo-doctor` before upgrading.
