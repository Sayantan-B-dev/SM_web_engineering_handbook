## 39.1 Architecture (New Architecture)

### Subtopic Tree
- JSI (JavaScript Interface) - replaces the Bridge
- Fabric - the new rendering pipeline
- TurboModules - lazy-loaded, type-safe native modules
- Codegen - generates native scaffolding from JS specs
- Hermes V1 - the JavaScript engine
- Worklets - multithreading for heavy computation
- Synchronous native communication
- The end of JSON serialization

### What Changed: Bridge → JSI
The legacy architecture communicated between JavaScript and native code through a **bridge** - an asynchronous serialization layer that passed JSON messages back and forth. Every interaction went through this bridge. It worked, but it was a source of **latency, memory overhead, and subtle timing issues** that became more pronounced as apps grew.

The New Architecture replaced the bridge with the **JavaScript Interface (JSI)** - a C++ layer that allows JavaScript and native code to hold **direct references to each other** and call across the boundary **synchronously without serialization**.

```text
Legacy:   JS → [JSON serialize] → Bridge → [JSON deserialize] → Native
New:      JS → [JSI direct call] → Native (C++)
```

### Fabric - The New Rendering Pipeline
Fabric replaced the legacy UI renderer - the component responsible for turning your React component tree into native UI elements. Fabric aligns with **React 18+ concurrent rendering** and allows fine-grained updates without blocking the UI thread.

**What Fabric enables:**
- Concurrent rendering (partial tree commits)
- Synchronous layout reads from JS
- Smoother lists, snappier gestures, better performance during frequent state changes
- Shadow Tree optimizations (coming in 2026)

### TurboModules - Lazy, Type-Safe Native Modules
TurboModules replaced the legacy native module system. Modules are now **loaded lazily on demand** rather than all at once at startup, improving startup performance significantly. TurboModules leverage JSI to improve how JavaScript communicates with native modules.

```typescript
// specs/NativeCalculator.ts - the spec file
import type {TurboModule} from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  readonly add: (a: number, b: number) => number;
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativeCalculator');
```

### Codegen - Type-Safe Native Scaffolding
Codegen reads your spec files (TypeScript or Flow) and generates the native scaffolding code for iOS and Android. This eliminates manual binding code and ensures type safety across the JS-native boundary.

### Hermes V1 - The JavaScript Engine
Hermes V1 is now the default JavaScript engine on both iOS and Android, following the initial experimental opt-in in React Native 0.82. It represents the next evolution of Hermes, with **significant improvements to both the compiler and VM** that deliver measurably better JavaScript performance.

**Key Hermes V1 features:**
- **Ahead-of-time bytecode compilation** - lower parse/compile time
- **Compact garbage collection** - smaller heap, faster GC, mobile-optimized
- **Smaller bundle sizes** vs JavaScriptCore
- **No migration required** - automatic performance gains for all apps

### Worklets - Multithreading Made Simple
React Native Worklets (built for Reanimated) have transformed into a **general-purpose concurrency engine**. They allow developers to run heavy computations, continuous processing, or real-time tasks **off the main JS thread**, keeping UIs and interactions smooth.

**In 2026, developers won't have to jump into native modules for many performance-critical tasks**. Worklets run in a separate, isolated runtime with low latency.

### Deeper Explanation: The New Architecture Changes What Is Possible

The legacy bridge serialised messages between JS and native, which made frequent cross-boundary work expensive. The New Architecture (Fabric for the UI, TurboModules for native calls, JSI for synchronous calls, Hermes, and codegen'd typed interfaces) removes most of that cost and enables synchronous native calls and concurrent React features.

Practical consequences:

- **Fewer "bridge" performance cliffs**, but you still pay for expensive work on the JS thread; long tasks block interactions just as on the web.
- **Concurrent features (transitions, `useDeferredValue`) work**, so lists and heavy screens can stay responsive with the same techniques as a web app.
- **Native modules are typed and generated** â€” a shared spec means the interface cannot drift from the implementation.
- **Enabling it requires native dependency compatibility.** Libraries without New Architecture support are the main migration blocker, so audit dependencies before upgrading.

### Additional Pitfalls
- **Assuming the new architecture removes all jank.** JS-thread work and excessive re-renders still drop frames.
- **Migrating with incompatible libraries.** Audit each native dependency before switching.
- **Ignoring codegen.** Hand-written native interfaces drift; use the generated specs.
- **No profiling.** Use the RN DevTools/Perfetto traces rather than guessing which thread is busy.

### Real-World Deal-Breakers
- **Still using the legacy bridge** → 42% slower startup, 30% jankier UI, 35% more memory.
- **Third-party libraries without New Architecture support** → crashes or no-op native calls. Use `npx expo-doctor` to validate dependencies.
- **Hermes V1 opt-out** → you lose significant performance gains. Only opt out if you have a specific compatibility need.
- **Assuming JSI eliminates all cross-boundary costs** → frequent cross-boundary calls can still hurt responsiveness. Batch read/write operations.
