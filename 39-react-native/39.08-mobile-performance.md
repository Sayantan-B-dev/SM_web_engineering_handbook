### The JS Thread vs UI Thread
React runs on a **JavaScript thread**; native views update on **UI threads** (per platform). Heavy synchronous JS work **drops frames (jank)** even if native GPU is idle. Profile JS frame time separately from layout cost.

### FlatList vs FlashList

| | FlatList | FlashList |
|--|----------|-----------|
| **Recycling** | Mounts/unmounts rows | **Recycles** row views |
| **Throughput** | Baseline | ~10× higher |
| **Memory** | Higher (unmount/remount churn) | Lower (reuse) |
| **API** | React Native default | Nearly drop-in replacement |

FlashList from Shopify gives roughly **10× the throughput** by recycling row views instead of mounting and unmounting them.

### `getItemLayout` - The Single Highest-Impact Optimization
`getItemLayout` is **consistently the highest-impact single FlatList optimization** - it **eliminates item height measurement entirely**.

```tsx
<FlatList
  data={items}
  renderItem={({ item }) => <Item item={item} />}
  keyExtractor={(item) => item.id} // Stable key
  getItemLayout={(data, index) => ({
    length: ITEM_HEIGHT,
    offset: ITEM_HEIGHT * index,
    index,
  })}
  windowSize={5}              // Render 5 screens worth
  initialNumToRender={10}     // Render 10 items initially
  maxToRenderPerBatch={5}     // Render 5 more per batch
  removeClippedSubviews={true} // Unmount offscreen items
/>
```

### Common FlatList Anti-Patterns
- **Unstable `keyExtractor`** → forces reconciliation churn and hurts scroll FPS
- **Inline `renderItem`** → new function every render
- **Heavy unmemoized rows** → each row re-renders on any parent change

### The 2026 Performance Playbook
1. **Enable the New Architecture first** (Fabric + TurboModules + JSI) - the gains are foundational, ~30% smoother UI rendering
2. **Default to FlashList, not FlatList**
3. **Use `getItemLayout`** for fixed-height items
4. **Memoize rows** with `React.memo` and stable keys
5. **Use Hermes V1** - automatic performance gains
6. **Offload heavy work to Worklets** - run off the main JS thread

### Deeper Explanation: Four Numbers And Four Fixes

Mobile performance is dominated by four measurable things: **JS-thread blocking** (long tasks from rendering/state), **list rendering** (unvirtualised long lists), **image cost** (oversized decodes and memory), and **startup** (time to interactive).

| Symptom | Likely cause | Fix |
|---|---|---|
| Janky scroll in a long list | All items rendered, heavy rows | `FlatList`/`FlashList`, memoised rows, `getItemLayout` |
| Dropped frames on interaction | Synchronous work on the JS thread | Move work to native or a worker-like task, defer with transitions |
| Rising memory then a crash | Large images held in memory | Resize/cache images, release on unmount |
| Slow cold start | Too much JS at boot, sync storage reads | Defer work, lazy screens, keep the initial bundle small |
| Battery drain | Polling, frequent timers, wakeups | Event-driven updates, batch network calls |

Measure with the platform profilers and the JS thread trace, on a real mid-tier device, and keep a performance budget in CI for startup and scroll smoothness.

### Additional Pitfalls
- **`ScrollView` with 500 items.** All of them render; use a virtualised list.
- **Inline functions and object props in list rows.** They defeat memoisation and re-render every row.
- **Unoptimised images.** Server-side resizing plus a caching image component is nearly always required.
- **Animating layout properties.** Use transforms on the native thread (Reanimated/Animated native driver).
- **Profiling on a flagship device only.** The p95 user is on something three years older.
- **No startup budget.** Cold start creep is invisible until it is five seconds.

### Real-World Deal-Breakers
- **Not using `getItemLayout`** → FlatList measures every item height dynamically, causing scroll jank.
- **Unstable `keyExtractor`** → reconciliation churn on every data change.
- **Heavy synchronous JS on the main thread** → drops frames even if the GPU is idle.
- **Using FlatList for large lists** → FlashList gives 10× throughput with recycling.
- **Not enabling the New Architecture** → missing 42% faster startup, 30% smoother UI, 35% less memory.
