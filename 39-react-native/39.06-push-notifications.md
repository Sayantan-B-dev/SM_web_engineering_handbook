### The Mental Model
Push is a three-party system: the OS provider (APNs/FCM) holds a device token, your server sends a payload to that token, and the app decides what to show and where to navigate. The part that most apps get wrong is that *delivery is best-effort* â€” the payload is a hint, not a data source. The reliable pattern is: notification carries an id, the app fetches the real state on open.

```ts
// Registration: permission first, then token, then sync it to your server
import * as Notifications from 'expo-notifications';

export async function registerForPush(userId: string) {
  const { status: existing } = await Notifications.getPermissionsAsync();
  const status = existing === 'granted' ? existing : (await Notifications.requestPermissionsAsync()).status;
  if (status !== 'granted') return { ok: false as const, reason: 'denied' as const };

  const token = (await Notifications.getExpoPushTokenAsync({ projectId: PROJECT_ID })).data;
  await api.post('/push/devices', { userId, token, platform: Platform.OS });
  return { ok: true as const, token };
}
```

### Real-World Deal-Breakers
- **Treating delivery as guaranteed.** Tokens expire, users disable notifications, providers throttle; the in-app inbox is the reliable channel.
- **Requesting permission on first launch.** Denied at a high rate and hard to recover; ask at the moment of value.
- **Trusting payload data as the source of truth.** It can be stale; fetch on open.
- **No token refresh or cleanup.** Sending to dead tokens wastes quota and hurts deliverability.
- **No user preferences.** Notification categories plus a settings screen are expected; a global on/off toggle is not enough.
- **Ignoring platform channel rules.** Android channels and iOS categories determine grouping and importance; they are code, not settings.
- **No deep-link QA.** A notification that opens the wrong screen is worse than none.
