## 11.1 React Server Components

### Subtopic Tree
- Definition: components that render ahead of time on server/build
- Async components (`await` in render)
- Zero JavaScript shipped to client
- Direct backend access (DB, filesystem, secrets)
- RSC Payload (serialized UI tree)
- No hooks, no state, no browser APIs
- Use cases: static content, data fetching, heavy libraries
- Build-time vs request-time execution

### What RSC Actually Are
React Server Components are a **new type of component** that renders ahead of time, before bundling, in an environment separate from your client app or SSR server. This separate environment is the "server" in RSC. They can run once at build time on CI, or on each request using a web server.

The core insight: **not every component needs to ship JavaScript to the browser**. A blog post renderer, a data table, a product card - these often have zero interactivity. Shipping React, the rendering libraries, and all the data-fetching code to the client is pure waste.

```jsx
// Server Component - no directive needed (default in RSC frameworks)
import marked from 'marked';        // 35.9K - NOT shipped to client
import sanitizeHtml from 'sanitize-html'; // 206K - NOT shipped to client

async function Page({ page }) {
  // Runs on the server during render
  const content = await file.readFile(`${page}.md`);
  return <div>{sanitizeHtml(marked(content))}</div>;
}
```

Without RSC, the same page would require:
1. Shipping `marked` and `sanitize-html` to the client (~75K gzipped).
2. A client-side fetch to an API route after first render.
3. A loading state while waiting for data.

With RSC, the client receives only the **rendered output** - the original `Page` component and its expensive libraries never reach the browser.

### Server Components Without a Server
RSC can run at **build time** to read from the filesystem or fetch static content - a web server is not required. The rendered output can be SSR'd to HTML and uploaded to a CDN. When the app loads, the client sees only the rendered HTML, not the component or its dependencies.

### RSC Payload
Server Components produce a **serialized UI tree** - called the RSC payload - which is streamed to the client as the component tree resolves. It's not HTML; it's a compact representation that React on the client can reconstruct into the DOM without re-running the server component code.

### What Server Components CANNOT Do
- Use hooks (`useState`, `useEffect`, etc.)
- Use browser APIs (`window`, `document`, `localStorage`)
- Attach event handlers (`onClick`, `onChange`)
- Be rendered from Client Components (only imported *into* them)

```jsx
// ❌ Server Component with client-only features
async function BadServerComponent() {
  const [count, setCount] = useState(0); // Error: hooks not allowed
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
  // Error: event handlers not allowed
}

// ✅ Server Component - pure data + markup
async function UserProfile({ id }) {
  const user = await db.user.findUnique({ where: { id } });
  return <div><h1>{user.name}</h1><p>{user.email}</p></div>;
}
```

### Real-World Deal-Breakers
- **Using hooks in Server Components** → build/runtime error. Server Components have a limited API.
- **Passing event handlers from Server → Client Components** → functions aren't serializable. Define handlers inside the Client Component instead.
- **Assuming RSC replaces SSR** → they're complementary. RSC renders the component tree; SSR renders HTML for the first paint.
- **Fetching data with `useEffect` in a Server Component** → `useEffect` doesn't exist on the server. `await` directly in the component body.
