### How Streaming Works
Instead of waiting for the entire page to render on the server before sending anything, streaming sends HTML in chunks as soon as each piece is ready.

```jsx
// Server
import { renderToPipeableStream } from 'react-dom/server';

const { pipe } = renderToPipeableStream(<App />, {
  bootstrapScripts: ['/main.js'],
  onShellReady() {
    res.setHeader('Content-Type', 'text/html');
    pipe(res);
  },
});
```

### Suspense Boundaries as Stream Points
Place `<Suspense>` boundaries around components that might delay the initial render. The browser receives the shell (header + fallbacks) immediately, then each Suspense boundary resolves and streams its content.

```jsx
function Page() {
  return (
    <>
      <Header /> {/* fast - part of shell */}
      <Suspense fallback={<FeedSkeleton />}>
        <Feed /> {/* slow - streams when ready */}
      </Suspense>
      <Suspense fallback={<SidebarSkeleton />}>
        <Sidebar /> {/* slower - streams separately */}
      </Suspense>
      <Footer /> {/* fast - part of shell */}
    </>
  );
}
```

### Out-of-Order Streaming
Late-arriving content doesn't block the rest of the page. When a slow component resolves, React injects its HTML into the correct slot via a hidden `<template>` and a small script.

### `use()` Hook for Promises
React 19's `use()` hook lets components consume promises directly, eliminating complex state management.

```jsx
async function Comments({ commentsPromise }) {
  const comments = await commentsPromise; // Server Component - await directly
  return <ul>{comments.map(c => <li key={c.id}>{c.text}</li>)}</ul>;
}

// Or with use() in Client Components
'use client';
import { use } from 'react';

function Comments({ commentsPromise }) {
  const comments = use(commentsPromise); // unwraps the promise
  return <ul>{comments.map(c => <li key={c.id}>{c.text}</li>)}</ul>;
}
```

### Nested Suspense
```jsx
<Suspense fallback={<PageSkeleton />}>
  <Suspense fallback={<SidebarSkeleton />}>
    <Sidebar />
  </Suspense>
  <Suspense fallback={<FeedSkeleton />}>
    <Feed />
  </Suspense>
</Suspense>
```
Each boundary is independent; only the innermost pending tree triggers its own fallback.

### Error Handling in Streams
React swallows errors on the server-side and retries the `<Suspense>` boundary on the client-side. If it fails again, the error boundary catches it.

### Real-World Deal-Breakers
- **No Suspense boundaries** → the entire page blocks until every async component resolves. ALWAYS wrap slow async components in `<Suspense>`.
- **Fallback very different from content** → CLS on hydration; use skeletons matching the final layout.
- **Too many nested Suspense boundaries** → visual jank as content pops in at different times. Group related content.
- **Suspense without error boundary** → if the suspended component throws, the error propagates and can crash the app.
