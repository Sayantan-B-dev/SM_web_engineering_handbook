## 34.12 Authentication

### Subtopic Tree
- Session-based auth (server stores session, cookie stores session ID)
- Token-based auth (JWT - stateless)
- OAuth 2.1 / OpenID Connect (delegated auth)
- Password hashing (bcrypt, Argon2id)
- Access token + refresh token pattern
- JWKS-based JWT validation
- Multi-factor authentication (MFA)
- Passkeys (WebAuthn)

### JWT Pattern (2026 Baseline)
```typescript
// Access token: JWT, 15min expiry, payload: { userId, email }
// Refresh token: JWT, 7d expiry, stored in httpOnly cookie

function generateTokens(userId: string) {
  const accessToken = jwt.sign(
    { userId, email: user.email },
    process.env.JWT_SECRET,
    { expiresIn: '15m' }
  );
  const refreshToken = jwt.sign(
    { userId },
    process.env.JWT_REFRESH_SECRET,
    { expiresIn: '7d' }
  );
  return { accessToken, refreshToken };
}

// Refresh token rotation: each refresh invalidates the old token
async function refresh(refreshToken: string) {
  const payload = jwt.verify(refreshToken, process.env.JWT_REFRESH_SECRET);

  // Check if token is blacklisted (rotation)
  if (await isBlacklisted(refreshToken)) throw new Error('Token reused');

  await blacklist(refreshToken); // invalidate old token
  return generateTokens(payload.userId);
}
```

### Password Hashing
```typescript
import { hash, verify } from '@node-rs/argon2';

const passwordHash = await hash(password, {
  memoryCost: 19456, // 19 MiB
  timeCost: 2,
  parallelism: 1,
});

const valid = await verify(passwordHash, password);
```

**Argon2id** is the 2026 recommended password hashing algorithm (winner of the Password Hashing Competition). bcrypt is still acceptable but slower.

### Deeper Explanation: Authentication Is A Series Of Boundaries

Authn answers "who is this?" across several boundaries: credential collection, verification, session establishment, session transport, and session invalidation. Each has a standard answer and a common mistake:

| Boundary | Standard answer | Common mistake |
|---|---|---|
| Password storage | Argon2id/bcrypt with per-user salt | Fast hashes (MD5/SHA) |
| Session | Server-side session id in `__Host-` httpOnly cookie | JWT in `localStorage` |
| MFA | TOTP/WebAuthn, step-up for sensitive actions | SMS-only, or optional for admins |
| OAuth/OIDC | Authorization Code + PKCE, short-lived access tokens | Implicit flow, long-lived tokens |
| Reset | Single-use, expiring, rate-limited token | Predictable tokens, unlimited attempts |
| Invalidation | Server-side revocation; short access-token TTL | "Logout" that only clears the client |

Also make the flow observable and rate-limited: login attempts, reset requests, and MFA challenges are all abuse targets.

### Additional Pitfalls
- **Timing-side-channel login responses.** Distinguish "user not found" less explicitly; rate-limit instead of leaking.
- **Session ids that never rotate.** Rotate on login, privilege change, and password change.
- **Password reset leaking account existence.** Always respond generically.
- **Access tokens with long TTLs and no revocation.** Compromise windows measured in hours.
- **MFA bypass on recovery paths.** The support/reauth flow is where MFA usually breaks.

### Real-World Deal-Breakers
- **Storing JWT in `localStorage`** → XSS can read it. Store access tokens in memory and refresh tokens in `HttpOnly` cookies.
- **No refresh token rotation** → a stolen refresh token is valid forever. Rotate on every use.
- **No `Secure`/`HttpOnly` on auth cookies** → XSS and MITM exposure.
- **Generic error messages** → "Invalid credentials" (never reveal whether the user exists).
- **No password hashing** → plaintext passwords in the database. Use Argon2id or bcrypt.
