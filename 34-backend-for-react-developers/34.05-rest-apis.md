## 34.5 REST APIs

### Subtopic Tree
- Resource-oriented design (nouns, not verbs)
- HTTP methods (GET, POST, PUT, PATCH, DELETE)
- HTTP status codes (200, 201, 400, 401, 403, 404, 500)
- URL structure (`/api/v1/users/:id/posts`)
- Versioning (URL path vs header)
- Pagination (offset, cursor)
- Error model (RFC 9457 Problem Details)
- OpenAPI 3.1+ contract-first design
- Caching (ETag, Cache-Control)
- HATEOAS (rarely used in practice)

### Design Principles
Modern API design focuses on **consistency, predictability, and developer experience**. A single `/orders` endpoint with filtering parameters is more maintainable than separate endpoints for pending, completed, and cancelled orders.

```typescript
// ✅ Resource-oriented
GET    /api/v1/users          // list
GET    /api/v1/users/:id      // get one
POST   /api/v1/users          // create
PATCH  /api/v1/users/:id      // partial update
DELETE /api/v1/users/:id      // delete

// ❌ Verb-oriented
GET /api/getUsers
POST /api/createUser
POST /api/updateUser
```

### HTTP Status Codes

| Code | Meaning | When to use |
|------|---------|-------------|
| 200 | OK | Successful GET, PATCH |
| 201 | Created | Successful POST |
| 204 | No Content | Successful DELETE |
| 400 | Bad Request | Validation failure |
| 401 | Unauthorized | Missing/invalid token |
| 403 | Forbidden | Valid token, insufficient permissions |
| 404 | Not Found | Resource doesn't exist |
| 409 | Conflict | Duplicate resource |
| 422 | Unprocessable Entity | Semantic validation failure |
| 429 | Too Many Requests | Rate limited |
| 500 | Internal Server Error | Unhandled exception |

### Deeper Explanation: REST Is A Contract For Resources And Cacheability

A well-designed REST API is not "URLs that return JSON" â€” it is a set of conventions that let clients, caches, and future teams reason predictably: resources as nouns, verbs as methods, status codes with meaning, consistent error envelopes, pagination contracts, and cacheability declared via headers.

Design decisions that pay off immediately:

- **Pagination**: cursor-based for changing data (`?cursor=&limit=`), returning `nextCursor`; offset pagination breaks under writes.
- **Filtering/sorting**: an explicit, documented parameter set; never pass raw query strings to the database.
- **Errors**: one envelope (`{ error: { code, message, details } }`) with stable machine-readable codes.
- **Idempotency**: `Idempotency-Key` on `POST` for retry safety.
- **Versioning**: additive changes where possible; a version path only when a breaking change is unavoidable.
- **Caching**: `ETag`/`If-None-Match` and `Cache-Control` for publicly cacheable reads.

### Additional Pitfalls
- **`200 OK` with an error body.** Clients cannot rely on status codes; the whole contract degrades.
- **Offset pagination on a live table.** Items are skipped or duplicated as rows change.
- **Breaking changes shipped without versioning or a deprecation window.**
- **Unbounded `limit`.** A client can request the entire table.
- **Inconsistent naming across endpoints.** `createdAt` in one place and `created_at` in another guarantees client bugs.

### Real-World Deal-Breakers
- **No versioning** → breaking changes break clients. Use `/api/v1/` from day one.
- **No pagination** → `GET /users` returns 100,000 records. Use cursor-based pagination for large datasets.
- **No error model** → clients get inconsistent error shapes. Use RFC 9457 Problem Details.
- **No OpenAPI spec** → contract drift between frontend and backend. Use OpenAPI 3.1+ with contract-first design.
