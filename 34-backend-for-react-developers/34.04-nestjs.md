## 34.4 NestJS

### Subtopic Tree
- Opinionated, Angular-inspired framework
- Modules (`@Module()`, feature modules, shared modules, dynamic modules)
- Controllers, Services, Providers
- Dependency Injection (DI container)
- Decorators (`@Get()`, `@Post()`, `@Injectable()`)
- Pipes (validation), Guards (auth), Interceptors (logging)
- Default adapter: Express (can swap to Fastify)
- When to use: enterprise greenfield, teams with Angular/.NET background, complex domains

### What NestJS Is
NestJS is an **opinionated framework** that adds architectural guardrails. It uses **modules, dependency injection, and decorators** inspired by Angular. NestJS "usually sits on top of Express by default, inheriting its risk profile unless explicitly configured otherwise". It narrows Express's validation gap with `class-validator` and `ValidationPipe`, but that protection is **opt-in** - developers must remember to attach `@UsePipes(new ValidationPipe())`.

```typescript
// users.module.ts
@Module({
  imports: [PrismaModule],
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService],
})
export class UsersModule {}

// users.controller.ts
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get(':id')
  async findOne(@Param('id') id: string) {
    return this.usersService.findOne(id);
  }

  @Post()
  @UsePipes(new ValidationPipe()) // OPT-IN - must be attached
  async create(@Body() dto: CreateUserDto) {
    return this.usersService.create(dto);
  }
}

// users.service.ts
@Injectable()
export class UsersService {
  constructor(private prisma: PrismaService) {}

  async findOne(id: string) {
    const user = await this.prisma.user.findUnique({ where: { id } });
    if (!user) throw new NotFoundException('User not found');
    return user;
  }
}
```

### Module Types

| Module Type | Purpose | Example |
|-------------|---------|---------|
| **Feature Module** | Business feature | `UsersModule`, `OrdersModule` |
| **Shared Module** | Reusable utilities | `DatabaseModule`, `LoggerModule` |
| **Core Module** | App-wide singletons | `ConfigModule`, `AuthModule` |
| **Dynamic Module** | Runtime configuration | `TypeOrmModule.forRoot()` |

### Deeper Explanation: Structure As A Feature

NestJS brings opinionated structure â€” modules, controllers, providers, dependency injection â€” to Node. Its value is organisational: large teams get consistent architecture, testable services via DI, and framework-agnostic business logic (Express or Fastify underneath). Its cost is ceremony and indirection, which is real for small projects.

The parts worth adopting even conceptually: **modules as bounded contexts**, controllers that only translate HTTP, providers that hold logic and are injectable (so tests can substitute fakes without module mocking), guards for authorisation, interceptors for cross-cutting concerns, and pipes for validation/DTO transformation.

### Additional Pitfalls
- **Business logic in controllers.** It becomes untestable outside HTTP and duplicates across endpoints.
- **Over-modularisation.** Ten modules for five endpoints is ceremony without benefit.
- **DI used as a service locator.** Inject explicitly rather than reaching into the container.
- **Ignoring the underlying platform.** Knowing whether Fastify or Express is running underneath matters for behaviour and performance.
- **DTOs without validation.** Use `class-validator`/Zod pipes; DTO types alone do not validate.

### Real-World Deal-Breakers
- **ValidationPipe not global** → `@UsePipes(new ValidationPipe())` is opt-in. Wire it in `main.ts` globally or forget validation entirely.
- **NestJS on Express** → inherits Express's CVE surface unless you swap to Fastify during setup.
- **High boilerplate** → NestJS is overkill for small projects. Use Fastify or Express.
