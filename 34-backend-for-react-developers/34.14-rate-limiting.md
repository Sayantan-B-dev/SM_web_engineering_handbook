## 34.14 Rate Limiting

### Subtopic Tree
- Token bucket, sliding window, fixed window
- `express-rate-limit` (version 8.6.2, August 2026)
- Redis-backed distributed rate limiting
- Per-IP, per-user, per-endpoint limits
- `Retry-After` header
- `429 Too Many Requests` response
- Rate limiting for auth endpoints (brute-force protection)

### Express Rate Limiting
```typescript
import { rateLimit } from 'express-rate-limit';
import RedisStore from 'rate-limit-redis';
import { createClient } from 'redis';

const redis = createClient();
await redis.connect();

// Global rate limit: 100 requests per minute
const globalLimiter = rateLimit({
  windowMs: 60_000,
  max: 100,
  standardHeaders: 'draft-7',
  legacyHeaders: false,
  store: new RedisStore({ sendCommand: (...args) => redis.sendCommand(args) }),
});

// Strict limit for auth endpoints: 5 attempts per 15 minutes
const authLimiter = rateLimit({
  windowMs: 15 * 60_000,
  max: 5,
  message: { error: 'Too many attempts, try again later' },
  store: new RedisStore({ sendCommand: (...args) => redis.sendCommand(args) }),
});

app.use('/api/', globalLimiter);
app.use('/api/auth/login', authLimiter);
```

---

### Deeper Explanation: Protect Capacity, Not Just Endpoints

Rate limiting exists to keep a service available and to make abuse expensive. The design questions are: **what key** (IP, user, API key, route), **what algorithm** (fixed window, sliding window, token bucket, leaky bucket), **what limits** (per route class), and **what happens on exceed** (429 with `Retry-After`, or queueing for expensive operations).

Practical layering: a coarse global limit at the edge, per-identity limits at the API, and per-resource limits for expensive operations (search, exports, AI calls). Distributed systems need a shared counter store (Redis) or a deterministic sharding scheme, and every limit needs distinct handling for legitimately bursty clients (token bucket) versus abuse. Combine with cost-based limiting when a single request can be expensive â€” AI tokens per user is a cost limit masquerading as a rate limit.

### Additional Pitfalls
- **Limiting by IP only.** NATs punish shared networks and attackers rotate IPs; add user and key dimensions.
- **Fixed windows with no burst allowance.** Legitimate bursts get rejected; use token buckets.
- **No `Retry-After` or `RateLimit-*` headers.** Clients cannot back off intelligently.
- **Limits in application memory.** They reset on deploy and do not hold across instances.
- **No limit on expensive endpoints.** One search or export query can consume more than a thousand normal requests.
- **Silent dropping.** Explicit 429s with a reason beat mysterious timeouts.

### Real-World Deal-Breakers
- **No rate limiting** → brute-force attacks on auth endpoints succeed. Add strict limits on login/register.
- **In-memory store** → rate limits reset on every server restart and don't work across multiple instances. Use Redis.
- **No `Retry-After` header** → clients don't know when to retry. Return `Retry-After` on 429.
- **No per-user limits** → rate limiting by IP alone fails behind NAT. Combine IP + user ID.
