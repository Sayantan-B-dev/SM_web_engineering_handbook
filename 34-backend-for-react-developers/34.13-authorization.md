## 34.13 Authorization

### Subtopic Tree
- Role-Based Access Control (RBAC)

### RBAC Pattern
```typescript
// Middleware guard
function requireRole(...roles: string[]) {
  return (req, res, next) => {
    if (!req.user) return res.status(401).json({ error: 'Unauthorized' });
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({ error: 'Forbidden' });
    }
    next();
  };
}

// Usage
app.delete('/api/users/:id', requireRole('admin'), deleteUser);
app.get('/api/admin/stats', requireRole('admin'), getStats);
```

### Resource Ownership
```typescript
// Check ownership before allowing access
async function getPost(req, res) {
  const post = await db.post.findUnique({ where: { id: req.params.id } });

  if (!post) return res.status(404).json({ error: 'Not found' });
  if (post.authorId !== req.user.id && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'Forbidden' });
  }

  res.json(post);
}
```

---

### Deeper Explanation: Authorisation Belongs At The Data Boundary

Authorisation is answering "may this principal do this to this resource?" â€” and the only reliable place to answer it is where the data is read or written, per resource, using the authenticated principal. Middleware that checks "is logged in" or "has role admin" is necessary but not sufficient: object-level checks (does this order belong to this user?) are where real breaches happen.

Three models, increasingly common in combination:

- **RBAC** â€” roles to permissions; simple, coarse.
- **ABAC** â€” attributes/policies (tenant, region, plan, ownership); precise, needs a policy engine or disciplined helper.
- **ReBAC** â€” relationships ("editor of document X"); the right fit for collaborative products (Zanzibar-style, Cerbos/OpenFGA).

Whichever you choose, enforce in one place (`can(principal, action, resource)`), test it with adversarial cases (other tenant's id, deleted resource, escalated role), and never trust a role or id supplied by the client.

### Additional Pitfalls
- **UI-only authorisation.** The API is the boundary; guards in components are UX.
- **IDOR (insecure direct object reference).** Every lookup by id must be scoped to the principal.
- **Role checks without tenancy.** Cross-tenant leaks come from forgetting the tenant predicate.
- **Scattered permission logic.** Ten checks in ten handlers drift; centralise and test.
- **No audit trail for privileged actions.** Compliance and incident response both need it.

### Real-World Deal-Breakers
- **Client-side-only authorization** → the API is unprotected. Always validate on the server.
- **No ownership checks** → any user can access any resource by guessing IDs.
- **RBAC without resource checks** → a user with `editor` role can edit any post, not just their own.
- **No Row-Level Security** → database returns data the user shouldn't see. Use RLS in PostgreSQL.
