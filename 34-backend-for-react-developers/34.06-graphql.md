## 34.6 GraphQL

### Subtopic Tree
- Single endpoint, client-selected fields
- Schema (SDL) with types, queries, mutations, subscriptions
- Resolvers
- Over-fetching/under-fetching solution

- Query depth/cost attacks
- Caching complexity (no CDN URL caching)
- Federation (Apollo) vs schema stitching
- When to use: multiple client surfaces, complex data graphs, mobile bandwidth budgets

### What GraphQL Is
GraphQL is a **query language and runtime** where clients request exactly the fields they need from a single endpoint. It excels when "clients need to compose data from multiple sources or when the access patterns vary widely". However, it "requires careful work to avoid expensive queries, depth attacks, and complex caching".

```graphql
# Single query fetches exactly what the UI needs
query GetUserWithPosts {
  user(id: "123") {
    name
    email
    posts(first: 10) {
      title
      createdAt
    }
  }
}
```

### The 2026 Reality
> "Most engineering orgs in 2026 run both: REST for the stable, cacheable, resource-shaped surface, GraphQL for the product UI that needs to assemble a screen's worth of data in one round-trip."

---

### Deeper Explanation: GraphQL Moves Complexity To The Server, Deliberately

GraphQL's bargain: the client asks for exactly what it needs, and the server must therefore solve problems that REST avoids by construction â€” query depth, N+1 fetching, authorisation per field, caching, and cost limits. Adopt it when those costs are worth paying: heterogeneous clients, deep object graphs, and rapidly evolving frontends.

Non-negotiables for a production GraphQL server: **depth and complexity limits**, **persisted queries** (so clients cannot send arbitrary queries in production), **DataLoader batching** to kill N+1s, **per-field authorisation**, and **query cost budgeting**. On the client, request only what you render and use fragments so cache normalisation works.

### Additional Pitfalls
- **No depth/complexity limit.** A single nested query can exhaust the database.
- **N+1 resolvers.** One query becomes hundreds of database calls; batch with DataLoader.
- **Authorisation at the root only.** Field-level data leaks through nested objects.
- **Caching treated like REST.** HTTP caching rarely applies; you need response-level caching or a normalised client cache.
- **Schema drift without deprecation.** Removing a field breaks deployed clients; deprecate, monitor usage, then remove.

### Real-World Deal-Breakers
- **N+1 problem** → each `user.posts` field triggers a separate DB query. Use DataLoader for batching.
- **No query depth limiting** → a malicious query can traverse 100 levels deep and crash the server. Add depth/cost limits.
- **No CDN caching** → GraphQL's single POST endpoint can't be cached by URL. Use persisted queries or APQ.
- **Federation complexity** → Apollo Federation adds a gateway (180ms cold-start overhead) and schema registry.
