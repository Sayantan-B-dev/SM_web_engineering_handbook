## 34.10 Cookies

### Subtopic Tree
- `Set-Cookie` (name, value, attributes)
- `Secure` (HTTPS only)
- `HttpOnly` (not accessible to JavaScript)
- `SameSite` (`Strict`, `Lax`, `None`)
- `Domain` and `Path` scoping
- `Max-Age` / `Expires`
- Cookie prefixes (`__Host-`, `__Secure-`)
- Session cookies vs persistent cookies
- Cookie-based auth vs token-based auth

### Secure Cookie Configuration
```javascript
res.cookie('session', token, {
  httpOnly: true,    // XSS can't read
  secure: true,      // HTTPS only
  sameSite: 'lax',   // CSRF protection
  maxAge: 7 * 24 * 60 * 60 * 1000, // 7 days
  path: '/',
});
```

### SameSite Values

| Value | Behavior | CSRF protection |
|-------|----------|-----------------|
| `Strict` | Cookie never sent cross-site | Strongest |
| `Lax` | Sent on top-level GET navigations | Strong |
| `None` | Always sent (requires `Secure`) | None |

---

### Deeper Explanation: Cookies Are A Security Boundary

Cookies are the only credential the browser attaches automatically, which makes them powerful and dangerous. Every attribute is a security decision:

- **`HttpOnly`** â€” JavaScript cannot read it, so XSS cannot steal the session.
- **`Secure`** â€” HTTPS only; without it, credentials travel in cleartext.
- **`SameSite=Lax`** â€” default-safe for CSRF; `Strict` breaks some cross-site navigations, `None` requires `Secure` and re-opens CSRF risk.
- **`Path`/`Domain`** â€” scope narrowly so preview and subdomains do not receive production cookies.
- **`Max-Age`/`Expires`** â€” session cookies vs persistent; shorter is safer.
- **`__Host-` prefix** â€” enforces `Secure`, no `Domain`, `Path=/`: a strong default for session cookies.

Also decide the model deliberately: cookie sessions with server-side storage (revocable, and CSRF protections apply) versus bearer tokens in JS storage (simpler cross-origin, but readable by any script). For browser apps, cookie sessions are usually the safer default.

### Additional Pitfalls
- **Session cookies without `HttpOnly`.** One XSS turns into account takeover.
- **`SameSite=None` without CSRF defence.** The cookie is sent cross-site; you need tokens or origin checks.
- **Storing JWTs in `localStorage`.** Any injected script can exfiltrate them.
- **`Domain=.example.com` on a session cookie.** Every subdomain (including previews) receives it.
- **No rotation on privilege change.** Sessions should be re-issued after login and elevation.

### Real-World Deal-Breakers
- **No `HttpOnly`** → XSS can read session tokens. Always set `HttpOnly` for session cookies.
- **No `Secure`** → cookies sent over HTTP. Always set `Secure` in production.
- **No `SameSite`** → CSRF vulnerability. Use `SameSite=Lax` or `Strict`.
- **`SameSite=None` without `Secure`** → browsers reject the cookie.
