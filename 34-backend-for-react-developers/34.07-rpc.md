## 34.7 RPC (tRPC)

### Subtopic Tree
- Remote Procedure Call (call functions, not resources)
- tRPC: end-to-end TypeScript type safety
- No schema definition, no code generation
- Shared types between frontend and backend
- React Query integration
- WebSocket subscriptions
- When to use: TypeScript monorepos, Next.js apps, internal APIs

### What tRPC Is
tRPC is the **most-used internal-RPC layer for React + Next.js in 2026**. It provides **end-to-end type safety without schema definition**. The TypeScript types are the contract - no SDL files, no code generation, no federation gateway.

```typescript
// server/router.ts
import { initTRPC } from '@trpc/server';
import { z } from 'zod';

const t = initTRPC.create();

export const appRouter = t.router({
  getUser: t.procedure
    .input(z.object({ id: z.string() }))
    .query(async ({ input }) => {
      return db.user.findUnique({ where: { id: input.id } });
    }),

  createUser: t.procedure
    .input(z.object({ name: z.string(), email: z.string().email() }))
    .mutation(async ({ input }) => {
      return db.user.create({ data: input });
    }),
});

export type AppRouter = typeof appRouter;
```

```typescript
// client.tsx
import { trpc } from './trpc-client';

function UserProfile({ id }: { id: string }) {
  const { data: user } = trpc.getUser.useQuery({ id });
  const createUser = trpc.createUser.useMutation();

  // user is fully typed - no manual type definitions
  return <h1>{user?.name}</h1>;
}
```

### Performance: tRPC vs Apollo Federation
A production migration from Apollo Federation to tRPC reported:
- **Cold start**: 180ms (Apollo) → 45ms (tRPC) - **75% improvement**
- **Average response**: 38ms → 12ms
- **P95 latency**: 85ms → 28ms
- **P99 latency**: 156ms → 42ms
- **Bundle size**: 142KB (Apollo Client) → significantly smaller (tRPC + React Query)

### Deeper Explanation: RPC Trades Resource Semantics For Type Safety

RPC-style APIs (tRPC, gRPC, Connect) optimise for the developer experience: call typed functions, get typed results, no modelling of resources or caching semantics. For a TypeScript monorepo with one client, tRPC is often the highest-leverage choice â€” the client's types are derived from the server's implementation, so a signature change breaks the build instead of production.

The trade-offs are structural: it couples client and server versions (fine for a monorepo, harder for third parties), it does not give you HTTP caching semantics, and it needs discipline to keep procedures small and authorisation explicit. gRPC adds performance and code generation across languages, at the cost of browser awkwardness (grpc-web, streaming via Connect) and tooling complexity.

### Additional Pitfalls
- **Public API shaped as RPC.** Third-party consumers expect stable resources, versioning, and caching.
- **One giant procedure.** Coarse RPC calls become the new monolithic endpoint.
- **Authorisation in middleware by name pattern.** Fragile; keep checks per procedure and per resource.
- **Ignoring batching.** Many small RPC calls need request batching or a loader to avoid a waterfall.
- **Version coupling without a migration plan.** A monorepo deploy is atomic; external clients are not.

### Real-World Deal-Breakers
- **No request batching** → tRPC doesn't have GraphQL's built-in batching. Use `httpBatchLink` for batching.
- **TypeScript-only** → tRPC requires TypeScript on both ends. Non-TS clients can't consume it.
- **No public API** → tRPC is for internal APIs. Use REST or GraphQL for public APIs.
