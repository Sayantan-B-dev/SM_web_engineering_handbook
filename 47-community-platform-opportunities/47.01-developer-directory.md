## 47.1 Developer Directory

### Subtopic Tree
- Definition: searchable index of community members

- Availability status (open to work, open to mentoring, open to speaking)

- The Kolkata React developer talent pool

### What a Developer Directory Is
A developer directory is a **searchable, filterable index of community members**. It answers the question every community member asks: **"Who else is here, and what do they know?"**

The directory is the **foundation layer** of the platform. Without it, there is no community profile, no speaker directory, no mentor directory. Every other platform opportunity depends on the identity layer.

```text
Developer Directory Data Model:
─────────────────────────────────
id: uuid
name: string
email: string (private)
github_username: string
linkedin_url: string
skills: string[] (React, Next.js, TypeScript, Node.js, GraphQL, etc.)
experience_level: enum (student, junior, mid, senior)
location: string (Kolkata, West Bengal, Remote)
availability: enum (open_to_work, open_to_mentoring, open_to_speaking, all)
joined_at: timestamp
contributions: Contribution[] (talks, projects, mentoring, PRs)
badges: Badge[]
```

### Search and Filter Use Cases
- **Hiring manager**: "Find mid-level React developers in Kolkata open to work."
- **First-time speaker**: "Find senior developers in Kolkata open to mentoring."
- **Event organizer**: "Find all community members who have spoken before."
- **Contributor**: "Find developers working on Next.js projects."

### Privacy Controls
The directory must have **granular privacy controls**. Not every member wants their email visible, their availability public, or their contribution history searchable. The default should be **minimal public profile** with opt-in for visibility.

---

### Deeper Explanation: A Directory Is Search Plus Trust

The product problem is discoverability ("find React developers in Kolkata who know design systems"), and the data problem is keeping entries accurate. Design decisions that matter: structured skills/tags rather than free text, explicit visibility controls (what recruiters can see vs other members), verification for claims where it matters, and an update prompt (profile freshness) so entries do not rot.

```ts
type Profile = {
  id: string;
  displayName: string;
  headline: string;
  location: { city: string; remote: boolean };
  skills: string[];                      // from a controlled vocabulary
  experienceYears: number;
  links: { github?: string; site?: string; linkedin?: string };
  visibility: 'public' | 'members' | 'recruiters-only';
  openTo: Array<'hiring' | 'mentoring' | 'collaboration' | 'speaking'>;
  updatedAt: string;
};
```

### Additional Pitfalls
- **Free-text skills.** Search fails and matching is impossible; use tags plus synonyms.
- **No visibility controls.** People will not list themselves where recruiters can see them by default.
- **Stale profiles.** Prompt for confirmation periodically and show the last-updated date.
- **No search filters that matter.** Location, remote, skills, and "open to" cover most queries.
- **Scraping made easy.** Expose nothing bulk-accessible without consent.

### Real-World Deal-Breakers
- **No directory** → the community has 11,000+ LinkedIn followers but no way to find the right person for a job, a talk, or a mentorship.
- **No privacy controls** → members don't join the directory because they don't want their email or availability public.
- **No skill tagging** → the directory is a list of names, not a searchable talent pool.
- **No integration with contributions** → a developer's directory profile is empty. It shows nothing about what they've contributed to the community.
