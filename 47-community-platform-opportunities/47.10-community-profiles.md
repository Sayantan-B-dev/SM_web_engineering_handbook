## 47.10 Community Profiles

### Subtopic Tree
- Definition: persistent identity for every community member

- Contribution graph (talks, projects, mentoring, PRs)
- Badges and achievements
- Activity feed
- Privacy controls
- Integration with directory, speaker directory, mentor directory

### What a Community Profile Is
A community profile is a **persistent identity layer** for every React Kolkata member. It answers: **"Who is this person, and what have they contributed?"**

The profile is the **integration layer** for every other platform opportunity. The developer directory, speaker directory, and mentor directory all read from the same profile.

### Profile Data Model
```text
Profile:
─────────────────────────────────
member_id: uuid
name: string
bio: text
skills: string[]
location: string
github_url: string
linkedin_url: string
website_url: string
contributions:
  - talks: Talk[]
  - projects: Project[]
  - mentoring: Mentorship[]
  - open_source: PullRequest[]
  - events_attended: Event[]
badges: Badge[]
joined_at: timestamp
privacy:
  email: enum (public, members_only, private)
  availability: enum (public, members_only, private)
  contribution_graph: enum (public, members_only, private)
```

### Contribution Graph
The contribution graph is the **most valuable feature** of the community profile. It shows a member's entire React Kolkata journey:

```
Talks: 3 (2 lightning, 1 full)
Projects: 2 (Project Parbon submission, React Kolkata website)
Mentoring: 1 (Project Parbon mentee)
Open Source: 5 PRs merged (React Kolkata website)
Events Attended: 8 (5 online, 3 offline)
```

---

### Deeper Explanation: Identity, Reputation, And Privacy In One Place

A community profile aggregates a member's participation: talks given, projects shown, mentorship offered, contributions, and badges. It is the social layer that makes directories meaningful and gives contributors a portable reputation â€” and it is the module where privacy decisions are most consequential, because it accumulates data the member did not explicitly publish.

Design rules that hold: only aggregate what is already public or explicitly consented, give granular per-section visibility, never infer sensitive attributes, and allow full export and deletion. Reputation features (badges, leaderboards) should recognise contribution, not rank people against each other in ways that discourage the majority.

### Additional Pitfalls
- **Aggregation without consent.** "You attended X" is surprising and often unwanted.
- **Permanent public history.** Allow hiding old activity.
- **Ranking over recognition.** Leaderboards can demotivate; badges celebrate milestones.
- **No deletion path.** Privacy obligations and trust both require it.
- **Profile as an identity silo.** Support linking external identities (GitHub, site) rather than duplicating them.

### Real-World Deal-Breakers
- **No community profile** → a member's contribution is invisible. They speak at a meetup and it's forgotten the next day.
- **No contribution graph** → there's no way to prove community involvement. It's all anecdotal.
- **No privacy controls** → members don't create profiles because they don't want everything public.
- **No integration** → the profile is isolated. It doesn't feed the directory, speaker directory, or mentor directory.
