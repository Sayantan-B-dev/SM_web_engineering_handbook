## Dependency Vulnerabilities

### Subtopic Tree
- The transitive dependency surface of a React app
- Advisories (`npm audit`, GitHub Advisories, OSV) and their noise problem
- Reachability: is the vulnerable code path actually used?
- Patching cadence and automatic updates (Renovate, Dependabot)
- Lockfiles, reproducibility and `npm ci`
- Overrides/resolutions for forced patches
- Vendor risk: abandoned and single-maintainer packages
- CI gating without blocking delivery

### The Mental Model
Every dependency is code you ship and are responsible for, and the average frontend app has hundreds of them transitively. Vulnerability management is therefore a **triage pipeline**, not a lint rule: detect (advisories in CI), assess (severity plus reachability), remediate (upgrade, override, or replace), and record the decision.

```yaml
# CI: audit on the lockfile, then triage by severity instead of blocking on everything
- run: pnpm audit --audit-level=high --prod     # production deps only, fail on high/critical
- run: pnpm audit --json > audit.json || true   # full report for review and dashboards
```

```json
// Force a patched transitive version while an upstream fix lands (document why + remove later)
{
  "pnpm": { "overrides": { "postcss@<8.4.31": ">=8.4.31" } }
}
```

### Real-World Deal-Breakers
- **No lockfile in CI.** Resolution drift means you ship versions you never tested (`npm ci`/`--frozen-lockfile` is mandatory).
- **`npm audit fix --force` in a branch nobody reviews.** It upgrades majors and breaks the build silently.
- **Blocking every advisory.** Teams disable the gate entirely; triage deviations from high/critical instead.
- **Ignoring dev-only advisories forever.** They matter for CI and developer machines, but rank below shipped code.
- **No patch cadence.** Monthly batch upgrades beat emergency upgrades during an incident.
- **Abandoned packages left in place.** No maintainer means no fix; plan a replacement before it matters.
