### Where React's Auto-Escaping Stops
Values inside JSX curly braces are escaped, so `{userComment}` renders a `<script>` payload as inert text. That protection **does not cover**: raw-HTML injection via `dangerouslySetInnerHTML`, URL-bearing attributes like `href` and `src`, or anything you write to the DOM manually with a `ref`. Treat those three as the only XSS surfaces worth arguing about in a React review.

```tsx
// ✅ SAFE - React escapes automatically
<div>{userComment}</div>

// ❌ DANGEROUS - raw HTML, no escaping
<div dangerouslySetInnerHTML={{ __html: userComment }} />

// ❌ DANGEROUS - javascript: URL executes
<a href={userUrl}>Click</a>

// ❌ DANGEROUS - manual DOM write
useEffect(() => {
  ref.current.innerHTML = userContent;
}, []);
```

### `dangerouslySetInnerHTML` - The Primary React XSS Vector
`dangerouslySetInnerHTML` injects a string into the DOM verbatim, bypassing the automatic escaping that makes JSX safe by default. A value like `<img src=x onerror=alert(1)>` executes as script the instant it's mounted. OWASP's Cross-Site Scripting Prevention Cheat Sheet lists this exact pattern as a primary framework-specific injection vector and recommends avoiding the prop entirely.

```tsx
// ✅ SAFE - sanitize at render time, not storage time
import DOMPurify from 'dompurify';

function Article({ html }) {
  const clean = DOMPurify.sanitize(html);
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}
```
Sanitize at the moment of render, not when it was stored - your allowlist can change between storage and display.

### URL Scheme Injection
```tsx
// ❌ DANGEROUS - javascript: URLs execute
<a href={url}>Click</a>

// ✅ SAFE - allowlist schemes explicitly
function safeHref(url: string): string {
  try {
    const u = new URL(url, window.location.origin);
    return ['https:', 'http:', 'mailto:'].includes(u.protocol) ? url : '#';
  } catch {
    return '#';
  }
}
```
Escaping HTML entities does nothing to a URL scheme.

### Trusted Types (Cross-Browser Feb 2026)
Trusted Types prevent DOM XSS by requiring sanitized values for dangerous DOM sinks. Enable with `require-trusted-types-for 'script'` in your CSP. Cross-browser since February 2026 (Chrome + Firefox).

### Deeper Explanation: Output Encoding Plus CSP Plus No Sinks

XSS is one bug with many vectors: HTML injection (rendered markup), attribute injection, URL injection (`javascript:`), DOM sinks (`innerHTML`, `eval`, `document.write`), and content-driven cases (a sanitised library that still allows dangerous attributes). The defence has three layers, and skipping one is what produces production incidents:

1. **Never build HTML from strings.** Use framework interpolation; forbid `dangerouslySetInnerHTML`/`innerHTML` except through a reviewed sanitiser.
2. **Encode by context.** HTML, attribute, URL, and JS contexts need different escaping; a generic escape is the classic mistake.
3. **Enforce with CSP.** A nonce-based `script-src` with `strict-dynamic` means an injected `<script>` does not execute even if it lands â€” and Trusted Types can block DOM sinks entirely.

Since a React app's most likely XSS is a rich-text field, markdown renderer, or third-party widget, those are the places to enforce sanitisation with a library plus tests containing known payloads.

### Additional Pitfalls
- **Sanitising on the server and rendering raw on the client.** The client is where the DOM sinks are; sanitise at the point of rendering.
- **`javascript:` URLs from user data.** Validate schemes in hrefs (`http`, `https`, `mailto`) and reject the rest.
- **`target="_blank"` without `rel="noopener"`.** The opener can navigate your tab.
- **Sanitiser allow-lists that keep `style` or `on*`.** These reopen injection paths.
- **No CSP report-only phase.** Roll out CSP with reporting before enforcement to find the breakages.

### Real-World Deal-Breakers
- **`dangerouslySetInnerHTML` without DOMPurify** → instant XSS. Any pull request introducing this prop should require an explicit sanitization step and reviewer sign-off.
- **No URL scheme validation** → `javascript:stealCookies()` in an `href` executes on click.
- **Sanitizing at storage time** → the allowlist can change between storage and display. Sanitize at render time.
- **No CSP** → even if an injection lands, nothing stops the script from running. A strong CSP means the browser refuses to execute the attacker's script.
- **Trusting TypeScript for XSS prevention** → TypeScript's types vanish the moment your bundler finishes compiling, leaving every fetch response effectively untyped at runtime.
