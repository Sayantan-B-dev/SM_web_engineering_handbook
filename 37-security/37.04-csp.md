### What CSP Is
A Content Security Policy is an HTTP header that tells the browser which sources of script, style, and other content it is allowed to load and execute - a browser-enforced allowlist for executable content. Its primary job is to contain cross-site scripting: even if an attacker manages to inject markup into your page, a well-built CSP stops the injected script from running. That makes CSP a genuine last line of defense.

### The Short Answer for 2026
Deploy a **strict, nonce-based CSP with `strict-dynamic`**, avoid `unsafe-inline` and host allowlists, roll it out first in report-only mode, and add Trusted Types to close off DOM-based XSS.

### Why Host Allowlists Fail
Any allowed host with an open redirect, a JSONP endpoint, or an outdated library becomes a bypass. Research repeatedly shows the majority of allowlist-based policies are trivially bypassable.

### Strict, Nonce-Based CSP
With a nonce, the server generates a fresh random value per response and stamps it on every script tag it trusts. The browser runs only scripts carrying the correct nonce, so injected script (which cannot know the nonce) never executes. Adding `strict-dynamic` lets your trusted scripts load further scripts they need, so you don't have to allowlist every CDN.

```http
Content-Security-Policy:
  script-src 'nonce-r4nd0m123' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  require-trusted-types-for 'script';
```

```html
<script nonce="r4nd0m123" src="/app.js"></script>
```

### Three Details That Make or Break a Strict CSP
1. **The nonce must be unguessable and unique per response** - a static or reused nonce is worthless.
2. **`object-src 'none'` and `base-uri 'none'`** close off plugin and base-tag injection vectors.
3. **Never add `unsafe-inline` to `script-src`** - when a nonce is present modern browsers ignore it anyway, but adding it out of habit signals a policy that was copied rather than designed.

### Rollout in Report-Only Mode
Do not enforce a new CSP blind. Ship it first as report-only, which reports violations without blocking anything. Collect reports for a representative period, fix legitimate sources that trip the policy, then switch to enforcement.

```http
Content-Security-Policy-Report-Only:
  script-src 'nonce-r4nd0m123' 'strict-dynamic';
  object-src 'none';
  report-to csp-endpoint
```

---

### Deeper Explanation: CSP Is An Encoding-Success Detector

The strategic value of Content Security Policy is that it turns "did we inject?" into a mechanical question: if an attacker's payload appears, it fails to execute. That requires a policy without the escape hatches â€” no `unsafe-inline`, no `unsafe-eval`, no wide `script-src` domains, and a nonce or hash for your own inline code.

Layers worth adding once the base policy works: `strict-dynamic` (trusts scripts you load, so you can drop domain allow-lists), `Trusted Types` (`require-trusted-types-for 'script'` blocks DOM sink injection entirely), `frame-ancestors 'none'` (the modern clickjacking defence), `base-uri 'none'`, `object-src 'none'`, `form-action 'self'`, and a `report-uri`/`report-to` endpoint with alerting on violations.

### Additional Pitfalls
- **`unsafe-inline` in `script-src`.** It nullifies XSS protection, and many "CSP failures" are fixed by removing it rather than adding to it.
- **Domain allow-lists with CDNs.** A JSONP endpoint on an allowed CDN is an execution path.
- **Report-only forever.** Nobody reads the reports; enforce after a short observation window.
- **Nonce per build.** Nonces must be per response â€” a static nonce is equivalent to allowing inline.
- **Ignoring violations.** CSP reports are the highest-signal XSS detector you own.

### Real-World Deal-Breakers
- **`unsafe-inline` in `script-src`** → defeats the entire policy.
- **`unsafe-eval`** → allows `eval()` and similar functions, which is exactly what XSS attacks use.
- **Static or reused nonces** → worthless. Generate a fresh nonce per response.
- **No `object-src 'none'`** → plugin injection vectors remain open.
- **No `base-uri 'none'`** → base-tag injection can redirect all relative URLs.
- **Enforcing without report-only** → you break your app in production. Always rollout in report-only first.
