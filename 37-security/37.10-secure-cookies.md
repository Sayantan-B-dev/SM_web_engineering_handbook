## 37.7 Secure Cookies

### Subtopic Tree
- `Secure` attribute (HTTPS only)
- `HttpOnly` (not accessible to JavaScript)
- `SameSite` (`Strict`, `Lax`, `None`)
- `Domain` and `Path` scoping
- `Max-Age` / `Expires`
- Cookie prefixes (`__Host-`, `__Secure-`)
- Session cookies vs persistent cookies
- Cookie-based auth vs token-based auth

### The Three Attributes You Must Set
```typescript
res.cookie('session', token, {
  httpOnly: true,    // XSS can't read it
  secure: true,      // HTTPS only
  sameSite: 'lax',   // CSRF protection
  maxAge: 7 * 24 * 60 * 60 * 1000, // 7 days
  path: '/',
});
```

### The `__Host-` Prefix (The Strongest Cookie)
A cookie named `__Host-session` with `Secure`, `Path=/`, and no `Domain` attribute is the most secure cookie configuration. It cannot be overwritten by a subdomain or a different path.

### Cookie Storage Comparison

| Attribute | Prevents | Notes |
|-----------|----------|-------|
| `HttpOnly` | XSS token theft | JavaScript cannot read the cookie |
| `Secure` | MITM | Cookie only sent over HTTPS |
| `SameSite=Strict` | CSRF (complete) | Breaks legitimate cross-origin links |
| `SameSite=Lax` | CSRF (most) | Allows top-level GET navigations |
| `__Host-` prefix | Subdomain cookie injection | Requires `Secure`, `Path=/`, no `Domain` |

---

### Deeper Explanation: Cookie Attributes As A Threat Model

Each attribute maps to an attack you are choosing to defend against:

- `HttpOnly` â†’ XSS credential theft
- `Secure` â†’ network interception
- `SameSite=Lax/Strict` â†’ CSRF
- `Domain`/`Path` scoping â†’ leakage to subdomains, previews, and adjacent apps
- `Max-Age`/`Expires` â†’ long-lived exposure after compromise
- `__Host-` prefix â†’ enforces `Secure`, `Path=/`, and no `Domain` (strongest session cookie default)
- `Partitioned` (CHIPS) â†’ isolates embedded third-party contexts

Also plan rotation: session ids must be re-issued on login, privilege escalation, and password change, and stored server-side so they can be revoked. For cross-site embeds, cookies should be `Partitioned` rather than broadly shared.

### Additional Pitfalls
- **`Domain=.example.com` for sessions.** Every subdomain (including user-content and preview hosts) receives the cookie.
- **Long-lived "remember me" cookies without rotation or binding.** Consider device binding or re-authentication for sensitive actions.
- **Cookies set on HTTP pages.** They are sent in cleartext; redirect to HTTPS first.
- **Session cookie not invalidated on logout server-side.** Clearing the cookie is not revocation.
- **Too many cookies.** They travel on every request; keep the total small.

### Real-World Deal-Breakers
- **No `HttpOnly`** → XSS reads session tokens. Always set `HttpOnly` for session cookies.
- **No `Secure`** → cookies sent over HTTP. Always set `Secure` in production.
- **No `SameSite`** → CSRF vulnerability. Use `SameSite=Lax` or `Strict`.
- **`SameSite=None` without `Secure`** → browsers reject the cookie.
- **Session token in `localStorage`** → XSS exfiltrates instantly. Use `HttpOnly` cookies or BFF.
