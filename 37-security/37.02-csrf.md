### How CSRF Works
A CSRF attack exploits the browser's cookie jar, not a vulnerability in your JavaScript. A user logged into `bank.example.com` has a session cookie. The attacker hosts a page with an auto-submitting form pointing at `bank.example.com/transfer`. When the victim visits that page, the browser sends the POST and attaches the session cookie automatically - because cookies are scoped to a domain, not to which page initiated the request.

No script injection, no XSS, no credential theft - just a forged request riding on real, valid credentials.

### SameSite Cookies - The Primary CSRF Defense
SameSite is the primary CSRF defense because it operates at the user agent, before the request is built.

| Value | Behavior | CSRF protection |
|-------|----------|-----------------|
| `Strict` | Cookie never sent cross-site | Strongest |
| `Lax` | Sent on top-level GET navigations | Strong |
| `None` | Always sent (requires `Secure`) | None |

**Chrome 80 (February 2020) changed the default to `Lax`** specifically because ambient cookie inclusion on cross-origin requests was such a widespread problem. Lax still allows top-level cross-site navigations (a user clicking a link) to carry cookies.

### The SameSite=Lax Bypass (CVE-2026-71378)
Browsers send `SameSite=Lax` cookies on cross-site top-level GET navigations. If an application performs state-changing operations on GET requests, an attacker can redirect the victim's browser to a listener URL and execute that action in the victim's authenticated session.

**The lesson:** Never perform state-changing operations on GET requests. Every POST/PUT/DELETE that relies on cookies needs CSRF protection.

### The Double-Submit Cookie Pattern
```typescript
// Server sets a random CSRF token in a cookie
res.cookie('csrf_token', token, { httpOnly: false, sameSite: 'lax', secure: true });

// Client reads the cookie and sends it in a header
fetch('/api/transfer', {
  method: 'POST',
  headers: { 'X-CSRF-Token': getCookie('csrf_token') },
  body: JSON.stringify(data),
});

// Server compares header token to cookie token
```

### The 2026 Baseline
A Node.js team in 2026 should treat CSRF defense as **layered, not single-technique**: set `SameSite=Lax` (or `Strict` where the UX allows it) plus `Secure` and `HttpOnly` on session cookies as the baseline; add a signed double-submit token for state-changing endpoints; validate `Origin`/`Referer` as a defense-in-depth layer.

---

### Deeper Explanation: Cookies Travel Automatically, That Is The Problem

CSRF exploits the browser's automatic cookie attachment: a hostile page causes a state-changing request to your origin, and the session cookie rides along. The modern defence is layered and mostly cookie-configuration-based:

- **`SameSite=Lax` (default in modern browsers)** stops cross-site POSTs for standard navigations; `Strict` is stronger but breaks inbound links with sessions.
- **`SameSite=None; Secure`** is required for cross-site embeds and re-opens CSRF, so those endpoints need a token or origin check.
- **Double-submit or synchroniser tokens** for anything with a broad `SameSite` posture.
- **`Origin`/`Referer` validation** on state-changing requests, particularly for API endpoints used by third-party integrations.
- **Custom headers or non-simple requests** for XHR-only APIs; CORS preflight becomes an implicit check (but not for simple-form posts).

For a cookie-session SPA the practical baseline is Lax cookies + origin checks + CSRF tokens on the few endpoints reachable cross-site.

### Additional Pitfalls
- **`SameSite=None` added to "fix" an embed.** It silently disables the main CSRF defence.
- **CSRF tokens only checked on some methods.** `PATCH`/`DELETE` bypasses are common.
- **GET endpoints with side effects.** They are trivially triggerable by images and links.
- **Login CSRF.** Forcing a victim to log into the attacker's account is often overlooked.
- **Token exposed in URLs.** Query strings leak through logs and referrers.

### Real-World Deal-Breakers
- **No SameSite attribute** → browsers default to Lax, but explicit is better. Set `SameSite=Lax` or `Strict`.
- **State-changing GET requests** → SameSite=Lax still sends cookies on top-level GET navigations. Never perform state-changing operations on GET.
- **`SameSite=None` without `Secure`** → browsers reject the cookie.
- **Relying only on SameSite** → OWASP explicitly lists SameSite as a complementary defense, not a replacement for application-level tokens.
- **Using `csurf`** → deprecated in October 2022. Use a modern alternative (double-submit cookies, origin validation, or a maintained library).
