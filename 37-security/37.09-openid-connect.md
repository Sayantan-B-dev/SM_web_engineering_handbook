## OpenID Connect

### Subtopic Tree
- Identity layer on top of OAuth 2.0
- The ID token (JWT) and its claims (`sub`, `aud`, `iss`, `exp`, `nonce`)
- Discovery (`/.well-known/openid-configuration`)
- The authorization code flow with PKCE and `nonce`
- Token validation: signature, issuer, audience, expiry
- UserInfo endpoint vs ID token claims
- Session management and logout (RP-initiated logout)
- Common misconfigurations

### The Mental Model
OIDC adds **identity** to OAuth's **authorisation**: after the code exchange you receive an ID token that asserts *who* the user is, signed by the identity provider. Your job is to verify that assertion rigorously, and to keep the distinction clear: the ID token is for your application's session, the access token is for calling APIs on the user's behalf.

```ts
// Verify an ID token properly: signature, issuer, audience, expiry, nonce â€” all of them
import { createRemoteJWKSet, jwtVerify } from 'jose';

const jwks = createRemoteJWKSet(new URL('https://idp.example.com/.well-known/jwks.json'));

export async function verifyIdToken(idToken: string, expectedNonce: string) {
  const { payload } = await jwtVerify(idToken, jwks, {
    issuer: 'https://idp.example.com',
    audience: 'web-client-id',
    clockTolerance: 5,
  });

  if (payload.nonce !== expectedNonce) throw new Error('nonce mismatch');   // replay defence
  if (!payload.sub) throw new Error('missing subject');

  return { userId: payload.sub, email: payload.email as string | undefined };
}
```

### Session And Logout
- **Keep your own session** (server-side, httpOnly cookie) rather than treating the ID token as the session; the token is proof of authentication at a moment in time.
- **Handle `auth_time`** for sensitive operations (step-up authentication if the login is old).
- **Implement RP-initiated logout** and consider back-channel logout so signing out at the IdP ends your session too.
- **Refresh with rotation**; a revoked refresh token must end the session.

### Real-World Deal-Breakers
- **Trusting `email` from an unverified token.** Only rely on verified claims, and check `email_verified` where relevant.
- **Not validating `aud`/`iss`.** Any token from any client of the same IdP would be accepted.
- **Using the ID token as an API access token.** They have different audiences and lifetimes.
- **Skipping `nonce`/`state`.** Replay and CSRF on the callback.
- **Key rotation ignored.** Cache JWKS with a short TTL and refresh on unknown `kid`.
- **Session never re-validated.** Users removed at the IdP keep access until expiry; consider periodic re-validation for privileged actions.
