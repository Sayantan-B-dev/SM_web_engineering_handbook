### The Two Facts That Dominate SPA Security
**First, your entire JavaScript bundle is public.** Anyone can open DevTools and read every line, so nothing secret can live in it.

**Second, in an SPA a single cross-site scripting flaw is not a bug, it is game over.** Injected script runs in the same context as your app, with access to whatever the app can reach, including auth tokens.

Every other SPA security decision - where you store tokens, how you configure OAuth, what your CSP allows - is downstream of those two realities.

### Deeper Explanation: Threat Model The Product, Not The Framework

Frontend security work is distributed across four layers, and a gap in any one of them is the breach:

| Layer | Controls | Failure mode |
|---|---|---|
| Browser | CSP, Trusted Types, sandboxed iframes, secure contexts | XSS achieves full origin control |
| Transport/session | TLS, HSTS, `__Host-` httpOnly cookies, SameSite | Session theft, CSRF |
| Application | Input validation, output encoding, authorisation per resource, rate limits | IDOR, injection, abuse |
| Supply chain | Lockfiles, provenance, scanning, least-privilege tokens | Compromised dependency or action |

The reframing that helps most: assume any XSS is game over for the origin, and design so an XSS is hard, detectable, and limited. That means strict CSP with nonces, no `dangerouslySetInnerHTML` on user content, httpOnly session cookies, and short-lived tokens for privileged operations.

### Additional Pitfalls
- **Security treated as a library.** Frameworks give escape hatches that reintroduce every classic bug.
- **No threat model per feature.** File upload, rich text, OAuth, and webhooks each have distinct attacks.
- **Controls not tested.** A CSP in report-only, or a SameSite change, must be verified with an actual adversarial test.
- **No incident plan.** You need logs, revocation, and user communication ready before the incident.

### Real-World Deal-Breakers
- **Assuming React handles security for you** → React escapes JSX text, and that single default has prevented a decade of XSS. Everything else - raw-HTML sinks, secrets in the bundle, token storage, npm dependencies - is on you.
- **No CSP** → one XSS is game over. CSP is your safety net for the XSS that slips past code review.
- **Tokens in localStorage** → readable by any JavaScript on the page. One XSS and the attacker exfiltrates the token instantly.
- **No supply chain monitoring** → a compromised dependency can inject a crypto-wallet-stealing payload directly into your bundle.
