### The Algorithm Confusion Attack
An attacker changes the `alg` header to `none` and some libraries trust this value and "validate" the JWT without checking any signature. An `RS256` parameter can be changed to `HS256`, and some libraries try to validate using HMAC-SHA256 with the RSA public key as the HMAC shared secret.

```typescript
// ❌ DANGEROUS - library auto-detects algorithm
const decoded = jwt.verify(token, key);

// ✅ SAFE - pin the algorithm explicitly
const decoded = jwt.verify(token, key, { algorithms: ['RS256'] });
```
Always specify the algorithm - never let the JWT library auto-detect. Never allow `algorithms: ['none']`.

### Claim Validation
Pin the accepted algorithm explicitly, verify the signature, and check `exp`, `nbf`, `iss`, and `aud` on every request.

```typescript
jwt.verify(token, publicKey, {
  algorithms: ['RS256'],
  issuer: 'https://auth.example.com',
  audience: 'https://api.example.com',
});
```

### Access Token Expiry
Set JWT access token expiry to **15 minutes or less** - use refresh tokens for session continuity.

### Refresh Token Rotation
Each time a refresh token is used, invalidate it and issue a new one. If an old refresh token is reused, revoke the entire token family (indicates theft).

```typescript
async function refresh(refreshToken: string) {
  const payload = jwt.verify(refreshToken, REFRESH_SECRET);

  // Check if token was already used (rotation)
  if (await isBlacklisted(refreshToken)) {
    // Token reuse detected - revoke entire family
    await revokeTokenFamily(payload.userId);
    throw new Error('Token reuse detected');
  }

  await blacklist(refreshToken);
  return generateTokens(payload.userId);
}
```

### When NOT to Use JWT
Use JWTs only if you genuinely need stateless validation. The reflexive choice of JWT for every API is one of the most common over-engineering moves.

| Use JWT | Use Session Cookies |
|---------|---------------------|
| Stateless validation required | Server-side session store available |
| Multiple services need to verify independently | Single backend service |
| Mobile/third-party API clients | Browser-only SPA (use BFF) |

---

### Deeper Explanation: A JWT Is A Container, Not A Session

A JWT is signed (or encrypted) JSON. Its useful properties are stateless verification and portable claims; its problems are revocation (nothing to invalidate), size (every request carries it), and the payload being readable by anyone holding it. So the engineering rules are: short expiry, minimal claims, no secrets in the payload, and a server-side record for anything that must be revocable.

Verification checks, in order: algorithm is what you expect (reject `none` and algorithm confusion), signature verifies against the correct key, `iss`/`aud` match your service, `exp`/`nbf` (with small clock tolerance), and any custom claims your code depends on. Skipping the algorithm check is the classic vulnerability; skipping `aud` is the one that lets another service's token through.

For sessions, consider the trade explicitly: JWTs scale verification without a database lookup, server-side sessions allow instant revocation. Many products use short-lived access tokens plus a server-side refresh token record â€” the best of both.

### Additional Pitfalls
- **Accepting `alg: none` or trusting the header's algorithm.** Always pin the expected algorithm.
- **Long-lived access tokens with no revocation.** Compromise windows in days, not minutes.
- **Sensitive data inside the payload.** It is base64, not encrypted; assume readability.
- **`localStorage` storage.** Any XSS exfiltrates the token; prefer httpOnly cookies.
- **No `jti`/replay protection for one-time tokens.** Password resets and email links need single use.

### Real-World Deal-Breakers
- **`algorithms: ['none']`** → allows unsigned tokens. Attackers can forge any identity.
- **HS256 with shared secrets in distributed systems** → use RS256 or ES256 asymmetric algorithms.
- **No algorithm pinning** → algorithm confusion attack. Always specify the accepted algorithm.
- **Weak symmetric keys** → vulnerable to offline brute-force. Use at least 256 bits for symmetric keys, 2048 bits for RSA.
- **JWT in localStorage** → XSS steals the token. Use HttpOnly cookies or BFF.
- **Long-lived access tokens** → a stolen token is valid for hours or days. Keep access tokens to 15 minutes or less.
