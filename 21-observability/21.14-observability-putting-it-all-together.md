## 21.13 Observability - Putting It All Together

```

│  ├── Grafana Faro Web SDK (auto + manual instrumentation)      │
```

### What to Instrument First (Priority Order)
1. **Errors** - with sourcemaps, release tags, PII filtering.
2. **Core Web Vitals** - LCP, INP, CLS, TTFB.
3. **API performance** - fetch spans with trace propagation.
4. **User actions** - checkout, signup, key workflows.
5. **Session replay** - on error, and sampled for all sessions.
6. **Custom business metrics** - conversion rate, cart value, feature usage.
7. **Geolocation and segmentation** - browser, device, region.

---

### Deeper Explanation: One Journey, Four Signals, One Budget

The end state is a pipeline where a real user interaction produces a metric, a log line, an error event (only if it failed), and a trace â€” all sharing a correlation id â€” and where the retention and sampling of each is a documented decision. Concretely, for a single `POST /api/orders` from the browser:

1. The frontend emits a span for the fetch and a `web_vital`-style metric for its duration.
2. The collector forwards the span to Tempo, applies a 5% probabilistic sample plus 100% for errors, and strips the `authorization` header.
3. The API writes a structured log with the same `trace_id`, and increments counters with bounded route/status labels.
4. If the call failed, the error monitor groups the issue against the release and attaches the last handful of breadcrumbs.
5. Alerts fire on user-visible symptoms (error rate, INP p75 on the checkout route), each linking a runbook and a trace explorer query.

The budget discipline that makes this sustainable: cap the frontend sampling rate, never label by high-entropy values, define retention per signal, and review the telemetry cost against the incident-recovery time it actually buys.

### Additional Pitfalls
- **Signals that never meet.** If nothing shares a trace id, correlation is manual archaeology at 3am.
- **No owner for the pipeline.** The collector, dashboards, and alerts rot silently without an owner.
- **Alerts without actions.** Every alert needs a runbook and a threshold derived from user impact.
- **Instrumentation without a privacy review.** Telemetry is data collection; treat it with the same rigour as any other user data flow.

### Real-World Deal-Breakers (Overall)
- **No release tracking** → you can't correlate errors with deploys.
- **No sourcemaps in production** → stack traces minified.
- **No PII filtering** → legal and security exposure.
- **No context propagation** → traces break at the browser → API boundary.
- **No SLOs** → no basis for alerting or error budgets.
- **No session replay** → debugging user-reported issues is guesswork.
- **No segmentation** → you miss bugs that only affect specific browsers or regions.
- **Error prioritization by volume** → you fix frequent errors, not the ones killing conversions.
- **No user action tracking** → you know the app is fast, not whether users succeed.
- **Telemetry blocks the app** → an observability SDK failure must never break the product.
