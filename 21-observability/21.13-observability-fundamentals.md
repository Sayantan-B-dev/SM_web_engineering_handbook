## 21.0 Observability Fundamentals

### Subtopic Tree
- Definition: ability to understand system state from external outputs
- The three pillars: logs, metrics, traces

### Observability vs Monitoring

| Monitoring | Observability |
|-----------|---------------|
| "Is the system up?" | "Why is the system behaving this way?" |
| Predefined dashboards | Exploratory investigation |
| Known failure modes | Unknown failure modes |
| Alerts on thresholds | Alerts on symptoms |
| Metrics-only | Logs + metrics + traces |

**Monitoring tells you something is wrong. Observability lets you ask why.**

### The Three Pillars (+ Frontend Context)

| Pillar | Backend | Frontend |
|--------|---------|----------|
| **Logs** | Server logs, request logs | Console errors, custom events |
| **Metrics** | CPU, memory, RPS, latency | Core Web Vitals, error rates, API latency |
| **Traces** | Distributed request tracing | Session tracing, browser → backend spans |

### Frontend Observability Is Fundamentally Different
> "Traditional frontend performance monitoring tells you whether your application is fast. It doesn't tell you whether people are actually succeeding when using it."

Backend observability asks: "Is the server responding?" Frontend observability must ask:
- **Is the user succeeding?** (conversion, workflow completion)
- **Which users are affected?** (browser, device, geolocation, plan)
- **Which session failed?** (session replay)
- **Is this error new?** (release tracking)

### SLI, SLO, SLA, Error Budget

| Term | Definition | Example |
|------|-----------|---------|
| **SLI** (Indicator) | Measured metric | p95 LCP = 2.1s |
| **SLO** (Objective) | Target for SLI | p95 LCP ≤ 2.5s for 99% of sessions |
| **SLA** (Agreement) | Contract with consequences | 99.9% uptime or refund |
| **Error Budget** | Allowed failure rate | 0.1% of requests can fail |

### Deeper Explanation: The Three Questions And The Cost Model

Observability answers three questions in order of urgency: *is it broken?* (alerting), *what broke?* (diagnosis), *why did it break?* (root cause). A dashboard that cannot answer the first is a decoration; most teams over-invest in the third before the first works.

The cost model matters just as much because frontend telemetry is volumetric data produced by untrusted clients:

| Signal | Volume | Cost driver | Keep it cheap by |
|---|---|---|---|
| Logs | High | Ingest + storage | Sampling, levels, no PII |
| Metrics | Low | Cardinality | No user IDs as labels |
| Traces | Medium | Spans Ã- retention | Head + tail sampling |
| Errors | Low | Per-event grouping | Fingerprints and rate limits |
| RUM/Web Vitals | Medium | Per-pageview | Sampling, aggregate before send |

The senior habit: decide the *retention and sampling policy before writing the instrumentation*, because retrofitting sampling onto an unusable signal stream means losing the data you needed.

### Additional Pitfalls
- **Instrumenting everything to syringes-of-logs level.** Signal gets buried; log decisions and outcomes, not every function entry.
- **Cardinality explosions from high-entropy labels.** A `userId` or `sessionId` label on a metric multiplies series and cost without adding insight.
- **Client-side `console.log` as production observability.** It vanishes with the tab and is invisible to the team.
- **No correlation identifier.** Without a request/trace id threaded through client, server, and logs, you reconstruct incidents by timestamp guessing.

### Real-World Deal-Breakers
- **Monitoring ≠ Observability** → threshold alerts without the ability to investigate root cause.
- **Backend-only observability** → you know the API is fast, but not that users can't complete checkout.
- **No SLOs** → no basis for alerting or release gates. You either alert on everything or nothing.
- **No release tracking** → errors spike after a deploy but you can't correlate.
