### Anatomy of a Trace
```
Trace: checkout-flow (2.3s total)
├── span: page_load (0ms → 800ms)
│   ├── span: html_download (0ms → 120ms)
│   ├── span: js_parse (120ms → 250ms)
│   └── span: react_render (250ms → 800ms)
├── span: api_get_cart (800ms → 1100ms)
│   └── span: db_query (820ms → 1080ms)
├── span: user_input (1100ms → 1500ms)
└── span: api_checkout (1500ms → 2300ms)
    ├── span: payment_gateway (1520ms → 2200ms)
    └── span: db_insert_order (2200ms → 2290ms)
```

### Browser → Backend Trace Propagation
```typescript
import { TracingInstrumentation } from '@grafana/faro-web-tracing';

initializeFaro({
  // ...
  instrumentations: [
    new TracingInstrumentation({
      instrumentationOptions: {
        // CRITICAL: without this, browser traces never connect to backend spans
        propagateTraceHeaderCorsUrls: [
          /https:\/\/api\.example\.com\/.*/,
        ],
      },
    }),
  ],
});
```

### Deeper Explanation: A Trace Is The Only View That Crosses Boundaries

Metrics tell you a number moved, logs tell you an event happened, and a trace tells you where the time went â€” across the browser, the edge, the API, the database, and the third-party call. It does this with three primitives: a **trace** (one user-facing operation), **spans** (timed units of work with a parent), and **context propagation** (a `traceparent` header that carries the trace id across process boundaries).

Practical implementation rules:

- **Sample at the edges, keep errors.** Head sampling (1-10%) keeps cost predictable; tail sampling keeps all traces containing an error or exceeding a latency threshold, which is where debugging happens.
- **Name spans for the work, not the function.** `GET /api/orders` beats `orderService.getOrderInternal`.
- **Attach business context as attributes** (`cart.items=3`, `feature=new-checkout`) and never as PII.
- **Correlate with the frontend**: propagate `traceparent` from RUM session to fetch header, and store `trace_id` in your error reports so an issue links to a trace.

### Extended Example: Propagating Trace Context From The Client

```ts
const traceparent = () => {
  const traceId = crypto.randomUUID().replace(/-/g, '');
  const spanId = crypto.randomUUID().slice(0, 16);
  return `00-${traceId}-${spanId}-01`;
};

async function tracedFetch(input: RequestInfo, init: RequestInit = {}) {
  const tp = traceparent();
  const res = await fetch(input, {
    ...init,
    headers: { ...init.headers, traceparent: tp },
  });
  observeSpan({ name: `${init.method ?? 'GET'} ${new URL(input as string, location.origin).pathname}`, tp, status: res.status });
  return res;
}
```

### Additional Pitfalls
- **Traces without sampling.** Full-fidelity traces on a busy site cost more than the app itself.
- **Spans that mirror function calls.** You get a 400-span trace nobody can read; instrument boundaries and await points.
- **Broken context across async boundaries.** Missing propagation produces two unrelated half-traces instead of one story.
- **PII in attributes.** Names, emails, and tokens inside span attributes are the most common accidental leak in telemetry.

### Real-World Deal-Breakers
- **No `propagateTraceHeaderCorsUrls`** → browser traces never connect to backend; you have two disconnected halves.
- **No sampling strategy** → tracing everything is expensive. Sample at 1-10% + 100% on errors.
- **Only backend traces** → you see the API is slow but not that it took the browser 3s to render before the API call.
- **No span attributes** → "this trace was slow" but not "this trace was slow for a user on Safari 17 in Mumbai."
- **No trace_id in logs** → you can't cross-reference logs and traces.
