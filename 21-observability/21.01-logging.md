### Structured Logging
```typescript
// ❌ Unstructured
console.log('User logged in: alice@example.com at ' + new Date());

// ✅ Structured
logger.info('user_login', {
  userId: '123',
  email: '[REDACTED]',
  sessionId: 'abc-123',
  timestamp: new Date().toISOString(),
});
```
Structured logs are **searchable, filterable, and machine-parseable**. The `trace_id` links logs to traces.

### Frontend Logging
```typescript
// Grafana Faro - automatic console capture
import { LogLevel } from '@grafana/faro-web-sdk';

faro.api.pushLog(['User completed checkout'], {
  level: LogLevel.INFO,
  context: { orderId: '456', amount: 99.99 },
});

faro.api.pushError(new Error('Payment failed'), {
  context: { orderId: '456', step: 'payment' },
});
```

### Log Sampling
You can't log everything in production - volume is too high, cost too great. Strategy:
- **Errors** → 100%
- **Warnings** → 100%
- **Info** → sample at 1-10%
- **Debug** → off in production

```typescript
if (Math.random() < 0.01) {
  logger.info('page_view', { path: window.location.pathname });
}
```

### Deeper Explanation: Logs Are Events, Not Print Statements

A production log line is a structured record with a lifetime and a cost. Treat it as an event with fields, not a sentence with interpolations, and three things become possible that never are with `console.log`: aggregation by field, alerting on patterns, and shipping the same event to a database without a parsing regex.

Frontend-specific realities:

- Logs from the browser must be **batched and sampled** (a `Beacon` flush on `visibilitychange`), because one request per log line destroys performance and battery.
- **Never log PII or tokens.** Redaction belongs in the logger, not in the caller's judgement, and the same logger runs client and server so the rule holds in one place.
- **Levels are a contract.** `error` pages someone, `warn` is investigated, `info` is normal lifecycle, `debug` is off in production. Teams that blur them lose their alerting signal first.

### Extended Example: Structured, Sampled, PII-free Client Logger

```ts
type Level = 'debug' | 'info' | 'warn' | 'error';

const secretKeys = new Set(['token', 'password', 'authorization', 'email']);

function redact(obj: Record<string, unknown>) {
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) => [k, secretKeys.has(k.toLowerCase()) ? '[redacted]' : v]),
  );
}

export function log(level: Level, event: string, data: Record<string, unknown> = {}) {
  const record = { level, event, ts: Date.now(), ...redact(data) };
  if (level === 'debug' && !import.meta.env.DEV) return;
  if (level !== 'error' && Math.random() > 0.1) return;   // sample non-errors at 10%
  queue.push(record);
}

// flush once, on the way out â€” never per log line
addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    navigator.sendBeacon('/telemetry/logs', JSON.stringify(queue.splice(0)));
  }
});
```

### Additional Pitfalls
- **String interpolation with user data.** It breaks aggregation and is how PII reaches a log store.
- **Logging on every render or keystroke.** Volume spikes make the whole pipeline expensive exactly when the app is slow.
- **Logging the error object as-is.** `Error` serialises to `{}`; log `message`, `stack`, and a `fingerprint`.
- **Different log shapes per team.** One schema (event name + typed fields) beats ten bespoke formats.

### Real-World Deal-Breakers
- **No structured logs** → `console.log('error')` gives zero context.
- **Logging PII** → emails, tokens, credit cards logged to third-party stores.
- **No sampling** → log volume explodes; costs skyrocket.
- **No `trace_id`** → logs and traces can't be correlated.
- **Only `console.log`** → not captured in production; no observability.
- **No log retention policy** → storage grows forever.
