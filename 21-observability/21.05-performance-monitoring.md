### Real User Monitoring (RUM) vs Synthetic

| RUM | Synthetic |
|-----|-----------|
| Real users, real devices, real networks | Controlled environment |
| Field data | Lab data |
| Millions of data points | Fewer, controlled |
| Reveals real-world issues | Reproducible benchmarks |
| Harder to reproduce | Easier to reproduce |

**You need both.** RUM tells you what's happening; synthetic tells you when it changed.

### Core Web Vitals Collection
```typescript
import { onLCP, onINP, onCLS, onTTFB } from 'web-vitals';

function sendToAnalytics(metric: Metric) {
  faro.api.pushMeasurement({
    type: `web_vitals_${metric.name.toLowerCase()}`,
    values: {
      value: metric.value,
      rating: metric.rating,
      delta: metric.delta,
    },
  });
}

onLCP(sendToAnalytics);
onINP(sendToAnalytics);
onCLS(sendToAnalytics);
onTTFB(sendToAnalytics);
```

### User Timing API for Custom Spans
```typescript
// Mark the start of a user action
performance.mark('checkout-start');

await processPayment();

// Mark the end
performance.mark('checkout-end');

// Measure the duration
performance.measure('checkout-duration', 'checkout-start', 'checkout-end');

const [measure] = performance.getEntriesByName('checkout-duration');
console.log(measure.duration); // ms
```

```yaml
# .github/workflows/ci.yml

```
Fails CI if bundle size exceeds budget - prevents silent regressions.

### Deeper Explanation: Field Data Beats Lab Data

Lab data (Lighthouse, a synthetic run on one machine) explains *how* to fix something. Field data (real users, real devices, real networks) tells you *whether* it matters. The Core Web Vitals are field-oriented by design, and each has a specific decision attached:

- **LCP** â€” was the main content fast? Failures are usually TTFB, blocking CSS/JS, or an unoptimised hero image.
- **INP** â€” did interactions feel instant? Failures are long tasks on the main thread, hydration, or heavy re-renders.
- **CLS** â€” did the layout jump? Failures are unsized media, late fonts, and injected banners.

Aggregate by *experience*, not by average: the standard is p75 over a 28-day window, segmented by device and route. A p75 of 4 s on mobile for one route is an actionable project; a mean of 2.1 s is a number that hides it.

### Extended Example: Route-Level Attribution With `web-vitals`

```ts
import { onLCP, onINP, onCLS, onTTFB, onFCP } from 'web-vitals';

const route = () => {
  const m = location.pathname.match(/^\/(products|checkout|account)\b/);
  return m ? m[1] : 'other';
};

const report = (metric: Metric) => {
  metric('web_vital', {
    name: metric.name,             // LCP, INP, CLS ...
    value: Math.round(metric.value),
    rating: metric.rating,         // good | needs-improvement | poor
    route: route(),
    navigation: metric.navigationType,   // navigate | reload | back-forward
    device: matchMedia('(pointer: coarse)').matches ? 'touch' : 'desktop',
  });
};

[onLCP, onINP, onCLS, onTTFB, onFCP].forEach((fn) => fn(report));
```

### Additional Pitfalls
- **Collecting only in the lab.** Lighthouse 100 with poor field INP means you optimised the wrong metric.
- **Reporting a mean.** Percentiles are the contract; a mean hides the tail that users feel.
- **No route dimension.** "The site is slow" is unactionable; "/checkout on mobile is slow" is a ticket.
- **Measuring on a warm cache only.** Cold-cache, throttled, mid-tier device is the realistic baseline.
- **Long task blindness.** LCP is fine while INP suffers from a 600 ms hydration; measure both.

### Real-World Deal-Breakers
- **Lighthouse only** → lab data ≠ field data. Measure with `web-vitals` + CrUX.
- **Averages instead of percentiles** → p50 of 100ms looks great until you see p99 of 8s.
- **No device segmentation** → performance on a MacBook Pro ≠ performance on a low-end Android.
- **No performance budgets** → every PR grows the bundle; nobody notices until it's 3MB.
- **No RUM** → you don't know how real users experience your app.
- **Ignoring INP** → a fast-loading page with a slow input handler still feels broken.
