## 21.2 Metrics

### Subtopic Tree
- Counter (monotonically increasing)
- Gauge (up/down value)
- Histogram (distribution, percentiles)
- Summary (percentiles in client)
- Dimensions/labels (browser, route, user_tier)
- Aggregation (sum, avg, p50, p95, p99)
- Metrics backends (Mimir, Prometheus, Datadog)
- Frontend metrics (Core Web Vitals, custom business metrics)
- Cardinality (avoid unbounded label values)

### Metric Types

| Type | When to use | Example |
|------|-------------|---------|
| **Counter** | Cumulative events | `api_requests_total` |
| **Gauge** | Current value | `active_sessions` |
| **Histogram** | Distribution | `http_request_duration_seconds` |
| **Summary** | Percentiles | `api_latency_p95` |

### Frontend Metrics
```typescript
// Core Web Vitals → Mimir via Faro
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP((metric) => {
  faro.api.pushMeasurement({
    type: 'lcp',
    values: { value: metric.value, rating: metric.rating },
  });
});

// Custom business metrics
faro.api.pushMeasurement({
  type: 'checkout_completion_time',
  values: { seconds: 45, order_value: 99.99 },
});
```

### Cardinality - The Hidden Cost
Every unique combination of label values creates a new time series. `route="/users/:id"` is fine. `route="/users/12345"` explodes cardinality.

```typescript
// ❌ Unbounded cardinality - millions of series
metrics.record('page_view', { url: window.location.href });

// ✅ Bounded cardinality
metrics.record('page_view', { route: normalizeRoute(window.location.pathname) });
// normalizeRoute('/users/123') → '/users/:id'
```

---

### Deeper Explanation: Metrics Are Cheap Because They Aggregate

A metric is a number with a name, a type, and bounded dimensions. Its value over logs is arithmetic: percentiles, rates, and ratios that alerting can act on. Its danger is cardinality â€” every unique combination of label values is a separate time series, and a high-entropy label multiplies series until the backend charges you for it.

Frontend metrics worth instrumenting, and the type to use:

| Metric | Type | Anti-pattern |
|---|---|---|
| Requests, errors, retries | Counter | Using a gauge that resets |
| Request duration, INP, LCP | Histogram | Storing the average only |
| Active websockets, queue depth | Gauge | Never decreasing |
| Error rate, cache hit rate | Derived ratio | Pre-aggregating raw counts per user |

Golden signals for any frontend service: **latency** (INP/LCP/API p75-p95), **traffic** (requests per route), **errors** (JS + 5xx), **saturation** (long tasks, memory, connection pool). Alert on symptoms (error rate, INP p75) rather than causes, and keep high-cardinality identifications in logs and traces, not labels.

### Extended Example: Comparable Cardinality-Safe Metrics

```ts
// Counters and histograms with bounded labels only.
const metric = (name: string, labels: Record<string, string>) =>
  navigator.sendBeacon('/telemetry/metrics', JSON.stringify({ name, labels, ts: Date.now() }));

// BAD: labels:{ userId, url } â†’ unbounded series
// GOOD: route is a bounded enum, never the full URL
metric('api_request_total', { route: '/api/orders', method: 'GET', status: '500' });
metric('api_request_duration_ms', { route: '/api/orders', bucket: '250' });

// Ratio, computed at query time so thresholds live in one place
// error_rate = rate(api_request_total{status=~"5.."}[5m]) / rate(api_request_total[5m])
```

### Additional Pitfalls
- **Averages for latency.** One 30-second outlier hides inside a 200 ms mean; use histograms and p75/p95.
- **User IDs, session IDs, or full URLs as labels.** That is the classic five-figure observability bill.
- **Counters that reset on reload.** Name them as counters and let the backend handle resets; do not fake them with gauges.
- **Dashboards nobody looks at.** Each dashboard should exist because an alert links to it, or it should be deleted.

### Real-World Deal-Breakers
- **Unbounded labels** → metric cardinality explodes; query performance tanks and costs surge.
- **No percentiles** → averages hide tail latency. A p50 of 100ms with p99 of 5s is a broken app.
- **No dimensions** → "errors happened" but not "errors on Safari 17.2 in India."
- **Counting without context** → `request_count` is useless without status, route, and duration.
- **No business metrics** → you know the app is up, not whether users are converting.
