### Setup (React)
```bash
npm install @sentry/react
```

```typescript
import * as Sentry from '@sentry/react';

Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment: process.env.NODE_ENV,
  release: process.env.NEXT_PUBLIC_APP_VERSION,
  tracesSampleRate: 0.1, // 10% of transactions
  replaysSessionSampleRate: 0.01, // 1% of sessions
  replaysOnErrorSampleRate: 1.0,  // 100% of sessions with errors
  integrations: [
    Sentry.browserTracingIntegration(),
    Sentry.replayIntegration({
      maskAllText: true,     // PII safety
      blockAllMedia: true,
    }),
  ],
  beforeSend(event) {
    // Filter PII
    if (event.user?.email) event.user.email = '[REDACTED]';
    return event;
  },
});
```

### What Sentry Does Well
- **Error tracking** - best in class. Fingerprinting, grouping, ownership, alert routing.
- **Performance** - traces, Web Vitals, custom spans.
- **Session Replay** - PII-safe by default.
- **Release tracking** - correlate errors with deploys.

### Sentry's Limits
- **Traces are sampled** - 100% tracing is expensive.
- **Session Replay is a separate SKU** - costs add up.
- **Not a full logging solution** - for logs, use Loki or Datadog.
- **Vendor lock-in** - while Sentry is open source, the managed cloud is the primary product.

---

### Deeper Explanation: The Workflow Is The Product

Sentry's differentiator is not error capture (everyone captures errors) but the loop around it: grouping into issues, assigning ownership, linking to the commit and release that introduced it, and tracking "regressed in version X". Configure those three things â€” **sourcemaps, releases, ownership** â€” and the tool pays for itself; skip them and you get a colourful list nobody reads.

Practical configuration that changes outcomes:

- **`release` and `dist`** per deploy so you can answer "which version is this, and is it new?".
- **Sourcemaps uploaded with the artifact** (hidden sourcemaps, uploaded in CI) â€” the single highest-value configuration item.
- **`beforeSend` scrubbing** for PII, cookies, and tokens; treat the error monitor as an untrusted sink.
- **Ownership rules** mapping route/path prefixes to teams, so issues land with the people who can fix them.
- **Alerting on new issues and regressions only**, with a spike detector rather than per-event notifications.

### Extended Example: CI Upload Plus Issue-Routing Rules

```yaml
- name: Build with hidden sourcemaps
  run: pnpm build   # vite: build.sourcemap: 'hidden'
- name: Create release and upload maps
  env:
    SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
  run: |
    npx sentry-cli releases new "web@$GITHUB_SHA"
    npx sentry-cli sourcemaps upload --release "web@$GITHUB_SHA" dist
    npx sentry-cli releases set-commits "web@$GITHUB_SHA" --auto
    npx sentry-cli releases finalize "web@$GITHUB_SHA"
```

### Additional Pitfalls
- **Public sourcemaps in the CDN.** Upload hidden maps to the error monitor and keep them private.
- **One Sentry project for everything.** Frontend, backend, and mobile noise mix; separate projects or at least separate environments and filters.
- **No release tagging.** Every issue looks equally new and regressions are invisible.
- **Alerts on every occurrence.** Teams mute the channel; alert on new issues, regressions, and spikes.
- **PII in breadcrumbs and request bodies.** It is the most common accidental data-flow into a third party.

### Real-World Deal-Breakers
- **No release tag** → errors spike after deploy but you can't correlate.
- **No sourcemap upload** → stack traces minified.
- **No PII filtering** → user emails/tokens sent to Sentry.
- **100% tracing** → huge bill.
- **No error boundary** → React errors silently lost.
- **No ownership rules** → errors go to no one; nobody fixes them.
