### User Action Tracking
Track the workflows that matter:
```typescript
faro.api.pushEvent('checkout_started', { cart_value: 99.99 });
faro.api.pushEvent('payment_submitted', { method: 'card' });
faro.api.pushEvent('checkout_completed', { order_id: '12345' });
faro.api.pushEvent('checkout_failed', { reason: 'card_declined' });
```

Now you can answer:
- What % of checkouts complete?
- Where do users drop off?
- Which payment methods fail most?
- Are failures correlated with a browser or region?

### Session Replay
Grafana Cloud's Session Replay lets you **visually replay what a user saw and did** inside your web application.
```typescript
initializeFaro({
  // ...
  instrumentations: [
    ...getWebInstrumentations({
      captureConsole: true,
      captureErrors: true,
    }),
    new SessionReplay(),
  ],
});
```

**Privacy warning:** Session replay records user interactions (clicks, keystrokes, screens). **Mask PII by default.**

### Segmentation - The Real Value
```text
"Error rate: 0.1%" - not actionable
"Error rate: 0.1% overall, but 12% for Safari 17.2 in India" - actionable
```

Always segment by:
- Browser / version
- Device / OS
- Geolocation
- User tier (free vs paid)
- App version
- Network type (WiFi vs 4G)

### Deeper Explanation: RUM Is Behaviour, Not Just Timing

Real User Monitoring answers "what did the session actually experience" â€” the funnel, the rage clicks, the JS error that happened just before abandonment. It complements performance data with behaviour, and its value depends on being *privacy-aware by construction*: session replay and heatmaps involve recording real user input, so masking, consent, and retention are design decisions, not settings.

Useful RUM questions and their signals:

| Question | Signal |
|---|---|
| Where do users abandon? | Step funnel + exit rate per step |
| Which errors precede churn? | Error rate per session, grouped by route |
| Do users fight the UI? | Rage clicks, dead clicks, scroll thrash |
| Is the new UI better? | Experiment cohort split by completion rate |
| Where is the true device mix? | Device/browser/network segmentation |

### Extended Example: Session Replay With Input Masking On By Default

```ts
Sentry.init({
  integrations: [
    Sentry.replayIntegration({
      maskAllText: true,               // opt in per element, not opt out
      maskAllInputs: true,
      blockAllMedia: true,             // no images/video in replay
    }),
  ],
  replaysOnErrorSampleRate: 1.0,
  beforeSend(event) {
    if (event.user) event.user = { id: pseudonymize(event.user.id) };
    return event;
  },
});
```

### Additional Pitfalls
- **Recording inputs by default.** Passwords and card fields end up in the replay unless masking is on by default.
- **No consent story.** Recording EU sessions without a documented lawful basis is a compliance problem.
- **Retention without policy.** Replays accumulate; set the shortest retention that still debugs incidents.
- **Correlating replay with identity in the clear.** Pseudonymise the user id and keep the mapping in your own database.
- **Using RUM as an A/B testing platform.** Experiments need assignment logic and statistics, not eyeballed replays.

### Real-World Deal-Breakers
- **No user action tracking** → you know the app is fast but not whether users are succeeding.
- **No session replay** → debugging a user-reported issue is guesswork.
- **No segmentation** → you miss that a bug only affects Safari users in one region.
- **Session replay without PII masking** → GDPR violation, legal exposure.
- **Errors prioritized by volume** → fix frequent errors, miss the conversion killer.
