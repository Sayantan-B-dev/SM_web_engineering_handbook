### Error Grouping
Errors are grouped by **fingerprint** - a hash of the stack trace, message, and error type. Without grouping, the same error from 1,000 sessions looks like 1,000 separate issues.

### Stack Traces + Sourcemaps (Critical)
```typescript
// In production, errors look like this without sourcemaps:
//   TypeError: t is not a function
//     at n (main.a1b2c3.js:1:45234)
//     at r (main.a1b2c3.js:1:45678)

// With sourcemaps:
//   TypeError: handleSubmit is not a function
//     at LoginForm (src/components/LoginForm.tsx:42:15)
//     at onClick (src/components/LoginForm.tsx:58:7)
```
**Always upload sourcemaps in CI.** Sentry, Faro, Datadog all support automatic sourcemap upload.

### Impact Prioritization (Not Volume)
Grafana's redesigned errors view **triages errors by user impact** rather than volume. An error affecting 10,000 users is more important than one affecting 100.

```text
❌ Prioritize by volume:
   1. "Cannot read property 'x'" (10,000 occurrences, 50 users)
   2. "Checkout button broken" (800 occurrences, 8,000 users)

✅ Prioritize by impact:
   1. "Checkout button broken" (8,000 users affected)
   2. "Cannot read property 'x'" (50 users affected)
```

### React Error Boundary + Monitoring
```tsx
class ErrorBoundary extends React.Component {
  componentDidCatch(error: Error, errorInfo: React.ErrorInfo) {
    captureException(error, {
      extra: errorInfo,
      tags: {
        app_version: process.env.NEXT_PUBLIC_APP_VERSION,
        route: window.location.pathname,
      },
    });
  }

  render() {
    if (this.state.hasError) return <ErrorFallback />;
    return this.props.children;
  }
}
```

### Deeper Explanation: Group, Rank, Assign â€” In That Order

An error monitor is a *triage queue*, not a log file. Three properties decide whether it earns its place: **grouping** (thousands of occurrences collapse into one issue with a stable fingerprint), **prioritisation** (users affected Ã- severity Ã- release regression, not raw count), and **ownership** (an issue has an assignee or rules route it to one).

Frontend-specific quality levers:

- **Sourcemaps uploaded per release** so the stack trace is readable; without them every issue is `t.min.js:1:48213`.
- **Release tagging** (`release: 2026-10-13.3`) so regressions are attributable to a deploy, and so a bad release's noise can be filtered while rolling back.
- **Handled vs unhandled split.** Deliberate `captureException` for business failures, automatic capture for crashes â€” mixing them makes severity meaningless.
- **Noise control** at the boundary: ignore `ResizeObserver loop`, browser-extension errors, `AbortError`, and third-party script stack traces by filtering on `error.source`/URL.

### Extended Example: SDK Configuration With Filters And Breadcrumbs

```ts
Sentry.init({
  dsn: env.VITE_SENTRY_DSN,
  release: `web@${__COMMIT_SHA__}`,
  environment: env.MODE,
  tracesSampleRate: 0.05,
  replaysOnErrorSampleRate: 1.0,
  replaysSessionSampleRate: 0,          // only capture when something went wrong
  ignoreErrors: [/ResizeObserver loop/, /AbortError/, /chrome-extension:\/\//],
  beforeSend(event) {
    if (event.request?.cookies) delete event.request.cookies;   // never ship cookies/tokens
    if (event.user) event.user = { id: hash(event.user.id) };   // pseudonymous
    return event;
  },
});

// business failures deserve intent, not ambiguity
function placeOrder(cart: Cart) {
  try {
    return api.orders.create(cart);
  } catch (err) {
    Sentry.captureException(err, { tags: { flow: 'checkout' }, extra: { items: cart.items.length } });
    throw err;
  }
}
```

### Additional Pitfalls
- **Shipping without sourcemaps.** Every stack trace becomes unreadable and triage stops.
- **`ignoreErrors` used to hide real bugs.** Filter third-party noise; never filter your own paths.
- **No release/session metadata.** You cannot answer "did this start with today's deploy?".
- **Alerts on every event.** Alert on issue creation and on rate regressions, not on each occurrence.
- **Capturing PII as breadcrumbs.** Form values and URLs with tokens end up in the issue; scrub them in `beforeSend`.

### Real-World Deal-Breakers
- **No sourcemap upload** → stack traces minified and useless.
- **No error grouping** → the same bug looks like 1,000 bugs.
- **No release tracking** → errors spike after deploy, but you can't correlate.
- **No error boundary** → React rendering errors silently lost.
- **Prioritizing by volume** → fix frequent low-impact errors, miss the conversion killer.
- **No PII filtering** → user data (emails, tokens, credit cards) sent to third-party services.
