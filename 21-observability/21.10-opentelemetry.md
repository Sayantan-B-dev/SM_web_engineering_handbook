### What OpenTelemetry Is
OpenTelemetry (OTel) is a **vendor-neutral, open standard** for collecting telemetry. One SDK, one protocol (OTLP), any backend. You instrument once, and can send data to Grafana, Datadog, Honeycomb, Jaeger, or any OTLP-compatible backend.

### Signals
| Signal | What it captures |
|--------|-----------------|
| **Traces** | Request flow with spans |
| **Metrics** | Counters, gauges, histograms |
| **Logs** | Structured log events |
| **Baggage** | Key-value context propagated across services |

### Browser Setup
```typescript
import { WebTracerProvider } from '@opentelemetry/sdk-trace-web';
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { registerInstrumentations } from '@opentelemetry/instrumentation';
import { FetchInstrumentation } from '@opentelemetry/instrumentation-fetch';
import { DocumentLoadInstrumentation } from '@opentelemetry/instrumentation-document-load';
import { resourceFromAttributes } from '@opentelemetry/resources';
import { ATTR_SERVICE_NAME } from '@opentelemetry/semantic-conventions';

const provider = new WebTracerProvider({
  resource: resourceFromAttributes({
    [ATTR_SERVICE_NAME]: 'my-frontend',
    'deployment.environment': 'production',
    'app.version': process.env.NEXT_PUBLIC_APP_VERSION,
  }),
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({ url: '/v1/traces' })
    ),
  ],
});

registerInstrumentations({
  instrumentations: [
    new DocumentLoadInstrumentation(),
    new FetchInstrumentation({
      propagateTraceHeaderCorsUrls: [/https:\/\/api\.example\.com\/.*/],
    }),
  ],
});
```

### OTLP (OpenTelemetry Protocol)
The wire protocol that carries telemetry from your app → collector → backend. Supports gRPC and HTTP. Most backends accept OTLP natively.

### Relation to Other Tools
- **Grafana Faro** → uses OTel under the hood for tracing.
- **Sentry** → accepts OTel traces via SDK bridge.
- **Datadog** → supports OTLP ingestion.
- **Honeycomb** → OTLP-native.

---

### Deeper Explanation: The Standard Exists So You Can Change Vendors

OpenTelemetry defines the data model (spans, metrics, logs), the SDKs that produce it, and the wire protocol (OTLP) that transports it. Adopting it is a bet on *portability*: your instrumentation survives a backend migration, and frontend, edge, and backend emit the same shape of data so correlation is free.

For the browser specifically:

- **Use the lightweight web SDKs** (`@opentelemetry/sdk-trace-web`, `instrumentation-fetch`, `instrumentation-document-load`) plus a user-interaction instrumentation for click-originated spans.
- **Batch and export via OTLP/HTTP** to a collector, not directly to a vendor endpoint, so sampling, filtering, and enrichment live in one place.
- **Set a service name and resource attributes** (`service.name=web`, `deployment.environment`, `service.version`) â€” without them, filtering by release is impossible later.
- **Correlate with your RUM error monitor** by putting `trace_id` in error events.

### Extended Example: Browser SDK Wired For Sampling And Correlation

```ts
import { WebTracerProvider } from '@opentelemetry/sdk-trace-web';
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { ZoneContextManager } from '@opentelemetry/context-zone';
import { registerInstrumentations } from '@opentelemetry/instrumentation';
import { FetchInstrumentation } from '@opentelemetry/instrumentation-fetch';
import { resourceFromAttributes } from '@opentelemetry/resources';

const provider = new WebTracerProvider({
  resource: resourceFromAttributes({
    'service.name': 'web-app',
    'service.version': __APP_VERSION__,
    'deployment.environment': env.MODE,
  }),
  sampler: { shouldSample: () => ({ decision: Math.random() < 0.05 ? 1 : 0 }) },
});

provider.addSpanProcessor(
  new BatchSpanProcessor(new OTLPTraceExporter({ url: '/otlp/v1/traces' })),
);
provider.register({ contextManager: new ZoneContextManager() });

registerInstrumentations({
  instrumentations: [
    new FetchInstrumentation({
      propagateTraceHeaderCorsUrls: [/^https:\/\/api\.example\.com/],
      clearTimingResources: true,
    }),
  ],
});
```

### Additional Pitfalls
- **Exporting straight to a vendor.** You lose the ability to sample, filter, and enrich centrally, and migration becomes a code change everywhere.
- **Missing resource attributes.** Traces without `service.version` cannot be tied to a deploy.
- **Span-per-function instrumentation.** Unreadable traces; instrument boundaries and user journeys.
- **Browser SDK on the critical path.** Export must be batched and asynchronous or it competes with rendering.

### Real-World Deal-Breakers
- **No context propagation** → traces break at service boundaries.
- **No semantic conventions** → custom attributes are inconsistent; queries become guesswork.
- **OTel in the browser without sampling** → 100% of page loads traced; huge cost.
- **No collector** → apps send directly to backends; no batching, no retry, no enrichment.
- **Assuming one-size-fits-all** → OTel is a standard, not a product. You still need a backend.
