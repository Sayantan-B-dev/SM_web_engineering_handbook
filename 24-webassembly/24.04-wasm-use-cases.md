### Production Case Studies

**ZEISS (microservices):** ZEISS implemented Fermyon's SpinKube platform, leveraging WASM to deploy event-driven microservices within existing Kubernetes clusters. Sample WASM applications achieved approximately **60% cost reductions**.

**Fermyon Wasm Functions on Akamai:** Scales to **75 million RPS**. Use cases include stopping bots at the front door, redirecting hundreds of thousands of URLs within 1 millisecond, and delivering sub-100ms time-to-first-byte for live streaming.

**Oracle MySQL WASM integration:** Deploy custom tokenization algorithms, run high-speed data cleaning, domain-specific engines, analytics, custom encryption/decryption, and image metadata extraction - all inside the database.

**@askturret/grid (React + Rust/WASM):** A high-performance React data grid handling **1 million rows at 60fps** with Rust+WASM trigram indexing. Sort: 18ms. Filter: <1ms. Render: <16ms.

### Deeper Explanation: The Shortlist Of Genuine Wins

WASM earns its complexity when one of four conditions holds: the code already exists in another language, the workload is numerically intensive, the code must run untrusted (sandbox), or the task must be portable across browser/edge/server. In production that maps to a short list:

- **Media**: image/video/audio codecs (raw decode, resizing, thumbnailing, filters).
- **Compression**: zstd/brotli/gzip in the browser for archives and large payloads.
- **Crypto**: constant-time primitives, signature/verification, zero-knowledge proofs.
- **Data engines**: SQLite (sql.js / OPFS-backed), DuckDB-WASM, Arrow/Polars for analytics.
- **Parsers**: PDF, Office documents, postscript fonts, CAD, GIS.
- **Simulation**: physics, gaming engines, audio DSP, computer vision (often with WebGPU or workers).
- **ML runtimes**: ONNX Runtime Web, TFLite, Transformers.js, whisper.cpp.

The common denominator: existing native code, hot numeric inner loops, large binary inputs, and a result that must come back to JS once.

### Additional Pitfalls
- **Rewriting small JS utilities in Rust "for speed".** Boundary and startup costs exceed the gain.
- **Pulling a 5 MB engine for a rare feature.** Lazy-load it behind a user action and show progress.
- **Ignoring WASM startup on mobile.** Parse/compile can be 10Ã- slower on low-end devices than on a laptop.
- **Shipping a native library without its licence review.** GPL/AGPL options exist across the ecosystem; check before vendoring.
- **No fallback path.** If the module fails to compile (CSP, MIME, size limits), the feature must degrade.

### Real-World Deal-Breakers
- **Using WASM for CRUD apps** → no benefit; JS is simpler and sufficient.
- **Using WASM for text processing** → string interop overhead kills the advantage.
- **Not profiling before/after** → WASM can be slower for small workloads.
- **Assuming WASM works everywhere** → server-side WASM (WASI) is still maturing; check runtime support.
