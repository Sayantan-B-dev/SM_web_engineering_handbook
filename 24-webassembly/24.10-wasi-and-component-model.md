### What WASI Is
WASI is the **system interface** for WebAssembly - it defines how WASM modules interact with the outside world (files, network, clocks, random). It's the enabler for server-side WASM.

> "WASI 0.3 brings native async to WebAssembly components, moving asynchronous functionality that previously lived in the wasi:io package into the core component model."

### Component Model
The Component Model defines a **standard, language-neutral, portable, and compositional way** to specify interfaces for coarse-grained interoperation between WebAssembly modules and the host environment or other WebAssembly components written in a different language.

```wit
// WIT (WebAssembly Interface Types)
interface calculator {
  add: func(a: u32, b: u32) -> u32;
  subtract: func(a: u32, b: u32) -> u32;
}

world my-app {
  export calculator;
  import wasi:filesystem/filesystem;
}
```

### Server-Side WASM Platforms
- **wasmCloud** - CNCF project; write business logic in any supported language (Rust, Go, etc.), deploy anywhere.
- **SpinKube** - Fermyon's Kubernetes operator; WASM instead of Docker containers.
- **Fermyon Wasm Functions** - edge serverless at 75M RPS.

### Deeper Explanation: WASI Is What Makes WASM Portable Beyond The Browser

Core WASM has no I/O: no files, no sockets, no clock. WASI defines those as **capability-based interfaces** where the host grants specific rights (this directory, this socket, this clock) â€” which is why the same module runs in a browser, Node, Deno, Cloudflare Workers, and a serverless runtime with only the host's capability set differing.

The component model layers composition on top: components declare typed imports/exports via WIT, so a component written in Rust can be composed with one written in Go without a shared ABI by hand. For web engineers the near-term relevance is real:

- **Edge functions** using WASI modules (Cloudflare Workers, Fastly Compute).
- **Portable plugins** â€” user-supplied extensions (for example, a custom extractor) run sandboxed with a granted capability set.
- **Shared logic across client and server** â€” same WASM artifact in a worker and in a Node/edge function.

### Additional Pitfalls
- **Confusing core WASM with WASI.** Browser engines do not implement WASI by default; you need a JS-side shim or a compliant runtime.
- **Assuming capability-based means safe.** Granted capabilities can still be abused; least privilege applies to directories and sockets.
- **Betting production on a preview interface.** Track the spec status and pin versions.
- **Ignoring the composition glue cost.** Cross-component calls have their own marshalling overhead; benchmark the seams.

### Real-World Deal-Breakers
- **Assuming WASI is stable** → WASI is still evolving (0.3.x as of 2026). API changes happen.
- **Component model for browser-only apps** → overkill. Components shine for server-side composition.
- **No WIT contract** → components can't compose across languages without a shared interface definition.
