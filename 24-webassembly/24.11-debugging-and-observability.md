### Debugging in Chrome DevTools
WASM is debuggable in Chrome DevTools if you compile with **DWARF debug info**:
```bash
# Rust with debug info
wasm-pack build --dev -- --debug

# Emscripten with debug info
emcc -g -o output.js input.c
```
Then in DevTools → Sources → you can set breakpoints and step through WASM.

### Whamm (Runtime Monitoring)
Whamm is a monitoring and debugging tool that accesses Wasm at runtime. Modules can be reused independently of the specific app. Developers use it to monitor, test, and debug Wasm apps.

### Wasmtime v39 (WebAssembly-Level Debugging)
Wasmtime v39 (November 2025) added initial support for **WebAssembly-level debugging natively** - operating at the WebAssembly abstraction level rather than machine-level. This complements existing DWARF-level debugging.

### LLDB WebAssembly Process Plugin
LLVM added a WebAssembly Process Plugin to LLDB, tested with the WebAssembly Micro Runtime (WAMR), which implements a GDB debug stub and supports the `qWasmCallStack` packet.

### Deeper Explanation: Debugging Crosses Two Languages

Debugging a WASM-in-JS app means keeping three things in view: the **JS side** (where the module lives, when it is instantiated, what messages cross), the **module side** (DWARF debug info, source maps for the original language), and the **memory** (linear memory, allocations, growth). In practice:

- **Build with debug symbols** (`debug = true` in Rust, `-g4` in emscripten, `-g` in AssemblyScript) and keep a separate release build for production. DWARF makes stack traces show real function names and line numbers.
- **Chrome DevTools** can show WASM frames when symbols are present, and pause inside wasm functions.
- **Source maps**: `wasm-bindgen` and AssemblyScript emit source maps so the JS glue maps to Rust/AS.
- **In production, symbolise offline.** Keep the symbolised build per release and turn a raw offset number into a name.
- **Instrument both halves** with the same trace id: a span on the JS call and a span inside the module (or at least timing marks around the boundary) so a slow path is attributable.

### Additional Pitfalls
- **Optimised builds only.** `wasm-opt -O3` strips names; debugging becomes offset archaeology.
- **No symbol artefacts kept per release.** You cannot symbolise a production crash after the build is gone.
- **Panics that trap silently.** A Rust panic becomes an `unreachable` trap; wire a panic hook that reports a message to JS.
- **Measuring only inside the module.** Copy-in/copy-out and instantiation are usually the largest costs.
- **Unhandled traps crashing the app.** Wrap every entry call and surface a typed error to React's error boundary.

### Real-World Deal-Breakers
- **No debug info in production builds** → WASM debugging is impossible; stack traces are opaque.
- **Debugging complex code without DWARF** → you see raw WASM instructions, not source code.
- **No runtime monitoring** → you can't see what WASM is doing inside the sandbox without instrumentation.
