### Toolchain Comparison

| Language | Toolchain | Best for | Binary size |
|----------|-----------|----------|-------------|
| **Rust** | `wasm-pack` + `wasm-bindgen` | Safety-critical, performance | Small |
| **C/C++** | Emscripten | Porting existing code | Medium |
| **AssemblyScript** | `asc` | TypeScript developers | Small |
| **Go** | TinyGo | Go developers, smaller binaries | Small |
| **C#/.NET** | Blazor | .NET ecosystem, React integration | Large |
| **Kotlin** | Kotlin/Wasm | Android/JVM developers | Medium |

> "Rust is the best fit - Rust has the most mature WASM toolchain (wasm-bindgen, wasm-pack)."

### Rust → WASM Workflow
```bash
# Install
cargo install wasm-pack

# Create library
cargo new --lib my-wasm-lib
cd my-wasm-lib

# Cargo.toml
[lib]
crate-type = ["cdylib"]

[dependencies]
wasm-bindgen = "0.2"

# Build
wasm-pack build --target web
# → pkg/my_wasm_lib.js (glue code)
# → pkg/my_wasm_lib_bg.wasm (binary)
```

### wasm-opt (Binaryen Optimizer)
```bash
wasm-opt -O3 -o optimized.wasm original.wasm
```
Optimizes WASM for size and speed. Use `-Oz` for size-critical, `-O3` for speed-critical.

### Deeper Explanation: Choose The Toolchain By Team, Not By Benchmark

Toolchains differ most in *who can maintain the code*, and the resulting ergonomics:

| Toolchain | Source language | Best for | Watch out for |
|---|---|---|---|
| Rust + wasm-bindgen/wasm-pack | Rust | New kernels, performance-critical libraries | Build complexity, toolchain pinning |
| Emscripten | C/C++ | Porting existing native code, SDL/GL apps | Large output, glue complexity |
| AssemblyScript | TypeScript-like | Teams that are all-JS, small hot paths | Subset of TS, smaller ecosystem |
| TinyGo | Go | Small binaries, embedded-style code | Limited standard library |
| .NET / Blazor | C# | Enterprise teams, existing .NET code | Payload size and startup |
| Kotlin/Wasm, Dart | Kotlin, Dart | Managed-language apps, GC-types era | Maturity and size |

Bundler integration matters as much as the compiler: Vite needs `?url`/`vite-plugin-wasm` and `optimizeDeps.exclude` for glue packages; webpack needs `asyncWebAssembly` experiments; Next.js needs the wasm asset served from a stable URL and often `outputFileTracingIncludes` for server-side use.

### Additional Pitfalls
- **`wasm-pack` output imported with a dynamic path.** Bundlers cannot statically analyse it; import through Vite's URL handling.
- **MIME type problems.** A `.wasm` served as `application/octet-stream` fails `instantiateStreaming`; configure the server.
- **No CI caching for the toolchain.** Rust + wasm builds are slow; cache `~/.cargo` and `target/` or every build pays full cost.
- **Ignoring binary size budgets.** A 4 MB module on a mid-tier phone is a multi-second startup; strip, `opt-level=z`, and `wasm-opt`.
- **Committing generated glue by hand.** Generate it in the build; hand-editing is guaranteed to drift.

### Real-World Deal-Breakers
- **Using Emscripten for new Rust projects** → wasm-bindgen is more ergonomic and produces smaller binaries.
- **AssemblyScript for heavy computation** → slower than Rust/C++ (though close - ~3% slower in one test).
- **Not running `wasm-opt`** → leaving 20-40% size/speed optimization on the table.
- **No WASM bundler integration** → need a plugin (Vite: `vite-plugin-wasm`, Webpack: `experiments.asyncWebAssembly`).
