## 24.1 WebAssembly 3.0 (The 2025 Standard)

### Subtopic Tree
- Released September 17, 2025
- 64-bit address space (i64 memory)

### The Major Features
Wasm 3.0 is a substantially larger update than 2.0. Several features have been in the making for six to eight years.

**64-bit address space:** Memories and tables can now use `i64` as their address type. This expands the available address space from 4 gigabytes to theoretically 16 exabytes. On the web, 64-bit memory is limited to 16 gigabytes, but non-web ecosystems can support much larger applications.

**Multiple memories:** A single module can now declare and access multiple memories directly, including copying data between them. This enables `wasm-merge` (static linking of modules) and new uses for separate address spaces - security, buffering, or instrumentation.

**Garbage collection:** Wasm now supports a separate form of storage automatically managed by the runtime via a garbage collector. Compilers can declare memory layout using struct and array types plus unboxed tagged integers. Everything else - method tables, closures, object systems - remains the compiler's responsibility.

**Typed references and tail calls:** The GC extension enables richer reference types with subtyping and type recursion. This allows safe indirect function calls without runtime type checks (`call_ref`). Tail calls avoid stack growth, critical for functional languages and internal stub techniques.

### Deeper Explanation: What Version 3.0 Actually Unlocked

The 3.0-era standard bundles several features that change *what you can build*, not just how fast it runs:

| Feature | Why it matters |
|---|---|
| **GC types** | Structs/arrays with managed references, so Kotlin, Dart, Java, OCaml can compile without bundling their own GC |
| **Exception handling** | Real `try/catch` across the boundary instead of error-code plumbing |
| **Tail calls** | Recursive/functional code without stack growth â€” required for Scheme-style and interpreter loops |
| **Multi-memory** | Separate memories for data and scratch; better isolation and simpler ports |
| **Relaxed SIMD** | Portable, faster vector kernels across engines |
| **Memory64** | Memories beyond 4 GB (server-side heavy) |
| **Threads + atomics** | True parallelism inside a worker (needs cross-origin isolation) |

The engineering consequence: languages with managed runtimes are now plausible web targets, and the "WASM is only for C/Rust kernels" assumption is dated.

### Additional Pitfalls
- **Assuming engine parity.** Feature support lands at different times across V8, SpiderMonkey, and JavaScriptCore; feature-detect with `WebAssembly.validate`.
- **Adopting GC types for a numeric kernel.** You add indirection for no gain; keep hot loops on plain typed arrays.
- **Shipping two toolchains' runtimes.** Managed-language output can be larger than the code you wrote; check bundle size, not just speed.
- **Ignoring memory64's real cost.** 64-bit indices make every access slightly more expensive; only use it when you need the address space.

### Real-World Deal-Breakers
- **Assuming 64-bit is free** → WebAssembly apps tend to run slower in 64-bit mode than 32-bit. The performance penalty depends on the workload. Only use Memory64 if you actually need more than 4GB.
- **Expecting GC to eliminate all manual memory management** → Wasm GC is low-level. It provides struct and array types, but compilers still handle higher-level constructs.
- **Using multiple memories for everything** → more memories means more overhead. Use only when you have distinct address spaces.
