### Loading a WASM Module
```javascript
// ✅ Best - streaming compilation
const response = await fetch('module.wasm');
const { instance } = await WebAssembly.instantiateStreaming(response);
// Server must serve Content-Type: application/wasm

// Fallback - arrayBuffer
const bytes = await fetch('module.wasm').then(r => r.arrayBuffer());
const { instance } = await WebAssembly.instantiate(bytes);
```

### Calling WASM from JS
```javascript
// Rust (wasm-bindgen) exports
// #[wasm_bindgen]
// pub fn calculate_primes(limit: u32) -> Vec<u32> { ... }

import init, { calculate_primes } from './pkg/my_lib.js';

await init();
const primes = calculate_primes(1_000_000); // JS calls WASM
```

### Calling JS from WASM
```javascript
// Pass JS functions as imports
const importObject = {
  env: {
    log: (value) => console.log('From WASM:', value),
  },
};

const { instance } = await WebAssembly.instantiate(bytes, importObject);
// WASM calls importObject.env.log()
```

### Interop Performance
Interop operations are roughly **an order of magnitude slower** than operations within the same boundary. Benchmark: JS interop at 0.000254 ms per operation vs .NET at 0.000021 ms per operation - **~12× slower**.

```text
Cross-boundary call:  ~0.25 µs per operation
In-boundary call:     ~0.02 µs per operation
```

For tight loops calling across the boundary, this overhead dominates.

### Minimizing Interop Overhead
```javascript
// ❌ BAD - many small cross-boundary calls
for (let i = 0; i < 1_000_000; i++) {
  wasm.processPixel(i); // 1M boundary crossings
}

// ✅ GOOD - one call, batch inside WASM
wasm.processAllPixels(buffer, length); // 1 crossing
```

### Deeper Explanation: The Boundary Is The API Design Problem

Interop between JS and WASM is a marshalling problem, and its cost is dominated by three things: **how many calls**, **how much data per call**, and **who owns the memory**. Design the interface around bulk operations over shared buffers:

- One call that processes a whole buffer beats 10 000 calls that process one element.
- Pass offsets and lengths into a single pre-allocated memory rather than creating views per item.
- Keep strings out of hot paths â€” encode once into a reused scratch buffer.
- Prefer returning a handle (an index into a WASM-side table) over copying structures out.

The idiomatic glue tools (wasm-bindgen, embind, AssemblyScript) make the ergonomics pleasant but not free: every `string` parameter through wasm-bindgen allocates, copies, and frees.

### Extended Example: Structure-Of-Arrays Exchange

```ts
// Rust side (sketch): pure functions over a float buffer, no allocation per call
// #[wasm_bindgen] pub fn heat_map_inplace(ptr: *mut f32, len: usize, k: f32) { ... }

const floats = new Float32Array(1_000_000);
const ptr = wasm.alloc(floats.byteLength);
new Uint8Array(wasm.memory.buffer, ptr, floats.byteLength).set(new Uint8Array(floats.buffer));

performance.mark('wasm-start');
wasm.heat_map_inplace(ptr, floats.length, 0.4);   // one call, one million elements
performance.mark('wasm-end');

// Copy back only what the UI needs to display
const result = new Float32Array(wasm.memory.buffer, ptr, floats.length).slice();
wasm.free(ptr, floats.byteLength);
```

### Additional Pitfalls
- **Re-creating views after `memory.grow()`.** Growth detaches every existing view; re-acquire them.
- **Leaking WASM allocations.** Every `alloc` needs a matching `free`, or memory climbs until the tab dies.
- **Passing strings in a loop.** Each one is an encode-copy-decode round trip; use a scratch buffer.
- **Assuming the same objects.** JS objects are not shared; only numeric memory is.
- **Benchmarking with `console.time` around one call.** Include the copy in and out or you measure fiction.

### Real-World Deal-Breakers
- **Individual DOM property access from WASM** → interop is slow and creates many proxies with high GC pressure. Batch operations.
- **Passing strings frequently** → strings must be encoded/decoded at the boundary. Minimize string passing.
- **No `instantiateStreaming`** → slower startup. Serve `.wasm` with `application/wasm` MIME type.
- **Calling across the boundary in tight loops** → 10× overhead. Batch work inside WASM.
