## 24.0 WebAssembly Fundamentals

### Subtopic Tree
- Definition: portable binary instruction format

- Versionless, backwards-compatible standard
- W3C standard since 2019

### The Core Mental Model
WebAssembly (WASM) is not a programming language you write by hand. It is a **portable compilation target** - a binary instruction format designed as a complement to JavaScript, not a replacement. You write code in C, C++, Rust, Go, or AssemblyScript, compile it to `.wasm`, and run it in the browser at near-native speed.

```text
C/C++/Rust source → Compiler (Emscripten/wasm-pack) → .wasm binary
                                                       ↓
                                             Browser WASM runtime
                                             (V8, SpiderMonkey, JSC)
```

### What WASM Is NOT
- **Not a JavaScript replacement** - it runs alongside JS, not instead of it.
- **Not a language you write directly** - you compile to it.
- **Not always faster** - for small tasks, JS can be faster due to interop overhead.
- **Not DOM-aware** - WASM has no access to the DOM. You bridge through JavaScript.

---

### Deeper Explanation: Wasm Is A Compilation Target, Not A Language

WebAssembly is a portable binary instruction set with a linear memory and a capability-based import/export model. Everything confusing about it comes from those three properties:

- **Linear memory is a single `ArrayBuffer`.** JS and WASM share it by index, not by reference. Passing a string means encoding into bytes, copying in, and decoding on the way out â€” that boundary cost is the whole performance story.
- **Imports/exports are the ABI.** JS supplies functions (env imports); WASM exposes functions. Nothing else crosses implicitly, which is why glue code (wasm-bindgen, Emscripten, AssemblyScript loaders) exists.
- **It is deterministic and sandboxed.** No ambient authority: a module can only do what JS hands it. That makes it safe to load untrusted code, and it is why WASI (a system interface) had to be invented for anything file/network-related.

Practical expectation setting: WASM is typically 1.1-2Ã- native for compute kernels, faster than JS by 2-20Ã- for tight numeric code, and slower than JS for anything dominated by string/object manipulation at the boundary.

### Additional Pitfalls
- **Assuming any JS compiles to fast WASM.** GC languages and dynamic dispatch add overhead; the wins are numeric, typed, and allocation-light.
- **Ignoring boundary costs.** A "10Ã- faster" kernel that crosses the boundary 10 000 times per second is a net loss.
- **Loading a 30 MB module eagerly.** Compile and instantiate lazily; it is startup cost, not just bytes.
- **Expecting DOM access.** WASM cannot touch the DOM; it returns data and JS renders it.

### Real-World Deal-Breakers
- **Treating WASM as a JS replacement** → it's a complement. UI rendering and event handling stay in JS.
- **Writing WASM by hand** → you compile to it. Hand-written `.wat` is for debugging, not production.
- **Assuming WASM is always faster** → interop overhead (JS↔WASM boundary) can make small tasks slower.
- **No fallback for old browsers** → WASM is supported everywhere modern, but check your baseline.
