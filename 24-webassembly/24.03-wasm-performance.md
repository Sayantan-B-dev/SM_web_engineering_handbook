## 24.3 WASM Performance

### Subtopic Tree
- Single-thread performance (2-4× faster than JS)
- Multi-thread performance (shared memory + atomics)
- Memory consumption (higher than JS)
- JIT vs AOT (Ahead-of-Time)
- Battery/power consumption
- Compilation time vs execution time
- Benchmarking methodology

### The Numbers
Research across multiple studies consistently shows WASM outperforms JavaScript for compute-intensive tasks. In web browsers, WASM in a single thread performs **2-4× faster** than pure JS implementations. WASM also performs better in energy consumption, with the advantage becoming more pronounced as program input size grows.

WASM binaries compiled from C/C++ perform better than those compiled from Rust or Go. Firefox generally performs better than Chrome for WASM execution.

### The Memory Trade-off
WASM consumes **much more memory than JS**. This is a deliberate trade-off: WASM's linear memory model is simpler and faster but less memory-efficient than JS's garbage-collected heap.

### AOT Compilation
Ahead-of-Time compilation can achieve **10×-40× speedups** over interpreted WASM for enterprise workloads.

---

### Deeper Explanation: Where The Speed Actually Comes From

WASM's speed has four sources and they are not interchangeable: **compact typed memory** (no boxing, no shape checks), **predictable control flow** (no hidden megamorphic dispatch), **SIMD** (4-16 lanes per instruction), and **AOT/AOT-like compilation** (the engine compiles once, well). If your workload lacks all four, WASM will not be faster than well-written JS.

### Additional Pitfalls
- **Benchmarking cold.** Compilation and first-call deoptimisation dwarf steady-state; warm up first.
- **Copying data in and out per call.** That cost is outside the kernel measurement and inside the user's experience.
- **Assuming SIMD is automatic.** Auto-vectorisation is limited; use explicit SIMD intrinsics or a library that does.
- **Comparing against naive JS.** A hand-optimised JS version with typed arrays closes much of the gap.
- **Ignoring memory bandwidth.** Both runtimes share the same bus; at scale you hit the same ceiling.

### Real-World Deal-Breakers
- **Assuming WASM is always faster** → for small tasks, interop overhead makes it slower. Profile both.
- **Ignoring memory overhead** → WASM's higher memory consumption can be a problem on low-end devices.
- **Not benchmarking across browsers** → performance varies significantly. Test Chrome, Firefox, and Safari.
- **Using WASM without SIMD or threads** → you're leaving 2-4× performance on the table.
