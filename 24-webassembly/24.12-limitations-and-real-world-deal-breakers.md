## 24.11 Limitations & Real-World Deal-Breakers

### Subtopic Tree
- DOM access (WASM has none)
- Interop overhead (10× slower than in-boundary)
- Memory overhead (higher than JS)
- Debugging complexity
- Cross-browser performance variance
- Compatibility issues
- Third-party ecosystem smaller than expected
- Security trade-offs
- Thread locking and heap contention

### The Honest Limitations
Tech teams adopting WASM face several roadblocks:

**DOM access:** "Wasm doesn't have direct access to the DOM, meaning we had to bridge data between JavaScript and Wasm, which can introduce significant overhead and increase complexity." The recommended approach is to segment tasks: image processing and data manipulation go to WASM, while UI rendering and event handling stay in JavaScript.

**Interop overhead:** Roughly **10× slower** than in-boundary operations. For tight loops across the boundary, this dominates.

**Memory:** "Wasm consumes much more memory than JS" - a deliberate trade-off for performance.

**Debugging:** "Debugging is complex and not well-supported".

**Cross-browser performance:** "Don't take cross-browser performance for granted" - performance varies significantly across Chrome, Firefox, and Safari.

**Third-party ecosystem:** "The third-party ecosystem is smaller than you think".

**Thread locking:** Portable multithreading in WASM suffers from excessive thread locking caused by the default WASI libc memory allocator. Replacing it with mimalloc (each thread allocates from its own heap) mitigates heap contention.

### Deeper Explanation: The Honest Cost Model

WASM is not free speed; it is a different set of costs. Before adopting it, price all five:

| Cost | Typical magnitude | Mitigation |
|---|---|---|
| Startup (download + compile) | 100 ms - 3 s | lazy load, `compileStreaming`, cache the compiled module |
| Boundary marshalling | 1-3 ms per MB copied | transfer buffers, batch calls, shared memory |
| Module size | 0.5-10 MB | `-Oz`, wasm-opt, strip symbols, split modules |
| Memory footprint | 2-10Ã- JS for the same data | reuse buffers, free allocations, cap heap |
| Team cost | Rust/C++ toolchain in CI, two debugging stacks | keep the surface small and behind one hook |

The decision rule: adopt WASM when the workload is hot, numeric, well-bounded, and already exists natively â€” or when you specifically need sandboxed untrusted code. Avoid it for UI logic, string processing, small utilities, and anything that would not survive a strict performance budget anyway.

### Additional Pitfalls
- **"Rewrite it in Rust" as a first optimisation.** Usually the problem is re-renders, unbounded lists, or unnecessary network calls.
- **Shipping WASM in the critical path.** Lazy-load behind interaction unless it is the product (an editor, a codec).
- **Two teams, one boundary, no contract.** Define the interface as typed data crossing a single module boundary.
- **No performance budget.** Without a target (startup ms, kernel ms, bytes), you cannot tell success from novelty.
- **Ignoring the fallback path forever.** Unsupported browsers, CSP restrictions, and device limits all exist; the JS path must remain tested.

### The Complete Deal-Breaker Checklist

| Area | Deal-Breaker | Consequence |
|------|-------------|-------------|
| **Fundamentals** | Treating WASM as JS replacement | It's a complement, not a replacement |
| **Fundamentals** | Writing WASM by hand | Compile from Rust/C++/AS |
| **WASM 3.0** | Assuming 64-bit is free | Slower than 32-bit; only use if >4GB needed |
| **WASM 3.0** | Expecting GC to handle everything | Wasm GC is low-level; compilers still manage higher-level constructs |
| **Interop** | Many small cross-boundary calls | 10× overhead per call |
| **Interop** | Individual DOM property access | Slow, creates GC pressure |
| **Interop** | Frequent string passing | Encode/decode overhead |
| **Performance** | Assuming WASM is always faster | Small tasks are slower due to interop |
| **Performance** | Ignoring memory overhead | WASM uses more memory than JS |
| **Performance** | No cross-browser testing | Performance varies significantly |
| **Use Cases** | WASM for CRUD apps | No benefit; JS is simpler |
| **Use Cases** | WASM for text processing | String interop kills the advantage |
| **Browser Computation** | WASM on main thread | Blocks UI; use Web Worker |
| **Browser Computation** | SharedArrayBuffer without COOP/COEP | Throws |
| **React Integration** | WASM computation during render | Blocks React rendering |
| **React Integration** | Not terminating workers on unmount | Memory leak |
| **Tooling** | Emscripten for new Rust projects | wasm-bindgen is more ergonomic |
| **Tooling** | No `wasm-opt` | 20-40% size/speed left on the table |
| **WASI** | Assuming WASI is stable | Still evolving (0.3.x) |
| **Debugging** | No debug info in production | WASM debugging impossible |
| **Limitations** | DOM access from WASM | Impossible; bridge through JS |
| **Limitations** | Thread locking | Default WASI libc allocator causes heap contention |
