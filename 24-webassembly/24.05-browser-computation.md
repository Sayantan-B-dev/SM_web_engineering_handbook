### WASM in a Web Worker
```javascript
// main.js - offload to worker
const worker = new Worker('wasm-worker.js');
worker.postMessage({ type: 'PROCESS', data: imageData.buffer }, [imageData.buffer]);

// wasm-worker.js
let wasm;

self.onmessage = async (e) => {
  if (!wasm) {
    const { instance } = await WebAssembly.instantiateStreaming(fetch('image.wasm'));
    wasm = instance.exports;
  }
  const result = wasm.process_image(e.data.data, e.data.length);
  self.postMessage({ result });
};
```

### WASM + SharedArrayBuffer (Threads)
```javascript
// Requires cross-origin isolation (COOP + COEP)
const memory = new WebAssembly.Memory({
  initial: 256,
  maximum: 256,
  shared: true, // enables pthreads
});

const { instance } = await WebAssembly.instantiate(bytes, {
  env: { memory },
});

// Spawn worker threads
const workers = [];
for (let i = 0; i < 4; i++) {
  workers.push(new Worker('thread.js'));
  workers[i].postMessage({ memory, threadId: i });
}
```

### Deeper Explanation: Four Ways To Compute In A Browser, In Order

Browser computation options form a spectrum from flexible to narrow, and picking the wrong end wastes months:

| Option | Strength | Limitation |
|---|---|---|
| JavaScript (typed arrays) | Zero setup, JIT-optimised, DOM access | Single thread, no SIMD control |
| WebAssembly (CPU) | Predictable throughput, existing native code | Boundary cost, no DOM |
| WebAssembly + threads | True parallel CPU | Cross-origin isolation, complexity |
| WebGPU / WebNN | Massive parallelism for data-parallel work (ML, graphics) | Device/API availability, different programming model |

The practical ladder: try a JS optimisation first (typed arrays, avoid boxing, chunk work), move to WASM when the kernel is hot and stable, add threads when the workload chunks well, and reach for WebGPU when the problem is *data-parallel* rather than *fast scalar*. Many "we need WASM" problems are really "we need to stop re-rendering" problems.

### Additional Pitfalls
- **Choosing the tool before measuring.** Profile first; the bottleneck is often React re-renders, not arithmetic.
- **Assuming WebGPU is always available.** It needs a modern browser and a non-blocklisted GPU; ship a CPU fallback.
- **Forgetting the memory limit.** Large WASM heaps and GPU buffers on mobile hit hard caps and get the tab killed.

### Real-World Deal-Breakers
- **WASM on the main thread** → still blocks UI. Always run in a Web Worker.
- **SharedArrayBuffer without COOP/COEP** → throws. Requires cross-origin isolation headers.
- **No SIMD** → 2-4× performance left on the table for data-parallel workloads.
- **Not using streaming compilation** → slower startup. `instantiateStreaming` compiles while downloading.
