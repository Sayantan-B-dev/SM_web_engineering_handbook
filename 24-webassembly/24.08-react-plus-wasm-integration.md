### Loading WASM in a React Component
```tsx
import { useState, useEffect } from 'react';

function WasmCalculator() {
  const [wasm, setWasm] = useState(null);
  const [result, setResult] = useState(null);

  useEffect(() => {
    let mounted = true;
    (async () => {
      const { instance } = await WebAssembly.instantiateStreaming(
        fetch('/calculator.wasm')
      );
      if (mounted) setWasm(instance.exports);
    })();
    return () => { mounted = false; };
  }, []);

  function calculate() {
    if (!wasm) return;
    const result = wasm.heavy_calculation(1_000_000);
    setResult(result);
  }

  if (!wasm) return <Spinner />;
  return <button onClick={calculate}>Calculate</button>;
}
```

### WASM + Web Worker in React
```tsx
function useWasmWorker(url) {
  const workerRef = useRef(null);
  const [result, setResult] = useState(null);

  useEffect(() => {
    const worker = new Worker(url);
    workerRef.current = worker;
    worker.onmessage = (e) => setResult(e.data);
    return () => worker.terminate();
  }, [url]);

  const process = useCallback((data) => {
    workerRef.current?.postMessage(data);
  }, []);

  return { result, process };
}
```

import { ComputeKitProvider, useComputeKit } from '@computekit/react';

function App() {

function HeavyComponent() {
  const { compute } = useComputeKit();

  const result = await compute('heavyFunction', data);

### WASM-Powered Virtualization (Warper)
Warper is a Rust + WASM React virtualization library. Benchmarks: 100,000 items → react-window at **~40 FPS** vs Warper at **120 FPS**. At 1 million items, Warper maintains **120+ FPS** with adaptive overscan and skip-render optimization.

### Deeper Explanation: WASM Belongs Behind A Hook, Not In A Component

React's rendering model and WASM's imperative, memory-based model clash in two specific ways: component re-renders can re-trigger expensive work, and WASM instances are singletons with global state. The integration pattern that survives review:

- **One instance, module-scoped.** Compile/instantiate once (or per worker), never per component.
- **A hook owns the lifecycle.** `useEffect` for load/unload, `AbortController`/cancellation for in-flight jobs, cleanup on unmount.
- **Jobs are requests with results.** The hook exposes `{ run, status, progress, result }`; components stay declarative.
- **Never hold WASM memory in React state.** State holds derived, serialisable snapshots; the buffer stays outside the render tree.
- **Code-split the module.** `import()` the loader so the WASM bytes are not in the initial bundle.

### Extended Example: A Load-Once, Cancel-Aware Hook

```tsx
import { useCallback, useEffect, useRef, useState } from 'react';

type Status = 'idle' | 'loading' | 'ready' | 'running' | 'error';

export function useWasmWorker<TIn, TOut>(loader: () => Promise<Worker>) {
  const workerRef = useRef<Worker>();
  const [status, setStatus] = useState<Status>('loading');

  useEffect(() => {
    let cancelled = false;
    loader().then((w) => {
      if (cancelled) { w.terminate(); return; }
      workerRef.current = w;
      setStatus('ready');
    }).catch(() => setStatus('error'));
    return () => {
      cancelled = true;
      workerRef.current?.terminate();
      workerRef.current = undefined;
    };
  }, [loader]);

  const run = useCallback((input: TIn): Promise<TOut> => {
    const worker = workerRef.current;
    if (!worker) return Promise.reject(new Error('not ready'));
    setStatus('running');
    const id = crypto.randomUUID();
    return new Promise((resolve, reject) => {
      const onMessage = ({ data }: MessageEvent<{ id: string; ok: boolean; result?: TOut; error?: string }>) => {
        if (data.id !== id) return;                 // ignore stale results
        worker.removeEventListener('message', onMessage);
        setStatus('ready');
        data.ok ? resolve(data.result!) : reject(new Error(data.error));
      };
      worker.addEventListener('message', onMessage);
      worker.postMessage(input);
    });
  }, []);

  return { status, run };
}
```

### Additional Pitfalls
- **Instantiating inside a component or a hook body.** React re-renders instantiate repeatedly; use a module-level cache or a ref.
- **Storing the WASM module or memory in state.** It triggers warnings, breaks immutability assumptions, and defeats memoisation.
- **Ignoring staleness.** Two in-flight jobs can return out of order; correlate by id and discard stale results.
- **Blocking render with a synchronous kernel.** Wrap the call so it can be cancelled or moved off-thread.
- **Forgetting StrictMode.** Development double-mount will instantiate twice unless the effect cleans up properly.

### Real-World Deal-Breakers
- **WASM computation during render** → blocks React rendering. Use `useEffect` + Web Worker.
- **Not terminating workers on unmount** → memory leak. Return `worker.terminate()` in cleanup.
- **Passing large data via React state** → triggers re-renders and copies. Use refs + Transferable Objects.
- **No WASM loading fallback** → React renders before WASM is ready; guard with loading state.
