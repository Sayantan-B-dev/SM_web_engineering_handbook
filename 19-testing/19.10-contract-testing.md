### What Contract Testing Solves
Contract testing ensures the **Provider** meets the exact data needs (the "Contract") of the **Consumer**, without having to spin up both services simultaneously for slow and brittle E2E tests. The consumer (frontend) specifies expected interactions; the provider (backend) verifies it honors them.

### Pact Workflow
```typescript
// Consumer (frontend) test
import { PactV3, MatchersV3 } from '@pact-foundation/pact';

const provider = new PactV3({
  consumer: 'FrontendWeb',
  provider: 'UserService',
});

it('fetches a user', async () => {
  await provider
    .given('user 1 exists')
    .uponReceiving('a request for user 1')
    .withRequest({ method: 'GET', path: '/users/1' })
    .willRespondWith({
      status: 200,
      body: MatchersV3.like({ id: 1, name: 'Alice', email: 'alice@example.com' }),
    })
    .executeTest(async (mockServer) => {
      const user = await fetchUser(mockServer.url, 1);
      expect(user.name).toBe('Alice');
    });
});
```

### The Contract
The consumer test generates a **pact file** (`frontendweb-userservice.json`) describing the expected interactions. This file is published to a Pact Broker.

### Provider Verification
```typescript
// Provider (backend) verification
const verifier = new Verifier({
  providerBaseUrl: 'http://localhost:3000',
  pactBrokerUrl: 'https://your-broker.pactflow.io',
  provider: 'UserService',
  publishVerificationResult: true,
});

await verifier.verifyProvider();
```
The backend runs the pact file against its real implementation. If it fails, the backend knows it broke the frontend's expectations.

### When Contract Testing Replaces E2E
- **Replaces** → slow, brittle full-stack integration tests for API shape.
- **Doesn't replace** → true user journey E2E tests (checkout flow, login flow).

---

### Deeper Explanation: Contracts Make Independent Deploys Safe

Contract testing exists because the expensive failure in distributed systems is not a broken component â€” it is a *compatible pair that drifts*. Consumer-driven contracts turn that into a build-time failure: the consumer records the interactions it depends on, and the provider proves in its own CI that it still satisfies every recorded interaction. Neither side needs the other running.

In practice React teams implement contracts at one of three weights:

1. **Schema as contract (cheapest, most common).** One Zod/TypeBox schema per endpoint, shared from a `packages/contracts` workspace. The client parses responses, the server parses requests; drift becomes a parse error plus a compile error where the schema's types are used on both sides.
2. **Spec as contract.** OpenAPI or GraphQL SDL is the source of truth, the client is generated, and a lint step fails the build on a breaking change. Best when non-JS consumers exist.
3. **Pact (consumer-driven, executable).** Generated interaction files are verified against the provider: the strongest guarantee and the most ceremony, worth it when two teams release on independent trains.

### Extended Example: One Schema Enforced On Both Sides

```typescript
// packages/contracts/src/order.ts
import { z } from 'zod';

export const Order = z.object({
  id: z.uuid(),
  status: z.enum(['pending', 'paid', 'cancelled']),
  totalCents: z.int().nonnegative(),
  createdAt: z.iso.datetime(),
});
export type Order = z.infer<typeof Order>;

export const ListOrders = z.object({
  items: z.array(Order),
  nextCursor: z.string().nullable(),
});
```

```typescript
// consumer test â€” the client fails loudly when the provider drifts
it('surfaces a contract violation as an error state', async () => {
  server.use(http.get('/api/orders', () => HttpResponse.json({ items: [{ id: 1 }] })));
  const { result } = renderHook(() => useOrders(), { wrapper });
  await waitFor(() => expect(result.current.isError).toBe(true));
  expect(result.current.error).toMatchObject({ name: 'ZodError' });
});

// provider test â€” the server still emits the contract
it('GET /orders matches the shared schema', async () => {
  const res = await app.inject({ method: 'GET', url: '/api/orders' });
  expect(ListOrders.safeParse(res.json()).success).toBe(true);
});
```

### Additional Pitfalls
- **Contract tests on the happy path only.** Error envelopes, pagination edges, and 401 shapes are where drift actually bites.
- **Hand-writing types on both sides.** Two interfaces drift silently; a shared schema package turns drift into a compile error.
- **Verifying provider contracts only nightly.** By morning the provider has shipped a breaking change and production is broken.
- **Assuming an API version bump makes changes safe.** Additive fields usually are; renames and tightening (non-nullable, narrowed enums) are breaking regardless of the version string.
- **Treating generated types as validation.** Types vanish at runtime â€” parse the response or you have no contract.

### Real-World Deal-Breakers
- **No Pact Broker** → contracts can't be shared; verification is manual.
- **Contracts not verified on provider CI** → frontend and backend drift silently.
- **Testing only happy path** → error responses (400, 404, 500) must also be in the contract.
- **Over-relying on contract tests** → they verify data shape, not behavior. E2E still needed for critical journeys.
- **No versioning** → contract changes break consumers silently. Use consumer version selectors.
