## 19.3 Component Testing

### Subtopic Tree

### React Testing Library Philosophy
RTL encourages testing components **the way users interact with them**: query by accessible names, roles, and text - not implementation details. Test behaviour, not implementation. Avoid testing internal state. Focus on user interactions.

### Query Priority
Use queries in this order of preference:

| Priority | Query | Use for |
|----------|-------|---------|
| **1** | `getByRole` | Almost everything - buttons, links, inputs, headings |
| **1** | `getByLabelText` | Form fields |
| **2** | `getByPlaceholderText` | Inputs with no label (and a hint to add one) |
| **3** | `getByText` | Non-interactive content |
| **4** | `getByTestId` | Escape hatch - last resort |

```tsx
// ✅ Best - accessible to everyone
screen.getByRole('button', { name: /submit/i });

// ✅ For form fields
screen.getByLabelText('Email');

// ⚠️ Fallback - prefer a label
screen.getByPlaceholderText('Enter your email');

// ❌ Last resort
screen.getByTestId('submit-btn');
```

### `userEvent` vs `fireEvent`
**Always prefer `userEvent`** - it simulates real user interactions (focus, keyboard, pointer events) while `fireEvent` just dispatches a single DOM event.

```tsx
import userEvent from '@testing-library/user-event';

// ✅ userEvent - simulates the full interaction
const user = userEvent.setup();
await user.click(screen.getByRole('button', { name: /submit/i }));
await user.type(screen.getByLabelText('Email'), 'test@example.com');

// ❌ fireEvent - dispatches a single event, no focus/pointer simulation
fireEvent.click(screen.getByRole('button'));
```

### Async Handling
```tsx
// ❌ Don't do this
await waitFor(() => {
  expect(screen.getByText('Loaded')).toBeInTheDocument();
});

// ✅ Prefer findBy - built-in waitFor + getBy
expect(await screen.findByText('Loaded')).toBeInTheDocument();

// ✅ Use waitFor only for assertions that aren't queries
await waitFor(() => {
  expect(mockFn).toHaveBeenCalledTimes(1);
});
```
**Rule:** Use `findBy` instead of `waitFor` + `getBy`.

### Full Component Test Example
```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { LoginForm } from './LoginForm';

describe('LoginForm', () => {
  it('submits with valid credentials', async () => {
    const onSubmit = vi.fn();
    const user = userEvent.setup();

    render(<LoginForm onSubmit={onSubmit} />);

    await user.type(screen.getByLabelText(/email/i), 'alice@example.com');
    await user.type(screen.getByLabelText(/password/i), 'password123');
    await user.click(screen.getByRole('button', { name: /sign in/i }));

    expect(onSubmit).toHaveBeenCalledWith({
      email: 'alice@example.com',
      password: 'password123',
    });
  });

  it('shows validation errors', async () => {
    const user = userEvent.setup();
    render(<LoginForm onSubmit={vi.fn()} />);

    await user.click(screen.getByRole('button', { name: /sign in/i }));

    expect(await screen.findByText(/email is required/i)).toBeInTheDocument();
    expect(screen.getByText(/password is required/i)).toBeInTheDocument();
  });
});
```

### Playwright Component Testing
Playwright Component Testing mounts UI components in a **real browser** without a full application. It provides true isolation, with a mounting and mocking model that's reliable and allows unit testing UI components without an actual server. Ideal for design systems and component libraries.

```typescript
// playwright-ct.config.ts
import { defineConfig } from '@playwright/experimental-ct-react';

export default defineConfig({
  testDir: './src',
  use: {
    ctPort: 3100,
  },
});
```

```tsx
// Button.spec.tsx
import { test, expect } from '@playwright/experimental-ct-react';
import { Button } from './Button';

test('renders and handles click', async ({ mount }) => {
  let clicked = false;
  const component = await mount(<Button onClick={() => { clicked = true; }}>Click</Button>);
  await component.click();
  expect(clicked).toBe(true);
});
```

### Deeper Explanation: Confidence Comes From Roles, Not Selectors

A component test is a *user simulation in jsdom*. Its assertions should survive a refactor that changes class names, DOM nesting, state shape, and internal APIs â€” and they only do so if queries are anchored to the accessibility tree. RTL's query order encodes that priority:

1. `getByRole` (with `name`) â€” how assistive tech and the user identify the control
2. `getByLabelText` / `getByPlaceholderText` â€” form affordances
3. `getByText` â€” content the user reads
4. `getByDisplayValue` â€” the current value of a control
5. `getByTestId` â€” last resort for structurally anonymous elements

When a component is hard to query by role, that is usually an accessibility bug rather than a tooling problem, which is why component tests are also the cheapest a11y regression net you have.

### Extended Example: Async Combobox With Keyboard Selection

```tsx
import { render, screen, within, waitFor } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('filters options and selects with the keyboard', async () => {
  const user = userEvent.setup();
  render(<CityPicker onSelect={vi.fn()} />);

  const input = screen.getByRole('combobox', { name: /city/i });
  await user.type(input, 'ko');

  const listbox = await screen.findByRole('listbox');
  expect(within(listbox).getAllByRole('option')).toHaveLength(2);

  await user.keyboard('{ArrowDown}{Enter}');
  await waitFor(() => expect(input).toHaveValue('Kolkata'));
  expect(screen.queryByRole('listbox')).not.toBeInTheDocument();
});
```

### Additional Pitfalls
- **`fireEvent.change` on a controlled input.** It skips focus, typing, and composition events; `userEvent.type` catches bugs the shortcut cannot.
- **Forgetting to `await` an interaction.** Every `await user.*` must be awaited or React updates stay pending and you get an `act()` warning.
- **Fake timers plus `userEvent`.** Install fake timers before `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })`, otherwise typed input never processes.
- **`toMatchSnapshot()` on a whole tree.** Large snapshots go unreviewed; assert the two or three roles that matter.
- **Querying by text split across elements.** `getByText` throws when markup breaks the string; `getByRole('button', { name: 'Save draft' })` normalises the accessible name.

### Real-World Deal-Breakers
- **`getByTestId` as primary query** → test breaks when you rename a test ID; doesn't verify accessibility.
- **`fireEvent` instead of `userEvent`** → misses focus/keyboard behavior; tests pass but real users can't interact.
- **`waitFor` + `getBy` instead of `findBy`** → verbose, slower, easier to get wrong.
- **Testing implementation details** → `expect(component.state.count).toBe(1)` breaks on refactor.
- **No `await` on `userEvent`** → interactions aren't fully processed.
- **`screen.debug()` left in tests** → console noise; remove before committing.
