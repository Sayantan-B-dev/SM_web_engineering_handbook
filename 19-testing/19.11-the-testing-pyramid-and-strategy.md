## 19.0 The Testing Pyramid & Strategy

### Subtopic Tree
- Unit tests (fast, isolated, many)

- Component tests (UI behavior in isolation)
- End-to-end tests (slow, full stack, few)

### The Modern Testing Pyramid

```text
        /\
       /E2E\         ← Few. Slow. Full app in real browser.
      /------\
     /  INT   \      ← Moderate. Real boundaries, mocked externals.
    /----------\
   / COMPONENT  \    ← Many. UI behavior, user-centric.
  /--------------\
 /     UNIT       \  ← Most. Pure logic, fast, isolated.
/------------------\
```

| Layer | Speed | Confidence | Count | What it tests |
|-------|-------|-----------|-------|---------------|
| **Unit** | ms | Low | Many | Pure functions, hooks, utils |
| **Component** | 10-100ms | Medium | Many | User-visible behavior of one component |
| **Integration** | 100ms-1s | High | Moderate | Multiple components + real API boundaries |
| **Contract** | 1-10s | High | Few | Service boundaries (frontend ↔ backend) |
| **E2E** | 1-30s | Very high | Few | Full user journeys in a real browser |

### The Testing Trophy (Kent C. Dodds)
The trophy emphasizes **integration tests** as the sweet spot: high confidence with reasonable speed. Unit tests are still valuable for pure logic, but over-investing in shallow unit tests gives false confidence.

### What to Test
- **Business logic** → unit tests
- **User interactions** → component tests
- **Data flow across components** → integration tests
- **Critical user journeys** → E2E tests
- **API contracts** → contract tests

### What NOT to Test
- Third-party libraries
- Framework internals
- Implementation details (CSS classes, state variable names)
- Trivial getters/setters
- Snapshot everything

---

### Deeper Explanation: The Cost Curve, Not Just The Shape

The pyramid is really a statement about the *cost curve* of confidence. A test's value is `probability of catching a regression Ã- cost of that regression`, and its price is `runtime + maintenance`. As you move up the pyramid both the value and the price rise, but the price rises faster, because higher-level tests duplicate the assertions of everything below them. That is why a healthy suite is not "one of each" but a deliberate distribution: roughly **70% unit/component, 20% integration, 10% E2E** for most product apps.

Two forces move that distribution:

1. **Architecture.** A pure-function core (pricing, validation, state machines) is cheap to test at the unit layer, so the pyramid stays bottom-heavy. A component that owns fetching, validation, and rendering has almost nothing to unit-test, so budget shifts to integration.
2. **Change frequency.** Code that changes weekly needs fast local tests. Code that changes yearly (auth, payments) earns an expensive E2E test even if it runs once per pull request.

The pyramid also answers "what should I *not* test": third-party library internals, CSS values, exact markup structure, private functions, and anything already guaranteed by the type system.

### Extended Example: Choosing The Cheapest Test That Actually Catches The Bug

```text
Change                                     Test that catches it
-----------------------------------------  --------------------------------------------------
Discount maths tweak                       Unit (pure function)
Form field labels / ordering               Component (role + label queries)
Checkout posts the right payload           Integration (MSW asserts the request body)
Session expiry redirects to login          E2E (real cookies, real server)
Date formatting uses the wrong locale      Unit with a pinned ICU locale
Bundle imports a server-only module        Build or lint check, not a test at all
```

### Additional Pitfalls
- **Chasing a coverage number instead of a risk model.** 100% line coverage with no edge-case assertions protects nothing; a 60% suite that covers every branch of the money path protects everything.
- **Duplicating the same assertion at three layers.** If the unit test proves the discount maths, the E2E test should prove the number is *displayed*, not re-derive it.
- **Measuring the pyramid once.** Distribution drifts as features land; re-measure each quarter or the "sweet spot" quietly becomes an E2E suite.
- **Treating mutation testing as a novelty.** It is the only reliable way to know your assertions bite. Run it on the critical module, not the whole repository.

### Real-World Deal-Breakers
- **Testing implementation details** → tests break on every refactor. Test behavior, not internals.
- **100% coverage goal** → chasing coverage leads to low-value tests. Aim for meaningful coverage.
- **Only E2E tests** → slow CI, flaky tests, hard to debug.
- **Only unit tests** → false confidence; components can still be broken.
- **No tests at all** → refactoring is terrifying; regressions ship silently.
