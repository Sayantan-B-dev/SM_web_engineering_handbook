## 19.7 React Testing Library (RTL)

### Subtopic Tree
- `render`, `screen`, `within`
- Queries: `getBy`, `queryBy`, `findBy` + `*AllBy`
- Query priority (role → label → text → testId)
- `userEvent` (preferred) vs `fireEvent`
- `waitFor` for non-query assertions
- `act` for state updates
- Custom render with providers
- `renderHook` for hooks
- `debug` for troubleshooting
- Accessibility-first queries

### RTL Philosophy
RTL encourages testing components **the way users interact with them**: query by accessible names, roles, and text - not implementation details. Test behaviour, not implementation. Avoid testing internal state. Focus on user interactions.

### Query Families

| Query | Not found | Found | Async |
|-------|-----------|-------|-------|
| `getBy*` | Throws | Returns | ❌ |
| `queryBy*` | Returns null | Returns | ❌ |
| `findBy*` | Rejects | Resolves | ✅ |

**Rule:** Use `getBy` for present elements; `queryBy` for absent elements (`.not.toBeInTheDocument()`); `findBy` for async elements.

### Query Priority
```
1. getByRole("button", { name: /submit/i })     ← Best
2. getByLabelText("Email")                       ← Form fields
3. getByPlaceholderText("Enter email")           ← Fallback
4. getByText("Welcome back")                     ← Non-interactive
5. getByDisplayValue("current value")            ← Form inputs with value
6. getByAltText("User avatar")                   ← Images
7. getByTitle("Close")                           ← Rare
8. getByTestId("submit-btn")                     ← Last resort
```
Use queries in this order of preference.

### `within` for Scoped Queries
```tsx
const dialog = screen.getByRole('dialog');
within(dialog).getByRole('button', { name: /confirm/i });
```

### Custom Render with Providers
```tsx
// test/render.tsx
function renderWithProviders(ui: React.ReactElement, options = {}) {
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });

  return render(
    <QueryClientProvider client={queryClient}>
      <ThemeProvider theme="light">
        {ui}
      </ThemeProvider>
    </QueryClientProvider>,
    options
  );
}
```

---

### Deeper Explanation: Render, Query, Interact, Assert â€” In The User's Model

RTL's value is a *constraint*, not a convenience: it deliberately does not hand you the component instance, so you cannot assert on props, state, or private methods. What remains is the user's view â€” what is on screen, what a control is called, and what happens after an interaction.

The moving parts:

- **`render`** mounts into a real (jsdom) document and returns queries scoped to that container; `screen` exposes the same queries against `document.body`, which reads better in tests.
- **Queries** are the accessibility tree. `findBy*` is `getBy*` plus retry, `queryBy*` returns `null` instead of throwing â€” that trio is the whole async vocabulary.
- **`userEvent`** simulates a realistic device: clicks come with pointer and mouse event sequences, typing triggers focus, keydown, input, keyup, and selection.
- **`act`** is the boundary that flushes React updates; RTL wraps your interactions in it, which is why *un-awaited* user events produce `act` warnings rather than silent passes.
- **Providers** belong in one shared `renderWithProviders` helper, not copy-pasted per test file.

### Extended Example: Custom Render Plus An Accessible Error Assertion

```tsx
// tests/render.tsx
import { useState } from 'react';
import { render as rtlRender } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

function Providers({ children }: { children: React.ReactNode }) {
  const [client] = useState(
    () => new QueryClient({ defaultOptions: { queries: { retry: false } } }),
  );
  return <QueryClientProvider client={client}>{children}</QueryClientProvider>;
}

export function render(ui: React.ReactElement) {
  return { user: userEvent.setup(), ...rtlRender(ui, { wrapper: Providers }) };
}
```

```tsx
it('announces a validation error and keeps focus on the field', async () => {
  const { user } = render(<SignupForm />);

  await user.click(screen.getByRole('button', { name: /create account/i }));

  const email = screen.getByRole('textbox', { name: /email/i });
  expect(email).toHaveAttribute('aria-invalid', 'true');
  expect(screen.getByRole('alert')).toHaveTextContent(/email is required/i);
  expect(email).toHaveFocus(); // focus management is part of the contract
});
```

### Additional Pitfalls
- **`container.querySelector('.field')`.** The moment you reach for the DOM you lose the refactor guarantee; if no query fits, the markup probably needs a role or a label.
- **Silencing `act()` warnings with a console spy.** The warning says a state update happened outside React's knowledge â€” await the interaction instead.
- **`render` in `beforeEach` but `screen` in the test body.** With several renders per file, use the returned bound queries so you cannot assert against a stale tree.
- **Asserting how many times a `useEffect` ran.** Assert the user-visible effect (toast, disabled button, URL), not the internal run count.
- **`jest-dom` matchers without the setup import.** `toBeInTheDocument is not a function`; register the matchers in the global setup file.

### Real-World Deal-Breakers
- **`getByTestId` as primary query** → doesn't verify accessibility; breaks on test ID rename.
- **`fireEvent` instead of `userEvent`** → misses focus, keyboard, pointer behavior.
- **`waitFor` + `getBy` instead of `findBy`** → verbose, slower.
- **No `await` on `userEvent`** → interactions aren't fully processed.
- **Testing internal state** → `expect(component.state.count)` breaks on refactor.
- **`screen.debug()` left in** → console noise; remove before commit.
- **Not using `within`** → queries match elements outside the intended scope.
