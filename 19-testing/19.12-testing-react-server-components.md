## 19.11 Testing React Server Components

### Subtopic Tree
- RSC testing is fundamentally different
- Server Components can't run in jsdom
- Three-tier strategy: unit + integration + E2E
- Mocking server boundaries
- Vitest for async RSC
- E2E for hydration behavior

### The Three-Tier RSC Strategy
This tutorial builds a testing strategy on three tiers: **unit tests for extracted business logic, integration tests for Server Components with mocked boundaries, and E2E tests reserved for hydration and browser-dependent behavior**.

| Tier | What | Tool |
|------|------|------|
| **Unit** | Extracted pure logic | Vitest |
| **Integration** | Server Components with mocked boundaries | Vitest + MSW |
| **E2E** | Hydration, browser behavior | Playwright |

### Testing an Async Server Component
```tsx
// UserProfile.tsx (Server Component)
async function UserProfile({ id }: { id: string }) {
  const user = await getUser(id);
  return <h1>{user.name}</h1>;
}
```

```tsx
// UserProfile.test.tsx
import { render, screen } from '@testing-library/react';
import { UserProfile } from './UserProfile';
import { getUser } from '@/lib/users';

vi.mock('@/lib/users');

it('renders user name', async () => {
  vi.mocked(getUser).mockResolvedValue({ id: '1', name: 'Alice' });
  const Component = await UserProfile({ id: '1' });
  render(Component);
  expect(screen.getByText('Alice')).toBeInTheDocument();
});
```

---

### Deeper Explanation: Two Runtimes, Two Test Strategies

A React Server Component is an `async` function that never ships to the browser and never hydrates. That breaks the default test setup in three ways:

- **It cannot render in jsdom as a live component** â€” there is no client runtime to mount it into.
- **`await`ing it is part of the test.** The correct call is `render(await Page({ params }))`, because you are testing a resolved tree, not a stateful component.
- **Framework imports are server-only.** `next/headers`, `next/navigation`, `cookies()`, and the `server-only` marker throw outside a request scope, so they must be mocked or injected.

The practical split for an App Router codebase:

| What you are testing | How |
|---|---|
| Server Component output | Vitest, node environment, `render(await Comp(props))` |
| Server data access | Unit test the query function with MSW |
| Client islands | RTL in jsdom, normal component rules |
| Streaming, Suspense, real navigation | Playwright against a running server |
| Server Actions | Call the action directly in node env, assert revalidation effects |

### Extended Example: Awaiting A Server Component And Faking Request APIs

```tsx
// app/dashboard/page.tsx
import { cookies } from 'next/headers';

export default async function Dashboard() {
  const token = (await cookies()).get('session')?.value;
  if (!token) return <p>Please sign in</p>;
  const user = await getUser(token);
  return <h1>Welcome {user.name}</h1>;
}
```

```typescript
// app/dashboard/page.test.tsx â€” vitest project: name 'server', environment 'node'
import { vi, expect, it } from 'vitest';
import { render, screen } from '@testing-library/react';
import Dashboard from './page';

vi.mock('next/headers', () => ({
  cookies: async () => ({
    get: (k: string) => (k === 'session' ? { value: 'test-token' } : undefined),
  }),
}));
vi.mock('@/lib/user', () => ({ getUser: vi.fn(async () => ({ name: 'Ada' })) }));

it('greets the signed-in user', async () => {
  render(await Dashboard());
  expect(screen.getByRole('heading', { name: /welcome ada/i })).toBeInTheDocument();
});

it('renders the signed-out state', async () => {
  const { cookies } = await import('next/headers');
  vi.mocked(cookies).mockResolvedValueOnce({ get: () => undefined } as never);
  render(await Dashboard());
  expect(screen.getByText(/please sign in/i)).toBeInTheDocument();
});
```

### Additional Pitfalls
- **`render(<Dashboard />)` on an async component.** The unresolved promise renders an empty tree and the test passes vacuously. Always await the component first.
- **Asserting `useState`/`useEffect` inside a Server Component.** Neither exists there; if the test needs them, the component is a client island and belongs in the jsdom project.
- **Letting `server-only` leak into a client test.** The import throws at module load with a misleading message; keep server and client specs in separate Vitest projects.
- **Mocking the framework instead of testing the branch.** Mock `cookies()` to control *your* decision, then assert the rendered outcome, not that the function was called.
- **No Suspense or streaming test.** A regression where the whole page blocks on one slow query is invisible to unit tests; assert the shell renders before the data in Playwright.

### Real-World Deal-Breakers
- **Trying to `render(<ServerComponent />)` directly** → Server Components are async; you must await them.
- **No mock for server boundary** → Server Component tries to hit a real database or API.
- **Testing Client Components with RSC patterns** → Client Components still use standard RTL patterns.
- **No E2E for hydration** → hydration mismatches are invisible to unit tests.
