### Core API
```typescript
describe('UserService', () => {
  let service: UserService;
  let mockRepo: jest.Mocked<UserRepository>;

  beforeEach(() => {
    mockRepo = {
      findById: jest.fn(),
      save: jest.fn(),
    };
    service = new UserService(mockRepo);
  });

  it('returns user when found', async () => {
    mockRepo.findById.mockResolvedValue({ id: 1, name: 'Alice' });
    const user = await service.getUser(1);
    expect(user.name).toBe('Alice');
  });

  it('throws when not found', async () => {
    mockRepo.findById.mockResolvedValue(null);
    await expect(service.getUser(1)).rejects.toThrow('User not found');
  });
});
```

### Mocking Strategies
```typescript
// Mock a function
const mockFn = jest.fn();
mockFn.mockReturnValue(42);
mockFn.mockResolvedValue({ data: 'ok' });
mockFn.mockImplementation((x) => x * 2);

// Mock a module
jest.mock('./api', () => ({
  fetchUser: jest.fn().mockResolvedValue({ id: 1, name: 'Alice' }),
}));

// Spy on an object method
const spy = jest.spyOn(console, 'error').mockImplementation(() => {});
```

### Fake Timers
```typescript
jest.useFakeTimers();

it('debounces search', () => {
  const search = jest.fn();
  debounceSearch(search, 300);
  jest.advanceTimersByTime(300);
  expect(search).toHaveBeenCalled();
});

afterEach(() => jest.useRealTimers());
```

### Deeper Explanation: Jest Is A Module Registry Per File

Jest runs every test *file* in its own sandbox with its own module registry, `globalThis`, and mock state. Inside a file everything is shared unless you reset it, which produces the two classic Jest failure modes: **mock leakage** (a `mockReturnValue` from test three changes test four) and **module state leakage** (a singleton caches data across tests in the same file).

The mental model to hold:

| Question | Jest answer |
|---|---|
| Where does `describe` come from? | Injected globals â€” the runtime provides them per file |
| Why did my import return a mock? | `jest.mock` is hoisted above the imports by the transform |
| Why is `Date` frozen in one test but not the next? | Fake timers are per-file state, real timers must be restored |
| Why does a singleton hold data from a previous test? | `jest.resetModules()` was never called, or the module was imported once |

Modern greenfield projects often pick Vitest for speed and native ESM, but Jest remains widespread in enterprise repos and is still the default in many React Native setups. Know both.

### Extended Example: Typed Manual Mock And Deterministic Time

```typescript
// src/lib/analytics.ts
export const track = (event: string, props?: Record<string, unknown>) => {
  void navigator.sendBeacon('/collect', JSON.stringify({ event, props }));
};

// src/lib/__mocks__/analytics.ts
export const track = jest.fn();

// src/lib/pricing.test.ts
jest.mock('./analytics'); // picks up the manual mock beside the module
import { track } from './analytics';
import { priceOrder } from './pricing';

const mockedTrack = jest.mocked(track);

beforeEach(() => {
  jest.useFakeTimers({ now: new Date('2026-01-01T00:00:00Z') });
  jest.clearAllMocks();
});
afterEach(() => jest.useRealTimers());

it('emits one conversion event per order', () => {
  priceOrder([{ sku: 'a', qty: 2 }], { userId: 'u1' });
  expect(mockedTrack).toHaveBeenCalledTimes(1);
  expect(mockedTrack).toHaveBeenCalledWith('order_priced', {
    userId: 'u1',
    total: expect.any(Number),
  });
});
```

### Additional Pitfalls
- **No `clearMocks` in config.** Implementations and call history persist inside a file; set it once in config instead of remembering per test.
- **A mock factory that omits exports.** `jest.mock('./x', () => ({ a: jest.fn() }))` breaks every other named import; spread `jest.requireActual('./x')`.
- **Fake timers with un-awaited promises.** Flush with `await jest.advanceTimersByTimeAsync(ms)` or the scheduling your library relies on never runs.
- **Believing jsdom is a browser.** No layout, no real `IntersectionObserver`, no media queries; polyfill or mock those APIs deliberately.
- **Snapshot files committed without review.** `--ci` plus a review rule beats "update snapshots" muscle memory.

### Real-World Deal-Breakers
- **Snapshot tests for everything** → snapshots grow huge; no one reviews them. Use for small, stable outputs.
- **No `afterEach(() => jest.clearAllMocks())`** → mock state leaks between tests.
- **Mocking too deeply** → mocking a module that imports another module that imports another... brittle.
- **`jest.mock` hoisting** → `jest.mock` calls are hoisted to the top; variables referenced must be prefixed with `mock`.
- **Jest + ESM pain** → Jest's ESM support is still experimental with frequent edge cases. Use Vitest for ESM-first projects.
