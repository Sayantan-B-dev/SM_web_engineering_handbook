### Pure Function Tests
```typescript
// utils/formatCurrency.ts
export function formatCurrency(amount: number, currency = 'USD'): string {
  return new Intl.NumberFormat('en-US', { style: 'currency', currency }).format(amount);
}

// utils/formatCurrency.test.ts
import { describe, it, expect } from 'vitest';
import { formatCurrency } from './formatCurrency';

describe('formatCurrency', () => {
  it('formats USD correctly', () => {
    expect(formatCurrency(1234.56)).toBe('$1,234.56');
  });

  it('formats EUR correctly', () => {
    expect(formatCurrency(1000, 'EUR')).toBe('€1,000.00');
  });

  it('handles zero', () => {
    expect(formatCurrency(0)).toBe('$0.00');
  });

  it('handles negative amounts', () => {
    expect(formatCurrency(-500)).toBe('-$500.00');
  });
});
```

### Custom Hook Tests
```typescript
import { renderHook, act } from '@testing-library/react';
import { useCounter } from './useCounter';

describe('useCounter', () => {
  it('initializes with default value', () => {
    const { result } = renderHook(() => useCounter());
    expect(result.current.count).toBe(0);
  });

  it('increments', () => {
    const { result } = renderHook(() => useCounter());
    act(() => result.current.increment());
    expect(result.current.count).toBe(1);
  });

  it('respects initial value', () => {
    const { result } = renderHook(() => useCounter(10));
    expect(result.current.count).toBe(10);
  });
});
```

### Arrange-Act-Assert
```typescript
it('applies discount when total exceeds threshold', () => {
  // Arrange
  const cart = new ShoppingCart();
  cart.addItem({ price: 150, quantity: 1 });

  // Act
  const total = cart.calculateTotal();

  // Assert
  expect(total).toBe(135); // 10% discount applied
});
```

### Deeper Explanation: What A "Unit" Really Is

A unit is not "a function" â€” it is **the smallest thing whose behaviour you want to guarantee independently of its collaborators**. In React apps that means a pure function, a reducer, a schema, a state machine, or a custom hook whose data source is injected. The practical test of unit-worthiness: *can I describe the failure without mentioning the UI, the network, or the clock?*

Three patterns make code unit-testable, and all three are architectural decisions:

- **Pure core / impure shell** â€” keep logic in a pure function and let the component adapt inputs to it, e.g. `calculateCart(items, { taxRate, now })`.
- **Dependency injection over module mocking** â€” pass `now`, `random`, or `fetchImpl` as arguments instead of reaching for `vi.mock`.
- **Total functions over exceptions** â€” return discriminated results (`{ ok: true, value } | { ok: false, error }`) so error paths become ordinary assertions rather than `expect(...).toThrow()` gymnastics.

### Extended Example: Determinism Plus Property Testing

```typescript
import { describe, it, expect } from 'vitest';
import fc from 'fast-check';

export type PriceInput = { net: number; rate: number };

export function gross({ net, rate }: PriceInput, round = Math.round): number {
  if (net < 0) throw new RangeError('net must be >= 0');
  if (rate < 0 || rate > 1) throw new RangeError('rate must be within 0..1');
  return round(net * (1 + rate));
}

describe('gross', () => {
  it('respects injected rounding', () => {
    expect(gross({ net: 10, rate: 0.2 }, (n) => Math.floor(n))).toBe(12);
  });

  it('never returns less than the net amount', () => {
    fc.assert(
      fc.property(
        fc.integer({ min: 0, max: 10_000 }),
        fc.float({ min: 0, max: 1, noNaN: true }),
        (net, rate) => gross({ net, rate }) >= net,
      ),
    );
  });

  it('rejects out-of-range input instead of producing NaN', () => {
    expect(() => gross({ net: -1, rate: 0.1 })).toThrow(RangeError);
    expect(() => gross({ net: 1, rate: 2 })).toThrow(RangeError);
  });
});
```

### Additional Pitfalls
- **Asserting on formatted strings when you meant to assert on values.** `Intl` output varies by ICU version; pin the locale (`'en-US'`) or assert on the number.
- **Snapshotting a data structure you still control.** Snapshots on pure data hide the diff you wanted to review â€” use `toEqual` with an explicit object.
- **Floating-point equality.** `0.1 + 0.2` will bite; assert with `toBeCloseTo` or work in integer minor units (cents).
- **Testing private helpers only through the public API and calling it coverage.** Export the pure core and test it directly; keep the rest genuinely private.

### Real-World Deal-Breakers
- **Testing implementation, not behavior** → test `result.current.count`, not internal state variables.
- **No edge cases** → test zero, negative, empty string, null, undefined, very large numbers.
- **Over-mocking** → if you're mocking 10 things to test one function, the function is too coupled.
- **Tests without assertions** → `it('renders', () => { render(<Button />) })` - what did you assert?
- **Shared mutable state between tests** → tests pass in isolation but fail when run together.
