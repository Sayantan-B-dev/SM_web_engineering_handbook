### Deeper Explanation: Deployment Topology Versus Team Topology

The real choice is between "one deployable unit" and "many independently deployable units", and the deciding input is organisational: how many teams need to release independently, and how different are their scaling and compliance needs?

| Signal | Monolith (modular) | Microservices |
|---|---|---|
| Teams | 1-3 | Many, independent release cadences |
| Scaling profile | Uniform | One component dominates |
| Consistency | Strong transactions | Sagas, eventuality |
| Ops maturity | Basic | Strong tracing, SLOs, on-call |
| Time to first feature | Fast | Slow (infrastructure first) |

The pragmatic path: modular monolith, extract the one component with a genuinely different profile (high compute, different scaling, stricter isolation), and repeat only when the pressure reappears.

### Real-World Deal-Breakers
- **Microservices for a small team.** Coordination overhead exceeds the benefit; velocity drops.
- **A shared database across services.** It re-couples deployments and negates the main advantage.
- **Extraction without observability.** Distributed debugging without tracing is guesswork.
- **Distributed transactions attempted directly.** Use sagas and idempotency instead.
- **Extracting the easiest module.** Extract the one with the different constraint, not the smallest.
