### The Seven Evaluation Constructs
The Di-Select framework synthesizes seven high-order evaluation constructs for technology selection:

| Construct | What it evaluates |
|-----------|------------------|
| **Performance** | Latency, throughput, scalability |
| **Security** | Default hardening, attack surface |
| **Connectivity** | Integration capability, protocol support |
| **Reliability** | Fault tolerance, recovery time |
| **Ecosystem** | Community, tooling, integrations |
| **Maintainability** | Code complexity, upgrade path |
| **Resource & Cost** | CPU, memory, licensing, operational cost |

### Fifteen Causal Propositions
These constructs formalize the trade-offs between criteria - for example, the **inverse relationship between default security hardening and resource consumption**, or between recovery time and resource requirements.

### The Four-Phase Selection Framework
A structured decision framework prevents analysis paralysis while ensuring rigorous evaluation:

**Phase 1 - Decision Framing**: Define the decision, criteria, weights, and constraints.
**Phase 2 - Evaluation Matrix**: Score each option 1-5 on weighted criteria. Options within 10% of each other → choose what team knows best.
**Phase 3 - Decision Trees**: Model the downstream implications of each choice.
**Phase 4 - Decision Documentation**: Produce an ADR capturing context, decision, alternatives, and consequences.

### Deeper Explanation: Choose For The Team You Have

Technology selection is usually a people decision: what can this team learn, operate, and hire for in the next two years? Performance benchmarks, community size, and GitHub stars matter less than the operational and cognitive load.

A workable evaluation: (1) does it solve a real constraint (not a hypothetical)? (2) can two engineers become productive in a week? (3) who operates it, and what breaks at 3am? (4) what is the exit cost if it fails? (5) does it fit existing conventions â€” or does it introduce a second way of doing everything? A time-boxed spike with a written recommendation beats a benchmark spreadsheet.

### Additional Pitfalls
- **Choosing by benchmark or popularity.** Adoption does not translate into fit.
- **Introducing a second tool for the same job.** Two state managers means permanent confusion.
- **Ignoring exit costs.** Encapsulate the choice behind an interface where possible.
- **No spike.** A week of real use reveals more than a month of reading.
- **Upgrading everything at once.** Unrelated migrations hide the source of regressions.

### Real-World Deal-Breakers
- **Comparing 10+ options without constraint filtering** → analysis paralysis.
- **Scoring all criteria equally** → ignores stakeholder priorities.
- **No decision trees** → you don't understand downstream implications.
- **No documentation** → the decision is forgotten.
