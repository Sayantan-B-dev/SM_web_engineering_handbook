### Deeper Explanation: Where The Source Of Truth Lives

Server-first: the server holds state, the client is a view; simplicity, strong consistency, and easy authorisation, but latency and offline failure. Local-first: the device holds a replica (often a CRDT), sync happens in the background; instant interaction, offline capability, and durability, but merge complexity, larger clients, and harder authorisation.

| Property | Server-first | Local-first |
|---|---|---|
| Latency | Network-bound | Instant (local reads/writes) |
| Offline | Broken or read-only | Fully functional |
| Conflict handling | Server decides | Merge rules in the data model |
| Authorisation | Simple and centralised | Harder; needs signed operations |
| Storage/complexity | Low | Higher (replica, sync, GC) |

Decision guide: choose local-first when offline editing, latency, or data ownership is core to the product (notes, docs, field work, creative tools). Choose server-first for anything money, permissions, or inventory-critical where a single authority is the point.

### Additional Deal-Breakers
- **Local-first for permission-critical data.** Eventual consistency and authorisation do not mix well.
- **Server-first with an offline promise.** Requests fail and users lose work.
- **No conflict strategy.** Concurrent edits silently overwrite.
- **Ignoring storage growth.** Update logs and tombstones need compaction.
- **No export path.** If the device holds the truth, users must be able to get it out.
