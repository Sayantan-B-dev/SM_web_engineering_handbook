### Deeper Explanation: Decide By Trust And Latency

The question is not "can the client do it" but "should the client be trusted with it, and does the latency budget matter".

| Work | Client | Server | Rule |
|---|---|---|---|
| Input validation/formatting | Yes (UX) | Always (security) | Server is authoritative |
| Authorisation decisions | Never | Always | Client checks are UX only |
| Computation over local data | Yes | â€” | Privacy and latency favour client |
| Secrets, payments, privileged writes | Never | Always | Keys never reach the browser |
| Heavy compute (search, ML) | If model fits | If it does not | Measure size, memory, and cost |
| Personalisation and rendering | Yes | Yes | Server renders for first paint, client for interaction |

The pattern that resolves most cases: **authoritative server, optimistic client**. The server owns truth and permissions; the client owns responsiveness.

### Real-World Deal-Breakers
- **Authorisation logic in the client.** Trivially bypassed; the API must enforce it.
- **Secrets or admin keys in the bundle.** Anything shipped is public.
- **Moving work to the client "to save server cost" without measuring device cost.** Users pay in battery and jank.
- **Duplicating business rules in both places.** They drift; share the schema or keep one authority.
- **Client-side-only validation.** Malformed data reaches the database.
