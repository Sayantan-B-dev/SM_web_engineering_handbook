### Deeper Explanation: Who Owns The Query Shape

REST: the server defines resources and endpoints; the client composes them. GraphQL: the client defines the query shape; the server resolves it. That single difference determines the cost profile: REST is cacheable, simple, and predictable; GraphQL solves over-fetching and client diversity at the price of server complexity (depth limits, N+1, authorisation per field, caching).

Decision guide: one first-party client using a typed API â†’ REST/JSON (or RPC); many heterogeneous clients with varied data needs â†’ GraphQL; a public API with third parties â†’ REST + OpenAPI for cacheability and familiarity.

### Real-World Deal-Breakers
- **GraphQL without cost controls.** One nested query can exhaust the database.
- **GraphQL to avoid designing endpoints.** You still need a data model and authorisation.
- **REST with chatty endpoints for a deeply nested view.** The client makes ten calls; aggregate server-side.
- **Caching assumptions.** HTTP caching largely does not apply to POST-based GraphQL; plan response caching.
- **Versioning neglect in REST.** Breaking changes need deprecation windows and versioned endpoints.
