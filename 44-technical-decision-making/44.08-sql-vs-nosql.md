### Deeper Explanation: Query Patterns Choose The Store

SQL (relational) gives you schema enforcement, joins, transactions, and ad-hoc querying; NoSQL gives you flexible shapes, horizontal scale, and store-specific access patterns at the cost of joins and multi-document transactions. The honest framing: **most products should start with Postgres** and move a specific workload to a specialised store when a real constraint appears (write throughput, full-text relevance, graph traversal, geo-distribution).

| Need | Choice |
|---|---|
| Transactions, constraints, reporting | Relational (Postgres/MySQL) |
| Document-shaped reads at scale | Document store |
| Massive write throughput, key access | Wide-column or KV |
| Search relevance and aggregation | Search engine (with a source of truth elsewhere) |
| Relationship traversal | Graph |

### Real-World Deal-Breakers
- **NoSQL chosen to "avoid migrations".** Schemas still exist; they moved into application code without enforcement.
- **Two stores with dual writes.** They drift; use outbox/CDC.
- **Relational schema for a document-shaped workload (or the reverse).** Either way you fight the tool.
- **Ignoring consistency in the second store.** The index lags the truth; the UI must tolerate it.
- **No owner for the second system.** Every additional datastore adds operational cost.
