### Deeper Explanation: Performance Is A Budget, Not A Goal

Performance work is an exchange: you buy milliseconds with complexity, memory, cache staleness, cost, or delivery risk. The discipline is to define the budget first (LCP p75, INP p75, bundle size, time-to-interactive on a mid-tier device), then decide what you are willing to pay to hit it.

| Technique | Buys | Costs |
|---|---|---|
| Code splitting | Faster first load | More requests, loading states |
| Caching (client/CDN) | Speed and cost savings | Staleness, invalidation bugs |
| Virtualisation | Rendering speed at scale | Complexity, measurement work |
| Optimistic UI | Perceived latency | Rollback logic, conflict handling |
| SSR/streaming | Faster first paint | Server cost and complexity |
| Worker/WASM offload | Main-thread freedom | Boundary cost, memory |
| Aggressive prefetch | Faster navigation | Wasted bandwidth, battery |

### Real-World Deal-Breakers
- **Optimising without a budget.** Effort goes wherever the last complaint came from.
- **Caching without invalidation design.** Stale data and "hard-refresh fixes it" support tickets.
- **Optimising a path nobody uses.** Measure usage before performance.
- **Paying with complexity where a server change would do.** Client workarounds are expensive to maintain.
- **No regression guard.** Without CI budgets, performance decays quietly.
