## 44.14 Decision Documentation

### Subtopic Tree
- ADR as the canonical documentation format
- RFC for proposals (longer than ADR)
- Design docs
- Decision log
- Dependencies and cross-references
- Annual review

### The Documentation Stack

| Format | Purpose | Length | Audience |
|--------|---------|--------|----------|
| **ADR** | Record a decision | 1 page | Future maintainers |
| **RFC** | Propose a change | 2-5 pages | Team + stakeholders |
| **Design Doc** | Detail the implementation | Variable | Engineers |
| **Decision Log** | Chronological index of decisions | 1 line each | Everyone |

### What to Document
Every decision document should capture:
- **Context**: the problem or opportunity.
- **At least 2 options considered**: alternatives evaluated.
- **Decision drivers**: explicitly listed.
- **Consequences**: both positive and negative outcomes.
- **Reversibility**: how easy it is to change later.
- **Dependencies**: upstream ADRs this relies on.

### Real-World Deal-Breakers
- **No documentation** → decisions are forgotten. The same debate happens every 6 months.
- **Documenting only the decision, not the alternatives** → future teams re-propose rejected options.
- **Documenting only the upside** → the team doesn't know what they're giving up.
- **No annual review** → decisions outlive their context.
