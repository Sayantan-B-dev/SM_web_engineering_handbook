### Deeper Explanation: Rendering Topology Determines Cost And Caching

CSR renders in the browser (simple hosting, but slower first paint and worse SEO); SSR renders on the server per request (faster first paint, better SEO, but a runtime and caching problem); static/ISR renders ahead of time (fastest and cheapest, but staleness). Modern frameworks blur the line with streaming and per-component choices, so this is now a *per-route* decision rather than a per-app one.

| Model | TTFB | First paint | Cost/request | Data freshness |
|---|---|---|---|---|
| CSR | Fast | Slow | ~zero | Client-controlled |
| SSR | Server-bound | Fast | Per request | Always fresh |
| Static/ISR | Fastest | Fastest | Near zero | Stale until revalidate |
| Streaming SSR + islands | Fast shell | Progressive | Per request | Fresh where needed |

Decision guide: content that is the same for everyone and changes slowly â†’ static/ISR; personalised first paint or SEO-critical pages â†’ SSR/streaming; authenticated app dashboards where first paint speed is not critical â†’ CSR with a well-optimised shell.

### Real-World Deal-Breakers
- **Global SSR because "it is faster".** Per-request cost and cache complexity for routes that never needed it.
- **CSR for SEO-critical marketing pages.** Crawlers may index an empty shell.
- **SSR with a slow data dependency.** You moved latency from the client to the server; the user still waits.
- **Static pages with no revalidation.** Content goes stale without an invalidation path.
- **Hydration mismatches.** Server and client rendering differently is the most common SSR bug.
