## 22.6 Storage APIs

### Subtopic Tree
- `localStorage` / `sessionStorage` (synchronous, strings only, 5MB)
- IndexedDB (asynchronous, structured data, large)
- Cache Storage API (HTTP request/response pairs)
- Origin Private File System (OPFS)
- Cookies (sent with every request)
- Storage quota and eviction
- `navigator.storage.estimate()`
- `navigator.storage.persist()`
- Cross-tab communication (`BroadcastChannel`)

### Which Storage to Use

| Use case | API | Why |
|----------|-----|-----|
| Network resources (HTML, JS, CSS, images) | **Cache Storage API** | Designed for HTTP request/response pairs |
| File-based content | **OPFS** | High-performance file system |
| Other structured data | **IndexedDB** | Large, indexed, asynchronous |
| Small session-specific data | `sessionStorage` | Tab-scoped, but synchronous |
| Authentication tokens | **Cookies** (`HttpOnly`, `Secure`) | Sent automatically, protected from JS |
| **Avoid** | `localStorage` | Synchronous, blocks main thread, strings only |

For network resources needed to load your app, use the **Cache Storage API** (part of Service Worker). For file-based content, use **OPFS**. For other data, use **IndexedDB** with a Promise wrapper. All modern browsers support IndexedDB, OPFS, and Cache Storage API. They are asynchronous and don't block the main thread.

### Avoid `localStorage`
Avoid `localStorage` because it is synchronous and blocks the main thread. Size limit is about 5 MB, and it can only contain strings. Web Workers and Service Workers cannot access `localStorage`.

---

### Deeper Explanation: Give Every Piece Of Data The Right Home

Storage choice is a four-question decision: how much data, how structured, does it need transactions, and does it need to be readable synchronously by the render path? The answer picks the API:

| Need | Use | Notes |
|---|---|---|
| Small flags, theme, token hints | `localStorage` | Synchronous, blocking, 5-10 MB, per origin |
| Session-scoped, tab-scoped | `sessionStorage` | Survives reload, dies with tab |
| Structured data, indexes, large volume | **IndexedDB** | Async, transactional, hundreds of MB |
| HTTP responses / offline shell | **Cache Storage** | Request/response only, service worker |
| Key-value with async and more capacity | **Origin Private File System** | File-based, fast random access |
| Server-known warm cookie | Cookie | Sent on every request; keep it tiny |

Two regulatory realities: storage keys and quotas are **per origin**, and eviction is at the browser's discretion unless you call `navigator.storage.persist()`. ### Additional Pitfalls
- **`localStorage` for anything sizable or hot.** It blocks the main thread; JSON-parsing a 2 MB blob on every navigation is a real cost.
- **Assuming persistence.** Private mode, quota pressure, and "clear site data" all delete it; always have a rebuild path.
- **Storing tokens in `localStorage`.** Any XSS becomes a full account takeover; prefer httpOnly cookies.
- **No versioning of persisted shapes.** Users with a two-month-old build break on the new schema.
- **Ignoring `storage.estimate()`.** You discover the quota by throwing during a save.

### Real-World Deal-Breakers
- **`localStorage` for large data** → blocks the main thread, 5MB limit.
- **No `navigator.storage.persist()`** → storage can be evicted under pressure. Request persistence for critical data.
- **Storing auth tokens in `localStorage`** → XSS can read them. Use `HttpOnly` cookies.
- **No quota monitoring** → storage quota errors crash the app. Use `navigator.storage.estimate()`.
- **IndexedDB without a Promise wrapper** → callback hell. Use `idb` or `Dexie`.
