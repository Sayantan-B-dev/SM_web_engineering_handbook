### Web Workers vs Service Workers

| | Web Worker | Service Worker |
|--|-----------|---------------|
| **Purpose** | Offload CPU work | Network proxy, offline, push |
| **Lifespan** | Tied to the page | Independent of tabs |
| **Scope** | One page spawns many | One SW controls all tabs under its scope |
| **DOM access** | No | No |
| **Network interception** | No | Yes (`fetch` event) |
| **Push notifications** | No | Yes (`push` event) |
| **Storage access** | IndexedDB, Cache API | IndexedDB, Cache API |

Both run in a secondary thread, allowing JavaScript code to execute without blocking the main thread and the user interface. They don't have access to the `Window` and `Document` objects, so they can't interact with the DOM directly, and they have limited access to browser APIs. Unlike web workers, service workers allow you to intercept network requests (via the `fetch` event) and to listen for Push API events in the background (via the `push` event). A page can spawn multiple web workers, but a single service worker controls all the active tabs under the scope it was registered with. The lifespan of a web worker is tightly coupled to the tab it belongs to, while the service worker's lifecycle is independent.

### Deeper Explanation: Choose The Worker Type By Ownership Model

There are four worker types and the choice is not about performance â€” it is about **who owns the instance and what the worker is allowed to touch**:

| Type | Instance owner | Can access | Use for |
|---|---|---|---|
| Dedicated | One document | Post-message only | Heavy computation for one tab |
| Shared | Origin (all tabs) | Post-message via ports | Shared connection/state across tabs |
| Service | Origin, acts as proxy | Cache, fetch, push, sync | Offline, push, background work |
| Worklet | Rendering/audio pipeline | Minimal (no DOM, no timers) | Audio/localised paint work |

The critical constraint is that **workers never touch the DOM**, and going to a worker costs a serialisation boundary. So the winning pattern is coarse-grained: send data in, get data out, keep messages few and large rather than many and small.

### Additional Pitfalls
- **One worker per small task.** Startup cost (tens of ms) plus module parsing makes trivial tasks slower off-thread.
- **Chatty protocols.** Thousands of messages per second with structured clone will saturate the main thread worse than the work would have.
- **Sharing a worker across unrelated features.** One slow job blocks all the others; pool or shard by concern.
- **Assuming workers can be imported synchronously.** Module workers load asynchronously, and worker scripts are separate bundles to build.
- **Ignoring error handling.** An uncaught worker error dies silently unless an `onerror`/`onmessageerror` handler reports it.

### Real-World Deal-Breakers
- **CPU-heavy work on the main thread** → blocks rendering, input, and GC. Move to a Web Worker.
- **Web Worker with DOM access** → impossible. Workers have no `window` or `document`.
- **Service Worker caching everything** → storage bloat, stale content. Cache selectively with versioned caches.
- **`SharedArrayBuffer` without COOP/COEP** → throws. Requires cross-origin isolation.
- **No worker termination** → leaked workers consume CPU. Call `worker.terminate()`.
