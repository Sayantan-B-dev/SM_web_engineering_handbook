## 22.1 Multi-Process Architecture

### Subtopic Tree
- Browser process (UI, network, storage, IPC)
- Renderer processes (one per site / tab)
- GPU process (Viz) - compositing, rasterization, draw
- Network service process
- Utility processes (audio, video, PDF)
- Site isolation (one site per renderer)
- Sandboxing (renderer has no file system, network, or GPU access)
- Process-per-tab vs process-per-site
- Memory overhead and process reuse

### Process Responsibilities

| Process | Responsibility | Sandboxed? |
|---------|---------------|-----------|
| **Browser** | UI, tabs, omnibar, IPC coordination | No |
| **Renderer** | JS, DOM, CSS, layout, paint, workers | Yes (highly) |
| **GPU (Viz)** | Compositing, rasterization, GPU commands | Yes (modified sandbox) |
| **Network** | Sockets, DNS, HTTP cache, cookies | Yes |
| **Utility** | Audio, video decode, PDF, data decoding | Yes |

The browser process starts first and hosts the Chrome UI. Renderer processes host untrusted code from the internet. The GPU process (Viz) isolates sensitive graphics tasks from the renderer and is highly sandboxed.

### Site Isolation
Since Chrome 67, **every site gets its own renderer process**. Different sites always end up in different render processes. Multiple tabs of the same site usually go in different render processes unless the tabs are related.

**Why it matters:** A malicious site cannot read memory from another site. Spectre-class attacks are mitigated by process boundaries.

---

### Deeper Explanation: Why Multi-Process Exists, And What It Costs You

Browsers moved to a multi-process model for three reasons: **isolation** (a crashing page takes nothing else down), **security** (each process is sandboxed, and cross-origin data lives in different processes), and **responsiveness** (the browser UI and other tabs keep running while one tab burns CPU). The cost is memory per process, plus the fact that anything needing cross-origin access must go through the browser process.

Consequences a frontend engineer actually feels:

- **`SharedArrayBuffer` and high-resolution timers require cross-origin isolation**, because they are only safe in a dedicated, isolated process.
- **Site isolation means cross-origin iframes are in different processes**, so `postMessage` between them is genuinely cross-process messaging â€” no shared objects, structured clone only.
- **A heavy tab can still starve its own process** â€” site isolation does not protect you from your own long tasks.
- **Process count is bounded**, so many tabs share processes (and therefore share fate) on low-memory devices.

### Additional Pitfalls
- **Expecting cross-origin iframes to be cheap.** They are separate processes with their own startup cost and memory.
- **Relying on high-resolution timers without cross-origin isolation.** `performance.now()` precision is intentionally coarsened to mitigate side channels.
- **Assuming a crash is contained.** It is contained across processes, but a tab can still lose unsaved state.
- **Ignoring the memory budget on mobile.** Process sharing means one memory-hungry page can evict another.

### Real-World Deal-Breakers
- **Process-per-tab memory overhead** → 50 tabs = 50 renderer processes, each with its own V8 heap. Chrome uses process reuse to mitigate this.
- **Site isolation breaks cross-site iframes** → an iframe from a different origin runs in a separate process, making synchronous access to its DOM impossible.
- **GPU process crash** → all renderers lose their compositor frames. Chrome recovers by restarting the GPU process, but the screen may flash.
