### The Mental Model
WebRTC moves bytes **directly between browsers**: it negotiates a media/data path (via signalling you implement), discovers a routable path (ICE, STUN, TURN), then encrypts it (DTLS/SRTP). The browser gives you the transport; everything about who should connect, and how they find each other, is application design.

```ts
const config: RTCConfiguration = {
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turns:turn.example.com:443', username: 'user', credential: 'pass' }, // relay fallback
  ],
};

const pc = new RTCPeerConnection(config);
const data = pc.createDataChannel('chat', { ordered: true });

data.onmessage = (e) => receive(e.data);
pc.onicecandidate = (e) => e.candidate && signal.send({ type: 'ice', candidate: e.candidate });
pc.onconnectionstatechange = () => {
  if (pc.connectionState === 'failed') pc.restartIce();   // network changed (wifi â†’ cellular)
};

// Caller
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
signal.send({ type: 'offer', sdp: pc.localDescription });

// Callee
signal.on('offer', async ({ sdp }) => {
  await pc.setRemoteDescription(sdp);
  const answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);
  signal.send({ type: 'answer', sdp: pc.localDescription });
});
```

### The Cost Reality
P2P is cheap on bandwidth and expensive on reliability. Roughly 10-20% of real-world pairs cannot connect directly and need TURN, which relays all their traffic â€” so budget for relay bandwidth and treat "direct" as an optimisation, not a guarantee.

### Real-World Deal-Breakers
- **No TURN server.** Works on your office network, fails for a meaningful slice of users on restrictive networks.
- **Ignoring `connectionstatechange`.** Devices move between networks constantly; without ICE restart the call silently dies.
- **Signalling woven into business code.** Keep it a thin, testable transport abstraction over your websocket, so the rest of the app is unaware.
- **Using media for structured data.** Data channels are the right tool for messages; media tracks are for audio/video.
- **Assuming peers persist.** Tabs close; design for a peer disappearing without a goodbye.
