### The Core Mental Model
A modern browser is not one program - it's an **operating system for the web**. It runs untrusted code from the internet inside sandboxed processes, isolates sites from each other, and coordinates rendering across multiple threads and processes to keep scrolling and animation at 60fps even when JavaScript is blocking the main thread.

```text
┌─────────────────────────────────────────────────────────────┐
│  Browser Process (one per browser)                          │
│  ├── UI (tabs, omnibar, bookmarks)                          │
│  ├── Network Service (sockets, DNS, cookies)                │
│  └── IPC coordinator                                        │
├─────────────────────────────────────────────────────────────┤
│  Renderer Process (one per site, sandboxed)                 │
│  ├── Main thread (JS, DOM, style, layout)                   │
│  ├── Compositor thread (scroll, compositor animation)       │
│  └── Worker threads (Web Workers, Service Workers)          │
├─────────────────────────────────────────────────────────────┤
│  GPU Process / Viz (one per browser)                        │
│  ├── Aggregates compositor frames from all renderers        │
│  ├── Rasterizes and draws via GPU (Skia)                    │
│  └── Issues GPU commands to the screen                      │
└─────────────────────────────────────────────────────────────┘
```

### Deeper Explanation: Know The Machine Or Pay For It Blindly

Browser engineering is the layer where "the app is slow" becomes a specific cause: which process is busy, which phase of the pipeline is expensive, which storage API the data belongs in, and which boundary a task must cross. You do not need to write a browser; you need four mental models:

1. **Processes and threads.** A tab is a process (usually), the main thread does everything the user sees, and workers are the only true escape hatch for CPU work.
2. **The rendering pipeline.** Style â†’ layout â†’ paint â†’ composite, with each phase's cost driven by what your CSS and DOM force it to do.
3. **The event loop.** Tasks, microtasks, and rendering are scheduled in a strict order; misreading it produces "why is my state not updated yet" bugs.
4. **The platform contracts.** Secure contexts, permissions, storage quotas, and the origin model decide which APIs are even available.

Everything else in this chapter is a consequence of one of these four.

### Additional Pitfalls
- **Treating the browser as a black box.** Performance work becomes guesswork; the DevTools performance panel is the ground truth.
- **Assuming one thread.** A synchronous 300 ms task freezes scrolling, input, and timers â€” everything.
- **Ignoring the origin model.** Storage, workers, and cookies are all scoped per origin; a proxy or preview subdomain changes everything.
- **Testing only on a high-end laptop.** Mid-tier Android hardware changes the decision about what must move off the main thread.

### Real-World Deal-Breakers
- **Assuming one thread** → JavaScript blocks rendering, layout, GC, and input on the main thread. Everything shares one thread.
- **Believing the browser is single-process** → Chrome, Edge, Firefox, and Safari all use multi-process architectures for security and stability.
- **Ignoring the compositor thread** → animations using `transform` and `opacity` run on the compositor thread and stay smooth even when the main thread is busy. Animating `width` or `left` does not.
