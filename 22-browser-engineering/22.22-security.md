### Same-Origin Policy (SOP)
The Same Origin Policy is a security mechanism implemented by browsers to isolate web applications of different origins from one another. It prevents one application from accessing the data of another.

### Content Security Policy (CSP)
CSP is a security mechanism for mitigating the impact of content injection attacks in general and in particular XSS. CSP is differently interpreted depending on the browser, the version of CSP it implements, and how compliant the implementation is.

### Cross-Origin Isolation (COOP + COEP)
Use COOP and COEP to set up a "cross-origin isolated" environment and enable features like `SharedArrayBuffer`, `performance.measureUserAgentSpecificMemory()`, and high-resolution timers. These headers instruct the browser to block loading resources or iframes not opted in by cross-origin documents, and to block cross-origin windows from interacting directly with your document.

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

---

### Deeper Explanation: The Browser Is Your Only Trusted Sandbox

Browser security for application engineers reduces to one principle: **all code and data crossing into your origin is untrusted, and the browser is the only thing enforcing the boundary**. Practical consequences:

- **The origin is the security unit.** Same-origin policy protects you from other sites, not from your own bugs. Any injected script runs with full access to storage, cookies (non-httpOnly), and the DOM.
- **XSS is an architecture problem.** A strict CSP with nonces plus framework escaping removes most injection paths; `dangerouslySetInnerHTML` and `innerHTML` reintroduce them.
- **Cross-origin isolation is opt-in.** `SharedArrayBuffer` and precise timers require COOP/COEP headers, which in turn require every embedded resource to be CORS-correct.
- **Sandboxing third-party content**: `<iframe sandbox>` with an explicit allow-list, and `Permissions-Policy` to remove capabilities from embedded frames.

### Extended Example: The Header Baseline Plus A Nonce'd CSP

```ts
// middleware: one CSP, nonce per response, no inline escapes
const nonce = crypto.randomUUID().replace(/-/g, '');

const csp = [
  `default-src 'self'`,
  `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`,
  `style-src 'self' 'unsafe-inline'`,
  `img-src 'self' data: https://images.example.com`,
  `connect-src 'self' https://api.example.com`,
  `frame-ancestors 'none'`,
  `base-uri 'none'`,
  `object-src 'none'`,
].join('; ');

headers.set('Content-Security-Policy', csp);
headers.set('Cross-Origin-Opener-Policy', 'same-origin');
headers.set('Cross-Origin-Embedder-Policy', 'credentialless');
headers.set('X-Content-Type-Options', 'nosniff');
headers.set('Referrer-Policy', 'strict-origin-when-cross-origin');
```

### Additional Pitfalls
- **`unsafe-inline` in `script-src`.** It nullifies the CSP's XSS protection entirely.
- **CSP started in report-only and never enforced.** The reports pile up and the policy protects nobody.
- **Trusting `postMessage` without an origin check.** Always verify `event.origin` and the expected shape.
- **Storing privileged tokens in JS-accessible storage.** Any injected script can read them; keep them in httpOnly cookies or mint per-request capabilities.
- **Third-party scripts inside the main frame.** They inherit your origin and CSP bypasses; isolate them or self-host with a version lock.

### Real-World Deal-Breakers
- **No CSP** → XSS vulnerability. Add `Content-Security-Policy: default-src 'self'`.
- **`unsafe-inline` in CSP** → defeats CSP's XSS protection.
- **No COOP/COEP** → `SharedArrayBuffer` unavailable; high-resolution timers limited.
- **No `SameSite` on cookies** → CSRF vulnerability. Use `SameSite=Lax` or `Strict`.
- **No `HttpOnly` on session cookies** → XSS can read session tokens.
- **CORS `Access-Control-Allow-Origin: *` with credentials** → invalid; browser rejects the response.
- **Trusted Types not enforced** → DOM XSS via `innerHTML`.
