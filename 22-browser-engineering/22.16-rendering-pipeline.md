### The 12-Stage Pipeline

The browser turns HTML, CSS, and JavaScript into pixels through a pipeline of discrete, well-defined stages. Chromium's modern implementation, RenderingNG, splits that pipeline across the renderer's main thread, the renderer's compositor thread, and a separate Viz process so that scrolling and compositor-driven animation can stay at 60fps even when the main thread is busy.

```text
Main thread (renderer):
  1. Parse HTML → DOM
  2. Parse CSS → CSSOM
  3. Style recalc → computed styles
  4. Layout → fragment tree (geometry)
  5. Pre-paint → paint property trees
  6. Paint → display lists (drawing commands)
  7. Commit → serialize to compositor thread

Compositor thread (renderer):
  8. Layerize → compositor layers
  9. Raster → decode pixels (worker threads)
  10. Activate → ready layers

Viz process:
  11. Aggregate → combine compositor frames
  12. Draw → GPU commands → screen
```

### Producer-Consumer Model
The rendering pipeline is a **producer-consumer system across threads and processes**. The main thread produces structured, immutable artifacts - DOM, CSSOM, computed styles, fragment tree, property trees, and display lists. The compositor thread consumes those artifacts to layerize, raster on worker threads, and assemble compositor frames. It also handles scroll and transform/opacity animation without going back to the main thread. The Viz process aggregates compositor frames from every renderer plus the browser UI and issues GPU commands to the screen.

### Short-Circuiting with Property Trees
The architectural lever is the **property trees**. When only compositor-driven properties (`transform`, `opacity`, scroll offset) change, Animate and Scroll can short-circuit straight into Aggregate - skipping the main thread entirely.

```css
/* ✅ Compositor-only animation - no main thread */
.card:hover {
  transform: translateY(-4px);
  opacity: 0.9;
}

/* ❌ Main-thread animation - triggers layout + paint */
.card:hover {
  width: 300px;
  left: 20px;
}
```

### Deeper Explanation: Every Animation Budget Is A Pipeline Budget

The pipeline (style â†’ layout â†’ paint â†’ composite) is where frame budgets are spent: a 16.7 ms budget at 60 Hz, 8.3 ms at 120 Hz. The engineering habit is to know which phases your change triggers:

| Change | Phases invalidated | Cost |
|---|---|---|
| `transform`, `opacity` | composite only | cheapest, GPU-friendly |
| `color`, `background` | paint (+ composite) | medium |
| `width`, `top`, `font-size` | style â†’ layout â†’ paint â†’ composite | most expensive |
| Adding DOM in a loop | all of the above, repeatedly | catastrophic |

Two modern nuances worth internalising: **`content-visibility: auto`** lets the browser skip rendering off-screen subtrees entirely, and **`contain`/`contain-intrinsic-size`** make layout work proportional to the subtree rather than the document. They turn "render a 10 000-row list" from a layout emergency into a routine screen.

### Additional Pitfalls
- **Forcing synchronous layout.** Reading `offsetHeight` after a write in a loop triggers layout thrash; batch reads then writes.
- **Animating layout properties.** `left`/`top`/`height` re-run layout every frame; `transform` does not.
- **Layout thrash from measurement libraries.** Anything that measures per element in a loop (some tooltip and virtualisation libraries) can add tens of milliseconds.
- **No `will-change`, or too much of it.** Promotes layers, costs memory: apply it narrowly, and remove it after the animation.
- **Believing `requestAnimationFrame` makes work free.** It aligns to the frame, it does not make the work cheaper.

### Real-World Deal-Breakers
- **Reading `offsetHeight` in a loop** → forces synchronous layout. Read all layout properties first, then write.
- **Animating `width`/`height`/`top`/`left`** → triggers layout + paint + composite on every frame. Use `transform` and `opacity`.
- **`document.write()` after load** → restarts the entire rendering pipeline.
- **Large DOM (10,000+ nodes)** → slows every pipeline stage: style recalc, layout, paint, and memory.
- **`will-change` overuse** → creates too many compositor layers, consuming GPU memory and causing crashes on low-end devices.
