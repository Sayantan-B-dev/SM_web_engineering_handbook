### The Mental Model
A WebSocket is a **persistent, symmetric message pipe** established by an HTTP upgrade: after the handshake, neither side is a "client" in the request/response sense. That gives you sub-100 ms server-initiated delivery, and it takes away everything HTTP gave you for free â€” status codes per message, retries, caching, and per-request authentication.

```ts
export class Socket {
  private ws?: WebSocket;
  private attempt = 0;
  private queue: unknown[] = [];

  constructor(private url: string, private onMessage: (data: unknown) => void) {}

  connect() {
    this.ws = new WebSocket(this.url);
    this.ws.onopen = () => {
      this.attempt = 0;
      this.queue.splice(0).forEach((m) => this.ws!.send(JSON.stringify(m)));
      this.heartbeat();
    };
    this.ws.onmessage = (e) => this.onMessage(JSON.parse(e.data));
    this.ws.onclose = () => {
      // exponential backoff with jitter â€” never a tight reconnect loop
      const delay = Math.min(30_000, 500 * 2 ** this.attempt++) * (0.5 + Math.random());
      setTimeout(() => this.connect(), delay);
    };
  }

  send(msg: unknown) {
    if (this.ws?.readyState === WebSocket.OPEN) this.ws.send(JSON.stringify(msg));
    else this.queue.push(msg);           // buffer while disconnected
  }

  private heartbeat() {
    const id = setInterval(() => {
      if (this.ws?.readyState === WebSocket.OPEN) this.ws.send(JSON.stringify({ type: 'ping' }));
      else clearInterval(id);
    }, 30_000);
  }
}
```

### Auth And Scaling Notes
- Browsers cannot set custom headers on `new WebSocket`, so authenticate with a cookie, a short-lived ticket in the query string, or a first authenticated message.
- Server fleets need sticky sessions or a pub/sub fan-out (Redis, NATS) so a message produced on one node reaches subscribers on another.
- Detect half-open connections: TCP can stay "open" long after the network is gone. Application-level ping/pong plus a server-side idle timeout is the only reliable detection.

### Real-World Deal-Breakers
- **No reconnection strategy.** One blip kills the session; backoff with jitter and a resync on reconnect are mandatory.
- **No message framing/versioning.** A deploy that changes the payload breaks every open client; include a version and tolerate unknown types.
- **Assuming ordering is preserved across reconnects.** It is preserved within a connection only.
- **Sending huge payloads in one frame.** Chunk or use SSE/downloads; large frames block the pipe for interactive messages.
- **Tight reconnect loops.** They turn a server incident into a self-inflicted DDoS.
