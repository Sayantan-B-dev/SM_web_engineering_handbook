## 22.11 Browser Engineering - Putting It All Together

### The Reference Architecture

```
User interaction
  → Browser process routes to renderer
  → Renderer main thread: JS → style → layout → pre-paint → paint
  → Commit → compositor thread
  → Compositor: layerize → raster (worker threads)
  → Viz process: aggregate → draw (GPU)
  → Screen

In parallel:
  → Network process: HTTP/3 + QUIC, cache, cookies
  → Worker threads: CPU-heavy computation
  → Service Worker: fetch interception, offline cache
  → GPU process: WebGPU compute, rasterization
```

### What to Instrument First
1. **Long tasks** (LoAF) - what's blocking the main thread?
2. **Core Web Vitals** - LCP, INP, CLS.
3. **Rendering pipeline** - layout, paint, composite timings.
4. **Network** - HTTP/3 adoption, cache hit rate, TTFB.
5. **Storage** - quota usage, eviction events.
6. **Security** - CSP violations, CORS failures.

---

### Deeper Explanation: One Slow Page, Four Layers Of Explanation

Take a checkout page that feels sluggish on a mid-tier Android phone. The layers give four different, complementary explanations:

- **Multi-process**: the cross-origin payment iframe lives in its own process; its startup is not free, and it cannot share objects with your page.
- **Pipeline**: the total-price row re-lays out on each keystroke because the change invalidates layout, not just paint.
- **Event loop**: the price recalculation is a synchronous loop over 4 000 line items, producing a 120 ms long task on each input event â€” the actual cause of the poor INP.
- **Networking/storage**: the item catalogue is fetched on each mount instead of being read from IndexedDB, adding 300 ms of latency and a loading flicker.

The fixes map back to the same layers: move the recalculation to a worker (loop/thread), memoise the derived total and animate with `transform` (pipeline), read the catalogue from IndexedDB with a background revalidate (storage/networking), and give the iframe a fixed size to avoid layout shift (pipeline again). No single layer explains the symptom; together they do.

### Additional Pitfalls
- **Optimising the layer you understand best.** The measured bottleneck is often one layer away from where the code looks wrong.
- **Ignoring the hardware you do not own.** A 4Ã- CPU throttled profile is the honest baseline.
- **Treating this as a one-off audit.** Layer-by-layer reasoning is a habit, not a project.

### Real-World Deal-Breakers (Overall)
- **Blocking the main thread** → everything freezes. Move work to workers.
- **Animating non-compositor properties** → jank. Use `transform` and `opacity`.
- **Type instability in hot functions** → deoptimization, slow bytecode.
- **`localStorage` for anything non-trivial** → synchronous, 5MB, blocks main thread.
- **No CSP** → XSS vulnerability.
- **No COOP/COEP** → no `SharedArrayBuffer`, no high-res timers.
- **WebGPU without fallback** → broken on older Safari.
- **Infinite microtask chain** → browser freeze.
- **No long task monitoring** → you don't know what's blocking the main thread.
