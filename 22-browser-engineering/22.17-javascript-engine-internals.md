### The Compilation Pipeline
V8 uses a multi-tier compilation system to balance startup time and peak performance.

```text
JavaScript source
  → Parser → AST
  → Ignition (bytecode interpreter)  ← starts fast
  → Sparkplug (baseline compiler)    ← quick optimization
  → TurboFan (optimizing compiler)   ← peak performance, speculative
  → Deoptimization (if speculation fails) → back to Ignition bytecode
```

If the speculation used during optimization turns out to be incorrect - for example, `add` suddenly receives a string - V8 **deoptimizes**: it discards the optimized machine code and falls back to executing Ignition bytecode to guarantee correctness.

### Hidden Classes (Maps)
V8 could treat each object as a bag of properties. Instead, it surmises that you'll only create so many different kinds of objects, and each kind will be used in stereotypical ways. The hidden class mechanism is the principal means to do this. The principal data structures are: **Map** (the hidden class itself, the first pointer in an object), **DescriptorArray** (the full list of properties), and **TransitionArray** (edges from one Map to another when a property is added).

**Advantages:** Property access does not require a dictionary lookup, and hidden classes enable inline caching - V8 can use the classic class-based optimization.

```javascript
// ✅ Same hidden class - fast property access
function Point(x, y) {
  this.x = x;
  this.y = y;
}
const p1 = new Point(1, 2);
const p2 = new Point(3, 4);
// Both share the same Map

// ❌ Different hidden classes - slow
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };  // different property order
const c = { x: 1, y: 2 };
delete c.x;                  // creates a new Map
```

### Inline Caches (ICs)
An IC caches the last Map seen at a property access site. The cached Map is stored inline in the code. When the same Map is seen again, V8 patches the inline cache to skip the lookup entirely.

### Deeper Explanation: Shapes, Hidden Classes, And Interpreter Tiers

A JS engine turns your source into bytecode, then optimises hot functions through tiers (Sparkplug/Maglev/Turbofan in V8). Optimisation is speculative: the engine guesses object shapes and types, and a guess that stops holding triggers deoptimisation. That is why certain patterns are consistently slow:

- **Objects that change shape.** Adding properties conditionally (`if (x) obj.a = 1`) creates multiple hidden classes; initialise all fields in the constructor and keep shapes monomorphic.
- **Mixed-type arrays.** `[1, 'a', {}]` cannot be a packed-elements array; numerical loops on it run 5-10Ã- slower than on `Float64Array`.
- **`delete` on an object.** It converts a fast property to a dictionary-mode lookup.
- **Long-lived closures capturing large scopes.** They keep whole graphs alive and slow down GC.
- **`try/catch` around a hot loop historically prevented inlining.** Modern engines are better, but exceptions in hot paths remain expensive.

The practical conclusion is not "hand-optimise" â€” it is "keep data shapes stable (which React and TypeScript naturally encourage), and use typed arrays when throughput matters".

### Additional Pitfalls
- **Micro-benchmarking in isolation.** Real gains come from algorithmic change or moving work off the main thread, not from bracket-shuffling.
- **`JSON.parse(JSON.stringify(x))` as a clone.** It destroys shapes and loses types; use `structuredClone`.
- **Overuse of `delete` and dynamic keys.** `Map` is the right structure for dynamic key sets.
- **Megamorphic call sites.** Passing differently shaped objects to one function deoptimises it for everyone.

### Real-World Deal-Breakers
- **Type instability in hot functions** → mixing types (`add(1, 2)` then `add('a', 'b')`) causes deoptimization, falling back to slow bytecode.
- **Deleting properties** → `delete obj.prop` changes the hidden class, slowing subsequent property access. Set to `null` instead.
- **Adding properties after creation** → changes the hidden class. Initialize all properties in the constructor.
- **Sparse arrays** → slower than dense arrays; holes force dictionary-mode elements.
- **`arguments` object** → prevents optimization in some cases. Use rest parameters.
