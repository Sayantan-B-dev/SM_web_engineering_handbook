### The Event Loop Algorithm
The event loop concept is very simple. There's an endless loop where the JavaScript engine waits for tasks, executes them, and then sleeps, waiting for more tasks. Tasks form a queue - the "macrotask queue" - processed on a first-come, first-served basis.

Two critical details:
1. **Rendering never happens while the engine executes a task.** It doesn't matter if the task takes a long time. Changes to the DOM are painted only after the task is complete.
2. **If a task takes too long**, the browser can't do other tasks, such as processing user events. After a time, it raises "Page Unresponsive".

### Execution Order
```javascript
console.log('1'); // sync

setTimeout(() => console.log('2'), 0); // macrotask

Promise.resolve().then(() => console.log('3')); // microtask

queueMicrotask(() => console.log('4')); // microtask

console.log('5'); // sync

// Output: 1, 5, 3, 4, 2
// Sync → microtasks drain fully → one macrotask
```

Microtasks execute before macrotasks in the same event loop iteration. All microtasks are completed before any other event handling or rendering or any other macrotask takes place.

### Long Tasks
Long Tasks API lets you monitor tasks that occupy the main thread for **50 milliseconds or more**. Long tasks can cause responsiveness problems. If a user tries to interact with a page but the main thread is busy with a long task, the user interaction is delayed.

```javascript
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('Long task:', entry.duration, 'ms');
  }
});
observer.observe({ type: 'longtask', buffered: true });
```

### Long Animation Frames API (LoAF)
Long Animation Frames API is an update to the Long Tasks API to provide a better understanding of slow UI updates. It helps identify slow animation frames that may affect Interaction to Next Paint (INP). Unlike Long Tasks, LoAF provides **attribution** - who caused the long task.

```javascript
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    for (const script of entry.scripts) {
      console.log('Script:', script.sourceURL, script.duration);
    }
  }
});
observer.observe({ type: 'long-animation-frame', buffered: true });
```

### Deeper Explanation: Task, Microtask, Render â€” In That Order, Always

The event loop runs the oldest task, then **drains the entire microtask queue** (promises, `queueMicrotask`, `MutationObserver`), then asks whether a render is due. Repeat. Two invariants explain almost every "unexpected" behaviour:

1. **Microtasks starve rendering.** An unbounded promise chain blocks the frame forever; `await` inside a loop of 100 000 iterations yields only to microtasks.
2. **Rendering is not guaranteed per task.** If you schedule work in a loop back-to-back, the browser may skip frames even when each task is small.

Where each scheduling API sits matters:

| API | Position | Use for |
|---|---|---|
| Promise / `queueMicrotask` | microtask | Sequencing without a paint |
| `setTimeout(0)` | next task | Yielding to rendering |
| `requestAnimationFrame` | before paint | Visual updates, animation |
| `requestIdleCallback` | idle time | Non-urgent work (analytics, prefetch) |
| `scheduler.postTask` | prioritised task | User-visible vs background work |
| `MessageChannel` | next task, fast | Worker-style yielding in one thread |

### Additional Pitfalls
- **Assuming `await` yields to rendering.** It yields to microtasks only; a long chain still blocks paint.
- **`setTimeout(fn, 0)` in a loop for "chunking".** Each iteration costs up to 4 ms of clamping in nested timers; use `scheduler.yield` or `requestIdleCallback`.
- **Reading a stale DOM in the same task after a state change.** React's update is a task/microtask boundary away; measure in an effect or after paint.
- **Assuming timers are accurate.** Background tabs throttle them heavily; never drive correctness from timing.
- **Blocking on `alert`/`confirm`.** They are synchronous and freeze the loop.

### Real-World Deal-Breakers
- **Infinite microtask chain** → `Promise.resolve().then(loop)` freezes the browser forever. Microtasks have priority over rendering.
- **`setTimeout(fn, 0)` is not 0ms** → minimum ~4ms after nesting; use `queueMicrotask` for true immediate deferral.
- **Long tasks > 50ms** → block input, animation, and rendering. Break them up with `scheduler.postTask` or `setTimeout`.
- **`requestAnimationFrame` for animations** → synced to the display refresh rate. `setTimeout(animate, 16)` drifts.
