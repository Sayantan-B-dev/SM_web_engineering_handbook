### Long Tasks Observer
```javascript
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    console.log(`Long task: ${entry.duration}ms`, entry.attribution);
  });
});
observer.observe({ type: 'longtask', buffered: true });
```

### Long Animation Frames (LoAF)
```javascript
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('LoAF:', entry.duration, 'ms');
    for (const script of entry.scripts) {
      console.log('  Script:', script.sourceURL, script.duration, 'ms');
    }
  }
});
observer.observe({ type: 'long-animation-frame', buffered: true });
```

### User Timing for Custom Spans
```javascript
performance.mark('checkout-start');
await processPayment();
performance.mark('checkout-end');
performance.measure('checkout', 'checkout-start', 'checkout-end');

const [measure] = performance.getEntriesByName('checkout');
console.log(measure.duration); // ms
```

### Deeper Explanation: Observers Give You The Real Timeline

The `PerformanceObserver` family records what actually happened in the browser rather than what you assume: timings for navigations, resources, long tasks, layout shifts, paint, and interaction latency. The three that shape frontend work:

- **Long tasks** (`longtask`) â€” anything over 50 ms on the main thread; the leading indicator of poor INP.
- **Layout shift** (`layout-shift`, excluding recent input) â€” the CLS contribution, with attribution to the element that moved.
- **Event timing** (`event`, with `durationThreshold`) â€” the actual INP contributors, including `interactionId` so you can group an interaction's processing.

Pair them with the modern primitives: `performance.mark`/`measure` for your own spans, `scheduler.postTask` for priority, and `PerformanceObserver` with `buffered: true` so you catch entries emitted before your observer attached.

### Extended Example: Long-Task And Shift Attribution In ~20 Lines

```ts
const longTaskObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report('long_task', {
      ms: Math.round(entry.duration),
      startMs: Math.round(entry.startTime),
      attribution: (entry as PerformanceLongTaskTiming).attribution?.[0]?.name ?? 'unknown',
    });
  }
});
longTaskObserver.observe({ type: 'longtask', buffered: true });

const shiftObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as (PerformanceEntry & { value: number; hadRecentInput: boolean; sources?: { node?: Node }[] })[]) {
    if (entry.hadRecentInput || !entry.value) continue;
    report('layout_shift', {
      score: Number(entry.value.toFixed(4)),
      tag: entry.sources?.[0]?.node?.nodeName ?? 'unknown',
    });
  }
});
shiftObserver.observe({ type: 'layout-shift', buffered: true });
```

### Additional Pitfalls
- **Attaching observers without `buffered: true`.** You miss everything emitted before the observer was created.
- **Counting all shift entries.** Shifts within 500 ms of user input are excluded from CLS; a naive sum reports phantom scores.
- **Ignoring `interactionId`.** Without it you cannot tell which interaction produced a slow frame, only that one occurred.
- **`performance.now()` for wall-clock timestamps.** It is monotonic relative to page start; use `Date.now()` for correlating with server logs.
- **Instrumenting in development only.** Real devices behave differently; ship the instrumentation.

### Real-World Deal-Breakers
- **Only `PerformanceObserver` for Long Tasks** → LoAF provides attribution (which script, which function). Use LoAF.
- **No `performance.mark` for custom flows** → you can't measure business-critical operations.
- **Ignoring INP** → a fast-loading page with a slow event handler still feels broken.
- **`performance.memory` (deprecated)** → use `measureUserAgentSpecificMemory()` with cross-origin isolation.
