### The 2026 State
> "The ecosystem moved to build-time CSS: Tailwind and CSS Modules dominate, and the zero-runtime camp (vanilla-extract, Panda CSS, StyleX) emits static CSS."

### Runtime vs Zero-Runtime

| | Runtime (styled-components, Emotion) | Zero-runtime (vanilla-extract, StyleX) |
|--|--------------------------------------|----------------------------------------|
| Runtime cost | Moderate | Zero |
| RSC-safe | ❌ | ✅ |
| Dynamic styles | ✅ (via props) | Limited (via variants) |
| Bundle size | Larger | Smaller |
| Theming | ThemeProvider | CSS variables |

### Why Runtime CSS-in-JS Is Declining
Runtime CSS-in-JS requires a **client-side runtime** - it parses styles at render time. This makes it **incompatible with React Server Components**. It also adds bundle size and render overhead.

### When CSS-in-JS Is Still Appropriate
- **Runtime theming** with prop-based dynamic styles (e.g., a color picker that generates styles from user input).
- **Legacy codebases** already invested in styled-components/Emotion.
- **Zero-runtime alternatives** (vanilla-extract, StyleX) when you want type-safe CSS with no runtime cost.

### Real-World Deal-Breakers
- **Runtime CSS-in-JS in RSC** → incompatible; requires client-side runtime. Use CSS Modules or Tailwind.
- **`styled-components` for new apps in 2026** → the ecosystem moved to build-time CSS. You're building on a declining foundation.
- **No build-time extraction** → styles are injected at runtime; slower first paint.
- **ThemeProvider for theming** → CSS variables are simpler, zero-runtime, and work in RSC.
