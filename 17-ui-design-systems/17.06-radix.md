### Core Principles
Radix UI provides **unstyled, accessible components (primitives)** that you can customize to match any design system. Key strengths: headless by design, accessibility built-in, composable primitives.

### `asChild` - Composition
Use `asChild` to compose Radix's functionality onto alternative element types. When `asChild` is set to `true`, Radix will not render a default DOM element, but instead clone the child and pass the props and behavior to it.

```tsx
// Render a link that behaves like a button
<Dialog.Trigger asChild>
  <a href="/settings">Open Settings</a>
</Dialog.Trigger>
```

### Installation (2026)
The per-component `@radix-ui/react-*` packages still work, but **the docs now steer you to the single `radix-ui` package** to avoid version drift:

```bash
# ✅ Current
import { Dialog } from "radix-ui"

# ⚠️ Still works, but version drift risk
npm i @radix-ui/react-dialog
import * as Dialog from "@radix-ui/react-dialog"
```

### Theming with CSS Variables
```css
:root {
  --radix-dropdown-menu-content-transform-origin: var(--radix-popper-transform-origin);
}
[data-theme="dark"] {
  --radix-dropdown-menu-content-background: var(--color-gray-900);
}
```

### Real-World Deal-Breakers
- **Fighting Radix's accessibility** → it handles keyboard, focus, ARIA. If you override, you break it.
- **Assuming Base UI and Radix have identical part trees** → Base UI may have extra parts (e.g., `Popover.Positioner`).
- **Using per-component packages without version pinning** → version drift between primitives causes subtle bugs.
- **Radix Themes when you need headless** → Themes is a styled library; use Primitives for full control.
