## 17.4 Accessibility (in Design Systems)

### Subtopic Tree
- WCAG AA as baseline (4.5:1 text, 3:1 UI)
- Keyboard navigation baked into primitives
- Focus management (trapping, restoration)
- ARIA roles and attributes from headless primitives
- `prefers-reduced-motion` support
- Token-level contrast fixes
- Screen reader testing
- Automated a11y testing (axe-core)

### Accessibility Is Built In, Not Bolted On
> "Keyboard, focus, ARIA, `prefers-reduced-motion` baked into the primitive (house opinion #1). Lean on accessible primitives (Radix/React Aria/Fluent) rather than re-implementing a combobox."

### Token-Level Contrast
Design systems should encode contrast at the token level. Atlassian updated **color tokens** to meet accessibility guidelines for contrast in light and dark themes, while maintaining brand hierarchy. When a token is fixed, every component using it inherits the fix.

### What Primitives Handle for You

| Concern | Handled by primitive |
|---------|---------------------|
| Keyboard navigation | Tab, Arrow keys, Enter, Escape |
| Screen readers | Proper ARIA attributes, live regions |
| Focus management | Automatic focus trapping and restoration |
| Disabled states | `aria-disabled` handling |

**Rule:** Never override accessibility features. Enhance, don't replace.

### Real-World Deal-Breakers
- **Reimplementing a combobox** → 200 lines of fragile keyboard handling; use Radix/React Aria instead.
- **`outline: none` without replacement** → keyboard users lose focus indicator.
- **No `prefers-reduced-motion`** → vestibular disorders triggered.
- **Color-only information** → "red = error" fails for colorblind users. Add icons/text.
- **No a11y tests in CI** → regressions ship silently. Add `axe-core` to your test suite.
