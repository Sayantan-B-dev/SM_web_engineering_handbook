### Reviewer Responsibilities
What to check:
- **Correctness**: Does the code do what it claims?
- **Quality**: Is it readable, maintainable, and well-structured?
- **Standards**: Does it follow team conventions?
- **Edge cases**: Are errors and edge cases handled?
- **Security**: Are there any security concerns?
- **Performance**: Any obvious performance issues?

### Review Etiquette
- **Be kind and constructive**
- **Ask questions rather than make demands**
- **Explain the "why" behind suggestions**
- **Approve if changes are good enough** (don't be a perfectionist)
- **Respond within 1 business day if able**

### Conventional Comments
Conventional Comments are a **standardized way of giving feedback** during reviews. They keep comments clear, respectful, and helpful.

| Label | Meaning | Example |
|-------|---------|---------|
| `praise:` | Highlight something good | `praise: Nice error handling here.` |
| `nitpick:` | Minor, non-blocking suggestion | `nitpick: Consider renaming this variable.` |
| `suggestion:` | Improvement idea | `suggestion: Could we use Array.filter() here?` |
| `issue:` | Something that must be addressed | `issue: This will throw if user is null.` |
| `question:` | Ask for clarification | `question: Why did we choose useEffect here?` |
| `thought:` | Non-blocking idea | `thought: We might want to cache this later.` |
| `chore:` | Simple task | `chore: Please update the changelog.` |

### Handling Disagreements
- Discuss in PR comments or Slack/Teams
- Default to the reviewer's suggestion unless there is strong reasoning otherwise
- Escalate to an organization owner if needed
- **Remember: both parties want good code**

### Review Timelines
- **Target response**: within 24 hours
- **Follow up**: if no response after 14 days, reviewer returns to the PR
- **Stale PRs**: close after a defined period (e.g., 30 days) if no activity

### Deeper Explanation: Review As Knowledge Transfer

Review is the highest-frequency teaching surface a team has. Done well, it transfers conventions, catches risk early, and spreads ownership; done badly, it becomes a stylistic battleground that slows work and damages trust. The core discipline: separate correctness from preference, be specific about why, and prefer questions which invite reasoning over commands.

For the reviewer: read the description first, focus on the change's intent, check tests actually assert behaviour, and label severity. For the author: keep diffs small, answer every comment, and push back with reasoning when you disagree â€” that conversation is often more valuable than the code.

### Additional Pitfalls
- **Style opinions as blockers.** Automate formatting; reserve blocking for substance.
- **Comments without rationale.** "Change this" teaches nothing and invites argument.
- **Reviewing the person.** "You alwaysâ€¦" destroys trust; describe the code.
- **Silent approval.** Say what you verified so the approval carries information.
- **Unbounded latency.** Reviews that wait days force bigger batches and lower quality.

### Real-World Deal-Breakers
- **Approving without reading** → bugs ship to production. Don't merge PRs you've only skimmed.
- **Requesting changes without explanation** → author doesn't know what to fix.
- **Not responding to review comments** → PR stalls indefinitely.
- **Taking review personally** → review feedback is the process working, not a personal attack.
- **Reviewing your own PR and self-approving** → defeats the purpose of review.
