### Types of Contribution
Contributing does not mean writing code. Contribution spans **documentation, testing, design, community management, issue triage, and code**. Anyone who has added any of these to a project is a contributor.

| Contribution Type | Examples |
|-------------------|----------|
| **Code** | Bug fixes, features, refactoring |
| **Documentation** | README updates, tutorials, API docs |
| **Triage** | Labeling issues, reproducing bugs, closing duplicates |
| **Design** | UI/UX improvements, logos, diagrams |
| **Community** | Answering questions, moderating forums, organizing events |
| **Translation** | Localizing docs and UI |
| **Testing** | Writing tests, reporting bugs, verifying fixes |

### Google Summer of Code (GSoC)
GSoC is a global program that pairs contributors with open source organizations for a 12-week project. In 2026, Django received over **200 proposals from contributors across the world**. GSoC is a structured entry point into open source contribution.

### Community Builder Programs
Programs like the **AWS Community Builders** provide resources, networking, and visibility for active community contributors. Requirements typically include at least two public, non-work technical contributions (blogs, tutorials, videos, webinars, live sessions) published within the last 1-12 months.

### Hackathons and Buildathons
Hackathons are **time-boxed events** where teams build projects. They are excellent for:
- Learning new technologies
- Meeting other developers
- Building a portfolio
- Winning prizes and recognition

### Writing and Speaking
- **Blog posts**: Share what you learned. Dev.to, Hashnode, Medium, personal blog.
- **Tutorials**: Step-by-step guides for specific tasks.
- **Documentation**: Improve the docs of projects you use.
- **Meetup talks**: 15-25 minute talks at local meetups.
- **Conference talks**: 30-45 minute talks at regional conferences.

---

### Deeper Explanation: Contribution Is A Habit, Not An Event

Communities (meetups, forums, open source, internal guilds) run on repeated small contributions: answering a question, reviewing a PR, writing a summary, hosting a session. The people who become central are the ones who show up consistently and do the unglamorous work.

A sustainable pattern: pick one community, commit to a small cadence (an hour a week), choose a repeatable contribution (triage, docs, beginner questions), and make it visible (notes, recordings, changelogs). Over a year that compounds into reputation, skills, and opportunities that no amount of job applications provides.

### Additional Pitfalls
- **Intending to contribute "someday".** Nothing happens without a cadence.
- **Only consuming.** Help is what builds standing.
- **Overcommitting in a burst.** Burnout ends involvement; small and steady wins.
- **No public trace.** Notes and changelogs are how contributions become visible.
- **Ignoring the newcomers.** Being welcoming is the highest-value contribution a senior engineer can make.

### Real-World Deal-Breakers
- **Thinking contribution = code** → you miss 80% of contribution opportunities. Docs, triage, and community are just as valuable.
- **Not reading `CONTRIBUTING.md`** → your contribution violates project conventions and is rejected.
- **Starting with a huge PR** → maintainers can't review it. Start small.
- **No follow-up** → you submit a PR and disappear. Respond to review feedback.
- **Contributing only for the resume** → maintainers see through it. Contribute because you care.
