### What Architecture Discussions Are
Architecture discussions are **structured conversations about technical decisions that are expensive to reverse**. They are not brainstorming sessions or whiteboard sketches. They are deliberate processes for making and documenting decisions that will affect the team for months or years.

### Architecture Decision Records (ADRs)
An ADR is a short markdown file documenting a significant decision.

```markdown
# ADR-0012: Use TanStack Query for Server State

## Status
Accepted

## Context
We fetch server data via useEffect + useState in 40+ components.
No caching, no deduplication. Multiple components fetch the same data
independently. Users see loading spinners on every navigation.

## Decision
Adopt TanStack Query for all server state. Keep Zustand for client state.

## Consequences
- + Caching, deduplication, background refetch
- + Consistent loading/error states across the app
- - New dependency, learning curve for the team
- - Existing useEffect fetches need migration (estimated: 40 files, 2 weeks)

## Alternatives Considered
- **SWR**: Simpler but less feature-rich. Rejected because we need
  mutations with optimistic updates and infinite queries.
- **Redux Toolkit Query**: Already using Zustand, not Redux.
  Adding Redux for RTK Query would be overkill.
- **Custom hook**: Rejected. Building a caching layer is hard to get right.
```

**Why ADRs matter:** In 2 years, when someone asks "why TanStack Query?", the answer is in the repo. The decision is not re-litigated every 6 months.

### The RFC Process
An RFC (Request for Comments) is a proposal for a significant change. It is longer than an ADR and is meant to gather feedback before a decision is made.

```
RFC-0042: Migrate from REST to tRPC

## Summary
Replace our REST API layer with tRPC for end-to-end type safety.

## Motivation
- REST endpoints require manual type definitions on the client
- Type drift between frontend and backend causes runtime errors
- tRPC eliminates the need for manual API client code

## Detailed Design
- Add tRPC router alongside existing REST routes
- Migrate endpoints incrementally
- Deprecate REST routes as tRPC equivalents are added

## Drawbacks
- tRPC is TypeScript-only; non-TS clients can't consume it
- Learning curve for the team
- Requires monorepo or shared types package

## Alternatives
- **GraphQL**: More flexible but heavier (gateway, schema registry)
- **OpenAPI codegen**: Type safety but codegen step and stale types
- **Continue with REST**: No type safety, manual client code

## Unresolved Questions
- How do we handle public API consumers who rely on REST?
- Do we migrate all endpoints or only internal ones?
```

### Deeper Explanation: Discussions Need Constraints Before Solutions

Architecture conversations stall when people argue solutions for different problems. The fix is disciplined framing: agree on the forces at play (scale, latency, cost, team size, compliance, time to market) before comparing designs, and record the decision even when the outcome is "keep what we have".

ADRs make this durable: a short file per decision with status, context, decision, consequences, and alternatives considered. The template (MADR) is intentionally lightweight so the decision gets written down at all â€” and the "alternatives considered" section is what prevents the same debate six months later.

### Additional Pitfalls
- **Jumping to solutions.** Without agreed constraints, comparison is taste.
- **Design by seniority.** Decisions attributed to authority get reversed when that person changes role; write the reasoning.
- **Undocumented decisions.** New team members re-litigate settled questions.
- **Endless spikes.** Time-box exploration and require a written recommendation afterwards.
- **Ignoring reversibility.** Irreversible decisions deserve more care than reversible ones.

### Real-World Deal-Breakers
- **No ADR** → decisions are forgotten, the same debate happens every 6 months.
- **No rejected alternatives** → future teams re-propose rejected options because they don't know why they were rejected.
- **Decision by authority, not evidence** → "We're using X because the CTO said so." No rationale, no trade-offs documented.
- **No ownership** → no one is accountable for the decision. When it fails, no one learns.
- **Too many decisions without discussion** → the team feels excluded. Adoption is low.
