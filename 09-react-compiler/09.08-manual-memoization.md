### When Manual Memoization Is Still Needed
React Compiler reduces routine memoization, but it **does not eliminate legitimate performance bottlenecks**. There are cases where manual memoization remains necessary:

1. **Cross-component referential stability** - when a parent passes a memoized value to a child, and you need to guarantee that reference doesn't change.
2. **Effect dependencies** - when an effect must not re-run unless specific values change.
3. **Third-party library integration** - libraries that require stable references (e.g., chart libraries, maps, editors).
4. **When the compiler bails out** - the component isn't optimized at all, so manual memoization is your only option.

### The Compiler's Stance on Existing Manual Memo
> **"React Compiler preserves your existing useMemo, useCallback, and React.memo calls. If you've manually memoized something, the compiler assumes you had a good reason and won't remove it."**

**But there's a critical problem:** When the compiler sees manual memoization that **does not match** the memoization it generated, it **bails out of optimizing the entire component** to prevent breaking your code.

```jsx
// Compiler sees this useMemo
const book = useMemo(() => createBook(a, b, c), [a, b, c]);

// If compiler's inferred memoization for `book` doesn't match,
// the ENTIRE component is skipped
```

This is a known pain point - "Either you fully lean into RC and gain benefits like JSX memoization, or you lean into manual, codebase-informed memoization."

### Double Memoization Problem
If you leave manual `useMemo`/`useCallback` in place while using the compiler, you get:
- **Double memoization** - manual memo + compiler memo.
- **Maintenance burden** - two systems to keep in sync.
- **Obscured intent** - readers don't know what's essential vs. redundant.

### Migration: Removing Manual Memoization
Once the compiler is enabled and validated, manual `useMemo`, `useCallback`, and `React.memo` wrappers become **redundant**. The compiler inserts equivalent (or better) memoization automatically.

**Steps:**
1. Enable the compiler.
2. Validate with React DevTools ("Memo ✨" badge).
3. Remove manual memoization that doesn't match one of the exceptions.
4. Use ESLint plugins to enforce the removal.

**ESLint plugin for enforcement:**
- `eslint-plugin-react-no-manual-memo` - flags `useMemo`, `useCallback`, `React.memo` in codebases using React Compiler.

**Codemod for removal:**
- `@thinksharpe/react-compiler-unmemo` - removes `useMemo`/`useCallback` from your codebase.

### The Three Exceptions (Keep These)
Despite the compiler, you may still need manual memoization for:

1. **Referential stability across memo boundaries** - when a `React.memo` child depends on a stable prop reference.
2. **Effect dependency stability** - when an effect must not re-run.
3. **Third-party library requirements** - libraries that check reference equality internally.

### Real-World Deal-Breakers
- **Removing `useMemo` before enabling compiler** → performance regression.
- **Keeping manual memo that doesn't match compiler output** → entire component bails out.
- **Adding new manual memo after enabling compiler** → interferes with compiler analysis.
- **Assuming all manual memo is safe to remove** → the three exceptions above still need it.
