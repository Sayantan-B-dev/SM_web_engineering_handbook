## 9.5 `use no memo`

### Subtopic Tree
- Purpose: opt out of compilation
- Function-level vs module-level
- When to use (debugging, incompatible code)
- Temporary escape hatch
- Documentation best practices
- Removal plan

### What It Does
`"use no memo"` **prevents a function from being optimized** by React Compiler. It works in **all compilation modes** - even `all` mode.

```jsx
function ProblematicComponent(props) {
  "use no memo"; // This component won't be compiled
  return <div>{/* ... */}</div>;
}
```

### When to Use
| Scenario | Why |
|----------|-----|
| **Debugging** | Isolate whether compiler caused a bug |
| **Incompatible code** | Code that violates Rules of React or uses unsupported syntax |
| **Third-party integration** | Components that break when memoized |
| **Gradual adoption** | Temporarily exclude problematic components during migration |

### Best Practices
Directives are **escape hatches** - use them sparingly and document them.

```jsx
// ✅ Good - clear explanation
function DataGrid() {
  "use no memo"; // TODO: Remove after fixing issue with dynamic row heights (JIRA-123)
  // Complex grid implementation
}

// ❌ Bad - no explanation
function Mystery() {
  "use no memo";
  // ...
}
```

**Plan for removal:** Opt-out directives should be temporary:
1. Add the directive with a TODO comment.
2. Create a tracking issue.
3. Fix the underlying problem.
4. Remove the directive.

### Real-World Deal-Breakers
- **`"use no memo"` everywhere** → compiler provides no benefit; you're paying build cost for nothing.
- **Forgetting to remove opt-outs** → permanent performance loss on affected components.
- **Using `"use no memo"` instead of fixing Rules of React violations** → masks bugs that could cause other problems.
- **Module-level `"use no memo"`** → disables compilation for the entire file, not just one function.
