## 9.3 Compiler Transformations

### Subtopic Tree
- AST → HIR lowering
- Data-flow analysis
- Mutability & aliasing analysis
- Reactive place inference
- Reactive scope inference
- Scope alignment to block boundaries
- Cache slot emission
- `_c` hook injection
- JSX memoization
- Component-level memoization

### The Compiler Pipeline (Simplified)
1. **Parse** → Babel AST.
2. **Lower** → HIR (Control Flow Graph based).
3. **Analyze** → data-flow, mutability, aliasing.
4. **Infer reactive places** → which values can change between renders.
5. **Infer reactive scopes** → group values into memoization units.
6. **Align scopes** → to block scopes in HIR.
7. **Emit** → cache slots + `_c` hook.

### Data-Flow & Mutability Analysis
The compiler must understand:
- Which values are **reactive** (can differ between renders).
- Which values **mutate together** (minimal sets of values that mutate together).
- Which instructions do the mutating.

These minimal sets become **reactive scopes**, which translate into memoization blocks in the output.

### Scope Barriers
Hook and `use()` calls are treated as **reactive scope barriers**. This prevents hooks from incorrectly spanning reactive scopes, which could lead to unintended side effects during compilation.

### What Gets Memoized
- **Values** - any computed value used in rendering.
- **JSX elements** - the entire returned tree is memoized.
- **Functions** - event handlers and callbacks.
- **Components** - the component function itself is memoized (equivalent to `React.memo`).
- **Props objects** - object literals passed as props.

### Example: JSX Memoization
```jsx
// Your code
function Parent({ count }) {
  return (
    <div>
      <ExpensiveChild />
      <p>{count}</p>
    </div>
  );
}

// Compiler output (conceptual)
function Parent({ count }) {
  const $ = _c(2);
  let t;
  if ($[0] === undefined) {
    t = <ExpensiveChild />; // memoized - never recreated
    $[0] = t;
  } else {
    t = $[0];
  }
  let p;
  if ($[1] !== count) {
    p = <p>{count}</p>;
    $[1] = count;
  } else {
    p = $[1];
  }
  return <div>{t}{p}</div>;
}
```

`ExpensiveChild` is created once and reused - its props never change, so its React element identity stays stable, preventing unnecessary re-renders.

### Real-World Deal-Breakers
- **Mutating values during render** → compiler cannot prove safety → bailout.
- **Optional chaining on refs during render** → bailout.
- **`try/catch` wrapping render expressions** → bailout.
- **Class component patterns** → bailout (compiler targets function components).
- **Destructuring props into another object** → can lead to under-optimized components (known issue).
