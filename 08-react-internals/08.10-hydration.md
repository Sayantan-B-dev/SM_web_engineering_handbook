### What Hydration Is
Server sends HTML (fast, viewable, no JS interactivity). Then React loads client JS and **hydrates**: it attaches event listeners and component state to the existing DOM instead of rebuilding it.

```jsx
// Server-side HTML
<button class="primary">Click</button>

// Client-side after hydration: React attaches onClick, hooks, etc.
```

### Hydration Mismatch
If the server-rendered HTML differs from what the client would render, React throws a warning and re-renders the subtree.

```jsx
// ❌ Mismatch: server time ≠ client time
function Clock() {
  return <p>{new Date().toISOString()}</p>;
}

// ❌ Mismatch: random
function Avatar() {
  return <img src={`/avatar/${Math.random()}`} />;
}

// ❌ Mismatch: browser-only API
function Banner() {
  return <p>{typeof window !== 'undefined' ? 'Client' : 'Server'}</p>;
}
```

**Fixes:**
- Render on client only after mount (`useEffect`).
- Use `useId` for IDs that must match.
- Move browser-only content into a client-only subtree.
- `suppressHydrationWarning` for known-safe mismatches (e.g., timestamps).

### `useId`
```jsx
function Form() {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>Name</label>
      <input id={id} />
    </>
  );
}
```
Generates IDs that are stable across server and client.

### Effects After Hydration
- `useLayoutEffect` runs during hydration commit.
- `useEffect` runs after.
- Both run **after** hydration completes for that subtree.

### Real-World Deal-Breakers
- **Using `window`, `document`, `localStorage` during render** → mismatch on server.
- **Non-deterministic content (Date, Math.random)** → mismatch.
- **Nested invalid HTML** → browser "fixes" HTML, causing mismatch.
- **`dangerouslySetInnerHTML` differences** → mismatch.
- **Hydration errors cost the whole subtree** → React may client-render it from scratch, defeating SSR's purpose.
