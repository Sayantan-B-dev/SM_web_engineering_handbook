### Why Scheduling Exists
Browsers run JS on a single main thread. Long tasks (>50ms) block input, animation, and paint. React's scheduler breaks render work into small chunks and yields between them so the browser can stay responsive.

### The Work Loop With Deadline
```
while (workInProgress && !shouldYield()) {
  workInProgress = performUnitOfWork(workInProgress);
}

if (workInProgress) {
  scheduleCallback(continueWork); // come back later
} else {
  commitRoot(); // all work done
}
```

`shouldYield()` returns true when React has used up its 5ms slice (or higher-priority work is pending).

### Priority Levels (React Scheduler)
| Priority | Use |
|----------|-----|
| `Immediate` | Synchronous, e.g., discrete input |
| `UserBlocking` | Clicks, key presses |
| `Normal` | Network responses, transitions |
| `Low` | Analytics, prefetch |
| `Idle` | Anything that can wait indefinitely |

Higher priority work interrupts lower priority work. Lower-priority render work is discarded and restarted with the new state if needed.

### Real-World Deal-Breakers
- **Blocking the scheduler with synchronous work** → your own long tasks still block the thread; use Web Workers.
- **Assuming `useEffect` runs immediately after render** → passive effects may be deferred.
- **Heavy work in event handlers** → scheduler can't help; break it up yourself.
- **`flushSync` in hot paths** → forces synchronous commit, defeats scheduling.
