## 8.12 React Scheduling (Practical Guide)

### The Practical Model
You don't call React's scheduler directly. You **label** updates:
- Default → urgent (`NormalPriority`).
- Discrete input → sync (`SyncLane`).
- `startTransition` → transition lane.
- `useDeferredValue` → transition lane.

React decides when to render based on these labels and the browser's availability.

### Real-World Priority Choices

| Scenario | Update |
|----------|--------|
| Text input value | Urgent |
| Filter results list | Transition |
| Tab switch → new content | Transition |
| Analytics ping | Idle/low |
| Modal open | Urgent |
| Autocomplete list | `useDeferredValue` |

```jsx
function SearchPage() {
  const [input, setInput] = useState('');
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function onChange(e) {
    setInput(e.target.value);          // urgent
    startTransition(() => {
      setResults(search(e.target.value)); // transition
    });
  }

  return (
    <>
      <input value={input} onChange={onChange} />
      {isPending ? <Spinner /> : <Results items={results} />}
    </>
  );
}
```

### Interaction with Suspense
- A suspended transition keeps the old UI visible.
- A suspended urgent update shows the nearest fallback.

### Pitfalls
- Overusing transitions → harder to reason about timing.
- Fighting the scheduler with `flushSync` → jank.
- Expecting deterministic timing → scheduling depends on the browser.

### Real-World Deal-Breakers
- **Putting the input value in `startTransition`** → laggy typing.
- **Using `flushSync` for a "correction"** → defeats concurrency.
- **Suspending urgent updates** → whole app flashes fallback.
- **Assuming `isPending` covers the whole transition** → it's a heuristic; may flicker on fast transitions.
