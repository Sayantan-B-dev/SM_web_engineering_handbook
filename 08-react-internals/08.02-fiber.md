### Why Fiber Exists
React 15's reconciler was a **recursive, synchronous** walk of the tree. Once started, it could not be stopped. A large update would block the main thread for hundreds of milliseconds → dropped frames, janky input.

Fiber (React 16+) rewrote reconciliation as an **iterative, interruptible work loop**. Instead of recursion, each component becomes a "fiber" node with explicit pointers, and React can pause, resume, or discard work.

### What a Fiber Node Contains (Simplified)
```javascript
{
  tag: FunctionComponent,      // type of work
  type: ComponentFn,
  key: null,
  stateNode: null,             // DOM node or class instance
  return: parentFiber,         // upward pointer
  child: firstChildFiber,      // downward pointer
  sibling: nextSiblingFiber,   // horizontal pointer
  alternate: otherTreeFiber,   // the "other" tree (double buffering)
  pendingProps: props,
  memoizedProps: props,
  memoizedState: hooksLinkedList, // hooks for this fiber
  updateQueue: queueOfUpdates,
  flags: Placement | Update | Deletion, // what to do at commit
  lanes: priorityLanes,
}
```

### The Fiber Tree
Unlike the element tree (which is top-down only), the fiber tree has **three pointers**: `child`, `sibling`, `return`. This is what allows iterative (non-recursive) traversal.

```
       App
        │ child
       ┌▼────┐
       │ Nav │
       └─┬───┘
  child  │  sibling
       ┌▼─┐   ┌────┐
       │A │──▶│ B  │
       └──┘   └────┘
```

To traverse: go down `child`, when there's no child, go `sibling`, when there's no sibling, go back up via `return` and take its sibling.

### Two Trees (Double Buffering)
React keeps two fiber trees:
- **current** - what's on screen.
- **workInProgress (WIP)** - the tree being built.

Each fiber in one tree has an `alternate` pointer to the other. When the work-in-progress tree is complete, React swaps the pointer → instant "commit".

This is why React can compute a new tree without touching the visible tree, and why it can discard partial work without side effects.

### Work Loop
```
1. Take the next unit of work from the work-in-progress queue.
2. Perform the work (render the component, diff children).
3. If time is up (or higher priority work arrives):
     - Pause and yield to the browser.
4. Otherwise, continue with the next unit.
5. When work completes, commit all flags to the DOM.
```

### Real-World Deal-Breakers
- **Assuming render functions are called once** → in concurrent mode, they may be called, discarded, and called again.
- **Relying on `componentWillMount`/`componentWillReceiveProps`** → removed for this reason; they were impure, hard to interrupt.
- **Touching refs during render** → unsafe because renders can be interrupted.
- **Immutability matters** → mutation during render corrupts both trees.
