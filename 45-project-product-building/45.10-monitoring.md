## 45.8 Monitoring

### Subtopic Tree
- Error tracking (Sentry, LogRocket, Debugbear, Datadog)
- Performance monitoring (Core Web Vitals, Lighthouse)

### The Monitoring Stack

| Layer | Tool | What it monitors |
|-------|------|-----------------|
| **Error tracking** | Sentry, LogRocket, Datadog | Crashes, exceptions, slow API responses |
| **Performance** | Lighthouse, Web Vitals | Core Web Vitals (LCP, INP, CLS) |
| **Coverage** | CodeCov | Test coverage trends |
| **Session replay** | LogRocket, Sentry | User session replays for debugging |
| **Long tasks** | PerformanceObserver | Tasks > 50ms blocking the main thread |
| **Health checks** | Custom endpoint | Uptime, dependency health |

### Application Monitoring
Use Sentry, LogRocket, Debugbear or Datadog for real-time error tracking and performance monitoring in production. Capture crashes, slow API responses, and user session replays.

### Health Check Endpoint
```typescript
// src/app/api/health/route.ts
export async function GET() {
  const checks = await Promise.allSettled([
    db.ping(),
    redis.ping(),
    externalApi.healthCheck(),
  ]);

  const healthy = checks.every(c => c.status === 'fulfilled');
  return Response.json(
    { status: healthy ? 'ok' : 'degraded', checks },
    { status: healthy ? 200 : 503 }
  );
}
```
Add a health-check route - you'll need it for both the CI pipeline and production monitoring.

### CodeCov: Test Coverage Enforcement
Integrating CodeCov into your development workflow, often as part of a CI/CD pipeline, allows you to visualize how much of your code is covered by tests. Set thresholds to prevent merging PRs that reduce coverage.

### DORA Metrics
- **Deployment Frequency**: How often you deploy.
- **Lead Time for Changes**: Commit → production.
- **Change Failure Rate**: % of deploys causing incidents.
- **MTTR**: Mean time to restore.

### Deeper Explanation: Monitor The User's Experience, Not The Server's Comfort

Product monitoring answers three questions: are users succeeding? is the system healthy? what broke and for whom? That maps to a small, deliberate set of signals: business events (signup, checkout), Core Web Vitals by route and device, error rates and API latency, saturation metrics (connections, queue depth), and cost.

Then define the response: which of these pages a human, which triggers an alert, and what the runbook is. Dashboards without alerting and ownership are decoration; alerts without runbooks generate fatigue.

### Additional Pitfalls
- **Server metrics without user metrics.** Healthy servers can host a broken checkout.
- **Percentiles missing.** Averages hide the tail that users feel.
- **No route or device segmentation.** "The site is slow" cannot be acted on.
- **Alerting on causes instead of user-visible symptoms.** It creates noise and misses real failures.
- **No ownership.** Unowned dashboards rot and unowned alerts get muted.

### Real-World Deal-Breakers
- **No error tracking** → you find out about bugs from user complaints, not alerts.
- **No performance monitoring** → you don't know your LCP is 8 seconds until conversions drop.
- **No health checks** → you don't know if your database is down.
- **No coverage thresholds** → test coverage silently degrades over time.
