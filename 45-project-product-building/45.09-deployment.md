### The Deployment Pipeline
A reliable deployment and monitoring strategy ensures that React applications are shipped safely, securely, and with confidence. This involves enforcing code quality before merge, automating deployments, and continuously monitoring performance in production.

```text
Pre-commit:   Husky runs linting & type checks
     ↓
Pull Request: CI runs tests, coverage, and lint checks
     ↓
Build:        Automated pipeline builds production bundles
     ↓
Deploy:       Preview per PR → Staging → Production
     ↓
Post-Deploy:  Monitoring + performance audits
```

### Pre-commit Hooks
Run linting (ESLint, Prettier) and type checking (TypeScript) automatically before committing. Catch errors early and enforce consistency across the codebase. Tooling: Use **Husky** for easy setup with Git hooks.

### Secrets Management
Store secrets and environment-specific values in `.env` files or secret managers (Vault, AWS Secrets Manager). Keep them out of version control. You can use tools like `git-secrets` or GitHub's secret scanning to prevent accidental leaks.

### Recommended CI/CD Workflow
1. **Pre-commit**: Husky runs linting & type checks.
2. **Pull Request**: CI runs tests, coverage, and lint checks.
3. **Build & Deploy**: Automated deployment pipeline builds production bundles.
4. **Post-Deployment**: Monitoring + performance audits.

### Rollback Procedures
Every deployment should have a documented rollback procedure. For content-hashed assets: upload new assets to CDN, update `index.html` to reference new entry points. Rollback means pointing the HTML at the previous set of hashes. Keep old assets for at least 30 days.

### Deeper Explanation: Deployment Should Be Boring

Boring means: automated, repeatable, observable, and reversible. The pipeline that delivers that has four properties â€” one artifact promoted across environments, migrations run ahead of code with backward compatibility, progressive rollout with health signals, and a one-command rollback.

For frontend apps the extra pieces are cache correctness (immutable hashed assets, short-cached HTML), preview environments for review, and feature flags to separate deploy from release. The measure of a good deployment process is how uneventful it is at 17:00 on a Friday.

### Additional Pitfalls
- **Environment-specific builds.** What you tested is not what you shipped.
- **Migrations coupled to code deploys.** Additive-first (expand/contract) avoids the lockstep break.
- **No rollback rehearsal.** The first rollback is the worst time to learn the procedure.
- **Silent deploys.** Announcements and observability windows are part of deployment.
- **Manual steps in the runbook.** Every manual step is a future incident.

### Real-World Deal-Breakers
- **No pre-commit hooks** → lint errors and type errors reach CI (or production). Use Husky.
- **No rollback plan** → a bad deploy becomes an emergency. Document and test rollback procedures.
- **Secrets in version control** → API keys leaked in git history. Use `git-secrets` or GitHub secret scanning.
- **No staging environment** → every deploy is a production experiment. Use staging for validation.
