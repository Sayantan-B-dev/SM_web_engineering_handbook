## 45.6 Scalability

### Subtopic Tree
- Definition: the ability of a system to handle growing amounts of work
- Vertical scaling vs horizontal scaling
- Scalability dimensions: users, data, requests, teams
- Scalability bottlenecks: database, network, memory, CPU
- Design for 10x, not 1000x (premature scaling)
- The scalability spectrum: from MVP to production to hypergrowth
- Load testing and capacity planning

### The Scalability Dimensions
Scalability is not one thing. A system scales along multiple independent axes:

| Dimension | What grows | Bottleneck |
|-----------|-----------|-----------|
| **Users** | Concurrent users | Connection limits, session management |
| **Data** | Records, storage | Query performance, index size |
| **Requests** | API calls per second | Throughput, rate limits |
| **Teams** | Developers, teams | Coordination overhead, architecture boundaries |

### Design for 10x, Not 1000x
The most common scalability mistake is **premature scaling** - building for a scale you don't have yet. A system that works for 100 users can usually be scaled to 10,000 with reasonable effort. Building for 1,000,000 before you have 100 is waste.

```text
MVP stage (0-1K users):      Single server + managed database
Growth stage (1K-100K):      Load balancer + read replicas + caching
Scale stage (100K-1M):       Sharding + CDN + queue-based processing
Hypergrowth (1M+):           Distributed systems + multi-region
```

### Load Testing & Capacity Planning
- **Load testing**: simulate concurrent users to identify bottlenecks.
- **Stress testing**: push beyond expected load to find breaking points.
- **Capacity planning**: estimate resources needed for projected growth.
- **Performance budgets**: set thresholds (e.g., API response < 200ms at p95) and alert when breached.

---

### Deeper Explanation: Find The First Bottleneck, Then Fix It

Scalability is not a general property; it is a series of specific limits met in order. The engineering habit is to name the next limit before it is hit: database connections, a single-writer table, an unindexed query, a cache miss storm, a bundle-size regression, a synchronous third-party call, or a per-user quota.

| Layer | First bottleneck | Fix |
|---|---|---|
| Client | Bundle size, long tasks | Code splitting, workers, virtualisation |
| API | Connections, N+1 queries | Pooling, batching, caching |
| Database | Indexes, locks, write throughput | Keyset pagination, partitioning, replicas |
| Infrastructure | Single instance limits | Horizontal scaling, CDN, queueing |
| Cost | Per-request cost | Cache, batch, precompute |

### Additional Pitfalls
- **Scaling components that are not the bottleneck.** Effort with no effect; measure first.
- **Caching to hide a slow query.** It buys time and adds staleness bugs; fix the query.
- **No load profile.** Without realistic concurrency assumptions, capacity planning is guesswork.
- **Ignoring cost per user.** A scalable system can still be unprofitable.
- **Skipping the boring fixes.** Indexes and connection pooling solve most early scaling problems.

### Real-World Deal-Breakers
- **Premature scaling** → building for 1M users before you have 100 wastes engineering time.
- **No monitoring** → you don't know your system is breaking until users complain.
- **Database as bottleneck** → every query is a full table scan. Add indexes before adding servers.
- **Ignoring organizational scalability** → code that works for 5 developers breaks at 50. Architecture boundaries matter.
