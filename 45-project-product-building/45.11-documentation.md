## 45.9 Documentation

### Subtopic Tree
- README.md (the entry point)
- CONTRIBUTING.md (how to contribute)
- SECURITY.md (security policy)
- CHANGELOG.md (release history)
- CODE_OF_CONDUCT.md (community standards)
- Issue and PR templates
- Architecture Decision Records (ADRs)
- The Diátaxis framework (tutorials, how-to, reference, explanation)
- docs-as-code approach

### The Essential Documentation Files

| File | Purpose | Priority |
|------|---------|----------|
| **README.md** | Project overview, quick start, usage | **Required** |
| **CONTRIBUTING.md** | How to contribute, PR workflow | **Required** |
| **CHANGELOG.md** | Release history, breaking changes | **High** |
| **SECURITY.md** | How to report vulnerabilities | **High** |
| **CODE_OF_CONDUCT.md** | Community standards | **Medium** |
| **LICENSE** | Legal terms | **Required** |
| **Issue/PR templates** | Structured contributions | **High** |

### README Essentials
`makeareadme.com` and the `awesome-readme` corpus identify mandatory README sections as: project name + one-line description, badges (CI status, license), brief "what is this?", installation/quick-start, usage examples, contributing pointer, and license.

### CONTRIBUTING.md
The CONTRIBUTING.md file tells potential contributors how to participate: workflow for submitting pull requests, branch naming and commit message conventions, testing requirements and code style checks. A clear CONTRIBUTING.md reduces friction and encourages first-time contributors. Include templates for issues and PRs where possible.

### The Diátaxis Framework
Organize documentation into four types:

| Type | Purpose | Example |
|------|---------|---------|
| **Tutorial** | Learning-oriented | "Getting started in 10 minutes" |
| **How-to** | Task-oriented | "How to configure authentication" |
| **Reference** | Information-oriented | "API reference" |
| **Explanation** | Understanding-oriented | "Why we chose tRPC over GraphQL" |

Keep docs in the repo, next to the code, so they version with it and rot less.

---

### Deeper Explanation: Docs Are Read Under Pressure

Documentation earns its place when it answers a question someone actually has at the moment they have it: how do I run this? why does this exist? what do I do when it breaks? The genres are distinct and should be separate:

| Genre | Question | Form |
|---|---|---|
| README / onboarding | How do I get started? | Steps that work from a clean machine |
| Reference | What does this option do? | Generated from types where possible |
| Guides / how-to | How do I do X? | Task-oriented with runnable examples |
| ADRs / design notes | Why is it like this? | One page per decision |
| Runbooks | What do I do during an incident? | Checklist with links and commands |

### Additional Pitfalls
- **Docs written once and never owned.** They drift and mislead.
- **Examples that do not compile.** Extract and test them.
- **One giant wiki page.** Readers cannot find the section they need.
- **No runbooks.** Incident response becomes improvisation.
- **Documentation for its own sake.** Write for a specific reader and question.

### Real-World Deal-Breakers
- **No README** → the repo is a mystery. No one knows what it does or how to use it.
- **No CHANGELOG** → users don't know what changed between versions.
- **Docs not versioned with code** → docs rot within weeks. Keep docs in the repo.
- **No CONTRIBUTING.md** → contributors don't know how to contribute. They leave.
