### What a Prototype Is (and Is Not)
A prototype is an **interactive model of a product** that teams build to test ideas, validate design decisions, and gather user feedback before investing in full-scale development. Prototypes range from hand-drawn paper sketches to fully interactive digital simulations.

A prototype is **not** a deliverable. It is a hypothesis. Kara Pernice calls a prototype "a hypothesis, a candidate design solution." You are not making a thing to show. You are asking a question and watching a real person answer it.

### The Three Rs of Prototyping
When we prototype, we embrace the three Rs: **rough, rapid, and right**. We keep prototypes rough, so that the people we design with feel comfortable providing honest feedback. We move rapidly, getting in as many reps as we can to open up creative possibilities. And we work very hard to get it right, creating lo-fi designs that test for just one variable at a time.

```text
Rough:  Ripping up code is expensive. Ripping up a piece of paper costs nothing.
Rapid:  A full prototype-and-test round takes less time than one polished screen.
Right: Test for one variable at a time. A beautiful design can distract from a less-than-ideal experience.
```

### Fidelity Levels

| Fidelity | When to use | What it tests |
|----------|-------------|---------------|
| **Low** (paper sketches) | Early exploration | Does the flow hold together? |
| **Medium** (interactive wireframes) | Refining flows | Is navigation intuitive? |
| **High** (code-backed simulations) | Pre-development validation | Does the experience feel right? |

Fidelity follows the question, not the calendar. If your question is "does this flow hold together," a paper sketch answers it. If your question is "can people read this type at this size," you need the visuals to be real.

### The StartFlow Method (2026)
StartFlow is a structured method that helps non-specialized professionals create MVP prototypes using the **wireflow technique** - a combination of wireframes and user flows. It consists of three steps: (i) organizing features; (ii) building wireflows; and (iii) verifying and refining them based on usability heuristics. Experiment results showed that participants who used StartFlow created clearer prototypes, adhered to user stories, and presented fewer usability defects.

### Deeper Explanation: Prototype To Answer A Question

A prototype is an experiment with a stated question: is this interaction understandable? Does the layout work with real data? Can this integration work at all? Choosing the fidelity follows from the question â€” a paper sketch answers "is the flow clear", a clickable mock answers "can users find it", a technical spike answers "is it feasible".

Rules that keep prototypes useful: time-box them, use throwaway data paths where possible, state explicitly that the code will not ship (or commit to hardening it), and record the findings in writing. The failure mode is prototype code silently becoming production code, carrying hardcoded data, absent error handling, and no tests.

### Additional Pitfalls
- **Prototype code promoted to production.** It carries debt nobody accounted for.
- **No stated question.** The prototype becomes an open-ended build.
- **High fidelity before the flow is validated.** Polish on the wrong idea.
- **Findings not written down.** The learning disappears with the prototype.
- **Prototyping with production data.** Privacy and safety risk with no benefit.

### Real-World Deal-Breakers
- **Polish too early** → once you invest hours in a design, it's harder to give it up if it doesn't work. You get married to the idea.
- **Hi-fi prototype treated as finished** → an executive sees the polish and says "ship it." A rough sketch signals the work is still open.
- **Polishing screens before checking the flow** → teams get stuck polishing one screen in isolation while the path between screens is still broken.
- **Treating prototyping as a one-time activity** → the most effective teams prototype early and iterate often - at least 3-5 rounds per major feature.
