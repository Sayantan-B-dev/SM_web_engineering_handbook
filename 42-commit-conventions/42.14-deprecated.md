### What Deprecated Means
Deprecation is a **warning**, not a removal. The functionality still works, but it's scheduled for removal in a future major version. The `Deprecation:` footer marks this without triggering a breaking change.

```bash
feat(api): deprecate v1 user endpoints

Deprecation: The /api/v1/users endpoint is deprecated and
will be removed in v3.0. Use /api/v2/users instead.
Fixes #456
```

### The Deprecation Lifecycle
1. **Deprecation commit** → `Deprecation:` footer, no breaking change.
2. **Deprecation period** → consumers have time to migrate.
3. **Removal commit** → `BREAKING CHANGE:` footer, MAJOR version bump.

The `Deprecation:` footer is a **greppable marker across history** that lets a maintainer enumerate outstanding deprecations and confirm each is removed on schedule.

### Deeper Explanation: Deprecation Is A Bridge, Not A Graveyard

Marking something deprecated (`DEPRECATED:`, `@deprecated` in the type, or a runtime warning) starts a defined window: the API keeps working while consumers migrate, the docs point to the replacement, and telemetry (if available) shows whether anyone still uses it. Without an owner and an expiry, deprecations accumulate and the codebase carries two ways to do everything.

The mechanics that work: emit a warning once per session (not per call), document the replacement with an example, and keep the API in the public surface for at least one minor-plus-major cycle before removal.

### Additional Pitfalls
- **Deprecated in name only.** No replacement, no docs, no deadline â€” it will never be removed.
- **A warning on every call.** It floods logs and gets suppressed.
- **Removing in the same release as deprecating.** That is a breaking change, not a deprecation.
- **Deprecating without measuring usage.** You may be removing something users depend on.
- **No migration path in types.** `@deprecated` with a `@see` link is the cheapest guidance available.

### Real-World Deal-Breakers
- **Removing functionality without a deprecation period** → consumers have no time to migrate. Always deprecate first.
- **No `Deprecation:` footer** → deprecations are invisible in the changelog. Consumers don't know what's scheduled for removal.
- **Deprecation without a removal timeline** → the deprecated code lives forever. Specify when it will be removed.
