## ci

### Subtopic Tree
- What belongs in `ci:` (workflows, pipeline steps, caching, matrices, gates)

- Secrets and permissions in pipelines
- Caching strategy changes and their risk
- Test sharding, parallelism and flake handling
- Version pinning of actions and runners

### The Mental Model
`ci:` marks changes to the **delivery pipeline** â€” workflow files, action versions, caching keys, matrix strategy, required checks, deployment steps â€” where the product artifact is unchanged but the process that verifies and ships it changes. Keeping it separate matters because pipeline regressions are invisible to tests and can block everyone's work.

```yaml
# ci: cancel superseded runs, cache the package store, shard the E2E suite
concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }
steps:
  - uses: actions/setup-node@v4
    with: { node-version: 22, cache: pnpm }
  - run: pnpm install --frozen-lockfile
  - run: pnpm exec playwright test --shard=${{ matrix.shard }}/4
```

### Real-World Deal-Breakers
- **Cache keys that never invalidate.** Stale caches produce failures nobody can reproduce locally.
- **`cancel-in-progress` missing.** Double runs waste minutes and race on deploy targets.
- **New required checks added without team communication.** PRs stall with no explanation.
- **Secrets exposed to fork PRs.** The classic `pull_request_target` mistake.
- **Unpinned action versions.** Supply-chain risk plus silent behaviour change on a tag update.
