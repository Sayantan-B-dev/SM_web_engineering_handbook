### The Mental Model
`build:` covers changes that affect **how the project is compiled, bundled, or packaged** â€” dependency versions, bundler configuration, TypeScript target, Docker base images, CI release scripts that produce artifacts. The value of a distinct type is that a reviewer knows to look for artifact-level impact (bundle size, runtime compatibility, lockfile changes) rather than application behaviour.

```text
build(deps): bump vite from 5.4.1 to 6.0.0
build(vite): raise build target to es2022 and drop the legacy plugin
build(docker): pin node:22-alpine as the runtime base image
```

### Naming Boundary
- `build:` â†’ artifact or dependency changes with no product behaviour change.
- `ci:` â†’ pipeline changes that do not alter the artifact.
- `feat:`/`fix:` â†’ the dependency bump is incidental to a behaviour change.
- `chore:` â†’ repo maintenance that changes nothing buildable.

### Real-World Deal-Breakers
- **Dependency bumps hidden inside a `feat:` commit.** Reviewers miss runtime compatibility risk and cannot revert the bump alone.
- **Lockfile churn mixed with source changes.** It hides the real diff; bump separately.
- **Major bumps without release notes or tests.** A major upgrade is a behaviour change in disguise.
- **Build config changes without a bundle-size check.** You only notice in production.
- **`build:` used for CI-only changes.** It pollutes artifact history; use `ci:`.
