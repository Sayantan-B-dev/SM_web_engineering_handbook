## 42.5 Footer

### Subtopic Tree
- Optional structured key-value pairs
- Separated from body by a blank line
- Git trailer format
- `BREAKING CHANGE:` - the most important footer
- `Fixes`/`Closes`/`Resolves` - issue references
- `Refs` - issue references without closing
- `Co-Authored-By` - co-authors
- `Reviewed-By` - reviewers
- `Deprecation:` - deprecation notices
- Multiple footers

### The Footer Specification
The footer is optional and follows the body after a blank line. A commit can contain a footer which **must consist of one or more Git trailers**. Each trailer must start on its own line, using the format `<key><sep><value>`.

```bash
feat(api): add user authentication feature

This commit adds user authentication to the API.

BREAKING CHANGE: The login endpoint changed from /api/login
to /api/v1/login. All previous tokens are invalid.
Fixes #142
Co-Authored-By: Thomas Miller <thomas@example.com>
```

### Footer Separators
Each footer must consist of a word token, followed by either `:<space>` or `<space>#`, followed by a string value. This is inspired by the Git trailer convention.

```bash
# ✅ Colon + space
Fixes: #142

# ✅ Space + hash
Fixes #142

# ✅ Both are valid
```

### The `BREAKING CHANGE:` Footer
A commit that has the text `BREAKING CHANGE:` at the beginning of its footer, or contains the `!` symbol after the type/scope, **introduces a breaking API change** (correlating with MAJOR in Semantic Versioning).

```bash
# ✅ Using ! after type
feat!: send email when product is shipped

# ✅ Using ! after scope
feat(api)!: send email when product is shipped

# ✅ Using BREAKING CHANGE footer
feat: allow config to extend other configs

BREAKING CHANGE: The `extends` key in the config file is now
used to extend other config files.
```

### `!` vs `BREAKING CHANGE:`
- **`!`** - quick signal in the header. Tools can detect it immediately.
- **`BREAKING CHANGE:`** - detailed explanation in the footer. Required for the changelog.

**Best practice**: Use both. `feat(api)!: remove v1 endpoints` with a `BREAKING CHANGE:` footer explaining the migration path.

### `Deprecation:` Footer
A `Deprecation:` footer marks functionality as deprecated without removing it. It's a **greppable marker** that lets maintainers enumerate outstanding deprecations and confirm each is removed on schedule.

```bash
feat(api): deprecate v1 endpoints

Deprecation: The /api/v1/users endpoint is deprecated and
will be removed in v3.0. Use /api/v2/users instead.
Fixes #456
```

---

### Deeper Explanation: Footers Are Machine-Readable Metadata

Footers are the trailer block: `BREAKING CHANGE:`, `Refs:`, `Co-authored-by:`, `Reviewed-by:`, `Fixes #123`. They are parsed by tooling (changelog generators, release bots, GitHub's issue linking), so their format matters â€” `Token: value` or `Token #value`, one per line, after a blank line.

The most consequential ones: `BREAKING CHANGE:` (drives major bumps and appears first in release notes), issue references (auto-close and traceability), and co-authorship (attribution). Anything you want automation to see belongs in a footer, not in prose.

### Additional Pitfalls
- **Breaking changes described only in the body.** Tooling misses them and consumers are surprised.
- **Issue references without a keyword.** `#123` alone does not close or reliably link it.
- **Multiple `BREAKING CHANGE:` blocks with inconsistent wording.** Keep one, explicit, migration-oriented.
- **Trailers before the body.** Parsers expect them at the end.
- **Signed-off-by omitted where the project requires it.** A DCO check fails.

### Real-World Deal-Breakers
- **No `BREAKING CHANGE:` footer for a breaking change** → consumers upgrade without knowing their code will break.
- **`fix` with a `BREAKING CHANGE:` footer** → the type says patch, the footer says major. Contradiction.
- **Footer without a blank line before it** → Git doesn't recognize it as a trailer.
- **`Fixes #142` in the subject line** → clutters the subject. Put it in the footer.
