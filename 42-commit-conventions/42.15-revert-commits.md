### The `revert` Type
The specification's FAQ suggests a **`revert:` type** and a `Refs:` footer listing the reverted commit hashes instead of Git's default subject.

```bash
# Git's default revert message
Revert "feat(auth): add Google OAuth login"

This reverts commit abc1234.

# Conventional revert format
revert: remove Google OAuth login

Refs: abc1234
```

### The `Refs:` Footer
The `Refs:` footer lists the **full hash of the reverted commit**. Multiple hashes can be listed if multiple commits are reverted.

```bash
revert: remove broken rate limiter

Refs: abc1234
Refs: def5678
```

### When to Use `git revert` vs `git reset`

| Command | Effect | Safe for shared branches? |
|---------|--------|--------------------------|
| `git revert` | Creates a **new** commit that undoes changes | ✅ Yes |
| `git reset --hard` | **Discards** commits (rewrites history) | ❌ No |

**Rule**: Use `git revert` on shared branches. Use `git reset` only on local, unpushed commits.

---

### Deeper Explanation: Revert, Do Not Rewrite

`git revert` creates a new commit that undoes a previous one, which is the only safe way to undo a change that has been shared or deployed. ### Additional Pitfalls
- **Force-pushing to remove a commit.** History rewriting breaks every other clone and can lose work.
- **Reverting without a reason.** The next person repeats the change and the same failure.
- **Revert conflicts resolved carelessly.** A partial revert can leave inconsistent state.
- **Reverting a merge without `-m`.** Git needs the parent specified; mistakes here drop unrelated changes.
- **Never re-landing.** The revert is correct, but the feature still needs a plan and an owner.

### Real-World Deal-Breakers
- **`git reset --hard` on a shared branch** → rewrites history, breaks everyone who pulled.
- **Revert without a `Refs:` footer** → no trace of what was reverted.
- **Revert of a revert** → `revert: revert "feat: add feature"` - confusing. Use `feat: re-add feature` instead.
