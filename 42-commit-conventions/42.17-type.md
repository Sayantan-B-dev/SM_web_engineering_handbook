## 42.1 Type

### Subtopic Tree
- The type is required and lowercase
- `feat` - new feature (MINOR)
- `fix` - bug fix (PATCH)
- `docs` - documentation only
- `style` - formatting, whitespace
- `refactor` - code restructuring
- `perf` - performance improvement (PATCH)
- `test` - tests
- `build` - build system, dependencies
- `ci` - CI/CD configuration
- `chore` - routine maintenance
- `revert` - revert a previous commit
- Additional types (custom types are allowed)

### The Type Specification
A commit message **must be prefixed with a type**, which consists of a noun - `feat`, `fix`, etc. - followed by an optional scope and an optional `!` symbol.

```bash
# ✅ Correct - lowercase type
feat: add voice input to chat panel
fix: resolve race condition in debounce timer

# ❌ Wrong - uppercase type
FEAT: add voice input
Fix: resolve race condition

# ❌ Wrong - empty type
: add voice input
```

### Type Semantics and SemVer Impact

| Type | Description | SemVer Bump |
|------|-------------|-------------|
| `feat` | A new feature | **MINOR** |
| `fix` | A bug fix | **PATCH** |
| `perf` | Performance improvement | **PATCH** |
| `docs` | Documentation only changes | None |
| `style` | Formatting, whitespace (no code meaning change) | None |
| `refactor` | Code change that neither fixes a bug nor adds a feature | None |
| `test` | Adding or correcting tests | None |
| `build` | Changes to build system or external dependencies | None |
| `ci` | Changes to CI configuration files and scripts | None |
| `chore` | Routine tasks (dependencies, merging) | None |
| `revert` | Reverts a previous commit | None |

### Choosing the Right Type
```bash
# ✅ feat - new functionality visible to users
feat(auth): add Google OAuth login

# ✅ fix - corrects broken behavior
fix(api): handle token refresh errors

# ✅ refactor - no behavior change, but code is restructured
refactor(database): simplify user queries

# ✅ perf - measurable performance improvement
perf(list): use FlashList for large datasets

# ❌ Wrong - "add logging" is not a feature
feat(logging): add log statements

# ✅ Correct - logging is a chore
chore(logging): add debug log statements
```

The line between `refactor` and `perf` is **measurement**. A refactor changes structure. A perf commit improves a measured metric. If you didn't measure it, it's a refactor.

### Custom Types
The specification allows **additional types beyond `feat` and `fix`**. The `@commitlint/config-conventional` config recommends `build`, `chore`, `ci`, `docs`, `style`, `refactor`, `perf`, `test`, and `revert`.

Some projects add domain-specific types:
- `deprecate` - deprecating functionality (Blockly uses this)
- `release` - release-related changes (Blockly uses this)
- `wip` - work in progress (discouraged in shared branches)

### Deeper Explanation: Type Is A Promise About Impact

The `type` in `feat(scope): summary` answers "what kind of change is this?" and, with Conventional Commits tooling, decides the version bump and the changelog section. That is why the mapping matters more than the naming: `feat` â†’ minor, `fix` â†’ patch, anything with `BREAKING CHANGE:` (or `!`) â†’ major.

| Type | Meaning | Version effect |
|---|---|---|
| `feat` | New capability | minor |
| `fix` | Corrects incorrect behaviour | patch |
| `perf` | Performance only, behaviour unchanged | patch |
| `refactor` | Restructure, behaviour unchanged | none |
| `docs`/`test`/`build`/`ci`/`chore` | Non-product changes | none |

### Additional Pitfalls
- **`chore` used for everything.** Automation and readers lose the distinction that makes the type useful.
- **`feat` for internal work.** Version bumps accumulate with nothing for users.
- **`fix` without a regression test.** The patch label implies the bug is genuinely closed.
- **Inconsistent casing/pluralisation.** `Fix`, `features`, `bugfix` break parsers and habits.
- **Breaking changes unmarked.** Downstream consumers get a minor bump and a broken build.

### Real-World Deal-Breakers
- **`fix` for a breaking change** → consumers don't know their code will break. Use `fix!` or a `BREAKING CHANGE:` footer.
- **`feat` for a refactor** → the changelog lists a "new feature" that doesn't add functionality.
- **`chore` for everything** → `chore` becomes a junk drawer. Types lose their meaning.
- **Uppercase types** → `commitlint` fails. `type-case` rule enforces lowercase.
- **Missing type** → `commitlint` fails. `type-empty` rule enforces non-empty.
