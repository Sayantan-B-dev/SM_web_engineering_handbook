## 42.3 Summary (Subject Line / Description)

### Subtopic Tree
- The description is required
- Imperative mood
- Lowercase (unless proper noun)
- No period at the end
- Maximum length (50-72 characters)
- What to describe (the change, not the intent)
- `commitlint` subject rules

### The Description Specification
The description immediately follows the type/scope and colon. It is the **most-read part of the commit message** - it appears in `git log --oneline`, GitHub's commit list, and changelogs.

```bash
# ✅ Imperative mood, lowercase, no period
feat(auth): add Google OAuth login
fix(api): handle token refresh errors
docs(readme): update setup instructions

# ❌ Past tense
feat(auth): added Google OAuth login

# ❌ Capitalized
feat(auth): Add Google OAuth login

# ❌ Period at the end
feat(auth): add Google OAuth login.
```

### The Three Rules

**1. Imperative mood** - Use "add" not "added" or "adds". The convention is that your commit message should complete the sentence: "If applied, this commit will...".

**2. Lowercase** - The first word should be lowercase unless it's a proper noun. `commitlint`'s `subject-case` rule enforces this: sentence-case, start-case, pascal-case, and upper-case subjects all fail.

**3. No period** - `subject-full-stop` rule enforces that the subject does not end with a period.

### Length Limits

| Limit | Character count | Source |
|-------|----------------|--------|
| **Ideal** | 50 characters | Common convention |
| **Soft limit** | 72 characters | `git log --oneline` truncation |
| **`commitlint` default** | 100 characters | `@commitlint/config-conventional` |

The 50-character limit comes from the classic 50/72 rule: subject line under 50 characters, body wrapped at 72 characters. The 72-character limit is where `git log --oneline` starts truncating.

### What to Describe
Describe **the change**, not the intent. The diff shows what changed; the commit message explains why.

```bash
# ✅ Describes the change
fix(auth): resolve token refresh loop

# ❌ Describes the intent (vague)
fix(auth): make login work better

# ❌ Describes the process
fix(auth): try different approaches until it worked
```

---

### Deeper Explanation: The Subject Line Is The Only Guaranteed Read

Most readers see one line: PR lists, `git log --oneline`, changelogs, blame annotations. So the subject must be self-contained: imperative mood, under ~72 characters, no trailing period, and describing the effect rather than the mechanism.

The classic test: "If applied, this commit will ___". "Fix currency formatting for non-US locales" passes; "Fixes some formatting" fails. If a subject cannot fit, it usually means the commit contains more than one change â€” split it rather than truncating meaning.

### Additional Pitfalls
- **Past tense or gerunds.** "Fixed"/"Fixing" is inconsistent with tooling conventions.
- **Ticket ids as the whole subject.** `JIRA-1234` says nothing; put the id in the body.
- **Over 72 characters.** It truncates in tooling and hides the useful part.
- **Vague verbs.** "Update", "improve", "refactor stuff" are unactionable.
- **Multiple changes summarised with "and".** Split the commit.

### Real-World Deal-Breakers
- **"fix bug"** → what bug? Where? The subject is useless.
- **"WIP"** → never commit WIP to a shared branch. Squash before pushing.
- **"update"** → what was updated? Everything and nothing.
- **Subject over 72 characters** → truncated in `git log --oneline`. Use the body for details.
- **Past tense** → inconsistent history. Use imperative mood.
