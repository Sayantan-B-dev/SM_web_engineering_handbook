## 42.6 BREAKING CHANGE

### Subtopic Tree
- Definition: a change that breaks backward compatibility
- Correlation with MAJOR in SemVer
- Two ways to mark: `!` or `BREAKING CHANGE:` footer
- The footer description must explain the migration
- Breaking changes can be any type
- Changelog rendering

### What a Breaking Change Is
A `BREAKING CHANGE:` footer or `!` after the type/scope **introduces a breaking API change** (correlating with MAJOR in Semantic Versioning).

```bash
# ✅ Breaking change with ! - quick signal
feat!: remove Node 6 support

# ✅ Breaking change with footer - detailed explanation
feat: remove Node 6 support

BREAKING CHANGE: Refactored to use JavaScript features
not available in Node 6. Minimum Node version is now 18.
```

### The Migration Path
The `BREAKING CHANGE:` footer **must describe what changed about the API** and how consumers should migrate.

```bash
# ❌ Vague
BREAKING CHANGE: The API changed.

# ✅ Actionable
BREAKING CHANGE: The login endpoint changed from /api/login
to /api/v1/login. Update all client calls. Previous tokens
are invalid and users must reauthenticate.
```

### Breaking Changes Can Be Any Type
A `BREAKING CHANGE` can be part of commits of **any type**. A `refactor` can be breaking. A `chore` can be breaking.

```bash
refactor!: rename `user` module to `account`

BREAKING CHANGE: All imports from `@/user` must be updated
to `@/account`. Run `npx codemod rename-user-to-account` to
migrate automatically.
```

### SemVer Correlation

| Marker | SemVer Bump | Example |
|--------|-------------|---------|
| `fix` | PATCH | 1.2.3 → 1.2.4 |
| `feat` | MINOR | 1.2.3 → 1.3.0 |
| `BREAKING CHANGE:` or `!` | **MAJOR** | 1.2.3 → 2.0.0 |

---

### Deeper Explanation: Make The Break Impossible To Miss

A breaking change is any change that requires consumers to modify something: removed or renamed exports, changed defaults, altered response shapes, tightened validation, or a dropped peer range. Announce it in three places so it cannot be missed: `!` after the type/scope, a `BREAKING CHANGE:` footer with migration instructions, and a changelog entry that links to a migration guide.

```text
feat(client)!: require an explicit transport option

BREAKING CHANGE: createClient() no longer defaults to HTTP.
Migration: pass `transport: http(url)` or `transport: ws(url)`.
See docs/migration-v3.md for the full upgrade path.
```

### Additional Pitfalls
- **A silent break in a minor release.** The single most damaging convention failure.
- **`BREAKING CHANGE:` without instructions.** Consumers are stuck; link the migration guide.
- **Tightened validation treated as a fix.** Rejecting input that used to be accepted breaks clients.
- **Dropped dependency ranges.** Widening/narrowing peers can break installs; treat both as breaking when narrowed.
- **Batched breaks spread across releases.** Group them in one major to spare consumers repeated upgrades.

### Real-World Deal-Breakers
- **Marking a breaking change as `fix`** → consumers upgrade expecting a patch, their code breaks. **This is the single most dangerous commit convention mistake.**
- **`!` without a `BREAKING CHANGE:` footer** → the changelog has no migration notes. Consumers are stuck.
- **`BREAKING CHANGE:` without details** → "The API changed" is useless. Describe what changed and how to migrate.
- **Forgetting the blank line before `BREAKING CHANGE:`** → Git doesn't parse it as a trailer.
