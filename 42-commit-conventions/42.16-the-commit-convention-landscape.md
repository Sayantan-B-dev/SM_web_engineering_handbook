### Core Mental Model
A commit message is not just a note to yourself. It is a **communication artifact** read by:
- **Future maintainers** trying to understand why a change was made
- **Automated tools** generating changelogs and version bumps
- **CI/CD pipelines** deciding what to build and release
- **Reviewers** deciding whether to approve a PR
- **Git tooling** (blame, bisect, log) surfacing context

Conventional Commits is a **lightweight convention on top of commit messages** that provides an easy set of rules for creating an explicit commit history, which makes it easier to write automated tools on top of. This convention dovetails with SemVer, by describing the features, fixes, and breaking changes made in commit messages.

```text
Without convention:              With convention:
───────────────                  ─────────────────
"fixed stuff"                     fix(auth): resolve token refresh loop
"WIP"                             feat(ui): add dark mode toggle
"updates"                         docs(readme): update setup instructions
"asdf"                            refactor(api): extract user service
```

The first column is a diary. The second column is a **changelog, a versioning signal, and a review aid** - all in one.

### The Structural Format
```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```
This is the complete structure. The header is required; body and footer are optional.

---

### Deeper Explanation: The Convention Is A Team Instrument

Every convention (Conventional Commits, Angular style, custom types) is a trade between expressiveness and automation. The evaluation criteria are practical: does it let tooling decide version bumps and changelogs, does it make history searchable, and does it survive a deadline?

What determines success in practice is the enforcement point: commit-msg hooks (local, bypassable), CI on the commit range (reliable), and PR-title validation (essential for squash-merge workflows, because the title becomes the commit). Pick the smallest type vocabulary the tooling needs; every extra type is a decision people make wrong.

### Additional Pitfalls
- **Conventions with no consumer.** Overhead without automation; skip them until tooling exists.
- **Enforcing only via hooks.** Web-UI commits and `--no-verify` bypass; validate in CI.
- **Squash-merge repos ignoring PR titles.** The single most common way history breaks convention.
- **Overly granular types.** `style`, `format`, `lint`, `deps`, `types`, `wip` â€” each adds ambiguity.
- **No onboarding.** New contributors fail checks for reasons they cannot infer.

### Real-World Deal-Breakers
- **No convention** → every commit message is a different style. Automated tools cannot parse history. Changelogs are manual.
- **Convention without enforcement** → developers forget. Pre-commit hooks and CI checks are required.
- **Convention without understanding** → developers write `fix: stuff` instead of `fix(auth): resolve token refresh loop`. The type is correct but the content is useless.
- **Over-engineering the convention** → adding 15 custom types and 5 mandatory footers. The convention becomes a burden, not an aid.
