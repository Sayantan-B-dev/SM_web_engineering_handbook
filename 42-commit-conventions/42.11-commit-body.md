## 42.4 Body

### Subtopic Tree
- Optional multi-paragraph explanation
- Separated from description by a blank line
- Explain **what** and **why** (not how)
- Wrap at 72 characters
- Before/after format
- When to include a body
- `commitlint` body rules

### The Body Specification
The body is optional and follows the description after a **blank line**. It provides detailed explanation of the change.

```bash
feat(auth): add Google OAuth login

This commit adds support for signing in with a Google account.
Users can now click "Sign in with Google" on the login page.
The OAuth flow uses PKCE for security and stores the refresh
token in an HttpOnly cookie.

The implementation reuses the existing rate limiter and
validates the Google ID token server-side.

Fixes #142
```

### What to Include
- **What changed** - the new behavior, the fix, the refactor
- **Why it changed** - the problem it solves, the motivation
- **Context** - links to issues, design docs, or prior discussions
- **Before/after** - what the behavior was before and after

### The Before/After Format
```bash
fix(auth): resolve token refresh loop

Before this commit, the refresh token was requested on every
API call, causing a loop when the token was expired.
After this commit, the refresh token is only requested once
per session, and the access token is refreshed proactively
5 minutes before expiry.
```

### Line Wrapping
Body lines should be wrapped at **72 characters**. This ensures readability in terminal-based Git tools (which are typically 80 characters wide) and in `git log` output.

### When to Include a Body
- The change is non-trivial (a one-line fix doesn't need a body)
- The **why** is not obvious from the diff
- There's important context (issue links, design decisions)
- The change has side effects or migration notes

---

### Deeper Explanation: The Body Carries The Reasoning

The subject says what; the body says **why, and what else a reader needs**: the problem, the constraints, the approach considered and rejected, side effects, and how it was verified. Wrap at ~72 characters, separate from the subject with a blank line, and use bullet points for multiple points.

The practical test of a good body: could a reader six months from now, with no context, decide whether this change is still correct? If the body explains the reasoning, yes. Include links to issues, designs, and related commits, and note any follow-up work explicitly so it is not lost.

### Additional Pitfalls
- **Body restating the diff.** "Changed x to y" adds nothing beyond the code.
- **No mention of trade-offs.** The next reader repeats the debate you already had.
- **Missing verification notes.** How to reproduce the fix or its test is high-value.
- **Unformatted walls of text.** Use short paragraphs and bullets.
- **Hidden follow-ups.** Mention them in the body or open an issue.

### Real-World Deal-Breakers
- **No body for a complex change** → six months later, no one knows why the change was made.
- **Body that repeats the subject** → `fix: resolve token loop` followed by "This commit resolves the token loop." Useless.
- **Body without line wrapping** → one 500-character line. Unreadable in terminal.
- **Body that explains "how"** → the diff shows how. The body should explain why.
