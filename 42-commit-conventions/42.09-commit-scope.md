### What Scope Is
An optional scope may be provided after a type to give **additional contextual information**, contained within parentheses. For example: `feat(parser): add ability to parse arrays`.

```bash
# ✅ With scope
feat(auth): add Google OAuth login
fix(api): handle token refresh errors
docs(readme): update setup instructions
refactor(database): simplify user queries

# ✅ Without scope (when the change spans the whole project)
feat: add voice input to chat panel
docs: correct spelling of CHANGELOG
```

### Common Scope Conventions

| Scope | Meaning | Example |
|-------|---------|---------|
| `auth` | Authentication | `feat(auth): add passkey support` |
| `api` | API layer | `fix(api): handle rate limit errors` |
| `ui` | User interface | `feat(ui): add dark mode toggle` |
| `db` | Database | `refactor(db): normalize user schema` |
| `config` | Configuration | `chore(config): update ESLint rules` |
| `deps` | Dependencies | `chore(deps): upgrade React to 19.2` |
| `ci` | CI/CD | `ci(actions): add Playwright tests` |
| `docs` | Documentation | `docs(readme): update setup instructions` |

### When to Omit Scope
- The change spans multiple modules
- The change affects the entire project
- The scope is obvious from the type

```bash
# ✅ Scope omitted - affects entire project
docs: correct spelling in CHANGELOG

# ✅ Scope included - affects only auth
fix(auth): resolve token refresh loop
```

### Multiple Scopes
Some teams allow comma-separated scopes: `fix(api,ui): resolve button state`. This is **not part of the specification** and may fail `commitlint`'s default scope rules. Use a single scope or omit it.

---

### Deeper Explanation: Scope Is A Namespace, Not A Sentence

Scope names the area the change touches, and its main benefit is filtering: `git log --grep "scope(pricing)"` and changelogs grouped by area. Good scopes mirror real ownership boundaries â€” package names in a monorepo, feature folders in an app â€” so they stay stable over time.

Rules that keep scopes useful: one scope per commit (if you need two, split the commit), no scope for repo-wide changes, lowercase and kebab-case for multiword areas (`release-workflow`), and a documented allowed list if you enforce it with commitlint.

### Additional Pitfalls
- **Invented scopes every commit.** They defeat filtering; constrain to a known set.
- **Two scopes in one commit.** The change probably should have been two commits.
- **Scope used for the file name.** `scope(Button.tsx)` is noise; use the domain.
- **No scope on genuinely cross-cutting changes.** `refactor: ...` is honest; inventing a fake area is not.
- **Scopes that drift from the code structure.** They need periodic reconciliation.

### Real-World Deal-Breakers
- **Uppercase scope** → `commitlint`'s `scope-case` rule enforces lowercase.
- **Scope too vague** → `fix(app): fix bug` is useless. Scope should pinpoint the area.
- **Scope too specific** → `fix(user-service-v2-auth-handler): fix bug` is unreadable.
- **Scope inconsistency** → `auth` in one commit, `authentication` in another. Standardize scopes in `CONTRIBUTING.md`.
