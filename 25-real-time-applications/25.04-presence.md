### How Presence Works
Presence lets each connected client publish a small piece of state - called a "presence payload" - to a shared channel. The server stores each client's payload under a unique presence key and keeps a merged view of all connected clients. When any client subscribes, disconnects, or updates their presence payload, three events fire: `sync` (full state updated), `join` (new client), and `leave` (client stopped).

### Supabase Presence (Example)
```javascript
const channel = supabase.channel('room_01');

channel
  .on('presence', { event: 'sync' }, () => {
    const state = channel.presenceState();
    console.log('Online users:', Object.keys(state).length);
  })
  .on('presence', { event: 'join' }, ({ key, newPresences }) => {
    console.log('Joined:', key, newPresences);
  })
  .on('presence', { event: 'leave' }, ({ key, leftPresences }) => {
    console.log('Left:', key, leftPresences);
  })
  .subscribe(async (status) => {
    if (status !== 'SUBSCRIBED') return;
    await channel.track({
      userId: 'user-1',
      onlineAt: new Date().toISOString(),
    });
  });
```

### Presence as Derived Multi-Session State
Presence is a **viewer-specific projection, not a boolean on a user row**. It derives from leased device sessions, recent activity, explicit availability, room membership, privacy policy, and regional evidence. A phone, a laptop, and a tablet are three sessions - presence must reconcile them.

### TTL-Based Presence
```javascript
// Redis-backed presence with TTL
async function heartbeat(userId, deviceId) {
  const key = `presence:${userId}:${deviceId}`;
  await redis.setex(key, 150, Date.now()); // expires in 150 seconds
}

async function getOnlineUsers(roomId) {
  const keys = await redis.keys(`presence:*:*`);
  const online = [];
  for (const key of keys) {
    const ttl = await redis.ttl(key);
    if (ttl > 0) online.push(key.split(':')[1]);
  }
  return [...new Set(online)];
}
```

### Deeper Explanation: Presence Is A Distributed Liveness Problem

"Who is online, and what are they doing?" looks trivial and is not: connections drop silently, tabs duplicate, users appear offline while typing, and the truth only exists if something expires. The standard design has three parts:

1. **A heartbeated lease.** Each client writes `{ userId, connectionId, lastSeen, status }` with a short TTL (30-60 s), refreshed by heartbeats. State expires on its own â€” never rely on a clean disconnect message.
2. **Join/leave events built on that TTL.** Presence viewed is "active but idle" versus "offline", broadcast as deltas to interested subscribers.
3. **Awareness vs presence.** Presence is coarse (online/away/offline); awareness carries richer ephemeral state (cursor, selection, typing) with a much shorter TTL (5-10 s).

Deterministic wording matters as well: presence holds `lastSeen`, so the UI can print "active 2 minutes ago" without guessing.

### Additional Pitfalls
- **Multi-tab double-counting.** Key by user plus connection; a user is offline only when all their connections expire.
- **No TTL.** Crashed clients stay "online" forever.
- **Broadcasting full presence lists.** Fan-out grows as O(nÂ²); send deltas and let each client maintain its own table.
- **Typing indicators without expiry.** "Ada is typingâ€¦" forever; short TTLs with explicit clears.
- **Presence used as security.** Liveness is not authorisation; verify permissions independently.

### Real-World Deal-Breakers
- **Tracking cursor position with Presence** → Presence syncs state through the server and notifies all subscribers on every change. Rapid `track()` calls flood the channel. Use Broadcast for high-frequency updates.
- **No TTL on presence keys** → a client that disconnects without a clean close stays "online" forever. Use heartbeat + TTL.
- **Presence without multi-device reconciliation** → a user with 3 devices appears as 3 users. Derive presence from sessions.
- **No debounce on presence updates** → every keystroke triggers a presence sync.
