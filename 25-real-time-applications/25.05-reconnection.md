### Why Connections Drop
WebSocket connections break constantly: mobile network switches (Wi-Fi → cellular), laptop sleep/wake, server deploys (rolling restarts), load balancer health checks, proxy timeouts (60-120 seconds), and ISP routing changes (BGP updates). Any application that uses WebSockets without handling reconnection will break in production.

### Exponential Backoff with Jitter
```typescript
class ReconnectingWebSocket {
  private attempt = 0;
  private baseDelay = 500; // ms
  private maxDelay = 30_000; // 30 seconds
  private ws: WebSocket | null = null;

  connect() {
    this.ws = new WebSocket(this.url);

    this.ws.onclose = () => {
      const delay = this.calculateDelay();
      this.attempt++;
      setTimeout(() => this.connect(), delay);
    };

    this.ws.onopen = () => {
      this.attempt = 0; // reset on successful connection
    };
  }

  private calculateDelay(): number {
    const exponential = Math.min(
      this.baseDelay * Math.pow(2, this.attempt),
      this.maxDelay
    );
    // Jitter: randomize between 50% and 100% of exponential delay
    const jitter = 0.5 + Math.random() * 0.5;
    return exponential * jitter;
  }
}
```

**The jitter is not optional.** When a server restarts, every connected client disconnects at the same instant. Without jitter, all clients retry at exactly the same intervals - 500ms, 1s, 2s, 4s - and every retry wave hits the recovering server simultaneously. This is the **thundering herd problem**, and it can keep a server down longer than the original failure. Jitter spreads reconnection attempts across time.

### State Synchronization (The Hard Problem)
Exponential backoff solves the transport problem. The hard problem is what happens after the transport reconnects: **there is state on both sides of the connection, and it has diverged.** The server had subscriptions, presence information, a position in a message stream. The client had unacknowledged outbound messages and expectations about what data it should be receiving. A new TCP connection knows nothing about any of this.

**Two fundamental approaches:**

**Route reconnecting clients to the same server:** Requires sticky sessions (IP hash or cookie affinity) or a connection registry. Fast (state is in memory) but breaks on the most common reconnection scenario - server restart.

**Stateless with a recovery protocol:** Persist session state externally (Redis, database, distributed log). Assign each message a sequence number. Client tracks the last sequence number it received. On reconnect, client sends its last sequence number; server replays all messages after that. This is more resilient - any server can handle the reconnection - but requires a server-side message buffer and gap detection logic.

### Deeper Explanation: Reconnect Is The Feature, Not The Fallback

Every long-lived connection dies â€” laptops sleep, phones switch networks, proxies reap idle sockets, deploys restart servers. Reconnection therefore deserves a design, not a `setTimeout`:

- **Exponential backoff with jitter.** Base 500 ms-1 s, cap 30 s, multiply by a random 0.5-1.0 factor so a fleet of clients does not retry in lockstep after an outage.
- **Stop retrying when retrying is wrong.** A 401/403 or a schema rejection must wait for user action, not hammer the server.
- **Resync on reconnect.** Reconnect without reconciliation is the bug people ship: sequences, cursors, or a full refetch must close the gap.
- **State machine, not flags.** `idle â†’ connecting â†’ live â†’ reconnecting â†’ stopped`. Render different UI per state; never show a spinner for a dead socket.
- **Observability.** Count reconnects, reconnect latency, and resync size; a rising reconnect rate is an early incident signal.

### Additional Pitfalls
- **Immediate infinite retries.** Turns a 30-second blip into a self-inflicted denial of service.
- **No "you are offline" UI.** Users think the app is broken when it is the network.
- **Losing writes made while disconnected.** Queue them, deliver after resync, and handle conflicts explicitly.
- **Reconnecting with a stale cursor.** The server may have compacted history; validate the resume point and fall back to a snapshot.
- **No caps on the outbound queue.** A long outage with an eager producer drains battery and memory.

### Real-World Deal-Breakers
- **No jitter** → thundering herd. Every client retries simultaneously and keeps the server down.
- **No sequence numbers** → on reconnect, the client has no way to request the data it missed.
- **No buffering strategy** → you need to decide how long to buffer (seconds? minutes? hours?) and what to do when the gap is too large to replay.
- **Infinite retries without backoff** → client hammers the server, making recovery impossible.
