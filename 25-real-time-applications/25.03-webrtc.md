## 25.3 WebRTC

### Subtopic Tree
- Peer-to-peer communication (no server round-trip)
- Signaling (offer/answer via WebSocket)
- STUN/TURN servers
- ICE candidates
- Data channels (arbitrary data, ordered/unordered)
- Media tracks (audio/video)
- `RTCPeerConnection`, `RTCDataChannel`
- React integration (`useWebRTC`, `@conference-kit/react`)
- Use cases: video calls, screen share, P2P file transfer, collaborative editing

### Basic Data Channel
```javascript
const pc = new RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.l.google.com:19302' }] });

// Create data channel
const channel = pc.createDataChannel('chat', { ordered: true });
channel.onopen = () => channel.send('Hello from peer 1');
channel.onmessage = (e) => console.log('Received:', e.data);

// Signaling (via WebSocket to a server)
pc.onicecandidate = (e) => { if (e.candidate) signaling.send(e.candidate); };

// Create offer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
signaling.send({ type: 'offer', sdp: offer });

// On the other peer
pc.ondatachannel = (e) => {
  e.channel.onmessage = (msg) => console.log('Received:', msg.data);
};
```

### React Hook
```tsx
import { useWebRTC, useDataChannel } from '@conference-kit/react';

function Chat() {
  const { connection, createOffer } = useWebRTC({ signalingUrl: '/ws' });
  const { send, messages } = useDataChannel(connection, 'chat');

  return (
    <>
      {messages.map((m, i) => <p key={i}>{m}</p>)}
      <button onClick={() => send('Hello')}>Send</button>
    </>
  );
}
```

### Use Cases
- **Video/audio calls** - media tracks over WebRTC.

- **P2P file transfer** - data channels.
- **Collaborative editing** - data channels + CRDT.

### Deeper Explanation: P2P Shifts Cost From Bandwidth To Reliability

WebRTC gives you a directly connected, encrypted transport between two browsers, negotiated through a signalling channel you provide. The bandwidth champion of real-time â€” audio/video or bulk peer data never touches your servers â€” but it trades away reliability: NAT traversal fails for a meaningful fraction of pairs, networks change mid-session, and TURN relay is a paid resource that must exist.

The essential sequence: gather ICE candidates (host, server-reflexive via STUN, relayed via TURN), exchange SDP offers/answers, then DTLS/SRTP encrypts the chosen pair. Practical architecture:

- **Signalling stays thin**: a websocket that forwards offers, answers, and candidates. No business logic.
- **Always configure TURN.** Without it, restrictive networks (corporate, some mobile) fail entirely.
- **Handle renegotiation and ICE restart** when `connectionState` goes to `disconnected`/`failed`.
- **Decide SFU vs mesh early**: mesh works to ~4 peers, beyond that use a media server (SFU) or you saturate uplinks.

### Additional Pitfalls
- **Testing only on a LAN.** The interesting failures appear across NATs; test with a TURN-relayed peer.
- **No ICE restart.** Switching Wi-Fi to cellular mid-call kills the session.
- **Assuming unordered/lossy defaults.** Data channels default to ordered, reliable TCP-like semantics; use `maxRetransmits`/`ordered: false` if you need low latency more than delivery.
- **Unbounded peer count.** Mesh uplink grows quadratically; cap or move to an SFU.
- **Signalling used for state.** Keep it a dumb relay; session state belongs to your application layer.

### Real-World Deal-Breakers
- **No TURN server** → WebRTC fails behind symmetric NATs (corporate networks). 10-20% of connections need TURN.
- **No signaling fallback** → if the WebSocket signaling server goes down, no new connections can be established.
- **Unreliable data channel for critical data** → `{ ordered: false, maxRetransmits: 0 }` drops packets. Use ordered/reliable for chat.
- **No connection state handling** → `pc.onconnectionstatechange` must handle `disconnected`, `failed`, and `closed`.
