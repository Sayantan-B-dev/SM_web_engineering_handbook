### The Transport Selection Decision Gate
The single most important architectural decision in real-time is choosing the right transport. The decision gate is: **Does the client ever need to send data back on the same connection?** If no → SSE. If yes → does the app need strict in-order, reliable delivery? Yes → WebSocket. Does the app need unreliable delivery (drop old data rather than block)? Yes → WebTransport. Does the interaction never touch a server? → WebRTC.

| Need | Default |
|------|---------|
| Notifications, dashboards, feeds | SSE |
| Chat, cursor sync, multiplayer interaction | WebSocket |
| Live game state, telemetry (stale frame beats waiting) | WebTransport |
| Video/audio calls, direct browser-to-browser | WebRTC |
| Rich collaboration with presence | Managed platform or CRDT stack |

---

### Deeper Explanation: Pick The Transport From The Direction Of Data

Real-time is a set of transports with different shapes, and the choice follows from two questions: **which way does data flow**, and **does the server need to initiate?**

| Transport | Direction | Server-push | Good for | Costs |
|---|---|---|---|---|
| Short polling | Request/response | No | Rare updates, simple ops | Latency, wasted requests |
| Long polling | Request/response | Simulated | Legacy proxies, low volume | Connection churn |
| **SSE** | Server â†’ client | Yes | Feeds, notifications, LLM tokens, prices | One-way, connection limit per origin (HTTP/1.1) |
| **WebSocket** | Bidirectional | Yes | Chat, collaboration, games, presence | State, scaling, auth |
| **WebRTC** | Peer-to-peer | n/a | Voice/video, low-latency P2P | Signalling, TURN relay, complexity |
| WebTransport | Bidirectional (QUIC) | Yes | Low-latency with unreliable datagrams | Newer API, limited support |

Rule of thumb: if the client only needs to *receive*, SSE is simpler, HTTP/2-friendly, and auto-reconnects. If both directions are conversational and low-latency, use WebSocket. Reserve WebRTC for media or genuinely peer-to-peer topologies.

### Additional Pitfalls
- **WebSocket chosen by default.** Chat-like products often only need server push plus occasional POSTs; SSE wins on ops cost.
- **Polling with a 1 s interval as "real time".** It is latency plus load; use it only for genuinely low-value freshness.
- **Ignoring connection limits.** Six connections per origin on HTTP/1.1 make many tabs starve; HTTP/2+ or shared sockets fix it.
- **No reconnect story for any transport.** Every real-time connection will drop; the design must assume it.

### Real-World Deal-Breakers
- **Choosing WebSocket for server-to-client-only updates** → SSE is simpler, HTTP/1.1-compatible, has browser-native reconnect via `Last-Event-ID`, and works through virtually every proxy without special configuration.
- **Choosing SSE for bidirectional interaction** → SSE is unidirectional; client-to-server requires separate HTTP requests.
- **Ignoring transport fallback** → some enterprise networks block UDP/QUIC (WebTransport) or proxy WebSocket upgrades.
