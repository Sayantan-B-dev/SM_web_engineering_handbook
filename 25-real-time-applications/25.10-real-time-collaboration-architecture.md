### Architecture Pattern
A distributed, event-driven architecture using WebRTC, Socket.io, Node.js, and React.js is the standard for real-time collaborative programming environments. The solution adopts this stack to enable synchronous multi-user programming with instant change visibility.

### Typical Stack
```text
Client (React)
  ├── WebSocket (signaling, presence, chat)
  ├── WebRTC data channels (P2P file transfer, cursor sync)
  └── CRDT (Yjs, Automerge) for conflict-free document editing

Server (Node.js)
  ├── WebSocket server (ws, Socket.io)
  ├── Redis pub/sub (room-based fan-out across instances)
  └── Session registry (presence, room membership)

Storage
  └── Redis (presence TTL, message buffer)
  └── PostgreSQL (durable document snapshots)
```

### Room-Based Fan-Out
```javascript
// Redis pub/sub for multi-instance WebSocket scaling
import Redis from 'ioredis';

const pub = new Redis();
const sub = new Redis();

sub.subscribe('room:123');

sub.on('message', (channel, message) => {
  const roomId = channel.split(':')[1];
  const payload = JSON.parse(message);

  // Send to all clients in this room on this instance
  rooms.get(roomId)?.forEach((client) => {
    if (client.readyState === WebSocket.OPEN) {
      client.send(JSON.stringify(payload));
    }
  });
});

function broadcastToRoom(roomId, payload) {
  pub.publish(`room:${roomId}`, JSON.stringify(payload));
}
```

### Deeper Explanation: From Sockets To A Collaboration Stack

A collaborative feature is a layered system, and each layer has a single responsibility:

1. **Transport** â€” one socket per client (or one SSE plus fetches), with heartbeat, backoff, and resync.
2. **Session/room registry** â€” who is in a document, with leases for presence and permissions for writes.
3. **Document model** â€” server-authoritative state plus an ordered log of operations (or a CRDT structure).
4. **Concurrency control** â€” sequence numbers, idempotent operations, and a merge rule (LWW, OT, or CRDT).
5. **Persistence** â€” periodic snapshots plus the operation log, so replay is bounded.
6. **Delivery** â€” broadcast deltas to subscribers, with presence and awareness on separate, shorter-lived channels.
7. **Client reconciliation** â€” optimistic apply, ack/nack, rollback, and resync on reconnect.

The architecture question that decides everything: **does the server own the order?** If yes, you need OT or a server-side lock for text; if no, you need a CRDT and the client owns convergence.

### Additional Pitfalls
- **Broadcasting before persisting.** A crash then loses acknowledged edits; persist, then fan out.
- **Per-edit network round trips.** Batch operations per frame; the network is not your state store.
- **Awareness mixed into the document stream.** Cursors and typing at 60 Hz will drown real edits; separate channels and TTLs.
- **No snapshotting.** Replaying a month of operations on every load is an outage waiting to happen.
- **Ignoring per-document fan-out limits.** A viral document with 5 000 concurrent authors needs sharding or hierarchical fan-out.

### Real-World Deal-Breakers
- **No CRDT/OT for collaborative editing** → conflicts are unresolvable. One user's changes overwrite the other's.
- **P2P WebRTC without a fallback** → some networks block UDP. Use TURN or fall back to WebSocket relay.
- **No room isolation** → messages leak between rooms. Always scope broadcasts by room ID.
- **No presence debouncing** → cursor moves flood the channel. Use Broadcast for high-frequency updates, Presence for low-frequency state.
- **No message buffer for reconnect** → clients miss messages during reconnection. Buffer with sequence numbers.
