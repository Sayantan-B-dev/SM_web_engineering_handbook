## 25.7 Backpressure

### Subtopic Tree

### The Problem
A fast producer (server) sends messages to a slow consumer (client). Without backpressure, the server's outbound buffer grows unbounded, eventually exhausting memory.

### Watermark-Based Flow Control
```javascript
// From the Celeris WebSocket library
const cfg = websocket.Config{
  MaxBackpressureBuffer: 1024,  // max chunks buffered
  BackpressureHighPct: 90,      // pause inbound at 90% full
  BackpressureLowPct: 50,       // resume inbound at 50% full
  Handler: func(c *websocket.Conn) {
    // ...
  },
};
```
When the buffer fills past `BackpressureHighPct`, the engine pauses inbound delivery for this connection (TCP-level backpressure). When it drains below `BackpressureLowPct`, delivery is resumed.

### Drop Policies
```javascript
// Drop oldest (default) - keep the connection alive, drop stale messages
const backpressure = {
  policy: 'drop-oldest',
  maxBytes: 1_048_576, // 1MB
};

// Close on backpressure limit - shed slow clients entirely
const backpressure = {
  closeOnBackpressureLimit: true,
  maxBytes: 1_048_576,
};
```
The default shed-and-continue behavior keeps the connection alive and silently drops frames past the cap, which is correct when you don't want a slow client to tie up buffer memory indefinitely.

### Deeper Explanation: Consumers Are Always Slower Than Producers Eventually

Backpressure is the discipline of not accumulating unbounded work when the consumer cannot keep up. In the browser it appears in four places: outbound socket buffers, inbound high-rate message streams, Web Streams, and React state updates driven by events.

The governing principles:

- **Bounded queues only.** Every queue must have a maximum size and an explicit policy when full: drop oldest, drop newest, coalesce, or disconnect.
- **Coalesce before queueing.** For state-like updates (cursor position, price tick, progress), keep only the latest value â€” a queue of 500 intermediate cursor positions is waste.
- **Check before sending.** `WebSocket.bufferedAmount` and `desiredSize` on streams tell you the consumer is behind without guesswork.
- **Move what you cannot drop.** Critical events need an ordered, durable path (IndexedDB queue with acks), not an in-memory array.

### Extended Example: Coalescing Updates Instead of Queuing Them

```ts
// High-frequency source (mouse move, price tick) â†’ latest-value wins
function createCoalescer<T>(flush: (value: T) => void, intervalMs = 50) {
  let latest: T | undefined;
  let scheduled = false;

  return (value: T) => {
    latest = value;
    if (scheduled) return;
    scheduled = true;
    setTimeout(() => {
      scheduled = false;
      if (latest !== undefined) flush(latest);
      latest = undefined;
    }, intervalMs);
  };
}

const sendCursor = createCoalescer<{ x: number; y: number }>((pos) => socket.send(pos), 50);

// Critical path: durable outbox with acks instead of drop-on-full
async function enqueueCritical(msg: OutboundMessage) {
  await db.put('outbox', { ...msg, status: 'pending', createdAt: Date.now() });
  await flushOutbox();      // sends in order, removing each entry on ack
}
```

### Additional Pitfalls
- **Unbounded arrays as queues.** They grow until the tab is killed; always cap and choose a policy.
- **Sending every intermediate state.** Coalesce state-like updates; only discrete events need full fidelity.
- **Retry loops with no cap.** Retries amplify load exactly when the server is struggling.
- **Ignoring `bufferedAmount`.** Large payloads silently queue and delay every later message.
- **Applying backpressure only on the client.** The server needs per-connection limits and slow-consumer disconnects too.

### Real-World Deal-Breakers
- **No `maxBackpressure`** → a single slow client can exhaust server memory.
- **Drop newest instead of oldest** → for real-time data, stale messages are worse than missing messages. Drop oldest.
- **No backpressure metrics** → `platform.pressure.backpressuredConnections` tells you how many clients are slow. Without it, you're blind.
- **Blocking the producer** → blocking on a slow consumer stalls the entire server. Drop and continue.
