### Server-Side Heartbeat (WebSocket)
```javascript
const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (ws) => {
  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });

  ws.on('message', (data) => {
    // handle messages
  });
});

// Every 30 seconds: ping all clients, terminate dead ones
const interval = setInterval(() => {
  wss.clients.forEach((ws) => {
    if (!ws.isAlive) return ws.terminate();
    ws.isAlive = false;
    ws.ping(); // ping frame
  });
}, 30_000);

wss.on('close', () => clearInterval(interval));
```

### Client-Side Heartbeat
```javascript
class HeartbeatWebSocket {
  private pingInterval: number | null = null;
  private pongTimeout: number | null = null;

  connect() {
    this.ws = new WebSocket(this.url);

    this.ws.onopen = () => {
      this.startHeartbeat();
    };

    this.ws.onmessage = (event) => {
      if (event.data === 'pong') {
        clearTimeout(this.pongTimeout);
        return;
      }
      // handle normal messages
    };
  }

  private startHeartbeat() {
    this.pingInterval = setInterval(() => {
      if (this.ws?.readyState !== WebSocket.OPEN) return;
      this.ws.send('ping');
      // If no pong within 5 seconds, consider dead
      this.pongTimeout = setTimeout(() => {
        this.ws?.close();
      }, 5000);
    }, 30_000);
  }
}
```

### For SSE (Keep-Alive Comments)
```javascript
// Server sends a comment every 15 seconds
const keepAlive = setInterval(() => {
  res.write(': keep-alive\n\n');
}, 15_000);

req.on('close', () => clearInterval(keepAlive));
```

### Deeper Explanation: Two Layers Of Liveness

A heartbeat answers one question: *is this connection still usable right now?* TCP's own keepalive is too slow (minutes to hours) and proxies add their own idle limits (often 60 s), so applications send their own. There are two layers:

- **Transport heartbeat** â€” protocol-level ping/pong (WebSocket control frames, `: ping` comments for SSE) that keeps intermediaries from closing the connection and reveals half-open sockets quickly.
- **Application heartbeat** â€” a periodic authenticated message carrying useful state (presence, cursor position, cursor for resume). Exactly where the transport heartbeat is opaque.

Budget them together: send interval well under the proxy idle timeout (typically 15-30 s), and require a *pong within N intervals* before declaring failure. Correlation ids make latency measurement free: the heartbeat doubles as a latency probe.

### Additional Pitfalls
- **Only pinging from the client.** The server also needs to detect dead clients; do both directions.
- **Treating a missing pong as instant death.** Allow two or three missed intervals before tearing the socket down.
- **Hearty heartbeats.** A 1 s interval with a large payload across thousands of clients is real traffic; use the smallest message that suffices.
- **Overloading heartbeats with business logic.** Keep them cheap so a slow handler cannot mask liveness.
- **Ignoring mobile backgrounding.** Browsers freeze timers in background tabs; treat the resumed session as a fresh connection.

### Real-World Deal-Breakers
- **No heartbeat** → dead connections stay open; server resources leak.
- **Heartbeat interval > idle timeout** → proxy kills the connection before the heartbeat fires. Use 30s heartbeat for 60s idle timeout.
- **No pong timeout** → client sends ping but never detects that the server is dead.
- **Application-level ping/pong instead of protocol-level** → unnecessary overhead. WebSocket has built-in ping/pong frames.
