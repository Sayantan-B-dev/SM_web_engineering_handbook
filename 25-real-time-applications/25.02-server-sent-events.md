## 25.2 Server-Sent Events (SSE)

### Subtopic Tree
- Unidirectional server-to-client streaming
- `text/event-stream` MIME type
- `EventSource` API
- `Last-Event-ID` for reconnect + replay
- `retry:` field (browser reconnect delay)
- Event format (`data:`, `event:`, `id:`, `retry:`)
- Named events (`event: trade`)
- Connection limits (6 per domain on HTTP/1.1)
- HTTP/2 multiplexing (no limit)
- Proxy buffering issues
- Keep-alive comments (`: ping`)

### Client-Side API
```javascript
const source = new EventSource('/api/stream');

source.onopen = () => console.log('Connected');
source.onerror = (error) => console.error('Error:', error);

// Default event
source.onmessage = (event) => {
  console.log('Message:', event.data, 'ID:', event.lastEventId);
};

// Named event
source.addEventListener('trade', (event) => {
  console.log('Trade:', JSON.parse(event.data));
});

source.close();
```

### Server-Side (Node.js)
```javascript
app.get('/api/stream', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');
  res.setHeader('X-Accel-Buffering', 'no'); // disable nginx buffering

  res.write(': connected\n\n'); // comment, not an event

  const interval = setInterval(() => {
    res.write(`id: ${Date.now()}\n`);
    res.write(`event: trade\n`);
    res.write(`data: ${JSON.stringify({ symbol: 'BTC', price: 50000 })}\n\n`);
  }, 1000);

  req.on('close', () => clearInterval(interval));
});
```

### The Wire Format
```text
id: 42
event: trade
retry: 5000
data: {"symbol":"BTC","price":50000}

: this is a comment (keep-alive)

data: plain message

```

### Critical Proxy Headers
Every `text/event-stream` response must carry three proxy-safety headers: `Cache-Control: no-cache`, `X-Accel-Buffering: no`, and `Connection: keep-alive`. Without these, proxies buffer the response and events arrive in bursts instead of immediately.

---

### Deeper Explanation: SSE Is The Right Default More Often Than It Is Used

Server-Sent Events are a text protocol over HTTP: the client opens one long-lived GET, the server writes `data:` lines, and the browser delivers them as `message` events â€” with automatic reconnection and `Last-Event-ID` resumption built into the API. Because it is plain HTTP, SSE works through proxies, CDNs, and corporate networks that break WebSockets, and it needs no special server library.

The trade-offs to know: it is one-directional (client sends via normal requests), browsers limit connections per origin on HTTP/1.1 (use HTTP/2+), and each event is text (binary needs base64 or a different transport). For token streaming from LLMs, feeds, notifications, and progress updates, SSE is usually the simplest correct answer.

### Extended Example: Typed SSE Client With Resumption And Backoff

```ts
type FeedEvent = { seq: number; kind: 'price' | 'status'; value: string };

export function connectFeed(onEvent: (e: FeedEvent) => void) {
  let lastId: string | null = null;
  let attempt = 0;
  let closed = false;

  const open = () => {
    if (closed) return;
    const url = lastId ? `/api/feed?lastEventId=${lastId}` : '/api/feed';
    // credentials: same-origin cookies are sent by default; include for cross-origin
    const es = new EventSource(url, { withCredentials: true });

    es.onopen = () => { attempt = 0; };
    es.onmessage = (e) => {
      lastId = e.lastEventId || lastId;
      onEvent(JSON.parse(e.data) as FeedEvent);
    };
    es.onerror = () => {
      es.close();
      if (es.readyState === EventSource.CLOSED) return;   // avoid reopening on hard close
      const delay = Math.min(30_000, 1_000 * 2 ** attempt++) * (0.5 + Math.random());
      setTimeout(open, delay);
    };
  };

  open();
  return () => { closed = true; };
}
```

### Additional Pitfalls
- **Proxy buffering.** Compression or buffering middleware delays every event until the response closes; disable both for the stream route.
- **No heartbeat comment.** Idle connections get reaped by proxies; send `: ping\n\n` every 15-30 s.
- **Ignoring `Last-Event-ID`.** Without resumption, every reconnect loses the gap and the UI silently diverges.
- **Treating it as bidirectional.** Client â†’ server updates still need fetch/POST; do not simulate a socket.
- **Unbounded client count per origin on HTTP/1.1.** Six connections total; use HTTP/2+ or a shared worker multiplexing one SSE connection.

### Real-World Deal-Breakers
- **No `X-Accel-Buffering: no`** → Nginx buffers the entire response; events never stream.
- **No keep-alive** → Azure Load Balancer has a 4-minute idle timeout. Send a comment every <4 minutes.
- **No `Last-Event-ID` handling** → on reconnect, the client misses everything that happened while disconnected.
- **SSE over HTTP/1.1 with many tabs** → browser limit of 6 connections per domain. Use HTTP/2 or domain sharding.
- **Enabling response logging** → logging request/response bodies can buffer the stream.
