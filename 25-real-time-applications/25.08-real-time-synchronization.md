## 25.8 Real-Time Synchronization

### Subtopic Tree
- State sync after reconnect (sequence numbers, replay)
- Conflict resolution (CRDT, OT, last-write-wins)
- Optimistic updates + reconciliation
- Event ordering (server-assigned sequence numbers, timestamps)
- Idempotency (deduplication keys)
- Vector clocks / Lamport timestamps
- Snapshot + delta sync

### Sequence Numbers + Replay
```javascript
// Server: assign a monotonically increasing sequence number to every message
let sequence = 0;

function broadcast(message) {
  const envelope = {
    seq: ++sequence,
    payload: message,
    timestamp: Date.now(),
  };

  // Store in a ring buffer for replay
  messageBuffer.push(envelope);
  if (messageBuffer.length > 10_000) messageBuffer.shift();

  // Send to all clients
  clients.forEach((client) => {
    client.send(JSON.stringify(envelope));
  });
}

// On reconnect: client sends its last sequence number
function handleReconnect(client, lastSeq) {
  const missed = messageBuffer.filter((m) => m.seq > lastSeq);
  missed.forEach((m) => client.send(JSON.stringify(m)));
}
```

### Optimistic Updates + Reconciliation
```javascript
// Client sends an optimistic update immediately
const optimisticMessage = { id: tempId, text: 'Hello', status: 'sending' };
setMessages((prev) => [...prev, optimisticMessage]);

// Server assigns the real ID and broadcasts
ws.send(JSON.stringify({ type: 'message', tempId, text: 'Hello' }));

// On server acknowledgment: replace the optimistic message
ws.onmessage = (event) => {
  const { tempId, id, status } = JSON.parse(event.data);
  setMessages((prev) =>
    prev.map((m) => (m.id === tempId ? { ...m, id, status: 'sent' } : m))
  );
};
```

### Event Ordering
```javascript
// Server assigns monotonic sequence numbers, not timestamps
// Timestamps can go backward (clock skew); sequence numbers cannot
{
  "seq": 42,
  "type": "cursor_move",
  "payload": { "x": 100, "y": 200 },
  "timestamp": 1704067200000
}

// Client applies messages in sequence order
let lastSeq = 0;

function onMessage(envelope) {
  if (envelope.seq <= lastSeq) return; // duplicate, ignore
  if (envelope.seq > lastSeq + 1) {
    // Gap detected - request replay
    ws.send(JSON.stringify({ type: 'replay', from: lastSeq + 1 }));
    return;
  }
  lastSeq = envelope.seq;
  apply(envelope.payload);
}
```

### Deeper Explanation: Three Guarantees You Must Choose Between

A real-time sync layer can provide, at most, two of three properties cheaply: **low latency**, **strong consistency**, and **partition tolerance**. The practical vocabulary:

| Model | Guarantee | Cost | Use when |
|---|---|---|---|
| Server-authoritative broadcast | Server order wins | Latency to the server | Most apps; simplest correct |
| Last-write-wins | Deterministic conflict resolution | Silent lost updates | Coarse fields, settings |
| Optimistic local + reconcile | Instant UI, eventual truth | Rollbacks, flicker | Interactive forms, likes |
| CRDT | Conflict-free merge, offline-capable | Memory and complexity | Collaborative text, local-first |
| OT | Centralised ordering | Server transform complexity | Document editing with a server |

Most product features are best served by server-authoritative ordering with optimistic local updates and a monotonic sequence number for gap detection. Reach for CRDT only when offline editing with concurrent authors is genuinely required â€” the complexity is permanent.

### Additional Pitfalls
- **No sequence numbers.** You cannot detect gaps, duplicates, or out-of-order arrival; add `seq` per channel.
- **Optimistic updates with no rollback path.** Failed writes must visibly revert, with an explanation.
- **Clock-based ordering.** Client clocks drift; order by server-assigned sequence, not timestamps.
- **Full-state broadcasts.** They beat delta fan-out on tiny apps and destroy large ones; send deltas plus periodic snapshots.
- **No idempotency on retries.** Duplicate delivery is normal; make every write idempotent by client-generated id.

### Real-World Deal-Breakers
- **Using timestamps for ordering** → clock skew causes out-of-order application. Use server-assigned sequence numbers.
- **No idempotency keys** → retried messages are applied twice. Include a unique key and deduplicate.
- **No gap detection** → if messages arrive out of order (unreliable transport), the client applies them incorrectly.
- **No snapshot mechanism** → replaying 100,000 messages on reconnect is slow. Periodically send a snapshot + delta.
- **Last-write-wins for collaborative editing** → user A's and user B's changes conflict; one is silently lost. Use CRDT or OT.
