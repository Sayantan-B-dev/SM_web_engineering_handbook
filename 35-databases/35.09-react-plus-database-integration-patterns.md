### The Local-First Stack (React + SQLite WASM + PowerSync + Supabase)
The concept is simple: instead of asking a remote server for permission to change a number, your app writes state directly to a **local SQLite database running in the browser via WebAssembly**. A sophisticated background engine then handles the hard work of syncing those changes to the cloud and other devices.

**Three architectural components:**
1. **Client-side UI and database** - React + SQLite WASM
2. **Syncing engine** - PowerSync
3. **Database of record** - Supabase (managed Postgres)

```tsx
// React component subscribes to local SQLite
function TodoList() {
  const todos = useLiveQuery(
    () => db.selectFrom('todos').selectAll().execute()
  );

  async function addTodo(text: string) {
    // Writes to local SQLite immediately (no network)
    await db.insertInto('todos').values({ text, done: false }).execute();
    // PowerSync syncs to Supabase in the background
  }

  return <ul>{todos?.map(t => <li key={t.id}>{t.text}</li>)}</ul>;
}
```

### TanStack DB - Reactive Client Database
TanStack DB is a **client-side database powered by differential dataflow** that plugs into your existing `useQuery` calls. Load normalized collections once, let TanStack DB stream **millisecond-level incremental joins in the browser**. No rewrites.

```tsx
import { useLiveQuery } from '@tanstack/react-db';

function UserWithPosts({ userId }) {
  const { data } = useLiveQuery((q) =>
    q.from({ user: usersCollection })
      .where(({ user }) => eq(user.id, userId))
      .join({ posts: postsCollection }, ({ user, posts }) => eq(posts.userId, user.id))
  );

  // data updates incrementally as collections change
  return <div>{data.user.name} has {data.posts.length} posts</div>;
}
```

### TanStack Query + PostgreSQL
`@dotdo/tanstack` connects TanStack Query directly to PostgreSQL. Type-safe queries, automatic caching, optimistic updates, and offline-first sync - all with the patterns you already know. Smart caching, query key generation, stale time, GC.

### Prisma vs Drizzle

| Feature | Prisma | Drizzle |
|---------|--------|---------|
| Type safety | Generated client | TypeScript-first |
| Query style | `prisma.user.findUnique()` | `db.select().from(users)` |
| Migrations | Prisma Migrate | Drizzle Kit |
| Bundle size | Larger (query engine) | Smaller (no engine) |
| Edge support | Limited | Excellent |
| SQL-like | No | Yes |

**Prisma** is better for teams that want a high-level, declarative API. **Drizzle** is better for teams that want SQL-like control and edge compatibility.

### React Query for Database Caching
```tsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

function UserProfile({ userId }) {
  const queryClient = useQueryClient();

  const { data: user, isLoading } = useQuery({
    queryKey: ['user', userId],
    queryFn: () => fetch(`/api/users/${userId}`).then(r => r.json()),
    staleTime: 5 * 60 * 1000, // 5 minutes
    gcTime: 30 * 60 * 1000,   // 30 minutes
  });

  const updateUser = useMutation({
    mutationFn: (data) => fetch(`/api/users/${userId}`, {
      method: 'PATCH',
      body: JSON.stringify(data),
    }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['user', userId] });
    },
  });

  if (isLoading) return <Skeleton />;
  return <h1>{user.name}</h1>;
}
```

### Server Components + Server Actions (Next.js)

// Server Component - fetches directly from database
async function UserProfile({ userId }) {

    where: { id: userId },

async function updateUser(formData: FormData) {

    where: { id: formData.get('id') },
    data: { name: formData.get('name') },
  });
  revalidatePath('/profile');
}

### Deeper Explanation: From Table To Screen Without Leaking The Schema

The integration layer between a React app and a database has three responsibilities: shape the data for the client (contracts), control the access pattern (pagination, filtering), and keep types aligned end to end. The patterns that keep it maintainable:

- **A contract layer** â€” explicit response types (Zod/TypeScript) generated or written per endpoint; never expose table rows directly.
- **Keyset pagination** with opaque cursors so the client cannot construct invalid queries and the ordering stays stable.
- **Server-side projection** â€” return only the fields the screen needs; it is the cheapest performance win available.
- **Optimistic concurrency** â€” expose a `version`/`updatedAt` on edits so the client can detect conflicts and re-fetch.
- **Cache invalidation keys** â€” a stable `updatedAt` or version in responses lets the client cache confidently (TanStack Query keys derived from filters).
- **Aggregations where they belong** â€” computed in SQL (window functions) rather than in the client over a full dataset.

### Additional Pitfalls
- **Returning entire rows to the client.** Leaks internal columns and inflates payloads.
- **Offset pagination.** It drifts under writes and degrades on deep pages.
- **Client-side filtering over a full fetch.** It breaks at scale and hides an index problem.
- **Types duplicated by hand.** Drift is guaranteed; derive from one source.
- **No conflict handling on updates.** Two tabs overwrite each other silently.

### Real-World Deal-Breakers
- **No client-side database** → every read is a network round-trip. Use SQLite WASM or TanStack DB for local-first.
- **No sync engine** → local-first without sync is just a local database. Use PowerSync, ElectricSQL, or Replicache.
- **No React Query for server state** → manual `useEffect` + `useState` for every fetch. No caching, no deduplication.
- **No ORM/query builder** → raw SQL with string concatenation. SQL injection risk.
- **N+1 queries in React** → each component fetches its own data. Use `Promise.all` or React Query's `useQueries`.
