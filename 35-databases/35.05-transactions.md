### ACID Properties
A key advantage of SQL databases is their adherence to ACID properties, which are essential for applications requiring high data integrity and reliability.

| Property | What it guarantees | Failure without it |
|----------|-------------------|-------------------|
| **Atomicity** | All or nothing | Partial writes corrupt data |
| **Consistency** | Constraints always valid | Invalid data enters the database |
| **Isolation** | Concurrent transactions don't interfere | Race conditions, dirty reads |
| **Durability** | Committed data survives crashes | Data loss on power failure |

### Isolation Levels

| Level | Dirty Read | Non-Repeatable Read | Phantom Read | Performance |
|-------|-----------|---------------------|--------------|-------------|
| **Read Uncommitted** | Possible | Possible | Possible | Fastest |
| **Read Committed** (default) | No | Possible | Possible | Fast |
| **Repeatable Read** | No | No | Possible | Moderate |
| **Serializable** | No | No | No | Slowest |

PostgreSQL implements full ACID transactions with four standard SQL isolation levels. Read Uncommitted is mapped to Read Committed. Repeatable Read and Serializable are built on MVCC.

**The default isolation level is `READ COMMITTED`** - sufficient for most applications. `REPEATABLE READ` gives a snapshot at transaction start, which may see stale data. `SERIALIZABLE` guarantees full isolation at the cost of throughput.

### Transaction Best Practices
```sql
-- ✅ Short transactions
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- ❌ Long transaction - blocks other transactions, causes bloat
BEGIN;
-- ... 50 more operations ...
-- ... network call ...
-- ... user think time ...
COMMIT;
```

**The rule**: transactions should be as short as possible. A long-running transaction holds locks, prevents vacuum from cleaning dead tuples, and can cause catastrophic bloat.

### Deadlock Prevention
```sql
-- ❌ Deadlock-prone: different lock order
-- Transaction A: UPDATE users SET ... WHERE id = 1; UPDATE orders SET ... WHERE id = 2;
-- Transaction B: UPDATE orders SET ... WHERE id = 2; UPDATE users SET ... WHERE id = 1;

-- ✅ Consistent lock order prevents deadlocks
-- Both transactions: lock users first, then orders
BEGIN;
SELECT * FROM users WHERE id = 1 FOR UPDATE;
SELECT * FROM orders WHERE id = 2 FOR UPDATE;
UPDATE users SET ... WHERE id = 1;
UPDATE orders SET ... WHERE id = 2;
COMMIT;
```

### Deeper Explanation: Isolation Levels Are A Trade Of Correctness For Throughput

Transactions give atomicity, consistency, isolation, and durability â€” and the *isolation* part is where the trade-offs live. Under Read Committed (Postgres default) you can see non-repeatable reads; Repeatable Read gives snapshot isolation but can throw serialization failures under Serializable. The design rule: pick the weakest isolation that is still correct for your invariant, and handle the retry path explicitly.

Patterns worth knowing:

- **Optimistic concurrency** â€” a `version` column with `UPDATE ... WHERE id = $1 AND version = $2`; zero rows updated means a conflict.
- **Idempotent writes** â€” an idempotency key with a unique constraint, so retries are safe.
- **Locking order discipline** â€” always lock rows in the same order to avoid deadlocks.
- **Outbox pattern** â€” write the event row in the same transaction as the state change, then publish asynchronously.

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = $1 AND balance >= 100;
  UPDATE accounts SET balance = balance + 100 WHERE id = $2;
  INSERT INTO outbox (id, type, payload) VALUES ($3, 'transfer.completed', $4);
COMMIT;
```

### Additional Pitfalls
- **Long transactions holding locks.** They block writers and vacuum; keep external calls outside them.
- **Read-modify-write without a version check.** Lost updates under concurrency.
- **Retry loops without idempotency.** The client's retry duplicates the effect.
- **Deadlocks from inconsistent lock order.** Standardise the order or take a single lock.
- **Assuming `SERIALIZABLE` is free.** It requires retry handling; budget for it.

### Real-World Deal-Breakers
- **Long-running transactions** → block vacuum, cause bloat, increase lock contention. Keep transactions short.
- **No deadlock handling** → the application crashes on deadlock. PostgreSQL automatically detects and aborts one transaction. The application must retry.
- **Serializable everywhere** → 10× throughput reduction. Use Read Committed by default.
- **No retry logic** → deadlocks and serialization failures require retries. Implement exponential backoff.
- **Holding transactions open during network calls** → the connection is blocked, the transaction holds locks, and bloat grows.
