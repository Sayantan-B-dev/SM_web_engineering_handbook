## 35.4 Indexes

### Subtopic Tree
- B-tree (default, equality + range)
- Hash (equality only)
- GIN (arrays, JSONB, full-text search)
- GiST (geometric, full-text)
- SP-GiST (space-partitioned)
- BRIN (block range, large ordered tables)
- Partial indexes (WHERE clause)
- Covering indexes (INCLUDE)
- Composite indexes (column order matters)
- Index-only scans
- Index bloat and maintenance
- When NOT to index

### PostgreSQL Index Types

| Index Type | Best for | Performance | Storage |
|-----------|----------|-------------|---------|
| **B-tree** | Equality, range, ORDER BY | O(log n) | Moderate |
| **Hash** | Equality only | O(1) | Smaller for long values |
| **GIN** | Arrays, JSONB, full-text | Fast lookup, slow update | Large |
| **GiST** | Geometric, full-text, multi-dimensional | O(log n) | Moderate |
| **BRIN** | Very large tables with natural ordering | O(n) worst case | Very small |
| **SP-GiST** | Space-partitioned data | Depends on data | Moderate |

B-tree is the default for most data types and is best for equality and range queries. GIN is faster for lookups but slower on updates. Hash indexes are optimized for equality comparisons only and can be smaller than B-tree for longer values.

### The Impact of Indexing (2026 Benchmark)

A study on PostgreSQL 18.0 with 500,000 records measured the performance impact of three indexing strategies:

| Index Type | Retrieval Improvement | Update Improvement | Deletion Improvement |
|-----------|----------------------|-------------------|---------------------|
| **Simple index** | 96.5% | 98.0% | 51.4% |
| **Composite index** | 96.3% | 98.7% | 60.3% |
| **Text index** | 98.8% | 99.9% | - |

Deletion operations showed more moderate gains, attributed to **index maintenance overhead**.

### Composite Index Column Order
```sql
-- Query: WHERE status = 'active' AND created_at > '2026-01-01'
-- ✅ Correct order: equality column first, range column second
CREATE INDEX idx_posts_status_created ON posts (status, created_at DESC);

-- ❌ Wrong order: range column first prevents equality optimization
CREATE INDEX idx_posts_created_status ON posts (created_at DESC, status);
```

**Rule**: Equality columns first, range columns last. The index can only use columns up to the first range condition.

### Partial Indexes
```sql
-- Only index active posts (smaller, faster)
CREATE INDEX idx_posts_active ON posts (created_at DESC)
WHERE deleted_at IS NULL;

-- Only index unverified users
CREATE INDEX idx_users_unverified ON users (created_at)
WHERE verified = false;
```
Partial indexes are smaller and faster because they exclude rows that don't match the WHERE clause.

### Covering Indexes (Index-Only Scans)
```sql
-- Include additional columns to enable index-only scans
CREATE INDEX idx_posts_author_covering ON posts (author_id)
INCLUDE (title, created_at);

-- This query can be satisfied entirely from the index (no table access)
SELECT title, created_at FROM posts WHERE author_id = '...';
```

### BRIN for Large Ordered Tables
```sql
-- BRIN is tiny compared to B-tree - perfect for append-only tables
CREATE INDEX idx_events_created_brin ON events USING brin (created_at);
```
BRIN stores min/max values per block range. For a table with 1 billion rows, a B-tree index might be 20GB; a BRIN index is ~100KB.

### When NOT to Index
- **Small tables** (< 1000 rows) → sequential scan is faster.
- **Low-cardinality columns** (boolean, status with 3 values) → index doesn't help.
- **Write-heavy tables** → every index slows down INSERT/UPDATE/DELETE.
- **Columns never used in WHERE/ORDER BY/JOIN** → wasted storage and write overhead.

---

### Deeper Explanation: An Index Is A Rewrite Of The Query Planner's Options

An index accelerates a specific access pattern; it does nothing for others. The mental model that prevents wasted indexes: for a query `WHERE a = ? AND b = ? ORDER BY c`, a composite B-tree on `(a, b, c)` can satisfy filter and order together (leftmost-prefix rules apply), while separate single-column indexes force bitmap combinations and a sort.

Signals you need an index: `EXPLAIN ANALYZE` showing sequential scans on large tables, a filter on a foreign key, or a hot `ORDER BY`. Signals you have too many: slow writes, storage bloat, and a plan that never uses a third of them. Partial and covering indexes are the two underused tools: `WHERE deleted_at IS NULL` shrinks the index; `INCLUDE (title)` avoids a heap fetch.

### Additional Pitfalls
- **Indexing every column "just in case".** Writes slow down and the planner may ignore them.
- **Wrong column order in a composite index.** The leftmost prefix rule decides whether it is used at all.
- **Missing index on a foreign key.** Deletes and joins scan; cascades become slow.
- **Functional predicates without functional indexes.** `LOWER(email) = $1` needs an index on `LOWER(email)`.
- **Ignoring index-only scans.** Adding `INCLUDE` columns avoids table lookups on hot reads.

### Real-World Deal-Breakers
- **No index on foreign keys** → JOINs do full table scans.
- **Wrong column order in composite index** → index is unusable for the query.
- **Over-indexing** → every index adds write overhead. "Index less than your instincts tell you".
- **No index maintenance** → bloat degrades performance. Use `REINDEX CONCURRENTLY` periodically.
- **Missing index for ORDER BY** → PostgreSQL sorts in memory (or disk). Add an index matching the sort order.
