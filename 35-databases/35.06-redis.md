### Caching Patterns

**Cache-aside (lazy loading)**
```typescript
async function getUser(id: string) {
  // 1. Try cache first
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  // 2. Cache miss → fetch from database
  const user = await db.user.findUnique({ where: { id } });

  // 3. Write to cache with TTL
  await redis.setex(`user:${id}`, 3600, JSON.stringify(user)); // 1 hour TTL

  return user;
}
```

**Write-through**
```typescript
async function updateUser(id: string, data: Partial<User>) {
  const user = await db.user.update({ where: { id }, data });
  await redis.setex(`user:${id}`, 3600, JSON.stringify(user));
  return user;
}
```

### TTL Strategy

| Data Type | TTL | Rationale |
|-----------|-----|-----------|
| User sessions | 7 days | Session expiry |
| Weather data | 5-10 minutes | Changes frequently |
| Destination data | 1 hour | Changes occasionally |
| Policy configurations | 24 hours | Changes rarely |
| Feature flags | 5 minutes | Fast propagation |

A layered caching strategy with Redis/memory cache: Weather data (5-10 min TTL), Destination data (1 hour TTL), Policy configurations (24 hour TTL).

### Rate Limiting with Redis
```typescript
async function rateLimit(userId: string, limit: number, windowSec: number) {
  const key = `ratelimit:${userId}`;
  const current = await redis.incr(key);

  if (current === 1) {
    await redis.expire(key, windowSec);
  }

  return current <= limit;
}
```

### Deeper Explanation: A Data-Structure Server, Not Just A Cache

Redis is an in-memory store with rich data structures (strings, hashes, lists, sets, sorted sets, streams, HyperLogLog, bitmap), which makes it more than a cache: rate limiters, leaderboards, queues, presence, session stores, and pub/sub all map onto its primitives. The engineering discipline is deciding **what is allowed to be lost** â€” a cache may be evicted at any time, a rate-limit counter resets acceptably, and a Pub/Sub message is gone if nobody was subscribed.

For frontend-relevant features: sorted sets for leaderboards and feeds, `INCR` with `EXPIRE` for rate limits, `SET NX PX` for locks, presence sets with TTL, and streams for lightweight job queues. Persistence options (RDB snapshots, AOF) determine restart behaviour; a cache should not depend on them.

### Additional Pitfalls
- **Treating Redis as durable storage.** Eviction policies and memory limits will surprise you.
- **Pub/Sub for critical messages.** It is fire-and-forget; use streams or a real queue.
- **Locks without expiry.** A crashed holder blocks everyone; always set a TTL and a fencing token.
- **Cache keys without versioning.** A shape change serves stale, wrong values; namespace and version keys.
- **No memory policy.** Set `maxmemory-policy` deliberately (allkeys-lru vs noeviction) or OOM becomes a read failure.

### Real-World Deal-Breakers
- **No TTL** → cache grows forever, memory exhausted, eviction of critical data.
- **No cache invalidation** → stale data served indefinitely.
- **No connection pooling** → Redis connection per request is expensive. Use ioredis or node-redis with pooling.
- **Using Redis as a database** → Redis is a cache. Data can be evicted. Always have a durable store.
- **No memory monitoring** → Redis can OOM. Set `maxmemory` and `maxmemory-policy`.
