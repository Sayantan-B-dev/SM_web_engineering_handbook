### The Four NoSQL Models

| Model | Database | Best for | Data shape |
|-------|----------|----------|-----------|
| **Document** | MongoDB, Couchbase | Flexible schema, content management | JSON-like documents |
| **Key-Value** | DynamoDB, Redis | Session, cache, simple lookups | Key → value |
| **Wide-Column** | Cassandra, ScyllaDB | High write throughput, time-series | Row → column families |
| **Graph** | Neo4j, Amazon Neptune | Relationships, social networks | Nodes + edges |

### When NoSQL Wins
- **Unstructured data** → NoSQL databases are designed to handle unstructured data and scale horizontally.
- **Horizontal write scale** → NoSQL databases give you horizontal write scale.
- **Flexible schema** → a new field ships with the save, no migration ceremony.
- **High write throughput** → ScyllaDB/Cassandra achieve 1M+ writes/sec per node with append-only architecture.

### When SQL Wins
- **Transaction integrity** → SQL databases enforce ACID, ideal for scenarios where data accuracy and transaction integrity are crucial.
- **Complex queries** → joins, aggregations, window functions.
- **Ad-hoc queries** → you don't know the query patterns in advance.
- **Data integrity** → foreign keys, unique constraints, check constraints.

### The 2026 Convergence
The honest 2026 answer is that **both camps have adopted each other's best tricks** - JSON in SQL, ACID in NoSQL, distributed SQL.

| SQL (2026) | NoSQL (2026) |
|------------|--------------|
| JSONB columns for document data | Multi-document ACID transactions (MongoDB) |
| Full-text search built-in | SQL-like query languages (CQL, N1QL) |
| Vector search (pgvector) | Distributed SQL (CockroachDB, YugabyteDB) |
| Horizontal scaling (Citus) | Schema validation (MongoDB) |

### Deeper Explanation: Access Patterns First, Then The Store

NoSQL databases (document, key-value, wide-column, graph, search) trade joins and strong schemas for scale, flexibility, and availability â€” and the price is that **your access patterns become the schema**. In a document store you design documents around the queries you will run, because joins are expensive and cross-document consistency is manual.

The honest decision guide for a React product: use Postgres until a specific pain appears (full-text relevance at scale, massive write throughput, geo-distributed multi-region writes, graph traversal). Then choose the store for that pain and accept the operational cost of a second system â€” including the consistency boundary between them (the outbox/CDC pattern).

### Additional Pitfalls
- **Documents designed like tables.** Many small documents plus per-document reads recreate the N+1 problem.
- **No transactional boundary.** Multi-document updates are not atomic in many stores; design invariants accordingly.
- **Assuming "schemaless" means no validation.** Enforce shape at the application boundary, ideally with schemas.
- **Second store without a sync strategy.** Dual writes drift; use CDC or an outbox.
- **Ignoring query cost in a search engine.** Deep pagination and expensive aggregations are still expensive.

### Real-World Deal-Breakers
- **Choosing NoSQL for ACID-critical data** → financial transactions need ACID. Use SQL.
- **Choosing SQL for extreme write throughput** → 1M+ writes/sec needs wide-column (ScyllaDB, Cassandra).
- **No schema at all** → "No schema" is a myth. NoSQL databases have schema - it's just enforced by the application, not the database.
- **No query patterns known upfront** → if you don't know how you'll query the data, SQL is safer.
