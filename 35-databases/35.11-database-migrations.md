### Zero-Downtime Migration Pattern
```sql
-- Phase 1: Add new column (nullable, no default)
ALTER TABLE users ADD COLUMN email_verified boolean;

-- Phase 2: Backfill in batches (not a single UPDATE)
UPDATE users SET email_verified = false WHERE email_verified IS NULL AND id IN (
  SELECT id FROM users WHERE email_verified IS NULL LIMIT 10000
);
-- Repeat until all rows are backfilled

-- Phase 3: Deploy code that reads/writes both columns
-- Phase 4: Add NOT NULL constraint (after backfill)
ALTER TABLE users ALTER COLUMN email_verified SET NOT NULL;
ALTER TABLE users ALTER COLUMN email_verified SET DEFAULT false;
```

### Migration Locking
```sql
-- Prevent concurrent migrations
SELECT pg_advisory_lock(12345);
-- ... run migration ...
SELECT pg_advisory_unlock(12345);
```

---

### Deeper Explanation: Migrations Are Deploys With A Rollback Problem

A migration changes a live system's state, and unlike code it usually cannot be reverted cheaply. That is why the safe pattern is **expand, migrate, contract**: add the new structure (nullable column, new table, dual write), backfill and verify, switch reads, then remove the old structure in a later deploy. Each step is independently deployable and reversible.

Practical rules:

- **One migration per change, versioned in the repository**, applied identically in every environment by the pipeline (never by hand).
- **Additive first.** Dropping or renaming a column is a separate, later migration after no code references it.
- **Backfill in batches** with throttling, not one giant `UPDATE`.
- **Indexes created concurrently** (`CREATE INDEX CONCURRENTLY`) to avoid long write locks on large tables.
- **Rollback rehearsed** for destructive steps, with a tested restore path as the fallback.
- **Migrations are code-reviewed** like application changes; they carry the same risk and more.

### Additional Pitfalls
- **Destructive migrations shipped with the feature.** The old client is still deployed and breaks instantly.
- **Long locks on big tables.** Adding a column with a default, or a non-concurrent index, can lock writes for minutes.
- **Manual "quick fixes" in production.** They break environment parity and are invisible to the next deploy.
- **No schema version in the database.** You cannot tell what state an environment is in.
- **Backfills without throttling.** They saturate the database during business hours.

### Real-World Deal-Breakers
- **Single massive migration** → `ALTER TABLE` with `ACCESS EXCLUSIVE` lock blocks all reads/writes for minutes.
- **No backfill strategy** → `UPDATE users SET ...` on a 10M row table locks the table.
- **No rollback plan** → a failed migration leaves the database in an inconsistent state.
- **No migration testing** → migrations run for the first time in production.
- **No advisory lock** → concurrent migrations from multiple instances cause corruption.
