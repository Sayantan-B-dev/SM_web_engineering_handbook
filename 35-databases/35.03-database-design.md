## 35.3 Database Design

### Subtopic Tree
- Normalization (1NF, 2NF, 3NF, BCNF)
- Denormalization for read performance
- Primary key selection (auto-increment vs UUID vs UUIDv7 vs ULID)
- Foreign keys and referential integrity
- Junction tables (many-to-many)
- Soft deletes vs hard deletes
- Timestamps (created_at, updated_at)
- Schema migrations (zero-downtime)
- Multi-tenancy patterns

### The Normalization vs Denormalization Trade-off

| Normalization (3NF) | Denormalization |
|---------------------|-----------------|
| Each fact stored once | Data duplicated |
| No update anomalies | Write amplification |
| Joins required at read time | Reads avoid joins |
| Cost concentrated at read time | Cost shifted to write time |

**The rule: start normalized, denormalize only when a specific query is measurably too slow**.

### Primary Key Selection

| Type | When to use | Trade-off |
|------|-------------|-----------|
| **Auto-increment** (bigserial) | Internal-only IDs, single-database systems | Not globally unique; reveals count |
| **UUIDv4** | Distributed systems, public IDs | Random - poor B-tree locality |
| **UUIDv7** (time-ordered) | Distributed systems, public IDs | Time-ordered - good B-tree locality |
| **ULID** | Distributed systems | Lexicographically sortable |

Use **UUIDv7** (time-ordered) for distributed systems or publicly exposed IDs. Use auto-increment for internal-only IDs in single-database systems.

### The Users / Organizations / Memberships Pattern
```sql
CREATE TABLE users (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email text UNIQUE NOT NULL,
  password_hash text NOT NULL,
  name text NOT NULL,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

CREATE TABLE organizations (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL,
  billing_email text,
  created_at timestamptz DEFAULT now()
);

-- Junction table with context
CREATE TABLE organization_members (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid REFERENCES users(id) ON DELETE CASCADE,
  organization_id uuid REFERENCES organizations(id) ON DELETE CASCADE,
  role text NOT NULL DEFAULT 'member', -- 'admin', 'member', 'viewer'
  joined_at timestamptz DEFAULT now(),
  status text DEFAULT 'active', -- 'pending', 'active', 'suspended'
  UNIQUE (user_id, organization_id)
);
```

**The most common mistake**: adding `organization_id` directly to the `users` table. This creates a "multi-tenant trap" where a user can only belong to one organization. Use a junction table so a user can belong to multiple organizations with different roles.

### Timestamps - The Non-Negotiable Rule
```sql
-- ✅ ALWAYS use TIMESTAMPTZ, never TIMESTAMP
created_at timestamptz DEFAULT now(),
updated_at timestamptz DEFAULT now()
```
`TIMESTAMPTZ` stores timezone information. `TIMESTAMP` does not - it's a bug waiting to happen.

### Soft Deletes
```sql
-- Add deleted_at column
ALTER TABLE posts ADD COLUMN deleted_at timestamptz;

-- Query only active records
SELECT * FROM posts WHERE deleted_at IS NULL;

-- Create a partial index for active records only
CREATE INDEX idx_posts_active ON posts (created_at DESC) WHERE deleted_at IS NULL;
```

**Trade-off**: Soft deletes preserve referential integrity but require every query to filter `deleted_at IS NULL`. Use RLS or views to enforce this.

### Zero-Downtime Migrations (Expand-Contract Pattern)
```sql
-- Phase 1: Add new column (backward compatible)
ALTER TABLE users ADD COLUMN full_name text;

-- Phase 2: Backfill data
UPDATE users SET full_name = first_name || ' ' || last_name;

-- Phase 3: Deploy code that writes to both columns
-- Phase 4: Deploy code that reads from new column
-- Phase 5: Drop old columns
ALTER TABLE users DROP COLUMN first_name;
ALTER TABLE users DROP COLUMN last_name;
```

### Deeper Explanation: Model For The Queries You Will Run

Schema design is a conversation between correctness and access patterns. Normalise to remove duplication and update anomalies, then denormalise deliberately where a hot read path demands it (maintained counters, materialised views, or duplicated display fields with an explicit sync rule).

Practical rules for product schemas:

- **Stable identifiers everywhere** (`uuid` or `bigint` + a public id) â€” the client needs them for keys, caching, and optimistic updates.
- **Timestamps with meaning**: `created_at`, `updated_at`, and (if soft deletes) `deleted_at`, all `timestamptz`.
- **Explicit tenancy**: `tenant_id` on every row that belongs to a tenant, plus indexes that start with it.
- **Constraints as documentation**: `NOT NULL`, `CHECK`, foreign keys, and unique indexes encode invariants the application cannot be trusted to enforce alone.
- **Soft vs hard deletes decided once**, with the retention and privacy implications written down.

### Additional Pitfalls
- **No `tenant_id` on a multi-tenant table.** Cross-tenant leaks start here.
- **UUIDv4 primary keys as clustered indexes.** Random inserts fragment B-trees; consider UUIDv7/ULID or bigint with a public id.
- **Money in floats.** Integers in minor units, always.
- **Nullable columns used as state.** Explicit status columns beat "IS NULL means cancelled".
- **No unique constraint where duplicates must not exist.** Application checks race; the database does not.

### Real-World Deal-Breakers
- **`TIMESTAMP` instead of `TIMESTAMPTZ`** → timezone bugs. Always use `TIMESTAMPTZ`.
- **No foreign keys** → orphaned records. Application code can't be trusted to maintain integrity.
- **Auto-increment for public IDs** → reveals record count and is guessable. Use UUIDv7.
- **No `created_at` / `updated_at`** → you can't debug when data changed. Add them to every table.
- **Direct `organization_id` on `users`** → multi-tenant trap. Use a junction table.
- **No soft delete strategy** → hard deletes break referential integrity and lose audit history.
- **Monolithic migrations** → `ALTER TABLE` with `ACCESS EXCLUSIVE` lock blocks all reads/writes. Use expand-contract.
