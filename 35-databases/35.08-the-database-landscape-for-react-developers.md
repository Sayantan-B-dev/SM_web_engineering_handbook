### The Core Mental Model
A React application touches databases at **three distinct layers**:

```text
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: Client-Side Database                               │
│  ├── SQLite WASM (in-browser)                                │
│  ├── TanStack DB (reactive client store)                     │
│  ├── IndexedDB (structured data)                             │
│  └── OPFS (large binary files)                               │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Caching Layer                                      │
│  ├── Redis (in-memory, sub-millisecond)                      │
│  ├── TanStack Query (client-side cache)                      │
│  └── CDN / Edge cache                                        │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Backend Database (Source of Truth)                 │
│  ├── PostgreSQL (relational, ACID, JSONB)                    │
│  ├── MySQL/MariaDB (relational)                              │
│  ├── MongoDB (document)                                      │
│  ├── DynamoDB (key-value, serverless)                        │
│  └── Cassandra/ScyllaDB (wide-column, high write)            │
└─────────────────────────────────────────────────────────────┘
```

### Deeper Explanation: The Four Decisions That Actually Matter

For a React application, database choice reduces to four decisions, in order of consequence:

1. **Where the data lives** (managed Postgres vs SQLite-on-the-edge vs a document store vs browser-local). This decides your consistency story and your failure modes.
2. **Access path** (direct from a server layer vs an ORM vs generated types). This decides how types flow to the client and how migrations are managed.
3. **Boundaries** (single database vs per-service; shared schema vs schema-per-tenant). This decides how the system evolves.
4. **Operational model** (managed with backups, or self-hosted). This decides who is paged at 3am.

The React-specific angle: the database shape shows up in the client as pagination contracts, cache invalidation, and optimistic updates. A schema without stable ids, `updatedAt`, and sensible list ordering makes every client feature harder.

### Additional Pitfalls
- **Choosing a database for the demo.** The first 1 000 users are easy on anything; the constraint appears at the join you cannot do.
- **No migrations tooling from day one.** Schema changes become manual and risky.
- **Client-side coupling to tables.** Expose a contract, not your schema; rename columns freely behind it.
- **Ignoring backups and restore drills.** An untested backup is a hope, not a plan.

### Real-World Deal-Breakers
- **Choosing a database by hype** → each database has a home game. PostgreSQL dominates OLTP; Redis dominates caching; ScyllaDB dominates extreme write throughput.
- **Ignoring connection pooling** → inefficient connection handling becomes the bottleneck, hindering the very performance your database is designed to provide.
- **Treating SQL vs NoSQL as a binary choice** → "SQL vs NoSQL" collapses two independent axes into one false dichotomy. Relational model (joins, ACID, ad-hoc queries) vs non-relational (key-value, document, wide-column, graph) is one axis; the other is single-node vs distributed.
- **No client-side database** → every read is a network round-trip. Local-first databases eliminate the loading spinner.
