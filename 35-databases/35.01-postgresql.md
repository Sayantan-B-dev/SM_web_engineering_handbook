### PostgreSQL 19 (2026) - What's New

PostgreSQL 19 contains many new features and enhancements including better performance in many areas, automatic scaling of the number of I/O worker processes, quicker foreign-key checks, and further planning and execution optimizations.

| Feature | What it does | Why it matters |
|---------|-------------|----------------|
| **REPACK CONCURRENTLY** | Reclaims disk space and reorganizes table contents without blocking reads/writes | Combines VACUUM FULL and CLUSTER; no downtime maintenance |
| **Logical replication of sequences** | Replicates sequence values; can be enabled without server restart | Simplifies failover and migration |
| **Parallel autovacuum** | Autovacuum uses parallel workers to vacuum a table's indexes | Faster vacuum on large tables; new scoring system prioritizes tables |
| **WAIT command** | Waits until a standby has replayed changes up to a chosen point | Enables "read-your-writes" on standbys |
| **pg_plan_advice** | Stabilizes and controls the query planner's decisions | Prevents plan regression |
| **pg_stash_advice** | Applies planner advice automatically based on the query | Automatic plan stabilization |
| **Quicker foreign-key checks** | Up to 2× better performance on inserts when FK checks are present | Major write performance improvement |
| **Async I/O** (PG 18) | Up to ~3× throughput in I/O-bound scenarios | Major read performance improvement |
| **Skip scan** (PG 18) | Supports skip scan for multicolumn B-tree indexes where leading column has no equality predicate | Dramatically reduces index scans |

### PostgreSQL as the Default
PostgreSQL dominates OLTP workloads. It provides relational integrity, ACID transactions, rich indexing (B-tree, Hash, GiST, SP-GiST, GIN, BRIN, bloom), JSONB for document data, full-text search, and an extension ecosystem (PostGIS for geospatial, pgvector for vector search, VectorChord for disk-efficient similarity search).

### JSONB - Document Data in a Relational Database
```sql
-- Create a table with a JSONB column
CREATE TABLE products (
  id bigserial PRIMARY KEY,
  name text NOT NULL,
  metadata jsonb DEFAULT '{}',
  created_at timestamptz DEFAULT now()
);

-- Index the JSONB column for fast queries
CREATE INDEX idx_products_metadata ON products USING gin (metadata);

-- Query nested JSON fields
SELECT name, metadata->>'brand' AS brand
FROM products
WHERE metadata @> '{"badges": ["new"]}';

-- Update a nested field
UPDATE products
SET metadata = jsonb_set(metadata, '{warranty, months}', '24')
WHERE id = 1;
```

PostgreSQL + JSONB is "the most overlooked optimal solution" - you get relational integrity AND document flexibility in one database.

### Row-Level Security (RLS)
```sql
-- Enable RLS on the table
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- Users can only see their own posts
CREATE POLICY user_posts_policy ON posts
  FOR ALL
  USING (author_id = current_setting('app.current_user_id')::uuid);

-- Admins can see all posts
CREATE POLICY admin_posts_policy ON posts
  FOR ALL
  USING (current_setting('app.current_role') = 'admin');
```

**RLS is the database-level authorization enforcement.** Application code changes frequently, but your data is permanent. RLS is the final line of defense.

### Deeper Explanation: Postgres As A Whole Application Backend

Postgres is not just a relational store; it is a platform: JSONB, full-text search, arrays, generated columns, materialised views, logical replication, extensions (pgvector, PostGIS, pg_trgm), row-level security, and `LISTEN/NOTIFY`. The practical consequence is that a React product can often run on Postgres alone far longer than teams expect â€” avoiding a search cluster, a cache, and a document store until they are genuinely needed.

Key operational knowledge: understand MVCC (why updates are cheap but bloat is real), `VACUUM`/autovacuum, connection limits and pooling (a serverless fleet will exhaust connections without a pooler), index types (B-tree, GIN for JSONB/arrays/full-text, GiST for ranges/geo, BRIN for large append-only tables), and `EXPLAIN ANALYZE` as the primary performance tool.

### Additional Pitfalls
- **One connection per serverless invocation.** Use a pooler (PgBouncer, RDS Proxy, Neon/Supabase pooler) or you will hit `too many connections`.
- **`SELECT *` in production paths.** It breaks on schema change and pulls large columns unnecessarily.
- **Long-running transactions.** They block vacuum and cause bloat; keep transactions short.
- **JSONB for everything.** Relational modelling with constraints beats a document blob for data you query.
- **No statement timeout.** A runaway query can exhaust the database for everyone.

### Real-World Deal-Breakers
- **No connection pooling** → PostgreSQL has a hard connection limit. Each connection consumes ~10MB RAM. Without PgBouncer or Pgpool-II, you'll hit the limit at scale.
- **No RLS for multi-tenant apps** → application-level authorization is bypassable. RLS enforces at the database level.
- **No JSONB index** → querying JSONB without a GIN index does a full table scan.
- **Forgetting VACUUM** → dead tuples accumulate, bloat grows, performance degrades. Autovacuum handles this, but monitor it.
- **No pg_plan_advice** → a single bad query plan can tank performance. Use pg_plan_advice to stabilize plans.
