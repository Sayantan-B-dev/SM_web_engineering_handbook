### The Connection Problem
Inefficient connection handling can become a bottleneck, **hindering the very performance and scalability the database is designed to provide**. PostgreSQL creates a new process for every connection. Each connection consumes ~10MB of RAM. A database with 1000 connections consumes ~10GB of RAM just for connections.

### PgBouncer
PgBouncer is the standard connection pooler for PostgreSQL. It sits between your application and the database, maintaining a pool of persistent connections and multiplexing thousands of client connections over a few database connections.

```ini
; pgbouncer.ini
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
listen_port = 6432
pool_mode = transaction      ; transaction pooling (recommended)
max_client_conn = 1000       ; max client connections
default_pool_size = 20       ; connections to PostgreSQL per user/database
min_pool_size = 5
reserve_pool_size = 5
reserve_pool_timeout = 5
```

**Pool modes:**
- **Session mode** - one connection per client session (safe, less efficient)
- **Transaction mode** - one connection per transaction (recommended, most efficient)
- **Statement mode** - one connection per statement (not for transactions)

### Connection Limit Math
```text
PostgreSQL max_connections = 100
Each connection = ~10MB RAM
Total RAM for connections = 1GB

With PgBouncer:
  1000 client connections → 20 database connections
  RAM for connections = 200MB
  Savings = 800MB
```

### Google AlloyDB Managed Connection Pooling
Google Cloud has made managed connection pooling generally available for AlloyDB for PostgreSQL, bringing PgBouncer-like functionality directly into the database service. The feature delivers **3× more client connections and up to 5× higher transactional throughput** than direct connections.

### Deeper Explanation: Connections Are A Finite, Expensive Resource

Every Postgres connection is a process on the server with memory overhead; a few hundred will exhaust a small instance. Pooling solves the mismatch between many short-lived application requests and few long-lived database connections. The subtleties appear in three configurations:

- **Long-running servers** â€” one pool per process, sized roughly `(cores Ã- 2) + effective spindles`, plus a queue with a timeout so overload fails fast rather than piling up.
- **Serverless/edge** â€” each invocation may create a connection; use an external pooler (PgBouncer in transaction mode, RDS Proxy, Neon/Supabase poolers) and beware transaction-mode limitations (no session-level state, no prepared statements in some modes).
- **Client-side** â€” the browser never connects to the database; all access goes through your API. Any "direct database from the frontend" pattern is a breach waiting to happen.

Also set `statement_timeout`, `idle_in_transaction_session_timeout`, and connection lifetime limits; leaked idle transactions are the most common cause of database-wide slowdowns.

### Additional Pitfalls
- **A pool per request.** The pool must be a singleton for the process.
- **Unbounded pool size.** It moves the bottleneck to the database and can take down other services.
- **Transaction-mode pooler with session features.** Advisory locks, `SET` sessions, and some prepared statements break.
- **No acquire timeout.** Requests hang instead of failing fast when the pool is saturated.
- **Idle-in-transaction connections.** They hold locks and block vacuum; set a server-side timeout.

### Real-World Deal-Breakers
- **No connection pooling** → connection limit hit at scale, "too many clients" errors.
- **Session mode instead of transaction mode** → fewer connections saved. Use transaction mode.
- **Pool size too large** → database overwhelmed. Start with 20 connections and scale up.
- **No pool monitoring** → you don't know if the pool is exhausted. Monitor `pgbouncer SHOW POOLS`.
